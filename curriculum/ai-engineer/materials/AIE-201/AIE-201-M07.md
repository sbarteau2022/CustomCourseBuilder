## Module overview

Every module before this one handed you data that was already numeric, already complete, already
one column per feature. That was never how tabular data actually arrives. A real table has a `region`
column with string values, an `income` column with 30% of its rows blank for reasons that are not
random, and a true relationship between two columns that neither column reveals on its own. **Feature
engineering — encoding, imputing, and constructing the features a model is actually fit on — is the
work that turns a messy table into the clean matrix every prior module quietly assumed you already
had**, and it is also where most of the leakage risk in a real ML pipeline actually lives, because
feature engineering is preprocessing that is unusually easy to get backwards without anything
crashing.

This module makes three claims, each earned with numbers, not received wisdom:

1. **Target encoding is a leakage risk with its own signature, distinct from what M05 taught.** A
   `StandardScaler` fit on the wrong rows leaks a little, because it estimates two numbers per
   feature. A target encoder estimates a number **per category, directly from the label** — and at
   real-world cardinality (dozens to hundreds of categories, modest rows per category), that is enough
   estimated parameters to memorize noise. Lesson 1 reproduces M05's exact discipline (split first,
   fit only on train) against a technique built specifically to break it if you don't.
2. **`dropna()` is not "handling" missing data — it is a policy decision with a population you never
   examined.** Lesson 2 builds the honest alternative: understand *why* a value is missing before
   deciding what to do about it, because the answer changes the model, and sometimes the fact that a
   value is missing is the single most informative thing about that row.
3. **Well-engineered features on a gradient-boosted tree still beat a neural network on realistic
   tabular data, and this course will make you prove it, not take the field's word for it.** Lesson 4
   builds both feature sets and both model families and reports what actually happens — a real,
   re-runnable benchmark, matched against the published finding (Grinsztajn et al., 2022;
   Shwartz-Ziv & Armon, 2022) that this course states as fact because the evidence, including the
   evidence you will generate yourself in Lab 3, supports it.

The descent: watch a target-encoded feature turn a coin-flip categorical into an implausibly strong
predictor, purely from split-order and cardinality (Lesson 1); watch `dropna` silently discard a
third of a deployment population while a naive mean-impute *loses to the majority-class baseline*
and a two-line missingness indicator wins back the signal both of them threw away (Lesson 2); watch
a linear model score *below chance* on a feature pair whose interaction is the entire signal, until
one multiplication fixes it — the exact multiplication a tree finds for free (Lesson 3); and close
by building the realistic, multi-technique feature pipeline this module has been assembling piece by
piece, feeding it into both a gradient-boosted tree and a small neural network, and reporting,
honestly, which one wins and why (Lesson 4). Re-ascent: you can look at a raw tabular dataset and
name, before writing a line of model code, which columns need target encoding (and how you'll keep
it honest), which missing values are actually informative, which pairs of features probably interact,
and why the answer to "should I reach for a neural net" is usually no — with a benchmark you ran
yourself as the evidence, not a blog post's opinion.

## Lessons

### Lesson 1 — Encoding categoricals: one-hot, ordinal, and target encoding's leakage risk

**Teaching text**

A categorical column has to become numbers before any model in this course can touch it. Three
encodings, three different costs:

- **One-hot encoding.** One binary column per category. Safe — it estimates nothing from the data,
  so it cannot leak — but its width grows with cardinality: a `zip_code` column with 8,000 distinct
  values becomes 8,000 sparse columns, most of which a tree will rarely split on and a linear model
  will barely have data to fit a coefficient for.
- **Ordinal (label) encoding.** One integer per category, e.g. `bronze=0, silver=1, gold=2`. Compact,
  and *correct* when the categories really are ordered — but assigning arbitrary integers to a
  **nominal** category (`region`, `product_sku`) invents a fake numeric order (`region_7 > region_3`)
  that a linear model will treat as meaningful and even a tree will spend extra splits working
  around.
- **Target (mean) encoding.** Replace each category with a statistic of the label within that
  category — most commonly `mean(y | category)`. This is the encoding of choice for high-cardinality
  nominal features precisely because it sidesteps one-hot's width problem: `region` becomes **one**
  numeric column, not eight, and that column already carries the category's empirical relationship
  to the outcome.

Target encoding is also the one of the three that can leak, and it leaks in a way M05's scaler
example did not, for a specific reason: **a `StandardScaler` estimates two numbers per feature from
the rows it's fit on (mean, std) — a target encoder estimates one number *per category*, and that
number is computed directly from the label**. The failure mode M05 taught — fit the transform on
the full dataset, including rows that will later be called "test" — applies here exactly as it did
to scaling. But the size of the resulting leak is not "small and inconsistent in direction," M05
Lesson 3's finding for a two-parameter scaler; it depends on how many rows back each category's
estimate, and at realistic cardinality that count can be small enough for the encoding to
memorize individual rows' labels rather than estimate a genuine population rate.

**Order of operations, stated precisely, the way M05 stated `fit_only_on_train`:** compute
`category → mean(y)` using **only** the rows in the current training fold, apply that fixed mapping
to every other row (validation, test, or a later production request) — never re-estimate it, never
let a row's own label influence its own encoded value.

**Worked example — pure-noise categories, three cardinalities**

Construct a categorical feature with **zero true relationship to the label, by construction** —
exactly M05 Lesson 3's pure-noise feature-selection setup, now applied to target encoding. `n=2,000`
rows, a binary `y ~ Bernoulli(0.5)` unrelated to `category` by construction, 70/30 split
(`rng = np.random.default_rng(301)`). Compare a **leaky** encoding (the category→mean(y) map is
fit on the full 2,000 rows, train and test together, before the split) against an **honest**
encoding (the map is fit on the 1,400 training rows only, and — because a training row encoded
using a map that includes its own label is still a subtler, milder form of the same problem — each
training row's own encoded value comes from a 5-fold **out-of-fold** map that never includes that
row):

| Categories | Avg. rows/category | Leaky acc | Leaky AUC | Honest (OOF) acc | Honest (OOF) AUC | Majority baseline |
|---|---:|---:|---:|---:|---:|---:|
| 100 | 20 | **0.590** | **0.613** | 0.517 | 0.504 | 0.517 |
| 20 | 100 | 0.518 | 0.546 | 0.517 | 0.508 | 0.517 |
| 5 | 400 | 0.517 | 0.535 | 0.517 | 0.499 | 0.517 |

Two things to read off this table together. First, at 20 rows per category the leaky encoding turns
**pure noise** into an AUC of 0.613 — a category with no true relationship to the label looks, after
leaky encoding, like a real, moderately informative feature, purely because with only 20 rows backing
each category's estimate, a category's mean(y) is a noisy small-sample statistic that happens to
correlate with the very rows used to compute it. Second, the honest (out-of-fold) column lands within
noise of the majority baseline at **every** cardinality — because the underlying relationship really
is nothing, and a correctly-built encoding correctly reports nothing. Third, the leak **shrinks as
rows-per-category grows** — at 400 rows per category the leaky number (0.535 AUC) is barely
distinguishable from honest (0.499) — for the identical mechanical reason M05 Lesson 3 found scaling
leakage shrinking with `n`: two rough estimates of the same underlying rate converge as the sample
backing each estimate grows. **High-cardinality categoricals with thin per-category counts are
exactly the target-encoding leakage danger zone**, and it is also exactly the situation target
encoding exists to handle (that's the entire reason to prefer it over one-hot) — the technique is
most tempting precisely where it is most dangerous.

**Named misconceptions**

- **"I split before encoding, so target encoding is safe here."** Splitting before fitting the
  encoder is necessary and not sufficient — a map fit on the full training fold and then applied
  *to that same training fold* still lets each row's encoded value be partly informed by its own
  label, which is why the honest pipeline above uses out-of-fold encoding for training rows, not
  just a train/test split.
- **"Target encoding and one-hot encoding carry the same kind of risk — one's just more compact."**
  A `StandardScaler` and a one-hot encoder never look at `y`; a target encoder's entire output is a
  function of `y`. That is a difference in kind, not degree, and it is why target encoding gets its
  own lesson instead of being folded into M05's "preprocessing leakage" as one more example.
- **"A feature that isn't leaky at high cardinality will scale down safely to low cardinality, or
  vice versa."** The table shows the *same* mechanism — leaky vs. honest — producing a real,
  measurable gap at 100 categories and almost none at 5; cardinality is not a detail, it is the
  variable that determines whether this specific leak matters.
- **"Out-of-fold encoding is extra machinery for a problem that a train/test split already
  solves."** The train/test split alone stops test-set leakage; it does nothing about a training
  row's encoded feature partly reflecting its own label during *fitting* — a distinct, milder leak
  that OOF encoding exists specifically to close.

### Lesson 2 — Missing data, honestly: mechanisms, and what `dropna` destroys

**Teaching text**

Real tabular data has holes, and the reflex — `df.dropna()` — is a policy decision dressed up as a
cleanup step. Before choosing what to do about a missing value, name **why** it's missing, because
the honest answer changes the model:

- **MCAR (missing completely at random).** The missingness has nothing to do with anything — a
  sensor occasionally drops a reading for reasons unrelated to the reading's value or any other
  variable. Dropping these rows costs you sample size and nothing else.
- **MAR (missing at random, conditional on something observed).** The missingness depends on another
  *observed* variable but not, once you condition on that variable, on the missing value itself
  (e.g., a field is skipped more often on a particular form version, and you know which form version
  each row used). Recoverable by conditioning on the observed variable.
- **MNAR (missing not at random).** The missingness depends on the value that's missing, or on
  something correlated with it, that you did *not* observe. A person is more likely to leave an
  income field blank *because* their income is low. This is the dangerous case, and it is also the
  common case in real tabular data — application forms, medical intake, survey non-response.

`dropna()` treats every one of these the same way: delete the row. That is a defensible choice under
MCAR. Under MNAR it is not cleanup, it is **silently changing which population you're modeling** —
the rows you kept are systematically different from the rows you dropped, in exactly the dimension
that made them go missing in the first place. And it has a second cost that has nothing to do with
statistics: a model trained on complete cases cannot score a real, incoming row with a missing field
at all without some fallback — `dropna` in production means "refuse to serve this customer," not
"clean the data."

**The honest alternative has two parts.** First, impute — fill the missing value with something
reasonable (a mean, a median, a model-based estimate), fit **only on the training data**, exactly
M05's clause-1 discipline applied to a new transform. Second, and this is the part `dropna` and naive
imputation both throw away: if the missingness itself is informative (MNAR), add a **missingness
indicator** — a binary column that is `1` exactly where the value was missing — so the model can use
the fact of absence as a feature in its own right, separately from whatever placeholder value you
imputed.

**Worked example — informative missingness in a loan application**

`n=3,000` applicants (`rng = np.random.default_rng(303)`), credit score and debt ratio drive default
risk as usual, and income is MNAR: applicants ranked in the bottom income quartile leave the income
field blank **47.5%** of the time; applicants in the top quartile, **8.3%** of the time (an overall
29.0% missing rate). Critically, the *act* of leaving income blank also carries real, independent
risk information in this population beyond what income itself would say — applicants who omit income
default at **35.1%**, applicants who report it default at **15.0%** (`corr(is_missing, default) =
0.224`). Compare four strategies, 70/30 split (`random_state=11`, stratified):

| Strategy | Test accuracy | Test AUC | Applicants it can score |
|---|---:|---:|---:|
| Oracle (true income, never missing, + missingness flag) | 0.800 | **0.737** | 100% |
| `dropna` (complete cases only) | 0.854 | 0.711 | **69.8%** |
| Mean-impute, **no** indicator | **0.792** | 0.653 | 100% |
| Mean-impute **+ indicator** | 0.798 | **0.733** | 100% |

Read every column, not just accuracy. `dropna`'s 0.854 accuracy looks like the best number on the
table — until you notice it was computed on the 69.8% of test applicants who happened to report
income, a population that is, by construction, less likely to be the risky, income-withholding
segment; **it cannot score the other 30.2% of applicants at all**, and the number it does report
describes an easier, self-selected subpopulation, not the population the model will actually meet in
production. Mean-impute with no indicator scores every applicant, but its accuracy (0.792) lands
**exactly on the majority-class baseline** — the model has, in effect, learned nothing usable from
income at all, because averaging away the missing values also averaged away the one thing that made
missingness informative. Adding a single binary indicator column recovers nearly the full gap to the
oracle (AUC 0.653 → 0.733, against an oracle ceiling of 0.737) for the cost of one extra feature and
zero extra assumptions about the missing value itself.

**Before you ship that indicator, ask what it's really encoding.** It closed the AUC gap because, in
*this* population, whatever caused someone to omit income also correlated with real default risk. It
cannot distinguish "omitted income because of elevated genuine risk" from "omitted income for a
reason unrelated to risk" — privacy preference, a gig-economy income stream with no single number to
report, distrust of the form. A feature that improves the aggregate number while reweighting *who*
the model gets wrong is precisely the shape of thing M06's per-subgroup audit exists to catch — this
module's Three-tier reading returns to this exact indicator with that tool in hand.

**Named misconceptions**

- **"`dropna` and imputation are two ways of doing the same cleanup."** `dropna` changes the
  population you evaluate on and the population you can serve in production; imputation preserves
  both, at the cost of introducing a placeholder value you have to be honest about.
- **"If I impute a reasonable value, I haven't lost any information."** Mean-imputation tied the
  majority-class baseline exactly in the worked example — the informativeness of *whether* a value
  was missing evaporates the moment every missing row gets the same fill value and nothing marks
  that it was filled.
- **"A missingness indicator is a hack, not a real feature."** It recovered 80 points of AUC gap in
  the worked example for a real, mechanical reason (the missingness pattern is MNAR and genuinely
  correlated with the outcome) — it is exactly as legitimate as any other engineered feature, which
  is also why it deserves exactly as much scrutiny as any other engineered feature, not less.
- **"A high complete-case accuracy means my missing-data handling worked."** `dropna`'s 0.854 is the
  best-looking single number on the table and describes the least useful model — it was never
  evaluated against the population it will actually have to serve.

### Lesson 3 — Feature interactions: what trees get for free and linear models must be told

**Teaching text**

A linear model (and logistic regression, its classification cousin from AIE-201-M02) computes a
weighted sum of features: $\hat{y} = w_0 + w_1 x_1 + w_2 x_2 + \dots$. The coefficient $w_1$ does not
depend on the value of $x_2$ — that is what "linear" means here, and it is also the model's central
limitation. If the true relationship between $x_1$, $x_2$, and $y$ is genuinely *interactive* — the
effect of $x_1$ on $y$ changes depending on $x_2$'s value — no linear combination of $x_1$ and $x_2$
alone can represent it, no matter how much data you feed it. The fix, when you can name the
interacting pair, is to hand the model the product explicitly as a new column: $x_1 \cdot x_2$.

A decision tree needs no such help. A tree splits on one feature at a time, but a **path** through
the tree — split on $x_1 > 0$, then within that branch split on $x_2 > 0$ — implements exactly the
kind of "the rule for $x_2$ depends on $x_1$" logic a linear model cannot express, entirely as a
byproduct of how trees are built (recall AIE-201-M03: split the data on the feature and threshold
that most purifies the two resulting groups, and recurse). Gradient-boosted trees inherit this for
free from every tree in the ensemble.

**Worked example — a pure interaction (XOR), zero marginal signal**

`n=4,000`, two features $x_1, x_2 \sim \text{Uniform}(-1, 1)$ (`rng = np.random.default_rng(311)`).
The label is 1 with probability 0.85 when $x_1$ and $x_2$ share a sign, 0.15 when they don't — a
noisy XOR. By construction, neither feature alone carries information about $y$:

| Quantity | Value |
|---|---:|
| $\text{corr}(x_1, y)$ | −0.023 |
| $\text{corr}(x_2, y)$ | −0.016 |
| $\text{corr}(x_1 \cdot x_2,\, y)$ | **0.538** |

Fit four models, 70/30 split (`random_state=7`, stratified):

| Model | Test accuracy | Test AUC |
|---|---:|---:|
| Logistic regression, raw $x_1, x_2$ | **0.420** | 0.505 |
| Logistic regression, $+\, x_1 \cdot x_2$ | 0.855 | 0.868 |
| Decision tree, raw features (depth ≤ 4) | 0.866 | 0.860 |
| Gradient-boosted trees, raw features | 0.862 | 0.865 |

Logistic regression on the raw features doesn't just fail to find the pattern — at 0.420 accuracy it
scores **below the 0.510 majority-class baseline**, worse than predicting the same class every time,
because the two features it can see are individually uninformative and the model has nothing
consistent to fit a sign to. Add one hand-built column, the product $x_1 \cdot x_2$, and the same
logistic regression jumps to 0.855 accuracy — the interaction term didn't add new information the
model couldn't have inferred, it made *already-present* information linearly expressible for the
first time. The tree and the gradient-boosted ensemble reach essentially the same 0.86-ish accuracy
**with no interaction engineering at all**, because their split-then-recurse structure already
encodes conditional logic.

**The tradeoff this doesn't erase.** Trees get *pairwise and low-order* interactions close to free.
They do not make interaction engineering pointless: (1) a tree still has to spend real splits and
real data discovering an interaction that a domain expert could simply name and hand it directly; (2)
enumerating **every** pairwise product for $p$ features costs $\binom{p}{2}$ new columns, which
explodes for wide tables and reintroduces exactly the high-dimensionality risk Lesson 1 flagged for
one-hot encoding; and (3), the reason this module keeps circling back to it, a linear or logistic
model with explicit, named interaction terms is often **still the right choice** in a regulated
setting (lending, insurance, hiring) where every prediction has to come with a reason code a human
can audit — a tree-based ensemble's implicitly-discovered interactions are real and often more
accurate, and also much harder to explain to a regulator or a rejected applicant than "your debt
ratio and your income interact this way, with this coefficient."

**Named misconceptions**

- **"If two features are each weakly correlated with the label, their interaction is probably weak
  too."** The XOR example is the sharpest possible counterexample: both marginal correlations are
  statistically indistinguishable from zero and the interaction correlation is 0.538 — marginal and
  interactive signal are not the same quantity and one cannot be inferred from the other.
- **"Gradient-boosted trees make interaction feature engineering obsolete."** They make it
  *unnecessary for predictive accuracy* in cases like this one; they do not make it unnecessary for
  interpretability, regulatory compliance, or a linear model's other advantages (speed, stability,
  a coefficient you can quote in a sentence).
- **"A model that fails this badly (0.42 accuracy, below baseline) must have a bug."** No bug —
  logistic regression is behaving exactly as specified; a linear decision boundary genuinely cannot
  separate XOR-structured classes, and a "correct" implementation of the wrong model class is
  expected to fail this specific way.
- **"I should just add every pairwise product to be safe."** With $p=50$ features that's 1,225 new
  columns, most of them noise, and — tying straight back to Lesson 1 and M05 Lesson 3 — feeding a
  feature-selection step across that many noise candidates and *that* selection process not being
  fit train-only is exactly the "search thousands of candidates" leakage mechanism M05 measured as
  the dangerous, non-shrinking kind.

### Lesson 4 — The tabular endgame: why engineered features on gradient-boosted trees still win

**Teaching text**

This course states, and defends with evidence rather than assumes, a claim that runs against the
default intuition that "more sophisticated model" means "neural network": **on real-world tabular
data — a table of heterogeneous, mostly-independent columns, not pixels or tokens — well-engineered
features fed to a gradient-boosted tree still match or beat a neural network, and this is the
consistent, published finding across dozens of real benchmark datasets, not a quirk of small
examples.** Grinsztajn, Oyallon, and Varoquaux (NeurIPS 2022, *"Why do tree-based models still
outperform deep learning on tabular data?"*) and Shwartz-Ziv and Armon (*"Tabular data: Deep learning
is not all you need,"* 2022) are the field's standard references for this result, and both name
mechanisms, not just outcomes:

1. **Tabular relationships are often irregular, not smooth.** A neural network's activation
   functions build smooth, continuous approximations by default; a genuine tabular relationship —
   an age bracket, a credit-score threshold, a policy cutoff — often has real corners and step
   changes that a tree represents exactly (one split, one threshold) and a smooth function has to
   spend extra capacity and data approximating.
2. **Real tables carry uninformative or weakly-informative columns, and trees are naturally
   robust to them.** Every split in a tree is chosen from the single best available feature at that
   node — an irrelevant column simply never gets picked. A neural network's dense layers use *every*
   input on every forward pass; irrelevant columns add noise the network has to learn to ignore
   rather than never touching in the first place.
3. **Tabular columns are not rotation-invariant the way pixels are.** Much of deep learning's power
   on images and audio comes from architectural assumptions (convolution, translation-invariance)
   that are true of that data and false of a table where column 3 is `age` and column 4 is
   `zip_code` — permuting the columns of an image barely changes what a CNN can learn from it;
   permuting the columns of a tabular dataset is a completely different problem with no natural
   architectural prior to exploit.

**This module's own reproduction, not just a citation.** Build a realistic churn dataset — 8,000
customers, 2 real numeric features (age, tenure), 2 categoricals (an 8-level `region` with a real
effect and a 40-level `channel` where only 4 of 40 levels carry real signal, echoing Lesson 1's
high-cardinality risk), an MNAR-missing `income` field with the same informative-missingness
structure as Lesson 2, a Lesson-3-style interaction between tenure and a usage flag, and — the detail
that makes this a *realistic* rather than a toy benchmark — **40 pure-noise numeric nuisance
columns**, standing in for the ordinary reality that a real feature table always has some columns
that turned out not to matter (`rng = np.random.default_rng(407)`). Build two feature sets: an
**unengineered** version (categoricals one-hot encoded, income mean-imputed with no indicator, no
interaction term — the "just get it into a matrix" pass) and an **engineered** version (this
module's own techniques: honest smoothed target encoding for `region`/`channel`, mean-impute **+**
missingness indicator for `income`, the tenure×usage interaction term made explicit). Fit
`HistGradientBoostingClassifier` (the histogram-based estimator AIE-201-M03 named but did not build
from scratch — its first real job in this course) and `MLPClassifier`, a small feedforward network,
on each:

| Feature set | GBT test AUC | GBT test acc | MLP test AUC | MLP test acc |
|---|---:|---:|---:|---:|
| Unengineered (one-hot, mean-impute, no interaction) | **0.688** | 0.665 | 0.552 | 0.617 |
| Engineered (target-encoded, indicator, interaction) | **0.802** | 0.739 | 0.785 | 0.724 |

*(Majority-class baseline: 0.626.)*

Gradient-boosted trees beat the neural network on **both** feature sets, and the margin is far
larger on unengineered features (+0.136 AUC) than on engineered ones (+0.017 AUC) — evidence for
mechanism (2) above, directly: the unengineered feature set is exactly where the 40 noise columns
and the wide, sparse one-hot expansion of `channel` do the most damage, and the neural network is the
one that pays for it. **This is not a one-seed fluke** — repeating the same comparison across 8
independent resamples of the dataset generator, the gradient-boosted tree's AUC advantage over the
neural network is **positive on every single seed**, averaging +0.094 (range +0.045 to +0.164) on
unengineered features and +0.021 (range +0.017 to +0.034) on engineered features — smaller on
engineered features, but never zero, never reversed.

**A genuinely useful side finding, and a caution against overreading it.** Feeding
`HistGradientBoostingClassifier` the **raw** columns directly — untouched categorical codes, `NaN`
left in place, using the estimator's native categorical and missing-value support rather than any
encoding this module built — scores AUC 0.691, essentially tied with the one-hot-encoded
unengineered version (0.688), and still far below the engineered feature set's 0.802. Modern
gradient-boosting implementations really do save you the mechanical work of one-hot encoding and
NaN-filling; **that convenience is not a substitute for the actual feature engineering** — target
encoding a meaningful `region` and `channel` signal, flagging informative missingness, naming the
real interaction — that is where the 0.688 → 0.802 jump actually comes from. The model's native
convenience closes an engineering-effort gap, not a signal gap.

**Named misconceptions**

- **"Deep learning is strictly more powerful than gradient boosting, so it should always win given
  enough data/tuning."** More parameters and more expressive function classes are not the same
  claim as "better inductive bias for this data's actual structure" — the mechanisms above (smooth
  vs. irregular relationships, universal vs. selective feature use) are about *fit between model
  and data*, not raw capacity.
- **"If GBT beats MLP here, feature engineering doesn't matter for GBT."** GBT's own AUC still moved
  from 0.688 to 0.802 between feature sets — a real, large gain — it simply paid a smaller *relative*
  tax than the MLP for not having it, which is a different claim than "doesn't matter."
- **"A GBT implementation that handles raw categoricals and NaN natively means I can skip encoding
  and imputation."** The native-handling number (0.691) essentially matches the naive one-hot
  version and sits far below the properly engineered version — native support saves you typing, not
  the actual engineering work.
- **"One benchmark, even a well-built one, proves the general claim."** This lesson's own numbers
  are offered as *evidence consistent with* the published, much larger-scale finding
  (Grinsztajn et al.; Shwartz-Ziv & Armon), not a replacement for it — the 8-seed robustness check
  exists precisely because a single run, on its own, would be exactly the kind of one-dataset anecdote
  this course otherwise warns against trusting.

## Labs

```python
import numpy as np

def fit_target_encoder(categories: np.ndarray, y: np.ndarray, n_categories: int,
                        smoothing: float = 0.0) -> np.ndarray:
    global_mean = y.mean()
    enc = np.full(n_categories, global_mean, dtype=float)
    for c in range(n_categories):
        mask = categories == c
        cnt = mask.sum()
        if cnt > 0:
            cat_mean = y[mask].mean()
            if smoothing > 0:
                enc[c] = (cnt * cat_mean + smoothing * global_mean) / (cnt + smoothing)
            else:
                enc[c] = cat_mean
    return enc

def apply_target_encoder(categories: np.ndarray, encoding_map: np.ndarray) -> np.ndarray:
    return encoding_map[categories]

def oof_target_encode(categories: np.ndarray, y: np.ndarray, n_categories: int,
                       n_folds: int, rng: np.random.Generator, smoothing: float = 0.0) -> np.ndarray:
    n = len(y)
    idx = rng.permutation(n)
    folds = np.array_split(idx, n_folds)
    out = np.zeros(n)
    for i in range(n_folds):
        held_out = folds[i]
        other = np.concatenate([folds[j] for j in range(n_folds) if j != i])
        enc_map = fit_target_encoder(categories[other], y[other], n_categories, smoothing)
        out[held_out] = apply_target_encoder(categories[held_out], enc_map)
    return out

def leaky_encode_pipeline(categories, y, train_idx, test_idx, n_categories, smoothing=0.0):
    enc_map = fit_target_encoder(categories, y, n_categories, smoothing)   # LEAK: sees test rows
    X_train = apply_target_encoder(categories[train_idx], enc_map)
    X_test = apply_target_encoder(categories[test_idx], enc_map)
    return X_train, X_test

def honest_encode_pipeline(categories, y, train_idx, test_idx, n_categories, n_folds, rng,
                            smoothing=0.0):
    X_train = oof_target_encode(categories[train_idx], y[train_idx], n_categories, n_folds,
                                 rng, smoothing)
    train_map = fit_target_encoder(categories[train_idx], y[train_idx], n_categories, smoothing)
    X_test = apply_target_encoder(categories[test_idx], train_map)
    return X_train, X_test

    it can never see the label attached to its own (only) row."""

import numpy as np

def fit_mean_imputer(col: np.ndarray) -> float:
    return float(np.nanmean(col))

def apply_mean_imputer(col: np.ndarray, fill_value: float) -> np.ndarray:
    return np.where(np.isnan(col), fill_value, col)

def missingness_indicator(col: np.ndarray) -> np.ndarray:
    return np.isnan(col).astype(float)

def complete_case_mask(*cols: np.ndarray) -> np.ndarray:
    mask = np.ones(len(cols[0]), dtype=bool)
    for c in cols:
        mask &= ~np.isnan(c)
    return mask
```

def build_churn_dataset(seed: int = 407, n: int = 8000, n_noise: int = 40) -> dict:
    """Generates the churn dataset (do not modify). Returns a dict of raw arrays:
    age, tenure, region, channel, observed_income, is_missing, short_tenure, high_usage,
    churn, noise (an (n, n_noise) array of pure nuisance columns)."""
    rng = np.random.default_rng(seed)
    age = rng.normal(40, 12, n)
    tenure = rng.exponential(24, n)
    region = rng.integers(0, 8, n)
    channel = rng.integers(0, 40, n)
    income = rng.lognormal(10.8, 0.45, n)

    region_effect = np.array([0.9, -0.6, 0.2, 1.1, -0.9, 0.4, -0.2, 0.0])[region]
    channel_effect_table = np.zeros(40)

import numpy as np
from sklearn.preprocessing import OneHotEncoder
from lab1_solution import fit_target_encoder, apply_target_encoder
from lab2_solution import fit_mean_imputer, apply_mean_imputer, missingness_indicator

def build_churn_dataset(seed: int = 407, n: int = 8000, n_noise: int = 40) -> dict:
    rng = np.random.default_rng(seed)
    age = rng.normal(40, 12, n)
    tenure = rng.exponential(24, n)
    region = rng.integers(0, 8, n)
    channel = rng.integers(0, 40, n)
    income = rng.lognormal(10.8, 0.45, n)

    region_effect = np.array([0.9, -0.6, 0.2, 1.1, -0.9, 0.4, -0.2, 0.0])[region]
    channel_effect_table = np.zeros(40)
    channel_effect_table[:4] = [1.2, -1.0, 0.8, -0.7]
    channel_effect = channel_effect_table[channel]

    short_tenure = (tenure < 12).astype(float)
    high_usage = (rng.uniform(size=n) < 0.5).astype(float)
    interaction_effect = 2.0 * (short_tenure == high_usage).astype(float)

    age_bracket_effect = np.where(age < 28, 0.9, np.where(age > 55, 0.7, -0.4))

    income_rank = income.argsort().argsort() / n
    p_missing = np.clip(0.5 - 0.45 * income_rank, 0.03, 0.5)
    is_missing = rng.uniform(size=n) < p_missing
    income_effect = -0.000018 * (income - 55000) + 0.8 * is_missing
    observed_income = income.copy()
    observed_income[is_missing] = np.nan

    z = -2.0 + region_effect + channel_effect + interaction_effect + income_effect + age_bracket_effect
    churn = (rng.uniform(size=n) < 1 / (1 + np.exp(-z))).astype(int)
    noise = rng.normal(size=(n, n_noise))

    return dict(age=age, tenure=tenure, region=region, channel=channel,
                observed_income=observed_income, is_missing=is_missing,
                short_tenure=short_tenure, high_usage=high_usage, churn=churn, noise=noise)

def build_unengineered_features(d, train_idx, test_idx):
    ohe_r = OneHotEncoder(sparse_output=False, handle_unknown="ignore").fit(
        d["region"][train_idx].reshape(-1, 1))
    ohe_c = OneHotEncoder(sparse_output=False, handle_unknown="ignore").fit(
        d["channel"][train_idx].reshape(-1, 1))
    r_tr, r_te = ohe_r.transform(d["region"][train_idx].reshape(-1,1)), ohe_r.transform(d["region"][test_idx].reshape(-1,1))
    c_tr, c_te = ohe_c.transform(d["channel"][train_idx].reshape(-1,1)), ohe_c.transform(d["channel"][test_idx].reshape(-1,1))
    fill = fit_mean_imputer(d["observed_income"][train_idx])
    inc_tr = apply_mean_imputer(d["observed_income"][train_idx], fill)
    inc_te = apply_mean_imputer(d["observed_income"][test_idx], fill)
    X_tr = np.column_stack([d["age"][train_idx], d["tenure"][train_idx], inc_tr, r_tr, c_tr, d["noise"][train_idx]])
    X_te = np.column_stack([d["age"][test_idx], d["tenure"][test_idx], inc_te, r_te, c_te, d["noise"][test_idx]])
    return X_tr, X_te

def build_engineered_features(d, train_idx, test_idx):
    ytr = d["churn"][train_idx]
    region_map = fit_target_encoder(d["region"][train_idx], ytr, 8, smoothing=20.0)
    channel_map = fit_target_encoder(d["channel"][train_idx], ytr, 40, smoothing=20.0)
    r_tr = apply_target_encoder(d["region"][train_idx], region_map)
    r_te = apply_target_encoder(d["region"][test_idx], region_map)
    c_tr = apply_target_encoder(d["channel"][train_idx], channel_map)
    c_te = apply_target_encoder(d["channel"][test_idx], channel_map)

    fill = fit_mean_imputer(d["observed_income"][train_idx])
    inc_tr = apply_mean_imputer(d["observed_income"][train_idx], fill)
    inc_te = apply_mean_imputer(d["observed_income"][test_idx], fill)
    ind_tr = missingness_indicator(d["observed_income"][train_idx])
    ind_te = missingness_indicator(d["observed_income"][test_idx])

    inter_tr = (d["short_tenure"][train_idx] == d["high_usage"][train_idx]).astype(float)
    inter_te = (d["short_tenure"][test_idx] == d["high_usage"][test_idx]).astype(float)

    X_tr = np.column_stack([d["age"][train_idx], d["tenure"][train_idx], inc_tr, ind_tr,
                             r_tr, c_tr, inter_tr, d["noise"][train_idx]])
    X_te = np.column_stack([d["age"][test_idx], d["tenure"][test_idx], inc_te, ind_te,
                             r_te, c_te, inter_te, d["noise"][test_idx]])
    return X_tr, X_te

## Three-tier reading — the feature that told the truth about the wrong thing

**Tier 1 — material ground.** Every number in this module is a specific, re-runnable artifact:
leaky-vs-honest target-encoding AUCs at three stated cardinalities, a missingness-indicator's exact
AUC recovery, an interaction term's exact accuracy jump, an 8-seed GBT-vs-MLP comparison with a
stated, never-negative advantage. The published benchmark claim this module states as fact
(Grinsztajn et al., 2022; Shwartz-Ziv & Armon, 2022 — gradient-boosted trees on engineered tabular
features match or beat neural networks on real-world tabular data) is not received wisdom here; it
is a claim this module's own Lab 3 reproduces with a stated, checkable margin. Feature engineering
itself is, like the labeled data this course's ethics thread names in Tier 1 elsewhere, **real,
measurable, uncompensated-in-the-final-metric labor** — the target encoder, the missingness taxonomy,
the interaction term are hours of a specific person's judgment, and none of that labor shows up in
the number "AUC: 0.802" that eventually goes in a slide.

**Tier 2 — what "the indicator improved the model" suppresses.** Lesson 2's missingness indicator is
this module's central case study, and it is worth stating its suppression precisely, because it is
not a bug: the indicator column recovers real signal *because*, in the training population, whatever
caused a person to omit their income correlated with genuine, measurable default risk. What the
single number "AUC: 0.733, up from 0.653" does not say is **why** any individual applicant's income
was missing. Some applicants who omit income are exactly the elevated-risk case this feature was
built to catch. Others omit it for reasons with no bearing on repayment at all — a gig-economy income
stream with no single figure to report, a justified reluctance to disclose financial detail on a
form, an applicant from a population with less standardized income documentation. The model cannot
tell these apart; it can only exploit whatever the aggregate correlation happens to be in the
training population it was fit on. **This is the exact mechanism the course's Tier 2 ethics thread
names generally — "what accuracy suppresses" — now sitting inside a single engineered column this
module taught you to build and be proud of.**

**Tier 3 — sit with this.** AIE-201-M06 built you a specific tool for exactly this situation: a
per-subgroup audit that checks whether a feature's aggregate gain is evenly distributed or
concentrated against a specific, identifiable group. Nothing in this module's Lab 2 required you to
run that audit before shipping the missingness indicator — the honest engineering discipline this
module teaches (fit only on train, use out-of-fold encoding, check the coverage `dropna` would have
cost you) certifies that the feature is *statistically clean*. It does not certify that it is
*fair*, and those are different claims that a green pytest suite cannot tell apart. You now have
every tool this module built — the leak-vs-honest comparison, the coverage audit, the interaction
test — and every one of them answers "is this feature computed correctly." None of them answers "is
it fair to build a risk score partly out of the fact that someone declined to tell you their income."
The next time a feature you engineered honestly, tested thoroughly, and can defend with a real AUC
number happens to correlate with something you didn't put in the training data on purpose — a zip
code standing in for something else, a missing field standing in for a reason you never asked about
