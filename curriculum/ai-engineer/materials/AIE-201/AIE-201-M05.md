## Module overview

Every module before this one ended with a number — an R², an accuracy, an inertia, an explained
variance ratio — and asked you to trust it. This module is about the machinery that number passes
through before it's allowed to mean anything, and about the specific, well-documented ways that
machinery gets built wrong without ever throwing an error. A leaked pipeline does not crash. It
runs cleanly, prints a great score, and gets shipped. The failure is invisible from inside the code
that produced it — which is exactly why this is the single most load-bearing module in the course:
every later diagnosis you make (drift in M06, "is this feature even legitimate" in M07, "should
this be ML at all" in M08, and every evaluation you run in AIE-204) inherits its trustworthiness
from whether the split underneath it was honest.

The central claim, stated plainly and then earned with numbers across four lessons: **a model's
reported score is only as trustworthy as the wall between what it was fit on and what it was
graded on.** Breach that wall — even by one column, one preprocessing step run in the wrong order,
one entity whose rows appear on both sides — and the score stops measuring generalization and
starts measuring memorization, while looking, to every metric you know how to compute, exactly like
success. You will build that wall four different ways (a disciplined train/val/test split, k-fold
cross-validation done correctly, a taxonomy of the specific ways it gets breached, and a floor —
the baseline — below which no claim of "it works" is even coherent), and then you will be handed a
pipeline with a wall that has already been breached, told nothing about where, and asked to find it
from the suspiciously good numbers alone. That last exercise is not a bonus round. It is the
certification artifact this module exists to produce: a learner who has memorized "always split
before you scale" can still be fooled by a leak they didn't anticipate; a learner who has
internalized *why* a number that's too good is itself evidence, not good news, can find leaks this
module never showed them.

The descent: define the contract precisely and watch a random split silently violate it when the
data has structure over time (Lesson 1); scale that contract up to cross-validation and discover
that "I used CV" is not a magic word that makes leakage impossible (Lesson 2); build the taxonomy —
target leakage via a proxy column, preprocessing fit on the wrong data, and group leakage — each
with a number that should have made you suspicious before you shipped it (Lesson 3); and establish
the baseline every one of those numbers has to clear, because "beats zero" and "beats chance" and
"beats yesterday's naive forecast" are three different, non-interchangeable bars, and most reported
"wins" only ever clear the easiest of the three (Lesson 4). Re-ascent: you can read a project report
that says "94% accuracy" and, before asking anything else, ask what the baseline was, whether the
split respected however the data is structured, and whether any of the accuracy came from a column
that will not exist the day this model is actually asked to predict something.

## Lessons

### Lesson 1 — The evaluation contract: train / validation / test, and what "fit only on train" actually forbids

**Teaching text**

State the contract precisely, because every leak in this module is a specific violation of one
clause of it:

1. **Train** is the only data any parameter — model coefficients, a scaler's mean and standard
   deviation, a feature selector's chosen columns, an imputer's fill values — is ever *fit* on.
2. **Validation** is data the model never trains on, used to make decisions *about* the model
   (which hyperparameter, which feature set, when to stop) — and once you have used it to make a
   decision, it has been spent; a validation set you tune against repeatedly quietly becomes a
   second training set.
3. **Test** is touched exactly once, at the end, to report the number you will stand behind. If you
   look at the test score and then go back and change anything — a feature, a hyperparameter, a
   preprocessing choice — test has become validation, and you no longer have a test set.

The clause that catches almost every real-world leak is clause 1, and it is stricter than it sounds:
"fit only on train" does not mean "don't look at the test *labels*." It means no function call that
estimates *any* number from data — `mean()`, `std()`, `corr()`, an eigendecomposition, a
feature-selection ranking, a target-encoding lookup table — is allowed to see a row that will later
be called "test," full stop, regardless of whether that row's label was involved. A `StandardScaler`
fit on the whole dataset never reads a single `y` value and it still leaks, because the *mean and
standard deviation it learned* were partly computed from rows the model will later be graded
against — information a genuinely deployed model, scoring one new row at a time in the future, could
never have had access to. **Order of operations is the whole discipline**: split first, fit every
transform on train only, then apply — never fit — those same transforms to validation and test.

**Worked example — a random split on data with a hidden clock**

Consider a KPI you're asked to model as a function of "how long the product has been live"
(`days_live`), a single feature, on `n = 900` daily observations with a slow upward trend plus a
50-day seasonal wave: `y_t = 0.008·t + 3·sin(2πt/50) + ε_t`, `ε_t ~ N(0, 1)`, `rng =
np.random.default_rng(205)`. Fit a $k$-NN regressor ($k=3$) two ways:

| Split strategy | Train / test sizes | Mean gap (days) from a test point to its nearest *train* point | Test $R^2$ |
|---|---:|---:|---:|
| **Random** (`rng.permutation`, 70/30) | 630 / 270 | **1.07** | **0.820** |
| **Chronological** (train = days 0–629, test = days 630–899, "the future") | 630 / 270 | 135.5 | **−1.043** |

Same data, same model, same 70/30 ratio — a 1.86-point swing from "explains 82% of the variance" to
"worse than just predicting the mean every time" ($R^2 < 0$). Nothing about the *model* changed.
What changed is what the split let the model see: under the random split, the nearest training
neighbor to almost every test point is a day and a bit away — the model is effectively
**interpolating between neighbors that straddle it in time**, which a genuine forward-deployed
model, scoring tomorrow with only yesterday's data, can never do. Under the chronological split,
the model is 135 days into territory it has never seen and must genuinely extrapolate the trend —
which $k$-NN, a purely local method with no notion of "keep going in this direction," cannot do at
all; it just returns the average of the last few training points, flat, while the real trend and
seasonal wave keep moving. **Ridge regression on the same two features shows the identical
direction of collapse, just less catastrophically** ($R^2 = 0.379$ random vs. $R^2 = 0.048$
chronological), because a linear extrapolation at least keeps moving in the right direction — but
it, too, was flattered by the random split.

The lesson is not "$k$-NN is bad" or "always use a chronological split." It is: **the split
strategy has to match the question you are actually going to be asked in deployment.** If tomorrow
you will always be predicting forward from everything you've seen so far, a random split answers a
question ("how well can I fill in a value it can interpolate between two known neighbors") that
production will never ask, and its glowing test score is measuring exactly that wrong question.

**Named misconceptions**

- **"Leakage is about not looking at the test set's *labels*."** The `days_live` example above never
  touches `y` improperly — the leak is entirely in which *rows* were nearby which other rows across
  the split boundary. Any information that crosses the train/test wall counts, features and row
  structure included, not just labels.
- **"If my model's test score is surprisingly good, that's good news."** A score well outside what
  domain knowledge or the baseline (Lesson 4) says is achievable is evidence to *distrust*, not
  celebrate — Lesson 3 turns this instinct into a specific, checkable procedure.
- **"The order I write code in doesn't matter as long as it eventually runs correctly."** `fit()` is
  the boundary that decides what a transform is *allowed to know*; running `fit_transform` on the
  full dataset before splitting silently teaches the transform about rows that will later be called
  "test," even though every line of code afterward looks completely ordinary.
- **"A random shuffle before splitting makes any dataset i.i.d.-safe."** Shuffling erases the very
  structure (time, repeated entities, geography) that made a random split wrong in the first place —
  it doesn't fix the leak, it *is* the mechanism that causes it when the data has structure a random
  split isn't allowed to ignore.

### Lesson 2 — Cross-validation, and why "I used CV" does not mean "I can't have leaked"

**Teaching text**

A single train/test split reports one number computed from whichever 30% of rows happened to land
in the test set — and that number has real sampling variance. **$k$-fold cross-validation** reduces
that variance by rotating which rows play "test": partition the data into $k$ roughly equal folds,
train on $k-1$ of them and evaluate on the held-out fold, repeat $k$ times so every row is scored
exactly once, and report the mean (and spread) of the $k$ scores instead of trusting any single
split.

On a synthetic 300-row, 12-feature regression (3 informative coefficients, 9 null, `rng =
np.random.default_rng(211)`), 5-fold Ridge ($\alpha=1$) gives:

| Fold | 1 | 2 | 3 | 4 | 5 | mean | std |
|---|---:|---:|---:|---:|---:|---:|---:|
| $R^2$ | 0.304 | 0.536 | 0.497 | 0.442 | 0.242 | **0.404** | **0.113** |

A standard deviation of 0.113 on a mean of 0.404 is enormous relative to the number itself — any
single one of those five folds, reported alone as "the" test score, would have been off by up to a
third of the estimate. **This is the whole justification for cross-validation over a single split:
not that it removes variance, but that it makes the variance visible instead of hiding it behind
one lucky or unlucky draw.**

**Cross-validation does not, by itself, prevent leakage.** This is the single most important
sentence in this lesson, and Lesson 3 will make it concrete with numbers that should feel alarming:
if a preprocessing step (a feature selector, a target encoder, a PCA) is fit on the *entire*
dataset before the $k$-fold loop even starts, every fold's "held-out" data was already used to shape
that preprocessing — the CV loop faithfully rotates through folds that are each individually
compromised, and averages five compromised numbers into one confident-looking compromised number.
Correct usage refits every such transform **inside** each fold, using only that fold's $k-1$
training partitions — which is exactly why `sklearn.pipeline.Pipeline` wrapped in `cross_val_score`
exists: it automates re-fitting the *entire* pipeline, preprocessing included, on each fold's
training data alone.

**Nested validation and the leak of *tuning* on the test set.** A second, subtler leak: choosing a
hyperparameter (Ridge's $\alpha$) by trying several values and keeping whichever one scores best
**on the test set** — then reporting that best test score as "the" result. This feels harmless
("I'm not fitting *coefficients* on test data") but it converts the test set into an unlimited
tuning oracle. On the 300-row dataset above, split 70/30 (`random_state=2`):

| $\alpha$ | 0.01 | 0.1 | 1.0 | 10.0 | 100.0 |
|---|---:|---:|---:|---:|---:|
| **Test $R^2$ if evaluated directly** ("peeking") | 0.267 | 0.267 | 0.269 | 0.284 | **0.309** |
| **Inner 5-fold CV $R^2$, train only** (honest) | 0.423 | 0.423 | 0.424 | **0.429** | 0.370 |

Peeking at the test set picks $\alpha=100$ (test $R^2=0.309$, the best-looking number on the table).
Honest inner cross-validation — run entirely inside the training 70%, never touching the test 30% —
picks $\alpha=10$. Evaluating the *honestly chosen* $\alpha=10$ once against test gives $R^2=0.284$,
**not** 0.309: the number you'd have reported by peeking overstates the number you'd have gotten by
tuning honestly, by 0.025 $R^2$, on this split alone. Repeating this comparison across 30 different
random 70/30 resamples of the same dataset: the peeked-minus-honest gap is **never negative** (min
0.000, mean **+0.006**, max +0.051, positive in 63% of resamples and exactly zero — the two
strategies coincidentally agreeing — in the other 37%). That "never negative" property isn't a
quirk of this dataset: picking the *best of several noisy estimates* is a biased estimator of the
best *true* value by construction — you are choosing the maximum of several numbers that are each
already noisy above or below their true value, and the maximum of noisy things is itself
systematically optimistic. Sometimes the noise cancels out and peeking happens to match honest
tuning exactly; it is never allowed, by the mathematics of taking a maximum, to be honest tuning's
*worse* case.

**Named misconceptions**

- **"A single train/test split gives a reliable performance estimate."** The five-fold spread above
  (0.242 to 0.536, same data, same model, different rows in the held-out set) shows a single split's
  number can be a lucky or unlucky draw; report the mean **and** the spread, not one split's score.
- **"As long as I use cross-validation, I can't have leaked anything."** Lesson 3's feature-selection
  example proves this false with numbers: CV run on top of data that was already contaminated
  *before* the CV loop started faithfully reports a contaminated number, five times, averaged.
- **"Picking whichever hyperparameter gets the best score on my held-out set is a normal, harmless
  way to tune."** That held-out set is now a second training set for the hyperparameter, and the
  "test" score you report from it is optimistically biased — never pessimistically — relative to
  what an honestly-tuned model would score on genuinely unseen data.
- **"If peeking and honest tuning land on the same answer sometimes, peeking must be fine in
  general."** A tie on one resample says nothing about the strategy's average behavior; the
  30-resample sweep is what reveals the systematic (if often small) upward bias that any single run
  can hide.

### Lesson 3 — The leakage taxonomy: target leakage, preprocessing leakage, group leakage

**Teaching text**

Three distinct mechanisms, each producing the same symptom (a suspiciously good number) through a
completely different route. Confusing them wastes debugging time, because the fix for each is
different.

**1. Target leakage via a proxy column.** A feature that is, causally, *downstream* of the outcome
you're trying to predict — it exists in your historical table because someone already knew the
answer when it was recorded, and it will not exist for a genuinely new case you're trying to score.
On a 1,000-row loan dataset (`rng = np.random.default_rng(207)`, four genuine features — income,
credit score, debt ratio, credit utilization — driving a logistic default probability with an
11.3% true base rate), add one more column: `collections_call_flag`, set to 1 for 97% of loans that
actually defaulted and for 2% of loans that didn't (a realistic false-positive rate on a genuine
process — the call gets logged *because* the loan defaulted, so it is a record of the outcome, not
a predictor of it):

| Model | Test accuracy | Majority-class baseline | Test AUC |
|---|---:|---:|---:|
| Genuine features only (income, credit score, debt ratio, utilization) | 0.887 | 0.887 | 0.723 |
| **+ `collections_call_flag`** | **0.987** | 0.887 | **0.980** |

Adding one column moved accuracy from *exactly tied with the majority-class baseline* to 98.7% and
AUC from 0.72 to 0.98. That size of jump from a single added feature, on a problem where every other
feature moves accuracy by fractions of a point, is itself the tell — quantify it and it stops being
a vibe: ranking every feature by absolute correlation with the target shows `collections_call_flag`
at **0.900**, roughly six times the next-highest genuine feature (credit score, −0.147). A
standardized logistic coefficient of **2.107** on that one column dwarfs every genuine feature's
coefficient (0.19–0.38). **None of this required looking at test labels improperly or violating the
split** — the leak is entirely in what the column *means*: it is a proxy for the answer, present in
the historical record, absent at prediction time.

**2. Preprocessing leakage — and why cross-validation alone cannot save you.** Fitting a transform
on the full dataset before splitting. The *size* of this leak depends entirely on how much the
transform estimates from the data. A `StandardScaler`'s mean and standard deviation are two numbers
per feature — on `n=60` two-feature data (age, income; wildly different raw scales), fitting the
scaler on all 60 rows versus fitting it on the 42-row training split alone moves test $R^2$ by
**+0.004 on average across 50 resamples** (std 0.021 — sometimes the "leaky" version even scores
*worse*, since two summary statistics estimated from 60 rows versus 42 rows are both just noisy
estimates of the same true mean and std). At $n=2{,}000$ that gap shrinks to essentially zero
(−0.0001). **Simple scaling leakage is usually small, and that is precisely what makes it dangerous
to reason about by "does the number look wrong" — it often doesn't.**

Contrast that with **feature-selection leakage**, where the transform doesn't estimate two summary
numbers, it *searches thousands of candidates and keeps whichever ones happen to correlate best with
this exact label vector*. On `n=200` rows and `p=5{,}000` features that are **pure noise, unrelated
to the label by construction**, selecting the top 20 features by correlation with $y$:

| Selection uses | Single-split accuracy | 5-fold CV accuracy on those columns |
|---|---:|---:|
| **All 200 rows** (leak — selection saw labels that end up in every fold's "test") | 0.800 | **0.765 (mean of 0.775, 0.700, 0.750, 0.825, 0.775)** |
| **Train rows only** (140/60 split, honest) | **0.467** | — |
| Majority-class baseline | 0.560 | 0.560 |

$X$ and $y$ have **zero** true relationship. Selecting features using train-only data correctly
returns a near-chance number (0.467, at or below the 0.560 baseline — no real signal to find, and
none was found). Selecting using all the data returns 76.5% cross-validated accuracy on data with
no signal in it at all — and note that the CV loop itself was run correctly, five honest folds,
faithfully averaged. **The leak happened upstream of the CV loop, at feature-selection time, and no
amount of correctness inside the loop can retroactively fix data that was already contaminated
before the loop started.** This is why a `Pipeline` that bundles the selector *inside* the
cross-validated step (refit fresh on each fold's training partition) is not a style preference — it
is the only way to make "I cross-validated" a true statement about leakage safety.

**3. Group leakage — the same entity's rows on both sides of the split.** Repeated-measures data
(patients with multiple visits, users with multiple sessions, sensors with multiple readings) has
rows that are not independent of each other — several rows come from the *same underlying entity*.
A row-level random split can and typically does put some of a given entity's rows in train and
others in test. On 60 simulated patients (10 visits each, a single feature — the patient's
underlying trait, repeated across visits with small measurement noise — weakly related to a binary
outcome):

| Model | Row-level random split (59/60 patients appear on **both** sides) | Group-aware split (`GroupKFold`, 0 patients appear on both sides) |
|---|---:|---:|
| 1-nearest-neighbor | **0.700** | 0.583 |
| Logistic regression | 0.656 | 0.700 |

$k$-NN, a method that can literally recognize a near-duplicate row, benefits from the leak (0.700 vs
0.583) because a test-set visit from a patient it already "met" in training is nearly identical to
that patient's training visits — it is recognizing the *person*, not generalizing the *pattern*.
Logistic regression, which fits a smooth global relationship rather than memorizing individual rows,
shows no such inflation (if anything the numbers move the other way here, within the noise of a
60-patient sample) — **the size of a group leak depends on how much the model can memorize identity,
but the split is wrong regardless of which model you happen to be using today**, and a model change
next quarter can silently turn a previously-harmless mistake into a serious one.

**Named misconceptions**

- **"Leakage means I looked at the test labels."** The proxy-column example never touches test
  labels improperly; the leak is in what the *feature itself* encodes about the outcome.
- **"A feature that's genuinely in my historical database is fair game."** Historical availability
  and prediction-time availability are different claims — `collections_call_flag` is real, accurate,
  and permanently absent for any loan application you haven't decided the fate of yet.
- **"I cross-validated my pipeline, so I can't have leaked."** The 5-fold CV number on the pure-noise
  feature-selection example (0.765, on data with zero true signal) is the direct counterexample —
  CV protects the fitting step it wraps, nothing that happened before it.
- **"Group leakage is a minor detail if my model isn't literally doing nearest-neighbor lookup."**
  The effect size varies by model (as shown above), but the *split itself* — a person's future data
  appearing in the same set as their own past data — misrepresents the deployment question for
  every model family; today's small effect is not a guarantee about tomorrow's.

### Lesson 4 — Baselines: the floor every claim of "it works" has to clear

**Teaching text**

Before any trained model's score means anything, establish the cheapest possible prediction rule
and beat it — not narrowly, not by an amount indistinguishable from noise, but by a margin large
enough to justify the model's added complexity. Three different baselines answer three different
questions, and using the wrong one is its own quiet failure mode.

**Regression: the mean predictor.** Predict the training mean for every row, always. By
construction this gives $R^2 \approx 0$ on the training data; on a genuinely held-out test set it
can land slightly above or below zero from sampling noise. On a 400-row, 6-feature synthetic
regression (3 informative coefficients, 3 null, `rng = np.random.default_rng(213)`, 70/30 split):

| Model | Test $R^2$ | Test MAE |
|---|---:|---:|
| Mean predictor (`sklearn.dummy.DummyRegressor(strategy="mean")`) | −0.010 | 2.706 |
| Ridge, $\alpha=1$ | **0.139** | **2.501** |
| A "weak" model (Ridge trained on **shuffled** training labels) | 0.003 | 2.699 |

Ridge clears the mean-predictor floor by a real margin (0.139 vs. −0.010). The shuffled-label model
— trained on the same features but with $y$ randomly reassigned within train, so the true
feature–target relationship is destroyed — lands at $R^2 = 0.003$, statistically indistinguishable
from the mean predictor's −0.010. **This is what "failing to beat baseline" looks like in practice:
not a negative or absurd number, but a number close enough to the floor that reporting it as "the
model works" would be a claim the evidence doesn't support.**

**Classification: the majority-class baseline.** Predict the more common class for every row,
always. Reusing Lesson 3's loan-default data (11.3% true default rate, so predicting "no default"
every time already gets you far): the genuine-features model's test accuracy (0.887) landed
**exactly on top of** the majority-class baseline (0.887, confirmed against
`sklearn.dummy.DummyClassifier(strategy="most_frequent")`), because at a standard 0.5 decision
threshold on a rare positive class, a real but modest model (AUC 0.72) never crosses 0.5 and
**recalls exactly 0% of actual defaults** — its balanced accuracy is 0.500, chance level, even
though its *raw* accuracy tied a baseline that looks, at a glance, hard to beat. **Accuracy on
imbalanced data can be won by never predicting the rare class at all** — this is base-rate neglect
made mechanical, and it is why the assessment components in this course's syllabus weight "diagnose
a sick model" work as heavily as raw implementation: a model can score identically to a baseline
that does no learning whatsoever and still look, by the single most commonly reported metric, like
it's working.

**Time series: the persistence (naive) baseline.** Predict that the next value equals the last
observed value. On a simulated AR(1) series (`y_t = 0.85·y_{t-1} + ε_t`, `ε_t ~ N(0,1)`,
`n=250`), evaluated on the same chronological test window for a fair comparison:

| Model | Test $R^2$ |
|---|---:|
| Persistence (predict $\hat{y}_t = y_{t-1}$) | **0.679** |
| Ridge regression on lags 1–3 | 0.677 |

A model with three features and a fitted coefficient vector **did not beat** a rule with zero
parameters and zero training. This is not a bug in the demonstration — for a series this close to a
pure random walk, the two additional lags genuinely carry almost no information the most recent
value didn't already contain, and the honest conclusion is that the fancier model isn't earning its
complexity. **The mean-predictor baseline would have been the wrong floor to check against here**
(a mean predictor scores far worse than persistence on autocorrelated data, so "beats the mean" is a
much lower and less meaningful bar for time series than "beats persistence") — picking the *right*
baseline for the data's structure is as much a judgment call as picking the right split strategy in
Lesson 1, and for the same underlying reason: both decisions have to match the real structure of the
problem, not the easiest structure to compute.

**Named misconceptions**

- **"High accuracy means the model is good."** The genuine loan model ties the majority baseline
  exactly on accuracy while recalling 0% of the outcome anyone actually cares about detecting —
  report a metric that survives class imbalance (balanced accuracy, recall, AUC) alongside accuracy,
  not instead of a baseline comparison.
- **"Beating $R^2=0$ (or any mean-predictor baseline) means the model is useful."** For
  autocorrelated or time-structured data, the mean predictor is a far weaker floor than persistence;
  "beats the mean" and "beats persistence" are different claims, and only the harder one is
  informative for deployment.
- **"More features or a fitted model is inherently better than a trivial rule."** The lag1–3 Ridge
  model, strictly more complex and more informed than persistence, still failed to beat it —
  complexity is not itself evidence of improvement; only the beat-the-baseline number is.
- **"An improvement over baseline that's technically positive is a real improvement."** The
  shuffled-label model's $R^2 = 0.003$ versus the mean baseline's −0.010 is technically an
  improvement and means nothing — report whether an improvement is large relative to the score's own
  variance (Lesson 2's fold-to-fold spread), not just whether its sign is positive.

import numpy as np

def fit_standard_scaler(X: np.ndarray) -> tuple[np.ndarray, np.ndarray]:
    mean = X.mean(axis=0)
    std = X.std(axis=0)
    std = np.where(std == 0, 1.0, std)
    return mean, std

def apply_standard_scaler(X: np.ndarray, mean: np.ndarray, std: np.ndarray) -> np.ndarray:
    return (X - mean) / std

def fit_top_k_selector(X: np.ndarray, y: np.ndarray, k: int) -> np.ndarray:
    Xc = X - X.mean(axis=0)
    yc = y - y.mean()
    num = (Xc * yc[:, None]).sum(axis=0)
    den = np.sqrt((Xc ** 2).sum(axis=0)) * np.sqrt((yc ** 2).sum()) + 1e-12
    corr = num / den
    order = np.argsort(-np.abs(corr))
    return order[:k]

def apply_selector(X: np.ndarray, columns: np.ndarray) -> np.ndarray:
    return X[:, columns]

def leaky_scale_pipeline(X, y, train_idx, test_idx):
    mean, std = fit_standard_scaler(X)                       # LEAK: fit on all of X
    Xs = apply_standard_scaler(X, mean, std)
    return Xs[train_idx], Xs[test_idx]

def honest_scale_pipeline(X, y, train_idx, test_idx):
    mean, std = fit_standard_scaler(X[train_idx])             # fit on TRAIN ONLY
    X_train = apply_standard_scaler(X[train_idx], mean, std)
    X_test = apply_standard_scaler(X[test_idx], mean, std)     # apply, never refit
    return X_train, X_test

def leaky_select_pipeline(X, y, train_idx, test_idx, k):
    columns = fit_top_k_selector(X, y, k)                     # LEAK: selected using all of y
    Xs = apply_selector(X, columns)
    return Xs[train_idx], Xs[test_idx], columns

def honest_select_pipeline(X, y, train_idx, test_idx, k):
    columns = fit_top_k_selector(X[train_idx], y[train_idx], k)   # selected using TRAIN ONLY
    X_train = apply_selector(X[train_idx], columns)
    X_test = apply_selector(X[test_idx], columns)
    return X_train, X_test, columns

import numpy as np
from sklearn.linear_model import Ridge
from sklearn.metrics import r2_score

def make_folds(n: int, k: int, rng: np.random.Generator) -> list[np.ndarray]:
    idx = rng.permutation(n)
    return np.array_split(idx, k)

def cv_r2_given_folds(X, y, alpha: float, folds: list[np.ndarray]) -> np.ndarray:
    scores = []
    for i in range(len(folds)):
        test_idx = folds[i]
        train_idx = np.concatenate([folds[j] for j in range(len(folds)) if j != i])
        model = Ridge(alpha=alpha).fit(X[train_idx], y[train_idx])
        scores.append(r2_score(y[test_idx], model.predict(X[test_idx])))
    return np.array(scores)

def nested_select_alpha(X_train, y_train, alphas, k, rng):
    folds = make_folds(len(y_train), k, rng)
    means = {a: cv_r2_given_folds(X_train, y_train, a, folds).mean() for a in alphas}
    return max(means, key=means.get)

## Assessment

Graded on the judgment trail — **predict, locate, fix, prove** — never on "the accuracy went down
after I changed something." A learner who fixes a bug they cannot explain, locate independently, or
prove the fix for scores no higher than a learner who never found it.

**Task.** You are given `assessment_pipeline.py` and its printed output (provided at assessment
time). The pipeline contains **exactly one** planted violation of the evaluation contract, drawn
from the taxonomy this module built — target leakage via a proxy column, preprocessing (scaling or
feature selection) fit before the split, or group leakage from a repeated-entity dataset — but you
are told neither which one nor where. The printed metrics look strong. Your data-generating seed and
the exact construction parameters are withheld from the module materials, exactly as in M04's
assessment.

1. **Predict, in writing, before reading past the pipeline's printed summary metrics:** (a) whether
   the reported score clears a "too good to be true" threshold relative to a domain-plausible
   ceiling and a computed baseline (majority-class, mean-predictor, or persistence — pick the one
   that matches this problem's structure, and justify the choice); (b) which category or categories
   of leak from Lesson 3's taxonomy you consider most likely given the shape of the pipeline code
   you can see (its features, its split logic, its preprocessing order), and why; (c) what
   diagnostic evidence (a specific number or comparison, not "I'll look at the code") would confirm
   or rule out each candidate category.
2. **Locate** the specific line, column, or step responsible, using diagnostic tooling built in this
   module's labs (a correlation-or-importance ranking, an ablation re-score, a re-split under a
   stricter/more realistic strategy, an inspection of what a preprocessing step was fit on) —
   applied to *this* pipeline, not copied from a lab's specific column names.
3. **Fix** the pipeline: remove or correct the offending step, preserving everything about the
   pipeline that was not the bug.
4. **Prove** the fix: report the corrected metric, the corrected baseline comparison, and — this is
   the step a passing script cannot fake — a short, specific explanation of *why* the corrected
   number is now trustworthy in a way the original number was not (what question does the corrected
   split/preprocessing/feature set actually answer, and does it match the question this model will
   really be asked in deployment).

**Gaming resistance.** Three defenses, stacked. First, the withheld seed, withheld construction
parameters, and unstated bug category mean a learner cannot pass by pattern-matching Lab 3's exact
column name (`collections_call_flag`) or Lab 1's exact numbers — only a learner who has internalized
*why* a score is suspicious, and *how* to interrogate a pipeline they've never seen before, can
transfer the diagnostic procedure to an unannounced bug. Second, locating the *symptom* (a score
that's too good) is easy and worth little on its own; the rubric weights **Locate** on whether the
learner used a specific, falsifiable diagnostic (a ranking, an ablation, a re-split) rather than
guessing-and-checking column removals until something worked, because guess-and-check does not
transfer to a bug this module's labs didn't rehearse. Third, **Predict** is graded before Locate is
attempted — a learner who writes vague or hedged predictions ("something might be wrong with a
feature") and then successfully locates the bug through undisciplined trial and error still fails
the Predict criterion, because the assessed skill is recognizing *from the numbers alone, before
digging*, that something demands investigation — the same skill a working data scientist needs the
day nobody hands them a labeled "check this pipeline" ticket.

| Criterion | Gaming-resistant because... | Excellent (4) | Adequate (3) | Developing (2) | Insufficient (1) |
|---|---|---|---|---|---|
| **Predict — suspicion from numbers alone** | Must commit to a threshold and a candidate mechanism before any code investigation, on an unannounced bug | Correctly identifies the score as implausible against a well-chosen baseline; names at least one specific, correctly-reasoned candidate leak category with a stated diagnostic that would confirm it | Correctly flags the score as suspicious with a reasonable baseline, but candidate category or diagnostic is vague or only partially justified | Suspicion is stated without a quantified threshold or a specific candidate mechanism | No prediction recorded before locating, or the "too good" judgment is asserted without justification |
| **Locate — diagnostic procedure, not guesswork** | Requires applying a falsifiable tool (ranking / ablation / re-split) to an unseen pipeline, not recalling a lab's answer | Uses a specific diagnostic correctly, correctly identifies the exact offending column/step, and reports the evidence (the number that proved it) | Diagnostic used correctly and the right step is identified, but the evidence supporting the identification is thin or informal | The right step is eventually found only after multiple undiagnosed trial-and-error removals | Wrong step identified as the cause, or the real bug is never located |
| **Fix — minimal, correct correction** | Requires distinguishing the actual bug from everything else that happens to also change the score | The fix removes or corrects only the offending step; every other legitimate part of the pipeline (real features, real preprocessing, real split ratio) is preserved unchanged | Fix is correct but also removes or alters something unrelated to the bug, muddying the before/after comparison | Fix partially addresses the bug (e.g., re-splits correctly but leaves a leaked column in place) | No working fix, or the "fix" removes the symptom without removing the cause (e.g., only lowering the reported number without correcting the pipeline) |
| **Prove — trustworthiness argument, not just a new number** | Requires explaining *why* the new number is trustworthy, which a learner who got lucky cannot fabricate convincingly | Reports the corrected metric and baseline, and explicitly connects the corrected split/feature set to the real deployment question it now honestly answers | Reports a corrected, plausible number, but the trustworthiness explanation is generic ("now it's fixed") rather than specific to what changed | Corrected number reported with no explanation of why it should now be believed | No corrected number reported, or the explanation contradicts the mechanics of the fix actually made |

A submission that scores 4 on Fix but 1 on Predict and Locate does not pass — a corrected pipeline
arrived at by deleting columns at random until the number looked more reasonable has not
demonstrated the diagnostic judgment this module exists to certify, even if the final code is
correct.

## Elle pacing notes

**The wall: "my score dropped after I fixed it — did I break something?"** This is the single most
common moment of doubt in this module, and it is *correct* to feel alarmed the first time it
happens, because every prior module in this course rewarded a rising number. Here, a falling number
after removing a leaked column is the entire point, and initially reads as a regression.
**Reroute:** have the learner re-state, out loud or in writing, what the *original* number was
actually measuring (a question deployment will never ask) versus what the *corrected* number
measures (the question deployment will actually ask) — the "drop" is not a worse model, it's the
same model, correctly measured for the first time. This should resolve in one pass, not a lengthy
struggle; if it's still read as "I broke something" after that reframing, intervene directly rather
than let the doubt compound into distrust of every subsequent number in the course.

**The wall: Lab 3's ablation test passes, but the learner can't yet explain *why* the collapse was
so sharp (not gradual).** A learner who successfully ablates `collections_call_flag` and sees the
score collapse to exactly the baseline can still be surprised by how total the collapse was, versus
the gentle, partial drop from ablating a genuine feature. **Reroute:** point back to the standardized
coefficient comparison in Lesson 3 (2.107 vs. 0.19–0.38) — a proxy this strongly correlated with the
label doesn't just add a little signal on top of the genuine features, it makes them nearly
irrelevant to the fitted model's decision boundary, which is exactly why removing it collapses
performance rather than merely denting it. This is a short, one-fact reroute, not a rebuild of the
lesson.

**The wall: the Assessment's withheld-category setup produces genuine, productive anxiety — "what if
I guess the wrong category and waste time investigating it?"** This is expected and should not be
short-circuited. **Let it run.** A learner who checks their most-likely candidate first, finds no
evidence, and moves methodically to the next candidate has performed exactly the diagnostic
discipline this module is built to certify — the anxiety is proportional to a genuinely open-ended
diagnostic task, which is what real, un-announced leaks feel like. **Intervene only if** a learner
has spent more than roughly 30 minutes making zero forward progress (no candidate ruled in or out,
no diagnostic run) — at that point, the honest non-hint redirect is "which of Lesson 3's three
categories would produce a suspicious number *without* touching test labels, and which would require
a specific kind of repeated-row structure to even be possible" — narrowing by elimination using the
taxonomy, not naming the answer.

**Accelerate condition.** A learner who, in the Predict step, names the correct category *and* the
correct diagnostic evidence that would confirm it — before running anything — has demonstrated the
core assessed skill; let them move directly to Locate/Fix/Prove without requiring a full walk
through every candidate category's diagnostic first (Lab 3's ablation control pattern is enough
evidence of transfer; re-deriving it from scratch under time pressure teaches nothing new).

**Struggle triage, condensed:**

| Symptom | Productive (let it run) | Blocked (intervene) |
|---|---|---|
| Learner alarmed that a "fixed" score is lower than before | No — this should resolve in one reframing pass, not a struggle | If still read as "I broke the model" after the drop-vs-question-measured reframing |
| Learner methodically ruling candidate leak categories in/out via diagnostics, some dead ends | Yes — this is the assessed diagnostic discipline, dead ends included | Past ~30 minutes with zero candidates ruled in or out and no diagnostic run yet |
| Learner surprised by how *total* the leak-column collapse is vs. a genuine feature's partial drop | No — quick, one-fact reroute (the coefficient-magnitude comparison), not a rebuild | If still treated as an unexplained anomaly after the coefficient comparison is shown |
| Learner tries removing columns one at a time with no ranking or ablation logic behind the order | No — this is exactly the "guess and check" pattern the rubric is built to catch and not reward | Whenever observed — redirect to Lab 1/3's diagnostic tools before more guessing |

## Three-tier reading — the number that looked earned

**Tier 1 — material ground.** Every number in this module's worked examples is a verifiable
artifact of a specific, checkable procedure: an $R^2$, an accuracy, an AUC, each computed from code
you can re-run and get the identical value from (to floating-point tolerance, as the labs' tests
confirm against `sklearn`). Leakage is not a matter of opinion or interpretation — the loan-default
example's accuracy moved from 0.887 to 0.987 for a specific, traceable reason (one column whose
definition includes post-outcome information), and that reason is demonstrable, not debatable. This
grounding matters because the temptation, once you've internalized "leakage is everywhere," is to
treat every strong result with generic suspicion; the discipline this module builds is *specific*
suspicion, backed by a diagnostic, not a vague distrust of good numbers in general.

**Tier 2 — what "beats the baseline" suppresses.** A model that clears a baseline by a real, honest
margin has still only answered the question the baseline and the split together defined — and both
of those are choices, not facts handed down by the data. Lesson 4 showed that the *same* trained
model can be reported as "beats chance" (true, against a majority-class baseline) or "doesn't beat
persistence" (also true, against a stronger baseline that matches the data's real structure) — two
honest, leakage-free numbers, computed correctly, that support opposite headlines. The choice of
which baseline to report is rarely neutral: a team under pressure to ship a result has every
incentive to report the comparison that clears the bar, and nothing about "I didn't leak anything"
prevents that choice from being made in bad faith. The technical discipline this module teaches
(honest splits, honest CV, honest baselines) is necessary and is not, by itself, sufficient to
guarantee an honest *claim* — the same clean pipeline can be paired with a baseline chosen because
it's easy to beat rather than because it's the right question to ask.

**Tier 3 — sit with this.** You will, at some point in your career, build a model whose evaluation
pipeline is clean — no leakage, an honest split, cross-validation done correctly, a fair baseline
that beats chance by a real margin — and someone above you will still ask you to describe it in
terms that overstate what it does, or will pick the friendliest of several honestly-computed
comparisons to put in the deck. Every tool this module gave you (the ablation test, the baseline
table, the "what question does this split actually answer" habit) is built to catch a *technical*
violation of the evaluation contract — a leaked column, a bad split, an unfair baseline. None of
those tools can catch, or defend you against, a request to describe an honestly-measured number
dishonestly. The corrected accuracy in Lab 3's ablation — 0.887, tied exactly with a model that
predicts "no default" for everyone — is a true, leakage-free, well-earned number, and it is also a
number that a loan officer's dashboard could quietly relabel from "flags high-risk applicants" to
"87% accurate model," true on its face, misleading in the way that matters most. When the numbers
you produced are honest and the story told about them is not, whose name is on the pipeline, and
whose name is on the deck?
