## Module overview

You will build linear regression twice — once as an algebra problem (solve for the exact
minimum in one shot) and once as an optimization problem (walk downhill toward the minimum,
the same walk you hand-derived in AIE-103-M06). Then you will do the thing sklearn hides
behind `alpha=1.0`: add a penalty term directly into the loss function you already wrote, watch
coefficients move as the penalty strength moves, and explain in writing — before you run
anything — which coefficients a penalty will kill and which it will merely shrink.

By the end of this module you will have four from-scratch estimators (`fit_ols_normal_equations`,
`gradient_descent_ols`, `fit_ridge`, `fit_lasso`) each matched against its scikit-learn
counterpart (`LinearRegression`, `Ridge`, `Lasso`) to numerical tolerances tight enough that
"my code is basically doing the same thing as the library" stops being a belief and becomes
a `np.allclose` assertion in a test file.

The descent: solve it exactly (Lesson 1), then solve it iteratively because "exactly" stops
scaling (Lesson 2), then discover the iterative loss function is just a sum you can add terms
to (Lessons 3–4). Re-ascent: you can now read `Ridge(alpha=2.0)` and know, structurally, what
number is being added to what, instead of treating `alpha` as a knob you turn until the
validation score looks better.

## Lessons

### Lesson 1 — Linear regression as an optimization problem: the normal equations

**Teaching text**

Every linear regression course starts with "fit a line." That framing hides the actual claim:
we are choosing the *one* set of coefficients that minimizes a specific number — the sum of
squared residuals — out of infinitely many lines we could have drawn. Linear regression is not
"finding the pattern." It is solving

$$\hat{w} = \arg\min_{w} \; \lVert y - Xw \rVert_2^2$$

where $X$ is the design matrix (one row per example, one column per feature, plus a column of
1s for the intercept if you fold it into $w$), $y$ is the target vector, and $w$ is the
coefficient vector you're solving for.

Because this loss is a smooth, convex quadratic in $w$, calculus gives you the minimum in
closed form. Take the gradient of the loss with respect to $w$, set it to zero, and solve:

$$\nabla_w \lVert y - Xw \rVert^2 = -2X^T(y - Xw) = 0 \;\;\Rightarrow\;\; X^TXw = X^Ty \;\;\Rightarrow\;\; w = (X^TX)^{-1}X^Ty$$

This is the **normal equation**. It is not an approximation, not an iterative estimate — it is
the exact minimizer, computed in one shot, whenever $X^TX$ is invertible. This is the same
"set the gradient to zero" move you did by hand in AIE-103 for scalar functions; the only new
idea here is that the gradient of a quadratic form in vector notation ($X^TXw - X^Ty$) still
reduces to a `linear system you can hand to np.linalg.solve`.

In practice you never compute $(X^TX)^{-1}$ explicitly — matrix inversion is numerically worse
and asymptotically no faster than solving the linear system directly. `np.linalg.solve(A, b)`
uses LU decomposition under the hood and is both faster and more numerically stable than
`np.linalg.inv(A) @ b`. This is the same "don't do the naive thing just because it's what the
formula says" lesson as choosing the right data structure in AIE-110 — the formula and the
implementation are different objects.

Cost: forming $X^TX$ is $O(np^2)$ ($n$ = rows, $p$ = columns), and solving the resulting
$p \times p$ system is $O(p^3)$. For $p$ in the tens or low hundreds this is instant. For $p$
in the tens of thousands (wide feature spaces — one-hot encodings, polynomial expansions),
$O(p^3)$ stops being instant, which is the seed of Lesson 2's motivation: gradient descent's
per-step cost is $O(np)$, and you trade an exact one-shot answer for a cheap-per-step
iterative one.

**Worked example**

```python
import numpy as np

rng = np.random.default_rng(201)
n, p = 200, 3
X = rng.normal(size=(n, p))
true_w = np.array([2.5, -1.0, 0.0])   # feature 2 is a true null — coefficient should land near 0
true_b = 4.0
y = X @ true_w + true_b + rng.normal(scale=1.0, size=n)

def fit_ols_normal_equations(X, y):
    """Exact OLS via the normal equations. Returns (intercept, coefficients)."""
    n = X.shape[0]
    X_design = np.hstack([np.ones((n, 1)), X])   # prepend bias column
    XtX = X_design.T @ X_design
    Xty = X_design.T @ y
    theta = np.linalg.solve(XtX, Xty)             # solve, never invert
    return theta[0], theta[1:]

b_hat, w_hat = fit_ols_normal_equations(X, y)
print(b_hat, w_hat)
# 4.0153 [ 2.3766 -0.9583  0.0154 ]
```

Note what the fitted values are versus the ground truth: `true_w = [2.5, -1.0, 0.0]` but the
fit recovers `[2.38, -0.96, 0.02]`. This gap is not a bug — it's sampling noise from
`rng.normal(scale=1.0, ...)` propagating through a finite sample of 200 points. A learner who
expects the fit to exactly reproduce `true_w` has misunderstood what "true" means in a
generative model versus what "fitted" means from a finite, noisy sample. This distinction is
load-bearing for the entire module: regularization deliberately *adds bias* to reduce this kind
of sampling variance, and you cannot evaluate that trade honestly if you think an unregularized
fit is supposed to recover the ground truth exactly.

**Named misconceptions**

- **"The normal equation is the definition of linear regression."** It's one solution method for
  one loss function (squared error). Change the loss (absolute error, Huber loss, quantile
  loss) and there is no closed form — you're in gradient-descent territory immediately. The
  closed form is a property of squared-error loss being quadratic, not a property of "linear
  regression" as an idea.
- **"If $X^TX$ is invertible, the normal equation always gives a good answer."** Invertible and
  *well-conditioned* are different things. Two nearly collinear columns make $X^TX$ technically
  invertible but numerically close to singular — `np.linalg.solve` will return an answer, and
  that answer's coefficients can be wildly unstable (large magnitude, opposite signs) even
  though the *predictions* are fine. This is the mechanical root of why Lesson 3's ridge penalty
  exists: $X^TX + \lambda I$ is invertible even when $X^TX$ is not.
- **"Centering/scaling the data is just good practice, not something with mathematical
  consequences."** Whether you include an intercept column and whether you standardize features
  changes what the coefficients *mean* and, critically for Lesson 3, whether penalizing the
  intercept makes sense (it doesn't — you never regularize the bias term, and you almost always
  standardize features before regularizing, because penalty strength interacts with feature
  scale: a feature measured in millimeters gets penalized far more per-unit than the same
  feature measured in meters, for no principled reason).

### Lesson 2 — Gradient descent for linear regression

**Teaching text**

The normal equation is exact and cheap when $p$ is small. It stops being cheap — or feasible,
if $X^TX$ becomes singular or you're not holding the whole design matrix in memory — as $p$ and
$n$ grow. Gradient descent is the tool you already built in AIE-103-M06: instead of solving for
the minimum in one algebraic step, you take the gradient of the loss, and repeatedly step in
the direction that decreases it.

Recall the gradient from Lesson 1: $\nabla_w \lVert y - Xw \rVert^2 = -2X^T(y-Xw)$. Averaged
over $n$ examples (so the update doesn't depend on dataset size), the mean-squared-error loss
and its gradient are:

$$L(w, b) = \frac{1}{n}\sum_i (y_i - \hat{y}_i)^2, \quad \hat{y}_i = X_i \cdot w + b$$

$$\nabla_w L = \frac{2}{n}X^T(\hat{y} - y), \qquad \nabla_b L = \frac{2}{n}\sum_i(\hat{y}_i - y_i)$$

The update rule is exactly the one from AIE-103-M06: `w -= lr * grad_w`. Batch gradient descent
computes this gradient using *all* $n$ examples on every step — the full batch, not a
mini-batch — which is what "batch" means here.

Two things determine whether this converges to the same answer the normal equation gives:
**learning rate** and **iteration count**. Because the OLS loss surface is convex with a single
global minimum, gradient descent is *guaranteed* to converge to the same point the normal
equation finds — provided the learning rate is small enough. Too large a learning rate doesn't
just converge slowly, it **diverges**: each step overshoots the minimum by more than the
previous step, and the loss grows without bound. This is not a subtle numerical artifact — it's
visible within single-digit iteration counts and the loss value explodes toward `inf` or `nan`.

Feature scaling matters more here than in Lesson 1. The normal equation solves the whole system
at once regardless of column scale. Gradient descent takes *one* learning rate for *all*
coefficients simultaneously — if one feature has values in the thousands and another has values
between 0 and 1, the loss surface is a long, narrow ellipse, and a learning rate that's stable
for one direction will be unstable for the other. Standardizing features (zero mean, unit
variance) before running gradient descent turns that ellipse closer to a circle and lets one
learning rate work for every coefficient.

**Worked example**

```python
import numpy as np

# same data as Lesson 1, standardized — required for a shared learning rate to behave
X_mean, X_std = X.mean(axis=0), X.std(axis=0)
Xs = (X - X_mean) / X_std

def gradient_descent_ols(X, y, lr=0.1, n_iters=1000):
    """Batch gradient descent for OLS. Returns (intercept, coefficients, mse_history)."""
    n, p = X.shape
    w = np.zeros(p)
    b = 0.0
    history = []
    for _ in range(n_iters):
        y_pred = X @ w + b
        error = y_pred - y
        grad_w = (2.0 / n) * (X.T @ error)
        grad_b = (2.0 / n) * np.sum(error)
        w -= lr * grad_w
        b -= lr * grad_b
        history.append(np.mean(error ** 2))
    return b, w, history

b_gd, w_gd, history = gradient_descent_ols(Xs, y, lr=0.5, n_iters=500)
print(b_gd, w_gd)
# 4.3135 [ 2.4261 -1.0050  0.0157 ]   <- matches closed-form fit on Xs to 1e-10
print(history[0], history[-1])
# 26.64 -> 1.01   (MSE drops from the zero-init baseline to the converged minimum)
```

Three learning rates on the same data show the whole story:

| `lr`  | MSE @ iter 10 | MSE @ iter 100 | MSE @ iter 500 | Behavior |
|-------|---------------|----------------|----------------|----------|
| 0.5   | 1.0107        | 1.0107         | 1.0107         | converges almost immediately |
| 0.1   | 1.4627        | 1.0107         | 1.0107         | converges, slower |
| 0.01  | 18.79         | 1.47           | 1.0107         | converges, needs ~160 iters to get close |
| 3.0   | 6.5e2 → 1.7e28 (by iter 20) | — | — | **diverges** |

**Named misconceptions**

- **"Gradient descent gives an approximate answer; the normal equation gives the true answer."**
  For OLS specifically, both converge to the *same point* — the unique global minimum of a
  convex loss. Gradient descent's answer is only "approximate" in the sense that you stopped
  it after a finite number of iterations before it fully converged; run it long enough at a
  safe learning rate and the gap to the closed-form answer shrinks to floating-point noise.
  They are not two different algorithms with two different targets.
- **"A smaller learning rate is always safer, so when in doubt, go smaller."** Smaller learning
  rates are safer against divergence, but they are not free — `lr=0.01` above needed roughly
  16× the iterations of `lr=0.5` to reach the same MSE. "Safe" and "cheap" trade off directly;
  picking a learning rate is a real design decision, not a matter of maximizing caution.
- **"If the loss goes down for a while, then explodes, something is wrong with my code."**
  Divergence from too-large a learning rate can *look* like decreasing loss for the first few
  steps before the overshoot compounds — the callback to AIE-103-M06 is that this is the same
  oscillate-then-diverge behavior from 1D gradient descent, just harder to see by eye in
  multiple dimensions. Plotting the loss curve, not eyeballing the final number, is the fix —
  and it is exactly the Verify step every lab in this module requires.

### Lesson 3 — Ridge regression: the L2 penalty as a literal term in the loss

**Teaching text**

Regularization is not a separate algorithm from linear regression — it is linear regression
with a new term physically added to the loss function you already wrote in Lessons 1 and 2.
**Ridge regression** (L2 regularization) adds the squared magnitude of the coefficient vector:

$$L_{ridge}(w) = \frac{1}{n}\lVert y - Xw \rVert^2 + \alpha \lVert w \rVert_2^2, \qquad \lVert w \rVert_2^2 = \sum_j w_j^2$$

Two consequences follow directly from adding this term, and both are visible in the gradient:

$$\nabla_w L_{ridge} = \frac{2}{n}X^T(Xw - y) + 2\alpha w$$

First, the closed-form solution still exists — set the gradient to zero and solve, same move
as Lesson 1 — and it becomes:

$$w_{ridge} = (X^TX + n\alpha I)^{-1}X^Ty$$

This is *why* ridge regression exists mechanically, not just statistically: adding $n\alpha I$
to $X^TX$ before inverting makes the matrix invertible even when $X^TX$ alone is singular or
near-singular (the collinearity problem flagged as a misconception in Lesson 1). Ridge is, at
the linear-algebra level, a numerical stability fix that happens to also reduce variance.

Second, look at the gradient step this produces: `w -= lr * (ols_grad + 2*alpha*w)`, which
rearranges to `w -= lr*2*alpha*w` (shrink toward zero) `- lr*ols_grad` (pull toward the data
fit). Every single gradient step multiplicatively shrinks $w$ toward zero *before* the data term
gets to move it anywhere. This shrinkage is smooth and proportional — a large coefficient gets
shrunk by more absolute amount than a small one, but a coefficient exactly at zero experiences
zero shrinkage pressure to begin with. **This is the mechanical reason ridge regression shrinks
coefficients continuously but essentially never sets any of them to exactly zero**: the penalty
gradient $2\alpha w$ vanishes as $w \to 0$, so there's no force pushing a small-but-nonzero
coefficient the rest of the way to exactly zero. Lesson 4's L1 penalty has a gradient that does
*not* vanish at zero — that's the entire mechanical difference between shrinkage and sparsity,
and you can see it by comparing the two gradients side by side before running a single line of
code.

That per-coordinate view explains why ridge never zeros a coefficient, but it is not the whole
story for *correlated* coefficients: the penalty gradient touches each $w_j$ independently, but
the data-fit gradient $\frac{2}{n}X^T(Xw-y)$ does not — its $X^TX$ term couples every pair of
correlated columns. The worked example below shows what that coupling does in practice, and it
is sharper than "ridge shrinks correlated coefficients together": near-perfectly collinear
features can have a wildly *unstable* split under plain OLS ($\alpha=0$), and it is specifically
adding the penalty that pulls the split back toward even and keeps it there.

As $\alpha \to 0$, ridge reduces exactly to OLS. As $\alpha \to \infty$, every coefficient is
driven to zero regardless of its relationship to $y$ — the penalty dominates the loss entirely.
Tracking coefficient values across a sweep of $\alpha$ values produces a **coefficient path**:
a plot where the x-axis is $\alpha$ (usually log-scaled) and each line is one coefficient's
trajectory from its OLS value down toward zero. Reading a coefficient path is a diagnostic
skill: which coefficients survive at moderate $\alpha$ tells you which features the model
leans on hardest once you've penalized complexity — not just which features "looked
significant" in an unregularized fit.

**Worked example**

```python
import numpy as np
from sklearn.linear_model import Ridge

# n=300 correlated-feature dataset: f0, f1 are near-duplicates of a shared latent z
# (r ~ 0.99), f2 is standard-normal noise with true coefficient 0
rng = np.random.default_rng(7)
n = 300
z = rng.normal(size=n)
f0 = z + rng.normal(scale=0.05, size=n)
f1 = z + rng.normal(scale=0.05, size=n)
f2 = rng.normal(size=n)
X = np.column_stack([f0, f1, f2])
true_w = np.array([1.5, 1.5, 0.0])
y = X @ true_w + rng.normal(scale=0.3, size=n)

Xs = (X - X.mean(0)) / X.std(0)
ys = y - y.mean()      # center y; never regularize the intercept

def fit_ridge_closed_form(X, y, alpha):
    """Ridge via the closed form. Loss = (1/n)||y-Xw||^2 + alpha*||w||^2."""
    n, p = X.shape
    return np.linalg.solve(X.T @ X + n * alpha * np.eye(p), X.T @ y)

for alpha in [0.0, 0.05, 0.5, 2.0, 8.0]:
    w = fit_ridge_closed_form(Xs, ys, alpha)
    print(f"alpha={alpha:5.2f}  w={np.round(w, 3)}  |w0-w1|={abs(w[0]-w[1]):.4f}")
# alpha= 0.00  w=[ 1.945  0.821 -0.015]  |w0-w1|=1.1242   <- OLS (no penalty): near-perfect
#                                            collinearity between f0/f1 makes the exact SPLIT
#                                            between them numerically unstable, even though
#                                            their sum (~2.77) is close to the true 1.5+1.5=3.0
# alpha= 0.05  w=[ 1.376  1.322 -0.006]  |w0-w1|=0.0543   <- a small penalty already pulls
#                                            the split most of the way back toward even
# alpha= 0.50  w=[ 1.107  1.102  0.027]  |w0-w1|=0.0054
# alpha= 2.00  w=[ 0.691  0.689  0.040]  |w0-w1|=0.0013
# alpha= 8.00  w=[ 0.276  0.276  0.022]  |w0-w1|=0.0003   <- f0/f1 converge to nearly identical
#                                            shrunk values; f2 (true 0) stays small throughout
#                                            but never hits exact 0 at any alpha
```

The `alpha=0.0` row is the important surprise: this is plain OLS, and it does *not* split the
shared signal evenly between two near-duplicate features — collinearity (Lesson 1's second
misconception) makes the exact per-feature split numerically unstable even though the *sum*
`w[0] + w[1]` sits close to the true combined effect. The moment any penalty is added, the
split snaps back toward even and stays there as `alpha` grows. This is **ridge's grouping
effect**: because the L2 penalty term is symmetric in every coordinate, and because $X^TX$
couples `w[0]` and `w[1]` through their correlation even though the *penalty gradient*
$2\alpha w$ touches each coordinate independently, minimizing the combined loss with two
near-identical columns pulls their coefficients toward each other, not apart. Ridge does not
just shrink correlated coefficients — for sufficiently collinear features, it actively
stabilizes an OLS split that was never reliable to begin with.

Matched against `sklearn.linear_model.Ridge(alpha=alpha * n, fit_intercept=False)` on the same
standardized, centered data, the closed-form weights agree to `atol=1e-6` — this is the
tolerance bar this module uses, the same bar AIE-102 and AIE-103 used for their from-scratch
implementations.

**Named misconceptions**

- **"Ridge and Lasso do the same thing, just with a different exponent."** They do structurally
  different things to the *solution*, not just the loss formula. Ridge shrinks continuously;
  Lasso (Lesson 4) performs feature selection by driving coefficients to *exactly* zero. Same
  general idea (penalize magnitude), mechanically different consequence.
- **"A higher `alpha` in sklearn always means more regularization, so I can guess the direction
  without checking the convention."** Different libraries and different textbooks scale the
  penalty term differently — some average by $n$, some don't; some use $\alpha$, some use
  $\lambda = 1/(2C)$ for a `C` you'd recognize from `LogisticRegression`. This module derives
  the exact conversion factor (`n * alpha`) needed to match this scratch implementation against
  sklearn's `Ridge` — because "roughly more regularization" is not the same claim as "the same
  loss function," and only the latter is checkable.
- **"If ridge doesn't zero out irrelevant features, it's not really doing feature selection, so
  it's not useful for reducing model complexity."** Ridge was never meant to select features —
  it reduces variance from correlated or noisy inputs while keeping every feature in the model
  at a smaller weight. Judging ridge by Lasso's job description is a category error the next
  lesson exists to prevent by contrast.

### Lesson 4 — Lasso, sparsity, and the arbitrary tie-break; regularized logistic regression

**Teaching text**

Swap the L2 penalty for an **L1** penalty — the sum of absolute values instead of squared
values — and you get **Lasso** regression:

$$L_{lasso}(w) = \frac{1}{2n}\lVert y - Xw \rVert^2 + \alpha \lVert w \rVert_1, \qquad \lVert w \rVert_1 = \sum_j |w_j|$$

The critical difference from Ridge is not the exponent — it's that $|w_j|$ is **not
differentiable at $w_j = 0$**. Its subgradient at zero is the entire interval $[-1, 1]$, not a
single vanishing value the way $2\alpha w_j \to 0$ vanishes for Ridge. This single fact is the
entire mechanical reason Lasso produces *sparse* solutions — exact zeros — while Ridge does
not. There is no closed form for Lasso (no smooth gradient to set to zero), so it's solved
iteratively, typically with **coordinate descent**: hold every coefficient fixed except one,
solve that one exactly, move to the next, repeat until convergence.

For each coordinate $j$, minimizing the loss with every other coefficient held fixed reduces to
one-dimensional **soft thresholding**: compute the partial residual correlation
$\rho_j = X_j^T r$ (where $r$ is the residual with feature $j$'s own contribution removed), then

$$w_j = \frac{\text{ST}(\rho_j,\; n\alpha)}{\lVert X_j \rVert^2}, \qquad \text{ST}(x, \lambda) = \text{sign}(x)\max(|x| - \lambda, 0)$$

`ST` is the soft-threshold function: it shrinks $x$ toward zero by $\lambda$, and clips
anything inside $[-\lambda, \lambda]$ to *exactly* zero. That clipping-to-exactly-zero step is
the sparsity — and it's a direct algebraic consequence of the L1 penalty's non-differentiability
at zero, not a rounding convention or a post-hoc "small coefficients get pruned" heuristic
bolted on afterward.

Coordinate descent's mechanics produce a consequence worth sitting with before you run the
lab: when two features are highly correlated, coordinate descent updates them **one at a time,
in whatever order the columns happen to be stored in**. The first feature visited absorbs
credit for the shared signal; by the time the second correlated feature is visited, most of the
residual it could explain has already been claimed. The result is that Lasso can assign wildly
different coefficients to two nearly-identical features — not because one feature matters more,
but because of which column index it happened to occupy. Swap the column order and the split
swaps too, with the *same data* and the *same alpha*.

**Regularized logistic regression** extends the same pattern to classification: swap the
squared-error loss for log loss, keep the penalty term, and gradient descent looks almost
identical to Lesson 2's OLS descent:

$$L(w,b) = \frac{1}{n}\sum_i \Big[-y_i\log\hat{p}_i - (1-y_i)\log(1-\hat{p}_i)\Big] + \alpha\lVert w\rVert_2^2, \qquad \hat{p}_i = \sigma(Xw+b)$$

$$\nabla_w L = \frac{1}{n}X^T(\hat{p} - y) + 2\alpha w$$

Compare this gradient to Lesson 2's OLS gradient — the only structural difference is
`error = sigmoid(z) - y` instead of `error = z - y`, plus the same `+ 2*alpha*w` penalty term
from Lesson 3. Everything you built for linear regression — the loss-plus-penalty structure,
the shrinkage-versus-sparsity distinction, the standardize-before-you-penalize discipline —
transfers directly. This is why the module builds linear regression first: logistic regression
is not a new topic, it's the same optimization skeleton with a different link function nailed
onto the front of the loss.

**Worked example**

```python
import numpy as np
from sklearn.linear_model import Lasso

def soft_threshold(x, lam):
    return np.sign(x) * np.maximum(np.abs(x) - lam, 0.0)

def fit_lasso_coord_descent(X, y, alpha, n_iters=3000, tol=1e-10):
    n, p = X.shape
    w = np.zeros(p)
    col_sq = np.sum(X ** 2, axis=0)
    for _ in range(n_iters):
        w_old = w.copy()
        for j in range(p):
            residual = y - X @ w + X[:, j] * w[j]   # add feature j's own contribution back
            rho = X[:, j] @ residual
            w[j] = soft_threshold(rho, alpha * n) / col_sq[j] if col_sq[j] > 0 else 0.0
        if np.max(np.abs(w - w_old)) < tol:
            break
    return w

# same near-duplicate f0/f1 dataset as Lesson 3 (r ~ 0.997), column order [f0, f1, f2]
w_orig = fit_lasso_coord_descent(Xs, ys, alpha=0.05)
print(w_orig)
# [1.907  0.808  -0.000]   <- f0 absorbs most of the shared signal, f1 gets the leftover

# same data, columns reordered to [f1, f0, f2] — nothing else changed
Xrev = np.column_stack([f1, f0, f2])
Xrevs = (Xrev - Xrev.mean(0)) / Xrev.std(0)
w_swapped = fit_lasso_coord_descent(Xrevs, ys, alpha=0.05)
print(w_swapped)
# [0.808  1.907  -0.000]   <- the split flips exactly. Same data, same alpha, different column order.
```

The two irrelevant/near-zero features (`f2` here, and in Lesson 3's 6-feature dataset) reach
zero at a small `alpha` in every ordering. It is specifically the *correlated pair* whose split
is order-dependent — the coefficients being zeroed are stable; which of two correlated
*survivors* gets the larger share is not.

**Named misconceptions**

- **"Lasso picks the 'more important' feature and drops the redundant one."** Section above:
  coordinate descent picks whichever correlated feature it visits first in that pass, and the
  choice flips under a column reorder with identical data and identical `alpha`. "Lasso
  selected feature A over feature B" is, for near-duplicate features, closer to a coin flip
  landing heads than a discovery about A being more predictive than B.
- **"A coefficient of exactly 0.000 from Lasso means the model found strong evidence the feature
  doesn't matter."** It means the *soft-threshold* clipped it — which happens whenever
  $|\rho_j| \le n\alpha$, a threshold you chose. Raise `alpha` and features with real predictive
  signal get clipped too (see the coefficient-path sweep in Lab 3). Zero is a statement about
  where you set the dial, filtered through evidence — not a pure statement about the world.
- **"Since logistic regression uses log loss instead of squared error, none of the linear
  regression machinery carries over."** The gradient-descent loop, the standardize-before-
  penalizing discipline, the shrinkage-vs-sparsity behavior of L2 vs L1, even the numerical
  convention mismatch between this module's `alpha` and sklearn's `C` (`C = 1/(2n·alpha)`,

def fit_ols_normal_equations(X: np.ndarray, y: np.ndarray) -> tuple[float, np.ndarray]:
    n = X.shape[0]
    X_design = np.hstack([np.ones((n, 1)), X])

    theta = np.linalg.solve(XtX, Xty)
    return theta[0], theta[1:]

```python
import numpy as np

def gradient_descent_ols(
    X: np.ndarray, y: np.ndarray, lr: float = 0.1, n_iters: int = 1000
) -> tuple[float, np.ndarray, list[float]]:
    n, p = X.shape
    w = np.zeros(p)
    b = 0.0
    history = []
    for _ in range(n_iters):
        y_pred = X @ w + b
        error = y_pred - y
        grad_w = (2.0 / n) * (X.T @ error)
        grad_b = (2.0 / n) * np.sum(error)
        w -= lr * grad_w
        b -= lr * grad_b
        history.append(float(np.mean(error ** 2)))
    return b, w, history
```

```python
import numpy as np

def fit_ridge_closed_form(X: np.ndarray, y: np.ndarray, alpha: float) -> np.ndarray:
    n, p = X.shape
    return np.linalg.solve(X.T @ X + n * alpha * np.eye(p), X.T @ y)

def soft_threshold(x, lam):
    return np.sign(x) * np.maximum(np.abs(x) - lam, 0.0)

def fit_lasso_coord_descent(X, y, alpha, n_iters=3000, tol=1e-10):
    n, p = X.shape
    w = np.zeros(p)
    col_sq = np.sum(X ** 2, axis=0)
    for _ in range(n_iters):
        w_old = w.copy()
        for j in range(p):
            residual = y - X @ w + X[:, j] * w[j]
            rho = X[:, j] @ residual
            w[j] = soft_threshold(rho, alpha * n) / col_sq[j] if col_sq[j] > 0 else 0.0
        if np.max(np.abs(w - w_old)) < tol:
            break
    return w
```

## Elle pacing notes

**The wall: closed-form-to-gradient-descent is a much smaller step than it feels like.**
Learners coming off AIE-103-M06 often expect gradient descent for linear regression to feel new
and hard. It's usually the opposite problem: because they already hand-derived 1D gradient
descent, Lesson 2 can feel like "the same thing but with vectors," and learners rush past the
standardization requirement because "it worked without it last time" (in 1D, or in
low-dimensional toy examples where feature scales happened to be similar). The actual wall
shows up quietly in Lab 2 when a learner skips standardization on a dataset with mismatched
feature scales and gets divergence they can't explain because they're staring at the wrong
`lr` value — the bug is in the missing standardization, not the learning rate they're tuning.
**Reroute:** before debugging `lr`, have them print `X.std(axis=0)` per column. If the ratio of
max to min standard deviation across columns exceeds ~5–10x, that's very likely the actual bug,
and no learning rate will look "correct" until it's fixed.

**The wall: "my numbers don't match sklearn" almost always means a scaling-convention
mismatch, not a math error.** This is the single most common stall point in Lessons 3–4 and
Labs 1–3, by a wide margin. A learner gets Ridge working, checks it against
`sklearn.linear_model.Ridge(alpha=same_number)`, and the coefficients don't match — because
sklearn's `alpha` and this module's `alpha` are scaled by a factor of `n` (derived explicitly
in Lesson 3, restated in the Lab 3 test file's `alpha * Xs.shape[0]`). This is productive
struggle exactly once: a learner working through the derivation by hand (write out both loss
functions, set them proportional, solve for the conversion factor) is doing real work that
transfers to reading any new library's regularization API for the rest of their career. It
becomes unproductive struggle past about 20 minutes of blind trial-and-error adjustment of the
`alpha` value hoping for a match — at that point, redirect them to write out
$L_{mine}(w) = \frac{1}{n}\lVert\cdot\rVert^2 + \alpha\lVert w\rVert^2$ and
$L_{sklearn}(w) = \lVert\cdot\rVert^2 + \alpha_{sk}\lVert w\rVert^2$ side by side and multiply
through by $n$ — the conversion falls out in one line once the two loss functions are actually
written next to each other instead of guessed at from memory.

**The wall: the Lasso column-reorder result reads as "my code has a bug."** This is the
single most important productive struggle in the module, and Elle-style pacing means *resisting
the urge to reassure too early*. When a learner sees `w_swapped[0] == w_original[1]` and their
first reaction is "I must have a bug in my coordinate descent loop," let them investigate for a
genuine stretch (10–15 minutes is reasonable) — checking the loop, the indexing, re-deriving
soft-threshold by hand — before confirming this is the *expected, correct, and pedagogically
central* result. The productive version of this struggle is a learner who re-derives why
coordinate order matters from the update rule itself. The unproductive version is a learner who
concludes "coordinate descent is broken" and starts hunting for a different algorithm instead
of sitting with the implication. If a learner is still convinced it's a bug after 20 minutes,
the fastest unstick is running `fit_lasso_coord_descent` with `n_iters=1` and printing `w` after
that single pass — watching the first coordinate claim nearly all the shared signal in one step
makes the mechanism visible in a way the fully-converged result does not.

**Accelerate condition.** A learner who derives the Lasso closed-form-doesn't-exist argument
unprompted (recognizing $|w_j|$'s non-differentiability at zero *before* Lesson 4 states it,
perhaps while still finishing Lesson 3's ridge closed form and wondering "why can't I just do
this for L1") is ready to skip straight to Lab 3's coordinate-descent Build step and treat the
teaching text as a check on their own derivation rather than new material. Do not slow this
learner down by making them read Lesson 4's full worked example line by line — hand them the
Predict step for Lab 3 directly.

## Three-tier reading — the reordering result, held up to the light

**Tier 1 — material ground.** L1-regularized linear and logistic models are in production use
for credit scoring, insurance underwriting, and clinical risk stratification specifically
*because* they are sparse and therefore "interpretable" — a model with 12 nonzero coefficients
out of 400 candidate features is presented to regulators, loan officers, and clinicians as more
explainable than a dense model using all 400. This is a verifiable, structural fact about why
Lasso and Lasso-like penalties (elastic net, group lasso) are chosen in regulated domains, not
a critique — sparse coefficients genuinely are easier for a human to audit than dense ones, and
that's a real, defensible reason to prefer L1 in a setting where someone has to be able to point
at the model and say what it used.

**Tier 2 — what "interpretable because sparse" suppresses.** Lab 3's reordering test is not a
toy exercise — it is the entire content of this tier made checkable in code. When a Lasso model
drops "zip code" and keeps "years at current address" (or the reverse) because those two
features were correlated at 0.9 in the training data, the deployed explanation — "the model
uses years at current address, not zip code, so it doesn't rely on geography" — is describing a
coordinate-descent tie-break as if it were a finding about the world. The feature that got
zeroed was not found to be irrelevant; it was found to be *redundant with whatever got fit
first*, which depends on solver internals (column order, warm-start values, convergence
tolerance) that have nothing to do with the underlying phenomenon. Regulatory and journalistic
accounts of "algorithmic fairness through feature exclusion" almost never distinguish these two
claims — "the model doesn't use race" is treated as settled once a race-correlated feature has
a zero coefficient, when Lab 3 demonstrated in your own code that the *other* correlated
feature could just as easily have been the one that hit zero, carrying the same predictive
signal under a different name. Sparsity is real; the story that sparsity tells about *which*
variable "mattered" is, for correlated features, substantially a story about the solver.

**Tier 3 — sit with this.** A regulator asks the team that shipped your L1-regularized credit
model for an explanation of a denial. Your model's nonzero coefficients are `years_at_address`
and `income`; `zip_code` — correlated with `years_at_address` at 0.89 in the training data — was
zeroed by Lasso. You now know, because you proved it yourself in Lab 3, that if the feature
columns had been ordered differently, or if a slightly different `alpha` or random warm-start
had been used, `zip_code` might have survived instead and `years_at_address` might have been
zeroed — carrying the same shared signal under a different label, with materially different
optics for a regulator checking for geographic (and therefore likely racial) proxy
discrimination. What does it mean to give a truthful "explanation" of a denial when the
specific feature named in that explanation was selected by a tie-break your model's authors did
not choose, cannot fully predict in advance, and could not reproduce identically if asked to
retrain the exact same model on the exact same data in a different feature order? Is "the model
doesn't use zip code" a true statement, a technically-true-but-misleading statement, or not
really a statement about the model at all — and who is responsible for knowing the difference
before the explanation goes out the door: the engineer who ran `fit_lasso`, the product owner
who signed off on the feature list, or nobody, because the model was "just doing math"?
