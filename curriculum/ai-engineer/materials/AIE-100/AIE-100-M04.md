## Lessons

Four lessons. The first kills "it ran." The second turns the M02 trace into an oracle. The third plants assertions as tripwires inside the code. The fourth builds the first real tests — and teaches the one discipline that separates a test from a decoration: it must be able to fail.

### Lesson 1 — "It ran" is not verification

**The teaching.** Put a claim and its evidence side by side. The claim you actually care about is **"this code is correct"** — it does what the spec says on every input in scope, including the edges. Now look at what "it ran without error" actually licenses you to say. It says: *on the one input I happened to give it, the interpreter reached the end without raising.* That is a real fact, but it is a fact about a single point, and it is silent about three things at once: the inputs you didn't try, the outputs that were wrong-but-not-crashing, and your own understanding. In M02 you watched `add_item(4)` return `[1, 2, 4]` — it ran, it returned a list, and it was wrong. "It ran" was true and worthless in the same breath.

So rank the evidence. This is the **ladder**, weakest rung first:

1. **"It ran."** Reached the end on one input without raising. Rules out only crashes-on-that-input.
2. **"It printed something plausible."** The output looked like the right *kind* of thing. Rules out nothing — plausible-but-wrong is the entire failure mode of generated code.
3. **"It matched my expectation on one input."** You had an expectation *and* it matched. Now we're getting somewhere — but one input.
4. **"It matched a check that could have failed, on an input chosen to discriminate."** You picked an input where a *plausible wrong version* would give a *different* answer, computed the right answer independently, and the code matched. This rung is verification. The ones below it are not.

The load-bearing phrase is **a check that could have failed**. A check that could not have failed — because you wrote it *after* seeing the output, or because you chose an input every plausible implementation handles the same way — carries zero information. It cannot distinguish a correct program from a wrong one, so passing it tells you nothing about which you have. This is the difference between an experiment and a ritual. An experiment has an outcome that would have changed your belief; a ritual has a foregone conclusion.

That gives us the working definition this whole module builds toward:

> A **discriminating check** is a check for which at least one plausible-but-wrong version of the code would produce a *different* result than the correct version — and you know, independently of running the code, which result is correct.

Every instrument in M04 — the trace, the assertion, the test — is a way to build and run a discriminating check.

**Worked example — two tests, one of which is a decoration.**

Here is an AI-written function and two tests a beginner might write for it. One is evidence; one is theater.

```python
def average(nums):
    return sum(nums) / len(nums)

# Test A
def test_average_A():
    assert average([2, 4, 6]) == 4

# Test B
def test_average_B():
    result = average([2, 4, 6])
    assert result == result
```

Both tests pass. Test B (`result == result`) is a **decoration**: there is no possible implementation of `average` — correct, wrong, or empty — for which `result == result` is false. It could not have failed, so its passing is not evidence of anything. Test A is a real check: a plausible wrong `average` that used `sum(nums) / (len(nums) - 1)` would return `12 / 2 = 6`, not `4`, so Test A *would have caught it*. Test A discriminates; Test B does not. And notice what *neither* test touches: `average([])` raises `ZeroDivisionError`. The happy-path test suite is green and the empty-list edge is completely unguarded — which is exactly the gap Lessons 3 and 4 close.

**Named misconceptions.**

- **"Green tests mean the code is correct."** Green tests mean *the code passed the checks you wrote.* If your checks could not have failed, or never touched the edges, green means nothing was tested. A suite of decorations is green on a broken program.
- **"If it runs and the output looks right, I've verified it."** "Looks right" is rung 2 — the plausible-printout rung — and plausible-but-wrong is the failure mode you are here to catch. `[1, 2, 4]` looked right too.
- **"More tests is more verification."** Ten tests on the same happy-path input are one check run ten times. Verification comes from *discrimination* — inputs where a wrong version diverges — not from volume. One test on the boundary beats ten on the middle.

### Lesson 2 — The hand-trace as an oracle

**The teaching.** To check that code produced the right answer, you need the right answer *from a source other than the code* — otherwise you are asking the code to grade its own homework. That independent source is called an **oracle**, and in this course your first oracle is your own hand-trace. In M02 you traced code to *understand* it; here you trace it — or better, trace the *problem* — to manufacture an expected value you can check against.

Two disciplines make a trace usable as an oracle:

1. **Compute the expected value from the spec, not from the code's output.** If you run the code first and copy its answer into your test, your "expected value" is just the code's actual value — the test can never fail, and a bug is now enshrined as the expected result. Compute the answer by hand, from what the function is *supposed* to do, *before* you run.
2. **Choose a discriminating input.** Not every input tells you something. `average([4, 4, 4])` returns `4.0` under the correct code *and* under the off-by-one-denominator bug (`12 / 2 = 6`... no — `12/2` is `6`, so actually it *does* discriminate; but `average([0])` gives `0/1=0` correct and `0/0` crash — different discrimination). The move is deliberate: pick an input where a *specific plausible wrong version* gives a *different* answer, so a pass rules that version out.

The clearest example of a non-discriminating input is a symmetric one. Consider "remove duplicates, keep first occurrence." The input `[1, 2, 3]` (already unique, already sorted) cannot distinguish the correct order-preserving version from a lazy `sorted(set(items))` version — both return `[1, 2, 3]`. The input `[3, 1, 3, 2, 1]` *can*: the correct version returns `[3, 1, 2]`, the `sorted(set(...))` version returns `[1, 2, 3]`. Same function, and only one of these two inputs is a check that could have failed.

**Worked example — trace to an oracle, then pick the input that discriminates.**

```python
def dedupe(items):
    seen = set()
    out = []
    for x in items:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out
```

Trace `dedupe([3, 1, 3, 2, 1])` by hand — one row per element, tracking `seen` and `out`:

| `x` | `x in seen`? | `seen` after | `out` after |
|---|---|---|---|
| 3 | no | {3} | [3] |
| 1 | no | {3, 1} | [3, 1] |
| 3 | **yes** | {3, 1} | [3, 1] |
| 2 | no | {3, 1, 2} | [3, 1, 2] |
| 1 | **yes** | {3, 1, 2} | [3, 1, 2] |

Oracle: `dedupe([3, 1, 3, 2, 1])` **must** return `[3, 1, 2]`. You computed that from the *definition* (keep first occurrence, preserve order) — you did not run the code. Now the discrimination: this input rules out the two most plausible wrong versions at once. A `sorted(set(items))` version returns `[1, 2, 3]` (wrong order). A version that keeps the *last* occurrence returns `[3, 2, 1]`. Your oracle `[3, 1, 2]` differs from both — so a test asserting `dedupe([3,1,3,2,1]) == [3,1,2]` is a check that *could* have failed against either wrong version. Compare: a test on `[1, 2, 3]` passes on all three versions and proves nothing.

**Named misconceptions.**

- **"I'll run it first, then write the test to match."** Then your expected value is the code's actual value and the test cannot fail. The oracle must come from the spec, computed independently — before the run — or it is not an oracle, it is an echo.
- **"Any input that exercises the function is a good test input."** Only inputs where a wrong version would diverge carry information. A symmetric or already-solved input (sorted, unique, all-equal) often can't tell correct from broken. Choose the input a bug would *stumble* on.
- **"Hand-computing the answer is what the computer is for."** The computer gives you the code's answer; verification needs a *second, independent* answer to compare it to. If the only source of the expected value is the thing under test, you have no check at all.

### Lesson 3 — Assertions: executable claims inside the code

**The teaching.** A comment says "x should be positive here" and the interpreter ignores it. An **assertion** says the same thing in a language the interpreter enforces: `assert x > 0`. If the claim is true, execution continues as if the line weren't there. If it is false, execution stops immediately with an `AssertionError` at that exact line. An assertion is a **tripwire** — a check that could fail, placed *inside* the code, that fires the instant reality diverges from what you claimed. That is why it belongs in this module: it is the cheapest possible discriminating check, and it moves the failure from "somewhere downstream, looking plausible" to "right here, loudly, at the line where the assumption broke."

Three kinds of claim are worth asserting, by *where* in a function they go:

- **Precondition** — a claim about the inputs, at the top. `assert n >= 0`. "I am promised this; if I'm not, stop now instead of computing garbage."
- **Postcondition** — a claim about the result, before you return it. `assert 0.0 <= result <= 1.0`. "Whatever I computed, it had better satisfy this, or I have a bug."
- **Invariant** — a claim that must hold at some point in the middle, often inside a loop. `assert lo <= hi`. "If this ever breaks, my logic went wrong before here."

The syntax is `assert CONDITION` or `assert CONDITION, "message shown on failure"`. Prefer the message form — a bare `AssertionError` tells you *where* but not *what you believed*:

```python
def scale_to_unit(x, lo, hi):
    assert lo < hi, f"expected lo < hi, got lo={lo}, hi={hi}"   # precondition
    result = (x - lo) / (hi - lo)
    assert 0.0 <= result <= 1.0, f"result {result} outside [0,1] for x={x}"  # postcondition
    return result
```

Call `scale_to_unit(5, 0, 10)` → `0.5`, both asserts pass silently. Call `scale_to_unit(5, 10, 10)` → the precondition fires *before* the division, with a message naming the violation — instead of a bare `ZeroDivisionError` three lines from the real cause. Call `scale_to_unit(15, 0, 10)` → precondition passes, but the postcondition catches `1.5 > 1.0` and tells you the input was out of the range you assumed.

**The one caveat that tells you what `assert` is for.** Python's `-O` (optimize) flag **removes all `assert` statements** from the running program. `python3 -O prog.py` runs with every assertion stripped. This is not a bug; it is the design telling you the contract: **assertions are for catching *your own* programming errors during development, not for validating untrusted input in production.** If a check must run even under `-O` — validating a user's input, a file's contents, an API response — you do not use `assert`. You use an explicit raise:

```python
def withdraw(balance, amount):
    if amount < 0:                         # real input validation -> if/raise, survives -O
        raise ValueError("amount must be non-negative")
    assert balance >= 0, "internal: balance went negative"  # programmer-error tripwire -> assert
    return balance - amount
```

The rule: **`assert` for "this should be impossible if my code is right"; `if/raise` for "this is a bad input the outside world can legitimately send."** Confusing the two ships code that silently skips its input validation the moment someone runs it optimized. When an AI hands you a function that "validates its inputs" with `assert`, that is a defect a reader catches and a run never will.

**Worked example — assertions turn a silent wrong answer into a loud one.**

```python
def percent_of_total(values):
    assert values, "values must be non-empty"                  # precondition 1
    assert all(v >= 0 for v in values), "values must be non-negative"  # precondition 2
    total = sum(values)
    assert total != 0, "total must be non-zero to take percentages"     # precondition 3
    result = [v / total * 100 for v in values]
    assert abs(sum(result) - 100.0) < 1e-9, "percentages must sum to 100"  # postcondition
    return result
```

`percent_of_total([1, 2, 1])` → total `4`, returns `[25.0, 50.0, 25.0]`; postcondition checks `sum == 100.0` ✓. Now the tripwires, each firing on a different bad input:
- `percent_of_total([])` → precondition 1 fires ("values must be non-empty") *before* any division.
- `percent_of_total([0, 0])` → passes 1 and 2, then precondition 3 fires ("total must be non-zero") — catching the `0/0` before it happens.
- `percent_of_total([-1, 2])` → precondition 2 fires ("values must be non-negative").

Without these, `[]` and `[0, 0]` crash with a bare `ZeroDivisionError` far from the cause, and `[-1, 2]` returns a *plausible-looking* `[-100.0, 200.0]` — a wrong answer that runs. The postcondition is the subtle one: it is a check on the code's *own output*, and it would fire if someone later "optimized" the arithmetic into a bug. That is a check that could have failed.

**Named misconceptions.**

- **"Assertions are just comments that run."** A comment is ignored; an assertion is a check that *stops the program* when false. The difference is the entire value: a wrong comment is silent, a wrong assertion is a loud failure at the exact line.
- **"I should use `assert` to validate user input."** No — `-O` deletes assertions, so input validation written with `assert` silently vanishes in optimized runs. Use `if/raise` for anything the outside world can send; reserve `assert` for "impossible if my code is correct."
- **"A postcondition is redundant — I can see the return is right."** You can see it on the one input you looked at. A postcondition checks *every* run, including the input you never tried and the refactor you'll make next month. It is the assertion most likely to catch a future bug you can't currently imagine.
- **"Adding asserts changes what the function computes."** On correct inputs, asserts are invisible — execution proceeds identically. They change behavior only by *failing loudly* where the code would otherwise have continued quietly wrong. That is the point.

### Lesson 4 — The first real tests: pytest, and the mutation that proves a test works

**The teaching.** An assertion checks the code *while it runs for real*. A **test** is different: it is a separate little program whose only job is to *call* your code on chosen inputs and assert the results, so you can re-run all your checks at once, on demand, forever. pytest is the tool. The anatomy of a test is three beats — **Arrange, Act, Assert**:

```python
# test_average.py
from average import average

def test_average_of_three():
    nums = [2, 4, 6]          # Arrange: set up the input
    result = average(nums)    # Act: call the code under test
    assert result == 4.0      # Assert: check the result against your oracle
```

A test function's name starts with `test_`; you put it in a file named `test_*.py`; you run `pytest -q`; pytest finds every `test_` function, runs it, and reports pass/fail. A test *passes* when no assertion inside it fails. That's the whole model.

Three tools you need almost immediately:

**(1) `pytest.raises` — asserting that bad input is *rejected*.** Some correct behavior is *raising an error*. You cannot assert that with `==`; you assert it with a context manager:

```python
import pytest
def test_empty_raises():
    with pytest.raises(ZeroDivisionError):
        average([])            # the test PASSES if this raises ZeroDivisionError
```

If the code raises `ZeroDivisionError`, the test passes. If it does *not* raise (or raises something else), the test fails. This is how you pin an edge that is *supposed* to blow up.

**(2) `pytest.approx` — comparing floats without lying to yourself.** `0.1 + 0.2 == 0.3` is `False` in Python (binary floating point), so `assert result == 0.3` on a computed float is a trap that fails on correct code. Compare with tolerance:

```python
def test_scaling():
    assert scale_to_unit(1, 0, 3) == pytest.approx(0.3333333333333333)
```

**(3) `parametrize` — one test body, many inputs.** Instead of five near-identical test functions, list the cases:

```python
@pytest.mark.parametrize("nums,expected", [
    ([2, 4, 6], 4.0),
    ([5], 5.0),
    ([1, 2], 1.5),
])
def test_average_cases(nums, expected):
    assert average(nums) == pytest.approx(expected)
```

pytest runs the body once per row and reports each as its own pass/fail, so you see *which* case broke.

**Now the discipline that makes all of this verification instead of decoration.** A test only counts as evidence if it *could have failed*. There is a mechanical way to check whether yours could: **break the code on purpose and confirm a test goes red.** This is called a **mutation test** — you introduce a deliberate bug (a "mutant") and watch whether your suite catches it. If you change `sum(nums) / len(nums)` to `sum(nums) / (len(nums) - 1)` and *no test fails*, your suite does not actually test the average — it is green on a broken program, which means it was green on the correct one for no reason. A suite that survives every mutation you can think of is earning its green. A suite nothing can break is a decoration you happen to run.

This reframes the goal. You are not writing tests to make the bar turn green. You are writing tests that are *trying to prove the code wrong* and failing to — and the way you know they were genuinely trying is that a planted bug makes them succeed at it.

**Worked example — a happy-path suite that a bug walks straight through.**

```python
def count_words(text):
    return len(text.split(" "))     # AI-written; splits on a single space
```

Here is a suite a beginner writes, and it is all green:

```python
def test_three_words():
    assert count_words("the cat sat") == 3     # passes
def test_two_words():
    assert count_words("hello world") == 2     # passes
```

Green. Ship it? No — every input here has *exactly one space between each pair of words and no edges*, and on those inputs the buggy `split(" ")` and a correct `split()` agree. The suite could not have failed, because it never picked an input where they diverge. Now mutate your *thinking* instead of the code: what input would a wrong splitter stumble on? Two spaces. A trailing space. The empty string. Compute the oracle by hand:

- `count_words("the  cat")` (two spaces) — correct answer is **2**. But `"the  cat".split(" ")` is `['the', '', 'cat']`, length **3**.
- `count_words("")` — correct answer is **0**. But `"".split(" ")` is `['']`, length **1**.
- `count_words("hi ")` (trailing space) — correct answer is **1**. But `"hi ".split(" ")` is `['hi', '']`, length **2**.

Each of those is a check that *could* have failed — and does. Add any one of them and the suite goes red, exposing the bug the happy-path tests were structurally blind to. The fix is `text.split()` (no argument), which splits on runs of whitespace and drops empties: `"".split()` is `[]` (length 0), `"the  cat".split()` is `['the', 'cat']` (length 2). The lesson is not "test more" — it is "test *where a wrong version diverges*," and the way you find those inputs is by imagining the wrong version.

**Named misconceptions.**

- **"A passing test proves the code works."** It proves the code passes *that* test. If the test could not have failed (decoration) or never touched a diverging input (happy-path blindness), passing proves nothing. Only a test that could have failed and didn't is evidence.
- **"I'll write the test after I see the output, to match it."** Then the test asserts whatever the code did — bug included. Compute the expected value from the spec, before running; the oracle must be independent of the code under test.
- **"`assert result == 0.3` is fine for computed floats."** Binary floating point makes many exact float comparisons false on correct code (`0.1 + 0.2 != 0.3`). Use `pytest.approx` for anything computed, or you will fail correct code and "fix" it into a bug.
- **"If my tests are green, there's nothing left to check."** Run a mutation: break the code deliberately. If the bar stays green, your tests were never testing that behavior. Green on a mutant is proof your suite is partly decoration.
- **"`pytest.raises` passing means no error occurred."** The opposite: the block inside `with pytest.raises(...)` *must* raise the named error for the test to pass. It is how you assert that bad input is correctly rejected.

### Lab M04-A — The trace as an oracle (compute the expected answer by hand, then pick the input that discriminates)

**Goal.** Manufacture an independent oracle by hand-tracing, then choose an input on which a plausible wrong version diverges — the two halves of a discriminating check. The function is correct; the skill is producing the check.

**Predict (on paper, before running).**
1. Hand-trace `dedupe` below on the input `[4, 2, 4, 3, 2, 5]`, one row per element, tracking `seen` and `out`. Write the exact returned list. This is your **oracle** — computed from the definition ("keep the first occurrence, preserve order"), *not* from running the code.
2. Name **two** plausible wrong versions of `dedupe` (one that changes the order, one that keeps a different occurrence) and state what *each* would return on your input. Confirm your oracle differs from both — that is what makes the input discriminating.
3. Predict `dedupe([])` and `dedupe([7, 7, 7])`. For each, state whether it discriminates the correct version from a `sorted(set(items))` version, and why.

```python
# starter: dedupe.py   (already complete — you are reading it, not writing it)
def dedupe(items):
    seen = set()
    out = []
    for x in items:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out


if __name__ == "__main__":
    print(dedupe([4, 2, 4, 3, 2, 5]))
```

**Build.** Your build is (a) the completed trace table and (b) **one added test** to `test_dedupe.py` whose input is your discriminating one and whose expected value is your hand-computed oracle. A correct trace:

| `x` | `x in seen`? | `seen` after | `out` after |
|---|---|---|---|
| 4 | no | {4} | [4] |
| 2 | no | {4, 2} | [4, 2] |
| 4 | **yes** | {4, 2} | [4, 2] |
| 3 | no | {4, 2, 3} | [4, 2, 3] |
| 2 | **yes** | {4, 2, 3} | [4, 2, 3] |
| 5 | no | {4, 2, 3, 5} | [4, 2, 3, 5] |

Oracle: `dedupe([4, 2, 4, 3, 2, 5]) == [4, 2, 3, 5]`. A `sorted(set(items))` version returns `[2, 3, 4, 5]` (wrong order); a keep-*last* version returns `[4, 3, 2, 5]`. Your oracle differs from both, so the test below could have failed against either.

```python
# test_dedupe.py
from dedupe import dedupe

def test_discriminating():           # <-- YOU add this from your oracle
    assert dedupe([4, 2, 4, 3, 2, 5]) == [4, 2, 3, 5]

def test_empty():
    assert dedupe([]) == []

def test_all_same():
    assert dedupe([7, 7, 7]) == [7]
```

**Verify.** Run `pytest -q`. All three pass against the correct `dedupe`. Now *prove your discriminating test could have failed*: temporarily replace the body of `dedupe` with `return sorted(set(items))` and rerun. `test_discriminating` must go **red** (`[2, 3, 4, 5] != [4, 2, 3, 5]`) while `test_empty` and `test_all_same` stay **green** — demonstrating that only the discriminating input carries information about order. Restore the original body.

```python
    return result
```

### Lab M04-D — The pinning suite and the mutation that proves it (capstone)

**Goal.** Integrate all three instruments: given an AI artifact and a written spec, build a full test suite that pins the contract — valid cases (`parametrize`, `approx`), rejected inputs (`raises`) — and then **prove the suite is verification, not decoration, by mutating the code and confirming a test goes red.** Gaming-resistant because the graded artifact is the mutation log: which bug you planted, which test caught it, and the one mutation (if any) your suite survived.

**The spec (the decidable contract you are pinning).** `price_after_tax(price, rate)`:
- Raises `ValueError` if `price < 0`.
- Raises `ValueError` if `rate` is outside the closed interval `[0, 1]`.
- Otherwise returns `price * (1 + rate)`, **rounded to 2 decimal places**.

**Predict (on paper, before running).**
1. From the spec alone, hand-compute the oracle for: `price_after_tax(100, 0.07)`, `price_after_tax(19.99, 0.05)`, `price_after_tax(0, 0.2)`, `price_after_tax(50, 0)`. (Watch the rounding: `19.99 * 1.05 = 20.9895` → `20.99`.)

```python
# starter: price_after_tax.py   (AI-written reference implementation)
def price_after_tax(price, rate):
    if price < 0:
        raise ValueError("price must be non-negative")
    if not (0 <= rate <= 1):
        raise ValueError("rate must be between 0 and 1")
```

**Build.** Write the pinning suite. The reference:

```python

import pytest
from price_after_tax import price_after_tax

@pytest.mark.parametrize("price,rate,expected", [
    (100.0, 0.07, 107.0),
    (19.99, 0.05, 20.99),    # rounding case: 20.9895 -> 20.99

    (50.0, 0.0, 50.0),       # zero rate -> unchanged

    with pytest.raises(ValueError):
        price_after_tax(-1.0, 0.1)

    with pytest.raises(ValueError):
        price_after_tax(10.0, 1.5)

def test_rate_below_zero_raises():
    with pytest.raises(ValueError):
        price_after_tax(10.0, -0.1)
```

| Mutation | What you change | Prediction | Which test catches it |
|---|---|---|---|
| M1 | `1 + rate` → `rate` | `test_valid_cases` fails (100·0.07 = 7.0 ≠ 107.0) | `test_valid_cases[100.0-0.07-107.0]` |
| M2 | delete `if price < 0: raise ...` | `test_negative_price_raises` fails (no error raised) | `test_negative_price_raises` |
| M3 | `round(..., 2)` → `round(..., 1)` | the `19.99` case fails (21.0 ≠ 20.99) | `test_valid_cases[19.99-0.05-20.99]` |

If **any** mutation leaves the bar fully green, your suite has a hole exactly there — a behavior nothing tests — and you must add a discriminating case that closes it. (For instance, if you had *omitted* the `19.99` rounding case, M3 would survive: `round(107.0, 1) == round(107.0, 2)`, so a suite testing only round-number prices cannot detect a broken rounding precision. That gap is why the rounding case is a check that could have failed.)

## Assessment

The assessment is **gaming-resistant by construction**: the passing bar is the *judgment trail* — the hand-computed oracle, the discriminating input, the check that could have failed, and the mutation that proves it could — never a green pytest run. A learner cannot pass by making the bar turn green, because a suite of decorations is green on a broken program, and the graded question is whether each check *could have failed* and how you *showed* it could.

### Component 1 — Lab judgment trails (30%)

Submitted **before** each lab's run. Graded on: were the oracle and the discriminating input (or the planted mutation) committed in writing before execution; is each proposed check accompanied by a stated *wrong version it would catch*; where a run contradicted the prediction, is there a written revision naming the mechanism (split-on-space vs whitespace, mutable arithmetic, `-O` stripping, float tolerance). **A correct predicted output with no named discriminating input scores below an incorrect prediction that was correctly revised with the mechanism named** — because the certified outcome is *building a check that could have failed*, not guessing an output.

### Component 2 — Module exam: harden an unseen artifact (55%)

You are handed an **unseen ~30-line Python function with a written spec and a green happy-path test suite**, and told the code contains **one planted defect that the given suite does not catch** (drawn from: an off-by-one bound; a `split(" ")`/whitespace confusion; a mutable-default accumulation; an `==`-on-floats comparison; input validation written with `assert` so it vanishes under `-O`; or a missing edge guard). Time-boxed, in this order, and **the order is graded**:

1. **Predict (before running):** from the spec, compute by hand the oracle for at least two inputs on which a *wrong* version would diverge from the correct one. State each expected value and the wrong version it discriminates against.
2. **Locate:** point to the exact line of the defect and name the mechanism in one or two sentences.
3. **Write a check that could have failed:** add either a discriminating `pytest` test or an assertion that fires on the defect. State, before running, whether it will pass or fail against the *given* code and why.
4. **Prove it could fail (mutation):** run your check; it must go red on the defective code. Then apply the one-line fix and show your check *and* the original happy-path suite all pass. Name the observable that proves the model — e.g., "the double-space input returns 3 before the fix and 2 after" — not merely that the bar is green.

Submitting a green suite *without* the pre-run oracle, the discriminating input, and the demonstrated red-then-green caps this component at **40%** — because a suite that was never shown able to fail is not verification, and reading correctness off a passing run is precisely the non-skill this course exists to replace.

### Component 3 — Mutation viva (15%)

A 5-minute oral/whiteboard: given a short function and a small suite, the examiner proposes a one-line mutation ("what if I change `<` to `<=` here?") and you must say, *before any run*, whether the suite catches it and which test goes red — then, if it survives, write the missing discriminating test live. This certifies the core discipline directly: you cannot bluff "would this test have failed?" out loud without actually modeling both the code and the check.

### Rubric

| Dimension | 0 — Absent | 1 — Emerging | 2 — Proficient | 3 — Fluent | Gaming-resistance (why a shortcut fails here) |
|---|---|---|---|---|---|
| **Oracle independence** | Expected value copied from the code's output | Hand-computes on the happy path only | Hand-computes the oracle from the spec, before running, incl. an edge | Computes the oracle *and* the wrong version's answer, showing the divergence | An echoed output can't fail; a spec-derived oracle predicted before the run can |
| **Discrimination** | Tests only symmetric/happy-path inputs | Picks a varied input but can't say what it rules out | Chooses an input where a named wrong version diverges | Chooses the *minimal* input that discriminates several wrong versions at once | A non-discriminating check passes on correct and wrong code alike |
| **Assertion use** | Uses `assert` for user-input validation, or not at all | Adds a precondition but no postcondition | Places pre/postconditions correctly; knows `assert` vs `if/raise` | Predicts `-O` stripping and chooses the right instrument per case | The `-O` behavior is invisible to a normal run; only reasoning reveals it |
| **Test that could fail** | "It's green" offered as proof | Writes tests that pass but never shows one could fail | Writes a discriminating test and demonstrates red-then-green | Predicts pass/fail of each check *before* running and is right | A decoration is green on a broken program; a demonstrated red is not fakeable |
| **Mutation discipline** | Never breaks the code to check the suite | Runs a mutation but can't predict which test catches it | Plants a mutation and confirms the predicted test goes red | Finds the mutation the suite *survives* and closes the gap | A suite that survives a mutation has an untested hole the green bar hides |
| **Float / edge correctness** | `==` on computed floats; edges ignored | Knows edges exist but doesn't test them | Uses `approx`; tests empty/zero/boundary | Predicts *why* `0.1+0.2 != 0.3` and picks tolerance deliberately | Correct code fails a naive `==`; only `approx` reasoning passes it honestly |

**Pass = ≥ 2 on every dimension AND, on the module exam, the pre-run oracle + discriminating input submitted before the run AND a check demonstrated red-then-green.** No compensatory averaging on the prediction-order gate or the mutation gate: a green suite with no demonstrated failure does not pass, because it does not demonstrate the outcome — *shipping every artifact with a check that could have failed.*

**Walls (expected stall points, with reroutes):**

- **Wall: the test-that-cannot-fail (the canonical wall of this module).** Symptom: the learner writes tests, they're all green, and every one of them uses a happy-path input the bug also passes — `count_words("the cat sat") == 3`, `average([2,4,6]) == 4`, on and on. They equate "green bar" with "done" and cannot see that their suite would be equally green on broken code. This reads as struggle-**blocked** when they keep adding *more* happy-path tests in response to "is that verified?" — increasing volume, not discrimination. **Reroute:** take the assertion away from them and hand them the mutant instead — "here is a broken version; make one of your tests catch it." ## Three-tier reading — verification, and the difference between a green bar and a defensible claim

**Tier 1 — Material ground (verifiable facts).** Every claim in this module is checkable at the keyboard in seconds, and none of it is opinion. `assert False` raises `AssertionError` at that line; `python3 -O` removes every `assert` from the run, provable by watching a failing assertion silently vanish and a downstream error take its place. `0.1 + 0.2` evaluates to `0.30000000000000004`, so `0.1 + 0.2 == 0.3` is `False` — correct arithmetic that a naive `==` test reports as broken, which is why `pytest.approx` exists. `"the  cat".split(" ")` is `['the', '', 'cat']` (length 3) while `"the  cat".split()` is `['the', 'cat']` (length 2) — two functions that agree on `"the cat sat"` and disagree the instant an input has doubled or edge whitespace, provable by typing both. `sorted(set([4,2,4,3,2,5]))` is `[2,3,4,5]` while the order-preserving dedupe is `[4,2,3,5]` — so a test on `[1,2,3]` cannot tell them apart and a test on `[4,2,4,3,2,5]` can. Each of these is a *fact about which inputs discriminate a correct implementation from a wrong one*, and every one of them is invisible from a single happy-path run — which is the entire reason verification is an instrument you build, not a bar you watch turn green.

**Tier 2 — What the field suppresses.** Two opposite distortions, each hiding the same truth about what a passing check is worth. The booster distortion — "the AI writes the code *and* the tests; you get a full green suite for free, verification solved" — suppresses that **an AI will happily generate a test suite that cannot fail**: happy-path inputs the bug also passes, `==` comparisons that never run the edge, and, worst, tests written to match code the model already wrote, so the test asserts the bug as the expected value. A green suite generated alongside the code it tests is not an independent check; it is the same mental model grading its own homework, and it is green on the broken program for the same reason it is green on the correct one — it was never able to tell them apart. The counter-distortion, the testing-purist one — "true verification means 100% coverage, property tests, formal proofs; anything less is negligence" — suppresses that **most of the value is captured by one discriminating check on the input a wrong version stumbles on**, and that coverage percentage counts lines executed, not bugs excluded: a suite can execute every line and assert nothing that could fail. Both camps avoid the honest middle: verification is not a quantity (of tests, of coverage, of green) but a *property* of each check — could it have failed, and did you show it could? The person who owns the shipped code is the one who can point to a check that came out the way they predicted *and* could have come out otherwise. One camp tells them the machine already did that; the other buries it under a coverage target. Neither will say the cheap true thing: one test that could have failed, on the input you chose because a bug would trip on it, is worth more than a thousand green decorations.

**Tier 3 — Sit with this (a question you cannot unknow).** You have now written a test suite that was fully green — and watched it stay green on a program you had personally broken. The bar told you nothing; it could not, because not one of your checks could have failed. You only learned the code was wrong when you stopped and asked a different question — not "does my test pass?" but "what wrong version would this catch?" — and chose the one input where the lie shows. Soon an assistant will hand you a function, a spec, *and* a full green test suite it wrote for itself, with a coverage number attached, and a deadline. **When you ship code because the suite was green — and the suite was green because it, like the code, was written by something that never asked which inputs would prove it wrong — whose check was it, really? Did you verify anything, or did you inherit a model's confidence and re-badge it as your own? And when it fails in production on the input no one chose because no one imagined the wrong version — what, exactly, will you have to point to as the check you ran that could have failed and didn't?**
