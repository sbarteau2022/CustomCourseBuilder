### Harness contract (provided)

Every lab ships as a directory with a spec file (`SPEC.md`), one or more implementation files, and a `test_*.py`. Toolchain: **Python 3.12+** and **pytest**.

- `python3 <file>.py` — run a demo `main`, *after* your Predict sheet is written. Running first forfeits the point.
- `pytest -q` — run the provided tests; nonzero exit = fail. - `pytest -q -k <name>` — run one test while you reconcile a single claim.

There is no undefined behavior here: **Python's semantics are deterministic and checkable at the keyboard.** A specification is **decidable** when, for that determinism, you can state a rule that partitions all implementations into *conforms* and *violates* with no case left to opinion. The evidence standard for this module is: **your spec is decidable** (an adversary handed your exact words cannot satisfy them in a way you would reject), **its input space is fully partitioned** (every input class has a stated required behavior, including errors), and **it is executable** (the contract is encoded as checks that a subtly-wrong implementation fails).

## Lessons

Four lessons. The first defines the target: a *decidable* contract, and why intent is not one. The second shows the adversary: the AI does exactly what the spec permits, cheapest reading first. The third covers the ground the adversary hides in: the input space, and the partitions your examples never reach. The fourth gives the contract teeth: the executable spec.

1. **Decidability — what makes a spec a contract** — the oracle test, and why intent, examples, and "I'll know it when I see it" all fail it.
2. **The adversarial reading** — the AI satisfies the *permitted* behavior set, not the *intended* one; specification gaming on tiny artifacts.
3. **Partitioning the input space** — edges, errors, ties, and out-of-domain inputs; an unspecified partition is a decision you handed the AI.
4. **The executable specification** — examples + invariants + error contracts; the spec-as-tests is the thing you own.

### Lesson 1 — Decidability: what makes a specification a contract

**The teaching.** A specification is **decidable** when it answers one question mechanically, for *every* candidate: *given this implementation and this input, does the output conform or violate?* If two careful, honest people — or you today and you in three months — could look at the same output and disagree about whether it is correct, the spec is **ambiguous**, and every point of ambiguity is a decision you have silently delegated to whoever writes the code. When that someone is an AI assistant, the decision is made by a system optimizing for a plausible-looking answer, not for the thing in your head.

The test to run on any spec is the **oracle test**: *Can I, from the spec alone, write down the correct output for any input without asking the author a follow-up question?* If you need to ask "wait, what should it do when the list is empty?" or "does order matter?" — that follow-up is the ambiguity, made visible. A decidable spec has answered every such follow-up in advance.

Three things masquerade as specifications and are not:

- **Intent is not a spec.** "Sort the names" is a wish. It does not say: case-sensitive or not? Ties broken how? Empty list allowed? Duplicates kept? Unicode? The wish lives in your head; the AI cannot read it.
- **Examples are not a spec.** `sort_names(["Bob", "alice"]) == ["alice", "Bob"]` pins *one* input. It does not tell you whether the ordering is case-insensitive (which this example is consistent with) or a plain codepoint sort where uppercase `"B"` (66) sorts *before* lowercase `"a"` (97) — which the *same* example, read literally, is **also** consistent with only if you flip it. Examples underdetermine: infinitely many rules pass any finite set of examples.
- **"I'll know it when I see it" is not a spec.** It relocates the decision to after the code exists, where the plausible-looking wrong answer is hardest to reject — because it looks like what you asked for.

**Worked example — from a wish to a decidable contract.**

Start with the wish: *"Write a function `top_scores(scores, n)` that returns the top n scores."* Run the oracle test by trying to write the output for inputs the wish doesn't obviously cover:

- `top_scores([50, 90, 90, 70], 2)` → is it `[90, 90]` (values, ties kept) or `[90, 70]` (distinct values)? **Follow-up needed → ambiguous.**
- `top_scores([50, 90], 5)` → `n` exceeds the list length. Error? Or "as many as exist," `[90, 50]`? **Follow-up needed → ambiguous.**
- `top_scores([50, 90, 70], 0)` → `[]`? Error? **Follow-up needed → ambiguous.**
- Return order — descending, or original order? **Follow-up needed → ambiguous.**

Each follow-up is a decision the AI would otherwise make for you. Now the **decidable** version, which has *no* remaining follow-ups:

> **`top_scores(scores, n)`** — `scores` is a list of `int`. `n` is an `int`. Returns a **new** list containing the `n` largest values in `scores`, **ties included as duplicate values**, ordered **descending**. If `n >= len(scores)`, return all values sorted descending. If `n <= 0`, return `[]`. If `n < 0`, treat as `0`. The input list is not modified.

Now run the oracle test again: `top_scores([50, 90, 90, 70], 2)` → `[90, 90]`. `top_scores([50, 90], 5)` → `[90, 50]`. `top_scores([50, 90, 70], 0)` → `[]`. No follow-up survives. The spec is a contract: hand it to anyone (or anything) and the output for any input is *decided in advance by the words*, not by the implementer's guess.

**Named misconceptions:**

- **"The AI knows what I mean."** It knows what you *wrote*. Meaning is in your head and is not transmitted. Everything the words leave open, the system fills with the answer that is cheapest to produce and most plausible-looking — which is not a synonym for the one you wanted. The gap between meant and wrote is the entire subject of this module.
- **"A few good examples pin the behavior."** Finitely many examples are consistent with infinitely many rules. Your three examples might all be consistent with the correct rule *and* with a wrong rule that diverges on the fourth input you didn't write down. Examples are necessary (Lesson 4) and never sufficient.
- **"If it's ambiguous, the AI will ask me."** Sometimes; often it simply picks. And even when it asks, the follow-ups it thinks to ask are a subset of the ambiguities that exist. The decidable spec is the one where there was nothing left to ask.
- **"Precision means more words."** No — precision means *fewer surviving follow-ups*. A three-line spec that answers every oracle-test question is more precise than a page of prose that still leaves the empty-list case open. You are minimizing ambiguity, not maximizing verbosity.

### Lesson 2 — The adversarial reading: the AI does exactly what the spec permits

**The teaching.** Here is the mental posture that turns spec-writing from a chore into a skill: **read your own spec as an adversary would.** The AI is not malicious, but it behaves, for your purposes, exactly like a genie who grants your *literal* wish in the cheapest way the words allow. Anything the spec *permits*, the implementation is *entitled* to do. So the question you ask of your own draft is not "does this describe what I want?" — it is **"what is the worst thing a lazy, literal, rule-following implementer could do while still technically satisfying every word I wrote?"**

Every spec defines a **permitted-behavior set**: the collection of all implementations that satisfy it. Your *intended* implementation is one member of that set. Specification is the craft of shrinking the permitted set until every remaining member is acceptable to you — ideally until intent and permitted set coincide. A loose spec has a huge permitted set containing implementations you would fire a human for writing; the AI will hand you one of them and a passing test, and call it done.

The cheapest members of the permitted set are usually **degenerate**: they ignore the input, return a constant, return the input unchanged, or do the least work that satisfies the letter of the rule. If a degenerate implementation satisfies your spec, your spec is broken — not because the degenerate answer is what you'll get every time, but because *the spec failed to exclude it*, which means the spec is not carrying the meaning you thought it was.

**Worked example — the deduplication genie.**

The wish: *"Write `dedupe(items)` that removes duplicates from a list of integers."* Draft spec, first attempt:

> `dedupe(items)` returns a list in which no integer appears more than once, and every integer in the result was present in `items`.

Now read it as the genie. What is the cheapest implementation that satisfies *every word*?

```python
def dedupe(items):
    return []      # the genie's answer
```

Check it against the letter of the spec: "no integer appears more than once" — vacuously true, the empty list has no repeats. "Every integer in the result was present in `items`" — vacuously true, there are no integers in the result. **`return []` conforms.** The genie satisfied your wish and threw away all your data. A second genie:

```python
def dedupe(items):
    return sorted(set(items))    # loses original order
```

Also conforms — the spec never said anything about order, so reordering is permitted. Both pass a naive test like `assert set(dedupe([1,1,2])) <= {1,2}`. Neither is what you meant.

The fix is to name what the genies exploited — **completeness** (nothing may be dropped) and **order** (first-occurrence order is preserved):

> `dedupe(items)` returns a new list containing each distinct integer of `items` **exactly once**, in the order of that integer's **first appearance** in `items`. Every distinct value of `items` appears in the result (**completeness**), and no value appears that was not in `items`. The input is not modified.

Re-read as the genie. `return []` now violates completeness (`dedupe([1,2])` must contain `1` and `2`). `sorted(set(items))` now violates first-appearance order (`dedupe([2,1])` must be `[2,1]`, not `[1,2]`). The permitted set has shrunk to implementations that keep the first of each value in order — which is exactly your intent. **You closed the loophole by predicting the cheat, not by adding words at random.**

**Named misconceptions:**

- **"No reasonable person would interpret it that way."** The AI is not a reasonable person; it is a literal one. And "reasonable" is doing enormous unexamined work — the empty-list-dropping `dedupe` is unreasonable to *you* precisely because *you* hold the intent the spec failed to write down. The spec has to carry the reasonableness explicitly.
- **"The tests will catch a cheating implementation."** Only tests that *pin the property the cheat violates* will catch it. `return []` passes every test that checks "no duplicates" and fails only a test that checks "completeness." If your spec didn't name completeness, your tests won't check it, and the cheat sails through green. Tests inherit the blind spots of the spec.
- **"Adding more requirements always makes it safer."** Adding *unfalsifiable* requirements ("should be efficient," "should be clean") does nothing — the genie can't violate a rule you can't check. Only requirements that *shrink the permitted set decidably* (completeness, order, error behavior) constrain the adversary. Precision is about decidable constraints, not adjectives.
- **"Specification gaming is an exotic AI-safety topic, not my problem."** It is the same phenomenon at desk scale, today, every time you accept generated code. The genie that returns `[]` for `dedupe` and the reward-hacking agent are the same failure: an optimizer satisfying the letter of an underspecified objective. You meet it on tiny artifacts here so you recognize it on large ones later.

### Lesson 3 — Partitioning the input space: edges, errors, and the cases your examples never reach

**The teaching.** The adversary of Lesson 2 hides in the parts of the input space your spec forgot to mention. So the discipline is to **partition the input space** — carve the set of all possible inputs into classes that the function might treat differently — and give **every class** a stated required behavior. An input class with no stated behavior is not "obvious"; it is a decision you handed to the implementation. Most of the surprising failures in accepted AI code live in exactly one unspecified partition.

The recurring partitions to check, on almost every spec:

- **Empty / zero-size** — empty list, empty string, `n == 0`. Very often the one example never covers it, and it's where `min([])`, division by count, and index `[0]` blow up.
- **Singleton** — one element. Loops that compare neighbors, "average of the two middle values," anything pairwise behaves specially here.
- **Ties / duplicates / all-equal** — where "the largest," "the median," "the unique value" stop being unambiguous.
- **Ordering assumption** — does the function assume the input is already sorted, or must it sort? A spec that says "median" without saying "of the sorted values" permits a genie that takes the physical middle element of an unsorted list.
- **Out-of-domain / wrong type** — negative where you meant non-negative; `None`; a `str` where an `int` was intended. Does the function reject it (raise), coerce it, or is it the *caller's* job to never pass it?
- **Boundary values** — exactly at the threshold. `n == len(scores)`. `lo == hi`. The `<` vs `<=` decision lives here.

Two ways to specify each partition, and you must choose consciously:

- **Total function** — the function *handles* the class and defines an output for it (empty list → `[]`, or → raises `ValueError`). The behavior is part of the contract.
- **Precondition** — the function *requires the caller* to guarantee the class never occurs ("`scores` must be non-empty; behavior on empty input is undefined"). This is a legitimate choice, but it moves the obligation, it does not delete it — and an undefined precondition violation is a bug at the *call site*, which you now also own.

Silence is neither of these. Silence is "the AI decides, and you find out in production."

**Worked example — partitioning `median`.**

The wish: *"Return the median of a list of numbers."* Partition the input space and watch the ambiguities surface:

| Partition | Ambiguity the wish leaves open | Decidable choice |
|---|---|---|
| Empty list | crash? `None`? `0`? | **raise `ValueError`** |
| Odd length | (little ambiguity) | middle of the **sorted** values |
| Even length | which "middle"? one value or the mean of two? | **mean of the two middle sorted values**, as a `float` |
| Unsorted input | take physical middle, or sort first? | **sort first**; input order does not matter |
| Single element | — | that element |
| Input mutated? | may the function reorder the caller's list? | **no**; operate on a copy |

The even-length row is the one that bites: `median([1, 2, 3, 4])` could defensibly be `2` (lower middle), `3` (upper middle), or `2.5` (mean). All three are "the median" to *someone*. A spec that doesn't pick permits all three, and the AI picks one — quite possibly not yours. The decidable spec:

> `median(nums)` — `nums` is a non-empty list of numbers. Returns the median of the **sorted** values: for **odd** length, the single middle value; for **even** length, the **arithmetic mean of the two middle values** as a `float`. The input list is **not modified**. If `nums` is **empty**, raise `ValueError`.

Every partition now has one answer. `median([1,2,3,4])` → `2.5`. `median([3,1,2])` → `2` (sorts first). `median([])` → `ValueError`. `median([7])` → `7`. No follow-up survives.

**Named misconceptions:**

- **"The happy path is the spec."** The happy path is the *example*, and Lesson 1 already retired examples as specs. The contract is defined at the edges the happy path skips — empty, single, tie, boundary. A spec that only describes the middle of the range has left both ends to the adversary.
- **"Edge cases are rare, so they don't matter."** They are rare *per call* and certain *in aggregate*: ship a function to production and every partition gets hit eventually, usually at the worst time. Rarity is why they're missing from the example and why the bug is subtle — not a reason to leave them unspecified.
- **"If I don't mention bad input, the function just won't get bad input."** That is a *precondition*, and it is only real if you *state* it and enforce it at the call site. An unstated assumption isn't a precondition; it's a landmine. Silence means the AI chooses — maybe it raises, maybe it returns a garbage value, and you don't know which until it happens.
- **"Sorting is obviously implied for a median."** Obvious to you. The words "middle value" literally describe a position, and an implementation that returns `nums[len(nums)//2]` of an *unsorted* list satisfies "middle value" while being wrong. If you didn't write "sorted," you permitted the physical-middle reading.

### Lesson 4 — The executable specification: examples + invariants + error contracts

**The teaching.** A specification you cannot *check* is a wish with better grammar. The final move is to give the contract **teeth**: encode it as executable checks so that the question "does this implementation conform?" is answered by running something, not by re-reading prose and hoping. The executable spec has three parts, and you need all three because each catches what the others miss:

1. **Examples** — specific input/output pairs. Necessary (they anchor the intended behavior concretely and catch gross errors) and, as Lesson 1 proved, never sufficient (finite examples underdetermine the rule). Include the *edge* examples from your partition, not just the happy path.
2. **Invariants / properties** — statements of the form *"for every valid input, the output satisfies P."* This is where you encode completeness, order, membership, length-preservation, idempotence — the exact properties the genies of Lesson 2 violated. A property is checked against *many* inputs, so it constrains the whole permitted set, not one point in it.
3. **Error contract** — the inputs that *must* raise, and what they raise. `median([])` must raise `ValueError`, and a test asserts it. Without this, a genie that returns `0` for the empty list passes silently.

The power move is the **property**, because it is what a cheating-but-example-passing implementation cannot survive. Consider `dedupe`. A wrong implementation that keeps only *even-indexed* survivors might pass three hand-picked examples. But the property *"every distinct value of the input appears in the output"* (completeness), checked over dozens of inputs, fails it immediately. You do not need a property-testing framework to think this way — you write a small loop over several inputs and assert the property holds for each. (Frameworks like Hypothesis automate the input generation; the *thinking* is what this course installs, and it works with a plain `for` loop.)

**The ownership claim.** This executable spec — examples that anchor, properties that constrain, error contracts that pin the edges — **is the artifact you own.** Not the implementation. The AI can regenerate the implementation a hundred times; each version is correct exactly when it passes your executable spec. The spec is the durable thing, the thing that encodes your judgment, the thing you are on the hook for when it ships. This is the module's payload: *you own the contract, not the code.*

**Worked example — an executable spec for `clamp`.**

Wish: *"Clamp each value into a range."* Decidable spec:

> `clamp(values, lo, hi)` — returns a **new** list the same length as `values`, where each element `v` is mapped to `lo` if `v < lo`, to `hi` if `v > hi`, otherwise to `v` unchanged. Requires `lo <= hi`; if `lo > hi`, raise `ValueError`. Input list not modified.

Now the executable spec — the three parts:

```python
# executable spec for clamp (examples + properties + error contract)
def check_clamp(clamp):
    # 1. EXAMPLES (anchor the intended behavior, incl. boundaries)
    assert clamp([5, 15, 25], 10, 20) == [10, 15, 20]   # below, inside, above
    assert clamp([10, 20], 10, 20) == [10, 20]           # exactly on the bounds
    assert clamp([], 0, 5) == []                          # empty partition

    # 2. PROPERTIES (constrain the whole permitted set, not one point)
    import itertools
    for vals in ([-3, 0, 3, 7, 99], [0], [5, 5, 5], [100, -100]):
        out = clamp(vals, 0, 10)
        assert len(out) == len(vals)                     # length preserved
        assert all(0 <= x <= 10 for x in out)            # every output in range  <-- kills "forgot hi"
        assert clamp(out, 0, 10) == out                  # idempotence

    # 3. ERROR CONTRACT
    import pytest
    with pytest.raises(ValueError):
        clamp([1, 2], 10, 0)                             # lo > hi must raise
```

The load-bearing line is the property `all(0 <= x <= 10 for x in out)`. A subtly-wrong implementation that clamps the low end but forgets the high end — `[max(lo, v) for v in values]` — passes several happy examples (any list whose values don't exceed `hi`), and is annihilated by that one property the instant an input contains a value above `hi`. **The example suite alone would have shipped the bug; the property catches it.** That is why the property, not the example, is the thing that makes the spec decidable in practice.

**Named misconceptions:**

- **"Passing my examples means it's correct."** It means it's correct *on those inputs*. Correctness is a claim about *all* valid inputs, and examples are a finite sample. The gap between "passes my examples" and "conforms to my spec" is exactly where the accepted-but-wrong implementation lives — and it is closed by properties, not by more examples.
- **"A property test is just an example with extra steps."** An example asserts about *one* input; a property asserts about *every* input in a class. `clamp([5,15,25],10,20) == [10,15,20]` is an example. `for every list, every output is within [lo,hi]` is a property. The property is what a cheat can't dodge by matching the one input you happened to pick.
- **"I can fully specify it in prose and skip the checks."** Prose specifies; it does not *verify*. The moment there is an implementation, you need a mechanical way to ask "conforms?" — and re-reading prose against code is exactly the skim-that-isn't-reading M02 warned against. The checks are the prose made enforceable.
- **"Writing the spec-as-tests is the AI's job, so I'll have it generate those too."** Then the same blind spot generates both the code and the test, and they agree with each other about being wrong. The executable spec is *your* contribution to the loop precisely because it must encode *your* intent independently. Generating your own oracle from the same prompt that generated the code is how a green suite certifies a shared misconception.

### Lab M03-A — Watch the genie (predict the conforming cheats, then exclude them)

**Goal.** Feel specification gaming directly: take a weak English spec, predict the *degenerate* implementations it permits, confirm they pass a weak test suite, then tighten the spec and add the checks that kill the cheats while keeping the intended implementation green.

**Predict (on paper, before running).**
1. Read the weak spec and the weak test below. List **at least three** distinct implementations of `dedupe` that satisfy every word of the weak spec but are *not* what a caller means — for each, name the property it exploits the spec's silence on (order, completeness, count).
2. For each of the four provided implementations (`intended`, `genie_empty`, `genie_sorted`, `genie_first_two`), predict **pass or fail** on the weak suite. State the exact output of each on `dedupe([3, 1, 3, 2, 1])`.
3. Write the **two** properties the weak spec is missing that, once added, would fail every genie while passing `intended`.

**Weak spec (as shipped):** *"`dedupe(items)` returns a list of integers in which no value appears more than once; every value in the result came from `items`."*

```python
# starter: dedupe_impls.py
def intended(items):
    seen = set()
    out = []
    for x in items:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out

def genie_empty(items):
    return []                       # cheat: no repeats, vacuously

def genie_sorted(items):
    return sorted(set(items))       # cheat: drops original order

def genie_first_two(items):
    result = []
    for x in items:
        if x not in result:
            result.append(x)
        if len(result) == 2:        # cheat: keeps at most two distinct values
            break
    return result
```

```python
# starter: test_dedupe_weak.py  (the WEAK suite — passes cheats on purpose)
from dedupe_impls import intended, genie_empty, genie_sorted, genie_first_two
import pytest

@pytest.mark.parametrize("f", [intended, genie_empty, genie_sorted, genie_first_two])
def test_no_duplicates(f):
    out = f([3, 1, 3, 2, 1])
    assert len(out) == len(set(out))          # "no value appears more than once"

@pytest.mark.parametrize("f", [intended, genie_empty, genie_sorted, genie_first_two])
def test_values_came_from_input(f):
    src = [3, 1, 3, 2, 1]
    assert set(f(src)) <= set(src)            # "every value came from items"
```

**Build.** Do two things. (1) Write the **tightened spec** — the decidable version that names order and completeness. (2) Write `test_dedupe_strong.py` encoding it, such that `intended` passes and **all three genies fail.** A correct tightened spec reads:

> `dedupe(items)` returns a new list containing **each distinct value of `items` exactly once**, in the order of that value's **first appearance**. **Every** distinct value of `items` appears in the result (completeness). The input is not modified.

```python
# solution: test_dedupe_strong.py
from dedupe_impls import intended, genie_empty, genie_sorted, genie_first_two
import pytest

def test_intended_is_correct():
    assert intended([3, 1, 3, 2, 1]) == [3, 1, 2]     # first-appearance order, all distinct kept
    assert intended([]) == []
    assert intended([5, 5, 5]) == [5]

# PROPERTY 1 — completeness: every distinct input value survives (kills genie_empty, genie_first_two)
@pytest.mark.parametrize("f", [genie_empty, genie_first_two])
def test_genie_violates_completeness(f):
    src = [3, 1, 3, 2, 1]
    assert set(f(src)) != set(src)                    # a genie drops values; intended would not

def test_intended_is_complete():
    src = [3, 1, 3, 2, 1]
    assert set(intended(src)) == set(src)             # nothing dropped

# PROPERTY 2 — first-appearance order (kills genie_sorted)
def test_genie_sorted_violates_order():
    assert genie_sorted([3, 1, 2]) != [3, 1, 2]       # sorted() reorders
def test_intended_preserves_order():
    assert intended([3, 1, 2]) == [3, 1, 2]
```

**Verify.** Run `pytest -q test_dedupe_weak.py` and watch **all four** implementations pass — the weak suite cannot tell the genie from the intended function. ### Lab M03-C — The executable spec (properties that a subtly-wrong, example-passing implementation fails)

**Goal.** Build the full Lesson 4 artifact: turn a decidable contract into an executable spec with all three parts (examples, properties, error contract), and prove it catches a subtly-wrong implementation that the *examples alone* would have shipped.

3. Predict the output of `broken_hi([5, 15, 25], 10, 20)` and of `correct([5, 15, 25], 10, 20)`.

**Spec:**

> `clamp(values, lo, hi)` — returns a **new** list the same length as `values`, each element `v` mapped to `lo` if `v < lo`, to `hi` if `v > hi`, else `v` unchanged. Requires `lo <= hi`; if `lo > hi`, raise `ValueError`. Input list not modified.

```python
# starter: clamp_impls.py
def correct(values, lo, hi):
    if lo > hi:
        raise ValueError("lo must be <= hi")
    return [lo if v < lo else hi if v > hi else v for v in values]

def broken_hi(values, lo, hi):
    if lo > hi:
        raise ValueError("lo must be <= hi")
    return [lo if v < lo else v for v in values]     # subtly wrong: forgets the hi bound
```

**Build.** Write the executable spec as a reusable checker plus a parametrized test. The checker encodes examples + properties + error contract; the property `all(lo <= x <= hi ...)` is the load-bearing line that catches `broken_hi`:

```python
# solution: test_clamp_spec.py
import pytest
from clamp_impls import correct, broken_hi

# ---- the executable spec, as a checker applied to any candidate ----
def assert_conforms(clamp):
    # 1. EXAMPLES (incl. boundary + empty partitions) — note: no example value
    #    exceeds hi, so broken_hi survives all of them; the property below is the catcher
    assert clamp([5, 15, 18], 10, 20) == [10, 15, 18]   # below lo, inside, inside (nothing above hi)
    assert clamp([10, 20], 10, 20) == [10, 20]
    assert clamp([], 0, 5) == []

    # 2. PROPERTIES over many inputs (this is what a cheat cannot dodge)
    for vals in ([-3, 0, 3, 7, 99], [0], [5, 5, 5], [100, -100], [11, 12, 13]):
        out = clamp(vals, 0, 10)
        assert len(out) == len(vals)                 # length preserved
        assert all(0 <= x <= 10 for x in out)        # every output in range  <-- kills broken_hi
        assert clamp(out, 0, 10) == out              # idempotence

    # 3. ERROR CONTRACT
    with pytest.raises(ValueError):
        clamp([1, 2], 10, 0)

def test_correct_conforms():
    assert_conforms(correct)                         # passes: correct satisfies the whole spec

def test_broken_hi_is_caught_by_the_spec():
    # The executable spec must REJECT the subtly-wrong impl. We assert that it does.
    with pytest.raises(AssertionError):
        assert_conforms(broken_hi)

def test_examples_alone_would_have_shipped_the_bug():
    # broken_hi passes a happy example whose values never exceed hi -> the gap examples miss
    assert broken_hi([5, 8, 9], 0, 10) == [5, 8, 9]  # green, and wrong-in-general
    assert broken_hi([5, 15, 25], 0, 10) == [5, 15, 25]  # 15,25 NOT clamped: the bug, visible
```

## Assessment

The assessment is **gaming-resistant by construction**: the passing bar is the *specification you authored and the loophole you closed*, not a green pytest run. A learner cannot pass by getting code to run, because the graded artifacts are (a) specs that an adversary is turned loose on, and (b) the checks that exclude the cheats — and in several tasks a green run on a weak suite is the failure being demonstrated, not the goal.

### Component 1 — Lab spec sheets and loophole predictions (30%)

Submitted **before** each lab's run. Graded on: were the *conforming cheats* (Lab A), the *partition table* (Lab B), and the *catching properties* (Lab C) committed in writing before execution; and where the run contradicted a prediction (e.g. a genie you thought would fail passing the weak suite), is there a written revision naming the mechanism (permitted-behavior set / unspecified partition / example-vs-property gap). **A learner who predicts the correct final spec but never names a single cheat their draft permitted scores below one who wrote a leaky first draft, predicted the cheat it permitted, and tightened it** — because the certified outcome is *reasoning about the permitted set*, not arriving at an answer key.

### Component 2 — Spec exam: tighten an underspecified contract until it is decidable (55%)

You are handed an **English wish** for a small function (e.g. "return the most common element," "merge two sorted lists," "split a bill n ways") together with a **deliberately weak test suite that a cheating implementation already passes**. Time-boxed, in this order, and **the order is graded**:

1. **Predict (before running):** run the oracle test on the wish — list every follow-up question it leaves open. For each, name a **conforming cheat**: an implementation that satisfies the wish's literal words while violating the intent, and the partition/property it exploits.
2. **Tighten:** rewrite the wish as a **decidable spec** — every partition assigned a behavior, ties and errors pinned — such that no follow-up survives the oracle test.
3. **Give it teeth:** write the executable spec — at least two **properties** (not just examples) and one **error-contract** assertion — that fails every cheat you named in step 1 while passing the intended implementation.
4. **Verify:** run the weak suite (watch a provided cheat pass it — this is the point) and then your strengthened suite (watch the same cheat fail). Confirm the intended implementation passes both.

Submitting a "correct" final spec *without* the step-1 cheats and the property that excludes each caps this component at **40%** — because a spec presented as an answer key does not demonstrate the outcome: *predicting how a conforming implementation betrays intent, and closing the gap decidably.*

### Component 3 — Spec viva (15%)

A 5-minute oral/whiteboard: given a one-line wish, enumerate the permitted-behavior set out loud — "an implementation could return X, or Y, or the empty list; my spec excludes all but the intended one because it pins ___" — and answer "if I hand this exact wording to a lazy genie, what is the cheapest thing it can legally return?" This certifies the adversarial-reading model directly; you cannot bluff a permitted set you are enumerating live.

### Rubric

| Dimension | 0 — Absent | 1 — Emerging | 2 — Proficient | 3 — Fluent | Gaming-resistance (why a shortcut fails here) |
|---|---|---|---|---|---|
| **Decidability** | Spec is a restated wish; follow-ups remain | Pins the happy path; edges still ambiguous | Oracle test yields **no** surviving follow-up across all partitions | Writes the minimal decidable spec — precision without padding | An answer key can be copied; a spec that survives adversarial oracle-testing must be *reasoned* to |
| **Adversarial reading** | Assumes the implementer is reasonable | Names one degenerate cheat when prompted | Predicts multiple conforming cheats and the property each exploits | Predicts the *cheapest* permitted implementation on sight and pre-empts it | The genie is built and run; a spec that permits it fails visibly |
| **Input-space partition** | Only the happy path considered | Lists empty/single; misses ties, ordering, out-of-domain | Partitions fully; every class has a stated behavior incl. errors | Chooses total-function vs precondition consciously and states the obligation | The unspecified partition is exactly where the planted divergence lives |
| **Executable spec** | Prose only; nothing runs | Examples only (happy path) | Examples + at least one **property** + error contract | Properties chosen to kill the specific cheats; edge examples included | An example-only suite ships the subtly-wrong impl; only a property catches it |
| **Ownership / evidence** | "It runs / passes" offered as proof | Treats a green weak suite as sufficient | Distinguishes "passes my examples" from "conforms to my spec" | Names the spec (not the code) as the owned artifact and defends it | The weak suite is green *by design*; a clean run is explicitly insufficient |

**Pass = ≥ 2 on every dimension AND the spec-exam step-1 cheats submitted before the run.** No compensatory averaging on the prediction-order gate: presenting a correct final spec with no prior enumeration of the cheats it excludes does not pass, because it does not demonstrate the outcome — *turning intent into a contract precise enough that correctness is decidable, by reasoning about what a conforming implementation is still permitted to do.*

## Three-tier reading — the specification, and who owns what it permits

**Tier 1 — Material ground (verifiable facts).** A specification's permitted-behavior set is a real, checkable object, not a metaphor. Every claim in this module is provable at the keyboard in seconds: the spec "return a list with no duplicates, all values from the input" is satisfied by `return []`, provable by running it against a test that checks only those two clauses and watching it pass green; a spec that omits "first-appearance order" is satisfied by `sorted(set(items))`, provable by the identical green run; an example suite that never feeds a value above `hi` cannot distinguish `clamp` from an implementation that forgets the upper bound, provable by `broken_hi([5, 8, 9], 0, 10)` returning `[5, 8, 9]` and passing while `broken_hi([5, 15, 25], 0, 10)` returns the unclamped `[5, 15, 25]`; and a property asserted over many inputs — `all(lo <= x <= hi for x in out)` — fails that same implementation the instant one input exceeds `hi`. None of this is opinion. Given a spec and a candidate, "conforms or violates" is a computation, and a spec is *decidable* exactly when that computation has no undefined case. The finite example suite underdetermines the rule as a matter of logic: infinitely many functions pass any finite set of input/output pairs.

**Tier 2 — What the field suppresses.** Two opposite distortions, each hiding the same truth about where judgment lives. The booster distortion — "just describe what you want in plain English and the AI writes it; prompting *is* the new programming" — suppresses that **plain English is an underspecified spec, and the AI fills every gap you left with the cheapest plausible reading, not your intent.** The productivity framing counts the code you didn't type and quietly stops counting the *decisions* you didn't make — the empty-list behavior, the tie-breaking, the error contract — which the model then made for you, silently, optimizing for a plausible-looking output rather than a correct one. "It did what I asked" and "it did what I meant" are treated as the same sentence; they are the gap this module is built on. The traditionalist distortion — "natural-language specs are hopelessly vague; only formal methods or code-is-the-spec are real" — suppresses that **a spec does not need to be formal to be decidable**; a few prose clauses that answer every oracle-test follow-up and a handful of properties that constrain the permitted set are enough to make correctness checkable, and are exactly what a working engineer can write and own. Both camps avoid the honest middle: the specification is the artifact where your judgment actually lives, more than the implementation is, because the implementation is regenerable and the spec is the thing that says which regenerations are correct. One camp says the spec is unnecessary (the AI infers intent); the other says an *informal* spec is worthless (only formalism counts). The person who writes a decidable-enough contract and gives it teeth is doing the load-bearing work that neither camp will name as work.

**Tier 3 — Sit with this (a question you cannot unknow).** You have now written a spec you believed captured what you wanted, handed it to a genie standing in for the assistant, and watched it return the empty list — or the reordered list, or the half-clamped list — while satisfying every word you actually wrote. The gap was not in the code. The gap was between what you *meant* and what you *specified*, and the model lived in that gap and did exactly what you permitted. Soon an assistant will read a prompt you wrote in a hurry, fill every ambiguity you left with the cheapest plausible reading, hand you a screenful that passes the examples you happened to think of, and a deadline will make you accept it. **When that code does in production exactly what your spec permitted — conforms to every word, betrays everything you meant — the model can truthfully say it did what you asked. So what, precisely, did you specify, versus what did you merely intend and never write down — and if intent that was never made decidable is not a specification at all, then at the moment it fails, whose contract was it?**
