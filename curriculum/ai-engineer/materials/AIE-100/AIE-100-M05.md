> **The descent, stated plainly.** Debugging is the one activity you cannot fake your way through. You can accept a spec you half-understand, skim code that runs, and ship a green test you never watched fail. But a bug does not move until you understand it. The grid won't stop turning a single edit into a whole column of 5s until you learn that `[[0]*n]*n` copies a *reference* n times, not a list. You did not choose to learn these concepts; the defect conscripted you. That is what "fundamentals arrive as instruments" means: not that you study a concept and later apply it, but that a broken program refuses to be fixed until the concept is in your hands. The wall of this module is not that debugging is hard. The wall is the reflex to **guess and re-run** — to change a line, run the tests, and if they go green declare victory — which produces code that stops failing *the one input you tried* while you understand it less than before you started.

> **The loop under every lab is AI-PRIMM, and nested inside it is the debugging loop.** Predict → Prompt → Read → Verify → Integrate, and the Verify step here contains its own four-beat machine: **Reproduce → Isolate → Hypothesize → Verify-the-fix** (RIHV). You do not touch the code until you can make the bug happen on demand; you do not fix until you can say *where* the cause is and *why* it produces the symptom; and you do not declare the fix done until you have watched the symptom return when you revert it. The graded artifact is never a green pytest. It is the **debugging trail**: the failing test that reproduces the bug, the localization note that separates symptom from cause, the falsifiable hypothesis you wrote *before* the fix, and the revert-red experiment that proves your one-line change is the thing that mattered.

### Harness contract (provided)

Every lab ships as a directory with the **buggy artifact** exactly as an assistant generated it, a **bug report** in plain English (a symptom, never a line number), a `test_*.py`, and a one-line runner. Toolchain: **Python 3.12+** and **pytest**.

- `python3 <file>.py` — run the demo to *observe* the symptom — **only after your Predict sheet is written and submitted.** Observing before predicting forfeits the point, because the whole skill is holding a hypothesis before you look.
- `pytest -q` — run the tests; nonzero exit = fail. The reproduction test is written to go **red on the shipped bug**; that red is your evidence the bug exists, not a failure of your work.
- `pytest -q -k <name>` — run one test while you reconcile a single claim.
- `python3 -c "import mod; print(mod.fn.__defaults__)"` — a localization probe. Debugging is a *search*, and the probe (a print, an `is` check, a `__defaults__` peek) is how you narrow it.

There is no undefined behavior in this module: Python's semantics are deterministic and fully checkable at the keyboard. Every bug has exactly one mechanism, and that mechanism is provable in seconds. The evidence standard is: **you reproduced the bug as a failing test before touching the code; you localized the cause and named it as a falsifiable mechanism; your fix turns the reproduction green without breaking the regression net; and reverting the fix makes the symptom return.** A green suite after a guessed change is *not* evidence — it is the failure this module is built to prevent.

## Lessons

Four lessons, one per beat of the debugging loop. The first refuses to let you touch the code until the bug is reproducible. The second separates where the symptom *appears* from where the defect *is*. The third turns "I have a fix" into a falsifiable claim — and that is the beat where the fundamental you skipped arrives as an instrument. The fourth proves the fix was the fix.

1. **Reproduce before you touch anything** — the deterministic, minimal, automated reproduction; turning a bug report into a red test.
2. **Isolate: put distance between symptom and cause** — bisecting the search space; the crash line is rarely the bug line.
3. **Hypothesize: name the mechanism as a falsifiable claim** — where the concept you skipped becomes the instrument that fixes the bug.
4. **Verify the fix — and prove it was the fix** — revert-red, the regression net, and the fix that masks vs the fix that cures.

### Lesson 1 — Reproduce before you touch anything

**The teaching.** The first move in debugging is not to fix and it is not even to look at the code. It is to make the bug happen **on demand** — the same way, every time, from a single command. A bug you cannot reproduce is a rumor: you cannot localize it (there is nothing to observe), you cannot hypothesize about it (you have no fixed behavior to explain), and — the part beginners skip — you cannot *know you fixed it*, because "I changed something and now I can't make it happen" is indistinguishable from "the bug is hiding." Reproduction is the ground truth that every later beat is measured against.

A good reproduction has three properties, and you build them in this order:

- **Deterministic** — it fails the *same way every run*. "It's flaky" almost always means "I haven't found the input that controls it yet," not "the universe is random." Chase the input until the failure is reliable.
- **Minimal** — the smallest input that still triggers it. A bug that reproduces on a 400-line dataset also reproduces on some 2-element list; find that list. Minimization is not tidiness — every element you remove that *doesn't* stop the failure is an element you've proven irrelevant, which is isolation you got for free.
- **Automated** — captured as a failing test, not a sequence of things you type by hand. The instant you can write `assert class_average([90, 89]) == 89.5` and watch it go red, you have converted a vague report ("averages look off") into a mechanical, repeatable, unarguable fact. That red test *is* the reproduction, and it is the first entry in your debugging trail.

The discipline that makes this hard is emotional, not technical: the bug is *right there*, you think you see the fix, and writing a test first feels like a detour. It is not. The test you write before the fix is the only test you can trust, for the exact reason M04 hammered: a test written *after* the fix pins whatever the fixed code does, so it passes by construction and proves nothing. Reproduce first, or you will "fix" bugs you never confirmed existed.

**Worked example — from "averages look off" to a red test.** The report: *"Students say their averages are showing up one point low sometimes."* "Sometimes" is the tell — it means some inputs trigger it and some don't, and your job is to find one that does, reliably. Try the smallest thing: two scores whose true mean is not a whole number.

```python
>>> class_average([90, 89])   # true mean is 89.5
89
```

There it is: `89`, not `89.5`. Now minimize — is two the smallest? One score can't have a fractional mean; two is minimal. Now automate:

```python
def test_average_is_true_mean():
    assert class_average([90, 89]) == 89.5    # RED on the shipped code
```

Run it, watch it go red. You have not looked at the implementation yet, and you already have a deterministic, minimal, automated reproduction. Notice what "sometimes" actually meant: `class_average([80, 90])` returns `85` under the *same* bug — because the true mean is already a whole number, the defect is invisible on that input. The bug isn't intermittent; it is fully determined by whether the mean is fractional. You just converted "flaky" into "exactly these inputs," which is most of the isolation done before Lesson 2 begins.

**Named misconceptions:**

- **"I saw it once, I'll just fix it."** You saw a *symptom* once. If you fix without reproducing, you have no way to check the fix worked — you'll change a line, fail to trigger the symptom (maybe because you fixed it, maybe because you didn't hit the triggering input), and ship on a coin flip. No reproduction, no verification. Full stop.
- **"Reproduce means run the whole program."** Reproduction means the *smallest* thing that triggers the failure. Running the 400-line pipeline reproduces the bug and buries it in noise. The two-element list that fails is worth more than the full run, because everything it *doesn't* contain is proven irrelevant.
- **"It's flaky, so I can't reproduce it."** In a deterministic language, "flaky" is a hypothesis you haven't finished — there is an input (or an order, or a shared piece of state) that controls it. Lesson 3's mutable-default bug looks maddeningly flaky until you notice the trigger is *which call number* it is. Determinism is there; you haven't found its handle yet.
- **"Writing a test first is a detour; I'll add tests after I fix it."** The after-the-fix test pins the fixed behavior and can't fail — it's the decoration M04 named. The only test that proves a bug existed is the one you watched go red *before* you touched the code. Reproduction is the test, and it comes first.

### Lesson 2 — Isolate: put distance between symptom and cause

**The teaching.** The place where a program *misbehaves* is almost never the place where it is *wrong*. A `KeyError` is raised at the line that reads the dictionary, but the bug is at the earlier line that failed to write the key. A wrong number surfaces in a report, but the defect is three functions upstream in the calculation. **Isolation** is the beat where you close the distance between the symptom you can see and the cause you can't — and the tool is not cleverness, it is **bisection**: repeatedly cut the search space in half by asking a question whose answer eliminates one half.

You can bisect along several axes, and a fluent debugger picks the cheapest one:

- **Bisect the pipeline.** The output of `report(scores)` is wrong. Is the average already wrong when it comes out of `class_average`, or is `class_average` right and the formatting downstream mangles it? One `print(avg)` in the middle answers it and throws away half the code as a suspect. You are looking for the **last point the state is good and the first point it is bad** — the defect lives in the step between them.
- **Bisect the input.** The bug fires on a 100-element list. Does it fire on the first 50? On the first 25? Each halving either keeps the trigger (search the smaller half) or loses it (the trigger was in the other half). This is the minimization of Lesson 1 turned into a search algorithm.
- **Bisect over calls / time.** Some bugs only appear on the *second* call, or *after* some earlier operation. If call 1 is fine and call 2 is wrong with identical arguments, the cause is *state that survived between the calls* — which is a very specific, very findable class of defect (Lesson 3's flagship).

The instrument of isolation is the **probe**: a `print`, an `assert`, an `is` check, a peek at `fn.__defaults__`. A probe is a question you ask the running program, and each answer removes suspects. The failure mode this lesson prevents is **shotgun debugging** — changing several things at once and re-running, hoping the green comes back. Shotgun debugging occasionally lands a fix, and it is catastrophic anyway, because you cannot say *which* change fixed it, you probably introduced a second bug with one of the other changes, and you learned nothing transferable. One probe, one answer, one eliminated half. That is the whole method.

**Worked example — the wrong number, bisected.** `report([90, 89])` returns the string `"average 89, grade B"`. Two suspects: the average calculation and the letter-grade mapping. Bisect the pipeline with one probe:

```python
def report(scores):
    avg = class_average(scores)
    print("PROBE avg =", avg)     # ask the program: is the state good here?
    return f"average {avg}, grade {letter_grade(avg)}"
```

Run it: `PROBE avg = 89`. The average is *already* `89` (should be `89.5`) before `letter_grade` is ever called. That single line acquits `letter_grade` entirely and convicts `class_average` — you have halved the code you need to read. Now the search is inside one small function, `sum(scores) // len(scores)`, and the last-good/first-bad boundary is a single operator: `sum([90,89])` is `179` (good), `179 // 2` is `89` (bad). The cause is the `//`. You never had to read `letter_grade` at all.

**Named misconceptions:**

- **"The bug is where the crash is."** The crash is where the program *could no longer continue*, which is where the *consequence* landed, not where the *cause* lives. A `list index out of range` at line 40 is often a list that was built one element too short at line 12. Read the traceback to find where to *start* searching upstream, not where to fix.
- **"Shotgun debugging is fine if it ends green."** It ends green and leaves you unable to name the fix, unable to rule out a second defect you just introduced, and unable to reproduce your own reasoning. A green you can't explain is a liability, not a fix — it is the exact "it runs" fallacy M04 destroyed, now wearing a passing test as a disguise.
- **"Adding lots of prints is the same as bisecting."** Ten prints dumped in at once is shotgun observation — a wall of output you then have to read like tea leaves. Bisection is *one* probe placed at the *midpoint* of the current suspect region, chosen so its answer eliminates half. It's the difference between binary search and a linear scan you have to squint at.
- **"I understand the code, so I don't need to isolate — I can see the bug."** Sometimes. But "I can see it" on code you didn't write is exactly the overconfidence M02 named as the skim-that-isn't-reading. The probe costs ten seconds and converts "I think it's the average" into "the average is provably 89 here." Cheap certainty beats expensive assumption.

### Lesson 3 — Hypothesize: name the mechanism as a falsifiable claim

**The teaching.** Once isolation has cornered the defect, the temptation is to *fix* it. Resist for one more beat, because this beat is the entire point of the module. A **hypothesis** is not "I think this line is wrong" and it is certainly not "I have a fix." A hypothesis is a falsifiable claim of the form: **"The symptom S is caused by mechanism M; therefore if I do experiment E, I will observe result R."** It names the *mechanism* — the actual reason the code does what it does — and it makes a *prediction* you can be wrong about. If you cannot state the mechanism, you cannot state the hypothesis, and that is where the concept you skipped comes to collect its debt: **to name the mechanism, you have to learn it.**

This is why debugging is where fundamentals stop being trivia and become instruments. Consider the bug that leaks student names between unrelated calls. You can *see* the symptom (call two contains call one's data). But you cannot write the hypothesis — "the default list is a single object created once at definition time and shared across every call that doesn't pass its own list" — unless you actually understand how Python evaluates default arguments. The bug hands you a reason to learn that concept that no lecture can match: the program will not behave until you know it. And once you know it, the fix is obvious and *principled*, not a guess. A hypothesis is falsifiable precisely because it predicts something specific: *"if the default is one shared object, then `add_student.__defaults__` will have grown after the first call."* You can run that. If the tuple hasn't grown, your mechanism is wrong and you hypothesize again. That loop — claim, predict, test, revise — is science, done at a keyboard, in seconds.

The failure this lesson prevents is the **fix-shaped guess**: "let me try `roster = list(roster)`" or "maybe add `.copy()` somewhere" — changes proposed *before* a mechanism is named, evaluated only by whether the tests go green. A fix that makes the tests pass without a named mechanism is indistinguishable from a coincidence, and it leaves you exactly as ignorant as before, now with more code. The rule: **you may not edit the artifact until you have written down the mechanism and one experiment that would prove you wrong.**

**Worked example — the leak, hypothesized.** Isolation (Lesson 2, bisect-over-calls) has established: call one with `"Ada"` returns `["Ada"]`; call two with `"Grace"`, passing *no* roster, returns `["Ada", "Grace"]`. The state survived between two calls that share no arguments. Now the hypothesis, mechanism first:

> **Mechanism:** the parameter default `roster=[]` is evaluated *once*, when the `def` statement runs, producing a single list object that is reused as the default on every call that doesn't supply its own. `append` mutates that one shared object, so it accumulates across calls.
> **Prediction (falsifiable):** the function's stored default is that growing object, so `add_student.__defaults__` will show the accumulated names after each defaulted call.

Run the experiment:

```python
>>> add_student("Ada");     add_student.__defaults__
(['Ada'],)
>>> add_student("Grace");   add_student.__defaults__
(['Ada', 'Grace'],)
```

The prediction holds: the default object itself is growing. The mechanism is confirmed, and — this is the payload — you now *understand* a real Python fundamental you may not have known an hour ago, because the bug forced you to. The fix follows from the mechanism directly: don't share a mutable default; use the `None` sentinel and build a fresh list inside. You are not guessing; you are applying a concept you just earned.

**Named misconceptions:**

- **"'I have a fix' is a hypothesis."** A fix is a proposed *change*; a hypothesis is a claim about *why the bug happens*. You can have a fix that works and still have no idea why — which means you can't tell if it cures the bug or hides it, can't defend it in review, and can't recognize the same bug next week. The mechanism is the asset; the fix is a corollary of it.
- **"It's probably just a typo."** Sometimes it is. But "typo" is a hypothesis too, and a testable one: if it's a typo, the corrected token produces the right output *for the stated reason*. Bugs called "just a typo" are frequently a misunderstood mechanism wearing a typo's clothes — `//` vs `/` isn't a slip of the finger, it's not knowing the two operators differ.
- **"I don't need to understand it, I just need it to pass."** This is the exact sentence the whole course exists to refuse. A fix you don't understand is a bug that stopped reproducing on the one input you tried — you have swapped a defect you could describe for one you can't. The green bar bought you nothing but the appearance of resolution.
- **"Understanding the concept is a separate task I'll do later."** The bug is the concept's delivery vehicle, and there is no better moment to learn default-argument evaluation than while a program refuses to work until you do. "Later" is where the concept goes to never be learned. The debt is due now, and the bug is the invoice.

### Lesson 4 — Verify the fix — and prove it was the fix

**The teaching.** A change that makes the tests go green is a *candidate* fix, not a confirmed one. Three things must be true before you are done, and the third is the one everyone skips:

1. **The reproduction goes green.** The red test from Lesson 1 now passes. Necessary — but on its own, worthless, because *any* number of changes could make one test pass, including changes that mask the bug instead of removing it.
2. **The regression net stays green.** The rest of the behavior you didn't mean to touch still works. A fix that repairs the average and silently breaks `passed()` is not a fix; it's a trade. This is why you keep, and run, the tests around the code you're changing — the fix is only real if it's *local*.
3. **Reverting the fix brings the symptom back.** This is the beat that separates debugging from wishful thinking. Put the bug back — change `/` to `//` again — and confirm the reproduction test goes **red again**. If it does, you have *proven your change is causal*: the symptom is present exactly when your change is absent. If reverting *doesn't* restore the symptom, then something else fixed it (or it was never reproduced, or the test is decoration), and you do not understand your own fix. This is the mutation test of M04 pointed at your repair: **a fix you can't make fail on demand is a fix you can't trust.**

The distinction this lesson protects is **cure vs mask**. A cure removes the mechanism (the shared default object no longer exists; each call builds its own list). A mask suppresses the *symptom you happened to test* while the mechanism survives (imagine "fixing" the leak by having the caller pass a fresh list every time in the one code path you checked — the default is still shared and still a landmine everywhere else). The revert-red experiment plus a **regression test that pins the mechanism, not just the example** is how you tell them apart. For the leak, the mechanism-pinning test isn't "call two returns `['Grace']`" — it's "a value from an earlier defaulted call never appears in a later defaulted call's result," asserted across calls. That test fails a mask and passes a cure.

The final entry in your debugging trail is therefore not "tests pass." It is: *reproduction was red; my one-line change made it green; the regression net stayed green; reverting the change made it red again; and I added a test that pins the mechanism so this class of bug cannot silently return.* That is a defensible claim of repair. "It passes now" is not.

**Worked example — proving the division fix.** The reproduction `test_average_is_true_mean` was red. Change `//` to `/`; it goes green. Run the whole suite: `passed([90, 89])` is still `True`, `passed([50, 60])` still `False` — regression net intact (division by `/` returns a float, and `89.5 >= 70` is still `True`, so the comparison-based function is unaffected). Now the proof: revert `/` back to `//` and re-run — `test_average_is_true_mean` goes **red again**, while the two `passed` tests stay green. That last fact is doubly informative: it proves the `//` is the cause of *the average bug*, and it proves the average bug never affected `passed` (the boundary comparison is immune to the one-point truncation at cutoff 70). You now know not just that you fixed it, but the exact blast radius of the original defect. Restore the `/`. Done — and provably so.

**Named misconceptions:**

- **"Green now, so I'm done."** Green now means *this candidate change makes this test pass*. It doesn't tell you the change is causal (revert-red does), that it's local (the regression net does), or that it cured rather than masked (a mechanism-pinning test does). "Done" is a claim with four parts; green is one of them.
- **"I fixed a few things and now it works."** Then you cannot say which change was the fix, you may have introduced a new bug with one of the others, and you have no revert-red experiment because reverting *which* change? One defect, one hypothesis, one minimal change, one proof. Batch fixes are how a fixed bug and a fresh bug ship together.
- **"A regression test is just re-running the old tests."** Re-running old tests catches breakage in *covered* behavior; it does not pin the *new* mechanism you just learned. The regression test you add is the one that would have caught *this* bug — it encodes the concept the defect taught you, so the class of bug is closed, not just the instance.
- **"Reverting to check is a waste of time — I can see it's fixed."** "I can see it's fixed" is the same confidence that shipped the bug. Revert-red costs one keystroke and one test run and converts belief into proof. Skipping it is choosing to *feel* certain over *being* certain — the precise trade this entire course is built to stop you making.

### Lab M05-A — Reproduce and isolate (the truncated average)

**Goal.** Run the first two beats cleanly: turn a vague bug report into a deterministic, minimal, automated red test, then bisect the pipeline to convict a single operator — separating the input that *reveals* the bug from the inputs that *hide* it.

**Bug report (as filed):** *"Students say their class averages show up one point low sometimes, but other times they look fine."*

**Predict (on paper, before running).**
1. Write the **reproduction**: one input to `class_average` you predict will expose the bug, the value the buggy code returns, and the value the spec (true arithmetic mean) requires. Then write one input you predict will *hide* the bug (buggy and correct agree) and say why. Name the property that separates the two classes.
2. **Isolate:** the observable symptom is in `report(...)`'s output string. Name the single probe you would place, and predict what it prints — i.e. predict whether the average is already wrong *before* `letter_grade` runs or only after.
3. State the **mechanism** in one sentence (what is `//` doing that `/` would not), and predict the *type* of `class_average([80, 90])` under the buggy code vs the fixed code.

**Buggy artifact (as generated):**

```python
# starter: report.py   (BUGGY — shipped by the assistant)
def class_average(scores):
    """Mean of a non-empty list of scores."""
    return sum(scores) // len(scores)          # planted defect

def letter_grade(avg):
    if avg >= 90: return "A"
    if avg >= 80: return "B"
    if avg >= 70: return "C"
    return "F"

def report(scores):
    avg = class_average(scores)
    return f"average {avg}, grade {letter_grade(avg)}"

def passed(scores, cutoff=70):
    """True if the class average meets the cutoff."""
    return class_average(scores) >= cutoff


if __name__ == "__main__":
    print(report([90, 89]))     # observe AFTER your Predict sheet is written
```

**Build.** (1) Write `test_report.py` containing your reproduction — a test that goes **red on the shipped code**. Include the non-discriminating input as a separate test and predict it passes even on the bug. (2) Apply the one-token fix. The cured `class_average`:

```python
# solution: report.py  (only class_average changes)
def class_average(scores):
    """Mean of a non-empty list of scores."""
    return sum(scores) / len(scores)           # true division: always the exact mean
```

```python
# solution: test_report.py
import pytest
from report import class_average, passed

def test_true_mean_not_truncated():
    assert class_average([90, 89]) == 89.5      # REPRODUCTION: red on `//`, green on `/`

def test_integer_mean_still_int_valued():
    assert class_average([80, 90]) == 85        # non-discriminating: 85 == 85.0, green both ways

def test_passed_unaffected_by_fix():
    assert passed([90, 89]) is True             # regression net: comparison immune to truncation
    assert passed([50, 60]) is False
```

**Verify.** Run `pytest -q` on the shipped code first and watch **`test_true_mean_not_truncated` go red** while the other two pass — that split *is* the isolation: the bug lives exactly in the fractional-mean class. Apply the fix, run again, all green. Then **revert** `/` to `//` and confirm the reproduction goes red again while `test_passed_unaffected_by_fix` stays green — proving the `//` is causal for the average bug and never touched `passed`. Restore the fix. Reconcile against your Predict sheet: did you name `[80, 90]` (or any even-sum input) as a hider before you ran it?

**Integrate.** Two sentences: (1) state the property that partitions inputs into "reveals the bug" and "hides the bug" (fractional vs whole-number mean), and (2) explain why a suite built only from `[80, 90]`-style inputs would have shipped this bug green — connecting it to M04's *discriminating check*: a test that can't tell the buggy code from the fixed code is decoration.

> **Elle signal (see pacing notes):** predicting that `[80, 90]` would *fail* on the buggy code (because "the average function is broken, so surely it's wrong here too"), then watching it pass green, is **struggle-productive** — the reveal/hide partition installing. Name it.

### Lab M05-B — Hypothesize the mechanism (the roster that remembers)

**Goal.** Run the hypothesis beat under load: a symptom that appears *across calls* forces you to learn how Python evaluates default arguments, because you cannot state the mechanism — and therefore cannot write the fix as anything but a guess — without it. This is the module's flagship: the bug conscripts the concept.

**Bug report (as filed):** *"When I register a second student without passing a roster, their roster somehow contains the first student too. Each student should start with a roster of just themselves."*

**Predict (on paper, before running).**
1. **Reproduce:** write the two-call sequence you predict exposes the bug — call one with `"Ada"` (no roster), call two with `"Grace"` (no roster) — and predict the exact return value of *each* call under the buggy code and under a correct implementation.
2. **Hypothesize (mechanism first):** in one sentence, state *why* call two sees call one's data. Your sentence must name what object `roster=[]` is and *when* it is created. If you cannot write the sentence, that gap is the concept the bug is making you learn — go learn it, then write it.
3. **Falsify:** name one experiment whose result would *disprove* your mechanism if you were wrong. (Hint: if the default is one shared, growing object, what does `add_student.__defaults__` show after each defaulted call?) Predict the experiment's output.

**Buggy artifact (as generated):**

```python
# starter: enroll.py   (BUGGY — shipped by the assistant)
def add_student(name, roster=[]):
    """Register a student and return the roster they belong to."""
    roster.append(name)
    return roster


if __name__ == "__main__":
    print(add_student("Ada"))       # observe AFTER your Predict sheet is written
```

## Assessment

The assessment is **gaming-resistant by construction**: the passing bar is the *debugging trail* — reproduction-before-fix, a falsifiable mechanism named before the edit, and a revert-red proof — not a green pytest run. A learner cannot pass by getting the tests green, because the graded artifacts are (a) the red reproduction written before any change, (b) the written mechanism and its falsification experiment, and (c) the revert-red demonstration that the fix is causal. A guessed fix that lands green produces none of these and fails the order gate.

### Component 1 — Lab debugging trails (30%)

Submitted per lab, in order. Graded on: was the **reproduction** captured as a red test *before* the code was touched (Lab A); was the **mechanism** written as a falsifiable sentence naming object-lifetime *before* the fix, with its falsification experiment run (Lab B); was the fix **proven causal** by revert-red and pinned by a mechanism-level regression test (Lab C). **A learner who writes a leaky first hypothesis, runs the falsification probe, sees it disproven, and revises scores above one who writes the correct fix with no hypothesis at all** — because the certified outcome is *reasoning to the mechanism*, not landing on a patch.

### Component 2 — Debug exam: corner a planted defect (55%)

You are handed a **buggy artifact** (a small beginner-Python module, e.g. an off-by-one slice, a `==` where `is` was meant, a shadowed built-in, a shared-reference accumulator) and a **plain-English bug report with no line number**. Time-boxed, in this order, and **the order is graded**:

1. **Reproduce (before touching the code):** write a deterministic, minimal, automated test that goes **red on the shipped artifact**. Name one input that *hides* the bug and say why.
2. **Isolate:** state the probe(s) you place and the last-good/first-bad boundary they establish — the point where state is still correct and the point where it first goes wrong.
3. **Hypothesize:** write the mechanism as a falsifiable claim ("symptom S is caused by mechanism M; experiment E will show R"), run the experiment, and record confirm/revise. The mechanism must name the *concept* (default-arg lifetime, reference aliasing, floor vs true division, closure late-binding — whichever applies).
4. **Verify:** apply the minimal fix, confirm the reproduction goes green and the regression net holds, then **revert and confirm red returns**. Add one regression test that pins the *mechanism*, not the example.

Submitting a working fix *without* the step-1 red reproduction and the step-3 written mechanism caps this component at **40%** — because a green suite with no reproduction and no named mechanism does not demonstrate the outcome: *repairing code you understand, provably, rather than making a symptom stop reproducing on one input.*

### Component 3 — Debug viva (15%)

A 5-minute oral/whiteboard on an unseen buggy snippet: narrate the search live — *"the symptom surfaces at line X; I'd probe here because it splits the suspects in half; my hypothesis is mechanism M; I'd falsify it by E; and I'd prove the fix with revert-red."* You cannot bluff a bisection you are performing out loud, and you cannot state a mechanism you do not hold. This certifies the loop as a reflex, not a memorized checklist.

### Rubric

| Dimension | 0 — Absent | 1 — Emerging | 2 — Proficient | 3 — Fluent | Gaming-resistance (why a shortcut fails here) |
|---|---|---|---|---|---|
| **Reproduction** | Edits code with no way to trigger the bug | Reproduces by hand, not captured as a test | Deterministic, minimal, automated red test written *before* any edit | Also names the input class that hides the bug and why | A fix with no prior red test has nothing to prove it fixed anything |
| **Isolation** | Fixes at the crash line; assumes symptom = cause | One probe, unclear what it eliminates | Bisects to a last-good/first-bad boundary; convicts one location | Chooses the cheapest bisection axis (input / pipeline / calls) deliberately | Shotgun changes can't name a cause; the probe answer is on the trail |
| **Hypothesis (mechanism)** | "I have a fix," no mechanism | Names the wrong line without a mechanism | States a falsifiable mechanism naming the concept, runs the experiment | Predicts the falsification result and revises cleanly when disproven | A fix-shaped guess has no mechanism to check; the concept must be named |
| **Fix verification** | "Green now, done" | Reproduction green; no regression or revert check | Regression net holds **and** revert-red proves causality | Adds a regression test pinning the mechanism, not the example (kills a mask) | Green alone can't distinguish cure from mask; revert-red is required |
| **Ownership / evidence** | "It passes" offered as proof | Treats a green suite as sufficient | Distinguishes "stopped failing" from "understood and cured" | Names the concept now held as an instrument and the bug's exact blast radius | The trail (red→green→revert-red) is the credential; a clean run is not |

**Pass = ≥ 2 on every dimension AND the exam's step-1 red reproduction and step-3 written mechanism submitted before the fix.** No compensatory averaging on the order gate: a correct fix presented without a prior reproduction and a named mechanism does not pass, because it does not demonstrate the outcome — *cornering a defect in code you didn't write by reproducing it, localizing it, explaining its mechanism, and proving the repair — rather than guessing until the bar goes green.*

## Three-tier reading — debugging, and the difference between a bug you fixed and a bug that stopped reproducing

**Tier 1 — Material ground (verifiable facts).** Every claim in this module is provable at the keyboard in seconds, and none of it is a matter of opinion. Floor division and true division are different deterministic operations: `179 // 2` is `89` and `179 / 2` is `89.5`, every run, forever. A default argument is one object created once at definition time, provable by watching `add_student.__defaults__` grow from `(['Ada'],)` to `(['Ada', 'Grace'],)` across two calls that shared no arguments. `[[0] * n] * n` produces a list whose rows are the *same* object, provable by `g[0] is g[1]` returning `True`, and mutating one row through `set_cell` changes all of them because they *are* one row — while rebinding an int cell touches nothing shared, which is why the inner `[0] * n` is harmless. And a fix is *causal* exactly when reverting it restores the symptom: red → green on the change, red again on the revert, is a controlled experiment with one variable, and its result is a fact, not a feeling. Given a symptom and a candidate cause, "does reverting the fix reproduce the symptom?" is a computation. A repair is *proven* precisely when that computation comes back red.

**Tier 2 — What the field suppresses.** Two opposite distortions, each hiding the same truth about where understanding lives. The booster distortion — "the AI writes the code *and* debugs it; just paste the traceback back and it'll fix it" — suppresses that **a fix to a bug whose mechanism you don't understand is not a repair, it's a second guess laundered through a green bar.** The paste-the-error loop optimizes for a plausible-looking patch that makes the reported symptom stop, and it will happily hand you a mask — a special-case, a suppressed exception, a fix in the one path you mentioned — while the mechanism survives everywhere else, and now you own code you understand *less* than the code you started with. The productivity framing counts the minutes saved not-debugging and quietly stops counting the *understanding* not-acquired — the concept the bug was trying to teach you, that you outsourced back to the model. The traditionalist distortion — "you have no business touching a bug until you've mastered a debugger and the language's semantics cold" — suppresses that **the bug itself is the most efficient teacher of the concept you're missing**, precisely because a broken program will not move until you learn the mechanism, which is a motivation no curriculum can manufacture. Both camps avoid the honest middle: debugging generated code is the fastest *legitimate* on-ramp to understanding it, and the person who reproduces, isolates, hypothesizes, and proves owns the code in a way that neither the paste-the-error engineer (who never learned the mechanism) nor the study-first purist (who never met the bug that would have taught it) does. One camp says understanding is unnecessary; the other says it must be complete before you begin. The engineer who lets the defect conscript exactly the concept needed to fix it — no more, no less — is doing the load-bearing work that neither camp will name as work.

**Tier 3 — Sit with this (a question you cannot unknow).** You have now watched a bug refuse to move until you understood it. The roster kept leaking until you learned that the default `[]` is one object born at definition; the grid kept filling whole columns until you learned that `* n` copies a reference, not a list. In each case the fix was trivial *once you held the mechanism* — and impossible to trust before. Soon an assistant will hand you code with a defect just like these, you will paste the error back, it will return a patch, the tests will go green, and a deadline will make you ship. The patch may be a cure. It may be a mask that made the one symptom you tested stop while the mechanism waits in every other path. **The difference between a bug you fixed and a bug that merely stopped reproducing is exactly one thing: whether you can state the mechanism — and the green bar looks identical either way.** So when the page fires at 2 a.m. because the same defect surfaced on a path your regression test never covered, and someone asks what you changed and why it worked — will you be able to answer, or did you launder a second guess through a passing suite and call it understanding? At the moment it fails again, *did you ever fix it — or did you just make it quiet, and never learn the difference?*
