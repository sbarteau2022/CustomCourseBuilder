### Lesson 1 — The competence trap

#### Teaching text

Here is the trap, stated once so you can never say you weren't told:

> **An AI coding assistant raises your *apparent* capability much faster than your *actual* understanding — and because the code runs, the gap between the two is invisible to you at the exact moment it is growing.**

Pull that apart. **Apparent capability** is what you can *produce*: a working function, a passing script, a green test suite, a merged pull request. Before AI assistants, producing those things was slow and it required understanding as a *side effect* — you couldn't get the loop to compile without knowing, at least roughly, what the loop did. Production and understanding rose together. That coupling is the thing the assistant breaks. Now you can produce a correct-looking, actually-running function in seconds while understanding *none* of it. Production shoots up. Understanding stays flat. And nothing on your screen shows you the second line.

Why is the gap invisible? Because the only feedback the machine gives you is **behavioral**: the program runs, or it doesn't; the output appears, or it doesn't. Running is a fact about the *machine's* behavior on *one* input. It is not, and can never be, a fact about *your* understanding. There is no error message for "you don't know why this works." There is no red squiggle under a line you can't explain. The interpreter has no opinion about your mental model, so it stays silent — and you read that silence as approval.

There is a well-studied human bias underneath this, and naming it helps. Psychologists call it the **illusion of explanatory depth**: people believe they understand things — zippers, toilets, tariffs — far better than they do, right up until they're asked to explain the mechanism step by step, at which point the confidence collapses. Reading fluent, working code triggers the same illusion at full strength. The code is *right there*, it *runs*, it *looks* obvious — so your brain reports "I understand this" without ever checking. Fluency of the artifact gets misread as fluency of the reader. That misreading is the competence trap's engine.

The trap is not that AI writes bad code. Often the code is excellent. The trap is that **good, running code is the most effective possible disguise for your own missing understanding** — because it removes the one signal (it broke) that used to force you to look.

This is why this entire course teaches **verification before generation**, and why it is the front door: every later course assumes you have already felt this trap close on your own hand, in a lab, on a five-line function — while the stakes were zero.

#### Worked example — the function that runs, looks right, and is wrong

An assistant is asked for "a function that returns the point halfway between two numbers." It returns:

```python
def midpoint(a, b):
    return (a + b) // 2
```

You try it. `midpoint(2, 4)` → `3`. Correct. It runs, it gives the right answer, it looks like exactly what you asked for. Apparent capability: you now "have" a midpoint function. Time elapsed: four seconds. Understanding exercised: none.

Now predict, on paper, before reading further: what is `midpoint(3, 4)`?

The true halfway point of 3 and 4 is 3.5. But `//` is **floor division** — it throws away the fractional part and returns an integer. So `midpoint(3, 4)` is `7 // 2`, which is `3`. Not 3.5. The function silently rounds down, for *every* pair whose sum is odd. It ran. It gave a right-looking answer on the first input you happened to try. And it is wrong for half of all inputs, quietly, with no error, forever — until it produces a bug in something downstream that you then debug for an hour without suspecting the four-second function.

The learner who *ran it and moved on* left the trap armed. The learner who *predicted `midpoint(3, 4)` before trusting it* found the floor in ten seconds, while it was free to find. That ten seconds is the entire skill.

#### Misconceptions to surface (name them out loud)

- **"If it runs, it works."** No — running means it did not crash on the input you gave it. That is rung one of five (Lesson 4). Surface it with `midpoint(3, 4)`: it runs perfectly and returns the wrong number. Running and correct are different claims; the machine only ever tells you the first.
- **"If it gives the right answer on my example, it's correct."** No — one right answer is evidence about one input. `midpoint(2, 4)` is right; `midpoint(3, 4)` is wrong; same function. Surface it by asking for a *second* input, specifically one on a boundary or with a different shape (odd sum).
- **"I'll understand it later if I ever need to."** The later never comes on your schedule; it comes at 3 a.m. when it breaks in production and you are the person responsible. Surface it by asking, right now, "explain why line 2 is correct" — if the answer is "because it ran," the trap is already closed.

### Lesson 2 — AI-PRIMM: the loop

#### Teaching text

The defense against the competence trap is not "be smarter" or "don't use AI." It is a **loop** you run every single time, until it is muscle memory. The loop is **AI-PRIMM**:

> **P**redict → **P**rompt → **R**ead → **V**erify → **I**ntegrate

It adapts a loop from computing education called PRIMM (Predict–Run–Investigate–Modify–Make), which was built to stop students from copy-pasting code they didn't understand. We reshape it for the world where a machine writes the code:

1. **Predict** — *before you prompt anything*, write down what a correct solution must do: specific inputs mapped to specific required outputs, including the boundaries and the empty/degenerate case. This is a falsifiable contract. It is the step everyone skips and the step this whole course is built to protect.
2. **Prompt** — now ask the assistant. Because you predicted first, you are directing it against a spec you already hold, not fishing for something that looks plausible.
3. **Read** — read the generated code line by line and say, for each line, what it does. Not "skim until it looks familiar." Read until you could have written the explanation without the code in front of you.
4. **Verify** — check the code against your *prediction*, not against your hope. Run it on the specific inputs you predicted — especially the boundary ones — and, where it matters, write a test. Verification is designed to *distinguish* correct from incorrect, which means you deliberately feed it the inputs most likely to expose a defect.
5. **Integrate** — only now do you accept it into your work, along with the trail: the prediction, the read, and any discrepancy you caught and resolved. The trail is what you keep. It is the credential.

The single most important structural fact about this loop: **Predict comes before Prompt.** The natural, dopamine-driven order is Prompt → see something that runs → ship. AI-PRIMM inverts the first two steps on purpose, because a prediction written *after* you've seen the output is not a prediction — it's a rationalization. You cannot be surprised by an answer you've already read. And surprise — the gap between what you predicted and what the machine did — is the only alarm that tells you your understanding was thinner than you thought.

#### Worked example — one full turn of the loop

Task: "a function that counts the vowels in a word."

**Predict** (written before prompting anything):

| input | required output | why |
|---|---|---|
| `"cat"` | `1` | one vowel: a |
| `"AEIOU"` | `5` | must count uppercase too |
| `"xyz"` | `0` | no vowels |
| `""` | `0` | empty string: degenerate case, must not crash |

**Prompt:** "Write a Python function `count_vowels(word)` that returns the number of vowels (a, e, i, o, u), counting both upper and lowercase."

**Read** — the assistant returns:

```python
def count_vowels(word):
    total = 0
    for ch in word.lower():
        if ch in "aeiou":
            total += 1
    return total
```

Line by line: `word.lower()` makes the whole word lowercase (so the `"AEIOU"` case is handled — good, I predicted that mattered); loop over each character; `if ch in "aeiou"` is `True` when the character is one of those five; count it. I can explain every line.

**Verify** — run it against the *predicted* table, boundary cases included:

```python
count_vowels("cat")    # 1  ✓ matches prediction
count_vowels("AEIOU")  # 5  ✓ the .lower() earned its place
count_vowels("xyz")    # 0  ✓
count_vowels("")       # 0  ✓ empty string didn't crash
```

All four match. **Integrate** — accept it, and keep the trail: the prediction table, the one-line read of `.lower()`, and the confirmation that the empty case is safe. Note what happened: because I predicted `"AEIOU"` and `""` *first*, I was actively checking whether the code handled case-folding and the empty string — I wasn't just admiring output. Had the assistant forgotten `.lower()`, my `"AEIOU"` prediction would have caught it in one line.

#### Misconceptions to surface

- **"Predict means guess what code the AI will write."** No — you predict the *behavior a correct solution must have* (inputs → outputs), never the syntax. You are writing the spec you'll grade against, not forecasting the assistant's style. Surface it by showing that two very different-looking functions both satisfy the same prediction table.
- **"I'll prompt first and figure out what I wanted from what it gives me."** That is the trap wearing the loop's clothes. A spec derived from the output can never contradict the output, so it can never catch a defect. Surface it by asking: "what input would prove this wrong?" — a question you can only answer if you predicted first.
- **"Read means skim until it looks familiar."** Familiarity is the illusion of explanatory depth again. Reading means being able to state what each line does with the code covered. Surface it by covering the screen and asking the learner to narrate line 3.

### Lesson 3 — Prediction before prompting

#### Teaching text

Lesson 2 gave you the loop. This lesson sharpens the one step the whole course rests on, because it is the one every learner quietly drops the moment they're tired: **Predict.**

A prediction is not a mood. "It should work" is not a prediction. "It'll probably handle that" is not a prediction. Those are hopes, and hopes are unfalsifiable — there is no result that could prove them wrong, which is exactly why they feel safe and exactly why they're worthless. A **prediction is a falsifiable claim**: it names a *specific input* and commits to a *specific output*, such that the machine can prove you wrong. If you cannot draw the table where "predicted" and "actual" could disagree, you have not predicted.

Three properties make a prediction real:

1. **Specific.** Concrete inputs and concrete outputs. Not "handles negatives" but `clamp(-3, 0, 10)` → `0`.
2. **Falsifiable.** There must exist a result that contradicts it. A prediction you cannot lose is not a prediction.
3. **Boundary-aware.** The happy path is where defects hide *from* you; boundaries are where they hide *from the assistant*. Every prediction table must include the edges: the smallest input, the empty input, the value exactly on the limit, the negative, the zero. Most AI defects that survive a casual glance live precisely there — on the boundary the demo input never touched.

Writing the prediction *before* prompting does something the order-swapped version cannot: it forces you to actually decide what "correct" means *while you still have an independent opinion*. Once you've seen fluent, confident output, your sense of "what it should do" quietly reshapes itself to match "what it did." This is not a character flaw; it is how anchoring works in every human brain. The only defense is to write the contract down before the anchor exists.

And here is the part that feels backwards: **you should aim to be wrong.** A prediction you got right taught you nothing — you already knew. A prediction you got *wrong*, and then reconciled ("I predicted 10, it returned 0, because the code returns `low` on both branches — corrected model: the too-high case is unhandled"), is the single most valuable artifact you can produce, because it is the exact moment a hidden hole in your understanding became visible while it was still cheap. The grading in this course, everywhere, rewards a sharp wrong-then-corrected prediction over a silent lucky hit. Predict honestly, predict specifically, and do not be afraid to miss.

#### Worked example — from a hope to a contract

An assistant is going to be asked for "a function that validates whether a string is a non-empty username of at most 8 characters." The lazy prediction is: *"it should validate usernames."* That is a hope. You cannot be wrong about it, so it cannot protect you.

The real prediction is a decision table you write *before prompting*:

| input | required output | which rule it tests |
|---|---|---|
| `"stew"` | `True` | ordinary valid name |
| `""` | `False` | non-empty rule — the degenerate case |
| `"abcdefgh"` | `True` | exactly 8 — the boundary, must be allowed |
| `"abcdefghi"` | `False` | 9 chars — one past the boundary, must be rejected |

Notice what the act of writing this forced: you had to *decide* whether 8 is allowed or rejected (it's allowed — "at most 8"), and you had to *decide* what the empty string does. Those two rows are where a generated `if len(name) > 8` versus `if len(name) >= 8` will disagree, and you now hold the answer *independently* of whatever the assistant produces. When the code arrives, `"abcdefgh"` → `True` either matches your contract or it doesn't. That is verification. Without the table, you'd have squinted at `>=`, thought "looks about right," and shipped an off-by-one.

#### Misconceptions to surface

- **"'It should work' is a prediction."** No — it's unfalsifiable, therefore worthless as a check. Surface it by asking "what specific input, with what specific output, would prove that false?" If they can't answer, they haven't predicted.
- **"Predicting the happy path is enough."** The happy path is exactly the input the assistant also optimized for; it's where you and the defect *agree*. The boundary is where you find out. Surface it by requiring one edge row (empty, zero, or the exact limit) in every table.
- **"Getting my prediction right is the goal."** No — a correct prediction confirms what you knew; a *reconciled wrong* prediction reveals what you didn't. Surface it by scoring a sharp miss-and-correction above a silent hit, out loud, so the incentive is unmistakable.

### Lesson 4 — What "it runs" is evidence of

#### Teaching text

The competence trap lives inside a single confusion: treating "it runs" as if it meant "it's correct and I understand it." Untangling that confusion is a matter of seeing that there is a **ladder of evidence**, and "it runs" is the bottom rung.

1. **It runs without error.** The interpreter accepted it and didn't raise on the input you gave. Evidence of: valid syntax and no crash *on that input*. Nothing more.
2. **It produces output.** Something came back. Evidence of: the function returns *a* value. Not that the value is right.
3. **The output is correct on the inputs I tried.** The values match expectation for the specific cases you ran. Evidence of: correctness *on those cases*. This is where the trap springs, because "the cases you tried" are usually the happy path.
4. **It is correct on the inputs that matter, including boundaries.** You ran it against a prediction table with the edges in it, and it held. Evidence of: correctness across the space you actually care about.
5. **I can explain why it is correct.** With the code covered, you can state the reason each part is right. Evidence of: understanding — the thing the machine never measures.

Every rung is *real* evidence. The error is reading a lower rung as a higher one. "It runs" (rung 1) is genuine information — a crash would be worse. But the distance from rung 1 to rung 5 is the entire competence trap, and the assistant delivers you to rung 1 or 2 for free while letting you *feel* like you're on rung 5. Only prediction-driven verification (rung 4) and reading-until-you-can-explain (rung 5) are climbed by hand. The machine cannot climb them for you, because they are facts about *you*, not about the code.

This is why, in this course, **the deliverable is never the running program.** A program that runs is rung-1 evidence — the cheapest kind, and the kind an assistant manufactures in seconds. The credential is the **judgment trail**: the prediction you committed to before you looked, the read that shows you climbed to rung 5, and the error you caught (or the reasoned confidence that there was none to catch). A learner who hands in a clean, passing program with no trail has demonstrated nothing the assistant couldn't have demonstrated alone. A learner who hands in a *buggy* program alongside an accurate prediction that *located the bug* has demonstrated exactly the outcome this course exists to build. Grade the trail, never the green checkmark.

#### Worked example — a function that climbs to rung 3 and stops

An assistant is asked for "the last element of a list." It returns:

```python
def last(xs):
    return xs[len(xs)]
```

Rung 1: it runs (the file imports without error). Rung 2: called on a list, it produces... an error, actually — but watch how easy it is to not notice. If your only test is reading it, `xs[len(xs)]` *looks* like "the element at the last position." It reads plausibly. That's rung-3-by-eyeball: it looks correct on the input you imagined.

Now verify at rung 4 with a concrete predicted input. Predict: `last([9, 8, 7])` should be `7`. Run it: `[9, 8, 7]` has length 3, so `xs[len(xs)]` is `xs[3]` — and valid indices are 0, 1, 2. Index 3 is out of range: `IndexError`. The last element is at index `len(xs) - 1`, or simply `xs[-1]`. The function is off by one, and *reading alone did not catch it* — only a concrete predicted input, actually run, exposed it. That is the difference between rung 3 (looks right) and rung 4 (proven right on the input that matters).

#### Misconceptions to surface

- **"Passing tests means it's correct."** No — tests are evidence only about the cases they contain. Green means "correct on what I checked," which reaches rung 4 *only if the revealing cases are in the suite*. Surface it with the buggy `clamp` from Lab M01-B: a suite that checks only `clamp(5, 0, 10)` and `clamp(-3, 0, 10)` passes green, because it never tries the one case — `clamp(15, 0, 10)` — that exposes the defect. Green with the wrong cases is a coverage gap wearing a passing badge.
- **"The running program is the deliverable."** No — the program is rung-1 evidence and the assistant makes it for free. The deliverable is the judgment trail. Surface it by asking "what did you hand in that the AI couldn't have?" — if the answer is "the code," nothing was demonstrated.
- **"A green CI badge means I understand it."** CI measures the machine's behavior, never your understanding. Surface it by covering the diff and asking the author to explain the change; green tells you it works, not that you could have written it.

## Labs

Three labs. All three are **prediction-first**: the Predict step is written and *sealed* before any code is read or run, and the sealed prediction plus the reconciliation is the graded artifact. M01-A and M01-B are core; M01-C is accelerate-optional (see Elle notes). The code is intentionally tiny and readable at a beginner level — the point is never to *write* it, only to *predict, read, and verify* it.

> **Harness.** A tiny provided module `primmharness.py` gives `seal(name, text)` — it appends your prediction to an append-only, timestamped file (`predictions.sealed.md`) so it cannot be edited after you measure. It is stdlib-only and runs anywhere Python 3.12 does. Full source:
>
> ```python
> # primmharness.py
> import datetime
> import pathlib
>
> SEAL_FILE = pathlib.Path("predictions.sealed.md")
>
> def seal(name: str, text: str) -> None:
>     """Append a prediction to an append-only, timestamped file."""
>     stamp = datetime.datetime.now().isoformat(timespec="seconds")
>     with SEAL_FILE.open("a", encoding="utf-8") as f:
>         f.write(f"\n## {name} @ {stamp}\n\n{text}\n")
>     print(f"sealed {name!r} at {stamp} -> {SEAL_FILE}")
> ```
>
> **What sealing does and does not enforce (know this going in).** `seal` guarantees one thing: you cannot edit a prediction *after* you've written it — the file is append-only and timestamped. It does **not** verify that you predicted *before* you read the code; that ordering runs on the honor system. The mechanism that actually deters peeking is not the seal — it is the **reconciliation-of-misses scoring**, which pays you more for being visibly wrong and then correcting sharply than for a silent lucky hit. A learner who peeks and back-fills a "correct" prediction forfeits exactly the miss-and-correction trail that earns the most marks. Predict honestly, and don't fear a miss.

### Lab M01-A — Predict before you peek *(the competence trap, in miniature)*

**Goal:** feel the trap close on a five-line function that runs perfectly and surprises you anyway — while the stakes are zero.

#### Predict (on paper, before reading or running anything)

You will be handed a function `add_item(item, basket)` that "adds an item to a basket and returns the basket." You have **not** seen its code. Predict, for this exact sequence of calls made one after another in a fresh program:

```python
first  = add_item("apple")
second = add_item("bread")
```

1. What is `first` right after line 1? Write the exact list.
2. What is `second` right after line 2? Write the exact list.
3. Is `first` the *same list object* as `second` (`first is second`)? Yes/No — and one sentence of why.

Seal it: run `python -c "from primmharness import seal; seal('M01-A', open(0).read())"`, paste your three answers, and press Ctrl-D. Your sheet is now write-locked.

#### Build

You are given `basket.py` (this is the artifact under judgment — read it only *after* sealing):

```python
# basket.py  — the artifact under judgment
def add_item(item, basket=[]):
    basket.append(item)
    return basket
```

There is nothing for you to write. This lab is trivial to *run* and hard to *predict* — that is the anti-gaming design. The credential is your sealed sheet and the reconciliation, not a program.

Autograded test (`test_basket.py` — checks the *behavior* is what it is, so you can verify your prediction; it does **not** grade your understanding, which the rubric does):

```python
# test_basket.py
from basket import add_item

def test_default_basket_is_shared_across_calls():
    # The two no-argument calls in this process share the SAME default list,
    # because the default [] is created once, when the function is defined.
    first = add_item("apple")
    second = add_item("bread")
    assert first is second
    assert second == ["apple", "bread"]

def test_explicit_basket_is_independent():
    # Passing your own list opts out of the shared default entirely.
    x = add_item("egg", [])
    y = add_item("milk", [])
    assert x == ["egg"]
    assert y == ["milk"]
```

Run it: `pytest test_basket.py -q`. Both tests pass — meaning the surprising behavior is real, not a mistake.

#### Verify / Integrate

Open your sealed sheet next to the result. The trap: most learners predict `first == ["apple"]` and `second == ["bread"]` and `first is second` → `No`. The machine says `first` becomes `["apple", "bread"]` too, and `first is second` → `Yes`. Why: the default `basket=[]` is created **once**, when the function is defined, and *reused* on every call that omits the argument — so both calls append to the same list. The code ran cleanly on every input; nothing warned you.

For **every** prediction you missed, write one sentence: *"I predicted X because I believed \_\_\_; the machine does Y, so the corrected model is \_\_\_."* A missed prediction with a sharp correction scores **higher** than a lucky hit with no reasoning. Then answer the one question that makes this the whole course in miniature: *the code ran and never errored — so what, exactly, would have caught this before you shipped it?* (Answer: predicting the second call's output specifically, before trusting the first.)

### Lab M01-B — Run the full AI-PRIMM loop *(the flagship)*

**Goal:** run all five steps — Predict, Prompt, Read, Verify, Integrate — against a spec, and catch a planted D2 defect using nothing but your own prediction table.

#### Predict (on paper, before reading the generated code)

The spec you are directing the assistant toward: **`clamp(value, low, high)` returns `value` constrained to the range `[low, high]` inclusive** — if `value` is below `low`, return `low`; if above `high`, return `high`; otherwise return `value` unchanged.

Before reading any generated code, fill in the required-output column. **Include the boundaries** — this is where the defect will live:

| input | required output | which rule it tests |
|---|---|---|
| `clamp(5, 0, 10)` | ____ | inside the range |
| `clamp(-3, 0, 10)` | ____ | below `low` |
| `clamp(15, 0, 10)` | ____ | above `high` |
| `clamp(0, 0, 10)` | ____ | exactly on `low` (boundary) |
| `clamp(10, 0, 10)` | ____ | exactly on `high` (boundary) |

Seal it: `python -c "from primmharness import seal; seal('M01-B', open(0).read())"`, paste the completed table, Ctrl-D.

#### Build

**Read** — the assistant returns this (`clamp.py`). Read it line by line and narrate each branch *before* you run anything:

```python
# clamp.py  — generated code, read it before trusting it
def clamp(value, low, high):
    if value < low:
        return low
    if value > high:
        return low   # generated line — does this match your predicted table?
    return value
```

**Verify** — the test encodes your predicted contract (`test_clamp.py`):

```python
# test_clamp.py
import pytest
from clamp import clamp

@pytest.mark.parametrize("value, low, high, expected", [
    (5, 0, 10, 5),      # inside
    (-3, 0, 10, 0),     # below low
    (15, 0, 10, 10),    # above high
    (0, 0, 10, 0),      # on low
    (10, 0, 10, 10),    # on high
])
def test_clamp_matches_spec(value, low, high, expected):
    assert clamp(value, low, high) == expected
```

Run `pytest test_clamp.py -q`. One case fails: `clamp(15, 0, 10)` returns `0`, but your sealed table says `10`. The generated code returns `low` on *both* out-of-range branches — the "above `high`" branch should return `high`, not `low`. This is a D2 defect: it passes three of five cases (including a boundary), reads plausibly, and would survive any test suite that forgot the "above the range" case. Your prediction table caught it because you predicted `clamp(15, 0, 10)` → `10` *before* the fluent code could anchor you to `0`.

**Integrate** — the corrected artifact (`clamp_solution.py`):

```python
# clamp_solution.py  — reference solution
def clamp(value, low, high):
    if value < low:
        return low
    if value > high:
        return high   # fixed: the too-high case is clamped to the high bound
    return value
```

Swap it in and re-run: all five cases pass.

#### Verify / Integrate

**Grading rule (state it up front):** full marks require the correct predicted table **and** locating the defect at the specific line **and** naming the input that reveals it (`clamp(15, 0, 10)`). A green test run with no prediction trail scores near zero — the passing program is rung-1 evidence the assistant could have produced alone. A learner who handed in the *buggy* `clamp.py` alongside "I predicted 10 for `clamp(15,0,10)`, the code returns `low` on both branches at line 5, corrected to `high`" has demonstrated the whole outcome, even though their program was the broken one.

Write the one-sentence rule this lab teaches: **the boundary case you predict before prompting is the one that catches the defect the demo input hides.**

### Lab M01-C — Clean-run discrimination *(no paranoia points)* — accelerate-optional

**Goal:** judge which AI snippets are actually broken *without* over-flagging the ones that are fine. Catching defects is half the skill; the other half is *not* crying wolf on clean code, or your judgment becomes noise nobody trusts.

#### Predict (before running)

You are given three tiny functions (`snippets.py`). For each, predict the output on the given input, and label it **CLEAN** or **DEFECTIVE**:

1. `is_even(4)` → ____ ; `is_even(7)` → ____ . Clean or defective?
2. `last([9, 8, 7])` → ____ . Clean or defective?
3. `first([9, 8, 7])` → ____ . Clean or defective?

Seal it: `seal('M01-C', ...)` as before.

#### Build

```python
# snippets.py
def is_even(n):
    return n % 2 == 0        # returns True when n is divisible by 2

def last(xs):
    return xs[len(xs)]       # generated — index it before you trust it

def first(xs):
    return xs[0]             # returns the element at index 0
```

Autograded test (`test_snippets.py`):

```python
# test_snippets.py
import pytest
from snippets import is_even, last, first

def test_is_even_is_clean():
    assert is_even(4) is True
    assert is_even(7) is False

def test_first_is_clean():
    assert first([9, 8, 7]) == 9

def test_last_is_defective():
    # xs[len(xs)] indexes one past the end: [9,8,7][3] is out of range.
    with pytest.raises(IndexError):
        last([9, 8, 7])
```

Run `pytest test_snippets.py -q`: all three pass, confirming that `is_even` and `first` are genuinely clean and `last` genuinely raises. The correct answer set is: **CLEAN, DEFECTIVE, CLEAN**. Only `last` is broken (`xs[len(xs)]` is off by one — the last element is `xs[len(xs) - 1]` or `xs[-1]`).

**Grading rule:** you get the marks for flagging `last` **and** for *not* flagging `is_even` or `first`. Flagging a clean function as defective is a **false positive** and costs marks — there are no paranoia points. This mirrors the course-level assessment component *clean-run discrimination (25%)*: a reviewer who flags everything is as useless as one who flags nothing. For each snippet, your trail must say *why* it is clean or defective in one sentence — "clean: `n % 2 == 0` is `True` exactly for even `n`" earns the mark; "clean: it ran" does not.

## Assessment

Maps to the course components **judgment-trails (60%)** and **clean-run discrimination (25%)**, with the weekly **sealed-readings (15%)** carried by the three-tier reading below. Gaming-resistance is the binding constraint, enforced three ways:

1. **The sealed prediction is the credential.** Every lab and the exam are graded primarily on the *Predict* artifact and the *reconciliation*, not on a passing program — the programs are provided complete (or trivial), precisely so that copying them earns nothing. A clean run with no trail scores below a wrong prediction with a sharp correction.
2. **The programs are anti-trophies.** There is no working program to hand in that demonstrates the outcome, because the outcome is *judgment* — a defensible prediction, a real read, a caught error — not a green checkmark. A buggy artifact with an accurate defect-locating prediction outscores a clean artifact with no trail.
3. **The exam is unseen and prediction-gated.** The prediction is sealed before the code is read; if the seal is missing or was edited after reading, the exam is void.

### Module exam — "Predict, read, verify, own"

The learner is handed an **unseen AI-generated Python function** (~10–15 lines, beginner-readable) implementing a small stated spec — for example, "return the number of days in a given month and year, accounting for leap years," with a planted D2 defect (e.g. a leap-year rule that checks `year % 4 == 0` but omits the `% 100` / `% 400` correction). They must, **in order, with the prediction sealed before reading the code**:

1. **Predict (sealed).** From the *spec alone*, write a falsifiable table of at least five inputs → required outputs, and it **must include boundary cases** (February; a century year like 1900; a `% 400` year like 2000).
2. **Read.** Narrate what each line of the generated code does, with the code covered where possible.
3. **Verify.** Run the code against your predicted table and identify which input the code disagrees with your prediction on.
4. **Locate & reconcile.** Point to the specific line that causes the disagreement, state the corrected mental model in one sentence, and — the ownership step — answer: *if this shipped and failed in production, what did you own, and what would have caught it?*

The submitted artifact is the judgment trail: sealed prediction → read → verification → located defect → the ownership sentence. A learner who runs the provided code but cannot predict scores near zero — running a provided script is not the outcome. A learner who predicts `1900` → `28` days, reads the `year % 4 == 0` line, and locates it as the defect has passed even if they never "fixed" the code.

### Rubric (gaming-resistant)

| Criterion | Weight | 0 — absent | 1 — partial | 2 — proficient | 3 — commanding |
|---|---|---|---|---|---|
| **Prediction sealed before reading** | gate | No sealed sheet, or edited after reading the code → **exam void** | — | Sealed, timestamped, unedited | Sealed with explicit per-row reasoning |
| **Prediction is falsifiable & boundary-aware** | 25% | Vague ("it should work"), no concrete I/O | Concrete but happy-path only | ≥5 concrete rows including one boundary | Boundaries chosen to *target* the likely defect (Feb, 1900, 2000) |
| **Read locates behavior in the code** | 20% | Can't say what lines do | Narrates some lines, misses the key one | Narrates every line, covered | Narrates *and* flags the suspect line before running |
| **Verification distinguishes** | 20% | Runs nothing, or only the happy path | Runs cases but not the revealing one | Runs the input that exposes the defect | Chose that input *because* the prediction predicted the split |
| **Clean-run discrimination** | 15% | Flags a correct function as broken (false positive) or misses a real defect | One error of either kind | Correct clean/defective call, thin reasoning | Correct call with a one-sentence mechanism for each |
| **Reconciliation & ownership** | 20% | Ignores misses; no ownership answer | Notes the miss, no corrected model | Every miss → corrected one-sentence model + names what it owned | Correction generalizes to a rule; ownership answer names *what would have caught it* |

**Passing requires ≥ 2 on "Prediction is falsifiable & boundary-aware" AND ≥ 2 on "Reconciliation & ownership."** A learner who reproduces a passing program but cannot predict a falsifiable boundary case, or cannot say what they would own when it fails, does **not** pass — matching the course spine: grade the prediction and the judgment, never the running program.

## Elle pacing notes

Signals for the adaptation runtime. M01's dominant risk is **not** difficulty — the code is five lines. The risk is *"why are you slowing me down, just let me prompt it."* Every reroute is built to let a *surprise* — the learner's own missed prediction — win the argument, not the instructor.

- **Wall — "predicting is a waste of time, the AI will just write it" (the prediction-resistance wall).** The most common M01 stall; reads as impatience, not struggle. **Reroute:** stop explaining, run Lab M01-A immediately and make them predict the two `add_item` calls *out loud* before revealing the code. The shared-default surprise on their own screen does the arguing. Do not return to theory until they've been wrong once. Log as `blocked-motivational`, distinct from `blocked-conceptual`.
- **Wall — "I read it, it looks fine" (the skim-as-read wall).** The learner equates familiarity with understanding (illusion of explanatory depth). **Reroute:** cover the code and ask them to narrate the suspect line from memory. If they can't, they skimmed. In Lab M01-B, have them state what line 5 (`return low` in the too-high branch) does *before* running the test. The gap between "looks fine" and "I can state what it does" is the whole lesson; make them feel it.
- **Wall — over-flagging / paranoia after the first caught defect.** Having been burned once (mutable default, off-by-one), some learners swing to "trust nothing" and flag clean code as broken. **Reroute:** Lab M01-C's no-paranoia-points rule, applied immediately — mark a false positive on `is_even` as a *miss*, equal in cost to missing `last`. Judgment is discrimination, not suspicion. Log `blocked-conceptual` on the discrimination model if it persists.
- **Signal — predicting `first is second` → No in Lab M01-A and being wrong.** This is the lesson *landing*: the learner just discovered the shared mutable default by falsified prediction, exactly the intended surprise. Log `struggle-productive`, never `blocked`. Do not smooth it away — the surprise *is* the outcome.
- **Signal — predicting `clamp(15,0,10)` → 10 and finding the code returns 0.** The flagship catch, produced by the learner's own boundary prediction. Log `struggle-productive`. If they *also* located line 5 as the cause, they've hit rung 5 — accelerate-eligible.
- **Signal — a learner who, even after Lab M01-A, still says "but it ran, so it's fine."** This is the one confusion that must die before M02 (Reading code you didn't write) or nothing downstream is coherent. If it survives Lab M01-A, hold the barrier: do the `midpoint(3, 4)` worked example one-on-one — a program that runs *and* returns the wrong number — before advancing. Log `blocked-conceptual` on the runs-vs-correct distinction specifically.
- **Accelerate — clean M01-A reconciliation + correct M01-B table *and* located defect.** Such a learner has demonstrated predict-read-verify end to end and may **skip Lab M01-C's build**, submitting only its prediction sheet (clean/defective calls with one-sentence reasons). Do not, however, let them skip the *sealing habit* — speed on judgment does not license dropping the Predict-before-Prompt discipline that the entire program rests on.
- **Do NOT accelerate past the sealing habit.** The point of M01 is not that the learner *can* predict once; it is that they predict *every time, before prompting, sealed*. Accelerate through the *labs*, never out of the *habit*. A learner who is fast but stops sealing has failed M01's actual objective.

## Three-tier reading

Specific to this module's subject — *outsourcing judgment to a machine that raises your apparent capability faster than your real understanding* — not boilerplate.

- **Tier 1 — material ground (verifiable, reproducible today).** An AI coding assistant is a model trained to predict plausible next tokens over an enormous corpus of human-written code — the accumulated labor of countless developers, much of it scraped from public repositories without individual consent, credit, or payment to the people whose work now answers your prompt. What it emits is optimized to *look* right — to be statistically typical of correct code — which is not the same property as *being* right, and the two come apart exactly on the boundary cases the training distribution underweights. You can reproduce the gap on your own laptop this hour: `midpoint(3, 4)` returns `3` and never errors; `clamp` returning `low` on the too-high branch passes three of five cases; `xs[len(xs)]` reads like "the last element" and raises `IndexError`. In every case the program *runs* — a fact about the machine's behavior on one input — while telling you nothing about whether you understand it or whether it's correct. That "it runs ≠ it's correct ≠ you understand it" is not opinion; it is demonstrable in five lines.

- **Tier 2 — what the field suppresses.** The dominant framing is *productivity*: lines shipped, tickets closed, time-to-merge, "10x engineer." That framing can measure everything except the one thing it is silently trading away — the transfer of *understanding* out of the person who remains responsible. The booster cannot say "the reviewer's competence quietly atrophies because the code always runs," because the product is sold on the promise that you no longer need that competence. The nostalgic critic cannot admit that the pre-AI craft they idealize also ran on copied Stack Overflow answers and cargo-culted patterns — understanding was never as universal as the eulogy claims. Both halves are true, and both are unspeakable in their own camp. "It made me faster" and "I understand my system less" are not contradictory reports; they are the *same* report, and the productivity metric is built to show you only the first half of it.

- **Tier 3 — sit with this (a question you can't unknow).** When the function you shipped fails at 3 a.m. — in production, in front of the person you answer to — and you open the file and cannot explain why line 5 is wrong because you never could, only that it ran the day you merged it: what, precisely, did you own? The output, or the understanding you traded for the speed that got you promoted? And the model that wrote the line you can't read — trained on the labor of developers you'll never meet, who can't see that their work is now the code you can't check — at what point does *not being able to verify what you ship* stop being a tooling limitation and become a choice you keep making, every time you skip the prediction?
