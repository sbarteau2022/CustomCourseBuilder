## Module overview

Four rooms, each one built on the wreckage of the room before it.

**Room one.** You wrap the AIE-302 system's model call in the plainest possible FastAPI endpoint — one process, one model, no cleverness — and you load-test it yourself, with a load-testing tool you write in about forty lines, before you're allowed to name a library that does it for you. It works fine at concurrency one. You will watch it, in numbers you produced, stop working fine.

**Room two.** You build a request batcher by hand — a queue, a background thread, a timeout — and discover that batching is not a free throughput multiplier. On the CPU this course runs on, it buys a real, measurable, and *modest* win (not the 5–10× a GPU gets, because a GPU has idle parallel lanes to fill and a CPU mostly doesn't), and it buys that win by making some individual requests *wait longer*, not shorter. You will predict the trade before you see it.

**Room three.** You make the same slow request feel fast without making it faster. Token-by-token streaming cuts the time to *first visible output* dramatically while leaving total completion time, total compute, and total cost completely unchanged. You will measure both numbers on the same request and learn to never again confuse them.

**Room four.** You stop paying for compute you didn't need to spend. A cache only works if the queries repeat, and "the queries repeat" is an empirical claim about *your* traffic, not a property of caches in general — so you build one, run it against a realistic, skewed (not uniform-random) query distribution, and read off a real hit rate instead of asserting one.

**The descent.** Each lesson is motivated by a measured failure of the lesson before it: the naive server's queueing collapse motivates batching; batching's amortization ceiling and its introduced tail latency motivate asking what you're actually optimizing (perceived latency vs. throughput are different axes, which motivates streaming); and the fact that batching and streaming both still pay full compute cost on every single request, repeat or not, motivates caching — the one technique in this module that makes a request disappear entirely instead of making it cheaper. **Re-ascent:** you leave this module able to take an unseen serving scenario — a load profile, an SLO, a cost budget — and say, with a computed number, which lever to pull first and what it will cost you not to.

## Lessons

### Lesson 1 — The synchronous API and its measured collapse

**Teaching text.** A model server's job looks, from the outside, like any other web service: receive a request, do some work, return a response. The difference that matters for everything else in this module is *what kind* of work sits in the middle. A database lookup is I/O-bound — the CPU is mostly idle, waiting on disk or network, and an operating system thread scheduler is very good at overlapping many such waits. A forward pass through a language model is **compute-bound** — for the whole duration of `generate()`, the CPU (or GPU) is doing dense linear algebra and nothing about the wait is idle. This single distinction is the reason a naive model server behaves nothing like a naive CRUD API under load, and most of the folklore that gets copied from web-service scaling advice into model-serving code is wrong for exactly this reason.

FastAPI's `def` (synchronous) route handlers run in a bounded thread pool; an `async def` handler runs on the event loop directly. The common misconception — "make it `async def` and it'll handle concurrency" — is backwards for compute-bound work: `async def` helps when a handler spends its time *awaiting* I/O, because the event loop can run other requests during that wait. A synchronous, CPU-bound `model.generate()` call blocks whatever thread is running it for its *entire* duration regardless of which route style you chose; making it `async def` without an `await` inside it doesn't parallelize the compute, it just blocks the *whole event loop* instead of one worker thread — a strictly worse outcome. This lesson isolates the one thing that actually determines throughput: how many of these compute-bound calls can genuinely run **at the same time**, on the same box.

For this module's labs, that number is pinned to exactly **one**, on purpose, with `torch.set_num_threads(1)` and a single server process. This is not a crippled setup — it is the cleanest possible instrument. With a single serialized compute resource behind the API, the server's behavior under load reduces to a textbook **closed queueing system**: `concurrency` simultaneous callers, each waiting for a response before sending the next request, all queuing for one resource that can only do one thing at a time. In that system, two quantities are exactly predictable from one measured baseline number:

```
L0 = mean single-request latency, measured alone, at concurrency = 1

Throughput ceiling:     X_max = 1 / L0                (requests/sec — flat, never rises)
Latency at concurrency c (c >= 1):     W(c) ≈ c · L0    (grows linearly, no plateau)
```

There is no knee in this curve, no "it's fine up to N users." With one serialized resource, the second concurrent request already waits behind the first — latency starts climbing at `c = 2`, not at some higher saturation point. This is the sharpest, most teachable version of "the naive server falls over": it isn't a cliff you hit at high load, it is a straight line with slope `L0` starting from the very first unit of concurrency past one, and no amount of client-side retrying, timeout-tuning, or thread-pool-size fiddling changes the slope, because none of those touch the actual bottleneck — one CPU, one model, one thing happening at a time.

**Worked example.** Reference measurement: `distilgpt2` (82M parameters, CPU, greedy decoding, `max_new_tokens=30`), single request, warm (post-first-call) latency `L0 = 0.340s`. *(Your own machine will measure a different `L0` — that's expected, and the point of the module: the shape of what follows is the real, general result; the specific seconds are yours to produce.)*

```
X_max = 1 / 0.340 = 2.941 requests/sec           <- flat ceiling, regardless of concurrency
W(1)  = 1 · 0.340 = 0.340 s
W(4)  = 4 · 0.340 = 1.360 s
W(8)  = 8 · 0.340 = 2.720 s
W(16) = 16· 0.340 = 5.440 s
```

At 16 concurrent callers, the *server* is doing exactly what it did at 1 caller — one 340ms forward pass at a time, `X_max` unchanged — but every individual caller now waits 5.44 seconds for a response that took 340ms of actual compute. Nothing crashed. No error was logged. The server is, by every naive health check, "up." It has simply queued 16x more work behind one door than the door can pass through, and the wait is the entire, undramatic, measurable story of "the server fell over."

**Named misconceptions**

- *"Making the route `async def` fixes the slowdown."* It does not touch the bottleneck. The event loop can interleave I/O-bound waits; it cannot make one CPU do two dense matrix multiplications simultaneously. An `async def` route that calls a blocking, compute-bound `generate()` directly (no `await`, no thread offload) is strictly worse than the synchronous version — it blocks the entire event loop, not just one worker thread, so *other* requests can't even get scheduled during that block.
- *"More `uvicorn` workers means more throughput, basically for free."* More worker *processes* each holding their own model copy genuinely does raise the throughput ceiling — because it adds more serialized resources, not because it's free. Each additional process costs its own full memory footprint (a second copy of every model weight) and its own slice of the host's actual CPU cores. "Add workers" is a real lever this module deliberately does not pull in Lessons 1–2, so that batching's effect can be measured in isolation from just buying more hardware — conflating the two is the single most common way a team over-reports what a code change bought them.
- *"A server that's still returning 200 OK under load is healthy."* The worked example returns correct, complete responses at every concurrency level in the table — and is unusable at `c = 16` by any real latency SLO. Status codes measure correctness, not capacity; this module's entire discipline is refusing to accept "it returns 200" as evidence about latency or cost.
- *"This is a small-model, CPU-only artifact of the lab — real (GPU, larger-batch) servers don't have this problem."* The *mechanism* — one finite compute resource, requests queueing linearly once demand exceeds it — is universal; only `L0` and the number of parallel resources change. A GPU server queues identically once concurrent demand exceeds what its batching and parallelism can absorb; Lesson 2 and AIE-303-M02 raise the ceiling, they do not remove it.

### Lesson 2 — Batching: what it actually buys, and what it costs someone

**Teaching text.** Lesson 1's `X_max = 1/L0` ceiling is flat because every request pays its own full fixed overhead — tokenization, padding, the Python-level dispatch into the model, memory movement — on top of its own compute. Batching's entire mechanism is amortizing that fixed cost across more than one request per call. Decompose a single request's latency into two pieces:

```
L0 = F + m
F = fixed, per-call overhead (tokenize, pad, dispatch — roughly independent of batch size)
m = marginal compute per sequence in the batch
```

A batched forward pass over `B` requests costs (approximately, on CPU) `F + B·m` total — one fixed cost, `B` marginal costs — so the batch's own throughput is:

```
X_batch(B) = B / (F + B·m)          requests/sec, for one serialized batching worker
```

As `B → ∞`, this approaches a ceiling of `1/m` — better than the unbatched `1/L0 = 1/(F+m)`, because the fixed cost `F` is being divided across more and more requests, but bounded by the marginal cost `m` you can never amortize away. **This is the honest, load-bearing distinction the folklore skips**: on a GPU, a batch of size 1 typically leaves most of the device's parallel compute lanes idle, so batching can buy a 5–10× throughput win by filling those lanes. On a CPU, there usually aren't idle parallel lanes sitting empty at batch size 1 — the marginal cost `m` is close to the true compute cost per item either way — so CPU batching's entire benefit is fixed-overhead amortization, which is real but small. Reporting a GPU-scale batching win from a CPU measurement (or vice versa) is not an exaggeration of degree, it is citing the wrong mechanism.

Batching's second, less-discussed effect is on **individual request latency**, and it is not uniformly good. A dynamic batcher accumulates requests up to `max_batch_size` or until `max_wait_ms` elapses, whichever comes first, then processes them as one call — and **every member of that batch waits for the whole batch to finish**, not just its own marginal share. The first request to arrive in a slow-filling batch pays the *full* batch latency, not its own `L0`. This produces the single most important nuance in the module: batching only helps a *saturated* server (where the alternative was standing in Lesson 1's linear queue anyway); at *low* load, where a naive server would have answered nearly instantly, a dynamic batcher can make things measurably **worse** by making a fast request wait around for a batch that isn't filling.

**Worked example.** Same reference machine, `L0 = 0.340s`, decomposed as `F = 0.060s` fixed overhead, `m = 0.280s` marginal cost per item (`F + m = 0.340` ✓, consistent with Lesson 1's baseline).

| Batch size B | X_batch(B) req/s | vs. solo (2.941 req/s) |
|---:|---:|---:|
| 1 | 2.941 | +0.0% |
| 4 | 3.390 | +15.3% |
| 8 | 3.478 | +18.3% |
| 16 | 3.524 | +19.8% |
| ∞ (ceiling, `1/m`) | 3.571 | +21.4% |

A **maximum possible** throughput gain of 21.4% on this CPU reference machine, achieved only in the limit of an infinitely large batch — and 18.3% of it is already captured at a modest batch size of 8. Compare the *latency* a member of an 8-batch pays: `F + 8·m = 0.060 + 2.24 = 2.30s` for **every** request in that batch, including the one that arrived first and, on a naive server, would have waited only `0.340s` to be served alone. At low concurrency, where batches fill slowly and mostly time out at `max_wait_ms` rather than filling to 8, a dynamic batcher's typical batch size stays small (1–3), so most of that 2.30s worst case never materializes — but it is a real, reachable number, and a team that ships a batcher tuned for peak-load throughput without checking its off-peak latency has shipped a regression for anyone using the system when it's quiet.

Converting the throughput gain to a cost number, at an illustrative $0.17/hr instance rate (substitute your own cloud's actual on-demand rate for a comparable CPU instance — the *mechanism* below is what transfers, not this specific dollar figure):

```
cost per request = hourly_rate / (3600 · throughput_req_per_sec)

naive (X=2.941 req/s):          $16.06 per million requests
batched, B=8 (X=3.478 req/s):   $13.58 per million requests   (-15.4%)
```

A real, computed, 15.4% cost reduction from batching alone — worth having, and nowhere close to the throughput story a GPU-serving blog post would tell you to expect from "just turn on batching."

**Named misconceptions**

- *"Batching always improves latency."* It improves *throughput*, always (up to the amortization ceiling). It improves *individual request latency* only when the alternative — an unbatched, saturated server — was already worse, i.e., only under real load. At low load it typically makes latency worse by making a request wait for batchmates or a timeout that a naive server wouldn't have imposed.
- *"A bigger `max_batch_size` is always better."* Throughput gain has strongly diminishing returns past a modest batch size (in the worked example, batch 8 already captures 85% of the *entire* theoretical ceiling's gain), while worst-case per-request latency keeps growing linearly with batch size for as long as you keep raising it. Past some point you are trading latency you can measure for throughput you can't collect, because nothing is arriving fast enough to fill the bigger batch anyway.
- *"CPU batching should behave like GPU batching, just slower."* The *mechanism* transfers (amortize fixed cost `F` over more items); the *magnitude* does not. A GPU has parallel compute lanes sitting idle at batch size 1 that batching fills; a CPU mostly doesn't. Expect a modest, overhead-amortization-bounded win on CPU (this module's ~20% ceiling) and a dramatic, lane-filling win on GPU (AIE-303-M02's territory) — citing one number in the other's context misrepresents what you measured.
- *"Batching and streaming compose automatically — just turn both on."* They do not, for free. A single call to a batched `generate()` (as built in this module's Lab M01-B) blocks until the **entire batch's** longest sequence finishes, so nobody in that batch sees a token before then — streaming individual tokens to N different callers out of one batched call requires a step-by-step decoding loop that yields each caller their own newest token every step (this is what production engines like vLLM and TGI call *continuous batching*), which is out of this module's scope by design. Lesson 3's streaming lab is built on Lesson 1's single-request path for exactly this reason — building the streaming mechanism cleanly first, before layering it onto the harder, batched case.

### Lesson 3 — Streaming: what it fixes, and the one thing it never touches

**Teaching text.** Everything in Lessons 1–2 optimized *when a response completes*. Streaming optimizes a different quantity entirely: **when the user sees the first useful thing**. These are not the same axis, and the gap between them is the whole lesson.

A non-streaming response returns exactly once, when generation is entirely finished. A streaming response returns incrementally — one token, or a small chunk of tokens, at a time — as soon as each one is produced, typically over **Server-Sent Events** (SSE): an HTTP response held open, with the server writing `data: <chunk>\n\n` lines as they become available and the client reading them as a stream instead of waiting for the connection to close. The key latency quantity streaming targets is **time to first token (TTFT)**: the delay between the request landing and the *first* piece of output reaching the caller — as opposed to **total completion time**, the delay until the *last* piece arrives, which is what Lessons 1–2 measured throughout.

Here is the part the folklore skips: **streaming does not reduce total completion time, total compute, or total cost.** The model still generates the same number of tokens, at the same per-token cost, taking the same total wall-clock time it always did. Streaming only resequences *when the caller is allowed to start reading* — moving the perceived wait from "nothing, then everything" to "something quickly, then a steady trickle." For a genuinely long generation this transforms the user's experience of the exact same underlying compute; for a short generation the win is proportionally smaller, because there's less total time to move perception around within.

Mechanically, HF's `generate()` is a blocking call that returns only once the entire sequence is complete — it does not natively hand back tokens as it produces them. `TextIteratorStreamer` solves this by running `generate()` on a **background thread** while the main thread iterates the streamer object, receiving each decoded piece as soon as that thread produces it; the FastAPI route then yields those pieces as SSE chunks through a `StreamingResponse`. This two-thread structure — one thread computing, one thread relaying — is the entire mechanism; nothing about the model itself changed.

**Worked example.** Same reference machine and request: `distilgpt2`, `max_new_tokens = 30`, total completion time `340ms` (Lesson 1's `L0`, unchanged — streaming does not touch this number). The forward pass over the prompt (computing the *first* output token) costs roughly the fixed overhead plus one decode step, closer to `F ≈ 60ms` than to an even per-token split; each *subsequent* token reuses cached keys/values from prior steps and is markedly cheaper, so the remaining 29 tokens split the remaining ≈`280ms` at roughly `9.7ms` each.

```
Non-streaming: caller sees nothing for 340ms, then the full 30-token response at once.
Streaming:     caller sees the first token at ≈95ms, then a steady trickle every ≈10ms
               until the same 340ms total completion.

TTFT reduction vs. total completion:  95ms / 340ms ≈ 28%
                                       -> first content ≈3.6x sooner
Total completion time:                340ms, UNCHANGED
Total compute / total cost:           UNCHANGED
```

The user's *perceived* wait dropped by more than half; the bill did not move by a single cent, and the last token still lands at exactly 340ms either way. A team that reports "streaming made the API 3.6x faster" from this number has reported a real, valuable, and completely different fact than "throughput went up" or "cost went down" — and conflating the three is the specific, common overclaim this lesson exists to prevent.

**Named misconceptions**

- *"Streaming makes the model generate faster."* It does not touch generation speed at all — same tokens, same per-token cost, same total time. It changes only when the caller is shown each piece.
- *"Streaming reduces server load or lets you serve more concurrent users."* The server still holds the same compute resource occupied for the same total duration per request; if anything, streaming a response over a long-held HTTP connection ties up a connection slot for longer than a single non-streaming round trip would, which is a real *added* resource cost some deployments have to account for, not a savings.
- *"If completion time is fine, streaming doesn't matter."* The two metrics answer different questions for different failure modes. A 340ms *total* completion is fine either way; a 3.4-second one (Lesson 1's `c = 8` queueing case) is a very different user experience streamed — seeing tokens trickle in starting at some hundreds of milliseconds — versus staring at nothing for the full 3.4 seconds. Streaming is most valuable exactly when total completion time is *not* fine and you can't fix that fact this week.
- *"Streaming is strictly an add-on you bolt onto whatever server you already have."* It composes cleanly onto a single-request path (Lesson 1's); composing it correctly onto a *batched* path (Lesson 2's) requires a fundamentally different, step-wise decoding architecture, not a wrapper — see Lesson 2's last misconception. Treating the two as interchangeably pluggable is how a team ships a "streaming" endpoint that silently blocks for the full batch duration before sending anything.

### Lesson 4 — Caching: a real hit rate, on a distribution you didn't make up

**Teaching text.** Batching and streaming both still spend full compute on every single request — a repeated question costs exactly what the first asking of it cost. Caching is the only technique in this module that makes a request's cost **disappear** rather than shrink it — but only for the fraction of traffic that actually repeats, and *that fraction is an empirical property of your real query distribution*, not a property of caches. A cache measured against uniformly random synthetic queries will show close to a 0% hit rate no matter how well it's built, and a team that benchmarks its cache that way has measured nothing about production.

Real query traffic is rarely uniform. It is usually **skewed** — a small number of queries asked very often, a long tail of queries asked once or never again — a pattern well modeled by a **Zipf distribution**: rank the distinct queries by frequency, and the probability of the query at rank `k` (out of `K` distinct queries) is:

```
p(k) = (1/k^s) / H,     where H = sum_{i=1}^{K} 1/i^s
```

`s` controls the skew — `s = 0` is uniform (no benefit from caching at all); larger `s` means a smaller number of queries dominate the traffic, and caching pays off harder and faster. This lesson's cache is deliberately the simplest possible design — an **exact-match LRU** (least-recently-used eviction, `O(1)` get/put via an ordered map) keyed on the literal prompt string — precisely so the *hit rate* you measure is attributable entirely to the traffic's real repeat structure, not to any cleverness (fuzzy matching, embedding-based "semantic" caching) that could also silently return a wrong-but-similar answer. Exact-match is the honest baseline; semantic caching is a real, further technique this module deliberately does not build, because it trades a new kind of correctness risk (a near-miss that's actually a wrong answer) for a higher hit rate, and that trade deserves its own lesson, not a footnote.

For a cache with capacity **at least as large as the number of distinct queries** that actually occur, the hit rate has a clean floor: every distinct query's *first* occurrence is a miss, and every occurrence after that is a hit —

```
hit_rate (unlimited cache) = (N - U) / N
```

— where `N` is total requests and `U` is the number of *distinct* queries that actually occurred (not necessarily the same as `K`, the number of possible queries, if the sample is small enough that some low-probability queries never show up at all). For a cache **smaller** than `U`, the achievable hit rate depends on which items LRU keeps resident, and the cumulative probability mass of the top-`C` ranks (`C` = cache capacity) is a useful upper-bound approximation — LRU will fall a little short of it in practice, because a moderately-ranked item can get evicted by a burst of a slightly-lower-ranked one before it's asked for again.

**Worked example.** `K = 50` distinct possible prompts, Zipf skew `s = 1.2`, `N = 500` total requests, seed `303` (fully reproducible — run it yourself and get exactly these numbers).

```
H = sum_{i=1}^{50} 1/i^1.2 ≈ 3.3096
p(1) = 1/1^1.2 / H ≈ 0.3022     p(2) ≈ 0.1315     p(3) ≈ 0.0808
p(4) ≈ 0.0572                   p(5) ≈ 0.0438
cumulative mass, top 10 ranks ≈ 0.7456
cumulative mass, top 20 ranks ≈ 0.8638      <- naive upper-bound estimate for a cap=20 cache
```

Measured, on the exact-match LRU built in Lab M01-C, seed `303`:

| Cache capacity | Predicted (naive formula) | Measured hit rate | Note |
|---:|---:|---:|---|
| ∞ (≥ all distinct items) | (500−50)/500 = 90.0% | **92.0%** (460/500) | Only **40** of the 50 possible prompts ever occurred in this sample (the lowest-probability tail never got asked) — 10 fewer "first-time misses" than the formula assumed, which is *why* measured beats the naive formula here, not a formula error |
| 20 | 86.4% (top-20 cumulative mass) | **81.4%** (407/500) | Real gap: LRU's recency-based eviction isn't a perfect "always keep exactly the top-20 most-frequent" oracle — a rank-21–25 item can bump a top-20 item out during a locally bursty stretch, costing a few extra misses the pure frequency-mass estimate doesn't account for |
| 10 | 74.6% (top-10 cumulative mass) | **65.4%** (327/500) | Same gap, larger at smaller capacity — less slack for LRU to absorb recency noise |

The two directions of the gap are both real and both worth naming out loud: the unlimited-cache case beat its naive formula because the formula assumed all `K` possible items would show up and fewer did; the capacity-20 and capacity-10 cases fell short of their naive formulas because LRU is a real, imperfect eviction policy, not an oracle. Neither gap is a bug — they are the two honest ways a clean theoretical estimate and a measured number diverge, and knowing which one you're looking at is the skill.

Converting to cost, at an assumed near-zero cache-hit cost (a dictionary lookup) versus the batched-server cost from Lesson 2 (`$13.58` per million requests) for every miss, at the measured 81.4% hit rate:

```
blended $/M = 0.814 · (~$0) + 0.186 · $13.58  ≈  $2.53 per million requests
```

**$2.53 per million, versus the naive server's $16.06 per million — an 84.3% reduction** achieved by a technique that never made the model itself faster or cheaper to run even once.

**Named misconceptions**

- *"Caching always helps — just add one."* A cache's hit rate is a fact about your traffic's repeat structure, not about the cache. Measured against a uniform-random query distribution (`s = 0`), this exact same LRU implementation would show a hit rate near zero — no amount of cache capacity fixes traffic that genuinely doesn't repeat.
- *"A bigger cache is always better, with no real downside."* Bigger capacity raises the achievable hit rate (with diminishing returns, per the worked table), but a larger cache costs real, ongoing memory — and past the point where capacity exceeds the number of *distinct* queries that actually occur, additional capacity buys nothing at all (the unlimited-cache row above is already the ceiling; a cache of 200 for this 50-item, 40-distinct-observed workload does no better than a cache of 40).
- *"Testing a cache on synthetic uniform-random queries is a reasonable stand-in for testing it on production traffic."* It is close to the worst possible stand-in — uniform traffic is the one distribution where caching structurally cannot help. A cache benchmark's *first* obligation is describing the query distribution it was measured against; a hit-rate number without that description is not a measured result, it's a made-up one wearing a percentage sign.
- *"Semantic (embedding-similarity) caching is strictly better than exact-match, so exact-match is just the beginner version."* Semantic caching can raise the hit rate further by matching *near*-duplicate queries, but it introduces a correctness risk exact-match structurally cannot have: returning a cached answer to a query that was similar but not identical, which can be a confidently wrong answer with no error signal anywhere in the stack. That is a real trade, not a strict upgrade, and this module builds exact-match first so the hit-rate number you measure is never confounded with a correctness question you haven't yet decided how to answer.

## Labs

Every lab's Predict step is written down, with numbers, before any code runs — per this module's Toolchain note, all four labs share `model_backend.py`, which loads `distilgpt2` once (CPU-feasible; substitutes cleanly onto a GPU by changing one `DEVICE` constant) and pins `torch.set_num_threads(1)` so the server's bottleneck is a single, clean, reproducible resource, matching Lesson 1's queueing model exactly.

```python
# model_backend.py -- shared model loading + inference for AIE-303-M01
# Loads a small, self-hostable causal LM (distilgpt2, ~82M params) once per
# process. CPU-only by default (GPU-optional: this module's numbers and code
# are unchanged if DEVICE resolves to "cuda" -- only the reference latencies
# in the worked examples will differ, faster).
import threading
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

MODEL_NAME = "distilgpt2"
DEVICE = "cuda" if torch.cuda.is_available() else "cpu"

if DEVICE == "cpu":
    # Pin to one thread: the whole point of Lesson 1's queueing model is that
    # the server has exactly one serialized compute resource. Multi-threaded
    # BLAS would blur that into "somewhere between 1 and N cores," which
    # breaks the clean W(c) = c*L0 prediction the labs are built to check.
    torch.set_num_threads(1)

_tokenizer = AutoTokenizer.from_pretrained(MODEL_NAME)
_tokenizer.pad_token = _tokenizer.eos_token
_tokenizer.padding_side = "left"  # required for correct batched causal-LM generation
_model = AutoModelForCausalLM.from_pretrained(MODEL_NAME).to(DEVICE)
_model.eval()

_lock = threading.Lock()  # serialize access to the one shared model instance

def generate_one(prompt: str, max_new_tokens: int = 30) -> str:
    """Single-request generation -- the naive Lab M01-A code path."""
    inputs = _tokenizer(prompt, return_tensors="pt").to(DEVICE)
    with _lock, torch.no_grad():
        out = _model.generate(**inputs, max_new_tokens=max_new_tokens,
                               do_sample=False, pad_token_id=_tokenizer.eos_token_id)
    return _tokenizer.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

def generate_batch(prompts: list[str], max_new_tokens: int = 30) -> list[str]:
    """True batched generation -- one padded forward pass for the whole batch."""
    inputs = _tokenizer(prompts, return_tensors="pt", padding=True).to(DEVICE)

                               do_sample=False, pad_token_id=_tokenizer.eos_token_id)
```

```python
"""Lab M01-B solution -- dynamic request batcher."""
import time
import threading
import queue
import concurrent.futures
from model_backend import generate_batch

class RequestBatcher:
    def __init__(self, max_batch_size: int = 8, max_wait_s: float = 0.05):
        self.max_batch_size = max_batch_size
        self.max_wait_s = max_wait_s
        self._queue: "queue.Queue" = queue.Queue()
        self._stop = threading.Event()
        self._thread = threading.Thread(target=self._worker_loop, daemon=True)
        self._thread.start()

    def submit(self, prompt: str, max_new_tokens: int = 30):
        fut: concurrent.futures.Future = concurrent.futures.Future()
        self._queue.put((prompt, max_new_tokens, fut))
        return fut

    def _worker_loop(self) -> None:
        while not self._stop.is_set():
            try:
                first = self._queue.get(timeout=0.1)
            except queue.Empty:
                continue
            batch = [first]
            deadline = time.monotonic() + self.max_wait_s
            while len(batch) < self.max_batch_size:
                remaining = deadline - time.monotonic()
                if remaining <= 0:
                    break
                try:
                    batch.append(self._queue.get(timeout=remaining))
                except queue.Empty:
                    break
            prompts = [item[0] for item in batch]
            max_new_tokens = batch[0][1]
            try:
                texts = generate_batch(prompts, max_new_tokens=max_new_tokens)
                for (_, _, fut), text in zip(batch, texts):
                    fut.set_result(text)
            except Exception as e:
                for (_, _, fut) in batch:
                    fut.set_exception(e)

    def shutdown(self) -> None:
        self._stop.set()
        self._thread.join(timeout=2.0)
```

```python
"""Lab M01-C solution -- SSE token streaming + exact-match LRU cache."""
import threading
from collections import OrderedDict
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from transformers import TextIteratorStreamer
import torch
from model_backend import _model, _tokenizer, DEVICE, _lock

app = FastAPI()

class GenerateRequest(BaseModel):
    prompt: str
    max_new_tokens: int = 30

def stream_tokens(prompt: str, max_new_tokens: int):
    inputs = _tokenizer(prompt, return_tensors="pt").to(DEVICE)
    streamer = TextIteratorStreamer(_tokenizer, skip_prompt=True, skip_special_tokens=True)
    gen_kwargs = dict(input_ids=inputs["input_ids"], attention_mask=inputs["attention_mask"],
                       max_new_tokens=max_new_tokens, do_sample=False,
                       pad_token_id=_tokenizer.eos_token_id, streamer=streamer)

    def _run():
        with _lock, torch.no_grad():
            _model.generate(**gen_kwargs)

    thread = threading.Thread(target=_run, daemon=True)
    thread.start()
    for piece in streamer:
        yield f"data: {piece}\n\n"
    thread.join()

@app.post("/generate_stream")
def generate_stream(req: GenerateRequest):
    return StreamingResponse(stream_tokens(req.prompt, req.max_new_tokens),
                              media_type="text/event-stream")


class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self._od: "OrderedDict" = OrderedDict()
        self.hits = 0
        self.misses = 0
        self._lock = threading.Lock()

    def get(self, key):
        with self._lock:
            if key in self._od:
                self._od.move_to_end(key)
                self.hits += 1
                return self._od[key]
            self.misses += 1
            return None

    def put(self, key, value):
        with self._lock:
            if key in self._od:
                self._od.move_to_end(key)
            self._od[key] = value
            if len(self._od) > self.capacity:
                self._od.popitem(last=False)  # evict least-recently-used

    @property
    def hit_rate(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total else 0.0
```

Solution (`lab3_zipf_workload.py`):

```python
"""Lab M01-C solution -- a realistic, skewed (not uniform) query workload."""
import numpy as np

def zipf_probs(k: int, s: float) -> np.ndarray:
    ranks = np.arange(1, k + 1)
    weights = 1.0 / ranks ** s
    return weights / weights.sum()

def sample_workload(rng: np.random.Generator, n_requests: int, n_unique: int, s: float) -> list[int]:
    probs = zipf_probs(n_unique, s)
    return rng.choice(n_unique, size=n_requests, p=probs).tolist()

def run_cache_experiment(cache, item_ids: list[int]) -> dict:
    for item_id in item_ids:
        if cache.get(item_id) is None:
            cache.put(item_id, f"<generated text for item {item_id}>")
    return {"hits": cache.hits, "misses": cache.misses, "hit_rate": cache.hit_rate}
```

```python
def generate_scenario(seed: int) -> dict:
    """Freshly parameterized serving scenario. Underscore-prefixed fields are
    withheld from the learner until grading."""
    rng = np.random.default_rng(seed)
    L0 = rng.uniform(0.15, 0.60)                    # single-request latency, s
    F_frac = rng.uniform(0.10, 0.35)                # fixed overhead as a fraction of L0
    F, m = F_frac * L0, (1 - F_frac) * L0
    K = int(rng.integers(20, 200))                   # distinct possible queries
    s_zipf = rng.uniform(0.2, 2.0)                    # skew: LOW values are deliberately
                                                       # included -- a near-uniform workload
                                                       # is a valid, gradeable scenario where
                                                       # caching is the WRONG first lever
    cache_capacity = int(rng.integers(5, K))
    hourly_rate = rng.uniform(0.10, 0.60)             # $/hr, instance cost
    sustained_concurrency = int(rng.integers(2, 40))
    budget_per_million = rng.uniform(1.0, 40.0)       # $ SLO
    p99_budget_ms = rng.uniform(300, 4000)            # latency SLO
    return {
        "L0": L0, "F": F, "m": m, "K": K, "s_zipf": s_zipf,
        "cache_capacity": cache_capacity, "hourly_rate": hourly_rate,
        "sustained_concurrency": sustained_concurrency,
        "budget_per_million": budget_per_million, "p99_budget_ms": p99_budget_ms,
    }
```

Given a generated scenario (only the non-underscored fields — none are withheld here, since the scenario itself *is* the given data, unlike AIE-204's answer-key fields), the learner must:

1. **Diagnose which lever — batching, streaming, caching, or "none of these, you need more hardware" — is the strongest first move**, from the specific numbers given, and name the one number in the scenario that drove that call (a low `s_zipf` with a small `cache_capacity/K` ratio should be diagnosed as "caching won't save you here," not defaulted to "always add a cache").
2. **Compute the predicted post-intervention numbers**: for batching, `X_batch(B)` at a stated `B` and the resulting `$/M`; for caching, the top-`cache_capacity` cumulative Zipf mass as the hit-rate ceiling and the resulting blended `$/M`; for the naive baseline, `W(sustained_concurrency) = c·L0` against `p99_budget_ms`.
3. **State whether the stated budget and SLO are met, barely met, or still missed**, with the margin in both dollars and milliseconds — not a yes/no.
4. **Propose the next lever**, if still missing budget after the first move, and predict its effect using the same formulas, not a restatement of "add more caching."

**Gaming resistance.** Parameters are freshly drawn per attempt, so memorizing this module's own worked-example constants (`$16.06`, `81.4%`, `2.941 req/s`) does not transfer — the learner must re-apply the formulas to numbers they've never seen. More importantly, **step 1's diagnosis is graded before, and independently of, step 2's computation**: a technically flawless caching hit-rate calculation performed on a low-skew (`s_zipf ≈ 0.2`) scenario, where caching was never going to be the right first lever, scores low on Diagnose regardless of how correct the arithmetic in Compute is — this closes the obvious gaming strategy of pattern-matching "serving clinic → talk about caching" without reading the specific numbers given.

## Three-tier reading

Specific to this module's subject — the arithmetic of making a request cheap and fast, and what that arithmetic never puts a number on.

- **Tier 1 — material ground.** The pattern behind "most ML failure in the wild is systems failure, not model failure" is well documented in the field's own canonical accounts of production ML (Sculley et al., "Hidden Technical Debt in Machine Learning Systems," NeurIPS 2015, is the standard citation), and this module gives you your own, reproducible instance of exactly that pattern: every number in Lab M01-A's collapse, Lab M01-B's throughput/latency trade, and Lab M01-C's hit-rate table comes from code you ran, not a model that got worse. The model in every lab of this module was identical, correct, and unchanged from Lesson 1 to Lesson 4 — every failure and every fix was a serving decision, never a modeling one.
- **Tier 2 — what a clean p99 dashboard suppresses.** This module trains you to measure throughput, latency, and cost exhaustively — and every one of those numbers is a property of the *system*, not of the people waiting on it. A p99 latency figure tells you how the slowest 1% of requests performed; it says nothing about **who** tends to land in that slowest 1%. Lesson 4's cache makes this concrete and structural, not hypothetical: an LRU cache, by construction, gives near-zero-cost, near-instant service to whichever queries are already common, and gives full, uncached latency and full cost to whichever queries are rare — every single time, forever, for as long as they stay rare. A system optimized on this module's own metrics (hit rate, `$/request`, p99) can hit every target on the dashboard while the users whose questions don't repeat pay the system's full, un-amortized cost on every single interaction, and nothing in a hit-rate percentage or a cost-per-million-requests number distinguishes "we're fast and cheap" from "we're fast and cheap for the common case and we never measured the rest."
- **Tier 3 — sit with this.** A cache doesn't just observe which queries repeat — once a product team is watching a `$/request` or a latency dashboard (and after this module, you will be, because the syllabus grades you on exactly that number), there is a real, ordinary, unremarkable pressure to make more traffic look like the traffic that's already fast and cheap: canned suggestion buttons, autocomplete toward common phrasings, FAQ prompts surfaced ahead of an open text box — each one a small, reasonable, individually-defensible product decision, and each one also, structurally, a decision that nudges the query distribution *toward* what the cache already serves well, which then improves the very hit-rate number that justified the nudge in the first place. Your model didn't get better at answering rare questions. Your users got quietly steered toward asking common ones, and the dashboard reported that as success, because "success," on this module's own metrics, is a number computed from the distribution *after* the nudging, not before. When your `$/request` figure is the thing that gets reviewed every week, and the query distribution that number depends on starts moving in the direction that flatters it — what would you have to go measure, that this module never asked you to measure, to find out whether your system adapted to your users, or your users adapted to your system?
