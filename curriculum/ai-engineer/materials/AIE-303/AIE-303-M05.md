## Lessons

### Lesson 1 — Tracing: turning "it responded in 2 seconds" into four numbers you can act on

**Teaching text.** A **log** is a timestamped fact about one moment ("retrieval returned 5 chunks"). A **metric** is a number aggregated over many requests ("p99 latency: 2.1s"). A **trace** is neither — it is the *causal, timed path one specific request took through your system*, stage by stage, with each stage's start, end, and the stages nested inside it. AIE-303-M01 and M02 gave you end-to-end latency numbers for a request; this lesson builds the thing that tells you *which stage* of that request ate the time, for any single request you want to inspect after the fact, not just the ones you happened to be watching live.

The unit of a trace is a **span**: a named, timed interval, tagged with the **trace ID** it belongs to (every span from one request shares one trace ID) and a **parent span ID** (which span it's nested inside — retrieval and generation both nest inside the outer "request" span; nothing nests inside them). Four fields make a span useful for debugging later, and all four are cheap to record: `name`, `trace_id`, `duration_ms`, `parent_span_id`. A trace of one request is just every span that shares its trace ID, reconstructable into a nested timeline from the parent links alone — this is the same tree structure a debugger's call stack shows you, except it survived past the moment the request finished, because you wrote it down.

**Worked example.** A traced RAG request: `request` (root span) contains `retrieval` and `generation` and `response`, each a child span with `parent_span_id` set to `request`'s span ID:

```
request       [======================================================]  353.0 ms
  retrieval   [==]                                                       12.4 ms
  generation  [    ================================================]   339.8 ms
  response    [                                                     ==]   0.8 ms
```

(Illustrative figures — a CPU-served small model's generation stage dominates end-to-end latency this heavily in practice; your own Lab A run will print real measured numbers to replace these with.) Generation is ~96% of the request here — not a surprise once you recall AIE-303-M02's prefill/decode split: retrieval is one fast lookup, generation is a serialized loop of forward passes. The value of the trace is not that number alone (a metrics dashboard could show you *an average* generation-stage duration too) — it's that this exact breakdown exists **per request**, so when one specific request's latency blew an SLO, you don't need to guess which stage did it; you read that request's four span rows.

Every span this module logs is one JSON object, one per line (JSON Lines / JSONL) — a format chosen on purpose: it's streamable (append one line as each span closes, never rewrite the file), greppable with plain text tools, and one malformed line doesn't corrupt the rest of the log the way one bad row can corrupt a CSV or a single giant JSON array. A single traced request in this module's harness produces 4 spans at roughly 200 bytes of JSON each — about 800 bytes/request. At a modest 100,000 requests/day that is **~80 MB/day of trace log** — small compared to a mid-sized production system's genuine log volume, but the number is worth computing once by hand, because "just log everything" stops being free arithmetic exactly where the field usually pretends it's still free: at scale, with retention, with more than 4 spans per request.

**Named misconceptions**

- *"`print()` statements are observability."* A print statement has no trace ID, no parent, no structured duration — it cannot be correlated across concurrent requests (two requests interleaving their prints on a busy server are indistinguishable in the output) and it cannot be queried later ("show me every request where retrieval took over 100ms" is a one-line query against structured JSONL and not a feasible `grep` against free-text prints). Observability requires structure captured *at write time*; you cannot retroactively structure a print statement.
- *"Total request latency is just the sum of the stage latencies, so I only need to time the whole request."* True only when stages run strictly sequentially with nothing else in flight, which this module's harness does — but the moment a system adds retries, streaming, or concurrent sub-calls (an agent loop firing two tool calls in parallel), the sum-of-parts breaks and only per-span timing tells you the truth. Building the habit of per-stage timing now is what makes those later systems debuggable instead of mysterious.
- *"One global timer around the whole endpoint is enough — I can see if the request was slow."* It tells you *that* a request was slow, never *which stage*. A traced system and an untraced-but-timed system report the identical 2.1-second total; only the traced one tells you whether that 2.1 seconds was 2.0 seconds of generation (a model problem) or 1.8 seconds of retrieval (an index problem) — two completely different fixes that look identical from outside the span.

### Lesson 2 — What a dashboard's aggregate can't show you: subgroup dilution

**Teaching text.** A dashboard's headline number is almost always a single statistic computed over the *whole* traffic stream: mean latency, mean satisfaction, mean retrieval similarity. That single number is mathematically a weighted average across every request type your system serves — and a weighted average has a structural property every observability practitioner needs to internalize before touching a drift detector: **a large regression in a minority subgroup can move the global average by only a small amount, even though the subgroup itself is in genuine crisis.** This isn't a measurement failure; it's arithmetic. If 25% of your traffic craters and the other 75% is unaffected, the global mean moves by roughly 25% of the size of the crater — visible if you're looking closely, easy to miss if your alert threshold was tuned for "the whole system is degrading," which is a different, louder failure mode than "one quarter of the system quietly broke."

This is the same shape of problem that a metrics-only dashboard has with tail latency: a p50 that looks fine can coexist with a p99 in flames, because p50 by construction doesn't see the tail. Subgroup dilution is the categorical version of the same trap — instead of a distribution's tail being invisible to its median, a category's failure is invisible to the population's mean, unless someone builds the slice.

**Worked example.** A support system serves four query categories evenly. Suppose the aggregate "retrieval relevance" metric a dashboard tracks is the mean similarity score across all traffic:

| Category | Share of traffic | Similarity before | Similarity after an incident |
|---|---|---|---|
| billing | 25% | 0.88 | 0.51 |
| shipping | 25% | 0.88 | 0.88 |
| account | 25% | 0.89 | 0.89 |
| product | 25% | 0.89 | 0.89 |
| **Global mean (what the dashboard shows)** | 100% | **0.885** | **0.793** |

The global mean drops from 0.885 to 0.793 — an 11% relative decline, real and not invisible to a *careful* reader. But run the *standard statistical test for exactly this question* — the Population Stability Index (PSI), Lesson 3's subject — over the same before/after split, and the global-level PSI comes out to **0.093**, which sits *below* the conventional "no meaningful shift" threshold of 0.1. Meanwhile the same test run on the billing category alone comes out to **0.391** — comfortably past the "significant shift" threshold of 0.25, while the other three categories (shipping, account, product) each stay under 0.06, safely inside "no shift." A monitoring setup that alerts on global PSI crossing 0.1 — a reasonable, textbook-correct threshold — **does not fire** while billing is in the middle of an outright collapse. (These are not hypothetical numbers — they're the exact measured output of Lab M05-B's detector on this module's own transcript stream, which plants precisely this failure. You'll reproduce them yourself.)

The lesson is not "PSI is broken" — PSI did exactly what it was asked to do, correctly, on the population it was given. The lesson is that **the population it was given was the wrong population to ask the question about.** A metric computed over the whole traffic stream answers "did the whole stream shift" — a real question, but not the one that matters when the failure is concentrated in a slice. The fix is not a better global statistic; there isn't one. It's slicing before you aggregate: category, cohort, time window, whatever dimension the failure might hide inside.

**Named misconceptions**

- *"If the dashboard's headline metric hasn't moved past its alert threshold, nothing is seriously wrong."* Shown false above: a global PSI of 0.093 (comfortably "no shift") coexists with a category-level PSI of 0.391 (well past "significant"). The headline metric answered a real question correctly — just not the question "is any part of my system broken."
- *"I should just add more global metrics — latency, satisfaction, error rate — to catch what one metric misses."* More *global* metrics dilute the same way; a second averaged number still averages over the same masking subgroup. What catches subgroup failure is *slicing an existing metric* by a meaningful dimension (category, cohort, model version, time), not accumulating more unsliced ones.
- *"Averages are the honest, unbiased summary — slicing is where you go looking for problems that aren't really there (p-hacking your own dashboard)."* Slicing by a dimension that's meaningful to the system's actual failure modes (query type, user cohort, retrieval source) is not fishing for noise — it's testing a specific, motivated hypothesis about where a failure could concentrate. The dishonest version is slicing by hundreds of arbitrary dimensions until one crosses a threshold by chance; slicing by category because your system is a RAG system whose retrieval quality plausibly varies by document freshness *per category* is exactly the disciplined use of the technique.

### Lesson 3 — Drift: from "state a metric moved" to "prove a distribution shifted, and where"

**Teaching text.** **Drift** is a change over time in the statistical distribution of something your system depends on or produces. **Data drift** (also called covariate shift) is a change in the *inputs* — the kinds of questions users ask, the documents retrieval returns, the length of a typical prompt. **Concept drift** is a change in the *relationship* the model is supposed to have learned — the same input now deserves a different answer (a policy changed; a price changed). This module's planted failure is data drift on the retrieval side: the *documents* retrieval returns for one category silently degrade, while the underlying question users ask does not change at all.

"The metric moved" is not the same claim as "a distribution shifted," and conflating them is the single most common drift-detection mistake. A metric — a mean, a rate — is one number; a shift in that number could come from a genuine distributional change, or from ordinary sampling noise, or (as Lesson 2 showed) from a real shift buried under an unaffected majority. The **Population Stability Index (PSI)** is a standard way to make the distinction rigorous instead of eyeballed: it bins a numeric metric's values, compares the *proportion* of a baseline sample falling in each bin against the proportion of a current sample falling in each bin, and sums a divergence term per bin:

```
PSI = Σ_bins (current_pct - baseline_pct) × ln(current_pct / baseline_pct)
```

Conventional reading (industry-standard, not this course's invention): **PSI < 0.10** — no meaningful shift; **0.10 ≤ PSI < 0.25** — moderate shift, worth watching; **PSI ≥ 0.25** — significant shift, worth acting on. PSI is symmetric in what it can catch (a distribution that moved but kept the same mean — say, it got bimodal — still shows up, because PSI compares the whole shape bin by bin, not just the average) and it is *not* a hypothesis test with a p-value; it is a magnitude, and the thresholds above are a convention, not a law of statistics — Lesson 3's own misconceptions cover exactly the trap of forgetting that.

The bare formula above has a sharp edge Lesson 2's slicing advice runs straight into: once you slice by category, each slice's sample is much smaller than the whole stream's, and a bin with only a handful of points in it can swing its percentage — and therefore the log-ratio — by a lot from ordinary sampling luck, with no real shift behind it at all. Lab M05-B's detector guards against exactly this by adding a small pseudo-count to every bin's raw count before computing percentages (a standard smoothing technique, the same idea as Laplace smoothing) — large enough to absorb a few points' worth of small-sample noise, small enough to leave a genuine, large shift (like billing's) untouched. Skipping that guard is what turns "slice before you aggregate" from Lesson 2's fix into a new failure mode: a false alarm on a category that never actually drifted, purely because its slice was small.

**Worked example (hand-computed).** Five bins, baseline evenly spread (20% per bin), current sample shifted so 60% now falls in the top bin instead of 20%:

```
baseline_pct = [0.20, 0.20, 0.20, 0.20, 0.20]
current_pct  = [0.10, 0.10, 0.10, 0.10, 0.60]

bin 1-4 each: (0.10 - 0.20) × ln(0.10/0.20) = (-0.10) × (-0.693) = 0.0693  →  ×4 = 0.2772
bin 5:        (0.60 - 0.20) × ln(0.60/0.20) = ( 0.40) × ( 1.099) = 0.4394

PSI = 0.2772 + 0.4394 = 0.7166
```

0.7166 is well past the 0.25 "significant shift" line — correctly, since 60% of the mass relocating into one bin is a dramatic reshaping of the distribution. Compare this by-hand arithmetic against Lesson 2's *real* numbers from Lab M05-B's detector: global-level PSI of **0.093** (no shift, correctly computed, on the wrong population) versus billing-category PSI of **0.391** (most of the current-window billing distribution has relocated well outside the baseline's observed range, into the edge bins the smoothing-adjusted formula still resolves clearly). Both numbers came from the identical formula; the difference is entirely which population went in. The other three categories — shipping (0.047), account (0.059), product (0.011) — all land safely under 0.10, exactly where Lesson 2's narrative says an unaffected category should sit; that this holds for account specifically (not just shipping and product) is Lab M05-B's small-sample smoothing guard doing its job, not a coincidence.

**Named misconceptions**

- *"A PSI (or any drift statistic) crossing its threshold proves the system's output quality got worse."* PSI measures a shift in an *input or intermediate* distribution (here, retrieval similarity scores) — it is evidence something changed upstream, not direct proof the final answers got worse. Confirming that requires checking an output-side signal too (Lab M05-C's relevance judgment, or better, your AIE-204 eval harness rerun on current traffic) — drift detection tells you *where to look*, not *what you'll find*.
- *"A small p-value (or a PSI safely under 0.10) from a global test means there's no drift anywhere in the system."* Lesson 2's whole point: a correctly-computed global statistic can be technically correct and practically blind, because it answers a question about the whole population, not about any one slice of it. Statistical correctness of the test and completeness of the population it was run on are two separate questions — this module fails a submission that only answers the first.
- *"A category's PSI crossing the threshold always means that category actually drifted."* Not if the slice is small. Slicing by category (Lesson 2's fix for dilution) shrinks each slice's sample size, and PSI computed on a small sample without a small-sample guard is itself noisy enough to cross 0.10 or even 0.25 on a category with **zero** real drift — the exact same arithmetic problem Lesson 2 taught you to watch for, just moved one level down, from "the global statistic is blind to the slice" to "the sliced statistic is unreliable at small n." A detector has to guard against both, or slicing trades one blind spot for a noisier one.
- *"Detecting drift means retraining or redeploying the model."* This module's planted drift is a *retrieval index* problem — nothing about the language model is wrong. The fix for the failure Lab M05-B finds is "the billing document index needs re-indexing after a migration," not "the model needs retraining." Drift's *cause* determines its fix, and finding the cause is the transcript-reading skill Lesson 4 builds — a detector alone tells you *that* and roughly *where*, never *why*.

### Lesson 4 — Reading transcripts as a skill: stratified sampling, hypothesis, confirmation

**Teaching text.** A drift detector (Lesson 3) tells you a distribution shifted and roughly which slice it shifted in. It does not tell you *why*, and it cannot, because "why" lives in the actual content of the requests — the specific question asked, the specific document retrieved, whether that document has anything to do with the question at all. Getting from "billing's retrieval similarity collapsed" to "the billing document index went stale after a migration and started serving a boilerplate fallback chunk" requires reading actual transcripts, and reading transcripts well is a skill with a structure, not a vague activity of "looking at some examples."

**The protocol this module teaches has three deliberate steps, in order.** (1) **Stratify before you sample.** Uniform random sampling over the *whole* traffic stream, at this module's numbers, draws roughly 25% billing traffic — and two-thirds of the *whole stream* is pre-drift, since the drift window is only the back third. A naive random sample of 20 transcripts would expect well under 10 affected billing transcripts, often fewer, sometimes zero — easy to read straight past. Stratifying by category and restricting to the window a detector already flagged as suspect (Lesson 3's job) turns a diluted 8%-of-traffic needle into a guaranteed, dense 25%-of-sample block you cannot miss. (2) **Form a hypothesis you can state as a sentence before you read the confirming evidence**, not after — "I expect billing's retrieved chunks in the current window to be topically unrelated to the question asked" is falsifiable and specific; "something seems off with billing" is neither. (3) **Confirm or kill the hypothesis against a count, not a vibe** — read every sampled transcript's question against its retrieved chunk, tag each pair relevant/irrelevant, and report the *rate*, the same discipline Lesson 2 demanded of a dashboard metric, just computed by a human eye on 20 examples instead of a formula on 100,000.

**Worked example.** Two transcripts a stratified sample from the current window would surface, read the way a human reads them — not as a dashboard row, as a small paragraph:

```
[ 214] category=billing
  Q: When is my invoice generated?
  retrieved: Billing questions are handled by our support team during business hours.
  A: [model's answer, built from an irrelevant chunk]
  retrieval_similarity=0.487

[ 221] category=shipping
  Q: How long does shipping take?
  retrieved: Standard shipping takes 3-5 business days; expedited shipping takes 1-2 business days.
  A: [model's answer, built from the right chunk]
  retrieval_similarity=0.901
```

The second transcript needs no judgment call — the retrieved chunk directly answers the question. The first is the pattern: the retrieved chunk is a real, well-formed, grammatically fluent sentence about billing — it is simply not an answer to *this* question. This is the specific, dangerous shape of RAG failure a satisfaction-score dashboard is worst at catching: the generated answer built on top of an irrelevant chunk can still *read* fluent and confident, because the language model's fluency is undamaged — only its grounding is. A user who doesn't already know the correct invoice date has no signal in the answer's tone that it's ungrounded. Reading the *retrieved chunk against the question*, not the final answer's tone, is what catches it — the transcript-level check Lab M05-C builds.

**Named misconceptions**

- *"Reading a handful of transcripts is anecdotal, so it's weaker evidence than a dashboard number."* A dashboard number computed over the wrong population (Lesson 2) is not stronger evidence than a correctly stratified sample of 20 read carefully — it's *differently* weak. The fix isn't choosing metrics over transcripts or transcripts over metrics; it's using drift detection to find where to look and stratified reading to find out what's actually there, each covering the other's blind spot.
- *"If the model's answer sounds confident and coherent, the underlying retrieval must have worked."* This is precisely backwards for the failure this module plants, and it's the reason RAG failures are more dangerous than a model just refusing — a small model handed an irrelevant-but-fluent-sounding chunk very often produces an equally fluent, equally confident, and simply wrong answer. Fluency is evidence about the language model's competence, not about the retrieved context's relevance; those are two different things to check, using two different pieces of the transcript.
- *"Once I've read enough transcripts to be confident of a pattern, I'm done — no need to also report a rate."* A hypothesis confirmed by feel on however many examples happened to be memorable is exactly the failure mode Lesson 2 spent a whole lesson on, just moved from dashboards to human reading. The protocol's third step — tag every sampled transcript, report the rate — exists so "I read some and it seemed bad" becomes "18 of 20 stratified samples in the flagged window and category showed an irrelevant retrieved chunk; 0 of 20 in the unaffected categories did," a claim someone else can check.

import json
import uuid
import contextlib
from dataclasses import dataclass, field


@dataclass
class Span:
    name: str
    trace_id: str
    span_id: str
    parent_span_id: str | None
    start_wall: float
    start_perf: float
    end_perf: float | None = None
    attributes: dict = field(default_factory=dict)

    @property
    def duration_ms(self) -> float:
        """Milliseconds elapsed between this span's start and end. Must
        raise ValueError if the span was never closed (end_perf is None)."""
        if self.end_perf is None:
            raise ValueError(f"span {self.name!r} was never closed")
        return (self.end_perf - self.start_perf) * 1000.0

    def to_dict(self) -> dict:
        return {
            "trace_id": self.trace_id,
            "span_id": self.span_id,
            "parent_span_id": self.parent_span_id,
            "name": self.name,
            "start_wall": self.start_wall,
            "duration_ms": self.duration_ms,
            "attributes": self.attributes,

    as one JSON-lines record per span to a log file."""

        self._spans: list[Span] = []
        self._stack: list[Span] = []  # open spans, for parent tracking

        with tracer.span("response", trace_id):
            response = {"query": query, "chunk": chunk, "answer": answer}
    return response

# solution: drift_detection.py (completed)
import json
import math
import statistics


def load_transcripts(path: str) -> list[dict]:
    with open(path) as f:
        return [json.loads(line) for line in f]


def psi(baseline: list[float], current: list[float], n_bins: int = 5, smoothing: float = 8.0) -> float:
    lo, hi = min(baseline), max(baseline)
    if lo == hi:
        return 0.0
    width = (hi - lo) / n_bins
    top_edge = hi + 1e-9

    def bin_counts(values):
        counts = [0] * n_bins
        for v in values:
            v = min(max(v, lo), top_edge - 1e-12)
            idx = min(int((v - lo) / width), n_bins - 1)
            counts[idx] += 1
        return counts

    base_counts = bin_counts(baseline)
    cur_counts = bin_counts(current)
    base_total = len(baseline) + smoothing * n_bins
    cur_total = len(current) + smoothing * n_bins
    total = 0.0
    for b, c in zip(base_counts, cur_counts):
        base_pct = (b + smoothing) / base_total
        cur_pct = (c + smoothing) / cur_total
        total += (cur_pct - base_pct) * math.log(cur_pct / base_pct)
    return total


def global_metric_shift(records: list[dict], baseline_end: int, metric: str = "retrieval_similarity") -> dict:
    baseline = [r[metric] for r in records if r["request_id"] < baseline_end]
    current = [r[metric] for r in records if r["request_id"] >= baseline_end]
    return {
        "baseline_mean": statistics.mean(baseline),
        "current_mean": statistics.mean(current),
        "psi": psi(baseline, current),
    }


def per_category_metric_shift(records: list[dict], baseline_end: int, metric: str = "retrieval_similarity") -> dict:
    categories = sorted(set(r["category"] for r in records))
    result = {}
    for cat in categories:
        baseline = [r[metric] for r in records if r["category"] == cat and r["request_id"] < baseline_end]
        current = [r[metric] for r in records if r["category"] == cat and r["request_id"] >= baseline_end]
        if not baseline or not current:
            continue
        result[cat] = {
            "baseline_mean": statistics.mean(baseline),
            "current_mean": statistics.mean(current),
            "psi": psi(baseline, current),
        }
    return result


def find_drift_onset(records: list[dict], category: str, metric: str, window: int = 20, threshold: float = 0.55):
    cat_records = sorted([r for r in records if r["category"] == category], key=lambda r: r["request_id"])
    values = [r[metric] for r in cat_records]
    ids = [r["request_id"] for r in cat_records]
    for start in range(0, len(values) - window + 1):
        window_vals = values[start:start + window]
        if statistics.mean(window_vals) < threshold:
            return ids[start]
    return None

    "billing": "Your invoice is generated on the 1st of each month and reflects your current plan tier.",
    "shipping": "Standard shipping takes 3-5 business days; expedited shipping takes 1-2 business days.",
    "account": "You can reset your password from the account settings page under Security.",
    "product": "The Pro plan includes unlimited projects and priority support.",
}


def stratified_sample(records: list[dict], per_category: int, min_request_id: int, seed: int = 0) -> list[dict]:
    rng = random.Random(seed)
    categories = sorted(set(r["category"] for r in records))
    sample = []
    for cat in categories:
        pool = [r for r in records if r["category"] == cat and r["request_id"] >= min_request_id]
        sample.extend(rng.sample(pool, min(per_category, len(pool))))
    return sample


def format_transcript(record: dict) -> str:
    return (
        f"[{record['request_id']:>4}] category={record['category']}\n"
        f"  Q: {record['question']}\n"
        f"  retrieved: {record['retrieved_chunk']}\n"
        f"  A: {record['answer']}\n"
        f"  retrieval_similarity={record['retrieval_similarity']}"
    )


def judge_relevance(record: dict) -> bool:
    return record["retrieved_chunk"] == CANONICAL_GOOD_CHUNK[record["category"]]


def category_relevance_rate(records: list[dict]) -> dict:
    categories = sorted(set(r["category"] for r in records))
    result = {}
    for cat in categories:
        cat_records = [r for r in records if r["category"] == cat]
        if not cat_records:
            continue
        relevant = sum(judge_relevance(r) for r in cat_records)
        result[cat] = relevant / len(cat_records)
    return result


if __name__ == "__main__":
    from drift_detection import load_transcripts

    records = load_transcripts("transcripts.jsonl")
    sample = stratified_sample(records, per_category=5, min_request_id=200, seed=1)

    print(f"stratified sample: {len(sample)} transcripts (5 per category, request_id >= 200)\n")
    for r in sample:
        print(format_transcript(r))
        print()

    print("--- category relevance rate on the FULL current window (not just the sample) ---")
    current = [r for r in records if r["request_id"] >= 200]
    for cat, rate in category_relevance_rate(current).items():
        print(f"{cat:10s} relevance_rate={rate:.2f}")

## Three-tier reading

Specific to this module's subject — what tracing and drift detection can prove, and what they can't.

- **Tier 1 — material ground.** A trace's per-span timings and a drift detector's PSI are both measurable, reproducible, and auditable exactly the way this module's labs required: run the same transcript stream through the same detector twice, get the same number. The Population Stability Index is a standard, widely-used industry technique with published conventional thresholds (<0.10, 0.10-0.25, ≥0.25) — nothing about the statistic itself is in dispute, and a skeptical reader can recompute every number in this module's labs from the raw transcripts.
- **Tier 2 — what the field suppresses.** A dashboard that reports "no significant drift" is reporting a true, correctly-computed fact about the population it was given — and the choice of *which population* to compute it over is a design decision made once, early, usually by whoever built the dashboard, and rarely revisited. This module's own worked numbers make the suppression concrete: a global PSI of 0.093 and a billing-category PSI of 0.391 are both honest outputs of the identical formula. The dashboard that only computes the first number isn't lying — it's answering a question nobody thought to ask differently, and the gap between "no drift" and "one quarter of the system is in collapse" is not a bug in the statistic, it's a scope decision nobody flagged as a decision. Most production monitoring stacks report the population-level number by default, because it's cheaper to compute once than to maintain a slice for every dimension that might someday matter, and that cost tradeoff, not malice, is why subgroup failures survive so long before anyone reads a transcript.
- **Tier 3 — sit with this.** The categories, cohorts, or query types most likely to fall into a diluted, dashboard-invisible subgroup are, structurally, the ones that are already a *minority* of your traffic — the less common question, the smaller customer segment, the query shape your system was tuned on the least. Lesson 2's arithmetic is symmetric: it doesn't care *which* 25% collapses, only that it's a minority large enough to matter and small enough to hide. But in a real production system, which slice of your users is most often the smaller, less-tuned-for slice is rarely random — it correlates with exactly the users a system was built with the least data about, the least testing against, the least attention paid to in the first place. A monitoring setup built entirely from global aggregates will, on average, take the longest to notice a regression in precisely the group of users it was already serving worst — and every dashboard involved will have been telling the truth the whole time. What would it take to build a monitoring practice where the *default* slice — the one nobody has to remember to add — is the one most likely to contain the failure nobody's watching for, instead of the one that's cheapest to compute?
