# AIE-303-M07 — Self-hosting and sovereignty: local inference economics

**Course:** AIE-303 — Production AI: Serving, Inference, and Operations · **Tier:** specialization · **Durability:** mixed
**Hours:** 10 · **Sits in the descent:** the last drop, and the re-ascent. Every technique this course built — serving (M01), quantization and the KV-cache byte budget (M02), the $/request cost model (M03), the eval-gated deploy and rehearsed rollback (M04), tracing and drift (M05), the incident drill (M06) — gets applied one more time, in full, to a system the learner owns end to end: their own box, their own patches, their own 2am page.
**Prereq:** AIE-303-M01 (a serving path and a hand-rolled load harness exist), AIE-303-M02 (your own measured latency numbers and the KV-cache byte formula — `2 × n_layers × n_heads × head_dim × dtype_bytes` per token), AIE-303-M03 (the $/request formula, and specifically its self-hosted/API breakeven calculation — this module goes back and corrects what that calculation left out), AIE-303-M04 (an eval gate that blocks a bad deploy, and a rollback you have personally rehearsed), AIE-303-M05 (a trace format cheap enough to log on a box you're paying for), AIE-303-M06 (the incident drill — this module's Lab C is that drill, run against hardware with no vendor SLA behind it). This module does not re-teach any of those six skills. It spends all six on one deployment you actually stand up.

> Folklore version of this module: "self-host it — no per-token markup, your data never leaves your servers, you're sovereign." Every clause of that sentence is either true and incomplete, or true and misleadingly framed as free. This module makes you build the number folklore skips: the *true* fixed cost of a box you own — not a box you rent by the hour, which AIE-303-M03 already showed is a different, cheaper thing than genuine sovereignty — and the volume at which that true cost actually beats an API, computed from your own measured hardware ceiling, not asserted from a slogan.

## Lessons

### Lesson 1 — Sovereignty is a property list, not a slogan

**Teaching text.** "Self-hosting" is used to mean at least three different things, and this course has already built two of them without calling either one "sovereign." AIE-303-M01's FastAPI server running on your laptop is self-hosted. AIE-303-M03's breakeven calculation used a *rented* cloud vCPU at `$0.048/hour` — also self-hosted, in the sense that you, not a model-API vendor, ran the inference — but that box is still someone else's hardware, someone else's hypervisor, someone else's kernel patches, in someone else's data center, billed by someone else's meter. What this module means by **sovereignty** is a third, stricter thing: hardware you or your organization physically possess, where a specific, nameable list of properties becomes true that is not true of either of the first two:

| Property | Rented API | Rented cloud VM (M03's "self-hosted") | Owned hardware (this module) |
|---|---|---|---|
| Data leaves your network at request time | Yes | Depends on VPC config | No |
| Vendor can deprecate/change the model under you | Yes | No (you control the weights) | No |
| Vendor can rate-limit or throttle you | Yes | Sometimes (shared tenancy) | No |
| Vendor patches the OS/kernel for you | N/A | Yes | **No — you do** |
| Vendor's SRE team pages for hardware failure | N/A | Yes | **No — you do** |
| Fixed cost if traffic is zero | \$0 | Yes (billed 24/7 if always-on) | Yes, **plus the hardware you bought is a sunk cost** |

The first three rows are the genuine, real properties sovereignty marketing is correct about — this module does not dispute them, and for some organizations (a regulated data-residency requirement, a contractual no-third-party-processor clause) they are non-negotiable and end the analysis on their own. The bottom three rows are what the slogan quietly transfers onto you, and they are exactly the properties this course spent AIE-303-M04, M05, and M06 building skill at owning *for a vendor's box*. This module's claim is narrow and falsifiable: sovereignty is real, and it has a price, and the price is not the compute rental M03 priced — it is the compute rental **plus** every one of those bottom-row rows, each converted to a dollar figure, because a dollar figure is the only form of that price a budget can be defended with.

**Worked example.** A learner asked to cost "self-hosting" for a stakeholder, using only M03's formula, reports the $34.56/month rented-vCPU figure from that module's Lesson 4 worked example (`$0.048/hour × 24 × 30`) as "the cost of self-hosting." That number is real and correctly computed — for what it measured. It is not the cost of sovereignty as defined in the table above: it has no capital cost (the rented box isn't owned), no electricity line (the cloud vendor's data center pays that and bakes it into the rental rate), and critically, **no labor** — the rented box's kernel is patched by someone whose salary is also baked into that rate. Lesson 3 builds the corrected number and shows exactly how large the gap is.

**Named misconceptions**

- *"Self-hosting and renting a cloud VM are the same thing, cost-wise."* They share a serving stack (this module reuses M01's exact FastAPI server) but differ in every row of the table above except the top three. AIE-303-M03's "self-hosted vs. API" breakeven used the rental number, which is real, but it answers "when does renting compute beat renting tokens," not "when does owning hardware beat renting tokens" — a materially different, and materially larger, question.
- *"If I'm not violating the first three rows, I'm not really giving anything up by not owning hardware."* True for some organizations and false for others — a regulated data-residency clause makes rows 1–3 the whole decision, full stop, no cost model needed. This module is for the case where the decision genuinely is economic, which is a real and common case, not a strawman — but naming which case you're in, explicitly, before building a cost model, is the first thing a defensible analysis does.
- *"Sovereignty is free once you've bought the hardware — the marginal cost per request is basically zero."* The *marginal* compute cost per request is genuinely near zero, same as any self-hosted box past its fixed cost. The *fixed* cost is not zero, and — this is Lesson 3's central number — it is dominated by a line item that has nothing to do with hardware at all.

### Lesson 2 — Standing up local inference for real: the same server, a real hardware ceiling

**Teaching text.** Sovereignty's technical half is unglamorous by design: it is AIE-303-M01's exact FastAPI server (`/generate`, a `GenerateRequest`/`GenerateResponse` pair, `model_backend.generate_one`), pointed at a model that lives on disk you control instead of an API endpoint you call. Nothing about the serving code changes. What changes is that there is no vendor absorbing the question "how much load can this thing actually take before it falls over" — that question, which AIE-303-M01 answered once, abstractly, for a shared cloud box, now has to be answered concretely, for the specific box sovereignty puts the model on, because nobody else is going to answer it for you.

Two numbers bound that box, and both are computable *before* you run anything, from work this course already did:

**Memory.** A loaded model costs, at minimum, its weight tensors in RAM: `n_params × dtype_bytes`, plus a real, nonzero framework overhead (Python interpreter, PyTorch's own allocator, FastAPI/uvicorn) that does not show up in any parameter count and has to be measured, not assumed — this module treats it as a stated constant to be calibrated against your own machine, exactly the way AIE-303-M01 treated `L0` as a number you measure on your own hardware before trusting any formula built on it. On top of the model sits the KV-cache fleet from AIE-303-M02 Lesson 3: `bytes_per_token × seq_len × concurrency`, where `concurrency` is how many requests you intend to hold in flight at once (AIE-303-M03 used 6, from M02's cache-budget analysis, as a worked example figure this module reuses).

**Throughput.** AIE-303-M01 Lesson 1's `X_max = 1 / L0` still holds exactly — a single worker process serves requests strictly one at a time, at a rate set by your own measured single-request latency, regardless of whether the model behind it is a vendor's or yours.

**Worked example.** `distilgpt2` (82,000,000 parameters), fp32 (4 bytes/param), a stated 200 MB framework-overhead constant, `seq_len = 512`, `concurrency = 6` (M03's figure), on a stated small owned box with 2,048 MB of RAM available to the inference process:

```
predicted_model_rss_mb    = (82,000,000 * 4) / (1024*1024) + 200
                           = 312.80 + 200.00 = 512.80 MB

predicted_kv_cache_fleet_mb = (36,864 * 512 * 6) / (1024*1024)   # 36,864 B/token from M02 L3, distilgpt2 config
                            = 108.00 MB

total_predicted_mb        = 512.80 + 108.00 = 620.80 MB
budget_mb                 = 2,048 MB
headroom_mb               = 2,048 - 620.80 = 1,427.20 MB   ->  fits, comfortably
```

Notice what this arithmetic actually shows: for a model this small, the KV-cache fleet (108 MB) is a rounding error next to the model weights and framework overhead (512.80 MB) — the opposite of AIE-303-M02's headline lesson, where KV cache was *the* memory-budget story for longer sequences and larger models. That is not a contradiction; it's the same formula producing a different dominant term at a different scale, and the reason to compute both terms explicitly instead of pattern-matching "KV cache is the memory problem" from a different module's worked example onto this one.

Using an illustrative int8-quantized single-request latency of `L0 = 0.27s` (substitute your own AIE-303-M02 Lab A measurement): `X_max = 1/0.27 ≈ 3.70 requests/second` from a single worker, **before** any of Lesson 3's cost arithmetic runs. This is the number that turns "can I self-host this" from a yes/no into a stated capacity: a single small owned box, serving this specific small model, single-worker, tops out around 320,000 requests/day at that latency — a ceiling this module's Lab A measures for real on your own hardware, not just predicts.

**Named misconceptions**

- *"Self-hosting requires a GPU, or at minimum a beefy multi-core server."* False for a model this small, and the worked example proves it with real bytes: 620.80 MB total, comfortably inside even a modest 2 GB budget. The misconception generalizes from stories about self-hosting large frontier-scale models — this module's whole point is that AIE-302's system, productioned at the scale this course has been costing throughout, does not need that hardware, and asserting it does without computing the byte budget first is exactly the slogan-not-number failure Lesson 1 named.
- *"The framework overhead is negligible next to the model weights, so I can skip measuring it."* At 200 MB against 312.80 MB of weights, framework overhead here is over a third of total memory — not negligible, and for a smaller model or a lower-precision quantization it becomes the *majority* of the footprint. Treat it as a number to calibrate on your own machine (Lab A does this), never as zero.
- *"`X_max` from a single worker is the real ceiling — if I need more throughput, the model itself has to get faster."* AIE-303-M01 Lesson 1 already named the other lever: more worker processes, each holding its own model copy, each costing its own full memory footprint. On an owned box, "add a worker" costs RAM you have to have physically installed, not a line on someone else's invoice — the memory budget from this lesson is exactly what tells you how many workers you can actually add before you run out.

### Lesson 3 — The true cost of ownership: capex, electricity, and the line item that dominates

**Teaching text.** AIE-303-M03 Lesson 4 computed a self-hosted/API breakeven using `fixed_monthly_hardware_cost = cost_per_vcpu_hour × 24 × 30`, a pure compute-rental number. This lesson builds the number that belongs in that formula for *owned* hardware, which has three components, not one:

```
capex_per_month    = hardware_purchase_price / depreciation_months
electricity_per_month = (watts / 1000) * hours_per_month * price_per_kwh
labor_per_month    = maintenance_hours_per_month * loaded_hourly_rate

true_monthly_fixed_cost = capex_per_month + electricity_per_month + labor_per_month
```

`capex_per_month` spreads the purchase price over a stated useful-life horizon — this is standard equipment depreciation, not a novel idea, but it is the term a "self-hosting is basically free after the upfront cost" argument silently sets to zero by only counting the upfront cost *once* instead of amortizing it against the months it actually serves. `electricity_per_month` is the line a cloud rental bakes invisibly into its per-hour price and an owned box makes you pay directly, on your own utility bill. `labor_per_month` is Lesson 1's bottom-row properties, priced: the hours a real person spends patching the OS, applying the AIE-303-M06 incident-response skills when the box has a bad night, and re-running AIE-303-M04's eval gate on every model or dependency update — multiplied by that person's fully loaded hourly rate, because that person's time is not free just because no invoice itemizes it.

**Worked example.** A modest owned box: a $900 mini-PC-class machine, 36-month depreciation, drawing 40W average under this workload, at a stated $0.14/kWh, with 2 hours/month of maintenance labor at a stated $75/hour fully-loaded rate:

```
capex_per_month        = 900 / 36                       = $25.00/month
electricity_per_month  = (40/1000) * 720 * 0.14          = $4.03/month
labor_per_month        = 2 * 75                           = $150.00/month
----------------------------------------------------------------------
true_monthly_fixed_cost                                   = $179.03/month
```

Compare against AIE-303-M03's compute-rental-only figure, `$34.56/month`:

```
sovereignty_premium = true_monthly_fixed_cost / rental_only_fixed_cost
                     = 179.03 / 34.56
                     ≈ 5.18×
```

The true fixed cost of owning this hardware is **5.18 times** what the compute-rental number alone implied — and 84% of that true cost (`150.00 / 179.03`) is the labor line, not the hardware or the electricity. This is the single most important number in this module: the dominant cost of self-hosting a small model is not the model, not the box, and not the power bill. It is the person who keeps the box alive, and a cost model that omits that person is not a conservative estimate of self-hosting's cost — it is missing its largest term.

Recompute AIE-303-M03 Lesson 4's breakeven with the corrected fixed cost, against that module's RAG-request API price of `$0.0002445/request`:

```
breakeven_true   = 179.03 / 0.0002445   ≈ 732,200 requests/month   (~24,400/day)
breakeven_rental = 34.56  / 0.0002445   ≈ 141,350 requests/month   (~4,700/day)   # M03's figure, unchanged
```

At the true, sovereign fixed cost, the traffic volume required before self-hosting beats the API is **5.18× higher** than M03's compute-only number implied — matching the sovereignty premium exactly, because breakeven volume is directly proportional to fixed cost at a constant per-request API price. A system running well below ~732,000 requests/month is, on the numbers, better served by the API — not because sovereignty's other properties (data residency, no vendor lock-in) don't matter, but because the *economic* argument for self-hosting specifically requires either genuinely high volume or a labor line item much smaller than $150/month, and a defensible recommendation says which of those is true for the system in front of you, with the arithmetic shown.

**Named misconceptions**

- *"Once the hardware is paid off, self-hosting is free."* Capex reaching zero at the end of its depreciation schedule removes one of three line items — electricity and labor both continue indefinitely, and labor was 84% of the total in the worked example. "Paid off" retires the *smallest* recurring cost in a well-run deployment, not the dominant one.
- *"2 hours/month of labor is a padding number, not a real constraint."* It is a genuinely optimistic estimate for a box running AIE-303-M04's eval-gated deploys, AIE-303-M05's tracing, and AIE-303-M06's incident response for real — patching, dependency updates, disk-space monitoring, and the occasional actual incident add up faster than a first guess suggests. Lab B has you build this number from your own stated assumptions, not copy this lesson's, precisely so a learner's own number is auditable rather than borrowed.
- *"The breakeven volume is a fixed fact about self-hosting in general."* It is a fact about *this* box, *this* labor rate, and *this* API price — change any one (a bigger box that serves more requests per dollar, a lower labor rate because patching is automated, a more expensive API alternative) and the breakeven moves. Lab B's `sovereignty_cost.py` is built so that changing any single assumption is a one-line edit, on purpose — a defensible number is one whose sensitivity to its own assumptions you can show, not just state.

### Lesson 4 — Owning the whole loop: the re-ascent, with no vendor to catch you

**Teaching text.** Every earlier module in this course built a skill against a system where, if the skill failed, there was a backstop: a managed API's own uptime SLA, a cloud vendor's own patched kernel, a hosted eval endpoint someone else keeps running. Self-hosting removes every one of those backstops, one at a time, in exactly the order this course built the skills that replace them:

- **AIE-303-M04's eval gate** still runs the same way — a candidate version is checked against the gold set *before* it is promoted — but on an owned box, there is no vendor staging environment to run it in first; the gate runs on the same hardware that will serve production traffic, and a slow gate is now *your* deploy velocity problem, not a vendor's.
- **AIE-303-M05's tracing** still logs the same four-field spans, but the disk they land on is a disk you provisioned, sized, and are responsible for not filling — that "~80 MB/day" figure from M05 Lesson 1 is no longer an abstract number to note, it's a real partition you sized in Lesson 2's hardware budget.
- **AIE-303-M06's incident response** is where the gap is sharpest: a rehearsed rollback against a hosted API's infrastructure assumes the *hosting* stays up while you revert the model version. On an owned box, the hosting *is* the thing that can fail — the process can OOM, the disk can fill from an unrotated trace log, the power can drop — and "roll back to the last good version" has to work even when the failure is the box itself, not just the model.

This module's Lab C is the concrete version of that last point: it deliberately separates two failure classes an owned deployment has to handle, because they are caught by different mechanisms and conflating them is the specific mistake that leaves one of them uncovered. A **correctness failure** — a candidate model or config that produces wrong output — is exactly what AIE-303-M04's eval gate exists to catch, *before* promotion, and Lab C proves this by constructing one and watching the gate refuse to promote it. A **capacity failure** — the box running out of memory or the process crashing under load past the ceiling Lesson 2 predicted — cannot be caught by an eval gate, because the model's output was never wrong; the *box* failed. That failure is caught, if at all, by the timed rollback drill this course has been building toward since AIE-303-M04, run for real, on real hardware, with a real stopwatch, because a rollback script that has only ever been read is — as M04 put it — not slower than a rehearsed one. It doesn't work.

**Worked example.** Two "deploys" attempted against the Lab A/B box: Deploy 1 swaps in a candidate whose tokenizer config is silently mismatched with its model weights — every generation produces near-garbage. Run through the eval gate (5 known prompts, expected-substring checks), it fails 5/5 and is never promoted; the `active` pointer never moves, and no user request is ever served the broken candidate. Deploy 2 is a good candidate, correctly promoted, serving traffic normally — and then a load spike (Lab C's deliberate break) pushes concurrent requests past Lesson 2's predicted 6-in-flight ceiling. The eval gate has nothing to say about this: the model's outputs, on the requests it does complete, are still correct. What fails is the process — and the only mechanism that helps is the rollback, timed, executed under the same pressure a 2am page would apply.

**Named misconceptions**

- *"A passing eval gate means the deploy is safe."* It means the deploy is *behaviorally correct on the gold set* — it says nothing about whether the box can carry the load that correctness will be asked to serve. Lab C's two failure classes exist specifically to break this conflation.
- *"Rollback rehearsal from AIE-303-M04 already covers this — nothing new to practice here."* The mechanism is the same; the failure surface is not. M04's rollback assumed the serving infrastructure kept running while the model version reverted. Here, Lab C's capacity-failure drill practices rolling back *while the box itself is the thing that's unhealthy* — a strictly harder and more realistic version of the same skill.
- *"Incident response for a self-hosted box is the same skill as for a managed one, just applied to different hardware."* The skill transfers; the backstop doesn't. A managed API's incident is triaged with a vendor status page to check against your own symptoms. An owned box's incident has no second opinion — the trace log and the rollback script are the entire toolkit, which is exactly why M05's tracing and M04's rollback both had to exist *before* this module could respons­ibly ask a learner to self-host anything.

@app.get("/health")
def health() -> dict:
    return {"status": "ok"}

# solution: hardware_ceiling.py (completed)
import psutil

BYTES_PER_MB = 1024 * 1024

def predicted_model_rss_mb(n_params: int, dtype_bytes: int = 4,
                            framework_overhead_mb: float = 200.0) -> float:
    return (n_params * dtype_bytes) / BYTES_PER_MB + framework_overhead_mb


def predicted_kv_cache_fleet_mb(bytes_per_token: int, seq_len: int, concurrency: int) -> float:
    return (bytes_per_token * seq_len * concurrency) / BYTES_PER_MB


def fits_in_budget(model_rss_mb: float, kv_cache_fleet_mb: float, budget_mb: float) -> dict:
    total_mb = model_rss_mb + kv_cache_fleet_mb
    return {
        "total_mb": total_mb,
        "fits": total_mb <= budget_mb,
        "headroom_mb": budget_mb - total_mb,
    }


def max_single_worker_throughput(latency_seconds: float) -> float:
    return 1.0 / latency_seconds


def process_rss_mb(pid: int) -> float:
    return psutil.Process(pid).memory_info().rss / BYTES_PER_MB

                             maintenance_hours_per_month: float, loaded_hourly_rate: float,

# solution: sovereign_ops.py (completed)
import json
import time
from pathlib import Path

REGISTRY_PATH = Path("deploy_registry.json")

GOLD_CHECKS = [
    ("The capital of France is", "Paris"),
    ("2 + 2 =", "4"),
]


def load_registry() -> dict:
    if REGISTRY_PATH.exists():
        return json.loads(REGISTRY_PATH.read_text())
    return {"active": None, "last_good": None}


def save_registry(registry: dict) -> None:
    REGISTRY_PATH.write_text(json.dumps(registry))


def run_gate(generate_fn, checks: list[tuple[str, str]] = GOLD_CHECKS) -> dict:
    failures = []
    for prompt, expected in checks:
        output = generate_fn(prompt)
        if expected.lower() not in output.lower():
            failures.append({"prompt": prompt, "expected": expected, "got": output})
    n_total = len(checks)
    n_pass = n_total - len(failures)
    return {"passed": n_pass == n_total, "n_pass": n_pass, "n_total": n_total, "failures": failures}


def promote(candidate_version: str, generate_fn, registry: dict) -> dict:
    gate_result = run_gate(generate_fn)
    if gate_result["passed"]:
        registry["last_good"] = registry["active"]
        registry["active"] = candidate_version
        save_registry(registry)
        return {"promoted": True, "gate_result": gate_result}
    return {"promoted": False, "gate_result": gate_result}


def rollback(registry: dict) -> dict:
    t0 = time.monotonic()
    target = registry.get("last_good")
    registry["active"] = target
    save_registry(registry)
    elapsed_s = time.monotonic() - t0
    return {"rolled_back_to": target, "elapsed_s": elapsed_s}

Specific to this module's subject — what owning the machine actually costs, and who that cost falls on.

- **Tier 1 — material ground.** The total cost of owning infrastructure is dominated by operational labor, not hardware or electricity — this is not a claim specific to AI serving; it is the well-documented, decades-old finding of total-cost-of-ownership analysis in every domain of self-hosted infrastructure, and this module's worked example (labor at 84% of true fixed cost) reproduces that finding at the scale of a single small model on a single small box. A cost model that omits labor is not a simplification; it is missing its largest term, verifiably, the way this module's Lab B makes concrete.
- **Tier 2 — what the field suppresses.** "Sovereignty" as marketed is a property of an *organization* — the data stays inside the company's perimeter, the company controls the model. What that framing suppresses is that the labor absorbing the properties in the bottom half of Lesson 1's table is not the organization's, in any diffuse sense — it is a specific person's hours, a specific person's on-call rotation, a specific person's 2am page when the box that used to be someone else's problem is now theirs. The word "sovereignty" describes the company's new independence; it says nothing about the one or two engineers who became that independence's cost center, and a pitch deck's "no vendor lock-in, full control" slide has no line for their sleep.
- **Tier 3 — sit with this.** This course's own rubric, in every module including this one, has graded a $/request number — a real, necessary, defensible number, and also a number that, by its own construction, only ever counts what shows up on an invoice. AIE-303-M03's ethics thread named this at the course level: what "reliability" metrics suppress is the system's effect on the people in its loop, unmeasured while everything else about the system is measured. This module's labor line item is the closest this course comes to putting a dollar figure on a person's time — and even that figure, $150/month for "2 hours of maintenance," is a euphemism the moment the box has a bad month: the incident that runs long, the rollback attempted at 2am under real pressure instead of Lab C's rehearsed calm, the on-call week that cost more than any spreadsheet line predicted. What would it take to build a cost model honest enough to show that number *before* the bad month happens — and if you built it, and it changed the self-host-or-not recommendation, is that a column you'd actually add to the spreadsheet you hand your stakeholder, or the one column every real cost model in this course, including this one, has quietly left out?
