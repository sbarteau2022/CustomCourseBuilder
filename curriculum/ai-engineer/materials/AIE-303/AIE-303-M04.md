## Lessons

### Lesson 1 — The eval gate: green CI, red system

**Teaching text.** A standard CI pipeline — lint, type-check, unit tests — verifies code *shape*: does it compile, does it satisfy the contracts you wrote tests for. None of that touches model *behavior*, and a deploy pipeline for a system with a model in it needs a stage that does. That stage is the **eval gate**: a CI step that runs the candidate version against a fixed, held-out gold set using the exact metric your team already trusts, and fails the build — a real nonzero exit code, not a Slack message someone might read — if the candidate regresses.

The gold set has to be *fixed*, not sampled from live traffic, for a reason worth naming: a fixed gold set with a deterministic classifier gives you an *exact*, reproducible number every time you run it — no sampling noise, no "run it again and see." That determinism is what makes it suitable as a hard merge-blocking gate. (Live traffic *is* useful signal — that's Lesson 2's canary — but it's noisy by construction, which makes it the wrong tool for a binary pass/fail gate and the right tool for a graduated, sample-size-aware decision.)

The next design question a gate has to answer is *what threshold blocks a deploy*, and the naive answer — "candidate must score above some fixed number" — is usually wrong, for the same reason a fixed absolute cost target was the wrong frame in AIE-303-M03: what you actually care about is *regression relative to what's already live*. A candidate that scores 0.85 when your current production system scores 0.80 is an improvement even though 0.85 might look mediocre in isolation; a candidate that scores 0.85 when production scores 0.95 is a regression that a fixed absolute floor of "0.80" would wave straight through. The gate this module builds compares the candidate to the *current live baseline*, with a stated tolerance for how much drop is acceptable — not to an arbitrary fixed number.

**Worked example.** `v1-stable` is the current live version — AIE-204-M02's `rule_classify`, unchanged. `v2-candidate` is a proposed cleanup: someone read the keyword lists, decided `"unauthenticat"` and `"enterprise customer list"` looked like overfit string matches, and dropped both from the `HIGH_KEYWORDS` list in an otherwise unrelated refactor PR. Run both against the real 50-ticket gold set:

```
v1-stable:    macro_f1 = 0.8897   high(recall=1.000, precision=0.667, f1=0.800)
v2-candidate: macro_f1 = 0.8632   high(recall=0.875, precision=0.636, f1=0.737)
```

Macro-F1 drops 0.0265 — 2.65 points, about a 3% relative decline. On an aggregate-only gate with a generous tolerance (say, "block only if macro_f1 drops more than 3 points"), this candidate **passes**. But look at what actually changed: exactly one ticket flipped, `G002` — *"We found an unauthenticated endpoint returning other tenants' billing records"* — from `high` to `medium`. That is not a random ticket to lose. It is the one ticket in the entire gold set that is, in plain language, a live security breach, and the candidate's only behavioral change is to silently deprioritize it. The aggregate number moved 3%; the thing that actually happened is that the system's response to "we found a breach" got quietly worse.

This is why the gate this lesson builds checks **two things, not one**: the aggregate macro-F1 (relative to baseline, with a tolerance) *and* a **per-class recall floor on the highest-severity class specifically** — because an aggregate average, exactly like AIE-303-M03's average-only cost figure, can hide a regression that's small in the mean and severe in the tail. With `macro_f1_tolerance = 0.03` and `min_high_recall = 0.90`: `v2-candidate`'s macro-F1 drop (0.0265) is *inside* the tolerance — that check alone passes. Its `high`-class recall (0.875) is *below* the floor (0.90) — that check fails, and the gate blocks the deploy. A gate built on the aggregate check alone would have shipped this.

Wired into an actual pipeline, the gate is just a script with an exit code:

```yaml
# .github/workflows/deploy.yml (excerpt)
- name: Eval gate (blocks merge if the candidate regresses gold-set performance)
  run: python deploy_gate.py v2-candidate   # nonzero exit fails the job — no merge, no deploy
```

There is no diagram step here that isn't also a real, runnable one — `deploy_gate.py`'s exit code *is* the block, the same script Lab M04-A builds and tests.

**Named misconceptions**

- *"Green CI means the deploy is safe."* Green CI means the code you wrote satisfies the tests you wrote. It says nothing about model behavior unless one of those tests *is* an eval gate against real ground truth — which is precisely the stage most CI pipelines for ML systems don't have, and precisely the stage this module adds.
- *"A single aggregate metric with a reasonable tolerance is a sufficient gate."* Shown false above: a 2.65-point macro-F1 drop, well inside a 3-point tolerance, corresponds to exactly one flipped ticket — and that ticket is the single most severe one in the set. An aggregate gate is necessary but not sufficient; a gate also needs a floor on whichever class's failure mode is least acceptable, checked independently.
- *"The eval gate and the eval harness are two different things."* They are the same code. AIE-204-M02 built `precision_for_class` / `recall_for_class` / `f1_for_class` / `macro_f1` to catch a gaming exploit in a metric design exercise. This lesson's gate calls those exact functions, unmodified, against the exact same gold set, from a CI step instead of a notebook cell. If your deploy gate reinvents its own scoring logic instead of calling your eval harness, you now have two eval implementations that can silently disagree — which one do you trust during an incident?

### Lesson 2 — Canary rollout: real traffic-splitting, and the sample size a decision actually needs

**Teaching text.** The eval gate blocks the worst regressions before merge, against a fixed gold set. But a fixed gold set can't tell you everything — it's the same 50 tickets every time, and real traffic has a distribution the gold set only approximates. A **canary rollout** answers a different question: route a small, live slice of real traffic to the candidate, keep the rest on the trusted baseline, and decide — from what actually happens on that slice — whether to widen the rollout, hold, or roll back.

The mechanism is **traffic splitting**: a function that, given a request identifier and a target percentage, deterministically routes that request to `"baseline"` or `"canary"`. Deterministic matters as much as the percentage does — routing has to depend only on the request's own identifier (hash it, take the hash mod some range, compare to a threshold), never on a counter or a coin flip, so that the *same* request always lands on the *same* arm no matter when or how many times you ask. That's what makes a canary debuggable: if a specific user reports a problem, you can recompute which arm they were on.

The harder question is not *how* to split traffic but *how much of it you need before you trust what you're seeing* — and this is where the canary's biggest trap lives. Say the highest-severity class is 8 of 50 tickets in the gold set (16%), and you're canarying 5% of traffic. The *expected* number of that class's tickets landing in the canary arm after `n` total requests is `n × 0.05 × 0.16`. To expect even 5 such tickets — arguably still a small sample for a class this consequential — you need `n ≈ 5 / (0.05 × 0.16) = 625` requests. Below that, any recall number you compute for that class is built from a handful of data points, and a handful of data points from a binary-ish outcome is exactly the setting where a metric can look perfect by chance and be wrong, or look broken by chance and be fine — the small-sample-noise problem AIE-204-M03 built the statistical vocabulary for, arriving here as an operational decision instead of a research one.

**Worked example.** Canarying `v2-candidate` at 5% against `v1-stable`, with a floor of 5 observed high-class tickets before trusting a decision (seeded, reproducible traffic simulation, so these are exact, not illustrative):

| Total requests | High-class tickets seen in canary | Canary `recall(high)` | Decision |
|---|---|---|---|
| 150 | 0 | — | `insufficient_data` |
| 300 | 0 | — | `insufficient_data` |
| 500 | 5 (exactly at the floor) | 1.00 | `promote` |
| 700 | 7 | 0.857 | `rollback` |
| 1,000 | 8 | 0.875 | `rollback` |

Read the 500-request row carefully: it just crosses the sample-size floor, and it returns a *misleadingly clean* verdict — `recall(high) = 1.00`, promote — purely because the specific tickets that happened to land in the canary arm by that point didn't include the one the candidate actually gets wrong. Two hundred requests later, at 700, the picture flips to `rollback`, and by 1,000 requests the canary's recall (0.875) has converged almost exactly onto the true full-gold-set value (also 0.875) computed directly in Lesson 1. **Crossing the minimum-sample floor is necessary, not sufficient** — it stops you from deciding on zero evidence, but it does not guarantee the evidence you have yet is representative. The practical implication: treat an early "promote" the same way you'd treat a first, small-sample experimental result anywhere else in this curriculum — as a hypothesis the *next* batch of traffic still gets to overturn, not a verdict to stop watching.

**Named misconceptions**

- *"5% canary traffic for an hour is obviously enough to know."* Shown false above: at similar or larger volumes than "an hour of traffic" for many real services, the canary can sit at zero samples of the class that matters most, or cross the floor and still hand you a fluke. Compute the expected-samples arithmetic for *your* traffic volume and *your* rarest consequential class before trusting a canary window's silence or its clean-looking result.
- *"A canary that looks fine after crossing the minimum sample size is safe to promote."* The 500-request row is the counter-example, built to order: it crosses the floor and is still wrong. A minimum sample size prevents zero-evidence decisions; it does not make a decision noise-free. A canary window that stays "promote" across *several* consecutive re-checks as volume grows is a much stronger signal than one clean reading the moment the floor is crossed.
- *"Widening the min-sample floor until the canary says what I expect is just tuning the gate."* It's the same move as re-labeling a gold set until a metric passes, which AIE-204-M02 named directly as gaming the eval. A canary threshold set *after* seeing an inconvenient result, to make that result go away, is not calibration — it's exactly the exploit this course has spent two courses teaching you to recognize when someone else does it.

### Lesson 3 — What a rollback actually reverts

**Teaching text.** "Roll back" sounds like one action. In a real deploy it's shorthand for **flip the pointer that decides which version is live back to the last known good one** — and the entire reason a rollback can be fast is that this pointer flip is supposed to be the *only* thing that has to change. That's a design property you have to build, not a fact that's true by default.

Concretely: the live version is a small piece of state — a config value, a routing weight, a row in a table — read by every request at serve time. A rollback writes that one value and nothing else. It is not "redeploy the previous build": rebuilding, re-containerizing, and re-provisioning the old version from source is the same slow pipeline that got the bad version out in the first place, running in reverse, and an incident is exactly the moment you can't afford that latency. The pointer flip has to be a write you can make in milliseconds, decoupled entirely from the build pipeline, which is precisely why `deploy_state.py` in this module's labs is a JSON file with one key, written **atomically** — write to a temp file, then `os.replace` over the target — so that even a process crash mid-write leaves either the old value or the new one, never a half-written, unreadable pointer at the exact moment you need to read it fastest.

The trap is treating the pointer flip as the *entire* rollback. In a real system, other state can silently fail to follow the pointer back: a response cache keyed partly by model version can keep serving cached outputs from the bad version after the pointer moves; sticky routing or session affinity can keep specific users pinned to the version they were already talking to; a feature flag toggled as part of the same deploy might not be included in "rollback" at all if it lives in a different system; and requests already in flight when the pointer flips will finish on whichever version they started on, not silently teleport to the new one. None of these are exotic edge cases — they're the ordinary shape of a system with more than one piece of state, and every one of them is a way a rollback can *report success* — the pointer changed, the deploy log says "rolled back" — while a user is still, in practice, talking to the broken version.

**Worked example.** This module's service reads its live version from `deploy_state.json` on every request — no cache, no session affinity, nothing else that could drift — specifically so that Lab M04-C's rollback is a clean, one-variable experiment: flip the pointer, and the *very next* request anywhere is guaranteed to see the new value. Real systems buy that guarantee deliberately (short cache TTLs on version-dependent data, stateless routing, explicit drain periods for in-flight requests) — they don't get it by accident. When you inherit a rollback runbook for a system you didn't build, the first question worth asking is not "does the pointer flip work" but "what else does this system's request path touch that the pointer flip doesn't."

**Named misconceptions**

- *"Rollback means redeploying the previous version."* That's a rebuild, and a rebuild carries the build pipeline's full latency into the middle of an incident. The fast path — the one worth rehearsing — is a version-pointer flip to a build that already exists and is already known-good, not a fresh build of it.
- *"If the pointer changed, the rollback is done."* Only if the pointer is the *only* state a request's behavior depends on. Caches, sticky sessions, feature flags, and in-flight requests are all places a rollback can report success while a real user is still on the broken path — check each one explicitly for your system rather than assuming the pointer speaks for all of them.
- *"Rolling back fixes the incident."* It stops the bleeding — no *new* requests get the bad behavior. It does nothing about requests the bad version already answered while it was live. Cleaning that up (identifying affected users, re-processing, notifying someone) is a separate, real step this module doesn't cover — AIE-303-M06's incident-response material picks it up — but a rollback that's reported as "the incident is resolved" without that step has quietly redefined "resolved" to mean "stopped getting worse."

### Lesson 4 — Rehearsal vs. runbook: MTTR as measured, not asserted

**Teaching text.** A **runbook** is a document: numbered steps someone wrote down for what to do during an incident. A **rehearsed** procedure is one of those steps that has actually been executed, under time pressure, at least once, by the person (or the automation) that will run it for real — and the difference between the two is not a matter of degree. This lesson's central claim, which Lab M04-C exists to make you prove on your own measured numbers rather than take on faith, is that **a rollback nobody has rehearsed doesn't work when you need it** — not "works, but slowly." Doesn't work: fails, gets retried, and only then works, at a cost measured in the incident's most expensive currency, elapsed time while something is broken.

The mechanism behind that claim is ordinary and worth stating precisely: a runbook step nobody has run has never been checked against reality. The exact version string in step 4 might be stale. The command in step 6 might reference a tool that got renamed. The person on call might not, in the moment, actually remember which of three plausible-sounding version identifiers is the real last-known-good one — and under paging pressure, at 3am, a plausible-but-wrong guess is exactly the failure mode a calm read-through the runbook the next morning would never catch. **Rehearsal is what converts "should work" into "does work"** — and it's a claim about having *executed the procedure*, independent of whether that procedure is manual or automated. A well-rehearsed manual runbook, run by someone who has done it before and knows the one right command, beats an unrehearsed one badly — automation on top of that then removes the remaining human latency, but rehearsal is the variable that removes the *failure*, not just the delay.

**Worked example.** Lab M04-C runs the identical injected failure — a bad version reaches the live pointer — against three procedures and times each with `time.perf_counter()`, not a stopwatch guess:

| Procedure | Elapsed | Attempts to recover |
|---|---|---|
| `automated_rollback` — a monitor polls `/healthz`, flips the pointer the instant it's unhealthy, no human involved | ~8 ms | 1 |
| `rehearsed_manual_rollback` — a human already knows the last-known-good version and the exact command | ~211 ms | 1 |
| `cold_manual_rollback` — a human has never done this before: pages in, searches logs, **guesses a plausible-sounding wrong version first**, discovers the mistake, searches again, finds the real one | ~1,210 ms | **2** |

The automation gap (`automated` vs. `rehearsed_manual`, ~26×) is real and worth having. But look at what separates `rehearsed_manual` from `cold_manual`: it isn't only the ~150 ms of extra searching-and-typing latency — it's that `cold_manual` needed **two attempts**, because the first one was a wrong guess that only failed *because nobody had run this procedure before and found that out safely, in advance*. That second attempt is the central claim, in a single number: an unrehearsed rollback is not merely a slower rollback, it is a rollback that fails at least once before it works, and how many times it fails, and at what cost, is exactly what you don't get to know if you never ran the drill until the incident forced you to.

**Named misconceptions**

- *"We have a runbook, so we have a tested rollback."* A runbook is a claim about what should happen. A drill is a measurement of what does happen. Only the second one has ever been checked against reality — this lesson's whole point is that those two things get treated as interchangeable and are not.
- *"MTTR is a number we report from the last real incident."* That measures your rollback under the worst possible experimental conditions — for real, for the first time, with something actually on fire, no ability to reset and try again. A rehearsed drill measures the same procedure under controlled conditions, repeatably, *before* an incident needs it — which is the only way to find the wrong-guess failure mode safely instead of live.
- *"Automating the rollback removes the need to rehearse it."* Automation removes human latency and human error in *that specific path* — it does not verify the path is correct. An `automated_rollback` that has never been run end-to-end against a real injected failure can have exactly the same "step 4 references a version that no longer exists" bug a stale manual runbook has; it's just a bug in code instead of prose, no less likely to fail silently until you drill it.

```python
"""AIE-204-M02's eval harness, reused unchanged (precision/recall/F1/macro-F1
and the rule_classify baseline), plus the two model versions this module's
labs deploy: v1-stable (the harness's own baseline) and v2-candidate (a
"cleanup" that drops two keywords its author considered noisy)."""
from gold_set_50 import GOLD_SET

Y_TRUE = [g[2] for g in GOLD_SET]

HIGH_KEYWORDS = ["down", "breach", "unauthenticat", "no backup", "audit", "immediately",
                 "100%", "entire app", "every account", "every customer",
                 "enterprise customer list", "broken after", "blocking their launch",
                 "refusing all connections", "500s for every"]
LOW_KEYWORDS = ["would be great", "someday", "just wanted to say", "just checking",
                "roadmap", "thanks", "demo account", "typo", "footer", "favicon",
                "changelog", "shortcut", "less aggressive", "personalize", "loving the"]

# v2-candidate drops these two HIGH_KEYWORDS entries as part of an unrelated
# cleanup PR ("unauthenticat" and "enterprise customer list" looked like
# overfit string matches to whoever wrote the diff).
V2_DROPPED_KEYWORDS = {"unauthenticat", "enterprise customer list"}


def precision_for_class(y_true: list[str], y_pred: list[str], label: str) -> float:
    tp = sum(1 for t, p in zip(y_true, y_pred) if p == label and t == label)
    fp = sum(1 for t, p in zip(y_true, y_pred) if p == label and t != label)
    return tp / (tp + fp) if (tp + fp) else 0.0


def recall_for_class(y_true: list[str], y_pred: list[str], label: str) -> float:
    tp = sum(1 for t, p in zip(y_true, y_pred) if p == label and t == label)
    fn = sum(1 for t, p in zip(y_true, y_pred) if p != label and t == label)
    return tp / (tp + fn) if (tp + fn) else 0.0


def f1_for_class(y_true: list[str], y_pred: list[str], label: str) -> float:
    p = precision_for_class(y_true, y_pred, label)
    r = recall_for_class(y_true, y_pred, label)
    return (2 * p * r / (p + r)) if (p + r) else 0.0


def macro_f1(y_true: list[str], y_pred: list[str], labels=("low", "medium", "high")) -> float:
    return sum(f1_for_class(y_true, y_pred, l) for l in labels) / len(labels)


def classify_v1_stable(text: str) -> str:
    t = text.lower()
    if any(k in t for k in HIGH_KEYWORDS):
        return "high"
    if any(k in t for k in LOW_KEYWORDS):
        return "low"
    return "medium"


def classify_v2_candidate(text: str) -> str:
    t = text.lower()
    high_keywords_v2 = [k for k in HIGH_KEYWORDS if k not in V2_DROPPED_KEYWORDS]
    if any(k in t for k in high_keywords_v2):
        return "high"
    if any(k in t for k in LOW_KEYWORDS):
        return "low"
    return "medium"


VERSIONS = {
    "v1-stable": classify_v1_stable,
    "v2-candidate": classify_v2_candidate,
}


def run_eval(classify_fn) -> dict:
    """Run `classify_fn` over the full gold set and return every number the
    deploy gate needs: macro_f1, and per-class precision/recall/F1."""
    y_pred = [classify_fn(text) for _, text, _ in GOLD_SET]
    return {
        "macro_f1": macro_f1(Y_TRUE, y_pred),
        "per_class": {
            label: {
                "precision": precision_for_class(Y_TRUE, y_pred, label),
                "recall": recall_for_class(Y_TRUE, y_pred, label),
                "f1": f1_for_class(Y_TRUE, y_pred, label),
            }
            for label in ("low", "medium", "high")
        },
        "predictions": y_pred,
    }
```

from eval_harness import VERSIONS, run_eval

MACRO_F1_TOLERANCE = 0.03
MIN_HIGH_RECALL = 0.90


def deploy_gate(candidate_result: dict, baseline_result: dict,
                 macro_f1_tolerance: float = MACRO_F1_TOLERANCE,
                 min_high_recall: float = MIN_HIGH_RECALL) -> dict:
    macro_f1_drop = baseline_result["macro_f1"] - candidate_result["macro_f1"]
    macro_f1_ok = macro_f1_drop <= macro_f1_tolerance

    high_recall = candidate_result["per_class"]["high"]["recall"]
    high_recall_ok = high_recall >= min_high_recall

    reasons = []
    if not macro_f1_ok:
        reasons.append(
            f"macro_f1 dropped {macro_f1_drop:.4f} vs baseline, "
            f"exceeds tolerance {macro_f1_tolerance:.4f}"
        )
    if not high_recall_ok:
        reasons.append(
            f"'high'-class recall {high_recall:.3f} is below floor {min_high_recall:.2f}"
        )

    return {
        "passed": macro_f1_ok and high_recall_ok,
        "macro_f1_drop": macro_f1_drop,
        "high_recall": high_recall,
        "reasons": reasons,
    }


def run_deploy_gate(candidate_version: str, baseline_version: str = "v1-stable") -> dict:
    baseline_result = run_eval(VERSIONS[baseline_version])
    candidate_result = run_eval(VERSIONS[candidate_version])
    verdict = deploy_gate(candidate_result, baseline_result)
    verdict["candidate_macro_f1"] = candidate_result["macro_f1"]
    verdict["baseline_macro_f1"] = baseline_result["macro_f1"]
    return verdict

import hashlib
import random
from gold_set_50 import GOLD_SET
from eval_harness import macro_f1, recall_for_class, VERSIONS

MIN_HIGH_SAMPLES = 5
MACRO_F1_TOLERANCE = 0.03
MIN_HIGH_RECALL = 0.90


def route_request(request_id: str, canary_percent: float) -> str:
    digest = hashlib.md5(request_id.encode()).hexdigest()
    bucket = int(digest[:8], 16) % 10_000
    return "canary" if bucket < canary_percent * 10_000 else "baseline"


def simulate_traffic(n_requests: int, canary_percent: float, seed: int = 0) -> dict:
    rng = random.Random(seed)
    arms = {"baseline": {"y_true": [], "y_pred": []}, "canary": {"y_true": [], "y_pred": []}}
    for i in range(n_requests):
        request_id = f"req-{i:06d}"
        _, text, true_label = rng.choice(GOLD_SET)
        arm = route_request(request_id, canary_percent)
        classify_fn = VERSIONS["v1-stable"] if arm == "baseline" else VERSIONS["v2-candidate"]
        pred = classify_fn(text)
        arms[arm]["y_true"].append(true_label)
        arms[arm]["y_pred"].append(pred)
    return arms


def canary_decision(arms: dict, min_high_samples: int = MIN_HIGH_SAMPLES,
                     macro_f1_tolerance: float = MACRO_F1_TOLERANCE,
                     min_high_recall: float = MIN_HIGH_RECALL) -> dict:
    baseline, canary = arms["baseline"], arms["canary"]
    n_high_in_canary = sum(1 for l in canary["y_true"] if l == "high")
    if n_high_in_canary < min_high_samples:
        return {"decision": "insufficient_data", "n_high_in_canary": n_high_in_canary,
                "min_high_samples": min_high_samples}

    baseline_macro = macro_f1(baseline["y_true"], baseline["y_pred"])
    canary_macro = macro_f1(canary["y_true"], canary["y_pred"])
    canary_high_recall = recall_for_class(canary["y_true"], canary["y_pred"], "high")
    macro_drop = baseline_macro - canary_macro
    macro_ok = macro_drop <= macro_f1_tolerance
    recall_ok = canary_high_recall >= min_high_recall
    decision = "promote" if (macro_ok and recall_ok) else "rollback"
    return {"decision": decision, "n_high_in_canary": n_high_in_canary,
            "baseline_macro_f1": baseline_macro, "canary_macro_f1": canary_macro,
            "canary_high_recall": canary_high_recall, "macro_drop": macro_drop}

"""The one thing a rollback actually flips: a version pointer on disk,
written atomically so a crash mid-write can never leave a corrupt pointer
(readers always see either the old value or the new one, never a half file)."""
import json
import os
import tempfile

DEFAULT_STATE_PATH = "deploy_state.json"


def read_live_version(path: str = DEFAULT_STATE_PATH) -> str:
    with open(path) as f:
        return json.load(f)["live_version"]


def write_live_version(version: str, path: str = DEFAULT_STATE_PATH) -> None:
    directory = os.path.dirname(os.path.abspath(path)) or "."
    fd, tmp_path = tempfile.mkstemp(dir=directory)
    try:
        with os.fdopen(fd, "w") as f:
            json.dump({"live_version": version}, f)
        os.replace(tmp_path, path)  # atomic on POSIX: old or new, never half-written
    except Exception:
        if os.path.exists(tmp_path):
            os.unlink(tmp_path)
        raise

## Three-tier reading

Specific to this module's subject — the mechanics of a gate that blocks, a canary that decides, and a rollback that's actually been tried.

- **Tier 1 — material ground.** Automated deploy gates against a held-out eval set, sample-size-aware canary rollouts, and rehearsed rollback drills (chaos-engineering-style, deliberately triggered before an incident forces the question) are documented, established practice at organizations that run software at scale — and postmortem literature repeatedly names an *untested* rollback or runbook as a factor that turned a contained incident into a longer one. None of this module's claims are novel; they're standard operational discipline, applied here to a model instead of a service.
- **Tier 2 — what the field suppresses.** "Green CI, canary looked good, we shipped it" is the sentence that gets reported upward — not the sample size behind "looked good," not whether the canary window crossed the rare-class floor by luck or by real volume, not whether the aggregate metric that passed was hiding a single, severe, class-specific regression the way `v2-candidate`'s did in this module's own worked example. The dashboards built to reassure a stakeholder report the number that reassures; they were never built to report the number that would have raised the question. A team can follow every practice this module teaches and still, honestly, not know whether their own canary window was a `500-request row` or a `700-request row` — because nobody asked, and the tooling that would answer wasn't built to volunteer it.
- **Tier 3 — sit with this.** A rollback undoes what changed in the *system*. It does not undo what already happened to the person on the other end of the request while the bad version was live — in this module's own worked example, that's a real security-breach ticket, silently reprioritized from `high` to `medium`, for however many minutes or hours the bad deploy was up before the gate, the canary, or an incident caught it. Every metric this module teaches you to build — MTTR, canary sample size, gate pass rate — measures the system's recovery. None of them measure what happened to that ticket, or who read it, or how long they waited, during the window the system was wrong. You will build dashboards that go green fast, and everyone watching them will feel the incident went well. What would you have to add — a query this module never asked you to write — to find out whether "the system recovered quickly" and "the person the system failed was made whole" are actually the same fact, or just two numbers that happen to both look good on the same day?
