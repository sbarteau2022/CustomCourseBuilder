## Lessons

Four lessons. The first shows that "tokenize the text" was always a byte-level problem wearing a character-level costume. ### Lesson 1 — Bytes, not characters: why BPE starts below the abstraction you already have

#### Teaching text

Every learner arrives at this module already believing they know what a "character" is, because Python made `"café"[0]` return `'c'` and never made them think about it further. That abstraction is doing real work, and BPE is built by first refusing it. A Python `str` is a sequence of **Unicode code points** — abstract integers, one per "character" in the Unicode standard, currently numbering over 1.1 million assigned. `"café"` is four code points: `c`, `a`, `f`, `é` (U+0063, U+0061, U+0066, U+00E9). But code points are not bytes, and a neural network's embedding table is indexed by integers over a **fixed, finite** vocabulary decided at training time — it cannot have an entry for a code point it has never seen, and Unicode adds new code points every year. A vocabulary built directly over code points has two fatal problems: it needs well over a million rows just to have *an* entry for every possible input character (almost all of them never seen in training, wasting embedding capacity on emoji and archaic scripts the model will never encounter), and it will still, eventually, meet a code point assigned *after* the vocabulary was frozen — a genuinely unrepresentable input, forcing an `<UNK>` token that silently destroys information every time it fires.

**UTF-8 solves the "unrepresentable input" half of this for free.** UTF-8 encodes every one of those 1.1 million code points as a sequence of 1 to 4 **bytes**, and a byte has only 256 possible values. A vocabulary whose base alphabet is the 256 possible byte values (not the 1.1-million-plus possible code points) can represent **any UTF-8-encoded text that exists or will ever exist** — new emoji, a script nobody has typed yet, a typo, raw binary garbage — because it never needs a symbol it doesn't already have. This is why GPT-2 and every serious BPE tokenizer since starts from **byte-level** BPE, not character-level BPE: the base vocabulary is fixed at exactly 256 tokens (ids 0–255, one per byte value) before a single merge is learned, and `<UNK>` becomes unnecessary — the worst case for an unfamiliar input is that it falls back to individual bytes, which is inefficient (many tokens for a short string) but never *impossible*.

`"café"` is a clean illustration of the code-point/byte distinction actually mattering: as code points it is 4 symbols; as UTF-8 bytes it is **5** bytes — `c`(1) `a`(1) `f`(1) `é`(2, because U+00E9 needs two bytes to encode in UTF-8: `0xC3 0xA9`). A byte-level tokenizer with no merges learned yet emits 5 tokens for `"café"`; a code-point-level tokenizer would emit 4. That extra byte is not a bug — it is the honest cost of `é` needing more information than an ASCII letter to represent, and it is a cost that (Lesson 4 will show) is distributed extremely unevenly across the world's scripts.

#### Worked example

```python
>>> s = "café"
>>> len(s)                      # code points
4
>>> list(s)
['c', 'a', 'f', 'é']
>>> b = s.encode("utf-8")
>>> len(b)                      # bytes
5
>>> list(b)
[99, 97, 102, 195, 169]
>>> bytes([195, 169]).decode("utf-8")
'é'
```

`é` alone decodes only when both bytes `195` and `169` are read together — byte `195` (`0xC3`) is not a valid standalone character, it is a **leading byte** signaling "two more bits of this code point follow." This is exactly why a byte-level BPE tokenizer's *first* useful merges, learned from real text, are overwhelmingly ASCII pairs like `(32, 116)` → `" t"` (space followed by the letter t) — ASCII bytes are self-contained and combine freely — while multi-byte UTF-8 sequences for accented or non-Latin characters start out **already spending 2–4 tokens on a single character**, before any merge has even had a chance to compress them. Lesson 4 measures exactly how much that head start costs.

#### Misconceptions to surface

- **"A character is the natural atomic unit of text, and tokenization just groups characters."** Python's `str` type made this feel true; it is true for code points but not for what a neural network actually consumes, which is bytes. Surface it by asking a learner to predict `len("café")` vs. `len("café".encode("utf-8"))` before running it — most predict they're equal.
- **"UTF-8 and Unicode are the same thing."** Unicode is the assignment of a number (code point) to a character; UTF-8 is one of several ways to *encode* that number as bytes (UTF-16 and UTF-32 are others, and they'd give different byte counts for the same string). Surface it by asking what `"café".encode("utf-16")` returns — it's neither 4 nor 5 bytes.
- **"Byte-level vocabularies need `<UNK>` for the same reason word-level ones do."** No — a byte-level vocabulary of exactly 256 entries can already represent *any* possible input, because any input is *some* sequence of bytes. `<UNK>` was a word-level and code-point-level problem (a symbol outside the fixed table); it is structurally impossible at the byte level. Surface it by asking what happens when a byte-level tokenizer meets a code point invented tomorrow — it degrades to more tokens, it never fails.

### Lesson 2 — The BPE algorithm, hand-traced on four words

#### Teaching text

Byte-Pair Encoding (BPE), adapted for subword tokenization by Sennrich, Haddow, and Birch (2016) from a much older text-compression algorithm, learns its vocabulary greedily and completely mechanically: **count every adjacent pair of symbols across the training corpus, merge the single most frequent pair into a new symbol, and repeat** for as many merges as you've budgeted. There is no model, no gradient, no randomness — only counting and merging, in order, and that order is the entire "model" a BPE tokenizer learns. Encoding new text later means replaying those exact merges, in the exact order they were learned, on the new text's bytes. This lesson does the whole algorithm on four words — small enough to count on paper — because the only way to actually believe "the tokenizer learned a vocabulary" is to be the one who did the counting.

**The corpus.** Four words, with frequencies (how many times each appears in a toy training text): `low` (5), `lower` (2), `newest` (6), `widest` (3). Split each word into its individual characters and append an end-of-word marker `</w>` (so the tokenizer can tell "the `t` that ends `newest`" from "a `t` that continues into the next characters" — without it, merges could bleed across word boundaries, which Lesson 3 explains is exactly what pre-tokenization exists to prevent even more robustly).

| word | frequency | starting symbols |
|---|---|---|
| low | 5 | `l o w </w>` |
| lower | 2 | `l o w e r </w>` |
| newest | 6 | `n e w e s t </w>` |
| widest | 3 | `w i d e s t </w>` |

**Round 1 — count every adjacent pair, weighted by word frequency.** In `low` (freq 5): pairs `(l,o)`, `(o,w)`, `(w,</w>)` each occur once per instance of the word, so each contributes 5 to its pair's total count. Doing this for all four words and summing:

| pair | from | count |
|---|---|---|
| `(e,s)` | newest (6) + widest (3) | **9** |
| `(s,t)` | newest (6) + widest (3) | **9** |
| `(t,</w>)` | newest (6) + widest (3) | **9** |
| `(l,o)` | low (5) + lower (2) | 7 |
| `(o,w)` | low (5) + lower (2) | 7 |
| `(w,e)` | lower (2) + newest (6) | 8 |
| `(w,</w>)` | low (5) | 5 |
| `(n,e)` | newest (6) | 6 |
| `(e,w)` | newest (6) | 6 |
| `(e,r)` | lower (2) | 2 |
| `(r,</w>)` | lower (2) | 2 |
| `(w,i)` | widest (3) | 3 |
| `(i,d)` | widest (3) | 3 |
| `(d,e)` | widest (3) | 3 |

Three pairs are tied for the maximum count of 9: `(e,s)`, `(s,t)`, `(t,</w>)`. A real BPE trainer needs a **deterministic tie-break rule** — otherwise two runs of "the same" training on the same data could learn different vocabularies, which would make the whole exercise unreproducible. This module's convention, used throughout every lab: **among pairs tied for the highest count, merge the one that is lexicographically smallest as a tuple.** Comparing `('e','s')`, `('s','t')`, `('t','</w>')` as tuples, `'e' < 's' < 't'`, so `('e','s')` wins.

**Merge 1: `(e, s)` → `es`, count 9.** Every occurrence of adjacent `e`,`s` in the corpus becomes the single new symbol `es`. `newest` becomes `n e w es t </w>`; `widest` becomes `w i d es t </w>`.

Recount. The pairs `(e,s)` no longer exist (they're gone, replaced by the single symbol `es`); new pairs `(w,es)` and `(es,t)` have appeared where `(w,e)`+`(e,s)` and `(e,s)`+`(s,t)` used to be. The relevant totals: `(es,t)` = 6+3 = **9** (still the newest/widest suffix, now one merge further along), `(t,</w>)` = 6+3 = **9** (unchanged — `t` and `</w>` were never touched by merge 1), and `(l,o)` = 7, `(o,w)` = 7 as before.

**Merge 2: `(es, t)` → `est`, count 9** — tied with `(t,</w>)` at 9, and `('es','t')` < `('t','</w>')` lexicographically (`'e' < 't'`), so `est` wins. `newest` → `n e w est </w>`; `widest` → `w i d est </w>`.

**Merge 3: `(est, </w>)` → `est</w>`, count 9** — now the unique maximum (nothing else is tied at 9 once `(es,t)` is gone). `newest` → `n e w est</w>`; `widest` → `w i d est</w>`. The shared suffix of "newest" and "widest" — the actual English morpheme *-est* plus its word boundary — is now a **single learned token**, purely from co-occurrence counting, with no linguistic rule anywhere in the algorithm.

**Merge 4: `(l, o)` → `lo`, count 7** — tied with `(o, w)`, also count 7 (both counts come from `low` freq 5 + `lower` freq 2, exactly as the round-1 table above already showed). Comparing `('l','o')` and `('o','w')` as tuples, `'l' < 'o'`, so `(l,o)` wins under this module's lexicographic tie-break rule — the same rule that broke the three-way tie at merge 1. `low` → `lo w </w>`; `lower` → `lo w e r </w>`.

**Merge 5: `(lo, w)` → `low`, count 7.** `low` → `low </w>`; `lower` → `low e r </w>`. The whole word "low" is now one token — not because the algorithm knows it's a word, but because "lo" and "w" happened to co-occur as often as "l" and "o" did.

| merge # | pair | new symbol | count |
|---|---|---|---|
| 1 | `(e, s)` | `es` | 9 |
| 2 | `(es, t)` | `est` | 9 |
| 3 | `(est, </w>)` | `est</w>` | 9 |
| 4 | `(l, o)` | `lo` | 7 |
| 5 | `(lo, w)` | `low` | 7 |

State of the corpus after 5 merges:

```
low     (freq 5)  -> ['low', '</w>']
lower   (freq 2)  -> ['low', 'e', 'r', '</w>']
newest  (freq 6)  -> ['n', 'ew'... wait, not yet: 'n', 'e', 'w', 'est</w>']
widest  (freq 3)  -> ['w', 'i', 'd', 'est</w>']
```

Encoding a **brand-new** word later (say `"lowest"`, never seen during training) means applying these five merges **in this exact order**: start from bytes `l o w e s t </w>`; merge 1 fires (`e s` → `es`) giving `l o w es t </w>`; merge 2 fires (`es t` → `est`) giving `l o w est </w>`; merge 3 fires (`est </w>` → `est</w>`) giving `l o w est</w>`; merge 4 fires (`l o` → `lo`) giving `lo w est</w>`; merge 5 fires (`lo w` → `low`) giving `low est</w>` — **two tokens**, and both of them are pieces the tokenizer built out of *other* words entirely (`low` from "low"/"lower", `est</w>` from "newest"/"widest"), never having seen "lowest" itself. This — a novel word decomposing cleanly into previously-learned pieces — is the entire reason subword tokenization exists instead of whole-word tokenization: it generalizes to words it never trained on, gracefully, using pieces it learned from *other* words that happen to share a beginning or a suffix.

#### Misconceptions to surface

- **"The merge order doesn't matter once training is done — it's just a vocabulary, a set."** It is not a set, it is an **ordered list**, and encoding replays it in order. Applying merge 5 (`lo w → low`) before merge 4 (`l o → lo`) on a fresh word would simply never fire, because the symbol `lo` wouldn't exist yet to feed into it. Surface it by asking a learner to encode `"lowest"` using the five merges **in reverse order** and watch it fail to produce `low`/`est</w>` at all.
- **"BPE is finding morphemes / linguistic units."** It found `est</w>`, which happens to align with the real suffix *-est*, but only because *-est* was frequent in this four-word toy corpus. BPE has no concept of morphology; it is pure co-occurrence counting, and it will just as happily merge two halves of an accidental frequent pair that means nothing linguistically (Lesson 3's real-corpus trace shows exactly this with `" corpus"` merging as a whole unit purely because the training text repeats the word "corpus"). Surface it by asking what BPE would learn from a corpus where "est" never meant a suffix at all — it would still merge it, for the same reason, with no idea it isn't a morpheme.
- **"Ties don't really happen / don't matter in practice."** Merge 1 above *was* a three-way tie broken by an arbitrary (if deterministic) convention — a different tie-break rule (e.g., "first pair encountered in a left-to-right scan" instead of "lexicographically smallest") would have picked `(t,</w>)` first instead of `(e,s)` first, and produced a **different** vocabulary from the identical corpus. Surface it by having the learner re-run the trace with the tie-break rule "largest pair wins ties" and compare the resulting merge list — same first-round *count*, different chosen pair, different downstream vocabulary. Reproducibility of a BPE trainer depends on this rule being written down, not assumed.

### Lesson 3 — Scaling up: pre-tokenization and the vocabulary-size trade-off

#### Teaching text

Lesson 2's four-word corpus was pre-split into words by hand before counting began. At real scale — a corpus of megabytes, not four words — that split has to be automatic, and it has to happen **before** BPE counting starts, for a reason Lesson 2's `</w>` marker only partially addressed: without an enforced word/token boundary, BPE would happily learn a merge that spans a space and glues the end of one word to the start of the next, purely because that pair happened to co-occur often (`"of the"` is extremely frequent in English text; nothing in raw byte-pair counting stops `"f"` + `" "` + `"t"`-adjacent merges from eventually fusing chunks across the boundary if left unconstrained). GPT-2's tokenizer (Radford et al., 2019) solves this with a **pre-tokenization regex** that splits text into chunks *before* any BPE merge is allowed to run, and merges are only ever learned and applied **within** a chunk, never across one. The real GPT-2 pattern (using the third-party `regex` library for full Unicode property classes `\p{L}` "any letter" and `\p{N}` "any number") is:

```
's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
```

Read left to right, in priority order: common English contractions get their own piece (`'s`, `'t`, ...); then a run of letters, optionally preceded by one space (`" hello"` or `"hello"`); then a run of digits, likewise; then a run of "other" characters (punctuation) that aren't whitespace, letters, or digits; then trailing whitespace that isn't followed by more non-space content; then any remaining whitespace. This course's from-scratch implementation uses only the Python standard library, so it approximates `\p{L}` and `\p{N}` — which require the third-party `regex` package for true Unicode property support — with stdlib `re`'s Unicode-aware `\w` character class instead:

```python
import re

# stdlib approximation of GPT-2's pattern: [^\W\d_] matches a Unicode "word"
# character that is not a digit and not underscore -- the closest stdlib re
# gets to \p{L} without the third-party `regex` package.
GPT2_PATTERN = r"""'s|'t|'re|'ve|'m|'ll|'d| ?[^\W\d_]+| ?\d+| ?[^\s\w]+|\s+(?!\S)|\s+"""
PAT = re.compile(GPT2_PATTERN)

def pretokenize(text: str) -> list[str]:
    return PAT.findall(text)
```

```python
>>> pretokenize("The corpus has 1023 documents, and it's growing.")
['The', ' corpus', ' has', ' 1023', ' documents', ',', ' and', ' it', "'s", ' growing', '.']
```

Two things to notice immediately: the **leading space travels with the word that follows it** (`' corpus'`, not `'corpus'` preceded by a separate space token) — this is deliberate, because it means `"corpus"` at the start of a sentence and `" corpus"` mid-sentence are genuinely different byte sequences the tokenizer can learn independently, which turns out to matter (a BPE tokenizer trained this way learns *both* `"The"` and `" the"` as candidates for merging, and they very often end up as different tokens with different frequencies). And the **digit run `1023` is pre-tokenized as one chunk**, but that only fixes where digit-vs-letter boundaries fall — it says nothing about how BPE will subsequently *merge within* that chunk, which is exactly the inconsistency Lesson 4 measures.

**BPE now trains only within each pre-tokenized chunk**, counting and merging pairs of *bytes* (not characters — see Lesson 1) inside each chunk, across the whole corpus, using the identical greedy algorithm from Lesson 2 at scale: maintain a frequency table of chunks (most real corpora have huge repetition — "the" appears constantly), count adjacent byte pairs weighted by chunk frequency, merge the max each round, repeat for `vocab_size - 256` rounds (the `-256` because the base byte vocabulary already fills ids 0–255).

**The vocabulary-size trade-off, measured.** Training the from-scratch tokenizer above (full trainer in Lab M01-B) on a ~17,000-byte English passage at increasing target vocabulary sizes, and measuring **bytes per token** on that same training text (higher is better — fewer tokens for the same content, meaning shorter sequences into the transformer, meaning cheaper attention and more content per fixed context window):

| target vocab size | merges learned | train bytes/token |
|---|---|---|
| 256 (no merges) | 0 | 1.00 |
| 300 | 44 | 1.63 |
| 400 | 144 | 2.86 |
| 600 (requested) | **259** (capped) | 4.70 |
| 900 (requested) | **259** (capped) | 4.70 |

Two real effects in that table, both measured, neither invented. First, **diminishing but real returns**: each additional 100 vocabulary slots bought less compression than the last as merges moved from "extremely common English digraphs" (`" t"`, `" a"`, `"he"`) to increasingly rare, corpus-specific chunks. Second — and this is a trap worth naming explicitly — **starting at the 600-token request, training silently capped at 259 merges (vocab 515)**, because this particular training passage ran out of any byte pair occurring more than once past that point; a real trainer must stop there (this module's reference implementation stops when the best remaining pair count drops below 2), which is why the 600 row and the 900 row report the identical 259 merges and the identical 4.70 bytes/token — the 900 request buys nothing beyond what the 600 request already hit the same ceiling on. A larger vocabulary budget only helps if the training corpus has enough real repetition to support it — throwing vocabulary slots at a small or unusually diverse corpus buys nothing past the point where the corpus's own redundancy runs out, and the AIE-203 corpus, being real and orders of magnitude larger and more varied than this 17 KB passage, will hit that ceiling much later, but it will still have one.

**Compression on training data is not the number that matters — generalization is.** The same tokenizer (vocab 600, trained on the passage above) measured on two sentences it never trained on:

| test sentence | domain | bytes | tokens | bytes/token |
|---|---|---|---|---|
| "The tokenizer documents the license of every source it trains on." | same topic as training text | 65 | 14 | **4.64** |
| "The mitochondria regulate calcium signaling within the hepatocyte cytoplasm." | unrelated (biology) | 76 | 46 | **1.65** |

Both sentences are unseen text the tokenizer never trained on. The in-domain one compresses almost as well as the training data itself (4.64 vs. 4.70 bytes/token) because it reuses the same vocabulary — "tokenizer," "documents," "license," "source," "trains" all appeared, or share pieces with words that appeared, during training. The out-of-domain sentence collapses to **1.65 bytes/token — barely better than no merges at all (1.00)** — because "mitochondria," "hepatocyte," "cytoplasm" share almost no byte sequences with anything the tokenizer ever saw, so it falls back to encoding them nearly byte-by-byte. **A BPE vocabulary's efficiency is not a property of the tokenizer in isolation — it is a property of the relationship between the tokenizer's training data and whatever text you later feed it.** Lesson 4 turns this exact measurement — same tool, same method — on language and script instead of topic, and the gap gets far larger.

#### Worked example — see the teaching text; every number above was measured, not estimated

The worked example *is* the two tables above — they were generated by the reference `ByteBPETokenizer` (Lab M01-B) run on real text on the authoring machine. Lab M01-B has the learner reproduce this exact experiment (different vocab sizes, in-domain vs. out-of-domain held-out sentences) on their own AIE-203 corpus slice, and predict the shape of the curve — flattening, not linear — before measuring it.

#### Misconceptions to surface

- **"A bigger vocabulary is strictly better — always train the largest one you can afford."** The 900-vocab row above is the counterexample: it bought *zero* additional compression over 600, because the corpus had nothing left to merge. Beyond that, a larger vocabulary has real costs Lesson 3 doesn't fully price but the model-building modules will: a bigger embedding table, a bigger softmax over the output vocabulary, and rarer tokens seen fewer times during training (worse-estimated embeddings for tail tokens). Surface it by asking the learner to predict what happens to the 900-vocab row *before* they measure it — most predict continued improvement.
- **"Pre-tokenization and BPE merging are the same step, just described two ways."** They are two different mechanisms with two different jobs: pre-tokenization (a fixed regex) decides *where merges are structurally forbidden to cross* (never across a chunk boundary); BPE merging (learned from data) decides *which* adjacent pieces *within* an allowed chunk get fused, and in what order. Surface it by asking what would happen to `"of the"` under BPE with no pre-tokenization step at all — nothing in raw byte-pair counting prevents a cross-word merge; the regex is the only thing that does.
- **"Compression ratio (bytes/token) is a single number that describes a tokenizer."** It is a number that describes a tokenizer **on a specific piece of text**, and the in-domain/out-of-domain table shows it can swing by nearly 3× on the *same* tokenizer depending only on what you feed it. Reporting "our tokenizer gets 4.7 bytes/token" without saying measured on what is the same category of error as reporting a model's accuracy without saying on what eval set — and Lesson 4 shows the highest-stakes version of that omission.

### Lesson 4 — Failure modes and the politics: whitespace, scripts, digits, and whose text pays

#### Teaching text

Lesson 3 closed on a measurement: the same tokenizer scored 4.64 bytes/token on in-domain English and 1.65 bytes/token on out-of-domain English — a real, measured 2.8× penalty for text unlike the training data, entirely within one language. This lesson runs the identical measurement — same tokenizer, same method, `bytes(text) / tokens(text)` — across **scripts** instead of topics, and the penalty stops being a curiosity and becomes structural. A BPE tokenizer trained (as almost every widely deployed one historically has been) on a corpus dominated by English and other Latin-script text will show every non-Latin script the *out-of-domain* penalty, permanently, for exactly the mechanism Lesson 3 already demonstrated: **BPE only merges bytes it has seen co-occur frequently in training, and a script the training corpus barely contains gives it almost no co-occurrence to learn from.**

**Measured.** The same `ByteBPETokenizer`, trained *only* on the English passage from Lesson 3 (no other language, no special handling, nothing adversarial — this is what training on an English-dominant corpus does by default, not a deliberately broken example), encoding equivalent short greetings in seven languages:

| language | script | chars | UTF-8 bytes | tokens | bytes/token |
|---|---|---|---|---|---|
| English | Latin | 36 | 36 | 21 | **1.71** |
| Spanish | Latin | 34 | 34 | 23 | **1.48** |
| Chinese | Han | 14 | 42 | 42 | **1.00** |
| Japanese | Kana/Han | 19 | 57 | 57 | **1.00** |
| Russian | Cyrillic | 39 | 70 | 70 | **1.00** |
| Arabic | Arabic | 35 | 63 | 63 | **1.00** |
| Hindi | Devanagari | 41 | 111 | 111 | **1.00** |

Read the right-hand columns as one fact, not seven separate ones: **every non-Latin-script sample scored exactly 1.00 bytes per token — meaning not a single merge fired on any of them.** Every byte of Chinese, Japanese, Russian, Arabic, and Hindi text passed through this tokenizer completely unmerged, at the base-vocabulary rate of one token per byte, because none of the byte pairs that make up those scripts' UTF-8 encodings ever co-occurred in an English training corpus. Spanish — a *different language* but the *same script* — still degraded (1.48 vs. English's 1.71) because specific Spanish words and diacritics (`ñ`, accented vowels) weren't in the training text, but it degraded far less than the non-Latin scripts, because it shares the base Latin letters and much of English's punctuation and spacing patterns. **The penalty scales with distance from the training distribution, and script is the largest single lever on that distance** — larger, in this measurement, than the in-domain/out-of-domain topic gap Lesson 3 found within English alone.

Compound this with Lesson 1's byte-cost fact and the effect stacks, rather than cancels: Han, Devanagari, and Cyrillic characters each cost 2–3 UTF-8 bytes *before* any tokenization even starts (vs. 1 byte per ASCII character), and then — because the tokenizer never learned to merge them — **each of those 2–3 bytes becomes its own separate token**, whereas an English sentence's 1-byte ASCII characters get compressed by the learned merges down to roughly one token per 1.7 bytes. A sentence carrying the *same amount of meaning* costs a Hindi speaker **111 tokens** and an English speaker **21 tokens**, on a tokenizer that never states this trade-off anywhere in its documentation, because nothing about training a tokenizer this way *requires* stating it — it is simply what happens when nobody asks the question.

**This is not a hypothetical about a toy tokenizer.** Published research measuring this at the scale of real deployed commercial tokenizers on parallel multilingual corpora — Petrov, Malfa, Torr, and Bibi, "Language Model Tokenizers Introduce Unfairness Between Languages" (NeurIPS 2023), and Ahia, Kreutzer, and Choi, "Do All Languages Cost the Same? Tokenization in the Era of Commercial Language Models" (2023) — found the same effect this lesson's toy tokenizer shows, at real scale: tokenizers behind commercially deployed language models require several times as many tokens for many non-English, non-Latin-script languages to encode equivalent content as they do for English. Go read the actual figures in those papers rather than take a number secondhand from this file — the point of citing them here is "verify this yourself in the literature," not "memorize this statistic." What this lesson's measurement gives you, that the citation alone cannot, is the **mechanism**: you just watched, with your own reproducible code, *why* it happens — not a mysterious bias baked into "AI," but the direct, traceable, arithmetic consequence of which text filled the training corpus, replaying the exact same "efficient merges require frequent co-occurrence" fact from Lesson 3, just applied across script instead of within one language.

**The cost is not evenly distributed once it leaves the tokenizer, either.** Every downstream system that bills, limits, or windows by token count inherits this gap directly: an API priced per token costs a Hindi-speaking user roughly 5× more than an English-speaking user for the same request; a fixed context window (say, 8,000 tokens) holds roughly 5× less actual content for that same user; a fixed generation-length limit produces roughly 5× less actual text. None of those downstream systems are doing anything "biased" in their own logic — they are token-counting faithfully. The inequity was fully decided at the tokenizer, upstream of every place anyone thinks to look for it.

**Digit splitting is a narrower, more mechanical failure mode, worth separating cleanly from the script-inequity finding above because it has a different cause.** BPE merges digit sequences exactly like any other byte sequence — greedily, by whatever pairs happened to be frequent in training — with no awareness that `1000` and `1001` are numerically close. Measured, from a tokenizer trained on a corpus containing years and counts:

| number | tokens learned | pieces |
|---|---|---|
| `2019` | 2 | `['20', '19']` |
| `2020` | 2 | `['20', '20']` |
| `1023` | 3 | `['1', '0', '23']` |
| `1400` | 2 | `['1', '400']` |
| `999` | 2 | `['99', '9']` |
| `1000` | 3 | `['1', '00', '0']` |
| `1001` | 3 | `['1', '00', '1']` |
| `12345` | 3 | `['1', '23', '45']` |

`1000` and `1001` — numerically adjacent, one apart — split into **completely different token shapes** (`['1','00','0']` vs. `['1','00','1']` do share a prefix here, but `1400` splits as `['1','400']`, sharing *no structural relationship* with `1000`'s split at all, despite both being four-digit numbers starting with `1`). A model reading these tokens has no consistent positional signal for "this is the hundreds place" the way it would if digits were always split into fixed-width chunks — it has to *relearn*, from scratch, in every different token-shape context, what arithmetic on numbers even means, which is a documented contributor to language models' well-known unreliability at multi-digit arithmetic. This is precisely why later tokenizers (e.g., the one behind GPT-3.5/GPT-4) deliberately override plain frequency-based merging for digits and force consistent chunking (typically into runs of up to three digits) — a hand-written rule layered on top of the learned algorithm, specifically because the algorithm's default behavior on numbers was bad enough to be worth a special case.

#### Misconceptions to surface

- **"Tokenization is a neutral preprocessing step — the real 'AI' and its biases live in the model weights, not here."** The measured table shows a 5×+ token-cost gap *before a single model weight has been touched* — this is not a claim about what a trained model "thinks," it is an arithmetic fact about a lookup table built from counting bytes. Surface it by asking a learner to locate, in the `ByteBPETokenizer.train` code, any line that references language, ethnicity, or intent — there is none; the disparity comes entirely from what text was and wasn't in the training corpus, which is precisely why it is a **documentable, citable, fixable-in-principle design decision**, not an inscrutable emergent property.
- **"If a language just isn't represented much online, its worse tokenization is an unfortunate but unavoidable fact, not a decision anyone made."** "Unavoidable" describes a law of physics; this is a corpus-composition choice, remade every time someone trains a new tokenizer on whatever web-scrape happened to be convenient. Multilingual and script-balanced training corpora exist and measurably close this gap when used — the gap in the measured table is a property of *this training corpus*, reproducible with a *different* training corpus that includes those scripts (predict, and then verify in Lab M01-C, what the same measurement looks like after adding even a small amount of Chinese and Hindi text to training). Surface it by asking what happens to the 1.00 bytes/token rows if you add just one paragraph of Chinese text to the training corpus before retraining — it moves, measurably, because the cause was never "the language" — it was the corpus.
- **"More tokens for the same content is just a cost issue — annoying, not unfair."** Token count doesn't only set price; it sets how much of a conversation, a document, or an instruction fits in a model's fixed context window, and how much output a fixed generation budget can produce. A user whose language costs 5× more tokens per idea gets roughly 5× less usable context and 5× less usable output from the *same* window and the *same* budget as an English-speaking user, for reasons that have nothing to do with the content of what either of them is saying. def merge_word(word, pair, new_token):
```python
    new_word = []
    i = 0
    while i < len(word):
        if i < len(word) - 1 and word[i] == pair[0] and word[i + 1] == pair[1]:
            new_word.append(new_token)
            i += 2
        else:
            new_word.append(word[i])
            i += 1
    return tuple(new_word)

def train_bpe_chars(word_freqs, num_merges, marker="</w>"):
    word_freqs = {word_to_symbols(w, marker): f for w, f in word_freqs.items()}
    merges = []
    for _ in range(num_merges):
        pair_counts = get_pair_counts(word_freqs)
        if not pair_counts:
            break
        best_pair = min(pair_counts.items(), key=lambda kv: (-kv[1], kv[0]))[0]
        count = pair_counts[best_pair]
        new_token = "".join(best_pair)
        new_word_freqs = Counter()
        for w, f in word_freqs.items():
            new_word_freqs[merge_word(w, best_pair, new_token)] += f
        word_freqs = dict(new_word_freqs)
        merges.append((best_pair, new_token, count))
    return merges, word_freqs

def encode_word_chars(word: str, merges, marker="</w>") -> list[str]:
    symbols = list(word_to_symbols(word, marker))
    for pair, new_token, _count in merges:
        symbols = list(merge_word(tuple(symbols), pair, new_token))
    return symbols
```

```python
def train(self, text, vocab_size, verbose=False):
    assert vocab_size >= 256
    word_freqs = Counter()
    for chunk in pretokenize(text):
        word_freqs[tuple(chunk.encode("utf-8"))] += 1

    next_id = 256
    for step in range(vocab_size - 256):
        pair_counts = get_pair_counts(word_freqs)
        if not pair_counts:
            break
        best_pair = min(pair_counts.items(), key=lambda kv: (-kv[1], kv[0]))[0]
        count = pair_counts[best_pair]
        if count < 2:
            break  # nothing left that co-occurs more than once -- Lesson 3's ceiling
        new_word_freqs = Counter()
        for w, f in word_freqs.items():
            new_word_freqs[merge_word(w, best_pair, next_id)] += f
        word_freqs = new_word_freqs
        self.vocab[next_id] = self.vocab[best_pair[0]] + self.vocab[best_pair[1]]
        self.merges.append((best_pair, next_id))
        if verbose:
            print(f"merge {step+1}: {best_pair} -> {next_id} "
                  f"({self.vocab[next_id]!r}) count={count}")
        next_id += 1
    return self

def encode_word(self, word_bytes):
    ids = list(word_bytes)
    for pair, new_id in self.merges:
        ids = list(merge_word(tuple(ids), pair, new_id))
    return ids
```

```python
def measure(tokenizer: ByteBPETokenizer, samples: dict[str, str]) -> dict[str, dict]:
    """Returns {language: {chars, bytes, tokens, bytes_per_token}}."""
    out = {}
    for lang, text in samples.items():
        ids = tokenizer.encode(text)
        nb = len(text.encode("utf-8"))
        out[lang] = {
            "chars": len(text),
            "bytes": nb,
            "tokens": len(ids),
            "bytes_per_token": nb / len(ids),
        }
    return out
```

```python
def fix_and_remeasure(english_corpus, extra_script_text, samples):

    tok_a.train(english_corpus, vocab_size=256 + 300)
```

```python
def test_non_latin_scripts_get_zero_compression_from_english_only_training(english_only_tok):
```
