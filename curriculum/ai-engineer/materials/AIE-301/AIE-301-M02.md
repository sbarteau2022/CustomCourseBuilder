## Before Lesson 1: the two artifacts this module inherits, read once

**From AIE-203-M05, the provenance manifest.** Every document in your corpus has a `ProvenanceRecord`:

```python
@dataclass
class ProvenanceRecord:
    doc_id: str
    source_name: str
    source_url: str | None
    license_or_consent: str
    retrieved_at: str
    decision: str                       # "kept" | "excluded"
    exclusion_reasons: list[str] = field(default_factory=list)
    content_hash: str | None = None
```

Sitting next to `manifest.jsonl` (one `ProvenanceRecord` per line, every document AIE-203 ever considered, kept or not) is a second file this module actually reads from: `documents.jsonl` — one `{"doc_id": ..., "text": ...}` object per line, **containing full text only for documents whose `ProvenanceRecord.decision == "kept"`.** This is a deliberate design choice, not an oversight: AIE-203-M05 already told a version of you that you would "no longer be able to see the raw sources — only this module's manifest," and the corollary is that there is no reason to keep the *text* of a document your own written consent posture said not to train on. The manifest remembers that `doc_9182` was excluded and why (`exclusion_reasons: ["pii"]`); nobody downstream needs its actual sentence ever again.

**From AIE-202-M05/M06, the architecture — with one change this module has to make itself.** M05 built and gradchecked an **encoder** block: bidirectional self-attention (every position attends to every other position, forward and backward), wrapped in `LayerNorm(x + Sublayer(x))`, stacked and fed through a mean-pool-and-readout for a toy scalar task. A pretrained LM cannot use that block unmodified, and naming why is this module's first real architectural decision, not a footnote: next-token prediction requires that token `t`'s prediction can only be a function of tokens `0..t-1` — if attention could see token `t+1` while predicting token `t`, the "prediction" would just be reading the answer off the input, and the loss would be a lie. The fix is a single addition to M05's own `scaled_dot_product_attention` — a **causal mask** that sets every score `(i, j)` with `j > i` to `-inf` before the softmax, so position `i`'s attention weights over future positions are exactly zero. Every other piece — multi-head projection, the FFN, the residual-wrapped LayerNorms — transfers unchanged. This module's `model.py` (Lesson 2) is M05's block plus one `torch.tril` mask and minus the mean-pool readout, replaced with a per-position vocabulary-sized output head.

## Lessons

### Lesson 1 — From provenance manifest to token blocks: the pretraining dataloader

#### Teaching text

A pretraining run needs one thing from all of AIE-203's careful document-level bookkeeping: a single, very long sequence of integers, chopped into fixed-length chunks, each chunk paired with the "next token" target one position ahead of it. Getting from `manifest.jsonl` + `documents.jsonl` to that sequence is four steps, and three of the four have a real, nameable failure mode if done carelessly — this lesson exists because "just concatenate the text and tokenize it" hides all three.

**Step 1 — filter to kept documents, in a stable order.** `[r for r in load_manifest("manifest.jsonl") if r.decision == "kept"]`, then join against `documents.jsonl` by `doc_id`. The order matters for reproducibility (a fixed `doc_id` sort, not dict-iteration order, which Python guarantees stable but which is easy to accidentally randomize by loading from a different source next time) but not for correctness — Step 2 destroys document order anyway, on purpose.

**Step 2 — tokenize each document, then concatenate with a reserved boundary token between documents, never within one.** Each document's own text is encoded independently (`tok.encode(text)` — a document never gets to see another document's context while itself being tokenized, since BPE merges are already frozen from M01's training run), and the resulting integer lists are concatenated into one long stream **with a boundary marker inserted between every pair of documents.** This module reuses byte value `0` (NUL) as that marker — a legal id in the base 256-byte vocabulary that real UTF-8 text essentially never contains, so no vocabulary slot needs to be added or reserved.

**Why the boundary marker is load-bearing, not decorative.** Concatenate two documents with no marker between them and the model is handed, as training data, the literal string `"...the service recovered within eleven minutes.the auth-gateway service failed with..."` — one unbroken sentence, as far as the loss function is concerned, with no signal anywhere that a new, unrelated document just started. Trained on enough of that, a model has no reason *not* to learn "an incident report's closing sentence is usually followed by the opening of a different, causally unrelated incident report" — a spurious pattern that exists only because of how the corpus was packed, not because it is true of the world the corpus describes. The boundary token gives the model something to condition on: "everything after this id is a fresh document, unrelated to what came before it," the same way `</s>`/`<s>` pairs do in every production tokenizer's special-token vocabulary.

**Step 3 — pack the boundary-marked stream into fixed-length blocks.** With `block_size = 64`, every training example is `block_size + 1 = 65` consecutive tokens: the first 64 are the model's input, the last 64 (positions `1..64`) are the target — token `t`'s target is token `t+1`, the standard next-token-prediction setup, and it is worth naming explicitly that this is the **first time** this course's transformer has ever trained on this objective. AIE-202-M05's toy task mean-pooled the whole sequence into one scalar; this module trains on a *prediction at every position*, all `block_size` of them, in parallel, from a single forward pass — `cross_entropy` computed once over a `(batch, block_size, vocab_size)` tensor of logits against a `(batch, block_size)` tensor of shifted targets.

**Step 4 — split into train and validation *before* packing, at the document level, never after.** This is the step this module's own Assessment is built to test whether you actually understood, so the reasoning is worth having cold now: if you concatenate every kept document into one stream and pack it into blocks *first*, then randomly assign 90% of the resulting **blocks** to train and 10% to val, a document longer than `block_size` can straddle the cut — part of its tokens land in a training block, the rest in a validation block. The validation loss on that split block is no longer measuring generalization to *unseen* text; it is measuring the model's ability to continue a document it partially trained on, seen from a slightly different offset. The correct order is: split whole `doc_id`s into train/val sets first (a document is entirely one or the other), *then* concatenate-and-pack each split independently. This module's own reference pipeline (Lab M02-A) does exactly this — the corpus below is small and heavily templated, so the leak this order avoids would be easy to miss by eye, which is precisely the point.

#### Worked example — measured, on the reference corpus

```
raw kept documents:  1,400
total corpus text:   344,893 characters
vocab_size (this module's reference tokenizer): 512
content tokens (all 1,400 kept documents, before packing): 91,519
mean tokens per document: 91,519 / 1,400 ≈ 65.37
```

`block_size = 64` is not an arbitrary round number — it was chosen deliberately close to the corpus's own **measured** mean document length (65.37 BPE tokens/document, only knowable after tokenizing once), so that most training blocks contain one complete incident report rather than a truncated fragment of a much longer one. A block size far smaller than the mean document length would spend most of its blocks mid-document with no coherent beginning; far larger would waste positions on padding or force many documents to share a block.

**Step 4 (split) has to happen before Step 3 (pack) actually runs, even though it's numbered after it here** — the numbering follows the order these four ideas need explaining in, not the order the code calls them in. The real call order is: filter to kept (Step 1) → split whole documents into train/val (Step 4's discipline) → pack *each split independently*, boundary markers and all (Steps 2–3), once per split:

```
documents split 90/10 by DOCUMENT (seed=0): 1,260 train docs, 140 val docs
train stream packed (block_size=64): 1,291 blocks
val stream packed (block_size=64):     138 blocks
```

#### Named misconceptions

**"AIE-203 already deduplicated the corpus, so there's nothing left to check before training starts."** AIE-203-M05's deduplication operates at the *whole-document* level — exact and near-duplicate detection between documents in the corpus. The contamination check this lesson's `pack_corpus` pipeline runs is a **different** check entirely, against a **different** reference set: AIE-204's held-out gold-set eval questions. A document can be perfectly unique in the corpus (no near-duplicate anywhere else in the 1,400 documents) and still happen to contain, verbatim or near-verbatim, the exact text of an eval prompt a later AIE-301 module will grade this model against — for instance, if the human who wrote the AIE-204 gold set lightly paraphrased a real incident report that also happens to be a training document. Deduplication and contamination-checking answer different questions ("is this document repeated within the corpus?" vs. "does this document leak an answer I'll later test against?"), and this lesson's pipeline runs the second check against the *packed training blocks*, at the substring level, independent of and after the first.

**"Picking a reserved separator token is a free, zero-risk implementation detail."** Reusing byte `0` costs nothing *if* the corpus genuinely contains no literal NUL bytes — but AIE-203's quality filters were built to catch PII, toxicity, and language, not raw control characters from a corrupted scrape that slipped past every earlier filter. If even one kept document contains a real NUL byte, this scheme silently conflates that byte with a document boundary, and the model is trained on a corpus with phantom document breaks in the middle of real content. The defensive fix is one assertion, run once at pack time: `assert all(0 not in tok.encode(text) for text in kept_texts)`, failing loudly rather than packing silently wrong data. "Reserved token" is a claim about the corpus, not just about the tokenizer, and it needs to be checked, not assumed.

### Lesson 2 — The training loop for real: schedule, clipping, checkpointing, and the init-scale trap

#### Teaching text

AIE-202-M07 built a full diagnostic harness (grad norms, activation stats) for a training loop with four *planted* defects, on a toy MLP, for eight epochs. This lesson builds the training loop those diagnostics get pointed at, and the loop itself has five real pieces, every one of which has a documented failure mode this module measures directly rather than asserts.

**The model: a decoder-only transformer, `torch.nn`, assembled from AIE-202-M05's block plus this module's causal mask (see "Before Lesson 1").** This module's reference architecture:

```
vocab_size = 512      (this module's reference ByteBPE)
block_size = 64        (context length — Lesson 1's choice, tied to mean doc length)
d_model    = 128
n_layer    = 4
n_head     = 4          (d_k = 32)
d_ff       = 512
```

```python
# model.py
import math
import torch
import torch.nn as nn
import torch.nn.functional as F


class CausalSelfAttention(nn.Module):
    def __init__(self, d_model, n_head, block_size):
        super().__init__()
        assert d_model % n_head == 0
        self.n_head = n_head
        self.d_k = d_model // n_head
        self.qkv = nn.Linear(d_model, 3 * d_model)
        self.proj = nn.Linear(d_model, d_model)
        mask = torch.tril(torch.ones(block_size, block_size)).view(1, 1, block_size, block_size)
        self.register_buffer("mask", mask)               # the one addition M05 didn't need

    def forward(self, x):
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=2)
        q = q.view(B, T, self.n_head, self.d_k).transpose(1, 2)     # (B, h, T, d_k)
        k = k.view(B, T, self.n_head, self.d_k).transpose(1, 2)
        v = v.view(B, T, self.n_head, self.d_k).transpose(1, 2)
        att = (q @ k.transpose(-2, -1)) / math.sqrt(self.d_k)
        att = att.masked_fill(self.mask[:, :, :T, :T] == 0, float("-inf"))   # causal mask
        att = F.softmax(att, dim=-1)
        out = (att @ v).transpose(1, 2).contiguous().view(B, T, C)
        return self.proj(out)


class Block(nn.Module):
    """Pre-LN: x = x + Sublayer(LN(x)) -- a CITED change from AIE-202-M05's
    Post-LN (the paper's own choice), justified by M05 Lesson 3's own
    MEASURED depth table: Post-LN's mean |grad| reaching the input SHRINKS
    with depth (0.70 at depth 4 -> 0.11 at depth 32) while Pre-LN's GROWS
    (1.20 -> 3.79) over the same range. This module trains for real, not
    just gradchecks once, so the more forgiving gradient profile is worth
    the documented tradeoff -- Pre-LN needs its own final LayerNorm after
    the last block (below), which is the price of that tradeoff."""
    def __init__(self, d_model, n_head, d_ff, block_size):
        super().__init__()
        self.ln1 = nn.LayerNorm(d_model)
        self.attn = CausalSelfAttention(d_model, n_head, block_size)
        self.ln2 = nn.LayerNorm(d_model)
        self.ffn = nn.Sequential(nn.Linear(d_model, d_ff), nn.ReLU(), nn.Linear(d_ff, d_model))

    def forward(self, x):
        x = x + self.attn(self.ln1(x))
        x = x + self.ffn(self.ln2(x))
        return x


class TinyGPT(nn.Module):
    def __init__(self, vocab_size, d_model, n_layer, n_head, d_ff, block_size):
        super().__init__()
        self.block_size = block_size
        self.tok_emb = nn.Embedding(vocab_size, d_model)
        self.pos_emb = nn.Embedding(block_size, d_model)
        self.blocks = nn.ModuleList([Block(d_model, n_head, d_ff, block_size) for _ in range(n_layer)])
        self.ln_f = nn.LayerNorm(d_model)              # Pre-LN's required final norm
        self.head = nn.Linear(d_model, vocab_size, bias=False)
        self.head.weight = self.tok_emb.weight          # weight tying
        self.apply(self._init_weights)

    @staticmethod
    def _init_weights(module):
        # See Lesson 2's init-scale worked example below for WHY this exists.
        if isinstance(module, nn.Linear):
            nn.init.normal_(module.weight, mean=0.0, std=0.02)
            if module.bias is not None:
                nn.init.zeros_(module.bias)
        elif isinstance(module, nn.Embedding):
            nn.init.normal_(module.weight, mean=0.0, std=0.02)

    def forward(self, idx, targets=None):
        B, T = idx.shape
        pos = torch.arange(T, device=idx.device)
        x = self.tok_emb(idx) + self.pos_emb(pos)[None, :, :]
        for block in self.blocks:
            x = block(x)
        x = self.ln_f(x)
        logits = self.head(x)
        loss = None
        if targets is not None:
            loss = F.cross_entropy(logits.reshape(-1, logits.size(-1)), targets.reshape(-1))
        return logits, loss


def count_params(model):
    return sum(p.numel() for p in model.parameters())
```

**Parameter count, verified by hand, not just printed.** `tok_emb`/`head` (tied): `512×128 = 65,536`. `pos_emb`: `64×128 = 8,192`. Per block: `qkv` (`128×384 + 384 = 49,536`) + `proj` (`128×128 + 128 = 16,512`) + `ffn` (`128×512+512` `+` `512×128+128` `= 66,048 + 65,664 = 131,712`) + two `LayerNorm`s (`2×(2×128) = 512`) `= 198,272` per block `× 4 layers = 793,088`. Plus `ln_f` (`256`). Total: `65,536 + 8,192 + 793,088 + 256 = 867,072` — matching this module's own measured `count_params(model)` output exactly.

**The optimizer, schedule, and clipping.** `AdamW(lr=3e-4, betas=(0.9, 0.95), weight_decay=0.01)` — `beta2=0.95` rather than PyTorch's `0.999` default is the widely-used LM-pretraining convention since the GPT-2/GPT-3-era recipes (Brown et al., 2020, "Language Models are Few-Shot Learners"), trading a shorter second-moment memory for faster adaptation to a loss landscape whose curvature changes quickly early in training. Learning rate follows a **linear warmup then cosine decay**:

```python
def lr_at(step, base_lr=3e-4, warmup_steps=100, max_steps=1200):
    if step < warmup_steps:
        return base_lr * step / warmup_steps
    progress = (step - warmup_steps) / max(1, max_steps - warmup_steps)
    return 0.5 * base_lr * (1 + math.cos(math.pi * progress))
```

Warmup exists because the model's very first gradients, computed against essentially-random weights, are large and not yet trustworthy directionally — taking a full-size step on them can push the model somewhere the rest of training has to spend many steps recovering from; ramping the learning rate up over the first 100 steps lets the optimizer's own moment estimates (`m`, `v`) stabilize before the step size reaches its peak. **Gradient clipping** (`torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)`, applied every step before `optimizer.step()`) is the training loop's direct answer to AIE-202-M07's "exploding loss" pathology family — not a diagnostic after the fact, but a guard that caps the size of any single destructive step before it happens, called on every step whether or not that step's gradient was actually large.

**Checkpointing — the whole optimizer state, not just the weights.** A checkpoint that only saves `model.state_dict()` looks complete and is not:

```python
checkpoint = {
    "step": step,
    "model_state_dict": model.state_dict(),
    "optimizer_state_dict": optimizer.state_dict(),
}
torch.save(checkpoint, f"ckpt_step{step}.pt")

# resume:
ckpt = torch.load(path)
model.load_state_dict(ckpt["model_state_dict"])
optimizer.load_state_dict(ckpt["optimizer_state_dict"])
start_step = ckpt["step"]
```

**Worked example — measured, isolating exactly this one variable.** Train to step 400 (this experiment's own reference run reaches train loss `0.2494` there — a separate, self-contained run from this lesson's other numbers, isolating one variable cleanly rather than reusing a longer log), save a full checkpoint, then continue for 30 more steps two ways, with **identical** model weights, **identical** batch order, differing in exactly one thing:

| resume method | mean loss, steps 401–405 | mean loss, steps 426–430 |
|---|---|---|
| **weights only** (`model.load_state_dict()`, fresh `AdamW`) | 0.2750 | 0.2452 |
| **full checkpoint** (weights + `optimizer.load_state_dict()`) | 0.2530 | 0.2421 |

Both branches compute the *identical* loss at step 401 (`0.2464` — same weights, same batch, no optimizer step has happened yet to diverge them), then split: the weights-only branch runs about 8.7% hotter, on average, for its first several post-resume steps, because `AdamW`'s per-parameter running mean and variance of the gradient (`m`, `v`) — the entire reason "adaptive" is in the optimizer's description — reset to zero and have to re-accumulate from scratch, during which the effective step size the optimizer takes is not the one it had converged to just before the checkpoint. By step 426–430 the two branches have mostly converged back together (`0.2452` vs. `0.2421`, about 1.3% apart, down from 8.7%), because 25–30 steps was enough runway at this toy scale for the second moment to re-stabilize. **This effect is real but modest here** — an 867K-parameter model, `lr=3e-4`, 30 steps of runway. At the scale production LM pretraining actually runs at (far larger models, learning rates chosen much closer to the edge of what the loss landscape's curvature tolerates, checkpoints spaced hours apart instead of a few dozen steps), this exact mechanism is the reason "resumed from a checkpoint" and "resumed the optimizer state" are treated as two different, non-interchangeable claims, and the industry-standard post-resume loss spike is the same story told at a scale where it isn't modest at all.

**Worked example — the initialization-scale story, measured across two full runs, identical in every other respect.** `vocab_size=512` predicts a specific, checkable number for the *very first* training loss, before a single optimizer step has meaningfully changed anything: a freshly initialized classifier with no learned signal yet should assign roughly uniform probability across all 512 possible next tokens, and cross-entropy against a uniform guess over `V` classes is `ln(V)` — here, `ln(512) ≈ 6.238`.

| step | fixed init (`std=0.02`) train loss | fixed init val loss | **default `nn.Embedding` init (`std=1.0`)** train loss | default init val loss |
|---|---|---|---|---|
| 1 | 6.2544 | 6.2563 | **127.2870** | 127.4204 |
| 20 | 6.0212 | 6.0041 | 123.4681 | 123.2128 |
| 100 | 3.6765 | 3.6439 | 11.5338 | 11.2734 |
| 400 | 0.2559 | 0.2744 | 0.5304 | 0.5804 |
| 800 | 0.2024 | 0.2371 | 0.2583 | 0.3075 |
| 1200 | 0.1805 | 0.2581 | 0.2408 | 0.2768 |

Two runs, identical model, identical data (identical document-level train/val split, Lesson 1's discipline), identical optimizer and schedule, differing in exactly one thing: whether `tok_emb`'s weight was initialized with `std=0.02` (this module's `_init_weights`, matching GPT-2's own convention) or left at PyTorch's `nn.Embedding` **default**, `N(0, 1)` — unit variance, **fifty times** wider a standard deviation (`1.0 / 0.02 = 50`). Because this model **ties** the embedding weight to the output head (`self.head.weight = self.tok_emb.weight`, the same weight matrix produces both the input representation and the output logits), a wide embedding produces wide logits from step zero, and the measured first-step loss (`127.29`) is nowhere near the `6.24` the `ln(vocab_size)` prediction assumed — roughly twenty times higher (`127.29 / 6.2544 ≈ 20.3`). Both runs eventually reach comparable final losses, but the default-init run spends its first ~100 steps mostly undoing the damage of its own initialization scale rather than learning corpus structure — visibly, in the step-100 row (`3.68` vs. `11.53`, still more than three times higher) — and is still noticeably behind by step 1200 (`0.1805` vs. `0.2408` train, the fixed-init run about a third lower).

#### Named misconceptions

**"The model's first training loss is basically noise — there's no point predicting it."** The measured table directly above refutes this: `ln(vocab_size)` is a real, checkable prediction for step 1, and the two runs' actual first-step losses (`6.26` vs. `127.37`) diverged from each other by more than 20× *before a single gradient step had meaningfully changed either model* — differing only in one weight tensor's initialization scale. If a real training run's measured first loss doesn't land within a small factor of `ln(vocab_size)`, that is not "just how training starts" — it is a checkable, diagnosable fact about your initialization or your loss computation, available for free at step 1, before you've spent any of the run's wall-clock budget finding out the hard way.

**"Reloading `model.load_state_dict()` after `torch.save(model.state_dict(), ...)` is 'resuming training,' full stop."** The resume-experiment table refutes this directly: identical weights, identical batch order, and the *only* difference (whether `AdamW`'s per-parameter moment estimates survived the checkpoint) produced a measurable, consistent gap in the first several post-resume steps (`0.2750` vs. `0.2530` mean loss, about 8.7% apart, narrowing to about 1.3% by step 426–430). "The weights are the same" and "the optimizer's state is the same" are different claims about a checkpoint, and only saving `model.state_dict()` — the common shortcut, and the one this lesson's own earlier reference run used for its sampling-only checkpoints, where it is harmless because those checkpoints are never resumed *into* — silently drops the second one.

### Lesson 3 — Reading the loss curve as diagnosis: entropy floors and the generalization gap

#### Teaching text

AIE-202-M07's four pathology families — exploding loss, silent data bug, frozen-gradient layer, normalization mistake — were each **planted**, one defect per reference run, on a toy MLP, so that a loss curve's shape could be matched to a root cause with a known answer key. This module's own training run has **no planted defect**, and its loss curve still needs reading, because a curve that looks "fine" (steadily decreasing, no NaNs, no plateaus) can still be telling you something you'd rather have caught before the model shipped: a widening gap between train and validation loss.

**The measured gap, from this module's own fixed-init reference run:**

| step | train loss | val loss | gap (val − train) |
|---|---|---|---|
| 400 | 0.2559 | 0.2744 | 0.0185 |
| 800 | 0.2024 | 0.2371 | 0.0347 |
| 1200 | 0.1805 | 0.2581 | 0.0776 |

Train loss keeps falling at every checkpoint (`0.2559 → 0.2024 → 0.1805`, monotonic). Val loss does **not** — it drops from step 400 to 800 (`0.2744 → 0.2371`) and then **rises** from 800 to 1200 (`0.2371 → 0.2581`), even as train loss keeps improving. This is not any of M07's four families — it is a fifth, genuinely different real-run signature, undramatic on purpose: **overfitting**, the model increasingly specializing to the specific 1,291 training blocks rather than the corpus's underlying template grammar, visible only by comparing two numbers side by side, never by looking at either curve alone.

**Why this corpus, at this model size, overfits by step ~800–1200 — reasoned from the corpus's own construction, not asserted.** The reference corpus is generated from a small, closed grammar: 5 templates, 5 services, 6 error types, 6 root causes, 6 fixes, with a 30% chance of a second chained incident. Even before counting the chained case, that is `5 × 5 × 6 × 6 × 6 = 5,400` distinct single-incident sentences the grammar can produce — and this corpus contains only 1,400 documents. An 867,072-parameter model has, in a very literal sense, more capacity than this corpus has genuine variety: past some point in training, the cheapest way to reduce loss further is not "understand the grammar better" but "memorize which of the 1,400 *specific* documents this training block happens to be," which does nothing for a validation block drawn from a document the model never saw during that memorization.

**A genuine, checkable floor beneath both curves — the corpus's own irreducible entropy.** Even a model that has learned the template grammar *perfectly* — every transition, every slot boundary — cannot drive loss to zero, because the grammar itself makes free, unpredictable choices at each slot (which of 5 services, which of 6 errors, etc.), and no amount of training teaches a model to predict a fair die roll. A rough estimate: one incident's free choices cost about `ln(5) + ln(5) + ln(6) + ln(6) + ln(6) ≈ 1.61 + 1.61 + 1.79 + 1.79 + 1.79 = 8.60` nats (template, service, error, cause, fix), spread across a document averaging `65.37` tokens (Lesson 1), for a back-of-envelope floor around `8.60 / 65.37 ≈ 0.13` nats/token — the *same order of magnitude* as the measured val loss plateauing around `0.26`, not an exact match. The gap between the `0.13` estimate and the `0.25` measured is itself informative, not a failure of the estimate: block packing (Lesson 1) sometimes splits a document's own free-choice slot across a document boundary within the same block's context, giving the model less of the full document to condition on than this estimate assumes, and 867K parameters over 1,200 steps has not fully closed the remaining gap to the grammar's true floor. Predicting the *order of magnitude* of a loss floor from a corpus's own generative structure, and then explaining a measured gap from that prediction, is the actual skill this lesson is teaching — not predicting the exact digit.

#### Named misconceptions

**"A healthy-looking, steadily-decreasing loss curve means the run is fine."** The train-loss curve alone, read without its validation counterpart, looks unambiguously good at every one of these three checkpoints — monotonically decreasing, no spikes, no plateau. The val-loss column is what turns "looks fine" into "is overfitting starting around step 800" — and the two numbers only exist side by side because Lesson 1's Step 4 built a genuine held-out split *before* packing. A pipeline that skips the document-level split (or worse, leaks train/val at the block level, this module's own Assessment scenario) cannot produce this diagnosis at all — it will report a val loss that agrees suspiciously well with train loss for the wrong reason, an opposite failure this lesson's Assessment is built around.

**"The loss can't be lower than zero, so eventually a well-trained model's loss will approach zero if you train it long enough."** Refuted by the entropy-floor estimate: a corpus with genuine, irreducible per-token randomness (here, which of 5 services/6 errors/6 causes/6 fixes a document happens to describe) has a *provably nonzero* loss floor for a perfect model of that corpus's grammar, not a training artifact to be optimized away. Confusing "loss isn't at zero yet" with "the model hasn't learned the pattern yet" leads to wasted training budget chasing a floor that was never reachable — the actual diagnostic question is whether the *measured* floor is in the right order of magnitude for the corpus's own structure, which is exactly the estimate this lesson built.

### Lesson 4 — Sampling from a checkpoint: temperature, top-k, and what "learned something" actually verifies

#### Teaching text

`model.generate()` turns a trained checkpoint's logits into text, one token at a time, and the two knobs that control how — **temperature** and **top-k** — are not cosmetic; they change what class of failure a small model's generations reveal.

```python
@torch.no_grad()
def generate(self, idx, max_new_tokens, temperature=1.0, top_k=None):
    for _ in range(max_new_tokens):
        idx_cond = idx[:, -self.block_size:]           # only the last block_size tokens fit
        logits, _ = self(idx_cond)
        logits = logits[:, -1, :] / temperature          # scale BEFORE softmax
        if top_k is not None:
            v, _ = torch.topk(logits, top_k)
            logits[logits < v[:, [-1]]] = float("-inf")  # zero out everything outside top-k
        probs = F.softmax(logits, dim=-1)
        next_id = torch.multinomial(probs, num_samples=1)
        idx = torch.cat([idx, next_id], dim=1)
    return idx
```

**Temperature** divides the logits before the softmax: `temperature < 1` sharpens the distribution (the already-most-likely token becomes relatively *more* likely), `temperature > 1` flattens it (closer to uniform, more surprising choices). **Top-k** truncates the candidate set to the `k` highest-logit tokens before sampling, which matters most at small model scale specifically because a small, undertrained model's probability distribution over 512 tokens often has a long, noisy tail of low-probability-but-nonzero tokens that were never meaningfully trained against; sampling from the *full* distribution at `temperature=1` lets that noisy tail occasionally get picked, derailing an otherwise-coherent generation on a single unlucky draw. This module's reference generations below use `temperature=0.8, top_k=40` — sharpened slightly, restricted to the 40 tokens the model is most confident about — a standard small-model sampling default, not this corpus's own tuned optimum.

#### Named misconceptions

**"If the exact sentence isn't in the training data, the model 'understood' something."** The verification above shows the generated sentence is novel at the full-sentence level while being built entirely from fragments (`checkout-svc` + `connection timeout`, seen together 10 times) the model was directly, repeatedly trained on. "Not verbatim in the corpus" and "demonstrates understanding beyond the corpus's own grammar" are different claims — this module's toy-scale model recombines within a closed, five-template grammar it was shown thousands of times; nothing about that recombination generalizes to a genuinely different sentence structure the corpus never demonstrated, and checking that distinction requires the corpus search above, not an impression from reading the output.

**"Sampling temperature and top-k are tuning knobs you set once and forget, like a learning rate."** Refuted by the step-100 checkpoint specifically: at `temperature=0.8, top_k=40`, a barely-trained model whose "vocabulary but not syntax" phase (above) is genuinely informative to see, at `temperature=1.0` with no top-k restriction, is far more likely to occasionally sample from that same noisy low-probability tail and produce output uninterpretable even as a diagnostic — the sampling settings change *what a given checkpoint's generation can teach you*, not just how "creative" the output looks. A checkpoint's generation quality is a function of the checkpoint *and* the sampling settings jointly; comparing generations across checkpoints with different temperature/top-k silently compares two things at once.

# lab_a_solution.py
import random

BOUNDARY = 0

def pack_corpus(kept_docs, block_size, boundary_id=BOUNDARY):
    stream = []
    for i, doc_ids in enumerate(kept_docs):
        stream.extend(doc_ids)
        if i < len(kept_docs) - 1:
            stream.append(boundary_id)
        else:
            stream.append(boundary_id)   # trailing boundary too -- harmless,
            # and keeps "a boundary always follows a document" a universal
            # rule rather than a special-cased one for the last document.
    chunk_len = block_size + 1
    n_blocks = len(stream) // chunk_len
    stream = stream[: n_blocks * chunk_len]
    return [stream[i * chunk_len:(i + 1) * chunk_len] for i in range(n_blocks)]


def split_documents(kept_docs, val_fraction=0.1, seed=0):
    idx = list(range(len(kept_docs)))
    random.Random(seed).shuffle(idx)
    n_val = max(1, int(val_fraction * len(kept_docs)))
    val_idx, train_idx = idx[:n_val], idx[n_val:]
    return [kept_docs[i] for i in train_idx], [kept_docs[i] for i in val_idx]


def contains_gold_leak(blocks, gold_texts, decode):
    hits = []
    for i, block in enumerate(blocks):
        text = decode(block)
        if any(gold in text for gold in gold_texts):
            hits.append(i)
    return hits
```

# lab_b_solution.py
import math
import torch
import torch.nn as nn

def lr_at(step, base_lr=3e-4, warmup_steps=100, max_steps=1200):
    if step < warmup_steps:
        return base_lr * step / warmup_steps
    progress = (step - warmup_steps) / max(1, max_steps - warmup_steps)
    return 0.5 * base_lr * (1 + math.cos(math.pi * progress))


def save_checkpoint(path, step, model, optimizer):
    torch.save({
        "step": step,
        "model_state_dict": model.state_dict(),
        "optimizer_state_dict": optimizer.state_dict(),
    }, path)


def load_checkpoint(path, model, optimizer):
    ckpt = torch.load(path)
    model.load_state_dict(ckpt["model_state_dict"])
    optimizer.load_state_dict(ckpt["optimizer_state_dict"])
    return ckpt["step"]


def train_step(model, optimizer, x, y, grad_clip=1.0):
    _, loss = model(x, y)
    optimizer.zero_grad()
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), grad_clip)
    optimizer.step()
    return loss.item()
```

    """Stand-in for TinyGPT -- same forward(idx, targets) contract, tiny
    enough that a full test suite runs in well under a second."""
    def __init__(self, vocab_size=16, d_model=8):
        super().__init__()
        self.emb = nn.Embedding(vocab_size, d_model)
        self.head = nn.Linear(d_model, vocab_size)

    def forward(self, idx, targets=None):
        logits = self.head(self.emb(idx))
        loss = None
        if targets is not None:
            loss = nn.functional.cross_entropy(logits.reshape(-1, logits.size(-1)), targets.reshape(-1))
        return logits, loss

def pack_and_split(kept_docs, block_size, val_fraction=0.1, seed=0):
    """Packs all kept documents into one boundary-marked stream, chops it

    val_idx, train_idx = set(idx[:n_val]), idx[n_val:]
    return [blocks[i] for i in train_idx], [blocks[i] for i in val_idx]
