## Where this module sits in the arc

Every module since M01 has ended the same way: `pytest -q` goes green, you push, CI goes green, you move on. That green bar has been quietly doing less than it looks like it's doing. It proves your **source tree**, imported with an editable install, behaves correctly on the inputs your tests chose. It has never once proven that a stranger who runs `pip install pytoolkit` gets a working package. Those are different claims, and this module is built entirely around the gap between them.

The gap exists because of a mechanism you have been relying on without naming it: `pip install -e .` does not copy your code anywhere. It writes a pointer — historically a `.pth` file, now a small import hook under PEP 660 — into your virtual environment's `site-packages`, aimed back at `src/`. Every `import pytoolkit` you have run since M01 has been satisfied by that pointer, live, against whatever bytes happen to sit in your working tree *right now*. Nothing has ever asked the question a real install answers: *if you froze this repo, ran the actual build step, and handed the result to someone with an empty machine, would it work?* A **build** — `python -m build`, producing a wheel — asks exactly that question, because a wheel is not a pointer. It is a fixed, self-contained snapshot: whatever files your build backend decided to include, and nothing else. The files you meant to include and the files that actually got included are two different lists, and until this module nothing in your pipeline has ever compared them.

This module descends into three substrates you've been standing on since M01 without examining: **environments** (what a venv actually is — an interpreter with its own `site-packages`, not a sandbox — and how `sys.path` resolves `import pytoolkit` at all), **packages** (what a build backend actually ships — a real, inspectable artifact, not "whatever's in the repo"), and **CI** (what a green pipeline actually proves — only what its steps actually exercise, and a pipeline that never builds a wheel has never tested packaging). You re-ascend commanding `pip`, `build`, and GitHub Actions as instruments whose output you can predict, not as ritual you run because that's what the last eight modules did.

The single reframe under everything: **a green build is a claim about exactly what its steps ran, and nothing else.** "It works" is not evidence unless you can say *which* artifact worked, installed *how*, verified *by what*.

By the end of M07, `pytoolkit` ships `pytoolkit/envcheck.py` (a hand-built reproducibility checker), `pytoolkit/pkgcheck.py` (a tool that inspects a *built wheel*, not the repo, for what it actually contains), a real `requirements-lock.txt`, and a two-job CI workflow where one job proves the source tree works and a second, independent job proves the **built wheel** installs and imports cleanly from outside the repo entirely. Every claim this module makes about packaging is one you will personally falsify — build something, break it on purpose, watch it break, fix it, watch the machine confirm.

### Module outcomes (what you will be able to demonstrate)

1. Explain what a virtual environment actually is (a directory with its own `site-packages` and a `pyvenv.cfg`; activation only rewrites `PATH`) and predict, from `sys.prefix` vs `sys.base_prefix`, whether a given interpreter is running inside one.
2. Explain why an editable install (`pip install -e .`) proves the source tree imports, and *why that is not the same claim* as "the package installs" — and predict, before building, whether a given file will appear inside a built wheel.
3. Read and write the packaging-relevant sections of `pyproject.toml` (`[build-system]`, `[project]` dependency specifiers, `[tool.hatch.build.targets.wheel] packages`), and state what each controls.
4. Distinguish a version *specifier* (`>=`, `~=`) from a *lock file*, explain what a lock file pins that a specifier does not (the whole dependency graph, not just top-level names), and predict a concrete way an unpinned build breaks with zero code changes on your side.
5. Read a CI workflow and state, for each job, exactly what claim its steps do and do not prove — in particular, whether it ever builds and installs the artifact it ships, or only ever runs against an editable install.
6. Ship a CI pipeline with a matrixed source-test job and an independent package-smoke-test job that builds a wheel, installs it into a clean environment, and imports it from outside the repository — green, and able to explain what would have to be true for each job to go red.

## Lessons

### Lesson 1 — What a virtual environment actually is, and how `import` finds your package

**Teaching text.**

`import pytoolkit` is not magic lookup by name. The interpreter walks a list, `sys.path`, in order — the invoking script's directory, then `PYTHONPATH` entries, then the standard library, then `site-packages` — and the first entry that has a matching directory or `.py` file wins. Everything about environments and packaging is downstream of that one list.

A **virtual environment** is not an OS-level sandbox. It is a directory (`.venv/`, conventionally) holding its own `site-packages`, a `pyvenv.cfg` file recording which system interpreter it was built from, and a copy or symlink of the interpreter itself. `python3 -m venv .venv` builds that directory. `source .venv/bin/activate` does exactly one consequential thing: it prepends `.venv/bin` to your shell's `PATH`, so typing `python` or `pip` finds the venv's copies instead of the system ones — plus it sets a `VIRTUAL_ENV` environment variable your prompt reads to remind you. That is the entire mechanism. Nothing stops you from typing the absolute path `/usr/bin/python3` inside an "activated" venv and running completely outside it; activation is a `PATH` convenience, not an enforcement boundary. This is why "I activated my venv" is not, by itself, evidence of anything — it's evidence you rewrote a shell variable.

The reason a virtual environment gives you isolation in practice is what's *inside* it: a fresh venv's `site-packages` is empty except for `pip` itself. Nothing you `pip install` in one venv touches another, and nothing you `pip install` system-wide (outside any venv) leaks in. That isolation is what makes "it works in my venv" a meaningful, reproducible claim *if and only if* you can also reproduce what got installed into it — which is exactly the problem Lesson 3 exists to solve.

`pip install -e .` (an **editable install**) is where your package meets `sys.path`. Rather than copying `src/pytoolkit/` into `site-packages`, it registers a pointer back at your working tree, so edits to your source are live without reinstalling — invaluable for development, and completely silent about whether the *build* is correct, because it never runs the build backend's file-selection logic at all.

**Worked example.**

```
$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) $ which python
/home/user/pytoolkit/.venv/bin/python
(.venv) $ python -c "import sys; print(sys.prefix); print(sys.base_prefix)"
/home/user/pytoolkit/.venv
/usr/lib/python3.12
(.venv) $ python -c "import pytoolkit"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'pytoolkit'
(.venv) $ pip install -e ".[dev]"
Obtaining file:///home/user/pytoolkit
  Installing build dependencies ... done
  ...
Successfully installed hypothesis-6.108.0 mypy-1.11.0 pytest-8.3.0 pytoolkit-0.7.0
(.venv) $ python -c "import pytoolkit.money as m; print(m.__file__)"
/home/user/pytoolkit/src/pytoolkit/money.py
```

Read that transcript as evidence, not narration. Before the install, `sys.prefix` differs from `sys.base_prefix` — proof this interpreter *is* inside a venv — and `import pytoolkit` still fails, proof that "inside a venv" and "has your package" are independent facts. After `pip install -e ".[dev]"`, the import succeeds and `m.__file__` resolves to `src/pytoolkit/money.py` — not a copy in `site-packages`, the *actual source file*. That is the pointer, made visible.

Now the trap this module spends three more lessons dismantling. If `pytoolkit` lived at the repo root (a **flat layout** — `pytoolkit/` and `tests/` as siblings) instead of under `src/`, `pytest` run from the repo root would import `pytoolkit` successfully **even with no install at all**, because pytest's default import mode inserts the test file's containing directories onto `sys.path`, and the repo root is on that path. Your tests would pass. Your package would still not be a real installable — nothing has proven it can be built and imported from anywhere else. The **`src/` layout** is not a style preference; it removes the accidental path that make this lie possible. Under `src/`, `import pytoolkit` from the repo root fails exactly like the transcript above, every time, until something — an editable install or a real one — actually registers the package. A green test suite under a `src/` layout is telling you the truth about whether the package is installed; a green test suite under a flat layout might just be telling you the repo root happens to be on `sys.path` right now.

**Named misconceptions.**

- *"Activating a venv isolates my code at the OS level."* It rewrites `PATH` (and sets `VIRTUAL_ENV`) so unqualified `python`/`pip` resolve to the venv's copies. An absolute path to another interpreter bypasses it instantly. The isolation you actually get is a *side effect* of the venv's `site-packages` being empty and separate — not enforcement by the activation step.
- *"If `import pytoolkit` works when I run `pytest` from the repo root, my package is installed correctly."* Under a flat layout it can work with **no install at all**, via pytest's own `sys.path` insertion. This is exactly why the course scaffold uses `src/` — it makes "the import works" mean "the package is actually installed," instead of "the repo root happens to be nearby."
- *"`pip install -e .` and a real install behave the same, so testing under one tells me about the other."* An editable install never runs the build backend's inclusion rules — Lesson 2's whole subject. It proves your source imports; it says nothing about what a *built* wheel would contain.
- *"`requirements.txt` and a virtual environment together are enough for reproducibility."* A venv is isolation *from other environments on this machine*; it says nothing about *which versions* got installed into it, which is a Lesson 3 problem, not a Lesson 1 one.

### Lesson 2 — A wheel is a real, inspectable artifact — not "whatever's in the repo"

**Teaching text.**

`python -m build` runs your project's declared **build backend** (`hatchling`, named in `[build-system]`) and produces two files in `dist/`: a **sdist** (`pytoolkit-0.7.0.tar.gz`, a source distribution — your source files plus build metadata, still requiring a build step at install time) and a **wheel** (`pytoolkit-0.7.0-py3-none-any.whl`, a zip of already-arranged, ready-to-install files, no build step needed). When `pip install pytoolkit` has a choice, it takes the wheel — it's strictly faster and doesn't require the recipient to have your build backend installed at all.

The load-bearing fact: **a wheel is a zip file, and you can open it with the standard library's `zipfile` module and read exactly what it contains.** Stop treating "does my package ship correctly" as a belief and start treating it as a question you can answer by listing a zip's contents. This is the same instrument shift as M06's profiler — evidence over intuition, aimed at a build instead of a runtime.

```
$ python -m build --wheel --outdir dist .
* Building wheel...
Successfully built pytoolkit-0.7.0-py3-none-any.whl
$ python -c "
import zipfile
for name in zipfile.ZipFile('dist/pytoolkit-0.7.0-py3-none-any.whl').namelist():
    print(name)
"
pytoolkit/__init__.py
pytoolkit/state.py
pytoolkit/money.py
pytoolkit/render.py
pytoolkit/result.py
pytoolkit-0.7.0.dist-info/METADATA
pytoolkit-0.7.0.dist-info/WHEEL
pytoolkit-0.7.0.dist-info/RECORD
```

Two things to notice, both load-bearing. First, the paths inside the wheel are `pytoolkit/money.py`, **not** `src/pytoolkit/money.py` — the build backend strips the `src/` prefix, because `src/` is a repository convention, not something that should exist on an installed user's `sys.path`. Second, `tests/` is nowhere in that list, and neither is `pyproject.toml`, `PREDICT.md`, or anything else at the repo root. A build backend does not ship "the repo" — it ships exactly what its configuration tells it a *package* is, and the config that answers that question is explicit:

```toml
[tool.hatch.build.targets.wheel]
packages = ["src/pytoolkit"]
```

This one line is doing all the work in the transcript above. It tells `hatchling`: "the installable package lives here, and only here." Anything outside `src/pytoolkit/` — `scripts/`, `tests/`, root-level docs — is invisible to the wheel builder by construction, regardless of what's tracked in `git`. This is a common, quiet class of packaging bug: you add a new subpackage, a new top-level script meant to ship as a console tool, or restructure a directory, and forget this line still only knows about the old shape. Your tests stay green (they run against the editable-installed source, Lesson 1), your `git status` is clean, and the artifact you'd actually publish silently doesn't contain what you think it does. Nothing in a `pytest -q` run — before this module — would ever have told you.

**Worked example.**

Deliberately break the config, and read the failure as evidence rather than guessing at it:

```toml
# pyproject.toml, deliberately mis-set
[tool.hatch.build.targets.wheel]
packages = ["src/pytoolkit_typo"]     # the real directory is src/pytoolkit
```

```
$ python -m build --wheel --outdir dist .
* Building wheel...
ERROR Cannot find any of ['src/pytoolkit_typo'] in ...
```

Hatchling refuses to build at all here — a fast, loud failure, because the *directory itself* doesn't exist. The more dangerous version of this bug is when the path resolves to something real but wrong-shaped: a `packages` list that's simply missing a *newer* subpackage that does exist. That version doesn't error — it silently ships a smaller wheel than you meant to, and the only way to catch it is to list the wheel's contents and check, which is exactly `pytoolkit/pkgcheck.py` in Lab 2.

**Named misconceptions.**

- *"If it builds without an error, it built the right thing."* `python -m build` reports success the moment it produces *a* wheel matching its config — it has no idea what you *meant* to include. A `packages` list that's real but incomplete builds cleanly and ships incompletely. "No error" and "correct contents" are different claims; only listing the wheel's contents checks the second one.
- *"Anything in my repo, or anything `pytest` can import, ships in the package."* Only what the build backend's configuration designates. `tests/`, `scripts/`, and `PREDICT.md` are real, tracked, importable-from-the-repo-root files that never appear in a correctly configured wheel — by design, not by accident.
- *"A sdist and a wheel are interchangeable, just different file extensions."* A sdist ships source and needs a build step at install time (fine for pure Python, but it means the installer needs your build backend available); a wheel is prebuilt — `pip` unpacks it directly into `site-packages`, no build step, no build-backend dependency at install time. `pip` prefers a wheel when one is offered.
- *"An editable install and a built wheel would obviously contain the same files."* An editable install never runs the packages-selection logic at all — it just points at your whole `src/` tree, whatever is or isn't correctly configured. It cannot tell you what a real build would include, because it never asked that question.

### Lesson 3 — Version specifiers are a promise; a lock file is a fact

**Teaching text.**

`pyproject.toml`'s `dependencies = ["requests>=2.31"]` is a **specifier**: an acceptable range, resolved fresh, by whatever `pip install` does *at the moment you run it*. Run that install today and you might get `requests==2.31.0`; run the identical command in six months and you might get `requests==2.35.2`, because a newer release now satisfies `>=2.31` and nothing pinned you to the older one. Both installs are "correct" by the specifier's own rule. Neither is *reproducible*, because "correct" and "identical to what I tested" are different claims, and a bare specifier only makes the first one.

A **lock file** answers a narrower, stronger question: *exactly which version of every package — including the ones you didn't ask for directly, pulled in transitively — was actually installed, the run that worked.* `pip freeze` is the simplest tool that can produce one: run inside a venv with everything installed, it prints every installed distribution as an exact `name==version` pin, transitive dependencies included.

```
$ pip freeze --exclude-editable > requirements-lock.txt
$ cat requirements-lock.txt
hypothesis==6.108.0
mypy==1.11.0
pytest==8.3.0
sortedcontainers==2.4.0
...
```

Read `--exclude-editable` carefully — it is not decoration. Without it, `pip freeze` also emits a line for *your own package*, because you installed it with `-e`:

```
-e file:///home/user/pytoolkit
```

That line has no `==` in it at all — it's a pointer, not a pin, for the same reason `pip install -e .` is a pointer and not a copy (Lesson 1). Any tool that naively parses a lock file expecting every line to be `name==version` — including the one you build in Lab 1 — will choke on that exact line if you forget the flag. This is not a hypothetical: it is the single most common way a hand-rolled lock-parsing script breaks on its first real run.

A lock file bought you something a specifier cannot: **it turns "install my dependencies" from a fresh resolution, re-run every time, into a replay of a resolution you already validated.** The gap it leaves is real too, and worth naming honestly. `pip freeze` records *what got installed*, not *cryptographic proof it's the same bytes* — a compromised package index could, in principle, serve different content under the same version string, and a plain version pin wouldn't catch it. Tools built for this (`pip-tools`'s `--generate-hashes`, `uv`'s `uv.lock`) record a hash per package alongside the version, and `pip install --require-hashes` refuses to install anything that doesn't match. This course uses `pip freeze` because it needs nothing beyond `pip` itself and teaches the *concept* — pin the whole graph, not just the top — but you should know the stronger version exists and why: a version number is a claim about *what the maintainer called it*; a hash is a claim about *what bytes you actually got*.

**Worked example — predicting a break with zero code changes.**

You wrote `dependencies = ["reportlib>=1.2"]` (a fictional stand-in — treat this as any real dependency), tested it, shipped it, and moved on. Six months later:

```
$ pip install -e ".[dev]"
Collecting reportlib>=1.2
  Downloading reportlib-2.0.0-py3-none-any.whl
...
Successfully installed reportlib-2.0.0 ...
$ pytest -q
FAILED tests/test_reports.py::test_render_summary - AttributeError:
  module 'reportlib' has no attribute 'render_summary'. Did you mean: 'render'?
```

Nothing in your repository changed. The maintainer of `reportlib` released `2.0.0` — a major version bump, which by SemVer convention *signals* a breaking change, and `render_summary` was renamed to `render` in exactly that release. Your specifier said "anything `>=1.2` is fine," and `2.0.0` technically satisfies it (`>=` doesn't cap the top). A build that was green last week is red today with a diff of zero lines in your own code. A lock file doesn't prevent the maintainer from making that change — nothing can — but it prevents *your* build from drifting into it silently: with a lock file, this install would have kept installing `reportlib==1.2.x` until a human deliberately re-ran the resolution and reviewed the diff.

**Named misconceptions.**

- *"Pinning every dependency to an exact version everywhere is always safest."* Over-pinning has its own failure mode: if two of your dependencies each demand an exact, *different* version of a shared third dependency, `pip` cannot satisfy both and the install fails outright — a dependency conflict a looser specifier would have avoided. Pinning is a tool for reproducibility of a *known-good* resolution, not a blanket policy of maximum strictness everywhere.
- *"SemVer means minor and patch upgrades are always safe to auto-accept."* SemVer is a promise the maintainer *intends* to keep, not a guarantee enforced by any tool. A lock file protects you from your own *unreviewed drift* when you didn't mean to upgrade at all — it does not protect you from a maintainer's mistake in a release you deliberately re-resolved against.
- *"`requirements-lock.txt` from `pip freeze` is a real lock file, full stop."* It pins exact versions of the whole graph — real, useful reproducibility over a bare specifier — but it has no hashes, so it doesn't defend against a package index serving different bytes under an unchanged version string. Know the gap even when you accept it for a course-scale project.
- *"Unpinned dependencies are fine because I'll notice when something breaks."* You notice when a test fails loudly, as above. You do not reliably notice a silent behavior change that no test exercises — the far more common and far more dangerous version of this exact bug.

### Lesson 4 — CI proves exactly what its steps run, and nothing else

**Teaching text.**

Every CI workflow you've pushed since M01 has had roughly this shape:

```yaml
- run: pip install -e ".[dev]"
- run: pytest -q
```

Read those two lines as a claim, precisely. They prove: *when the source tree is installed editable, on this runner, with whatever dependency versions were resolvable at this moment, the tests pass.* They do not prove: the package builds, the built wheel contains what you meant it to (Lesson 2), the dependency set is the one you validated (Lesson 3), or that any of this works on a machine that never had your repository checked out at all. "Green CI" and "the package works for a stranger who runs `pip install pytoolkit`" are different claims, and a pipeline that only ever runs an editable install has never tested the second one.

This module's CI change is not "add more steps" for its own sake — it's making the pipeline test the artifact you actually ship, not a proxy for it. Two additions do that:

**A version matrix**, so "the tests pass" means "on every Python version we claim to support," not just whichever one happens to be on the runner by default:

```yaml
strategy:
  matrix:
    python-version: ["3.12", "3.13"]
```

Each entry in the matrix multiplies out into its own full job run — two Python versions here means two independent runs of every step in that job, each on its own fresh runner. A matrix job going green on `3.12` and red on `3.13` is exactly the kind of fact an unmatrixed pipeline structurally cannot surface.

**A separate job that builds, installs, and imports the actual wheel — from outside the repository** — because that is the only sequence of steps that exercises Lesson 2's inclusion rules at all:

```yaml
package-smoke-test:
  runs-on: ubuntu-latest
  needs: test
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - run: pip install build
    - run: python -m build --wheel --outdir dist
    - run: |
        python -m venv /tmp/smoke-venv
        /tmp/smoke-venv/bin/pip install dist/*.whl
    - run: |
        cd /tmp
        /tmp/smoke-venv/bin/python "$GITHUB_WORKSPACE/scripts/smoke_test_install.py"
```

Read the last two steps as deliberately paranoid, because that's the point. `/tmp/smoke-venv` is a **fresh** venv — no `-e`, no pointer back at `src/`, built from nothing but the wheel. `cd /tmp` before running the smoke test means the repository checkout is not even the current working directory anymore, closing off any chance that an accident of `sys.path` (Lesson 1's flat-layout trap, in miniature) makes a missing file look present. If `pytoolkit.envcheck` were left out of the wheel by a `packages` misconfiguration, this is the only job in the entire pipeline that would ever notice — the `test` job, running against an editable install, imports `envcheck.py` directly off disk and would stay green regardless.

**Caching** speeds this up but is a bet, not a free lunch: `actions/setup-python`'s `cache: pip` option keys its cache to a hash of a file you name via `cache-dependency-path` — point it at `requirements-lock.txt` (Lesson 3), and a changed lock file correctly busts the cache. Point it at the wrong file, or don't set `cache-dependency-path` at all and let it default to `pyproject.toml`, and a dependency change that only touched the lock file leaves the cache key unchanged — CI keeps serving the *old* resolved packages, green, while your actual dependency set has silently drifted from what the cache is handing back. A stale cache doesn't fail loudly. It fails by *not testing what you think it's testing*, which is the exact failure mode this whole module exists to close.

**Named misconceptions.**

- *"Green CI proves my package installs correctly for users."* Only if some job actually builds and installs the artifact in isolation. A pipeline that only ever runs `pip install -e .` proves the source tree works when preinstalled editable — a real but strictly weaker claim.
- *"A matrix guarantees my package works on any machine."* It guarantees the versions and OS images you actually listed, on GitHub's runner architecture. Listing `ubuntu-latest` only says nothing about Windows; listing two Python versions says nothing about a third you didn't include.
- *"Caching can only make CI faster — it can't make CI wrong."* A cache key is a bet about which inputs matter. A key that doesn't include everything that can change your dependency set (the lock file, not just `pyproject.toml`) can serve stale packages that make a real regression invisible.
- *"If the smoke-test job is green, I don't need the matrixed source-test job (or vice versa)."* They prove different things and neither substitutes for the other: the matrix job proves your *logic* is correct across supported versions; the smoke-test job proves your *packaging* is correct at all. A regression can live in either without touching the other.

```toml
[project]
name = "pytoolkit"
version = "0.7.0"
requires-python = ">=3.12"

[project.optional-dependencies]
dev = ["pytest>=8.0", "hypothesis>=6.100", "mypy>=1.10", "build>=1.2"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/pytoolkit"]

[tool.pytest.ini_options]
testpaths = ["tests"]
markers = ["slow: marks tests as slow (build/subprocess-based; deselect with -m \"not slow\")"]

[tool.mypy]
strict = true
files = ["src/pytoolkit"]
```

Reinstall after editing: `pip install -e ".[dev]"` — this pulls in the new `build` dev dependency. You now run **three** verifiers across this module's labs: `pytest -q -m "not slow"` (fast), `pytest -q` (everything, including the build-based tests), and `mypy`.

> **The Predict step is graded.** For every lab, write your prediction **before running `python -m build`, before installing anything, before touching the venv** — as a specific, falsifiable claim ("this file will/will not appear in the wheel, because —"). A green suite with a thin `PREDICT.md` is not sufficient: the credential is the trail of what you expected the *build system itself* to do, not just what your code does.

#### Build

`src/pytoolkit/envcheck.py`:

```python
"""Environment reproducibility checks: are we in a venv, and does what's
installed match what the lock file says should be installed?"""
from __future__ import annotations

import sys
from importlib.metadata import PackageNotFoundError, version as _installed_version


def in_virtualenv() -> bool:
    """True if the running interpreter is inside a virtual environment.

    A venv's sys.prefix points at the venv directory; sys.base_prefix
    points at the system interpreter that built it. Outside any venv the
    two are identical. This is a fact about the *interpreter*, not about
    whether a shell happens to have an activated venv on its PATH.
    """
    return sys.prefix != sys.base_prefix


def parse_lockfile(path: str) -> dict[str, str]:
    """Parse a `pip freeze`-style lock file into {name: version}.

    Lines look like `pytest==8.2.0`. Blank lines and `#`-comments are
    skipped. A line with no '==' -- notably the `-e file://...` line
    `pip freeze` emits for an editable install of your OWN package -- is
    NOT a pin and raises loudly rather than being silently ignored: a
    parser that skips malformed lines quietly can hide a lock file that
    was never regenerated correctly with --exclude-editable.
    """
    pins: dict[str, str] = {}
    with open(path, encoding="utf-8") as f:
        for raw_line in f:
            line = raw_line.strip()
            if not line or line.startswith("#"):
                continue
            if "==" not in line:
                raise ValueError(
                    f"not a pinned line (no '=='): {line!r} -- "
                    "did you forget `pip freeze --exclude-editable`?"
                )
            name, _, ver = line.partition("==")
            pins[name.strip().lower()] = ver.strip()
    return pins


def installed_versions(names: list[str]) -> dict[str, str | None]:
    """Look up the installed version of each name; None if not installed."""
    result: dict[str, str | None] = {}
    for name in names:
        try:
            result[name.lower()] = _installed_version(name)
        except PackageNotFoundError:
            result[name.lower()] = None
    return result


def diff_against_lock(
    locked: dict[str, str], installed: dict[str, str | None]
) -> list[str]:
    """One human-readable line per mismatch; [] means fully reproducible.

    Three distinct kinds of drift, reported distinctly on purpose --
    "missing" and "wrong version" call for different fixes:
      MISSING  -- locked, but not installed at all
      MISMATCH -- locked, installed, but at the wrong version
      UNLOCKED -- installed, but the lock file says nothing about it
    """
    problems: list[str] = []
    for name, want in sorted(locked.items()):
        got = installed.get(name)
        if got is None:
            problems.append(f"MISSING: {name} (locked {want}, not installed)")
        elif got != want:
            problems.append(f"MISMATCH: {name} (locked {want}, installed {got})")
    for name, got in sorted(installed.items()):
        if name not in locked and got is not None:
            problems.append(f"UNLOCKED: {name} (installed {got}, not in lock)")
    return problems


def verify_environment(lockfile_path: str, names: list[str] | None = None) -> int:
    """Print any mismatches and return an exit code: 0 clean, 1 drifted.

    `names` defaults to every package the lock file itself mentions --
    pass an explicit subset to check only packages you care about.
    """
    locked = parse_lockfile(lockfile_path)
    check_names = names if names is not None else list(locked)
    installed = installed_versions(check_names)
    problems = diff_against_lock(locked, installed)
    if not problems:
        print("environment matches lock file")
        return 0
    for line in problems:
        print(line)
    return 1


if __name__ == "__main__":
    lock_path = sys.argv[1] if len(sys.argv) > 1 else "requirements-lock.txt"
    sys.exit(verify_environment(lock_path))
```

```python
"""Packaging verification: what does the BUILT WHEEL actually contain --
not the repo, not an editable install's pointer, but the fixed snapshot
the build backend produced."""
from __future__ import annotations

import zipfile
from pathlib import Path


def wheel_file_names(wheel_path: str | Path) -> list[str]:
    """List every file path stored inside a wheel. A wheel is just a zip."""
    with zipfile.ZipFile(wheel_path) as zf:
        return zf.namelist()


def wheel_contains_module(wheel_path: str | Path, dotted_module: str) -> bool:
    """True if the wheel contains the given dotted module as a .py file.

    'pytoolkit.envcheck' -> looks for 'pytoolkit/envcheck.py'.
    """
    expected = dotted_module.replace(".", "/") + ".py"
    return expected in wheel_file_names(wheel_path)


def wheel_excludes_prefix(wheel_path: str | Path, prefix: str) -> bool:
    """True if NO file inside the wheel starts with the given path prefix.

    Use to prove tests/, scripts/, or docs never ship -- a wheel should
    contain only the installable package, not the whole repository.
    """
    return not any(name.startswith(prefix) for name in wheel_file_names(wheel_path))
```

## Elle pacing notes

*Elle is the course's pacing intelligence. These notes name where learners wall, how to reroute, and which struggle is productive vs. blocked.*

**The wall (expected, productive — protect it).** The dominant wall is *"`pytest` passes, so packaging must be fine."* Every module before this one has rewarded exactly that inference, and this module is the first to punish it. When a learner first builds a wheel with a deliberately broken `packages` path and watches `pytest -q` stay perfectly green while the wheel silently ships incomplete (or fails to build at all), the disorientation is real and it is the lesson landing, not a distraction from it. **Do not preempt it by explaining editable-install pointers before they predict.** The learner who predicts "the wheel will contain `core.py`, because the tests import it fine," then lists the wheel's actual contents and finds it isn't there, has just had "green tests prove the package works" surgically corrected by evidence they generated themselves — durable in a way being told the mechanism up front never is.

**The wall that is blocked, not productive (clear it fast).** Raw environment friction: `python3 -m venv` failing because `python3-venv` isn't installed on a stripped-down Linux image, `pip install -e ".[dev]"` failing on a stale `pip` that doesn't understand PEP 660 editable hooks, `python -m build` failing because `build` wasn't actually added to `dev` extras before the reinstall, or a `PATH` that still points at a *different* venv from an earlier module. None of this teaches packaging; it burns a session on tooling archaeology. **Reroute immediately** — confirm `pip --version` is recent, confirm `pip install -e ".[dev]"` reports `build` among the installed packages before Lab 2 begins, and if a learner is 20 minutes into "why won't my venv build" rather than a packaging question, hand them the working recipe from Lesson 1's transcript and move on.

**A predictable detour: the lock-file tooling holy war.** Some learners, having heard of `pip-tools`, `uv`, `poetry`, and `pipenv`, want to relitigate which one is "correct" instead of finishing Lab 1 with plain `pip freeze --exclude-editable`. **This is a trap for the completionist**, structurally identical to M03's variance-lattice rabbit hole. The operational takeaway this module needs is not "which resolver is best" — it's "a lock file pins the *whole graph*, and hashes are the stronger version of the same idea." If a learner has spent more than ten minutes comparing lock-file tools rather than building one, redirect: the concept transfers to any of them; defer the tool comparison to whenever the learner's own project actually needs `uv`'s speed or `pip-tools`' hash enforcement.

**A second predictable detour: over-trusting the matrix.** After Lesson 4, some learners treat a green two-entry Python matrix as proof the package "works everywhere," and want to add ten more matrix entries (multiple OSes, multiple architectures) before finishing Lab 3's actual deliverable — the smoke-test job. **Do not let matrix expansion substitute for the smoke test.** The matrix and the smoke-test job prove different things (Lesson 4's closing misconception); a ten-way matrix that never builds a wheel still has zero packaging coverage. If a learner is polishing the matrix instead of writing `smoke_test_install.py`, redirect to the job that's actually still missing.

**Where reasoning quietly breaks (watch the trail, not the bars).** The dangerous learner here has a green `pytest`, a green `mypy`, a green two-job CI pipeline — and a `PREDICT.md` that never states, in their own words, what the `package-smoke-test` job proves that the `test` job doesn't. Two tells: (1) they wrote the smoke-test job by copying Lab 3's YAML without changing the working directory away from the checkout, silently reintroducing the exact accidental-import risk Lesson 1 named, and their `PREDICT.md` never flags it; (2) their lock file was generated with plain `pip freeze` (no `--exclude-editable`) and their `PREDICT.md` never mentions the resulting `-e file://...` line at all — meaning `parse_lockfile`'s loud failure was never actually exercised, just written to pass. **Both are invisible in the green bars.** If Elle sees all-green labs but a `PREDICT.md` that never names *why* the smoke test must run from outside the repo, or never mentions the editable-pointer line, route back to Lesson 1's flat-layout trap and Lesson 3's `pip freeze` gotcha before the assessment.

**Time budget reality.** 14 hours splits roughly: 3.5h across the four lessons (running the Lesson 1 `sys.prefix` transcript and the Lesson 2 wheel-listing transcript yourself, not just reading them, is non-negotiable), 2.5h Lab 1, 3h Lab 2 (the subprocess-build tests are genuinely slower than anything earlier in the course — budget for it, don't read it as something being wrong), 2.5h Lab 3, 2.5h assessment. The most common overrun is the first real `python -m build` a learner runs against their own, possibly-already-slightly-wrong `pyproject.toml` from earlier modules — treat the first clean build as a small milestone, and if CI's `package-smoke-test` job is the only thing not yet green at the 12-hour mark, accept a locally-green reproduction (`test_ci_smoke.py` passing) and let the real GitHub Actions run finish landing after the session, rather than blocking the whole module on Actions runner queue time.

## Three-tier reading — the index, the backend, and the runners you just trusted

*Subject: `pip`, PyPI, the `hatchling` build backend, and GitHub Actions — the exact infrastructure this module asked you to trust without ever asking who keeps it running.*

**Tier 1 — material ground (verifiable facts).** Every command in this module depended on infrastructure you didn't build and don't pay for directly. `pip` is maintained under the Python Packaging Authority (PyPA), a working group of largely volunteer maintainers; the Python Package Index (PyPI) — the server every `pip install` in this module talked to — is run by the Python Software Foundation, a nonprofit, and has at various points published its own funding shortfalls publicly, including grant-funded pushes specifically to build malware-scanning and typosquatting-detection into the index because the volume of uploads outpaced what volunteer review could keep up with. `hatchling`, the build backend named in every `pyproject.toml` this module used, is maintained by a small team led substantially by one maintainer's sustained, largely unpaid effort. GitHub Actions' free compute minutes for public repositories — the runners that built every wheel and ran every smoke test in Lab 3 — are provided by GitHub, a Microsoft subsidiary, at a cost Microsoft absorbs as infrastructure, not a cost you or the PSF pay. These are checkable facts: read PyPA's and PyPI's own published funding and security posts, read `hatchling`'s contributor graph, read GitHub's stated Actions pricing tiers for public vs. private repositories.

**Tier 2 — what the field suppresses (what boosters can't say and critics idealize).** The booster framing of this module's whole toolchain is "just run `pip install`" — as if the index you're pulling from is self-evidently trustworthy, self-evidently well-maintained, self-evidently going to be there next year in the same shape. What that framing suppresses is that PyPI's trustworthiness is actively, continuously produced labor: someone has to review reports of malicious packages, someone has to maintain the infrastructure that makes a billion-download-a-day service not fall over, and that someone has been, for long stretches, an underfunded nonprofit staff and a rotating set of volunteers working against a threat model — supply-chain attacks via typosquatted or hijacked packages — that scales with the ecosystem's popularity faster than its funding does. The cynic's mirror-image distortion says "corporate infrastructure like GitHub Actions is just generosity" — which suppresses that free CI minutes for public repos are also a funnel: the same platform that gives away build minutes owns the repository hosting, the issue tracker, the pull-request workflow, and increasingly the AI tooling wrapped around all of it, and "free" here means "the switching cost of leaving is also free labor you'd have to spend." Neither the pure-commons story nor the pure-cynicism story survives contact with the facts: PyPI genuinely runs on underfunded volunteer and nonprofit labor *and* GitHub genuinely subsidizes public CI *and* that subsidy is also a lock-in mechanism. Both are true at once, and the word "just" in "just push and let CI run" is doing the work of hiding both.

**Tier 3 — sit with this.** This module trained you to demand proof instead of belief: don't trust that a package installed correctly, list its contents; don't trust that a dependency is pinned, check the lock file; don't trust that CI is testing your artifact, read what its steps actually run. You now hold every third-party package you will ever `pip install` to that standard automatically, because Lesson 2 made "I assumed it shipped correctly" feel unacceptable. Point that same standard at the other side of the transaction. Your `requirements-lock.txt` freezes a maintainer's package at the exact version you validated — and then, having pinned it, you have no built-in mechanism that ever tells you when that version falls out of security support, or when the maintainer who wrote it has quietly stopped, or when the one-line bug you hit and worked around in your own code was already fixed two releases up and you never noticed because your lock file made you comfortable not looking. **You just spent a whole module learning to verify, rigorously, that the software you consume does what it claims. What is the name for a practice that applies that same rigor to whether a dependency works, but never once to whether the person who maintains it is still there, still paid, still willing — and is checking "did the build stay green" actually a substitute for checking that, or just the version of not-looking that happens to come with a passing test?**
