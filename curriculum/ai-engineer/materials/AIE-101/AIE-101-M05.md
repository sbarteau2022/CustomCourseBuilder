## Where this module sits in the arc

You have been running `git add`, `git commit`, and `git push` since M01. That is not the same as **git fluency**, and the gap is not a vocabulary gap — it is the same illusion this course keeps finding under different names. In M02 the illusion was "it runs, so it's correct." In M04 it was "it's green, so it's proven." Here it is: **"`git` is a fixed sequence of memorized incantations I run in order."** That model survives exactly until something goes wrong — a merge conflict, a rebase that doesn't want to continue, a push that gets rejected — and then it offers nothing, because it was never a model of what git *is*, only a transcript of what git *usually looks like when nothing goes wrong.*

The descent this module makes is the same one M03 made for objects: **a git repository is a small number of real, inspectable objects and a handful of files that point at them, and every porcelain command you've been running — `commit`, `merge`, `rebase`, `branch` — is sugar over reading and rewriting those objects.** A branch is not a container of commits; it is a 41-byte text file holding one SHA. `HEAD` is not an abstract "where am I"; it is almost always a *symbolic reference* — a file containing the text `ref: refs/heads/main` — that points at a branch, which points at a commit. A commit is not a diff; it is a snapshot (a tree) plus a **pointer to its parent's SHA**, which means a commit's own hash is computed *over* its parent's hash. That is the exact content-addressing idea from M03's `Money.__hash__` — a value's hash committing to its contents — applied recursively across an entire history: change any ancestor, and the hash of everything downstream changes, because every descendant's identity is partly *made of* its ancestor's identity. Once you can read `.git/refs/heads/main`, run `git cat-file -p <sha>`, and predict a SHA change before it happens, `merge` vs. `rebase` stops being "which one do I run" and becomes "which graph shape do I want, and what does each one cost."

The second half of the module ascends past the single repository into **collaboration as a craft with its own skills**: reading history to understand *why*, resolving a conflict as a judgment about which of two real edits should win (not a reflex to pick a whole side), and the review workflow — giving feedback that is specific enough to act on, taking feedback without either capitulating or digging in, and choosing a merge strategy (merge commit, squash, rebase-merge) based on what your team actually reads later, not on which one "feels more professional." By the end of this module your `pytoolkit` repo has shipped a real feature through a real branch and (for learners with a GitHub remote already live from M01) a real pull request, reviewed and merged — and it has a new module, `pytoolkit/vcs.py`, that reads git's own object graph in Python, so you can write a `pytest` test that asserts on the *shape of your own history*, not just the code inside it.

## Lessons

### Lesson 1 — A repository is objects and refs; a branch is a pointer

**Teaching text.**

Everything git stores is one of four object types, each identified by the SHA-1 (or SHA-256, on newer repos) hash of its own content: a **blob** (file contents, no name), a **tree** (a directory listing: names, modes, and the blob/tree hashes they point to), a **commit** (a tree hash, zero or more parent commit hashes, author/committer metadata, and a message), and a **tag** (a name pinned to one specific object). That's the whole vocabulary. `git add` writes blobs and updates the index; `git commit` writes a tree from the index and a commit object pointing at that tree and at the current branch tip as its parent; that's it.

A **reference** (a "ref") is a name for an object — almost always a name for a commit. Refs are not database rows; they are **files**. `refs/heads/main` is a plain text file whose entire content is one SHA. Moving the `main` branch forward by one commit is git overwriting 41 bytes in that file. `HEAD` is a ref too, but a special one: it is usually a **symbolic ref**, a file containing not a SHA but the text `ref: refs/heads/main` — one level of indirection that lets "the branch I'm on" and "the commit I'm on" both update together when you commit. Check out a specific commit instead of a branch (`git checkout <sha>`) and `HEAD` stops being symbolic and holds a SHA directly — **detached HEAD**: you are on a commit, not a branch, and a new commit here has no branch ref tracking it unless you create one.

This is why creating a branch is instant and free regardless of repository size: `git branch feature` does not copy any files or history. It reads the current value of `HEAD`, and writes that one SHA into a new file, `refs/heads/feature`. A repository with 500,000 commits and a repository with 5 commits pay the identical cost to create a branch — one small file write — because a branch was never a copy of anything.

| You run (porcelain) | What actually happens (plumbing) |
|---|---|
| `git branch feature` | write one SHA into the new file `.git/refs/heads/feature` |
| `git switch feature` | rewrite `.git/HEAD` to `ref: refs/heads/feature`, update the working tree to match that commit's tree |
| `git commit` | write a new commit object whose `parent` line is the current branch tip's SHA; move the current branch ref to the new commit's SHA |
| `git merge feature` (fast-forward possible) | move the current branch's ref forward to `feature`'s SHA — **no new object created** |
| `git merge feature` (fast-forward not possible) | write **one** new commit object with **two** `parent` lines; move the current branch ref to it |

**Merging** is where the graph shape decision lives. `git merge feature` first finds the **merge base** — the most recent commit reachable from both branches (`git merge-base main feature`) — and asks one question: is that merge base equal to the tip of the branch I'm merging *into*? If yes, every commit on `feature` already comes strictly *after* everything on `main`; there is nothing to combine, so git can simply move `main`'s pointer forward to `feature`'s tip. This is a **fast-forward**, and it creates zero new objects. If no — `main` has moved since the branches diverged — git performs a real **three-way merge**: it diffs the merge base against each tip, combines the two diffs, and writes a brand-new commit with **two parents**, recording that two lines of history joined.

**Worked example.**

```console
$ git init -q -b main && git config user.email you@x.co && git config user.name You
$ echo v1 > README.md && git add README.md && git commit -qm "Initial commit"

$ cat .git/refs/heads/main
2dcdaeafe34bd789dfb74e4894eaabf4c120badc

$ git symbolic-ref HEAD
refs/heads/main

$ git cat-file -p main            # the commit object itself, in the raw
tree 25b12f50b686ba0fbdbd20c847c3a7920edfeb22
author You <you@x.co> 1785279106 +0000
committer You <you@x.co> 1785279106 +0000

Initial commit
```

No `parent` line — this is a root commit. Now branch, advance `feature`, and inspect the parent line that appears:

```console
$ git switch -qc feature
$ echo v2 >> README.md && git commit -aqm "Feature: add v2 line"
$ echo v3 >> README.md && git commit -aqm "Feature: add v3 line"

$ git cat-file -p feature
tree e64e40922266f9b26674527c4f3c9283e60e68ac
parent d2311837042eed07c788afa6ca8d3b6b9322f6e0
author You <you@x.co> 1785279107 +0000
committer You <you@x.co> 1785279107 +0000

Feature: add v3 line

$ git merge-base main feature      # main hasn't moved -> merge base IS main's tip
2dcdaeafe34bd789dfb74e4894eaabf4c120badc
$ git rev-parse main
2dcdaeafe34bd789dfb74e4894eaabf4c120badc

$ git switch -q main
$ git merge feature
Updating 2dcdaea..1d0e01c
Fast-forward
 README.md | 2 ++
 1 file changed, 2 insertions(+)

$ git rev-parse main feature       # SAME sha -- main just moved, nothing new was created
1d0e01cea47bcf34e93538ad21f91118c6c0c351
1d0e01cea47bcf34e93538ad21f91118c6c0c351
```

`git merge-base main feature` returned exactly `main`'s own tip — the fast-forward precondition — and after the merge, `main` and `feature` point at the *identical* SHA. No merge commit exists anywhere in this history. Compare a `--no-ff` merge of the same two branches from the same starting point: git is forced to write a real merge commit, and `git cat-file -p main` afterward would show **two** `parent` lines. Lab 1 has you produce and inspect both shapes yourself.

**Named misconceptions.**

- *"A branch is a copy of the codebase, or of the commits."* It is one pointer — a 41-byte file. Nothing is duplicated when you branch; the cost is O(1) regardless of history size. What differs between branches is only *which commit each ref currently points at*, and the working tree files change only when you `switch`/`checkout` and git updates them to match that commit's tree.
- *"Merging always makes a new 'merge commit'."* Only when a fast-forward is impossible. A fast-forward merge creates **zero** new objects — it is purely a pointer move, and `git log --graph` afterward shows a single straight line, not a join, because no join was recorded.
- *"`HEAD` is just a name for 'the current branch'."* `HEAD` is a **file**, and normally a *symbolic* one pointing at the branch ref — one hop of indirection. Checking out a raw commit instead of a branch detaches `HEAD`: it now holds a SHA directly, "current branch" stops meaning anything, and a commit made here is only reachable by that SHA (and the reflog) until you attach a branch name to it.
- *"`git branch feature` and then `git checkout feature` do the same amount of work."* Creating the ref is instant (one file write); checking it out does real work proportional to how different the target tree is from your current working tree, because git has to update every file that differs.

### Lesson 2 — Rebase rewrites history; the golden rule; the reflog safety net

**Teaching text.**

M03 built the equality/hash contract into a value object by hand: `Money`'s hash was computed from its *contents*, so two `Money`s with the same cents and currency were interchangeable, and — this is the part that matters here — **an object's identity is entirely a function of what it contains.** A git commit is exactly this kind of value object, recursively: its SHA is a hash over its tree, its metadata, and **the SHA of its own parent**. That last part is the whole story of this lesson. Because a commit's hash includes its parent's hash, **you cannot change a commit's parent without changing the commit's own SHA** — and you cannot change one commit's SHA without changing the SHA of every commit that comes after it, because each of those, too, hashes its parent. History is a Merkle chain: touch any link, and every link downstream gets a new identity.

`git rebase <base>` replays your commits, one at a time, as brand-new commits whose parent is `<base>` (or the previous replayed commit) instead of their original parent. Even if the resulting diff is byte-for-byte identical to the original commit's diff, the **new commit is a different object with a different SHA**, because its parent line points somewhere new. This is why `git rebase` is described as "rewriting history": it does not edit the old commits in place — it can't; objects are immutable once written — it creates new ones and moves the branch ref to point at the new chain, leaving the old commits unreferenced by any branch (though still sitting in the object database until garbage collection).

That fact is the entire content of **the golden rule of rebase**: *never rebase commits that other people may already have based work on.* If you've pushed `feature` and a teammate has pulled it and started their own commits on top, and you then rebase `feature` and force-push, your teammate's local `feature` and the new remote `feature` no longer share a common ancestor at the tip — their next `git pull` tries to merge two histories that look unrelated at the point of divergence, typically producing a tangle of duplicate commits or a rejected push. The rule is not "rebase is dangerous"; it is "rebase is a rewrite, and a rewrite of something only you have is free, while a rewrite of something someone else has already built on is a rewrite of *their* work too, without their consent." Rebasing your own not-yet-shared commits, or a feature branch nobody else has pulled, is safe and is in fact the normal, encouraged way to clean up a branch before opening a review.

**Interactive rebase** (`git rebase -i <base>`) is the same replay mechanism with a plan you edit first: reorder commits, `reword` a message, `squash`/`fixup` one commit into the previous one, or drop a commit entirely. `--autosquash` automates the common review-feedback pattern: commit your fix with a subject starting `fixup! <exact subject of the commit it corrects>`, then `git rebase -i --autosquash <base>` finds it and folds it into the right place without you touching the interactive plan at all — the addressed-review-feedback workflow Lab 3 uses for real.

**The reflog is the safety net under all of this.** Every time `HEAD` (and, per-branch, every branch ref) moves — a commit, a checkout, a reset, a rebase step — git appends an entry to a local, per-repo log: `git reflog show HEAD` (or `git reflog show feature`). This log is **local only** (never pushed, never cloned) and by default entries expire after 90 days, but within that window, nothing a rebase or a `reset --hard` did is actually gone: the old commit objects are still sitting in the object database, unreachable from any current branch but perfectly intact, and the reflog is a list of the exact SHAs that used to be reachable. Recovery is `git reset --hard <old-sha>` or `git branch rescue-me <old-sha>` — you do not need the reflog if you captured the SHA yourself before the operation, but the reflog is what saves you when you *didn't* think to.

| Operation | New commit objects created? | Do existing SHAs change? |
|---|---|---|
| `git merge --no-ff` | one (the merge commit) | no — both input branches are untouched |
| `git merge` (fast-forward) | zero | no |
| `git rebase` | one per replayed commit | **yes** — every replayed commit gets a new SHA, even with an identical diff |
| `git commit --amend` | one (replaces the tip) | yes — the amended commit is a new object; the branch ref now points at it |
| `git cherry-pick` | one per picked commit | yes — same diff, new parent, new SHA |

**Worked example.**

```console
$ git commit -aqm "first"
$ OLD=$(git rev-parse HEAD)
$ echo more >> f.txt && git commit -aqm "first" --amend
$ NEW=$(git rev-parse HEAD)
$ [ "$OLD" = "$NEW" ] && echo same || echo different
different
```

`--amend` is the smallest possible rebase: it replaces exactly one commit, and the result is provably a *new object* — different SHA — not an edit of the old one, even though from the porcelain's point of view "you changed a commit." Now the reflog recovering a rebase you regret:

```console
$ OLD=$(git rev-parse feature)
$ git rebase main                 # rewrites feature's commits onto main
Successfully rebased and updated refs/heads/feature.
$ git rev-parse feature           # a genuinely different SHA now
80bbbcc...
$ git cat-file -p $OLD | head -1  # the OLD commit is still a real, intact object
tree 196228cf...
$ git reset --hard $OLD           # feature is back to exactly where it was
```

Nothing was deleted. The rebase moved the `feature` ref to point at new objects; the old object never stopped existing, and `git cat-file -p` on its captured SHA proves it. `git reflog show feature` would have told you the same SHA even if you hadn't written it down.

**Named misconceptions.**

- *"Rebase moves the same commits onto a new base."* It creates **new commit objects** with the same tree/diff but a different parent — and therefore a different SHA — for every commit it replays. "The same commits, relocated" is the porcelain's story; "new objects, old ones abandoned but intact" is what's actually on disk.
- *"Rebase and merge produce the same result, so it doesn't matter which I use."* The final *file contents* can match, but the **graph shape** differs (linear vs. a join with two parents), and rebase requires a force-push to publish, which is exactly the operation the golden rule is about. They are not interchangeable once anyone else has a copy of the branch.
- *"Force-pushing is always dangerous, so I should never do it."* The danger is rewriting commits someone else has already pulled. Force-pushing your **own** feature branch, before or during review, that nobody else has based work on, is normal and expected — that's what `--force-with-lease` (which refuses to overwrite the remote if it has commits you haven't seen) is *for*. The rule is about shared history, not about the flag.
- *"If `git reset --hard` or a bad rebase 'loses' my commits, they're gone."* Objects are not deleted by losing a ref to them. They remain in `.git/objects`, recoverable via the reflog or a captured SHA, until git's garbage collector eventually prunes genuinely unreachable objects — by default well after the 90-day reflog expiry window has already given you many chances to notice and recover.

### Lesson 3 — Reading history, and resolving a conflict as a judgment

**Teaching text.**

`git log` is your primary reading tool, and the flags change what question it answers: `--oneline --graph --all` shows the shape of the whole DAG at a glance; `-p` shows the actual diff each commit introduced; `--stat` shows which files and how much changed without the diff noise; `-S<string>` (the "pickaxe") finds every commit that *added or removed* a given string — the right tool for "when did this function first appear" or "when did we stop calling this API," which a plain text search across history cannot answer because it can't tell addition from deletion. `git blame <file>` annotates every line with the commit that last touched it — useful for "what was this line trying to do and why," dangerous read as "who broke this," because blame shows the most recent edit, not the original author, and a single reformat or a mechanical rename can make blame point at the wrong commit entirely unless you pass `-C`/`-M` to make it follow copies and moves. `git bisect` automates a binary search over history for the commit that introduced a regression: you mark one known-good and one known-bad commit, git checks out the midpoint, you test and report `good`/`bad`, and it narrows in `O(log n)` steps — for a thousand-commit range, about ten tests instead of a thousand.

**A merge conflict is not git detecting a bug.** It is git detecting that it **cannot algorithmically decide** which of two overlapping textual edits to keep. The three-way merge diffs the common ancestor against each side; when both sides changed the *same region* differently, there is no rule that says which change is "correct" — that is a judgment about intent, and git correctly refuses to guess. The file is left with **conflict markers**:

```
<<<<<<< HEAD
(the content on the side git calls "ours")
=======
(the content on the side git calls "theirs")
>>>>>>> <label for theirs>
```

Here is the trap that catches even experienced engineers: **which side is "ours" depends on which operation you're doing, and it flips between merge and rebase.** During a plain `git merge`, `HEAD` is the branch you're *on* (the one you're merging *into*), so `ours` = your current branch and `theirs` = the branch you named. During a **rebase**, git is replaying your commits *onto* the target one at a time; at the moment of conflict, `HEAD` is the target you're rebasing onto, so **`ours` = the base you're moving to, and `theirs` = your own commit being replayed** — the reverse of the merge case. A learner who assumes "ours always means my branch" and reaches for `git checkout --ours <file>` during a rebase conflict will silently discard *their own* change and keep the base's — exactly backwards from what they meant, and git will not warn you, because from git's point of view you asked for exactly what you got.

Resolving a conflict correctly is rarely "pick one side wholesale" — that throws away whichever side you didn't pick, even when both sides made real, wanted changes. It is normally: read both versions, understand what each one was trying to accomplish, and hand-edit the region to keep both intents (or the one that's actually still correct), then remove the markers entirely, `git add` the file, and `git commit` (to finish a merge) or `git rebase --continue` (to resume a rebase). `git merge --abort` / `git rebase --abort` back out completely if you get partway in and realize you don't yet understand the conflict well enough to resolve it — a legitimate move, not a failure.

**Worked example.** `VERSION` starts at `0.3.0`. `feature` branches off and bumps it to `0.4.0-rc1`. Meanwhile `main` bumps the *same line* to `0.4.0`. Rebasing `feature` onto `main` conflicts, because both sides changed the one line that exists relative to the shared ancestor:

```console
$ git switch feature
$ git rebase main
Auto-merging VERSION
CONFLICT (content): Merge conflict in VERSION
error: could not apply 2ac9467... VERSION: 0.4.0-rc1 (feature preview)

$ cat VERSION
<<<<<<< HEAD
0.4.0
=======
0.4.0-rc1
>>>>>>> 2ac9467 (VERSION: 0.4.0-rc1 (feature preview))
```

`HEAD` here is `main`'s value, `0.4.0` — because during this rebase, `main` is what git has already checked out as the base it's replaying onto. The reflex "ours is mine, so keep the top" would keep `0.4.0` and silently discard the feature branch's real content — which happens, in this case, to be the *wrong* call once you read both sides (a release supersedes a preview, so `0.4.0` is in fact correct here — but that is a judgment about the *meaning* of the values, not a fact `--ours` knows):

```console
$ git checkout --ours VERSION && git add VERSION && git rebase --continue
$ cat VERSION
0.4.0
$ git show 2ac9467:VERSION       # the pre-rebase feature commit still exists, still readable
0.4.0-rc1
```

The resolution happened to be right here because we independently decided the release value should win — not because `--ours` "knew" anything. Lab 2 has you resolve the same conflict by editing the file directly rather than trusting either flag, and prove the result with a test.

**Named misconceptions.**

- *"`ours` always means my branch, `theirs` always means the other one."* True for `merge`, reversed for `rebase`. During a rebase, `ours` is the commit you're rebasing *onto* and `theirs` is the commit being replayed — because a rebase is implemented as a series of merges of your commit into the new base, from the base's point of view.
- *"A merge conflict means something is broken."* It means two edits overlapped textually. Neither edit needs to be wrong; the file can be perfectly consistent after a clean, correct resolution, or subtly broken even with no conflict markers left — a conflict is a *textual* signal, not a correctness signal, and the only way to know which is to read the resolved code and run the tests against it.
- *"`git blame` tells me who is responsible for a bug."* It names the commit that most recently touched the line — which may be a reformat, a rename, or a mechanical refactor that moved correct code without changing its meaning. Use `-C`/`-M` to follow copies/moves, and treat blame as "where do I start reading," not a verdict.
- *"The safe way to resolve a conflict is to pick a whole side."* `--ours`/`--theirs` discard the *other* side's changes to that file entirely — correct only when one side is genuinely wrong start-to-finish, which is rare. Most real conflicts want a hand-merged result that keeps something from both, which is exactly what the conflict markers are showing you the raw material for.

### Lesson 4 — The review workflow: PRs, giving and taking review, and merge strategy

**Teaching text.**

A pull request is **not a git object.** Git has no concept of "PR" anywhere in its object model — no blob, tree, commit, or ref type represents one. A PR is a feature of the *platform* (GitHub, GitLab, and others each implement their own) built entirely from things git already has: two refs (a base branch and a head branch) and the diff between them, plus a database of comments, reviews, and status checks layered on top by the platform. You can see this directly: GitHub exposes every open PR as a fetchable ref, `git fetch origin pull/123/head:pr-123`, which pulls down exactly the commits on that PR's branch with no PR-specific git machinery involved at all. This matters practically: the *code* — the diff, the commit history — lives in git and would survive a platform migration intact; the *conversation* — the review comments, the approvals, the linked issues — lives in the platform's database and would not.

**Giving review** is a skill with a shape, not an instinct. A comment that says "this is wrong" or "I don't like this" gives the author nothing to act on — not what's wrong, not why, not what would fix it. A comment that names the concrete failure, cites the location, and states severity does:

> "This throws on an empty string — `s[0]` on line 12 is unguarded. `history("")` reproduces it. This should block merge; a one-line guard or an early return fixes it."

versus

> "I'd probably use a list comprehension here."

The first names a **behavior that is wrong** (a real input that crashes), locates it precisely, and states that it blocks merge. The second is a style preference with no behavioral claim behind it — worth saying, but the author should feel free to say "I like it explicit, thanks" and move on. Good review vocabulary makes this distinction explicit rather than leaving the author to guess how much a comment matters: mark comments as **blocking** ("must fix before merge — here's why") versus **nit/suggestion** ("optional, your call"). A reviewer who never marks anything as a suggestion, or never explains *why* something blocks, is not reviewing more carefully — they're making the author do the work of triage that the reviewer skipped.

**Taking review** is not the mirror of "do whatever the reviewer says," and it is not "defend every line." A blocking comment tied to a concrete, reproducible behavior (the empty-string crash above) should be fixed — that's not a negotiation, it's a bug report. A style suggestion is genuinely optional, and pushing back with a stated reason ("I kept it explicit because the comprehension version failed the `mypy --strict` inference in Lesson 4 of M03 without an extra annotation") is normal engineering conversation, not insubordination. The failure mode in both directions is real: capitulating to every nit produces code shaped by whoever commented most, not by what's correct; refusing every blocking comment because "it works on my machine" reproduces exactly the "runs but lies" failure M02 built an entire module around — except now a second person already told you where it lies, and you didn't check.

**Merge strategy** is the last decision, and it should be made on what the team reads later, not on habit. Three shapes are available once a PR is approved:

- **Merge commit** (`git merge --no-ff`) — preserves every commit on the feature branch, exactly as written, joined by one two-parent commit. History is complete and non-linear; `git log --graph` shows every branch as a visible fork-and-join. Best when the individual commits on the branch are themselves meaningful checkpoints someone will want to `git bisect` through or read individually later.
- **Squash merge** — collapses every commit on the branch into **one ordinary commit** on the base branch. Git records nothing about the fact that a merge happened at all — `describe_merge` on the result reports `"commit"`, not `"merge-commit"`, because a squash produces a single-parent commit like any other. The platform (not git) typically appends `(#123)` to the squashed commit's subject as the only trace that a PR was involved. History on the base branch stays perfectly linear and each PR is exactly one entry in `git log`; the individual WIP/fixup commits are gone from the base branch's history (though the PR page itself, and the branch if not deleted, still have them).
- **Rebase merge** — replays each commit on the branch individually onto the base, keeping per-commit granularity but with new SHAs (Lesson 2's rebase, applied at merge time) and no merge commit. Linear like squash, but preserves the branch's internal commit boundaries.

There is no universally correct choice. A team that regularly bisects and reads `git log -p` benefits from commit-level granularity (merge or rebase-merge); a team where PR-branch history is mostly noisy WIP commits benefits from squash's one-clean-entry-per-feature. The judgment to defend is the same one M03 asked for classes: not "which one is more professional," but "what does this team actually do with history later, and which shape serves that."

**Worked example.** The same feature, three ways, starting from identical branches — only the merge step differs:

Same feature, three different permanent records on `main`. Lab 3 has you produce and inspect the squash case for real, against a genuine remote.

**Named misconceptions.**

- *"A pull request is a git feature, and `git` knows what one is."* Git's object model has no PR type. A PR is entirely the platform's construction from two refs and a diff — provable by fetching it as a plain ref with no platform involved.
- *"Squash merge loses information."* It loses **commit granularity on the base branch**, not the PR itself — the platform keeps the full comment thread, review history, and (unless deleted) the original branch with every commit intact, permanently, at the PR's URL.
- *"Approving a PR means I read every line."* Approval is a **claim** you're making to every future reader of that green checkmark — exactly the M04 lesson about what a green proves, one level up. An approval given without reading manufactures false confidence for the next person who trusts it, which is worse than declining to review at all.
- *"If a reviewer leaves a comment, I should do what it says."* Only for comments tied to a concrete, reproducible behavior. A style suggestion is input to a conversation, not an order; stating your reasoning and disagreeing, when you have a reason, is the craft — not insubordination, and not the same as ignoring a real bug report.

```python
"""Small, honest wrappers around git plumbing."""
from __future__ import annotations

import subprocess
from pathlib import Path


def _git(repo: Path, *args: str) -> str:
    result = subprocess.run(
        ["git", "-C", str(repo), *args],
        capture_output=True,
        text=True,
        check=True,
    )
    return result.stdout.strip()


def sha_of(repo: Path, ref: str = "HEAD") -> str:
    return _git(repo, "rev-parse", ref)


def parent_count(repo: Path, ref: str = "HEAD") -> int:
    # "git rev-list --parents -n 1 <ref>" prints one line:
    #   "<this commit's sha> <parent1 sha> <parent2 sha> ..."
    line = _git(repo, "rev-list", "--parents", "-n", "1", ref)
    shas = line.split()
    return len(shas) - 1  # drop the commit's own sha, count what's left


def describe_merge(repo: Path, ref: str = "HEAD") -> str:
    n = parent_count(repo, ref)
    if n == 0:
        return "root"
    if n == 1:
        return "commit"
    return "merge-commit"
```

## Assessment

**Format.** A 90-minute practical, plus your three labs' `PREDICT.md` files (including the Lab 3 PR URL) and your CI-green `pytoolkit`. The practical hands you an unseen repository state — a git log, a working tree, and a short incident description — containing a **real, already-committed mistake**: a rebase that force-published over a teammate's pulled commits, or a conflict resolved by blindly picking `--ours` during a rebase and silently discarding real work. You run the full loop — **predict, locate, fix, prove** — scored on the judgment trail, not on the repository ending up in a valid state. Restoring the right content by luck or by re-typing it from memory, without demonstrating you understood *why* the mistake happened, fails the assessment even if the final `diff` looks correct.

**Gaming-resistance design.** You cannot pass by (a) fixing the working tree without correctly locating which git operation caused the loss and why, (b) recovering lost content by re-typing it instead of recovering the actual original commit via its SHA or the reflog, or (c) declaring a merge-strategy or review-severity judgment without grounding it in what the artifact is for. Each rubric row requires evidence a lucky fix cannot produce: a *pre-fix* written prediction of the mechanism, a recovery that demonstrably uses the *original* object (not a retype), and a review-severity call defended by whether the claim is reproducible and behavioral.

**The practical task (representative).** You are given a repository where `feature` was rebased and force-pushed after a teammate had already pulled it and added `9f8e7d6 "Add currency formatting"` on top of the old tip, and a second, independent scenario: a conflict in `pytoolkit/vcs.py` during a rebase that was resolved with `git checkout --ours` and clearly discarded a real bug fix (visible in the reflog).

You must: (1) **predict**, before running anything — what specifically broke for the teammate (state the golden-rule mechanism: the force-push moved `feature` to point at a chain with no common tip with what they built on), and whether the `--ours` resolution kept the fix or discarded it, and why (name which side `ours` was, for *this* operation); (2) **locate** — the exact commit where the force-push diverged, using `git log --graph --all` and the reflog, and the exact SHA of the pre-`--ours` conflicted commit whose fix was thrown away; (3) **fix** — recover the teammate's orphaned commit by cherry-picking it onto the new `feature` tip (not by re-typing `formatCurrency`'s body from memory), and recover the discarded bug fix from its original SHA via `git show <sha>:pytoolkit/vcs.py`, re-applying it correctly this time by reading both sides; (4) **prove** — with a `pytest` test (using `pytoolkit.vcs`) asserting the recovered commit is now an ancestor of `feature`'s new tip (`is_ancestor`), and a second test asserting the recovered file content matches the original fix's content, not the discarded resolution's.

### Rubric (graded on the judgment trail, not "the repo looks right")

| Dimension | Fail (0) | Developing (1) | Proficient (2) | Mastery (3) |
|---|---|---|---|---|
| **Predict (pre-run, mechanism-named)** | No written prediction, or written after fixing | States "something broke" with no named mechanism | Correctly predicts both failures (force-push over pulled work; `--ours` reversed during rebase) with the one-line mechanism for each | Both correct **and** states the general rule each instantiates (golden rule of rebase; ours/theirs reversal) in terms that would prevent a *different* incident of the same class |
| **Locate** | Points at the wrong commit or "somewhere in the history" | Finds one of the two incidents, misses the other | Finds both exact SHAs (the divergence point; the pre-`--ours` commit) using `git log --graph`/reflog | Both **and** explains why the divergence is only visible via reflog/orphaned-SHA inspection — i.e., why `git log` on the current `feature` alone cannot show it |
| **Fix** | No fix, fix breaks other history, or content re-typed from memory instead of recovered | Recovers one incident correctly; the other is re-typed or guessed | Both recovered from their **original objects** (cherry-pick; `git show <sha>:path`), not reconstructed by hand | Minimal, correct recovery for both, **plus** a one-sentence rationale for the chosen recovery mechanism over the alternatives (e.g., cherry-pick vs. re-merge) |
| **Prove** | No test, or a test that passes whether or not recovery actually happened | A test that only checks the file changed, not that it matches the *original* fix | A test using `is_ancestor`/content comparison that fails on the broken state and passes only after correct recovery | The above **plus** a test that would also have caught the *other* class of the same bug (e.g., generalizes to "any commit reachable before the force-push must still be an ancestor after recovery") |
| **Review-judgment vocabulary** | Calls every comment either universally binding or universally optional | Distinguishes blocker/nit inconsistently, or by tone rather than reproducibility | Classifies Comment A/B (Lab 3, Predict #5) correctly and states the reproducibility criterion | Applies the same criterion, unprompted, to a **novel** comment given in the practical, and correctly names which merge strategy (merge/squash/rebase-merge) fits the scenario's actual read pattern, with a stated reason |

**Passing bar:** ≥ 2 in every row, and the **Fix** row must be ≥ 2 (a working tree that looks correct but was rebuilt from memory rather than recovered from the real objects does not count — it demonstrates guessing, not the recovery mechanism). Total ≥ 12/15 with no zero rows.

**Why this resists gaming:** a submission that only "makes the repo look right" cannot produce the artifacts this rubric asks for — a pre-fix mechanism prediction (committed before you could have seen the fix work), a recovery traceable to the *original* SHA rather than a retype (checkable: does the recovered content's hash match the original commit's tree, or did you introduce a new, slightly-different diff), and a test that generalizes past the one incident shown. None of those can be backfilled after the fact by a lucky or memorized fix.

## Elle pacing notes

*Elle is the course's pacing intelligence. These notes name where learners wall, how to reroute, and when to accelerate — and which struggle is productive versus blocked.*

**The wall (expected, productive — protect it).** The dominant wall is **"but the diff is identical, why did the SHA change?"** in Lab 2, the moment a learner discovers that rebasing a commit whose *content* they didn't touch still produces a new SHA. This is the direct sequel to M03's dunder-dispatch wall and should be treated the same way: do not pre-explain the Merkle-chain mechanism before they hit it. Let them predict "same SHA, since nothing changed" (a very common, very reasonable-sounding wrong prediction), watch `git rev-parse feature` disagree, and *then* walk them to `git cat-file -p` on both the old and new commit — same tree, same message, different `parent` line, therefore different hash. The reframe — "a commit's identity includes its parent's identity, all the way back" — lands harder earned than told.

**The wall that is blocked, not productive (clear it fast).** Environment and tooling friction: `git init -b main` failing on a git older than 2.28 (defaults to `master` silently, breaking every worked example that assumes `main`); `GIT_EDITOR`/`GIT_SEQUENCE_EDITOR` not set, so an interactive rebase or a `--no-ff` merge without `-m` opens an editor the learner doesn't know how to exit (classic: stuck in `vim`); `gh` not installed or not authenticated for Lab 3's real-PR half. None of this teaches git; it burns the session on tooling. **Reroute immediately**: confirm `git --version` is ≥ 2.28, set `git config --global init.defaultBranch main` once at the start of the module, and give the exact `GIT_EDITOR=true` / `-m "..."` escape hatches *before* the first interactive command, not after someone is stuck in an editor they can't read.

**The reversed ours/theirs is the second wall, and it is a trap for confidence, not for beginners.** Learners who move fast through Lab 1 and 2 are *more* likely to reach for `--ours` on reflex in Lab 2's conflict, because it "worked" the way they expected in some past merge. **Do not accept a correct resolution here without the correct reasoning** — a learner who happens to type the right value into `VERSION` without being able to say which side `--ours` would have picked, and why that's backwards from a merge, has not cleared the wall, they've walked around it. Ask them to predict what `--ours` *would* have produced before they hand-resolve, even though they're not going to use it — the near-miss is more instructive than the correct path.

**A predictable detour: relitigating merge strategy as doctrine.** Some learners, especially those who've absorbed strong opinions from a previous job or a blog post, will argue "merge commits are always more honest" or "squash is always cleaner" as a fixed rule, mirroring M03's class-reflex detour. **Do not resolve it as a knowledge gap — make them defend it against a stated team behavior.** Ask: "this team runs `git bisect` weekly against production incidents — does squash help or hurt that?" and "this team's feature branches are 40 noisy WIP commits before review — does a merge commit help or hurt reading `git log` next year?" The reflex reveals itself once forced to answer for a concrete reading pattern instead of a general preference.

**Accelerate conditions.** A learner who (a) predicts the fast-forward/merge-commit shape correctly for both cases in Lab 1 unprompted, (b) correctly predicts the reversed ours/theirs *before* seeing the conflict in Lab 2, and (c) correctly classifies both review comments and the squash-merge parent count in Lab 3's Predict step without hesitation has cleared this module's core models. **Accelerate:** let them skip the guided walkthrough of Lab 1's `--no-ff` reproduction (they don't need to watch it to believe it) and move straight to Lab 3's real PR, then offer the stretch: set up a branch-protection rule on their published repo requiring the CI check from M03/M04 to pass **and** at least one approving review before merge is allowed — closing the loop from "green CI" as a nice-to-have (M04) to "green CI" as an actual, unbypassable gate.

**Where reasoning quietly breaks (watch the trail, not the repo state).** The dangerous submission in this module is a repository that *ends up* in the right state with a thin or absent `PREDICT.md` — a learner who fixed a force-push incident or a bad conflict resolution by trial and error, or by asking an AI assistant to "just fix the git history," without being able to state which commit diverged or why `--ours` was backwards. This is invisible in `git log --graph` looking correct. The tell: ask them to explain, without looking at the repo, what the reflog entry for the bad operation would have said, or which SHA the recovery actually pulled from. A learner who can't answer either recovered by luck, not by reading the graph — route them back to Lesson 1-2's `cat-file`/reflog worked examples before the assessment, not after.

**Time budget reality.** 12 hours splits: 4h across the four lessons (running `cat-file`, `symbolic-ref`, and the reflog by hand, live, is non-negotiable and is where the wall in Lesson 1-2 gets cleared), 2h Lab 1, 2.5h Lab 2 (the conflict-and-recovery sequence takes longer than it looks on paper — budget for at least one learner getting stuck mid-rebase and needing `git rebase --abort` walked through), 2.5h Lab 3 (real PR setup — `gh` auth, an actual reviewer or partner — is the most common overrun; if a learner has the simulated test green but no real PR by the 10-hour mark, let the real PR carry into open work time rather than blocking the module, but do not accept the simulated test as a substitute for the real artifact), 1.5h assessment.

## Three-tier reading

*Subject: the tool you just used to rewrite your own history, and the review culture you just practiced, both sit on top of unpaid and precariously-funded labor — a different layer of the same commons this course keeps returning to.*

**Tier 1 — material ground (verifiable facts).** Git itself was written by Linus Torvalds in 2005, in about ten days, after the Linux kernel project lost free access to the proprietary tool (BitKeeper) it had been using — a fact you can read directly in git's own early commit history, which git, self-referentially, still stores. Git has been maintained since by a small, named group of long-term committers; Junio Hamano has been git's release maintainer continuously since 2005, and `git shortlog -sn` on git's own source repository shows exactly who has contributed how much, by name, forever — the record is the tool. GitHub, the platform that turned git's raw branch-and-diff mechanics into the review workflow you practiced this module, is a separate, for-profit product built *on top of* the free protocol — acquired by Microsoft in 2018 for roughly $7.5 billion — and alternatives exist at every layer (GitLab, Gitea, sourcehut, or the Linux kernel's own continuing practice of reviewing patches by email with no platform at all). These are checkable facts: read git's `AUTHORS`/commit history yourself; look up the GitHub acquisition; compare what a PR actually *is* (Lesson 4) — two refs and a diff — against what the platform's UI makes it feel like.

**Tier 2 — what the field suppresses (what boosters can't say and critics idealize).** "Review culture" gets taught, including in this lesson, as a craft skill — specificity, kindness, distinguishing blockers from nits — as if the only scarce resource were technique. What that framing suppresses is that **review is unpaid labor with no natural limit**, and the maintainers of the open-source projects your `pytoolkit` already depends on (`pytest`, `hypothesis`, and everything under them) absorb an amount of it that dwarfs anything practiced in this module: a popular library's maintainer fields review requests from strangers indefinitely, is expected to be patient and pedagogical with contributors who've never read the lesson you just read, and is compensated, in the median case, not at all — while every company whose CI depends on that library extracts the value of a reviewed, working dependency for free. The booster story ("open source review makes software better") is true and says nothing about who pays for the hours. The critic's mirror-image story — that corporate involvement in open-source tooling is contamination, that the "real" community is the unpaid one — dodges the same question from the other side: unpaid is not automatically healthier, it is just differently precarious, and burnout is not evidence of purity. And the platform-capture point sits underneath both: the review culture your career will run on for the next decade lives inside a for-profit product (GitHub, owned by one company) that could change its pricing, its review tooling, or its terms at any point — "the community reviews on GitHub" quietly means "the community's review workflow is a single company's leverage point," a fact the word "community" is doing real work to obscure.

**Tier 3 — sit with this.** You just practiced giving review that is specific, evidenced, and kind, and taking review without either capitulating or digging in — a real skill, learned this module, that costs real attention to do well. The maintainers of the projects underneath your toolkit give exactly this kind of skilled, patient review to strangers, for free, indefinitely, on top of unpaid code maintenance, and a meaningful fraction of them burn out doing it — not because they lack the craft, but because the craft has no floor under it.

**You now know, specifically, what a *good* review costs to give — not "reviewing is nice," but the actual minutes of reading, the actual restraint of marking something a nit instead of a blocker, the actual patience of explaining a mechanism instead of just fixing it yourself. The next time you open a pull request against someone else's unpaid open-source project and wait for a stranger to review it with exactly that care — what, concretely, have you budgeted to give back, in the same currency you are about to ask them to spend on you?**
