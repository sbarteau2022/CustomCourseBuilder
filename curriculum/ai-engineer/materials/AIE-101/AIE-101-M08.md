## Where this module sits in the arc

Every module before this one handed you code and asked you to change it, fix it, or extend it. This module hands you code and asks you to do something quieter and, it turns out, harder: **understand it, accurately, without changing a line, against a clock.** AIE-100 taught you to read a ten-line snippet and predict what it does before you trust it. That skill does not automatically scale — a snippet fits in working memory; a 2,000-line repository does not, and the instinct that served you on ten lines ("read it top to bottom, carefully") is the instinct that fails you here, because top-to-bottom reading of everything is the slowest possible strategy and it produces a paraphrase, not a map. This module is the capstone reading skill for the whole foundation tier: **read a real, unfamiliar, 2,000-line open-source repository and produce an accurate structural map in under two hours** — assessed with the same rigor as writing code, because it is not a lesser skill than writing code. It is the skill that determines whether you can safely touch a codebase at all before you write a line in it.

The illusion this module dismantles is that "reading a codebase" means opening files in some order and absorbing them, and that a fluent-sounding summary is evidence of understanding. It is not. A summary — yours or an AI assistant's — is a claim. Lesson 4 states this as the module's central discipline: **a structural map is a set of falsifiable claims, checked against the actual code, not a paraphrase of what you skimmed.** "The entry point is `main.py`" is a claim, falsifiable by checking `pyproject.toml`. "This is the most important module" is not a claim until it's rephrased as "this module has the highest import fan-in, measured by `build_import_graph`, at N" — and then it is falsifiable, and you check it, and sometimes it's wrong. Every lab in this module produces a tool that does the checking: a static import-graph builder (Lesson 2 / Lab 1), a git-history hotspot ranker (Lesson 3 / Lab 2), and a rehearsal of the full technique against an unseen package (Lesson 4 / Lab 3), before the timed capstone exam does it for real, on a repository you have never seen, with a clock running.

**The loop under every lab is still AI-PRIMM.** Predict → Prompt → Read → Verify → Integrate. In this module the Predict step has a specific, narrow shape: **you predict structure from the outside — a README, a `pyproject.toml`, a directory listing — before you read more than one or two files of implementation.** This is not a formality. It is the actual skill. A learner who can only produce an accurate structural claim *after* reading the whole file has not yet separated "what the shape of this codebase probably is" from "what I found once I looked," and the timed exam is built specifically so that separation is what gets you through in two hours instead of running out of clock on file eleven of forty.

## Lessons

### Lesson 1 — Read outside-in: entry points, and why file order lies

**Teaching text.**

A codebase is not a stack of files to get through. It is a **call graph** — a set of functions that call other functions, rooted at one or more places execution actually begins — and the file system's ordering of that codebase (alphabetical, by directory, by file size) has no necessary relationship to that graph's shape at all. "Read top to bottom, file by file, alphabetically" is a strategy that treats a graph as if it were a list, and it is the single most common way a two-hour reading budget disappears without producing a usable map: you can spend forty minutes deeply understanding a 400-line utility module that turns out to be called from exactly one place, doing something minor, while the file that actually orchestrates the whole program sits unopened at the bottom of the alphabet.

The fix is to read **outside-in**: find where execution actually starts, and follow the calls forward from there, reading only what that path actually touches, in the order it's actually touched. Three places tell you where a Python program starts, in order of reliability:

1. **`pyproject.toml`'s `[project.scripts]` table.** A package that ships a command-line tool declares it here: `notifyhub-send = "notifyhub.cli:main"` means the string typed at a terminal, `notifyhub-send`, resolves to the function `main` inside the module `notifyhub.cli`. This is the single most reliable signal, because it is exactly what `pip install` uses to wire up the actual executable — it is not documentation of the entry point, it *is* the entry point, mechanically.
2. **A `__main__.py` at the top of a package**, which runs when the package itself is invoked with `python -m thatpackage`. By convention it is a thin adapter — import the real entry function from elsewhere, call it under `if __name__ == "__main__":` — and reading it tells you exactly one thing: which module actually holds the logic.
3. **The README's usage section**, which is documentation, not mechanism, and therefore the least reliable of the three — a stale README can describe a command that no longer exists, or omit one that does. Cross-check it against `pyproject.toml`; when they disagree, the `pyproject.toml` is telling you the truth about what actually runs, and the README is telling you what somebody meant to keep true.

Older or `setuptools`-based projects use `setup.py`'s `entry_points={"console_scripts": [...]}` instead of `[project.scripts]` — same mechanism, older syntax; look for both. Once you have the entry function, read *only* what it directly calls, then only what those calls directly call, one layer at a time — this is a breadth-first trace of the call graph, not a depth-first plunge into the first function you see, and it is what lets you stop the moment you've covered the path that matters instead of running out of clock on files the entry point never reaches.

**Worked example.**

A small package, `taskqueue/`, ships this `pyproject.toml`:

```toml
[project]
name = "taskqueue"
version = "0.1.0"

[project.scripts]
taskqueue = "taskqueue.cli:main"
```

Before opening a single implementation file, this line alone tells you: running `taskqueue add "buy milk"` at a terminal calls `taskqueue.cli.main()`. Open exactly that one file:

```python
# taskqueue/cli.py
import argparse

from .core import enqueue, run_worker


def main() -> None:
    parser = argparse.ArgumentParser(prog="taskqueue")
    sub = parser.add_subparsers(dest="command", required=True)
    sub.add_parser("worker")
    add = sub.add_parser("add")
    add.add_argument("name")

    args = parser.parse_args()
    if args.command == "add":
        enqueue(args.name)
    elif args.command == "worker":
        run_worker()
```

Reading only this file, outside-in, you now know — accurately, without opening anything else — that the package has exactly two commands (`add`, `worker`), and that both delegate immediately to two functions imported from `.core`. Your next read is not "whatever file is next alphabetically" (which would be `__init__.py`, empty, teaching you nothing); it is `core.py`, because that is where the call graph actually goes next. This is the entire technique: the file you read next is determined by the path execution takes, not by the file system's ordering of the directory.

**Named misconceptions.**

- **"The entry point is always `main.py`, or always `__main__.py`."** Neither is guaranteed, and `main.py` specifically is not a Python convention that means anything to the interpreter or to `pip` — it is a name some projects happen to choose. The only mechanically authoritative source is `[project.scripts]` (or `setup.py`'s `entry_points`); `__main__.py` exists in some packages and not others, and when it exists it may just re-export the same function `[project.scripts]` already points at.
- **"You have to read every file before you can understand any of it."** This is the belief that produces the top-to-bottom strategy, and it is false in a specific, checkable way: a function you have not opened cannot affect your understanding of a call path that never reaches it. Reading outside-in from the entry point, one call-layer at a time, covers exactly the code that matters to the program's actual behavior first, and it is what makes a two-hour budget on a 2,000-line repository survivable at all.
- **"Alphabetical or largest-file-first is as good an order as any, since you'll read it all eventually."** Under a real time budget you will not read it all, and the two-hour capstone exam is built specifically so this is true. The files a program's entry point never calls (dead code, alternate unused implementations, test fixtures, vendored copies) exist in almost every real repository, and an ordering that doesn't start from execution has no way to tell you which files those are before you've already spent the time on them.

### Lesson 2 — Reading module boundaries without running the code: the import graph

**Teaching text.**

`import` statements form a directed graph: module A imports module B means an edge A → B, and that graph — not the directory tree — is the real shape of a codebase's internal structure. You can build this graph **statically**, meaning you parse the source text into a syntax tree and read the import statements out of it, without ever executing a single line — which matters for two reasons: it works on code that's broken, has missing dependencies, or you have specific reason not to run yet, and it is fast enough to run against a whole repository in under a second.

Python's `ast` module (standard library) does this in two calls. `ast.parse(source)` turns source text into a tree of nodes. `ast.walk(tree)` visits every node in that tree, in no particular guaranteed order, including nodes nested arbitrarily deep — inside functions, inside `if` blocks, inside classes. That second fact is the one worth sitting with: **`ast.walk` does not care whether an import is "real" in the sense of always running.** An import guarded by `if TYPE_CHECKING:` (a `typing` flag that is always `False` at runtime, used purely so type checkers can see imports that would otherwise create a circular dependency) is still a syntax node, still visited, still counted as an edge. An import written *inside a function body*, deliberately placed there by whoever wrote it to break an import cycle at call time rather than at module-load time, is still a syntax node inside that function's body, still visited by `ast.walk`, still counted. A tool built on `ast.walk` reports the codebase's **textual** dependency shape — everything that is *written*, whether or not it always *runs*.

That precision has a real limit, and you should know it before you trust the tool blindly: **`from package import name` is syntactically ambiguous between "`name` is a submodule of `package`" and "`name` is an attribute defined in `package/__init__.py`."** `ast` sees the same node either way — it has no way to distinguish `from .channels import email` (where `email` is a file, `channels/email.py`) from `from .channels import some_constant` (where `some_constant` is just a name bound inside `channels/__init__.py`). A static import-graph tool built the way this lesson builds one records an edge to the *package* in both cases and cannot, from syntax alone, tell you which one it was — a real, permanent gap between "what the import statement says" and "what actually got imported," and one more reason a structural map's claims need to be checked against more than one instrument (Lessons 3 and 4 add two more).

Relative imports (`from . import x`, `from .. import y`) resolve against the *package* the importing file belongs to, not against the file itself. For a regular module `pkg.sub.mod`, that package is `pkg.sub` — one dot climbs to it, two dots climb one level further, to `pkg`. For a package's own `__init__.py` — the file that *defines* `pkg.sub` — one dot resolves *inside* `pkg.sub` itself, because the `__init__.py` file **is** the package it names, not a submodule sitting inside it. Getting this one case backwards is a genuinely easy mistake to make (and Lab 1's Predict step asks you to reason about it before you write the resolver), because it is the one place where "strip the last dotted component to find the enclosing package" — correct for every other file — is wrong.

**Worked example.**

```python
# taskqueue/core.py
from typing import TYPE_CHECKING

from .storage import load, save

if TYPE_CHECKING:
    from .models import Task          # only needed for type hints


def enqueue(name: str) -> "Task":
    ...
```

A static import extractor built with `ast.walk` reports **three** module names referenced here — `typing`, `.storage`, and `.models` — not two. The `TYPE_CHECKING`-guarded import is textually present and gets walked exactly like the unconditional one above it, even though at runtime the `if TYPE_CHECKING:` branch never executes (`TYPE_CHECKING` is `False` at runtime by design; it exists purely so tools like this one, and real type checkers, can see the import). Running the extractor's core loop by hand against this file:

```python
>>> import ast
>>> tree = ast.parse(open("taskqueue/core.py").read())
>>> modules = set()
>>> for node in ast.walk(tree):
...     if isinstance(node, ast.ImportFrom):
...         level = node.level
...         name = ("." * level + (node.module or "")) if level else node.module
...         modules.add(name)
...
>>> modules
{'typing', '.storage', '.models'}
```

Both `.storage` (imported unconditionally, at module load time) and `.models` (imported only inside the `if TYPE_CHECKING:` block, never at runtime) show up identically. A tool that only walked the module's *top-level* statements — skipping into `if` blocks — would still catch this one (it's a top-level `if`), but would silently miss a `from .util import atomic_write` written *inside a function body*, several indentation levels deep. `ast.walk`'s whole-tree traversal is what makes the difference: it finds import statements no matter how deeply nested they are, because it doesn't reason about which branches would actually execute — it just visits every node.

**Named misconceptions.**

- **"A `TYPE_CHECKING`-guarded import doesn't count — it's not a real dependency, it never runs."** It is a real *textual* dependency, and that's exactly what a static reading tool reports: what the code says, not what a particular execution path happens to do. Whether `.models` "counts" depends on the question you're asking — "does `core.py` ever construct a `Task` at runtime" is a different, narrower question than "does `core.py`'s source reference `.models` anywhere," and Lesson 2's tool answers the second one, deliberately, because that's the one you can check without ever running the code.
- **"Only imports written at the top of the file, before any function or class, are part of the module's dependencies."** A function-local import (written to defer a dependency, often specifically to break an import cycle) is just as real a textual reference as a top-level one — it will execute, and bind the name, the moment that function is called. `ast.walk`'s traversal into function bodies is precisely what catches these; a tool that only scanned top-level statements would silently under-report a codebase's real coupling.
- **"The import graph, once built, tells you *exactly* which names got imported from where — it's a complete, unambiguous picture."** It tells you which *modules* were referenced, textually. `from .channels import email` cannot be statically distinguished, by syntax alone, from a case where `email` is merely an attribute defined inside `channels/__init__.py` rather than a submodule file — both parse to the identical `ImportFrom` node. The tool built in this lesson resolves the ambiguous case to the *package*, and you should read a package-level edge as "at least this much coupling exists," not as proof of exactly which file is on the other end.

### Lesson 3 — History and tests as ground truth: churn beats size, tests beat comments

**Teaching text.**

A file's line count tells you how much text it contains. It does not tell you how much anyone has had to think about it, and those are different questions with different answers surprisingly often. `git log` gives you a second, independent signal: **how many separate commits touched this file** — its *churn*, or more precisely its **touch frequency**. A file that was written once, in one commit, and never revisited is stable — whatever complexity it has was handled correctly enough, once, that nobody has had to come back. A file that has been the target of six separate commits, even if it's tiny, is a file people keep having to return to — a bug kept resurfacing there, or a requirement kept changing, or the abstraction was wrong and got patched around instead of fixed. **Touch frequency is a much stronger "read this closely" signal than raw size**, precisely because it measures revisits, not bulk — and the two rankings frequently disagree, sharply, on real code.

`git log --name-only --pretty=format:` produces exactly the data this needs: for each commit, in order, a blank line followed by the list of file paths that commit changed. Counting how many times each path appears across the whole log gives you the touch-frequency ranking directly — no need to parse diff line counts at all, which matters, because a naive "total lines added and removed" metric has a real flaw: a single commit that writes a 200-line file **once** contributes 200 to that total, indistinguishable from 200 lines' worth of accumulated small bug fixes spread across dozens of commits. Counting *commits*, not *lines*, filters that flaw out — one big write-once commit counts once, no matter how many lines it touched.

The second ground-truth source in this lesson is closer to home: **when a docstring or comment and a test disagree about what a function does, trust the test.** A comment is prose, checked by nobody, and it rots silently the moment the code beneath it changes and the comment doesn't. A test is code, and — if your CI is doing its job, which yours has been since M01 — it is re-executed on every push and fails loudly the moment it stops matching reality. That asymmetry is the whole argument: a stale comment costs nothing to leave wrong; a stale, wrong test either gets fixed or gets *noticed* failing. Reading test names and their assertions before reading a function's docstring is often the faster and more reliable way to learn a function's actual, current contract — not because docstrings are worthless, but because only one of the two artifacts is mechanically checked.

**Worked example.**

Two files in a small package's history:

- `models.py` — written once, 200 lines, in a single commit; never touched again.
- `storage.py` — written small (2 lines, currently), and independently patched **six** separate times across its history.

`git log --name-only --pretty=format:` on this repository, fed through a touch-counter, reports `storage.py: 6` and `models.py: 1`. Raw `wc -l` reports `models.py: 200` and `storage.py: 2` — a hundredfold size gap, in the opposite direction. A learner budgeting reading time by file size would spend the bulk of it on `models.py` and skim `storage.py` in passing; a learner budgeting by touch frequency reads `storage.py` first and closely, because six independent commits against a two-line file is a loud, specific signal that something about it kept needing a human's attention — and in this case, it does: `storage.py` is the file whose `save()` function three later commits had to patch around a subtle ordering bug (below).

Now the tests-over-docstrings case, same package:

```python
# taskqueue/core.py
def run_worker() -> None:
    """Mark every pending task as done."""
    for task in load():
        if not task["done"]:
            task["done"] = True
    save(load())
```

Read only the docstring and the shape of the loop, and the natural prediction is: after `run_worker()` runs, every task on disk has `done: True`. Here is the test that actually ships with this function:

```python
def test_run_worker_docstring_claims_tasks_are_marked_done_but_they_are_not(
    tmp_path, monkeypatch
):
    monkeypatch.setattr(storage, "_PATH", tmp_path / "tasks.json")
    storage.save([{"name": "buy milk", "done": False}])

    core.run_worker()

    assert storage.load() == [{"name": "buy milk", "done": False}]
```

Run it: it **passes**, as written — meaning the task is still `done: False` on disk after `run_worker()` runs, exactly the opposite of what the docstring claims. Read the function again with that fact in hand and the bug is visible: the `for` loop iterates over one call to `load()` and mutates dictionaries in that specific returned list — but the final line calls `save(load())`, which calls `load()` **again**, fetching a second, independent, still-unmutated copy from disk, and saves *that*. The mutations made inside the loop are thrown away; nothing that happened inside it was ever persisted. A learner who trusted the docstring and moved on would carry a wrong model of this function into every later decision that depends on it. A learner who read the test first — or who, per Lesson 4, treated "this function marks tasks done" as a claim to verify rather than a fact to note — catches it in one test run.

**Named misconceptions.**

- **"A file's total lines-changed across history (`git log --numstat`, summed) is the same signal as touch frequency, just measured differently."** It is a related but meaningfully weaker signal, because a single large commit that writes a file once inflates a lines-changed total without indicating any revisiting at all. Counting *commits that touched the file* (via `--name-only`) rather than *lines changed* is what isolates "how often did humans come back to this," which is the question worth answering; a 200-line one-time write and 200 lines accumulated over forty bug-fix commits produce the same lines-changed total and utterly different touch-frequency counts.
- **"The docstring is the authoritative description of what a function does — that's what it's for."** It's what it's *for*, in the sense of stated intent, but it is not mechanically checked by anything, and this lesson's worked example is a real, reproduced case of a docstring stating something the function's own test suite disproves. Treat a docstring as a claim about intent, verify it the same way you'd verify any other claim in a structural map — against the test suite or the code itself — before you build further understanding on top of it.
- **"Reading test names and assertions is a shortcut for people who don't want to understand the real implementation — real understanding means reading the function body."** Test names and assertions describe *contract* — what the function promises, checkably, right now — which is frequently the more useful and more current fact than the implementation's internal mechanism, especially under a time budget. Reading the implementation matters too, but reading it *after* the tests, so you already know what "correct" is supposed to look like, is faster and catches exactly the class of bug this lesson's worked example demonstrates: an implementation that looks right at a glance and is not.

### Lesson 4 — Producing a structural map: skim, target, verify

**Teaching text.**

Put Lessons 1 through 3 together and you have a technique, not just three tools. **Skim** (10–15 minutes): read the README, the entry point declaration in `pyproject.toml`, and a directory listing — get every module's name and a one-sentence guess at its purpose, and nothing more. Do not open implementation files yet. **Targeted deep read** (the bulk of the budget): trace the actual call path for the program's two or three core operations, outside-in from the entry point (Lesson 1), cross-checking what you find against the import graph (Lesson 2) and the git-history ranking (Lesson 3) — you are reading the code the entry point actually reaches, in the order it reaches it, prioritized by which modules the evidence says matter. **Verify** (the last stretch, never skipped): write the map down as a set of specific, checkable claims, then go back and check two or three of them against the actual tools' output — not from memory, not because they "seem right," but because you ran the check and it agreed.

That last phase is the one a rushed reading skips, and it is the one that actually earns the word "map." **A structural map is not a summary of what you read — it is a set of falsifiable claims, checked.** "The entry point calls `cli.main`, which calls `core.send`" is a claim, and it's falsifiable by checking whether `notifyhub.cli` → `notifyhub.core` is really an edge in the import graph you built in Lab 1. "`retry.py` is structurally central" is not yet a claim — restated as "`retry.py` has the highest import fan-in in the graph, at 2, versus every other module's 0 or 1" it is one, and it's the kind of claim Lab 3's automated checker cross-verifies against the actual repository, mechanically, the same way a test asserts a fact about code rather than describing it in prose.

The map format this module uses has three parts. A **module table** — name, one-line role, LOC, fan-in — built from Lessons 2 and 3's tools directly, no guessing. An **entry-point trace** — the numbered call chain from Lesson 1, stated as a path through the import graph, not a paragraph of prose. And **verification notes** — for each non-obvious claim, which tool or command confirmed it, and what it returned. A map without verification notes is a set of assertions with no way to tell which ones are actually load-bearing versus which ones are a plausible-sounding guess that happened not to get checked — and under a time-boxed exam, the difference between those two is the entire grade.

One trap deserves naming on its own, because it is exactly the shape of Lesson 3's `run_worker` bug, generalized: **running the happy path once and watching it "work" does not verify a claim about the code's actual behavior — it verifies that one execution didn't visibly fail.** `run_worker()` runs without raising an exception, prints nothing alarming, and the docstring's claim ("marks tasks as done") *looks* consistent with a program that ran and didn't crash. Only checking the actual persisted state afterward — which is what the test does — falsifies it. A structural map claim verified only by "I ran it and it seemed fine" has the same blind spot: it says nothing about the error paths, the edge cases, or in this specific case, the exact bug that a closer check catches in seconds.

**Worked example — a structural map for `taskqueue`.**

```markdown
# Structural map: taskqueue

## Entry point
`taskqueue` (console script, pyproject.toml [project.scripts])
  -> taskqueue.cli:main
    -> taskqueue.core.enqueue      (command: add)
    -> taskqueue.core.run_worker   (command: worker)

## Module table
| module              | role                          | loc | fan-in |
|----------------------|-------------------------------|-----|--------|
| taskqueue.cli        | argparse CLI, dispatch only   |  11 |   1    |
| taskqueue.core       | enqueue/run_worker logic      |   9 |   1    |
| taskqueue.storage    | JSON load/save                |   8 |   1    |
| taskqueue.util       | atomic_write helper            |   6 |   1    |
| taskqueue.models     | Task dataclass (type-only)     |   5 |   1    |
| taskqueue.__main__   | `python -m taskqueue` adapter  |   4 |   0    |

## Verification notes
1. CLAIM: core.py imports storage AND models (models is TYPE_CHECKING-only).
   VERIFIED: build_import_graph()["taskqueue.core"] ==
   {"taskqueue.storage", "taskqueue.models"} -- both present, confirming
   the TYPE_CHECKING guard doesn't hide the edge from a static reader.
2. CLAIM: storage.py's internal import of util is function-local, not
   top-level. VERIFIED: grep -n "^import\|^from" storage.py shows only
   json/pathlib at top level; `from .util import atomic_write` is inside
   save(), confirmed by opening the file at that line.
3. CLAIM: run_worker() persists task completion to disk.
   NOT VERIFIED BY INSPECTION ALONE -- ran the existing test suite;
   test_run_worker_docstring_claims_tasks_are_marked_done_but_they_are_not
   PASSES, meaning the claim is FALSE: the loop's mutations are discarded
   because the final line calls save(load()), reloading an unmutated copy.
   Docstring is wrong; test is the ground truth. Flagged for a fix, not
   assumed correct because it "read fine."
```

Notice claim 3: the map does not report a wrong belief as fact. It reports the *checked* answer, including the case where the naive first guess (from reading the docstring) turned out false — that is what makes this a map instead of a paraphrase.

**Named misconceptions.**

- **"Reading every file top to bottom is the thorough way to build a map, even if it's the slow way."** Thoroughness here is properly measured by call-path coverage — how much of what the program actually does you can accurately describe — not by files opened. A map built by tracing every path the entry point reaches, verified, covers the parts of the codebase that matter to its actual behavior; reading every file including ones the entry point never calls covers more *text* while covering the same or less *behavior*, for far more time spent.
- **"A structural map is a summary — write down what you understood, in your own words, and that's the deliverable."** A summary and a map differ in exactly one load-bearing way: a map's claims are checked against the code, mechanically, and a summary's aren't. "I understood X" is not evidence X is true; "I checked X against the import graph / the test suite / a grep, and it held" is. Lab 3's checker exists specifically because a fluent, confident, wrong summary is indistinguishable from a fluent, confident, correct one until something verifies it.
- **"If I ran the program on its main path and it worked, my map's claims about that code are confirmed."** One successful run confirms that one execution didn't visibly fail — it says nothing about error paths, unreached branches, or (as in the `run_worker` case) about whether the visible "success" is actually doing what it looks like it's doing. `run_worker()` runs cleanly, prints nothing wrong, and still doesn't persist anything; the only thing that catches this is checking the *actual resulting state*, not just watching the run not crash.

Solution:

```python
"""Static import extraction and per-package import-graph construction.

Everything here is *static*: it parses source text with `ast`, it never
imports or executes the code it's reading. That's the point -- you can map
an unfamiliar (possibly broken, possibly untrusted) codebase without running
a single line of it.
"""
from __future__ import annotations

import ast
from pathlib import Path


def extract_imports(source: str) -> set[str]:
    """Return the set of module names imported anywhere in `source`.

    Captures `import x` and `import x.y as z` (recorded as top-level "x"),
    `from x.y import z` (recorded as top-level "x"), and relative imports
    `from . import y` / `from .mod import y` (recorded with their leading
    dots intact, e.g. "." or ".mod", for the caller to resolve).

    Walks the *entire* tree with ast.walk, not just the module's top level,
    so imports inside functions/methods and inside `if TYPE_CHECKING:`
    blocks are all captured -- they are still syntax nodes, even though one
    only runs conditionally and the other only runs to avoid a circular
    import at call time.
    """
    tree = ast.parse(source)
    modules: set[str] = set()
    for node in ast.walk(tree):
        if isinstance(node, ast.Import):
            for alias in node.names:
                modules.add(alias.name.split(".")[0])
        elif isinstance(node, ast.ImportFrom):
            if node.level and node.level > 0:
                modules.add("." * node.level + (node.module or ""))
            elif node.module:
                modules.add(node.module.split(".")[0])
    return modules


def build_import_graph(root: Path) -> dict[str, set[str]]:
    """Map each `.py` file under `root` (as a dotted module name) to the set
    of *internal* modules it imports. Third-party and stdlib imports are
    dropped -- this graph is for reading this codebase's own shape, not its
    external dependencies.
    """
    root = Path(root)
    py_files = sorted(p for p in root.rglob("*.py"))
    module_names = {_module_name(root, p) for p in py_files}

    graph: dict[str, set[str]] = {}
    for path in py_files:
        name = _module_name(root, path)
        # The package a relative import resolves against: for a package's
        # own __init__.py, that's the package itself (level-1 "from . import
        # x" inside pkg/__init__.py means pkg.x); for any other module, it's
        # everything but that module's own last dotted component.
        package = name if path.name == "__init__.py" else name.rsplit(".", 1)[0]
        imported = extract_imports(path.read_text())
        internal = {
            resolved
            for imp in imported
            if (resolved := _resolve(imp, package, module_names)) is not None
        }
        graph[name] = internal
    return graph


def _module_name(root: Path, path: Path) -> str:
    rel = path.relative_to(root).with_suffix("")
    parts = list(rel.parts)
    if parts and parts[-1] == "__init__":
        parts = parts[:-1]
    return ".".join([root.name, *parts]) if parts else root.name


def _resolve(imp: str, package: str, known: set[str]) -> str | None:
    """Resolve one raw import name to an internal module name, or None if
    it isn't part of this codebase (stdlib/third-party).

    `package` is the dotted name of the package a relative import in this
    file resolves against -- the importing module itself, if it's a
    package's `__init__.py`, otherwise the importing module minus its own
    last component. Level-1 ("from . import x") resolves inside `package`
    directly; each extra dot climbs one more level up `package`'s parents.
    """
    if imp.startswith("."):
        level = len(imp) - len(imp.lstrip("."))
        rest = imp[level:]  # text after the leading dots, may be ""
        pkg_parts = package.split(".") if package else []
        climb = level - 1  # level 1 = stay in `package`; each extra dot climbs one
        base = pkg_parts[: len(pkg_parts) - climb] if climb else pkg_parts
        target = ".".join([*base, rest] if rest else base)
        return _match(target, known)
    return _match(imp, known)


def _match(name: str, known: set[str]) -> str | None:
    if name in known:
        return name
    for candidate in known:
        if name.startswith(candidate + "."):
            return candidate
    return None
```

Solution:

```python
"""Git-history-informed reading: where has this codebase actually been
*revisited*, as opposed to where it merely has a lot of lines.

The metric here is **commit-touch frequency** -- the number of separate
commits that changed a given file -- not total lines added/removed. A
single big commit that writes a 200-line file once inflates a
lines-changed total without indicating anything about how often humans
had to come back and think about that file again. Several small bug-fix
commits against a two-line file are a stronger "read this closely" signal
than one large commit that wrote a stable file a single time.
"""
from __future__ import annotations

from pathlib import Path


def parse_touches(output: str) -> dict[str, int]:
    """Parse the output of `git log --name-only --pretty=format:` into a
    per-path count of how many separate commits touched it.

    `git log --name-only` prints, for each commit, a blank line followed by
    the list of paths that commit changed (merge commits with no file
    changes print nothing for that commit). Every non-blank line is a
    path; blank lines are the commit separators and are skipped.
    """
    touches: dict[str, int] = {}
    for line in output.splitlines():
        path = line.strip()
        if not path:
            continue
        touches[path] = touches.get(path, 0) + 1
    return touches


def count_loc(root: Path) -> dict[str, int]:
    """Map each `.py` file under `root` (path relative to root, as a
    string with forward slashes) to its line count. A raw-size
    measurement, deliberately naive, so it can be compared against
    `parse_touches`'s frequency counts.
    """
    root = Path(root)
    loc: dict[str, int] = {}
    for path in sorted(root.rglob("*.py")):
        rel = path.relative_to(root).as_posix()
        loc[rel] = len(path.read_text().splitlines())
    return loc


def rank_hotspots(
    touches: dict[str, int], loc: dict[str, int]
) -> list[tuple[str, int, int]]:
    """Return (path, touch_count, loc) triples for every path in
    `touches`, sorted by touch_count descending -- the most-revisited
    file first, regardless of its size. Paths with no LOC entry (e.g.
    deleted since) are reported with loc=0.
    """
    return sorted(
        ((path, count, loc.get(path, 0)) for path, count in touches.items()),
        key=lambda row: row[1],
        reverse=True,
    )
```

## Assessment

**Format.** A 2-hour timed practical: you are handed a real, unseen open-source Python repository (grader-selected, roughly 2,000 lines, a single-purpose library or tool — never discussed or previewed in this module) with its full git history intact. At the 2-hour mark you submit `PREDICT.md`, `STRUCTURAL_MAP.md`, and `claims.json` (same schema discipline as Lab 3, extended: entry-point chain, top-3 modules by fan-in, top-3 modules by touch frequency, and at least one explicit "looks important but isn't, or looks unimportant but is central" claim). Immediately after, a 20-minute oral defense.

**Gaming-resistance design.** You cannot pass by (a) reading every file top to bottom and writing a fluent paraphrase — the two-hour clock on ~2,000 unfamiliar lines punishes exactly that strategy, and `claims.json` must still pass its automated checker regardless of how well the prose reads; (b) asking an AI assistant to summarize the repository and transcribing its output as your map — every `claims.json` entry must be reproducible on demand from a specific tool run or `git`/`grep` command, and the oral defense picks claims at random and asks you to reproduce the exact evidence, live, which a transcribed-but-unverified summary cannot survive; (c) submitting plausible-sounding claims without running the checker against them — `claims.json` is graded by the same class of automated cross-check as Lab 3's, so an unverified guess fails mechanically the moment it's checked, independent of how convincing it sounds.

**The practical task.** In order, and the order is graded: (1) **Predict** — from the README, `pyproject.toml` (or `setup.py`), and a directory listing alone, before opening more than one or two files — the entry-point call chain, and a hypothesis for whether the highest-fan-in module and the largest-by-LOC module will be the same module or different ones; (2) **Build the map** — run your Lab 1/2 tools (extending them if this repository's shape needs it — a namespace package, an older `setup.py`-style entry point) to generate the import graph and the touch-frequency ranking, then write `STRUCTURAL_MAP.md` and `claims.json`; (3) commit both, with `PREDICT.md`, at the 2-hour mark, whatever state they're in; (4) the **20-minute oral defense** — the grader selects three entries from your `claims.json` and asks you to reproduce, live and cold, the exact command or tool output that verifies each one.

Both together close the gap a written-report-only assessment would leave open: it is entirely possible to write a fluent, wrong structural summary of an unfamiliar repository, and this assessment is built so that fluency alone does not clear either gate.

## Elle pacing notes

**Walls (expected stall points, with reroutes):**

- **Wall: "I'll just read it top to bottom, file by file — I'll get through it."** Symptom: faced with an unfamiliar package for the first time (Lab 3, or the timed capstone), the learner opens `__init__.py`, then the next file alphabetically, working through the directory in file-system order rather than tracing from the entry point. This is the module's single most tempting default, because it's how every earlier module's smaller code samples were, in fact, read — nothing before this module punished it. **Reroute:** run a visible stopwatch. Time how far top-to-bottom reading gets in 15 minutes against how far an entry-point trace plus import graph gets in the same 15 minutes on the same unfamiliar package. The gap is usually dramatic and self-evident; let the clock make the argument instead of arguing abstractly for outside-in reading.

- **Wall: "the biggest file has to be the most important one — look how much is in it."** Symptom: in Lab 3, faced with `legacy_formatters.py` dwarfing every other file in the directory listing, the learner's structural prediction assumes it's central before checking, and is reluctant to trust the fan-in count of **0** once the tool reports it — rereading the file looking for the import they're sure must exist somewhere. This is the wall Lab 3 is specifically built to hit; **treat it as the target experience, not a mistake to prevent.** The surprise that the file everyone's eye goes to first is structurally disconnected is Lesson 4's central claim, landed by a wrong guess corrected by the checker, not by being told the answer up front.

- **Wall: "the docstring says what it does, why do I need to check the test too?"** Symptom: in Lesson 3's worked example or an analogous case in the timed capstone, the learner reads a clearly written docstring, accepts it, and moves on without running or reading the corresponding test. This is real signal worth taking seriously — most docstrings in most real code are, in fact, accurate — but the module's outcome is the discipline of checking, not a claim that docstrings are usually wrong. **Reroute:** have them predict, in writing, what `run_worker`'s test asserts, *before* reading it. If their prediction (task ends up `done: True`) is wrong, the disagreement between "what the docstring says" and "what the test proves" is the whole lesson, landed by their own wrong prediction, not a lecture about trusting comments less.

- **Wall: "my map sounds right, I'm done."** Symptom: `STRUCTURAL_MAP.md` reads fluently, is organized, uses the right vocabulary — and `claims.json` was never actually run against the checker before being called finished. This is the most dangerous wall because it is invisible without checking: a confident, well-written, wrong map and a confident, well-written, correct map look identical until the automated checker runs. **Reroute, firmly:** "done" is defined operationally in this module as "the checker passed," not as "I'm confident in what I wrote." Make running `pytest tests/test_structural_map_claims.py` (or its capstone equivalent) a hard gate before a learner is allowed to call a lab finished, the same way M06 made a debugger transcript a hard gate before a fix could be considered proven.

**Signals (struggle that is the lesson landing — do NOT reroute):**

- **Hesitating to write a claim into `claims.json` until it's actually been reproduced, even for something that "obviously" seems true.** That hesitation — refusing to assert a fact about the codebase without having generated the check for it first — is exactly the discipline this module is building. Encourage it; do not rush a learner past double-checking something they're already fairly sure of, because the habit of checking things you're *sure* of is the harder and more valuable half of this skill.

- **Re-running the checker a second time after it already passed, "just to be sure."** This is the evidence-first reflex from M06 (debugger/profiler before trusting a fix) correctly transferring to a new domain. It costs a few seconds and it is not wasted time.

**Accelerate conditions (skip/compress when earned):**

**Do NOT accelerate past** the requirement that every `claims.json` entry — in Lab 3 and in the timed capstone alike — pass the automated checker before a map is considered done, regardless of how fast or confident a learner is. ## Three-tier reading — the repositories you can now read, and the people who wrote them

*Subject: static reading tools, `git` history, and the human structure — often just one or two unpaid people — underneath the codebases this module just taught you to map in two hours.*

**Tier 1 — Material ground (verifiable facts).** Every tool this module built is standard library plus `git` itself: `ast.parse`/`ast.walk`, `pathlib`, and one `git log` invocation — no install, shipped with every CPython release and every `git` install this course has used since M01. Every number in this module's worked examples was measured, not estimated: `extract_imports` run against the `TYPE_CHECKING`-plus-function-local-import sample returned exactly `{"typing", ".models", ".util"}` — both the conditionally-executed and the deeply-nested import captured identically to a top-level one. The churn worked example's demo repository, built fresh by `scripts/build_demo_repo.py`, measured `storage.py` touched by **6** separate commits at a final size of **2** lines, against `models.py` touched by **1** commit at **200** lines — a hundredfold size gap with the revision-frequency ranking pointing the opposite direction, exactly as `git log --name-only` reported it, not as narrated. `notifyhub`'s planted trap, `legacy_formatters.py`, measured **520** lines with **0** fan-in, against `retry.py` at **12** lines carrying the graph's unique highest fan-in, **2** — the same "big does not mean central" finding, independently measured a second time on different, unrelated code. One fact of provenance is equally checkable: this module's central instrument, `git`, and the read-the-history discipline it enables, exist because Linus Torvalds needed a way to track patches to the Linux kernel after BitKeeper's free license was withdrawn in 2005 and wrote `git` in roughly ten days — infrastructure this course has assumed since M01 that was, itself, a piece of unpaid, urgent, individual labor before it became something the entire industry now reads history through without a second thought.

**Tier 2 — What the field suppresses.** Two distortions, pulling in opposite directions, both about the same suppressed labor this module makes newly visible to you. The **booster distortion** says reading an unfamiliar codebase is a solved problem now — paste the repository into an AI assistant, get a fluent summary back, done — and this module's own gaming-resistance design exists specifically because that framing launders "a plausible-sounding paraphrase" into "verified understanding" without ever checking a single claim against the actual code. The sharpest real-world evidence against it is the 2024 `xz-utils` backdoor (CVE-2024-3094): a multi-year, patient supply-chain compromise, inserted into a widely-depended-on compression library by a contributor who had gradually earned co-maintainer trust on a project that — like most of the dependency graph under any Python project, including your own `pytoolkit` — was maintained by essentially one or two unpaid people. It was discovered not by a tool summarizing the repository, but by a developer (Andres Freund) noticing anomalously slow SSH login latency and then doing exactly this module's kind of close, suspicious reading — of build scripts, of commit history, of what a diff actually changed versus what its message claimed — the malicious code was deliberately built to look unremarkable to a casual read, hidden inside binary test fixtures and build-system macros exactly the way a fluent AI summary or a rushed top-to-bottom skim would gloss past it. The **cynic's mirror-image distortion** says codebase-reading skill is purely technical, orthogonal to who wrote the code or why — which suppresses the fact that the single-or-two-maintainer structure that made `xz` vulnerable to a patient social-engineering takeover is not a rare edge case. It is close to the norm across the dependency graph nearly every real Python project sits on, including, almost certainly, several packages your own `pytoolkit` already depends on.

**Tier 3 — Sit with this (a question you cannot unknow).** You now have, in under two hours, the skill to read any of your dependencies closely enough to know who actually maintains it — one name in `git log`, or many — how recently, how its real internal structure compares to what its README claims, and where a change would be hardest for a casual reader to notice. That is close to exactly the skill that would have let an ordinary, non-security-researcher user of `xz` — someone who simply happened to read a build script closely, the way Lesson 1 and Lesson 2 just taught you to — raise a question years earlier than it was actually caught. You are not going to audit every dependency you use before you use it; nobody does, and that is not a personal failing — it is a structural fact about how much software any one person now runs on top of code they will never fully read. But this module just made the cost of *one* such check concrete and small: an import graph, a touch-frequency ranking, and about thirty minutes, on a package you already depend on. Given that the check is now that cheap for you specifically — which one dependency, in your own toolkit or somewhere else you rely on, would you actually run it against this month? And once you know what it finds — a bus factor of one, a churn pattern that doesn't match what the README claims the project is, a module structurally central that nobody's touched in years — what do you actually do with that: file the issue, offer the fix, or keep it to yourself, and does your answer change depending on whether you're the one who benefits from the library staying healthy?
