### Lesson 1 — A function is a contract: signature, purity, and the default that remembers

**The teaching.** A function's **signature** is its public promise: the names and kinds of its parameters, and — by convention and docstring — the shape of what it returns and what it does to the world. Python gives you four kinds of parameter binding, and choosing among them *is* API design:

- **positional-or-keyword** — `def f(a, b):` — the default; callable as `f(1, 2)` or `f(a=1, b=2)`.
- **defaulted** — `def f(a, b=10):` — `b` is optional; the default expression is evaluated **once, at function-definition time**, not per call. This is the trap of the module.
- **variadic** — `def f(*args, **kwargs):` — `args` is a `tuple` of extra positionals, `kwargs` a `dict` of extra keywords.
- **keyword-only** — `def f(a, *, verbose=False):` — everything after the bare `*` *must* be passed by name. Use this for flags, so no caller writes `f(x, True)` and leaves the reader guessing what `True` meant.

Beyond the signature sits the part the signature cannot show you: **purity.** A **pure** function's output depends only on its inputs and it changes nothing outside itself — no mutation of arguments, no I/O, no global state. Pure functions are the ones you can predict, test in isolation, cache, and reason about. Every function in this module states, in its docstring, whether it mutates its inputs — because "does this touch my list?" is the single most common question a *reader* of your toolkit will ask, and the AI that calls your function cannot know the answer unless you wrote it down.

**The default that remembers.** Here is the promise Python lets you break silently:

**Worked example — the accumulator that leaks across calls.**

```python
def add_tag(tag, tags=[]):        # tempting, and wrong
    tags.append(tag)
    return tags

print(add_tag("a"))    # ['a']
print(add_tag("b"))    # ['a', 'b']   <-- surprise: 'a' is still here
print(add_tag("c"))    # ['a', 'b', 'c']
```

The default `[]` is evaluated **once**, when `def` runs — not each time you call. Every call that omits `tags` shares *the same list object*, which accumulates forever. This is not a crash; it is a function quietly lying about being fresh. Coming from the intuition "the default is `[]`, so each call starts empty," the natural prediction is `['a']`, `['b']`, `['c']`. The machine prints an accumulating list. The fix is the **`None` sentinel**:

```python
def add_tag(tag, tags=None):      # correct
    if tags is None:
        tags = []                 # a fresh list PER CALL
    tags.append(tag)
    return tags
```

Now `tags is None` is checked each call and a new list is built each time the default is wanted. (`is None`, never `== None`: `None` is a singleton; identity is exactly right here, and it is faster and un-foolable by a class that overloads `__eq__`.)

**Named misconceptions:**

- **"The default `[]` gives each call a fresh empty list."** No — the default *expression* runs once at definition time; the resulting object is reused. Mutable defaults (`[]`, `{}`, `set()`) are shared state hiding in a signature. The rule you carry forever: **default arguments must be immutable** (`None`, numbers, strings, tuples); for a mutable default, pass `None` and build inside.
- **"A function that returns the right value is correct."** Correctness includes *what it touched*. `def sort_in_place(xs): xs.sort(); return xs` returns a sorted list **and** mutated the caller's list — a side effect the return value hides. Two functions with identical return values can have opposite contracts. State purity in the docstring or the contract is incomplete.
- **"`*args`/`**kwargs` are for advanced code."** They are for *honest* code: a wrapper that forwards arbitrary arguments, a function that genuinely takes a variable number of items. Reaching for them when you have exactly two parameters, though, hides the real signature from your reader — precision beats flexibility in a toolkit others read.

### Lesson 2 — The four containers and the cost you can name: list, dict, set, tuple

**The teaching.** Python hands you four core containers. Choosing the wrong one is rarely a *bug* — it is a program that works on your test input and is `O(n)` slower than it needed to be on real data, or one that says something false about your intent. Choose against a cost model you can state:

| Container | Ordered? | Mutable? | Duplicates? | Membership `x in c` | Typical use |
|---|---|---|---|---|---|
| `list` | yes (position) | yes | yes | **O(n)** — linear scan | an ordered sequence you append to / index |
| `dict` | yes (insertion) | yes | keys unique | **O(1)** avg — hashed | a mapping from key → value; the workhorse |
| `set` | no | yes | no | **O(1)** avg — hashed | membership / dedup / set algebra |
| `tuple` | yes (position) | **no** | yes | O(n) | a fixed record; a **hashable** key |

Two facts do most of the work. First, **`in` on a `list` is a linear scan; `in` on a `set`/`dict` is a hash lookup.** If you test membership inside a loop over `n` items against a `list` of `m` items, you have written `O(n·m)`; switch the `m`-collection to a `set` and it is `O(n)`. Second, **only hashable (roughly: immutable) things can be `set` elements or `dict` keys.** A `tuple` of numbers is hashable and makes a fine dict key; a `list` is not — `d[[1, 2]] = x` raises `TypeError: unhashable type: 'list'`. That single rule is why `tuple` exists as a distinct type from `list`: not "an immutable list for safety," but "a *hashable* sequence you can use as a key."

**Worked example — the membership test that is secretly quadratic.**

```python
def common_slow(a, b):                    # O(len(a) * len(b))
    return [x for x in a if x in b]       # `x in b` scans the LIST b every time

def common_fast(a, b):                    # O(len(a) + len(b))
    b_set = set(b)                        # build the hash set ONCE
    return [x for x in a if x in b_set]   # each `in` is now O(1) average
```

Both return the same list. On `a` and `b` of a few elements they are indistinguishable — this is why the slow one passes tests. On `len(a) == len(b) == 100_000`, `common_slow` does ~10 billion comparisons and `common_fast` does ~200 thousand hash lookups. The correctness is identical; the *cost* is a factor of tens of thousands, and no test on small inputs will ever show it. You catch it only by reasoning about the structure you chose.

**Worked example — the tuple as a key the list cannot be.**

```python
scores = {}
scores[("alice", 2026)] = 91     # tuple key: hashable, fine
print(scores[("alice", 2026)])   # 91
scores[["alice", 2026]] = 91     # TypeError: unhashable type: 'list'
```

The `tuple` version works because a tuple of hashables is itself hashable; the `list` version raises deterministically, every run, before any value is stored. When you need a compound key — a (row, col), a (user, year) — the container that *can* be a key is `tuple`.

**Named misconceptions:**

- **"`in` is `in`; it costs the same on any container."** No — membership is `O(n)` on `list`/`tuple` (scan) and `O(1)` average on `set`/`dict` (hash). The identical spelling hides a thousand-fold cost difference at scale. When membership is in a hot loop, the collection you test against should almost always be a `set` or `dict`.
- **"`tuple` is just an immutable list; use it when you want to be careful."** Its defining property is not immutability-for-safety, it is **hashability** — it can be a `set` element or `dict` key, which a `list` never can. Reach for `tuple` when you need a fixed-length record or a compound key, not merely when you feel cautious.
- **"`dict`s are unordered, so I can't rely on order."** True before Python 3.7; **false since.** CPython `dict` preserves insertion order as a language guarantee. `list(d)`, iteration, and `json.dumps` all see first-inserted-first. (A `set`, however, still has no meaningful order — do not confuse the two.)
- **"A set will dedup my list and keep the order."** It dedups but **loses order**. To dedup *preserving first-seen order*, use `list(dict.fromkeys(xs))` — the dict remembers insertion order and drops duplicate keys. This idiom is Lab A.

### Lesson 3 — Laziness: the iterator protocol, generators, and the value you can only take once

**The teaching.** A `for` loop does not "loop over a list." It loops over an **iterator** — an object with a `__next__` method that hands out one value per call and raises `StopIteration` when spent. `for x in c:` is sugar for: call `iter(c)` to get an iterator, call `next()` on it until `StopIteration`. Lists, dicts, sets, files, and strings are all **iterable** — `iter()` gives each a fresh iterator. This is the substrate under every loop you have ever written.

A **generator** is the easiest way to *build* an iterator: a function containing `yield`. Calling it runs **no body**; it returns a generator object. Each `next()` runs the body until the next `yield`, hands back that value, and **freezes** — locals and instruction pointer preserved — until the next `next()`. This buys you **laziness**: values are produced one at a time, on demand, so you can process a ten-gigabyte file, or an infinite sequence, in constant memory. The cost is the property that trips everyone: **a generator is single-pass.** Once exhausted, it is empty forever; iterating it again yields nothing.

**Worked example — the generator that is empty the second time.**

```python
squares = (n * n for n in range(5))   # a generator EXPRESSION (parens, not brackets)

print(sum(squares))    # 30   -> 0+1+4+9+16, and this DRAINS the generator
print(sum(squares))    # 0    <-- already exhausted; there is nothing left to sum
print(list(squares))   # []   <-- still empty
```

No exception. `sum` walked the generator to `StopIteration` the first time; the second `sum` gets an already-dead iterator and, summing nothing, returns `0`. The natural prediction — "it's `squares`, so it's `30` again" — treats the generator like a list. It is not a container of values; it is a *recipe that runs once*. If you need the values twice, either materialize them (`squares = [n*n for n in range(5)]` — a list, re-iterable) or rebuild the generator. Contrast with the list comprehension, which *is* a container:

```python
squares = [n * n for n in range(5)]   # a LIST (brackets)
print(sum(squares))    # 30
print(sum(squares))    # 30   <-- a list can be iterated any number of times
```

The single character `[` vs `(` is the difference between "compute all five now, keep them" and "produce them lazily, once." That is a design decision about memory and reusability, not a syntax nicety.

**Worked example — laziness that pays: reading a huge file without loading it.**

```python
def line_lengths(path):
    with open(path) as f:
        for line in f:            # a file object is a lazy iterator of lines
            yield len(line.rstrip("\n"))   # one length at a time; file stays on disk

# Works on a 10 GB file in constant memory; `[len(l) for l in open(path)]` would try to
# hold every line at once.
total = sum(line_lengths("big.log"))
```

**Named misconceptions:**

- **"A generator is a kind of list."** It is a kind of *iterator*: single-pass, lazy, holds one value at a time, has no `len`, cannot be indexed, and is empty after one full traversal. A list holds all its values, is re-iterable, indexable, and has a length. Choosing between them is choosing between "keep everything, reusable" and "one at a time, once."
- **"Building a generator runs the function."** Calling a generator function runs *none* of the body until the first `next()`. If your generator has a side effect (a print, an open), it will not happen until something iterates it — a real source of "why didn't my logging fire?" confusion.
- **"`sum(gen)` returning 0 the second time is a bug."** It is the *definition*. The bug is expecting a spent iterator to refill. Deterministic, not flaky: exhausted generators always yield nothing.
- **"Comprehension parens vs brackets are interchangeable style."** `[...]` builds a list (eager, reusable, in memory); `(...)` builds a generator (lazy, once, streaming). They differ in memory profile and reusability, not just looks.

### Lesson 4 — Comprehensions, and the standard library you must read before `pip`

**The teaching.** A **comprehension** is a declarative build of a container from an iterable: *what* you want, not the mechanics of appending. Four forms, distinguished by brackets:

```python
[f(x) for x in xs if pred(x)]        # list comprehension  -> list
{f(x) for x in xs if pred(x)}        # set comprehension   -> set (deduped, unordered)
{k(x): v(x) for x in xs}             # dict comprehension  -> dict
(f(x) for x in xs)                   # generator expression -> lazy iterator
```

Prefer them to hand-rolled `for`/`append` loops when the loop's whole job is to build a container: they are shorter, they read as intent, and they are marginally faster. But **stop before they nest three deep or grow a side effect** — a comprehension exists to *build a value*, not to *do things*; `[print(x) for x in xs]` (a list of `None`s, built for its side effect) is an abuse a reader will curse.

**The standard library is the toolbox you read before reaching for `pip`.** Python ships "batteries included" — a large collection of modules maintained *with the interpreter*, already installed, already audited, already on every machine that has Python. Every third-party dependency you add is code you must trust, update, and carry; a great deal of what beginners `pip install` is already in the stdlib. The professional reflex is: **before you add a dependency, check the standard library.** A starter map for this module's subject:

- **`collections`** — `Counter` (tallies), `defaultdict` (auto-initializing dict), `deque` (O(1) append/pop at both ends), `namedtuple`.
- **`itertools`** — lazy building blocks: `islice`, `chain`, `groupby`, `count`, `product`, `combinations`.
- **`functools`** — `reduce`, `lru_cache` (memoization in one decorator), `partial`.
- **`dataclasses`** — `@dataclass` generates `__init__`/`__repr__`/`__eq__` from typed fields.
- **`pathlib`** — `Path` objects for filesystem work, cleaner than string paths.

**Worked example — reimplement `Counter` by hand, then earn the right to reach for it.** The descent-then-ascend in miniature: build the tally at the substrate so you *understand* it, then command the stdlib tool.

```python
# By hand — you must understand this before you delegate it:
def tally(items):
    counts = {}
    for x in items:
        counts[x] = counts.get(x, 0) + 1   # .get(x, 0): read-with-default, no KeyError
    return counts

print(tally("mississippi"))   # {'m': 1, 'i': 4, 's': 4, 'p': 2}

# The stdlib tool that does exactly this, plus most_common(), arithmetic, and speed:
from collections import Counter
c = Counter("mississippi")
print(c)                 # Counter({'i': 4, 's': 4, 'p': 2, 'm': 1})
print(c.most_common(2))  # [('i', 4), ('s', 4)]   <-- sorted by count, descending
```

You do not reach for `Counter` because it is shorter; you reach for it because you have *built* the thing it is, so you know exactly what it promises.

**Worked example — the stdlib tool with a sharp edge: `itertools.groupby` needs sorted input.** Reading the stdlib is not optional trust; the tools have contracts, and this one has a contract beginners violate constantly. `groupby` groups **consecutive** equal keys — it does not sort for you:

```python
from itertools import groupby

data = [1, 1, 2, 1, 3, 3]                       # note: the two 1s are NOT all adjacent
result = {k: len(list(g)) for k, g in groupby(data)}
print(result)    # {1: 1, 2: 1, 3: 2}   <-- NOT {1: 3, 2: 1, 3: 2}
```

`groupby` yields groups `(1,[1,1]) (2,[2]) (1,[1]) (3,[3,3])`; the dict comprehension's later `1` key overwrites the earlier one, and you get a silently wrong tally. It does not crash. It returns a plausible dict. To count occurrences you want `Counter`; to use `groupby` correctly you must `sorted(data)` first so equal keys are adjacent. **Reading a tool's contract before using it is the same discipline as reading code before trusting it — the stdlib is not exempt from AI-PRIMM.**

**Named misconceptions:**

- **"Comprehensions are just faster loops; use them everywhere."** They are for *building a container from an iterable*. Used for side effects (`[do(x) for x in xs]`) they build a throwaway list of `None`s and hide the intent; used three levels deep they become unreadable. When the loop's purpose is an effect, write the `for` loop.
- **"If I need a tool, I `pip install` it."** Check the stdlib first. `Counter`, `defaultdict`, `groupby`, `lru_cache`, `Path` are already installed, already maintained, already audited — every avoided dependency is risk and weight you do not carry.
- **"`groupby` groups all equal keys."** It groups **consecutive** equal keys; unsorted input yields fragmented, silently wrong groups. Its contract is "sort first, or accept run-length grouping." Stdlib tools have contracts you must read.
- **"`defaultdict` and `dict.get(k, default)` are the same."** `d.get(k, 0)` returns a default *without inserting*; `defaultdict(int)[k]` inserts the default *and* returns it (and the missing-key machinery only fires through `__getitem__`). For accumulation both work; for "did I ever see this key?" they differ — `get` leaves the dict untouched, `defaultdict` grows it.

def dedup(items):
    seen = set()

    for x in items:
        if x not in seen:      # O(1) membership: seen is a SET, not a list

            out.append(x)

def word_count(text):

**Program 4 — `groupby` on unsorted input.**

Solution:

```python
def chunked(iterable, size):
    if size <= 0:
        raise ValueError("size must be positive")
    it = iter(iterable)                 # one iterator, advanced across calls
    while True:
        chunk = list(islice(it, size))  # take up to `size` more items, lazily
        if not chunk:                   # iterator exhausted -> stop
            return
        yield chunk


def top_n(items, n):
    return Counter(items).most_common(n)
```

**Verify.** Run `python3 -m pytest -q tests/test_streams.py`. Reconcile:
- `list(chunked([1,2,3,4,5], 2))` is `[[1, 2], [3, 4], [5]]` — the last chunk has length 1 because 5 is not a multiple of 2; `islice` simply returns what remains.
- Calling `list(g)` twice on one `chunked(...)` object returns the full list then `[]`: a generator is single-pass (Lesson 3), exhausted after the first full traversal.
- `top_n(["a","b","a","c","a","b"], 2)` is `[('a', 3), ('b', 2)]` — `most_common` sorts by count descending; among equal counts it preserves first-encountered order (`Counter` is insertion-ordered).
- Big-O honesty: `Counter` does **not** beat a hand-rolled `dict` tally asymptotically — both are `O(len(items))` to build and the top-`n` selection is the same. ## Three-tier reading — the standard library, and the maintainers you will never thank

**Tier 1 — Material ground (verifiable facts).** The standard library is real, vast, and already on your machine — you can inventory it at the keyboard. `import sys; len(sys.stdlib_module_names)` prints a few hundred module names; `import this` prints the Zen that governs their design; `Counter`, `defaultdict`, `deque`, `groupby`, `lru_cache`, `Path`, `dataclass` are all importable right now with no `pip install`, because they ship *with* CPython and are maintained *alongside* it. Every claim in this module is checkable: `dedup([3,1,3,2,1])` is `[3,1,2]`; a mutable default accumulates across calls and the `None` sentinel fixes it; `sum(g)` on a generator returns its total once and `0` forever after; `set` membership is `O(1)` average and `list` membership `O(n)` (measure it with `timeit` on a 100k-element haystack and watch the gap open); `groupby` on unsorted input under-counts, deterministically. And one fact of provenance, equally checkable: open CPython's issue tracker and its `Misc/ACKS` file, and you will find that the modules you `import` for free were written and are patched, reviewed, and kept working across versions by people — a core team of a few dozen, plus a long tail of volunteers — most of whom were paid nothing by you and will never hear from you.

**Tier 2 — What the field suppresses.** Two opposite distortions, each hiding the same labor. The booster distortion — "Python has batteries included, just `import` it, it's *free*" — suppresses that *free-to-use* is not *free-to-make*: `Counter` did not fall from the sky; someone designed its API, argued the edge cases in a PEP, wrote the tests you now rely on, and has maintained backward compatibility for a decade so your code doesn't break on upgrade. "Included" quietly launders continuous unpaid (or under-paid) maintenance into a feature of the download. The consumer distortion — "it's open source, it's *community*, we're all in this together" — suppresses that the "community" is overwhelmingly *takers*: millions import the modules; a few hundred maintain them. The word *community* implies reciprocity that the numbers do not support; it is, for most of us, extraction with a friendly name — we take the audited, battle-tested tool and contribute nothing back, not a bug report, not a doc fix, not a thank-you. Both camps avoid the honest middle: the reliability you build your career on is **real, and it is subsidized** — by maintainers absorbing the cost of your convenience, often on nights and weekends, until they burn out and hand the keys to the next volunteer, or don't, and a module you depend on quietly goes unmaintained while you keep importing it. The safety is not free; you are just not the one paying.

**Tier 3 — Sit with this (a question you cannot unknow).** You have spent this module learning to *read before you trust* — to predict a function's behavior before you run it, to check a tool's contract before you call it. You applied that to code you can see. But `import Counter` is an act of trust in code you did *not* read, written by people you cannot name, maintained for reasons that are not your convenience and may not outlast their patience. Your toolkit — the one you are building, commit by commit, all course — sits on a stack of such trust, all the way down, and every layer of it was made by someone who owed you nothing and gave it anyway. **When your published toolkit finally depends on a stranger's unpaid Saturday — the `groupby` you didn't write, the hash table under every `dict`, the bytecode compiler that runs your every line — what, concretely, do you owe the commons you build on: is a green CI badge and a `pip install` the whole of the relationship, or is "I took the battery and never asked who charged it" a debt you have simply decided not to see?**
