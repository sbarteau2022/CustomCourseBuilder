## Lessons

### Lesson 1 — The interpreter is a machine that evaluates

**Teaching text.**

When you type `1 + 1` at the Python prompt and see `2`, it is tempting to think "the computer did math." Something more specific happened, and the specificity is the whole point of this course. CPython — the reference interpreter you are almost certainly running — did four things: it *tokenized* your text, *parsed* it into a tree, *compiled* that tree to **bytecode** (a compact list of instructions for a stack machine), and then *executed* the bytecode one instruction at a time. `2` is not "the answer the computer knew." `2` is an **object** the interpreter constructed (or reused) and then handed back to the REPL, which printed its `repr`.

Everything in Python is an object. An object is a region of memory with three properties that never change for the life of the object:

- **identity** — *which* object it is. You read it with `id(obj)`; in CPython it is the object's address. Compared with `is`.
- **type** — *what kind* of object it is. You read it with `type(obj)`. It determines what the object can do.
- **value** — the data the object holds. Compared with `==`.

Identity and type are fixed at creation. Value may or may not be changeable — that distinction (mutability) is Lesson 3, and it is where programs get hard.

The reason we start at the bytecode is that it makes assignment legible. You cannot see "a name pointing at an object" in the source text `x = 1`, but you can see it in the instructions the interpreter runs. We will read those instructions with the `dis` module. You do not need to memorize opcodes. You need one habit: when you are unsure what a line does, *ask the interpreter to show you*, then verify.

**Worked example.**

```python
>>> import dis
>>> dis.dis("x = 1")
  0           RESUME                   0

  1           LOAD_CONST               0 (1)
              STORE_NAME               0 (x)
              RETURN_CONST             1 (None)
```

Read it top to bottom. `LOAD_CONST 0 (1)` builds (or reuses) the integer object `1` and pushes it onto an internal stack. `STORE_NAME 0 (x)` pops that object and **binds the name `x` to it** in the current namespace. That is what `=` means: not "put 1 into the box x," but "make the name x refer to this object." The `RETURN_CONST` is the module implicitly returning `None`.

> The exact opcodes and offsets are CPython-version-specific — `RETURN_CONST` exists in 3.12 but not 3.11, and offsets shift between patch releases. **Do not memorize this output. Run it yourself on your interpreter.** That act — "I was unsure, so I asked the machine and read the answer" — is the entire verification stance of this course, applied to the interpreter itself.

Now watch the same idea with a value you can inspect:

```python
>>> x = 1
>>> type(x), id(x)          # your id() number will differ; that's expected
(<class 'int'>, 140704...)
>>> x = "one"               # rebinding: x now refers to a different object
>>> type(x), id(x)
(<class 'str'>, 140705...)
```

The name `x` did not "change type." Names have no type. The *object* `x` refers to changed, from an `int` to a `str`, because `x = "one"` rebound the name.

**Named misconceptions.**

- *"Python is interpreted, so there's no compilation."* There is. CPython compiles your source to bytecode (`.pyc` files cache it) and then interprets the bytecode. "Interpreted vs. compiled" is not a binary; it is a question of *what* is compiled and *when*.
- *"`id()` gives me a permanent ID for a value."* `id()` is unique and constant only for the **lifetime of that object**. Once an object is garbage-collected, its `id` can be reused by a new, unrelated object. `id` identifies an object, not a value.
- *"The REPL shows me the value."* The REPL shows you `repr(value)`, a *string chosen by the type* to represent the object. `repr` can lie by omission (a huge list is truncated in some displays) and it is not the object. This matters the moment you debug by printing.

### Lesson 2 — Names are bindings, not boxes

**Teaching text.**

Here is the model, stated flatly, because getting it wrong is the source of most bugs beginners cannot explain: **assignment binds a name to an object. Multiple names can be bound to the same object. Assignment never copies the object.**

`b = a` does not copy whatever `a` refers to. It binds `b` to the *same object* `a` is already bound to. Now `a` and `b` are two names for one object — they are **aliases**. If that object is mutable and you change it through one name, the change is visible through the other name, because there is only one object.

This is the aliasing you predicted in AIE-100 while reading code. Now you own the mechanism. Two operators let you observe it:

- `a is b` asks **"same object?"** — it compares `id(a)` with `id(b)`.
- `a == b` asks **"equal value?"** — it calls `a.__eq__(b)`, which the type defines.

Two distinct list objects with the same contents are `==` but not `is`. One list object referred to by two names is both `==` and `is`. Keeping these separate is not pedantry; it is the difference between "these look the same" and "these *are* the same, so mutating one mutates the other."

There is a trap laid by CPython's implementation. Small integers (−5 to 256) and some short strings are **cached / interned** — the interpreter reuses one object for them. So `a = 256; b = 256; a is b` is `True`, while `a = 257; b = 257; a is b` may be `True` or `False` depending on whether the two `257`s were compiled together. This does not contradict the model; it means *identity of immutable values is an observable implementation detail you must never write code against.* Use `==` for value, always. Reserve `is` for `None`, `True`, `False`, and genuine identity questions.

**Worked example.**

```python
>>> a = [1, 2, 3]
>>> b = a                 # bind b to the SAME object; no copy
>>> a is b
True
>>> b.append(4)           # mutate the one object through b
>>> a
[1, 2, 3, 4]              # visible through a — there is only one list
>>> c = [1, 2, 3, 4]      # a brand-new, separate list object
>>> a == c                # same contents
True
>>> a is c                # different objects
False
```

Contrast with rebinding, which breaks the alias:

```python
>>> a = [1, 2, 3]
>>> b = a
>>> b = b + [4]           # b + [4] builds a NEW list; b is rebound to it
>>> a
[1, 2, 3]                 # a is untouched: b no longer refers to a's object
>>> a is b
False
```

The single-character difference between `b.append(4)` (mutate the shared object) and `b = b + [4]` (build a new object and rebind `b`) is the difference between changing `a` and not. Predicting which one a line does — *before running it* — is the core skill of Lab 2.

**Named misconceptions.**

- *"`=` copies the value."* Never. `=` binds a name. If you want a copy you must ask for one explicitly (`list(a)`, `a.copy()`, `copy.deepcopy(a)`). This is the single most expensive misconception in the module; the labs exist to burn it out.
- *"`is` is just a faster `==`."* They answer different questions. `is` is identity; `==` is value. `[] is []` is `False`; `[] == []` is `True`. Using `is` to compare values *works by accident* for cached small ints and *fails silently* the moment your values leave the cache — a bug that appears only for large inputs.
- *"If `a == b` then they're interchangeable."* Only if you never mutate. Two equal-but-distinct lists diverge the instant you append to one. Equality now says nothing about equality later once mutation enters.
- *"Aliasing is a rare edge case."* It is the default. Function arguments alias. List elements alias. `dict.values()` aliases. You are always aliasing; the question is only whether the aliased object is mutable.

### Lesson 3 — Mutability is the fault line

**Teaching text.**

Every Python object is either **mutable** (its value can change in place, its identity staying the same) or **immutable** (its value is fixed for life; any "change" is really a new object). This one property decides whether aliasing is harmless or hazardous.

Immutable, in the standard library you'll use daily: `int`, `float`, `bool`, `str`, `bytes`, `tuple`, `frozenset`, `None`. Mutable: `list`, `dict`, `set`, and most objects you define with `class`.

The tell is whether an operation mutates in place or rebinds:

- `list.append`, `list.sort`, `dict.__setitem__` (`d[k] = v`), `set.add` — **mutate in place**, return `None`, keep identity.
- `+`, `sorted()`, slicing `a[:]`, `str.upper()` — **build a new object**, leave the original alone.
- `+=` is the subtle one. For a **mutable** left side it usually mutates in place (`list.__iadd__` extends the existing list); for an **immutable** left side it *must* rebind (`x += 1` on an int builds a new int and rebinds `x`, because ints cannot change). So `+=` sometimes mutates and sometimes rebinds — determined entirely by the type on the left.

The most infamous consequence is the **mutable default argument**. A function's default values are evaluated **once**, when the `def` runs, and stored on the function object. If a default is a mutable object, every call that uses the default shares *that one object* across calls. State leaks between invocations that look independent.

**Worked example.**

`+=` cuts both ways depending on mutability:

```python
>>> x = 10
>>> y = x
>>> x += 1        # int is immutable: builds a new int 11, rebinds x
>>> x, y
(11, 10)          # y unchanged; they were never linked after rebinding

>>> a = [1, 2]
>>> b = a
>>> a += [3]      # list is mutable: extends the existing list in place
>>> a, b
([1, 2, 3], [1, 2, 3])   # b sees it too — same object
```

The mutable default trap, and its fix:

```python
>>> def add_item(item, bucket=[]):     # BUG: one list shared across all calls
...     bucket.append(item)
...     return bucket
...
>>> add_item("a")
['a']
>>> add_item("b")          # expected ['b']; got the leftover 'a'
['a', 'b']
>>> add_item("c")
['a', 'b', 'c']            # state accumulates in the shared default object
```

```python
>>> def add_item(item, bucket=None):   # FIX: sentinel + fresh object per call
...     if bucket is None:
...         bucket = []
...     bucket.append(item)
...     return bucket
...
>>> add_item("a")
['a']
>>> add_item("b")
['b']                      # independent, as intended
```

Note the fix uses `is None`, not `== None` — identity, because there is exactly one `None` and we mean "the caller passed nothing," not "the caller passed something equal to None."

**Named misconceptions.**

- *"Tuples are immutable, so a tuple can't change."* The tuple's *bindings* can't change — you can't reassign `t[0]` or add elements. But if a tuple holds a mutable object, that object can still mutate: `t = ([],); t[0].append(1)` leaves `t == ([1],)`. Immutability is one level deep.
- *"`+=` is just shorthand for `x = x + y`."* Not for mutable types. `a = a + [3]` always builds a new list and rebinds; `a += [3]` mutates the existing list in place. For a list that other names alias, these produce *different observable results*. The shorthand equivalence holds only for immutable types.
- *"The mutable-default bug is about lists specifically."* It's about *any* mutable default: `{}`, `set()`, a `datetime.now()` captured at def-time, a growing counter object. The rule is: default values are evaluated once at definition. Never let a mutable object be a default; use `None` and build fresh inside.
- *"A function that takes a list can't affect my list."* It can and will, if it mutates the argument — because the parameter is an alias of your object, not a copy. "Pass by value or reference?" is the wrong frame in Python. Python passes **object references by value**: the function gets a new name bound to your object. Rebinding that name inside the function doesn't touch yours; mutating the object does.

### Lesson 4 — State is what makes programs hard

**Teaching text.**

A pure expression — `2 + 2`, `len(s)`, `sorted(xs)` — is easy to reason about: same inputs, same output, no trace left behind. **State** is everything that violates that. State is the accumulated, mutable memory of a program: which mutable objects exist, what they currently hold, and which names alias them. State is what lets a program "remember," and it is precisely what makes a program hard to reason about, because the answer to "what does this line do?" now depends on history you can't see in the line.

Three lessons compound here. Objects have identity (L1). Names alias objects without copying (L2). Some objects mutate in place (L3). Put together: **a mutation through any alias, anywhere, at any earlier time, can change what your code sees now.** That is the difficulty. Large programs are hard not because the syntax is hard but because the state space is large and invisible.

The engineering response is discipline, and it has two moves:

1. **Don't share mutable state you didn't mean to share.** When a function must not affect its caller's object, *copy at the boundary* — take a snapshot. When you hand data out, hand out a copy, not your internal object, so callers can't reach in and mutate you.
2. **Make state testable by making it observable.** A function that mutates hidden state is hard to test. A function that takes state in and returns new state out (or exposes a read-only snapshot) can be tested by *arranging* a known state, *acting*, and *asserting* the resulting state. This Arrange–Act–Assert shape is why testing is the primary instrument of this course, not an afterthought: a test is how you *prove* a claim about state instead of hoping.

The choice between "copy" and "share" is a real engineering decision with a cost (copies use time and memory) and a benefit (isolation). The `freeze` and `Ledger` you build in Lab 3 are two answers: `freeze` produces a deeply immutable snapshot you can safely hand out or compare against later; `Ledger` guards its internal list so callers get copies, never the original.

**Worked example.**

A function that leaks state by returning its own mutable internals, and the fix:

```python
>>> class Cart:
...     def __init__(self):
...         self._items = []
...     def add(self, item):
...         self._items.append(item)
...     def items_leaky(self):
...         return self._items          # BUG: hands out the internal list itself
...     def items_safe(self):
...         return list(self._items)    # FIX: hands out a copy
...
>>> c = Cart()
>>> c.add("apple")
>>> leaked = c.items_leaky()
>>> leaked.append("SMUGGLED")           # caller mutates our internal state!
>>> c.items_leaky()
['apple', 'SMUGGLED']                   # corruption from outside

>>> c2 = Cart()
>>> c2.add("apple")
>>> snap = c2.items_safe()
>>> snap.append("SMUGGLED")             # caller mutates only their copy
>>> c2.items_safe()
['apple']                               # internal state intact
```

The bug is not visible in `items_leaky`'s body — it's a correct-looking `return`. It's only a bug in the presence of a caller who mutates. That invisibility is the nature of state bugs, and it's why we test the boundary rather than eyeball the body.

**Named misconceptions.**

- *"If my function returns the right value, it's correct."* Not if it also mutated a caller's object as a side effect, or exposed internal state a caller can corrupt. Correctness includes *what you left behind*. A test that only checks the return value misses half the contract.
- *"Global state is the only dangerous state."* Any shared mutable object is shared state: a list passed to three functions, an object attribute handed out by a getter, a default argument. Globals are just the most obvious case.
- *"Copying is always the safe choice, so always copy."* Copies cost memory and time and can hide bugs (you fixed the symptom, not the accidental sharing). The judgment is *where* the boundary is — copy once at the edge of your abstraction, then share freely inside it. Reflexive `deepcopy` everywhere is a performance and clarity problem, not a solution.
- *"Immutable means slow / wasteful."* Immutability buys you reasoning: an immutable snapshot cannot be corrupted by any alias, so you can share it freely with *no* defensive copying. Sometimes the cheapest safe design is to freeze once and share the frozen thing everywhere.

```python
from __future__ import annotations

from typing import Any


def is_same(a: Any, b: Any) -> bool:
    """Return True iff ``a`` and ``b`` are the same object (identity).

    True

    False
    """
```

### Lab 2 — The mutation you didn't order: aliasing and the mutable default

**Goal.** Predict the behavior of two notorious snippets, then ship a *correct* accumulator that does not leak state — `accumulate(item, into=None)` — with a test that would **fail** on the buggy version. This proves your fix, rather than merely running.

#### Predict (on paper, before any code)

Snippet A:

```python
def add_item(item, bucket=[]):
    bucket.append(item)
    return bucket

r1 = add_item("a")
r2 = add_item("b")
r3 = add_item("c")
```

Predict `r1`, `r2`, `r3` **and** `r1 is r2` and `r1 is r3`. State the mechanism in one sentence.

Snippet B:

```python
def extend_all(target, extra):
    target += extra          # is this mutate-in-place or rebind?
    return target

original = [1, 2]
result = extend_all(original, [3, 4])
```

Predict `original`, `result`, and `original is result`. State why `+=` here does what it does.

Finally, write the **one-line rule** you would give a teammate to avoid Snippet A's bug forever.

#### Build

Add to `src/pytoolkit/state.py`:

```python
def accumulate(item: Any, into: list[Any] | None = None) -> list[Any]:
    """Append ``item`` and return the list, WITHOUT sharing hidden state.

    If ``into`` is not given, a fresh list is created for this call — so two
    calls with no ``into`` never share a list. If ``into`` is given, ``item``
    is appended to that caller-owned list in place (the caller opted in).

    The sentinel is ``None`` compared with ``is`` (identity), because we mean
    "the caller passed nothing," not "the caller passed something == None".

    >>> accumulate("a")
    ['a']
    >>> accumulate("b")          # independent of the call above
    ['b']
    >>> mine = []
    >>> accumulate("x", mine)    # opt in to sharing
    ['x']
    >>> mine
    ['x']
    """
    if into is None:
        into = []
    into.append(item)
    return into
```

#### Verify

```python
def test_accumulate_does_not_leak_state_between_default_calls():

    assert second == ["b"]        # buggy version would give ["a", "b"]

    b = accumulate("y")
    a.append("z")

```

### Lab 3 — Snapshots against corruption: `freeze` and `Ledger` (with a property-based test)

**Goal.** Ship two real state-safety tools — `freeze(obj)`, which returns a deeply immutable snapshot, and `Ledger`, an append-only record that never hands out its internal list — and prove the safety property with `hypothesis`, not just examples. This is the first time your toolkit defends an invariant against *all* inputs, not a handful you thought of.

#### Predict (on paper, before any code)

```python
def freeze(obj: Any) -> Any:
    """Return a deeply immutable snapshot of ``obj``.

    - list / tuple  -> tuple of frozen items
    - dict          -> tuple of (key, frozen-value) pairs, sorted by repr(key)
    - set / frozenset -> frozenset of frozen items
    - anything else -> returned unchanged (assumed already immutable)

    The result cannot be mutated, so it is safe to hand out or to keep as a
    "what the state was at time T" record that no alias can corrupt.

    >>> freeze([1, [2, 3]])
    (1, (2, 3))
    >>> freeze({"b": 4, "a": 5})
    (('a', 5), ('b', 4))
    """
    if isinstance(obj, (list, tuple)):
        return tuple(freeze(item) for item in obj)
    if isinstance(obj, dict):
        return tuple(sorted(((k, freeze(v)) for k, v in obj.items()),
                            key=lambda kv: repr(kv[0])))
    if isinstance(obj, (set, frozenset)):
        return frozenset(freeze(item) for item in obj)
    return obj


class Ledger:
    """An append-only record of events. Reading never exposes internal state.

    ``record`` adds an event. ``snapshot`` returns a COPY of the events, so a
    caller who mutates the returned list cannot corrupt the ledger. ``len``
    reports how many events were recorded.

    >>> log = Ledger()
    >>> log.record("created")
    >>> log.record("updated")
    >>> len(log)
    2
    >>> snap = log.snapshot()
    >>> snap.append("forged")      # caller mutates only their copy
    >>> len(log)                   # ledger is unaffected
    2
    """

    def __init__(self) -> None:
        self._events: list[Any] = []

    def record(self, event: Any) -> None:
        self._events.append(event)

    def snapshot(self) -> list[Any]:
        return list(self._events)   # copy at the boundary: hand out a copy

    def __len__(self) -> int:
        return len(self._events)
```

```python
from hypothesis import given, strategies as st

from pytoolkit.state import freeze, Ledger


def test_freeze_is_deeply_immutable():
    frozen = freeze([1, [2, 3], {"b": 4, "a": 5}])
    assert frozen == (1, (2, 3), (("a", 5), ("b", 4)))
    with_hashable = {frozen}          # provable immutability: it's hashable
    assert frozen in with_hashable


def test_freeze_snapshot_does_not_track_later_mutation():
    original = [1, 2, 3]
    snap = freeze(original)
    original.append(4)                # mutate AFTER freezing
    assert snap == (1, 2, 3)          # the snapshot is unchanged


def test_ledger_snapshot_cannot_corrupt_internal_state():
    log = Ledger()
    log.record("a")
    log.record("b")
    snap = log.snapshot()
    snap.append("forged")             # attacker mutates the returned list
    assert len(log) == 2              # ledger's own state is intact
    assert log.snapshot() == ["a", "b"]


# Property-based: the invariant must hold for ANY list of events.
@given(st.lists(st.integers()))
def test_ledger_length_equals_events_recorded_for_any_input(events):
    log = Ledger()
    for e in events:
        log.record(e)
    # Adversarially mutate a snapshot; the ledger must not change.
    stolen = log.snapshot()
    stolen.append(object())
    stolen.clear()
    assert len(log) == len(events)
    assert log.snapshot() == events
```

## Assessment

**Format.** A 90-minute practical, plus submission of your three labs' `PREDICT.md` files and your CI-green `pytoolkit`. The practical hands you a short unfamiliar program with a state bug and asks you to run the full loop: **predict, locate, fix, prove**. You may run code, but the score is on your judgment trail, not on getting a green bar. A passing green bar with an empty or hand-wavy prediction/reasoning trail **fails** the assessment.

**Gaming-resistance design.** You cannot pass by (a) making tests green without explaining the mechanism, (b) copying the reference fix without predicting the bug first, or (c) fixing the symptom with reflexive `deepcopy` without naming the accidental sharing. Each rubric row requires an artifact that a working-but-unexplained program cannot produce: a *pre-run* written prediction, a *cited mechanism*, a *captured failure* of the buggy version, and a *test that distinguishes* correct from buggy.

**The practical task (representative).** You are given:

```python
class Inventory:
    def __init__(self, starting=None):
        self.stock = starting or {}
    def restock(self, item, n):
        self.stock[item] = self.stock.get(item, 0) + n
    def report(self):
        return self.stock

def make_two_stores(seed):
    return Inventory(seed), Inventory(seed)

a, b = make_two_stores({"apples": 5})
a.restock("apples", 3)
# QUESTION: what is b.report()? Why? Fix so the two stores are independent.
```

You must: (1) **predict** `b.report()` and state the mechanism *before running*; (2) **locate** the exact line that causes the coupling and name why; (3) **fix** it so the two stores never share a dict, without over-copying; (4) **prove** with a test that fails on the original and passes on your fix.

### Rubric (graded on the judgment trail, not "it runs")

| Dimension | Fail (0) | Developing (1) | Proficient (2) | Mastery (3) |
|---|---|---|---|---|
| **Predict (pre-run)** | No written prediction, or written after running | Prediction present but no mechanism, or mechanism wrong | Correct prediction of `b.report()` with a correct one-line mechanism (shared dict via `starting or {}` aliasing) | Correct prediction **and** correctly anticipates the second-order case (both share the *same* dict object, so `b` also shows `apples: 8`), citing identity |
| **Locate** | Points at the wrong line or "somewhere in restock" | Names `__init__` region but not the aliasing operator | Identifies `self.stock = starting or {}` as binding both instances to the one passed-in dict | Identifies it **and** explains why `or {}` doesn't help here (the truthy dict is returned as-is, aliased), distinguishing from the mutable-default variant |
| **Fix** | No fix, or breaks other behavior | Fix works but over-copies (e.g. `deepcopy` everywhere) with no rationale | Copies at the boundary (`dict(starting) if starting else {}`), isolating the two stores | Correct minimal fix **and** a one-sentence justification of *where* the copy boundary belongs and its cost/benefit |
| **Prove** | No test, or a test that passes on both buggy and fixed code | Test passes on the fix but is not shown to fail on the original | A test that **fails on the original and passes on the fix**, with the captured original-failure output | The above **plus** a property-based test asserting independence for *any* seed dict |
| **Mechanism vocabulary** | Uses "copy"/"reference" interchangeably and incorrectly | Mostly correct but conflates `is`/`==` or "mutate"/"rebind" once | Uses identity vs. value and mutate-in-place vs. rebind correctly throughout | Teaches it: explains the bug to an imagined teammate in ≤3 sentences with no wrong term |

**Passing bar:** ≥ 2 in every row, and the **Prove** row must be ≥ 2 (a fix you cannot demonstrate as distinguishing buggy from correct does not count as a fix). Total ≥ 11/15 with no zero rows.

**Why this resists gaming:** the two artifacts a lucky-green submission lacks are the *pre-run prediction with mechanism* and the *captured failure of the original*. Both are impossible to backfill convincingly, because the prediction must commit to `b.report()` before you could have seen it, and the captured failure requires you to have understood the bug well enough to reproduce it on demand.

## Elle pacing notes

*Elle is the course's pacing intelligence. These notes name where learners wall, how to reroute, and when to accelerate — and which struggle is the productive kind we protect versus the blocked kind we clear.*

**The wall (expected, productive — do not clear it too fast).** The dominant wall is the box model of variables carried in from prior languages or intuition: "`b = a` copies." Roughly two-thirds of learners hit Lab 2 still holding it, and the mutable-default bug in Snippet A *offends* them — they are certain `add_item("b")` returns `["b"]`. **This offense is the productive struggle. Protect it.** The learner who is confidently wrong, predicts on paper, and then sees `["a", "b"]` print has the misconception surgically removed. Do not preempt this by explaining the answer before they predict. The paper prediction is the anesthetic-free extraction; it works precisely because they committed.

**The wall that is blocked, not productive (clear it fast).** Environment friction: `pip install -e` failing, `pytest` not finding `pytoolkit` due to `src/` layout, `hypothesis` not installed, CI YAML indentation. None of this teaches state; it just burns hours and morale. **Reroute immediately** — give the exact `pyproject.toml` and directory tree from the Labs preamble, confirm `pip install -e ".[dev]"` succeeds and `pytest -q` collects tests, *before* Lab 1's concepts. If a learner is 40 minutes into Lab 1 fighting imports, that is a blocked wall; hand them the working scaffold and move on.

**Reroute for the `is`/small-int detour.** A predictable rabbit hole is Lab 1 row 4 (`1000 is 1000`), where a learner gets a surprising `True` in one context and `False` in another and tries to derive the *rule* for when caching happens. **This is a trap for the completionist.** Reroute: the correct takeaway is not "here is the caching rule" but "identity of immutable values is an implementation detail I must never write code against — so `==` for value, `is` for `None`/`True`/`False` only." Redirect energy from *predicting the cache* to *never depending on it*. If they've spent more than ten minutes hunting the caching boundary, that's the signal.

**Accelerate conditions.** A learner who (a) predicts all six rows of Lab 1 correctly *including* naming row 4 as "it depends and I must not depend on it," and (b) writes the mutable-default one-line rule unprompted before Lab 2, already owns the model. **Accelerate:** let them skip the falsification step in Lab 2 (they don't need to see the bug fail to believe it), and send them straight into Lab 3's hypothesis property, which is the real stretch. Offer the optional extension: make `freeze` handle nested `Ledger` objects, or make `Ledger` reject unhashable events. Do not make fluent learners grind the falsification drills built for the wall they've already cleared.

**Where reasoning quietly breaks (watch the trail, not the bar).** The dangerous learner is the one whose tests are green and whose `PREDICT.md` is thin. They pattern-matched their way to a passing fix without the model. The tell is the **Locate** and **Mechanism** rows of the assessment: they say "I added `dict()`" but cannot say *why* `starting or {}` aliased, or they use "reference" and "copy" as synonyms. **This is blocked, not productive, and it is invisible in the green bar** — which is exactly why the assessment grades the trail. If Elle sees green labs but vocabulary conflation, route the learner back to Lesson 2's `is`/`==` worked example and the Lab 2 falsification step they skipped, before the assessment, not after.

## Three-tier reading

*Subject: the interpreter you just spent 14 hours reading, and the toolkit you just started shipping, are made of other people's unpaid labor.*

**Tier 1 — material ground (verifiable facts).** CPython, the interpreter that ran every line in this module — that tokenized your `x = 1`, cached your small integers, and executed your `dis` output — is free and open-source software, developed in the open and maintained substantially by volunteers and a small number of funded contributors. `pytest`, which you used to prove every claim in every lab, and `hypothesis`, which found the counterexample your example-tests missed, are open-source projects maintained largely by volunteers; `hypothesis` was created by a single developer (David MacIver) and grew through years of largely unpaid work. Python's own package index, PyPI, distributes billions of downloads a month on infrastructure run by the non-profit Python Software Foundation. These are checkable facts: read the `LICENSE` files, the `AUTHORS` files, the contributor graphs, the foundations' funding disclosures. You did not pay for any of it, and you used all of it today.

**Tier 2 — what the field suppresses (what boosters can't say and critics idealize).** The booster story is "community" — a warm, self-sustaining commons where everyone contributes. What that framing suppresses is the shape of the actual exchange: the overwhelming majority of the industry, including companies worth trillions, *extracts* from these projects — depends on them in production, ships them inside paid products — without *contributing* back in code, money, or maintenance labor. "Community" makes a labor relationship sound like a potluck. The 2014 Heartbleed vulnerability in OpenSSL — a library securing much of the internet — was maintained by a tiny, underfunded team; the 2022 `log4j` and the 2024 `xz` backdoor incidents showed the same fault line: critical infrastructure resting on one or two exhausted, often unpaid, maintainers. The critics' idealization is the mirror image: that maintainers are noble martyrs who want nothing, that "do it for love" is sustainable, that burnout is a personal failing rather than a structural outcome of extraction-without-contribution being the *norm*, not the exception. Both stories let the extractor off the hook. The verifiable middle is harder: you are, starting this module, a beneficiary of a subsidy paid in other people's unpaid time.

**Tier 3 — sit with this.** Your `pytoolkit` — the thing you are building to become an engineer who outpaces the field — will, by the end of this course, sit on a stack of dependencies maintained by specific people you will never meet and, almost certainly, never thank. Some of them are tired. Some will quit. The question is not "should open source be paid?" — that's a policy debate you can hide inside. The question you cannot unknow is narrower and it is *yours*:

**When your toolkit ships green on the backs of maintainers you'll never name, what — concretely, this year, in an amount you'd actually part with — do you owe the commons you build on? And if the honest answer is "nothing," what does that make the word "community"?**
