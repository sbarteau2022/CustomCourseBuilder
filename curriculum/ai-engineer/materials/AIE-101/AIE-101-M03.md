## Where this module sits in the arc

In M01 you learned that a value is an **object** — a region of memory with an identity, a type, and a value — and that names are labels tied to objects. In M02 you learned that a function is an object too, with its own captured state. This module takes the last step of the "everything is an object" descent: you build your own **types**. A `class` is the machinery Python gives you to mint objects that carry their own data *and* their own behavior, and to plug into the operators and built-ins the interpreter already knows how to call.

The single hardest reframe in this module is this: **the interpreter does not "know" how to add, compare, print, or iterate your objects. It knows how to *look up a method with a special name* and call it.** `a + b` is not arithmetic; it is a lookup of `type(a).__add__`. `len(x)` is a lookup of `type(x).__len__`. `for y in xs` is a lookup of `type(xs).__iter__`. These special-named methods — **dunders** ("double underscore") — are the protocol between your object and the language. Duck typing is the consequence: Python never asks *what class* an object is, only *whether it has the method being called*. Once you see that, `typing.Protocol` stops being magic — it is just a way to write that "whether it has the method" question down so a **type checker** can answer it before you run.

And that is the second spine of this module: **type hints are a machine-checked contract, checked by a tool, not by the interpreter.** Python does not enforce `x: int` at runtime — the hint is erased. `mypy` (or `pyright`) reads your hints and proves, statically, that the shapes fit. This course's stance — *predict, then verify* — gets a new instrument here: you will **predict the type error on paper**, then run the checker to confirm the machine agrees. A green `mypy` run is a proof about *all* code paths, including the ones your tests never exercised.

The module closes on a judgment, not a technique: **when is a class the right tool, and when is a function enough?** Beginners reach for classes reflexively because object-oriented is what they were taught "real code" looks like. You will learn to reach for the smallest thing that carries the contract — and to say *why*.

By the end of M03 your `pytoolkit` package has three new shipped, tested, type-checked modules: `pytoolkit/money.py` (a value object built by hand), `pytoolkit/render.py` (a protocol and the functions typed against it), and `pytoolkit/result.py` (a typed container, and the class-vs-function decision made explicit). CI now runs `mypy --strict` as well as `pytest`.

## Lessons

### Lesson 1 — A class is a factory with a shared namespace

**Teaching text.**

A `class` statement does two things at once, and separating them dissolves most beginner confusion. First, it **runs a block of code in a fresh namespace** and packages the result into a *class object* (itself an object — `type(Money)` is `type`). Second, it gives you a **factory**: calling that class object, `Money(500)`, builds a new *instance*, runs `__init__` to populate the instance's own namespace, and hands the instance back.

So there are two namespaces in play, and attribute lookup walks them in order:

- The **instance namespace** — the per-object data. By default this is a dict, `instance.__dict__`; with `__slots__` it is a fixed set of named slots (no dict, less memory, and typos become errors). `self._cents = cents` writes here.
- The **class namespace** — shared by *all* instances. Methods live here. `Money.__add__` is one object, shared by every `Money` you ever create; the instance does not get its own copy.

When you write `m.method(...)`, Python looks up `method` on the instance first, then on the class, then up the base classes (the MRO — method resolution order). It finds `__add__` on the class. When you write `m._cents`, it finds it on the instance. This is the same aliasing model from M01, one level up: methods are shared objects; instance data is per-object.

`self` is not a keyword. It is an ordinary parameter — the instance, passed as the first argument by the `instance.method()` call syntax. `m.render()` is sugar for `type(m).render(m)`. Once you see `self` as "the instance, passed explicitly," the mystery evaporates: a method is just a function that lives in the class namespace and takes the instance as its first argument.

**Worked example.**

```python
>>> class Counter:
...     kind = "counter"          # class namespace: shared by all instances
...     def __init__(self, start):
...         self.n = start        # instance namespace: per object
...     def bump(self):
...         self.n += 1
...
>>> a = Counter(0)
>>> b = Counter(100)
>>> a.__dict__                    # a's own data only
{'n': 0}
>>> b.__dict__
{'n': 100}
>>> Counter.bump is a.bump.__func__   # one shared function object
True
>>> a.kind, b.kind                # both read the SAME class attribute
('counter', 'counter')
>>> a.kind = "special"            # writes an INSTANCE attribute, shadowing
>>> a.kind, b.kind, Counter.kind  # only a is shadowed; class unchanged
('special', 'counter', 'counter')
>>> Counter.bump(a)               # method call, desugared: pass the instance
>>> a.n
1
```

The last two lines are the lesson: `a.bump()` and `Counter.bump(a)` do the same thing, because `self` *is* `a`. And assigning `a.kind` did not change the class attribute — it created a new instance attribute that shadows it for `a` only. Attribute *reads* fall through to the class; attribute *writes* land on the instance.

**Named misconceptions.**

- *"`self` is a special keyword the language fills in."* It is a plain parameter, named `self` only by convention. The `instance.method()` call syntax binds the instance to the first parameter, whatever you name it. `def bump(this):` works identically (and is discouraged only because readers expect `self`).
- *"Each instance has its own copy of the methods."* No. Methods live once in the class namespace and are shared. Only the data in `self` is per-instance. This is why adding a method to a class affects instances that already exist.
- *"Class attributes are like instance defaults."* They are shared, not copied. A *mutable* class attribute (`items = []` at class level) is the class-level cousin of M01's mutable-default bug: every instance that reads-then-mutates it corrupts the one shared list. Class attributes are for constants and shared config, not per-instance mutable state.
- *"`__slots__` is just an optimization I can ignore."* It also changes behavior: with `__slots__` there is no instance `__dict__`, so `m.typo = 1` raises `AttributeError` instead of silently creating a new attribute. That is a correctness win — a whole class of typo bugs becomes a loud error.

### Lesson 2 — Dunder methods are the protocol the interpreter calls

**Teaching text.**

Here is the reframe that this whole module turns on. The interpreter has no built-in idea of how to add, compare, print, hash, measure the length of, or iterate over *your* object. What it has is a fixed rule: **for each operator and built-in, look up a specifically-named method on the object's type and call it.** These specially-named methods are **dunders**. You do not call them directly; the *syntax* calls them for you.

| You write | The interpreter calls | Bytecode you'd see with `dis` |
|---|---|---|
| `a + b` | `type(a).__add__(a, b)` | `BINARY_OP` `(+)` |
| `a == b` | `type(a).__eq__(a, b)` | `COMPARE_OP` `(==)` |
| `repr(a)`, REPL echo | `type(a).__repr__(a)` | — |
| `len(a)` | `type(a).__len__(a)` | `CALL` to `len`, which calls the dunder |
| `for x in a` | `type(a).__iter__(a)` | `GET_ITER` |
| `hash(a)`, `a` as dict key | `type(a).__hash__(a)` | — |

Two dunders form a **contract you must not break**: `__eq__` and `__hash__`. The rule is: **if `a == b`, then `hash(a) == hash(b)` must also be true.** Dicts and sets rely on it — they use the hash to pick a bucket, then `==` to confirm a match within the bucket. If two equal objects hash differently, a set can hold both (it looked in different buckets and never noticed they were equal), and a dict lookup can miss a key that is present. Python enforces one half of this automatically: **defining `__eq__` sets `__hash__` to `None`**, making your object unhashable, precisely so you cannot *accidentally* keep the default identity-based hash that would violate the contract. If your object is a value (immutable, compared by value), you must supply a matching `__hash__`; if it is mutable, leave it unhashable.

`__eq__` should return `NotImplemented` (the singleton, not `raise NotImplementedError`) when it does not know how to compare against the other type. Returning `NotImplemented` tells Python "try the other operand's `__eq__`, and if that also declines, fall back to identity" — which is why `Money(500) == "500"` correctly yields `False` instead of crashing.

**Worked example.**

A value object with the four dunders, and a demonstration that the interpreter dispatches to them:

```python
>>> class Money:
...     __slots__ = ("_cents", "_currency")
...     def __init__(self, cents, currency="USD"):
...         self._cents = cents
...         self._currency = currency
...     def __repr__(self):
...         return f"Money(cents={self._cents!r}, currency={self._currency!r})"
...     def __eq__(self, other):
...         if not isinstance(other, Money):
...             return NotImplemented
...         return (self._cents, self._currency) == (other._cents, other._currency)
...     def __hash__(self):
...         return hash((self._cents, self._currency))
...     def __add__(self, other):
...         if not isinstance(other, Money):
...             return NotImplemented
...         return Money(self._cents + other._cents, self._currency)
...
>>> a = Money(500); b = Money(500)
>>> a == b            # calls a.__eq__(b): equal value...
True
>>> a is b            # ...but distinct objects (the M01 distinction, revisited)
False
>>> {a, b}            # hash agrees with ==, so the set dedups to ONE element
{Money(cents=500, currency='USD')}
>>> a + b             # calls a.__add__(b)
Money(cents=1000, currency='USD')
>>> a == "500"        # __eq__ returns NotImplemented -> False, no crash
False
```

Ask the machine what `a + b` compiles to, exactly as you did with `dis` in M01:

```python
>>> import dis
>>> dis.dis(compile("a + b", "<repl>", "eval"))
  ...
              LOAD_NAME                0 (a)
              LOAD_NAME                1 (b)
              BINARY_OP                0 (+)
              RETURN_VALUE
```

There is no "add" instruction that knows about money. There is `BINARY_OP (+)`, which at runtime looks up `__add__` on the left operand's type. Your `Money.__add__` *is* what `+` means for money. (Opcodes are version-specific — run this on your own 3.12 interpreter and read what you get; the habit, not the exact output, is the point.)

Now watch the contract break, because seeing it break is how you learn to trust it:

```python
>>> class BadMoney(Money):
...     __slots__ = ()
...     def __hash__(self):
...         return id(self)        # BUG: hash by identity, but == by value
...
>>> x = BadMoney(500); y = BadMoney(500)
>>> x == y                          # equal by value
True
>>> len({x, y})                     # but different hashes -> set keeps BOTH
2
```

Two objects that are `==` sit in the set as if they were different. Nothing raised. The set is silently wrong. This is why the `__eq__`/`__hash__` contract is a *contract* and not a suggestion.

**Named misconceptions.**

- *"`a + b` does arithmetic; the class just customizes it."* There is no arithmetic to customize. `+` *is* a call to `__add__` from the very start; for `int` the built-in `int.__add__` happens to do machine addition. Your object is not a special case of "real" addition — it is the same mechanism.
- *"I defined `__eq__`, so my objects work in sets."* Defining `__eq__` alone makes them *unhashable* — Python sets `__hash__` to `None`. You get `TypeError: unhashable type` the moment you put one in a set. You must define `__hash__` too (for value objects) or accept unhashability (for mutable ones).
- *"`__hash__` can return anything as long as it's fast."* It must be *consistent with `__eq__`*: equal objects, equal hashes. It also must not change over an object's lifetime while it is in a set/dict — which is why only *immutable* objects should be hashable. A hash that "works" but violates equality is worse than none: it fails silently and only on collisions.
- *"Return `NotImplementedError` from `__eq__` when types don't match."* Return the singleton `NotImplemented` (no exception). Raising `NotImplementedError` turns `x == y` into a crash; returning `NotImplemented` lets Python try the reflected operation and fall back to `False`. They look alike and behave oppositely.

### Lesson 3 — Duck typing, and Protocols that make it checkable

**Teaching text.**

Because the interpreter dispatches by *method name*, not by class, Python never asks "is this a `Duck`?" It asks "does this respond to `.quack()`?" This is **duck typing**: if it walks like a duck and quacks like a duck, it is a duck *for the purposes of the code calling `.quack()`*. A function that does `item.render()` works on *any* object with a `render()` method — `Heading`, `Bullet`, a class you haven't written yet, a mock in a test. You get polymorphism for free, with no base class and no inheritance. This is **structural** typing: what matters is the shape (the methods present), not the name (the class in the hierarchy). Contrast **nominal** typing (Java, C++), where an object fits an interface only if its class was *declared* to implement it.

Duck typing's strength — anything with the right shape works — is also its weakness: the requirement is invisible. Nothing writes down "`render_all` needs objects with a `render() -> str` method." You discover the requirement by reading the body, or by an `AttributeError` at runtime when you pass the wrong thing. `typing.Protocol` fixes this: it lets you **write the shape down as a type** so a checker can verify it *before* you run.

```python
from typing import Protocol

class Renderable(Protocol):
    def render(self) -> str: ...
```

Now `def render_all(items: list[Renderable]) -> str:` states the contract. `mypy` will confirm — statically, across all call sites — that every object you pass has a `render(self) -> str`. A class satisfies `Renderable` **without declaring anything**: no `class Heading(Renderable)`, no registration. If it has the method with the right signature, it fits. That is duck typing, made checkable. This is the opposite of a nominal base class (an ABC), where a type fits only if it explicitly inherits.

Two sharp edges you must predict:

1. **`@runtime_checkable` is shallow.** Decorate a Protocol with `@runtime_checkable` and `isinstance(x, Renderable)` works at runtime — but it checks only that the *method names exist*, not their signatures, argument counts, or return types. An object whose `render(self, extra)` takes a wrong argument still passes `isinstance`. The static checker catches the signature; `isinstance` does not. Never lean on `isinstance` against a Protocol for anything the type checker should be doing.
2. **`list` is invariant.** A `list[Heading]` is **not** an acceptable `list[Renderable]`, even though every `Heading` *is* a `Renderable`. This surprises everyone. The reason is soundness: if `list[Heading]` were usable as `list[Renderable]`, a function taking `list[Renderable]` could `.append(a_Bullet)` into your list of headings, and now your `list[Heading]` contains a `Bullet`. To stay safe, mutable containers are **invariant** — the element type must match exactly. The fix when you only *read* the container is to type the parameter as `Sequence[Renderable]` (read-only, and **covariant**), which *does* accept a `list[Heading]`.

**Worked example.**

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Renderable(Protocol):
    def render(self) -> str: ...

class Heading:
    def __init__(self, text): self.text = text
    def render(self) -> str: return f"# {self.text}"

# Structural fit: Heading was never declared Renderable, yet:
print(isinstance(Heading("Hi"), Renderable))   # True (name 'render' present)

class NoRender:
    def draw(self): return "x"
print(isinstance(NoRender(), Renderable))       # False (no 'render')

# The shallowness gap: wrong SIGNATURE still passes isinstance
class Weird:
    def render(self, extra): return "x"         # takes an extra arg
print(isinstance(Weird(), Renderable))          # True !!  isinstance is shallow
# ...but mypy, checking `render_all([Weird()])`, WOULD reject Weird.
```

Under `mypy`, the invariance edge:

```python
def render_all(items: list[Renderable]) -> str:
    return "\n".join(i.render() for i in items)

hs: list[Heading] = [Heading("a")]
render_all(hs)   # mypy ERROR: list[Heading] is not list[Renderable] (invariant)
```

```
error: Argument 1 to "render_all" has incompatible type "list[Heading]";
       expected "list[Renderable]"  [arg-type]
note: "list" is invariant -- see .../common_issues.html#variance
note: Consider using "Sequence" instead, which is covariant
```

Change the parameter to `Sequence[Renderable]` and the same call type-checks clean — because a read-only sequence cannot smuggle a `Bullet` into your `list[Heading]`.

**Named misconceptions.**

- *"To be `Renderable`, a class must inherit from it."* No — that is nominal typing (an ABC). A Protocol is structural: a class fits by *having the methods*, with no inheritance and no registration. Inheriting a Protocol is allowed (it lets the checker verify you got the shape right) but never required to satisfy it.
- *"`@runtime_checkable` gives me real runtime type safety."* It gives you a *name-presence* check, nothing deeper. Signatures, argument counts, and return types are invisible to `isinstance`. Treat `isinstance(x, SomeProtocol)` as "has these method names," not "conforms to this contract."
- *"If `Heading` is a `Renderable`, then `list[Heading]` is a `list[Renderable]`."* Not for mutable containers. `list` is invariant: the element types must match exactly, because a writable `list[Renderable]` could have the wrong element appended. Use `Sequence`/`Iterable` (covariant, read-only) in parameters when you only iterate.
- *"Protocols are just documentation."* They are checked. `mypy`/`pyright` verify every call site against the Protocol and fail the build on a mismatch. A Protocol is an enforced contract, checked by a tool — not a comment.

### Lesson 4 — Type hints as a machine-checked contract, and when a class is enough

**Teaching text.**

Type hints are annotations the *interpreter ignores* and a *checker enforces*. At runtime, `def f(x: int) -> str:` does not verify that `x` is an `int`; call `f("hello")` and Python runs it happily. The hint lives in `f.__annotations__` as data. The enforcement comes from a **separate program** — `mypy` or `pyright` — that reads your whole codebase, infers types, and proves the shapes fit before you ship. This is the same predict-then-verify loop as your tests, but static: a green `mypy --strict` run is a proof about *every* code path, including the branches your tests never hit.

That last point is why typing belongs in this course from the start, not as an afterthought. A test proves a claim about the *inputs you thought to write*. A type check proves a claim about *all inputs of the declared types*. They are complementary instruments: tests catch logic bugs on real values; the checker catches shape bugs on all values. You reach for both.

The verification skill you build here is **predicting the type error before running the checker.** Given a snippet, you state on paper: "line 12 is an error — `list[Heading]` is not `list[Renderable]` because `list` is invariant." Then you run `mypy` and confirm the machine agrees, reading its message as evidence. Two tools make this precise:

- `reveal_type(x)` — a checker-only pseudo-function (you never actually run it) that makes `mypy` print the type it inferred for `x`. Your instrument for "what does the checker think this is?"
- **narrowing** — after `if isinstance(r, Ok):`, the checker *narrows* `r` from `Ok[int] | Err` to `Ok[int]` inside the branch, so `r.value` type-checks there but not outside. Accessing `.value` on the un-narrowed union is an error, because `Err` has no `value`.

`--strict` is not optional rigor for this course; it is the point. It turns on "no implicit `Any`," "every function annotated," "no untyped calls," and more. `Any` is the type checker's off switch — a value typed `Any` silences all checks on it. Reaching for `Any` to make an error go away is the typed-code equivalent of `except: pass`. Sometimes correct, usually a smell.

**And now the judgment this module has been building toward: when is a class the right tool, and when is a function enough?** The honest default is *a function is enough far more often than beginners think.* Reach for a class when you have **data and behavior that travel together and must stay consistent** — an identity, an invariant to protect, multiple methods sharing state. Reach for a `@dataclass` when you have **data that mostly just needs to be held, compared, and printed** — it generates `__init__`, `__repr__`, `__eq__` (and `__hash__` if `frozen=True`) for you, so you write the fields and stop. Reach for a `Protocol` when you have **behavior you want many unrelated types to provide** without an inheritance hierarchy. Reach for a plain **function** when you have **a transformation** — inputs to outputs, no state to keep between calls. The anti-pattern is the class with one method and no state that isn't `__init__`: that is a function wearing a costume. The signal is *state that outlives a single call and an invariant that must hold across methods*. No state, no invariant, one operation — write the function.

**Worked example.**

A typed container where narrowing does real work:

```python
from typing import Generic, TypeVar
T = TypeVar("T")

class Ok(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value

class Err:
    def __init__(self, error: str) -> None:
        self.error = error

Result = Ok[T] | Err

def parse_int(s: str) -> Result[int]:
    try:
        return Ok(int(s))
    except ValueError:
        return Err(f"not an int: {s!r}")

r = parse_int("42")
reveal_type(r)        # mypy note: Revealed type is "Ok[int] | Err"
print(r.value)        # mypy ERROR: Item "Err" of "Ok[int] | Err" has no attribute "value"

if isinstance(r, Ok):
    print(r.value)    # OK here: r narrowed to Ok[int] inside the branch
```

```
note: Revealed type is "pytoolkit.result.Ok[builtins.int] | pytoolkit.result.Err"
error: Item "Err" of "Ok[int] | Err" has no attribute "value"  [union-attr]
```

The checker forces you to handle the `Err` case before touching `.value` — a whole class of `AttributeError`-in-production bugs, made impossible at build time. And the class-vs-function call: `Ok`/`Err` *earn* being classes because they carry different data and a shared shape you branch on. But `parse_int` is a plain function — a transformation, no state kept between calls. If you had wrapped `parse_int` in a `Parser` class with one method and no fields, you'd have added a costume and no contract.

The `@dataclass` re-ascent — the same value-object shape as `Money`, generated instead of hand-written:

```python
from dataclasses import dataclass

@dataclass(frozen=True)     # frozen -> immutable -> __hash__ generated too
class Point:
    x: int
    y: int
    def moved(self, dx: int, dy: int) -> "Point":
        return Point(self.x + dx, self.y + dy)

p = Point(1, 2)
p == Point(1, 2)            # True  — __eq__ generated
hash(p) == hash(Point(1, 2))  # True — __hash__ generated (because frozen)
p.x = 9                     # raises FrozenInstanceError — immutability enforced
```

You hand-built `Money`'s dunders in Lab 1 so you understand what `@dataclass(frozen=True)` *generates*. That is the descend-then-re-ascend: build the dunders by hand to command the tool that writes them for you.

**Named misconceptions.**

- *"Type hints make my code run safer / faster."* At runtime they do neither — they are erased data. Safety comes from running the *checker*. A program with perfect hints and no `mypy` in CI has documentation, not enforcement.
- *"If it type-checks, it's correct."* The checker proves *shapes*, not *logic*. `def add(a: int, b: int) -> int: return a - b` type-checks perfectly and is wrong. Types and tests catch different bugs; you need both.
- *"`Any` is just 'unknown type,' harmless."* `Any` disables checking on that value and everything it flows into. It is a hole in the contract that spreads. Prefer `object` (which forces you to narrow) or a real Protocol; reserve `Any` for genuine dynamic boundaries and justify it.
- *"Real engineers use classes; functions are for beginners."* Backwards. Reaching for a class when a function suffices adds state, surface area, and lifecycle you must now maintain. The senior move is the *smallest* construct that carries the contract. A class earns its place by holding state with an invariant across methods — not by looking professional.
- *"A `@dataclass` is a lesser class."* It is a normal class with the boilerplate generated. You can add methods, properties, validation (`__post_init__`), and it participates in inheritance and Protocols like any class. `frozen=True` gives you a correct, hashable value object for free — exactly what you hand-wrote in Lab 1.

```python
"""A value object built by hand: Money, and the __eq__/__hash__ contract."""
from __future__ import annotations


class Money:
    """An immutable amount of money in integer minor units (cents).

    Value semantics: two Money objects with the same cents and currency are
    equal (``==``) and hash equal, so they deduplicate in sets and collide
    as dict keys — even though they are distinct objects (``is`` is False).

    >>> Money(500) == Money(500)
    True
    >>> Money(500) is Money(500)
    False
    >>> Money(500) + Money(250)
    Money(cents=750, currency='USD')
    >>> len({Money(500), Money(500)})
    1
    """

    __slots__ = ("_cents", "_currency")

    def __init__(self, cents: int, currency: str = "USD") -> None:
        if not isinstance(cents, int):
            raise TypeError(f"cents must be int, got {type(cents).__name__}")
        self._cents = cents
        self._currency = currency

    @property
    def cents(self) -> int:
        return self._cents

    @property
    def currency(self) -> str:
        return self._currency

    def __repr__(self) -> str:
        return f"Money(cents={self._cents!r}, currency={self._currency!r})"

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Money):
            return NotImplemented
        return self._cents == other._cents and self._currency == other._currency

    def __hash__(self) -> int:
        # Consistent with __eq__: equal Money -> equal hash. Immutable, so
        # the hash is stable for the object's whole life.
        return hash((self._cents, self._currency))

    def __add__(self, other: Money) -> Money:
        if not isinstance(other, Money):
            return NotImplemented
        if other._currency != self._currency:
            raise ValueError(f"cannot add {self._currency} and {other._currency}")
        return Money(self._cents + other._cents, self._currency)


def total(items: list[Money]) -> Money:
    """Sum a non-empty list of same-currency Money. Empty is undefined."""
    if not items:
        raise ValueError("total() of empty list is undefined (no currency)")
    acc = items[0]
    for m in items[1:]:
        acc = acc + m
    return acc
```

```python
"""Duck typing made checkable: a Protocol and functions typed against it."""
from __future__ import annotations

from typing import Protocol, Sequence, runtime_checkable


@runtime_checkable
class Renderable(Protocol):
    """Structural type: anything with ``render(self) -> str`` satisfies it.

    No inheritance or registration needed — a class fits by having the method.
    ``@runtime_checkable`` enables ``isinstance``, but note isinstance checks
    only that the method NAME exists, not its signature (see the tests).
    """

    def render(self) -> str: ...


def render_all(items: Sequence[Renderable]) -> str:
    """Render each item and join with newlines.

    Typed as ``Sequence`` (read-only, covariant) so a ``list[Heading]`` is
    accepted: we only iterate, never append, so no unsafe write is possible.
    """
    return "\n".join(item.render() for item in items)


class Heading:
    def __init__(self, text: str) -> None:
        self.text = text

    def render(self) -> str:
        return f"# {self.text}"


class Bullet:
    def __init__(self, text: str) -> None:
        self.text = text

    def render(self) -> str:
        return f"- {self.text}"
```

```python
"""When a class earns its keep: a typed Result, plus a frozen dataclass."""
from __future__ import annotations

from dataclasses import dataclass
from typing import Callable, Generic, TypeVar

T = TypeVar("T")
U = TypeVar("U")


@dataclass(frozen=True)
class Point:
    """Immutable value object — generated __init__/__repr__/__eq__/__hash__.

    This is the @dataclass re-ascent of Lab 1's hand-built Money: frozen=True
    makes it immutable and hashable, so it works as a dict key and in sets.
    """

    x: int
    y: int

    def moved(self, dx: int, dy: int) -> "Point":
        return Point(self.x + dx, self.y + dy)


class Ok(Generic[T]):
    """The success arm of a Result: carries a value of type T."""

    __slots__ = ("value",)

    def __init__(self, value: T) -> None:
        self.value = value

    def map(self, f: Callable[[T], U]) -> "Ok[U]":
        return Ok(f(self.value))

    def unwrap(self) -> T:
        return self.value

    def __repr__(self) -> str:
        return f"Ok({self.value!r})"


class Err:
    """The failure arm of a Result: carries an error message, no value."""

    __slots__ = ("error",)

    def __init__(self, error: str) -> None:
        self.error = error

    def map(self, f: Callable[..., object]) -> "Err":
        return self  # map over an error is a no-op

    def unwrap(self) -> object:
        raise ValueError(f"unwrap() on Err: {self.error}")

    def __repr__(self) -> str:
        return f"Err({self.error!r})"


Result = Ok[T] | Err


def parse_int(s: str) -> Result[int]:
    """Parse ``s`` as an int without raising on bad input.

    A plain FUNCTION, deliberately: a transformation with no state kept
    between calls. Wrapping it in a one-method class would add a costume,
    not a contract.

    >>> parse_int("42").map(lambda n: n + 1).unwrap()
    43
    >>> parse_int("nope")
    Err("not an int: 'nope'")
    """
    try:
        return Ok(int(s))
    except ValueError:
        return Err(f"not an int: {s!r}")
```

## Elle pacing notes

*Elle is the course's pacing intelligence. These notes name where learners wall, how to reroute, and when to accelerate — and which struggle is the productive kind we protect versus the blocked kind we clear.*

**The wall that is blocked, not productive (clear it fast).** `mypy` environment and invocation friction: the checker not installed, `mypy` reporting "Cannot find implementation" for `pytoolkit` because of the `src/` layout and no editable install, `[tool.mypy]` not being read, or a flood of errors from a stray untyped file. **Reroute for the invariance rabbit hole.** Lab 2's list-invariance error (`list[Heading]` ≠ `list[Renderable]`) is a predictable trap for the thorough learner, who tries to derive the *full* variance rules — covariance, contravariance, `TypeVar` bounds — from one error message. **This is a trap for the completionist.** The correct takeaway is not the variance lattice; it is the *operational rule*: "mutable containers (`list`, `dict`, `set`) are invariant — match the element type exactly; when a parameter only reads, type it `Sequence`/`Iterable` and it accepts subtypes." ## Three-tier reading

*Subject: the type checker that just proved your code, the Protocol machinery you just used, and the frozen dataclass that wrote your dunders for you — none of it was inevitable, and much of it was built by people the "community" narrative renders invisible even as it depends on them.*

**Tier 1 — material ground (verifiable facts).** `mypy`, the checker that verified every type claim in this module, began as a research project by Jukka Lehtosalo and became a core tool of Python static analysis; `typing`, `Protocol`, and `TypeVar` — the machinery you used to make duck typing checkable — entered the standard library and the `typing_extensions` backport through years of PEP work (PEP 484, 544, 585, and more) authored and reviewed by a shifting set of contributors, some paid by employers with a stake, many not. `pyright`, the alternative checker, is built and funded by Microsoft; `mypy`'s maintenance has at various times been carried by Dropbox employees, by Python core developers, and by volunteers, with funding waxing and waning as corporate priorities shifted. `hypothesis`, which found the counterexamples your example-tests missed, and `pytest`, which ran every assertion, remain maintained largely by volunteers. These are checkable facts: read the PEP author lists, the `mypy` and `pyright` commit histories and their corporate email domains, the moments maintainers publicly noted funding starting or stopping. You did not pay for any of it, and you used all of it today.

**Tier 2 — what the field suppresses (what boosters can't say and critics idealize).** The booster story about typing is "the ecosystem matured" — as if type checkers *arose*, a natural evolution of the language. What that framing suppresses is that maturation is *labor*, and the labor was unevenly and precariously funded. `mypy` advanced fastest when a company (Dropbox) had a business reason to fund it, and slowed when that reason faded — the tool you now treat as bedrock had its velocity set by one firm's internal priorities, not by the needs of the millions who depend on it. This is the shape the word "community" hides: the pace and survival of critical tooling is often set by whichever corporation currently finds it convenient, and when convenience ends, the volunteers absorb the gap or the project stalls. The critics' idealization is the mirror image — that corporate funding is *contamination*, that "pure" volunteer open source is the authentic form, that taking a paycheck to maintain infrastructure is selling out. Both stories dodge the verifiable middle: the tools are neither a spontaneous commons nor a corporate product, but a fragile hybrid where trillion-dollar firms extract far more value than they return, fund selectively and revocably, and let the word "community" launder a labor relationship into a potluck. `pyright` being a well-funded Microsoft product while `mypy`'s funding flickers is not two success stories — it is the same extraction with different logos.

**Tier 3 — sit with this.** In this module you learned to reach for the *smallest* construct that carries the contract — a function over a class, when a class buys you nothing. You learned to name what a thing costs to maintain and to refuse the costume that adds surface area without value. You have, in other words, been trained to see maintenance as a real and unequal cost, and to allocate it deliberately. Now turn that exact lens outward. Every `mypy` run you make this year rides on maintenance labor that someone is paying for — sometimes a corporation with a quarter-to-quarter reason, sometimes a volunteer with none — and you will benefit identically whether that labor is sustainably funded or quietly burning out, because the tool is green either way. The green bar tells you nothing about who is tired.

**You have learned to judge, precisely, what a thing costs to maintain and who should bear it. When you apply that judgment to your own code and refuse to add a class that costs more than it's worth — and then run `mypy` on the backs of maintainers whose cost you never counted and whose funding you never checked — what is the name for a discipline that measures maintenance cost everywhere except where you're the one extracting it?**
