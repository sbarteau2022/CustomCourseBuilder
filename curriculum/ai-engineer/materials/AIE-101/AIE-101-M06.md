### Lesson 1 — Exceptions done right: the hierarchy, catching narrow, and chaining with `from`

**The teaching.** Every exception is a class, and classes form a hierarchy rooted at `BaseException`. The branch you almost always want is `Exception` and below: `ValueError`, `TypeError`, `LookupError` (parent of `IndexError` and `KeyError`), `ArithmeticError` (parent of `ZeroDivisionError`), `OSError` (parent of `FileNotFoundError`, `PermissionError`, `IsADirectoryError`). `BaseException` also covers `SystemExit` and `KeyboardInterrupt` — the exceptions Python raises when the program is told to *stop* — which is exactly why you never catch below `Exception` on purpose.

Two habits separate exception handling that helps from exception handling that hides. **Catch the narrowest type you can actually do something about.** `except FileNotFoundError:` says "I have a plan for exactly this." `except Exception:` says "I have a plan for anything," which is almost never true — it also catches the `NameError` from your own typo three lines up, the `TypeError` from a caller passing the wrong argument, and every bug you haven't written yet. **Bare `except:` is worse still**: it catches `SystemExit` and `KeyboardInterrupt` too, so a user's Ctrl-C inside your `try` block gets silently absorbed and the program that was supposed to quit keeps running.

The second habit is **chaining**. When you catch a low-level exception and raise a more meaningful one, `raise NewError(...) from original_exception` attaches `original_exception` to the new exception's `__cause__`. Python does this *implicitly* too — any exception raised inside an `except` block gets the exception being handled attached to its `__context__`, printed as "During handling of the above exception, another exception occurred." Explicit `from` overrides that with an intentional, meaningful cause; `from None` *suppresses* it entirely, which you use only when the low-level cause is truly uninformative noise (rare — usually you want it).

**Worked example — translating a low-level error into a domain error, without losing the evidence.**

```python
class ConfigError(Exception):
    """Raised when a config file exists but cannot be parsed."""


class ConfigNotFoundError(ConfigError):
    """Raised when the config path does not exist."""


def load_config(path):
    try:
        text = Path(path).read_text()
    except FileNotFoundError as e:
        raise ConfigNotFoundError(f"no config at {path}") from e
    try:
        return json.loads(text)
    except json.JSONDecodeError as e:
        raise ConfigError(f"{path}: invalid JSON at line {e.lineno}: {e.msg}") from e
```

Run this on a malformed file and Python prints **both** exceptions, in order, connected by the chain:

```
json.decoder.JSONDecodeError: Expecting property name enclosed in double quotes: line 1 column 2 (char 1)

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  ...
toolkit.config.ConfigError: config.json: invalid JSON at line 1: Expecting property name enclosed in double quotes
```

**Read a chained traceback bottom-up, then walk the chain upward.** The very last line is the exception that actually terminated the program — here, `ConfigError`, the one you wrote, with a message aimed at whoever reads this log. But the *cause* of it — the raw `JSONDecodeError` with the exact line and column — is preserved above it, not thrown away. A caller who only reads the last line gets a clear domain-level message; a caller (or you, later, with a debugger — Lesson 3) who reads the whole chain gets the raw evidence too. `except Exception: pass` would have made the entire chain vanish and returned `{}`, as if the file were valid and empty.

**Named misconceptions:**

- **"`except Exception: pass` is a safe way to keep the program running."** It is the single most dangerous line in this lesson, because it doesn't just hide the error you expected (a missing file, bad JSON) — it hides *every other exception that could ever occur in that block*, including a `NameError` from your own typo, a `TypeError` from a refactor that changed a function's signature, or a `KeyboardInterrupt`-adjacent situation your code has no business intercepting. A block that swallows everything makes your own future bugs invisible forever, not just today's expected failure.
- **"`raise NewError(str(e))` without `from` loses nothing important — Python still shows the chain automatically."** Python *does* attach an implicit `__context__` when you raise inside an `except` block, so you're right that nothing is lost *by default*. But `raise ... from None` is one keystroke away and is often reached for out of misplaced tidiness ("I don't want two tracebacks cluttering the log") — and that keystroke deletes the original exception's traceback entirely. Suppress a cause only when you've confirmed it's genuinely uninformative; when in doubt, chain explicitly with `from e` rather than relying on the implicit context or, worse, suppressing it.
- **"Bare `except:` is just a shorter spelling of `except Exception:`."** It is not — it also catches `SystemExit` (raised by `sys.exit()` and, at process end, by the interpreter) and `KeyboardInterrupt` (raised by Ctrl-C). A bare `except:` around a long-running loop means the user's Ctrl-C gets swallowed and the loop keeps going; this is the concrete, reproducible cost of the "shorter spelling."

### Lesson 2 — Structured logging: the instrument that survives shipping

**The teaching.** `print()` is fine for a five-line throwaway script and wrong for anything that ships. It has no levels (you can't turn off the noisy ones without deleting the line), no timestamps, no way to route output differently in development versus production, and it is either always on or manually stripped out before commit — which means the next person debugging the same code re-adds the exact same prints you just deleted. The standard library's `logging` module fixes all four: a **logger** (`logging.getLogger(__name__)`) has a **level** (`DEBUG` < `INFO` < `WARNING` < `ERROR` < `CRITICAL`), records only get emitted at or above the configured threshold, and **handlers** and **formatters** — configured once, at the application's entry point — decide where records go and how they look, without touching a single call site.

**Levels are a contract, not decoration.** `DEBUG` is detail a developer wants when actively investigating; `INFO` is a notable event in normal operation ("sync started"); `WARNING` is something recoverable but worth a human's attention ("retry 2 of 3"); `ERROR` is an operation that failed; `CRITICAL` is the whole program at risk. Choosing the level correctly is what lets an operator run at `WARNING` in production, silently, until something actually needs attention.

**One placement rule matters more than any of the level choices: libraries never configure logging; only the application does.** A library calls `logging.getLogger(__name__)` and logs to it — it never calls `logging.basicConfig()`, never attaches a handler, never sets a level globally. `basicConfig()` called from inside library code clobbers whatever configuration the *application* set up (or races it, depending on import order), which is exactly the kind of bug that only appears once your toolkit is imported by someone else's program.

**Format lazily, with `%s` and arguments — never with an f-string.** `logger.debug(f"user={user}")` builds the string **unconditionally**, every call, even if `DEBUG` is disabled and the record is discarded immediately. `logger.debug("user=%s", user)` passes the raw value and format string separately; the logging module only calls `%` to interpolate them **if the record will actually be emitted**. At `DEBUG` volume in a hot loop, this is the difference between "free when disabled" and "always paying the formatting cost."

**Worked example — a retry loop, logged at the right levels, with the exception attached correctly.**

```python
import logging

logger = logging.getLogger(__name__)

def sync_records(fetch_fn, attempts=3):
    last_exc = None
    for attempt in range(1, attempts + 1):
        try:
            return fetch_fn()
        except ConnectionError as e:
            last_exc = e
            logger.warning("sync attempt %d/%d failed: %s", attempt, attempts, e)
    logger.error("sync failed after %d attempts", attempts, exc_info=last_exc)
    raise ConnectionError(f"sync failed after {attempts} attempts") from last_exc
```

Each retry is `WARNING` — recoverable, worth noting, not yet an incident. Exhausting all attempts is `ERROR`, and `exc_info=last_exc` attaches the full traceback of the exception object to the log record, so whoever reads the log later gets the stack, not just the message.

**Named misconceptions:**

- **"`logger.debug(f'value={x}')` is the same as `logger.debug('value=%s', x)`, just a different style."** They differ in *when the string gets built*. The f-string interpolates immediately, unconditionally, as part of evaluating the argument — before `logger.debug` even runs, before the level check happens. The `%s` form passes `x` untouched; the interpolation happens inside `logging` **only if the record clears the level filter**. In a hot loop with `DEBUG` disabled, the f-string version still pays full formatting cost on every call; the lazy version pays nothing.
- **"`print()` during development, delete before commit — that's a fine workflow."** It requires you to edit the file to observe anything, and to edit it again to stop observing, and it leaves nothing behind for the next person who hits the same confusing behavior in production, where you can't attach a debugger. A `logger.debug(...)` call can live in the code permanently and be switched on with a config change, not a code change and a redeploy.
- **"`logger.exception(...)` and `logger.error(..., exc_info=some_exception)` are interchangeable ways to log a traceback."** They are not, and the gap between them is exactly the bug Lab M06-B is built on. `logger.exception(msg)` is shorthand for `logger.error(msg, exc_info=True)`, and `exc_info=True` means *"look up the exception currently being handled via `sys.exc_info()`."* That only works **inside an active `except` block**. Call `logger.exception(...)` *after* the block has exited — as in a retry loop that logs once, after the loop, once attempts are exhausted — and `sys.exc_info()` is already `(None, None, None)`; you get a log line with no traceback and no error. The fix, when you're outside the `except` block but still holding a reference to the exception object, is to pass it explicitly: `exc_info=last_exc`.

### Lesson 3 — Debugging with a debugger, not print

**The teaching.** Print-debugging has a fixed cost per question: add a print, rerun the whole program, read the output, remove or add another print, rerun again. Every new question about the program's state costs a full re-execution, and every print you add is a code edit that has to be reverted before you commit. A debugger inverts this: you pause the program **without modifying it**, and from that paused frame you can ask as many questions as you want — inspect any variable, move up and down the call stack, even change a value to test a hypothesis — all without a single rerun.

`breakpoint()` is the built-in hook (Python 3.7+): calling it pauses execution at that exact line and drops you into an interactive debugger — `pdb` by default, but redirectable via the `PYTHONBREAKPOINT` environment variable (set it to `0` to disable all `breakpoint()` calls globally without touching source, which is exactly why you write `breakpoint()` in your code and never hardcode `pdb.set_trace()`). At the `(Pdb)` prompt, the core vocabulary is small:

| Command | Does |
|---|---|
| `l` (list) | Show source around the current line |
| `n` (next) | Run the current line, stop at the next one **in this frame** (does not step into calls) |
| `s` (step) | Run the current line, stop at the **first line of whatever it calls**, if anything |
| `c` (continue) | Run until the next breakpoint or the program ends |
| `p expr` / `pp expr` | Print (pretty-print) the value of an expression, in the current frame |
| `w` (where) | Show the full call stack, current frame marked with `>` |
| `u` / `d` (up/down) | Move one frame up (toward the caller) or down (toward the callee) — **without re-running anything** |
| `b file:line` | Set a breakpoint at a location, optionally `, condition` |
| `q` (quit) | Abort |

**Post-mortem debugging is the single highest-value habit in this lesson.** When a program raises an exception you didn't expect, you don't have to *reproduce* it with a breakpoint placed in advance — you can debug the crash **that already happened**, live, in the exact frame where it occurred: `python3 -m pdb path/to/script.py`, then `c` to run; on an uncaught exception, pdb announces `Uncaught exception. Entering post mortem debugging` and drops you into the innermost frame with every local variable exactly as it was at the moment of the crash. `pytest --pdb` does the same at the point a test fails. In a REPL or notebook, `import pdb; pdb.pm()` post-mortems whatever exception was raised most recently.

**Worked example — a bug a traceback's text can't fully explain, resolved by walking the stack.** Take a function that finds the first repeated value:

```python
def first_duplicate(nums):
    seen = []
    for i, n in enumerate(nums):
        if n in seen[1:]:        # BUG
            return n
        seen.append(n)
    return None
```

`first_duplicate([3, 1, 3, 5])` should return `3`; it returns `None`. This doesn't crash, so post-mortem doesn't apply — but the same *frame-inspection* instrument does. Put `breakpoint()` right before the `if`, run the script, and at each pause:

```
> demo.py(3)first_duplicate()
-> if n in seen[1:]:
(Pdb) p i, n, seen
(0, 3, [])
(Pdb) c
> demo.py(3)first_duplicate()
-> if n in seen[1:]:
(Pdb) p i, n, seen
(1, 1, [3])
(Pdb) c
> demo.py(3)first_duplicate()
-> if n in seen[1:]:
(Pdb) p i, n, seen
(2, 3, [3, 1])
(Pdb) p seen[1:]
[1]
```

At `i=2`, `n` is `3` — the duplicate — and `seen` is `[3, 1]`, but `seen[1:]` is `[1]`: the slice excludes `seen[0]`, so the check compares against the wrong sub-list and the duplicate is never seen. No amount of staring at the one-line `if` tells you the *slice* is the culprit as fast as watching `seen[1:]` evaluate to the wrong list, live, at the exact moment the comparison happens.

**Named misconceptions:**

- **"Print-debugging is just as fast as a debugger for a simple bug."** For a single scalar checked once, maybe. But the moment you need a *second* question — "wait, what was `seen` on the previous iteration too?" — print-debugging costs another edit and another full rerun, while a paused debugger frame answers it with one more `p`, in the same session, on the same paused state.
- **"`breakpoint()` and `pdb.set_trace()` are two different tools; pick whichever."** `breakpoint()` is the modern universal hook: by default it calls `pdb.set_trace()`, but it does so through `sys.breakpointhook`, which is configurable via the `PYTHONBREAKPOINT` environment variable — set to another debugger's entry point in a different environment, or to `0` to disable every `breakpoint()` call in the codebase without touching a single line of source. Hardcoding `pdb.set_trace()` loses that switch entirely; always write `breakpoint()`.
- **"Post-mortem debugging just tells me which line crashed — same information as reading the traceback text."** A traceback shows you the call chain and the exception's type and message — real information, but static. `pdb.pm()` (or `pytest --pdb`, or `python -m pdb script.py` on an uncaught exception) drops you **into the live frame** at the moment of failure, with every local variable in every frame on the stack inspectable via `u`/`d`. A traceback can tell you *where* it crashed; only the live frame can answer *"what was this specific variable, right here, right before it crashed"* — which is usually the actual question.

### Lesson 4 — Profiling: fix slowness by measurement, not guessing

**The teaching.** Intuition about which line of a program is slow is wrong often enough that it cannot be trusted on its own — a nested loop that *looks* quadratic might dominate, or might be negligible next to one I/O call; a "fast-looking" one-liner might hide an O(n²) cost inside a single library call. The only reliable way to find out where time actually goes is to **measure**, and Python ships two complementary instruments for it.

**`cProfile`** answers *"across this whole run, which function ate the time?"* It's a deterministic profiler — it instruments every function call, not a statistical sample — so its attribution is exact, at the cost of real overhead (it can slow a run down by 2–5×, which is fine for finding the hot function and wrong for measuring absolute wall-clock time). Run it as `python -m cProfile -s tottime script.py`, or programmatically:

```python
import cProfile, pstats
pr = cProfile.Profile()
pr.enable()
dedupe_report_slow(transactions)
pr.disable()
pstats.Stats(pr).sort_stats("tottime").print_stats(8)
```

**Two columns matter, and confusing them is the single most common profiling mistake.** `tottime` is the time spent **inside that function's own code**, excluding time spent in anything it called. `cumtime` is the time spent in that function **plus everything it called**. Sorting by `cumtime` on a typical program puts `main` (or your test runner) at the top every time — of course it's cumulatively slowest, it called everything — which tells you nothing. Sorting by `tottime` tells you which function is *actually doing the expensive work*, which is the number that names your bottleneck.

**`timeit`** answers the narrower question *"how long does this exact snippet take, cleanly?"* — it disables garbage collection and runs the snippet many times to average away one-shot noise, which makes it the right tool for confirming a fix's speedup, not for locating which function is slow across a whole program.

**Worked example — profiling names the real bottleneck, and it isn't the one that "looks" slower.** Two functions build a customer report, both written the slow way:

```python
def unique_customer_ids_slow(transactions):        # O(n^2): scans a growing list
    ids = []
    for t in transactions:
        if t["customer_id"] not in ids:
            ids.append(t["customer_id"])
    return ids

def format_id_list_slow(ids):                       # O(n^2): repeated string copies
    out = ""
    for i, cid in enumerate(ids):
        if i:
            out += ", "
        out += cid
    return out
```

Both are quadratic on paper, so intuition alone can't rank them. Profiling on 5,000 transactions / 2,000 unique customers gives an unambiguous answer:

```
         2005 function calls in 0.040 seconds

   Ordered by: internal time

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.039    0.039    0.039    0.039 report_slow.py:1(unique_customer_ids_slow)
        1    0.001    0.001    0.001    0.001 report_slow.py:10(format_id_list_slow)
     2000    0.000    0.000    0.000    0.000 {method 'append' of 'list' objects}
```

`unique_customer_ids_slow` accounts for **39 of the 40 milliseconds** — nearly all of it — while `format_id_list_slow` is noise by comparison. The reason is in the shape of the work, not the code's appearance: the membership check `t["customer_id"] not in ids` runs once per **transaction** (5,000 times), each scan up to 2,000 elements deep; the string-building loop runs once per **unique id** (2,000 times), each copy only a few characters long. Fixing the string builder first — the one that "looks" like the classic quadratic-string-concatenation warning — would have been almost entirely wasted effort. Note also `ncalls` for the culprit: **1**. The O(n²) cost is not spread across thousands of calls to a slow function; it is hidden *inside the body* of one call, in its internal loop — which is exactly why `tottime` on the one enclosing function, not call counts, is what exposes it.

Rewriting both with the right data structures and confirming with `timeit` on the same input:

```python
def unique_customer_ids(transactions):              # O(n): set membership is O(1) avg
    seen, ids = set(), []
    for t in transactions:
        cid = t["customer_id"]
        if cid not in seen:
            seen.add(cid)
            ids.append(cid)
    return ids

def format_id_list(ids):                             # O(n): one pass, no repeated copies
    return ", ".join(ids)
```

measured **91× faster** on the same 5,000-transaction input (37.3 ms → 0.41 ms), with byte-for-byte identical output — the fix changed complexity, not behavior. And scaling the *unfixed* version's input by 10× (5,000 → 50,000 transactions, proportional unique customers) measured **≈102× slower**, not 10× — the empirical signature of O(n²): input scales by k, cost scales by roughly k².

**Named misconceptions:**

- **"I can tell which function is slow just by reading the code."** The worked example is a direct counterexample: both functions are O(n²) on paper, and only measurement reveals that one accounts for 39 of 40 ms and the other is noise. Intuition ranks by how a piece of code *looks* (a string `+=` in a loop is a well-known smell); measurement ranks by how much of the actual clock time it consumes on the actual input shape — and those two rankings are not guaranteed to agree.
- **"cProfile's absolute numbers tell me my real production runtime."** Deterministic profiling instruments every function call, and that instrumentation has real overhead — a profiled run is routinely 2–5× slower than the same code unprofiled, and the overhead is not evenly distributed (functions with many small, cheap calls are hit hardest, proportionally). Use `cProfile` for **relative attribution** — which function dominates the total — and use unprofiled `timeit`/`time.perf_counter` runs for any number you intend to compare against an SLA or a "how much did the fix help" claim.
- **"`tottime` and `cumtime` are basically the same number, just labeled differently."** They diverge exactly where it matters: `cumtime` **double-counts** — a function's `cumtime` includes every function it called, which is why the top of a cumulative-sorted profile is almost always your `main`/entry point, uselessly. `tottime` isolates a function's *own* work, excluding what it delegated, which is the number that actually points at the line doing the damage. Sorting the wrong way is a common enough mistake that it's worth checking which column a profile is sorted by before trusting the ranking.

### Lab M06-A — Exceptions done right: stop swallowing, start chaining

**Goal.** Fix `load_config`, a toolkit function whose `except Exception: pass` currently turns *every* failure — a missing file, malformed JSON, or a bug in the function itself — into a silent `{}`. Replace it with narrow, chained exceptions: a `ConfigNotFoundError` for a missing path, a `ConfigError` (chained to the original `json.JSONDecodeError`) for malformed content, and everything else left to propagate untouched.

**Predict (on paper, before any code).**
1. Given a file containing `{not valid json`, predict what the **current (buggy)** `load_config` returns — not raises. State the concrete value.
2. Suppose someone editing the buggy `load_config` introduces a typo — say, references an undefined variable inside the `try` block, raising a `NameError`. Predict whether the current `except Exception: pass` reports that `NameError` or silently returns `{}` exactly as if the file had been fine.
3. After the fix: predict the exception type raised for a missing file, for malformed JSON, and for a `PermissionError` on the read — and state which of the three should **not** be translated into a `ConfigError` at all.
4. Predict what `exc_info.value.__cause__` will be, in a `pytest.raises(ConfigError)` block, when the failure is malformed JSON — name the exact type.

**Build.**

```python
# starter: toolkit/config.py
import json
from pathlib import Path


def load_config(path):
    """Load a JSON config file. BUGGY: swallows every error and returns {}."""
    try:
```

```python
import json
from pathlib import Path


class ConfigError(Exception):
    """Raised when a config file exists but cannot be parsed."""


class ConfigNotFoundError(ConfigError):
    """Raised when the config path does not exist."""


def load_config(path):
    """Load a JSON config file.

    Raises ConfigNotFoundError if `path` does not exist.
    Raises ConfigError (chained) if the file is not valid JSON.
    Anything else (PermissionError, etc.) propagates unchanged --
    we only translate the two failures we know how to explain.
    """
    try:
        text = Path(path).read_text()
    except FileNotFoundError as e:
        raise ConfigNotFoundError(f"no config at {path}") from e

    try:
        return json.loads(text)
    except json.JSONDecodeError as e:
        raise ConfigError(f"{path}: invalid JSON at line {e.lineno}: {e.msg}") from e
```

```python
import logging

logger = logging.getLogger(__name__)


def sync_records(fetch_fn, attempts=3):
    """Fetch records, retrying on ConnectionError.

    Logs WARNING per failed attempt. When attempts are exhausted, logs ERROR
    with the traceback attached explicitly via exc_info=<the exception
    instance> -- logger.exception() would NOT work here: it is a shortcut for
    exc_info=True, which reads the CURRENTLY HANDLED exception from
    sys.exc_info(), and by this point (outside the except block) there isn't
    one.
    """
    last_exc = None
    for attempt in range(1, attempts + 1):
        try:
            return fetch_fn()
        except ConnectionError as e:
            last_exc = e
            logger.warning("sync attempt %d/%d failed: %s", attempt, attempts, e)
    logger.error("sync failed after %d attempts", attempts, exc_info=last_exc)
    raise ConnectionError(f"sync failed after {attempts} attempts") from last_exc
```

- `caplog.set_level(logging.WARNING, ...)` filters out anything below `WARNING`; an `INFO` call (there isn't one in this function, but if there were) would not appear in `caplog.records`.
- Two failures then a success: exactly **2** `WARNING` records, **0** `ERROR` records (confirmed by `test_sync_succeeds_after_retries_logs_two_warnings`). def unique_customer_ids(transactions):
```python
    """Return unique customer ids, in first-seen order. O(n)."""
    seen = set()
    ids = []
    for t in transactions:
        cid = t["customer_id"]
        if cid not in seen:                   # O(1) average membership check
            seen.add(cid)
            ids.append(cid)
    return ids


def format_id_list(ids):
    """Join ids into a comma-separated string. O(n)."""
    return ", ".join(ids)                     # one pass, no repeated copies


def dedupe_report(transactions):
    ids = unique_customer_ids(transactions)
    return f"{len(ids)} unique customers: {format_id_list(ids)}"
```

## Elle pacing notes

**Walls (expected stall points, with reroutes):**

- **Wall: "I'll just wrap it in `except Exception: pass`, the tests pass anyway."** Symptom: in Lab A, faced with an unfamiliar failure mode, the learner reaches for the broadest catch available to make a red run go quiet, rather than narrowing it. This is the single most tempting shortcut in the module and it is **blocked**, not productive, struggle if it persists past one redirect. **Reroute:** don't argue abstractly — have them deliberately introduce a typo (rename a variable) inside the guarded block and watch the broad `except` swallow *that* too, silently, with zero test failures. The lesson lands the moment they watch their own bug vanish, not when they're told it could.

- **Wall: "the fix works, why do I need the debugger transcript too?"** Symptom: in Lab C or Component 2, the learner reads the buggy code, correctly guesses the fix by inspection, and treats the `pdb` walkthrough as busywork tacked onto a diagnosis they already had. This is real signal worth taking seriously — sometimes the guess *is* right — but the module's outcome is the discipline of confirming before changing, not the fix itself. **Reroute:** ask them to predict, in writing, what `p group`/`p scores`/`p cleaned` will show *before* running — if the prediction is right, that's evidence the reading skill is real, not evidence the transcript was unnecessary. If it's wrong (common: predicting the wrong group, or forgetting `cleaned` is already `[]` by the time you're one frame up), the transcript just did real work the guess couldn't.

- **Wall: "the string concatenation loop is obviously the slow one, I don't need to profile it."** Symptom: in Lab D, the learner fixes `format_id_list_slow` first, confident from the well-known "string `+=` in a loop is O(n²)" warning, without running `cProfile` first. This is the wall the lab is *built* to hit — treat it as the target experience, not a mistake to prevent. **Reroute:** let them fix it, then have them re-measure. The report is barely faster, because `format_id_list_slow` was never the bottleneck — `unique_customer_ids_slow`, running its O(n) scan 5,000 times against a growing 2,000-element list, was. Only then hand them the profiler. The surprise that "the obviously slow line" wasn't the one that mattered is the whole point of Lesson 4, landed by a wrong guess corrected by evidence, not by being told the answer.

**Signals (struggle that is the lesson landing — do NOT reroute):**

- **Frustration that `logger.exception()` "should" work right after the loop, followed by watching `exc_info` come back empty.** This is Lesson 2's sharpest misconception meeting its own evidence. Let the confusion sit for a beat before explaining `sys.exc_info()` — a learner who is surprised has correctly assumed logging "just knows" the recent exception, which is a reasonable assumption that happens to be wrong in exactly this one placement, and discovering the boundary themselves is stickier than being told it up front.
- **Genuine hesitation before typing `q` to leave a post-mortem session, re-checking one more variable first.** That extra `p some_var` before quitting is exactly the behavior Lesson 3 is trying to install — squeezing every remaining question out of a paused frame before it's gone, instead of quitting the moment the first answer arrives and having to reproduce the crash to ask a second question.
- **Reaching for `exc_info=`, a specific exception subclass, or `tottime` sorting *unprompted*.** A learner who writes `logger.error(..., exc_info=captured_exc)` without being told, or who says "sort by tottime, not cumtime, cumtime will just show main" before running anything, has internalized the instrument. Encourage; do not accelerate past — this is the habit forming, not yet fully load-bearing.

**Accelerate conditions (skip/compress when earned):**

- **Clean Lab A with a correctly pre-committed prediction that the buggy code would also swallow a fresh typo** → they may skip the guided walkthrough of Lab B's `caplog` mechanics and go straight to writing the `sync_records` fix and its tests, self-checking against the provided test file.
- **Correct, pre-committed predictions of both the crash frame's `u`-distance and the exact values of `group`/`scores`/`cleaned` in Lab C** → they may compress Lab D's Predict step to the single highest-value question (#1, the `tottime` ranking) and skip the scaling-rate prediction (#3), which reinforces a claim about O(n²) already demonstrated in AIE-101's earlier modules.
- **A fluent evidence-reading viva done early** (correctly reading an unfamiliar traceback, profile, or `caplog` list cold, without prompting) can substitute for Component 2's Predict step on one of the two defects — the destination (evidence over guessing) is already reached for that defect type.

**Do NOT accelerate past** Component 2's evidence-before-fix gate under any circumstances, even for a learner who diagnoses both defects instantly and correctly by inspection. The gate certifies *generating and reading evidence before changing code*; speed and correctness of the guess is not that outcome and actively hides its absence — a learner who fixes both defects without ever running a debugger or a profiler has demonstrated exactly the "guessed right, learned nothing repeatable" pattern this module exists to replace with something that works even when the guess would have been wrong.

## Three-tier reading — the tools that watch your program fail, and the people who wrote them

**Tier 1 — Material ground (verifiable facts).** Every instrument in this module — `except`/`raise ... from`, the `logging` module, `pdb`, `cProfile` — is standard library: no install, no invoice, shipped with every CPython release since long before this course. Every claim here is checkable at the keyboard, and this module's numbers were: `except Exception: pass` was run and measured to return `{}` for both a missing file and malformed JSON, indistinguishably; a `logger.exception()` call placed after an `except` block was run and confirmed to produce a log record with `exc_info=None`, exactly as `sys.exc_info()` predicts; `python3 -m pdb scripts/debug_groups.py` was run and produced the exact post-mortem transcript reproduced in Lab C, unedited; and Lab D's two "equally slow-looking" functions were profiled and measured — one at 39 of 40 milliseconds, the other at 1 — with the fixed version measured at roughly 91× faster on 5,000 transactions and the unfixed version measured at roughly 102× slower on a 10× larger input, the empirical signature of O(n²). One fact of provenance is equally checkable: `pdb` was written by Guido van Rossum himself in Python's earliest years and has been maintained inside CPython ever since by the same small, largely volunteer core-development community that maintains the language — the debugger you used to find a bug three frames deep has, itself, been debugged by people who were never paid specifically for that file.

**Tier 2 — What the field suppresses.** Two distortions, both about the same suppressed labor, running in opposite directions. The **booster** distortion treats "it didn't crash" and "the tests pass" as proof of correctness and speed alike — a `try/except` that silences an error is invisible in a demo, a log line that never fires is invisible in a screenshot, and a function that's "fast enough on my laptop" is invisible until it meets production data — and this framing quietly launders the *absence of a crash* into a claim of *quality*, when this module's own labs show code that is crash-free and green while actively wrong (Lab A, before the fix) or 91× slower than it needs to be (Lab D, before profiling). The **cynic's mirror-image distortion** says debugging tools and profilers are "just infrastructure, they're always there" — which suppresses that `pdb`'s post-mortem mode, `logging`'s level-filtering machinery, and `cProfile`'s call-graph instrumentation are decades of accumulated, mostly volunteer engineering that most working programmers will never read a line of and never be asked to fund. The debugging and observability commons runs on the same unpaid-maintainer foundation as testing (AIE-101-M04's ethics thread) — and it carries an extra, sharper cost this module makes visible: every `except Exception: pass` that ships into the world is a bug report that never gets filed, upstream or otherwise, because the evidence that would have generated it was thrown away at the point of catching it. The industry norm of "fail silently, ship it" doesn't just hide bugs from *your* users — it withholds the diagnostic signal that would have told an open-source maintainer, somewhere upstream, that their code was being misused, or that a library's contract was ambiguous enough that everyone works around it in the exact same silent way.

**Tier 3 — Sit with this (a question you cannot unknow).** Every debugging tool in this module exists because someone decided a crash was worth understanding rather than suppressing, and made the tool to understand it *available to everyone, for free, forever*. You now know how to write `except Exception: pass` and make any failure disappear from view in under a second — and you also now know exactly what that second costs: not just your own future debugging time, but the chance that the evidence your silenced exception was carrying would ever have reached the person who could fix it at the source. **The next time your code catches an error you don't fully understand and you're deciding whether to log it, chain it, propagate it, or quietly let it die in an `except Exception: pass` — who is actually best positioned to learn from that failure: you, right now, under deadline; a future maintainer of your code, including future you; or the person upstream whose library raised it in the first place, who will never know it happened unless someone tells them? And if the honest answer is usually "the third one, and I usually don't" — what would it actually cost you, this week, to file the one upstream issue your last silently-caught exception was quietly withholding?**
