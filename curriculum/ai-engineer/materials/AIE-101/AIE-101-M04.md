### Lesson 1 — A test is an executable claim: `assert`, Arrange-Act-Assert, and writing it red first

**The teaching.** A pytest test is just a function whose name starts with `test_`, containing a plain `assert`. That plainness is the whole design. In `unittest` you write `self.assertEqual(a, b)`, `self.assertTrue(x)`, `self.assertIn(k, d)` — a vocabulary of dozens of methods. pytest throws all of that away and lets you write `assert a == b`, `assert x`, `assert k in d`, because it **rewrites the bytecode of your `assert` statements at import time** to introspect the operands and, on failure, print them. You write the language you already know; pytest supplies the diagnostic.

A test has a shape, and the shape is not decoration — it is how you keep a test honest about what it measures. **Arrange-Act-Assert (AAA):**

- **Arrange** — build the exact inputs and state the claim depends on, and nothing else.
- **Act** — perform the *one* operation under test.
- **Assert** — state what must now be true, as an executable claim.

One Act per test. A test that acts three times and asserts once cannot tell you *which* act broke the claim; a test that asserts on a value it never explicitly arranged is trusting global state you can't see.

**The discipline that separates a test from a receipt: write it red first.** Before the code exists — or before you trust an existing test — you must see the test **fail for the reason you expect**. A test you have only ever seen pass may be passing because it asserts nothing, because pytest never collected it, or because it is comparing a value to itself. Watching it go red first is the only proof that it *can* go red — that it is wired to the behavior at all.

**Worked example — the plain assert, and the introspection you get for free.**

```python
# tests/test_math.py
def test_add_two_ints():
    # Arrange
    a, b = 2, 3
    # Act
    result = a + b
    # Assert — an executable claim about the Act's result
    assert result == 5
```

Now make one fail on purpose to see what pytest gives you that a bare `assert` in a script never would:

```python
def test_add_is_introspected():
    assert 2 + 2 == 5
```

```
    def test_add_is_introspected():
>       assert 2 + 2 == 5
E       assert 4 == 5
```

pytest rewrote `assert 2 + 2 == 5` to compute and display `4 == 5`. You did not write `assertEqual`, and you did not lose the diagnostic. That trade — plain syntax, rich failure — is why pytest won.

**Named misconceptions:**

- **"A passing test proves the code is correct."** It proves the code satisfies *the claims the test actually asserts, on the inputs it actually supplies* — no more. A test you have never watched fail may assert nothing at all. The rule you carry: **a test is not trustworthy until you have seen it red for the right reason.** Correctness is a claim about all inputs; a green example test is a claim about the handful you chose.
- **"`assert` in a test is the same `assert` I was warned about in library code."** Same keyword, opposite context. In *library* code, `assert` is for internal invariants and is **stripped entirely when Python runs with `-O`** — never use it to validate untrusted input (raise a real exception). In *test* code under pytest, `assert` is the idiom precisely because pytest rewrites it; just never run your test suite under `python -O`, which would silence every assertion and turn the whole suite green-and-blind.
- **"pytest finds my tests automatically, so naming doesn't matter."** Discovery is a *convention*, not magic: files must match `test_*.py` (or `*_test.py`), functions must start with `test_`, test classes must start with `Test` and have no `__init__`. Misname a function `check_add` and pytest **silently does not collect it** — the suite is green because it ran zero of your intended tests. A suite that runs nothing is the most dangerous green there is.

### Lesson 2 — Fixtures: setup as dependency injection, isolation, and the state that leaks between tests

**The teaching.** A **fixture** is a function decorated with `@pytest.fixture` that supplies a test with something it needs — a temp file, a database connection, a configured object, a chunk of sample data. A test requests a fixture by **naming it as a parameter**; pytest sees the name, runs the fixture, and passes the result in. That is **dependency injection**: the test declares what it depends on in its signature, and the framework provides it. Fixtures are not "setup helper functions" — a helper you *call*; a fixture you *request*, and pytest wires it up, composes it with other fixtures, and tears it down for you.

Two properties make fixtures the backbone of an honest suite. **First, isolation.** By default a fixture is **function-scoped**: it runs fresh for every test, so no test can see another test's state. This is the property that lets you run tests in any order, in parallel, or one at a time with `-k`, and get the same answer — the property a suite loses the instant two tests share one mutable object. **Second, teardown via `yield`.** A fixture that `yield`s a value runs the code *before* `yield` as setup, hands the value to the test, and runs the code *after* `yield` as teardown — **guaranteed to run even if the test fails**:

```python
import pytest

@pytest.fixture
def temp_file(tmp_path):
    p = tmp_path / "data.txt"      # setup: tmp_path is a per-test temp dir
    p.write_text("hello")
    yield p                        # the test runs here, with p
    # teardown runs after the test, pass or fail
    print(f"cleaning up {p}")      # (tmp_path itself is auto-removed by pytest)
```

`tmp_path` is a **built-in** fixture: a unique, empty `pathlib.Path` directory created fresh for each test and cleaned up automatically. It is the correct way to test anything that touches the filesystem — never write into the repo, never share a path between tests. Fixtures compose: `temp_file` *requests* `tmp_path` just by naming it, exactly as a test requests `temp_file`.

Fixtures defined in a file named **`conftest.py`** are available to every test in that directory and below, with no import — pytest injects them by name. That is how a project shares fixtures without a web of imports.

**Worked example — a fixture that provides sample data, requested by two tests.**

```python
# tests/test_inventory.py
import pytest
from toolkit.inventory import total_value

@pytest.fixture
def cart():
    # Each test gets its OWN fresh dict — mutating it in one test
    # cannot affect another, because this runs again for the next test.
    return {"apple": (3, 0.50), "bread": (1, 2.00)}  # item -> (qty, price)

def test_total_value(cart):
    assert total_value(cart) == pytest.approx(3.50)

def test_total_value_ignores_added_item_in_other_test(cart):
    cart["milk"] = (2, 1.25)          # local mutation
    assert total_value(cart) == pytest.approx(6.00)
    # The other test still sees {apple, bread} only — isolation holds.
```

**Named misconceptions:**

- **"A module- or session-scoped fixture that returns a mutable object is a nice way to avoid rebuilding setup."** It is the classic way to make tests **leak state into each other**. Widen a fixture's scope to `module`/`session` and every test in that scope shares *one* object; the first test that mutates it changes what the next test sees, and now your suite passes or fails *depending on test order*. Order-dependent green is a lie waiting for a reorder. Keep fixtures function-scoped unless the resource is expensive **and** immutable (a read-only loaded file, a spun-up server you only read from).
- **"Fixtures are just setup functions I could replace with a helper I call at the top of each test."** You could — and lose teardown-on-failure, composition, scoping, and `conftest.py` sharing. A helper you call runs *only if the line is reached*; a `yield` fixture's teardown runs *even when the test raises*. The framework wiring is the point, not the setup line you saved.
- **"I can request a function-scoped fixture like `tmp_path` inside a `@given` property test."** You can write it, and Hypothesis will **fail the test with a `HealthCheck.function_scoped_fixture` error** — because Hypothesis runs the test body hundreds of times but pytest sets the function-scoped fixture up **once**, so every generated example shares one temp dir, silently breaking the isolation the fixture existed to give. Property tests belong over **pure functions** with no fixture-supplied state; if you truly must combine them, you suppress that health check *on purpose and in writing*, never by accident. (This trap is exactly why Lab A's fixtures and Lab C's properties live in different labs.)

### Lesson 3 — Parametrization and exceptions: one test, many cases; and asserting on failure

**The teaching.** When a claim should hold for many inputs, the wrong instinct is a `for` loop inside one test. `@pytest.mark.parametrize` is the right one, and the difference is not cosmetic:

```python
import pytest
from toolkit.text import slug

@pytest.mark.parametrize("raw, expected", [
    ("Hello World", "hello-world"),
    ("  spaced  ", "spaced"),
    ("Already-Slug", "already-slug"),
    ("", ""),
], ids=["two-words", "trim", "hyphen-kept", "empty"])
def test_slug(raw, expected):
    assert slug(raw) == expected
```

This is **four independent tests**, each with its own name (`test_slug[trim]`), each run whether or not the others fail, each reported separately. A `for` loop over the same cases is **one** test that stops at the first failing case — so you never learn that cases 3 and 4 also fail, and the failure message points at a loop line, not the input. Parametrize turns "one of my cases is wrong" into "*which* case is wrong," which is the entire diagnostic value.

**Asserting that code fails** is a first-class claim, made with `pytest.raises` as a context manager:

```python
def test_slug_rejects_none():
    with pytest.raises(TypeError):
        slug(None)

def test_factorial_negative_message():
    with pytest.raises(ValueError, match="negative"):   # match is a REGEX on the message
        factorial(-1)
```

The block passes **only if** the body raises the named exception (or a subclass). Two rules keep this honest. **Name the specific exception, not `Exception`** — `pytest.raises(Exception)` passes when a *typo* raises `NameError`, certifying "it failed" while hiding *why*. **Put nothing after the raising call inside the block that you expect to run** — code after the line that raises never executes, a trap Lab B makes you feel.

**Floats never compare with `==`.** `0.1 + 0.2 == 0.3` is `False`, because neither `0.1` nor `0.3` is exactly representable in binary floating point. The instrument is `pytest.approx`:

```python
def test_float_sum():
    assert 0.1 + 0.2 == pytest.approx(0.3)          # True: compares within a small tolerance
```

**Worked example — parametrize catches the case a loop would hide.** Suppose `slug` forgot to strip surrounding whitespace, so `slug("  spaced  ") == "-spaced-"`. The parametrized suite reports **exactly** `FAILED tests/test_text.py::test_slug[trim] - assert '-spaced-' == 'spaced'` while `[two-words]`, `[hyphen-kept]`, and `[empty]` still run and pass — you learn the defect is *specifically* the trim case. A `for` loop would have raised on `trim`, printed a loop-line traceback, and never checked `empty` at all.

**Named misconceptions:**

- **"A `for` loop over cases is the same as parametrize, just less fancy."** No — a loop is *one* test that halts at the first bad case; you lose per-case names, you lose the later cases, and the failure blames the loop, not the input. Parametrize is *N* tests. When you have a table of input→expected, parametrize it.
- **"`pytest.raises(Exception)` proves my error handling works."** It proves *something* raised — including bugs you didn't mean. A `NameError` from a misspelled variable satisfies `pytest.raises(Exception)`, and now your "it rejects bad input" test is green while the rejection path is broken. Assert the **specific** type and `match=` a substring of the message, so the test fails when the *wrong* error is raised.
- **"I'll just `round()` my floats and compare with `==`."** Rounding to a fixed number of places reintroduces the same representability problem at a different scale and hard-codes a precision you didn't reason about. `pytest.approx` states "equal within tolerance" directly and lets you set `rel=`/`abs=` when you must. Float `==` is the bug `approx` exists to prevent.

### Lesson 4 — Property-based testing: the inputs you didn't think of

**The teaching.** An example test asserts a claim on the inputs *you enumerated*. Its blind spot is total: it can only ever check the cases you thought of, and the bugs that ship are, almost by definition, in the cases you didn't — the empty list, the single element, the negative number, the duplicate, the Unicode character, the value at the boundary. **Property-based testing** inverts the burden. Instead of "for these five inputs, the output is these five values," you state a **property** — something that must be true for *all* valid inputs — and let Hypothesis *generate* hundreds of inputs, including the mean ones you'd never type, trying to find one that breaks it.

You write a property with `@given` and a **strategy** — a description of the inputs to draw from:

```python
from hypothesis import given, strategies as st
from collections import Counter

@given(st.lists(st.integers()))
def test_sorted_orders_and_preserves_multiset(xs):
    result = sorted(xs)
    # Invariant 1: the output is non-decreasing
    assert all(result[i] <= result[i + 1] for i in range(len(result) - 1))
    # Invariant 2: the output is a permutation of the input (same elements, same counts)
    assert Counter(result) == Counter(xs)
```

Hypothesis draws `[]`, `[0]`, `[3, 3, 3]`, huge lists, negative-heavy lists, and tries to falsify the property. When it **can't**, you have vastly stronger evidence than any five examples. When it **can**, it does the thing that makes the technique worth learning: it **shrinks** the failing input to a small, simple counterexample and **saves** it, so it replays deterministically until you fix the code.

**You do not need a reference implementation to have a property.** Three patterns cover most functions:

- **Roundtrip** — `decode(encode(x)) == x`. Encoders, serializers, parsers. (Beware: a roundtrip only tests what the *inverse* is strict about; a lenient inverse can accept malformed output and pass anyway — Lab C is built on exactly this trap.)
- **Invariant** — a property of the output alone: `sorted(xs)` is ordered; `len(dedup(xs)) <= len(xs)`; `int_to_roman(n)` never repeats a symbol four times. No oracle needed.
- **Oracle / reference** — compare against a known-correct but slower or simpler implementation (`my_sum(xs) == sum(xs)`), or a hand-built table for small inputs.

**Worked example — shrinking turns a random failure into a diagnosis.** Suppose a `title_case` function is meant to uppercase the first letter of each word but has a bug on single-character words. Hypothesis, given `st.text()`, will eventually generate some 400-character Unicode monster that fails — useless as-is. Then it shrinks: it repeatedly simplifies the input while keeping it failing, and reports something like `Falsifying example: test_title_case(s='a')`. The bug is now a one-character input you can reason about in a second. That reduction — from a random haystack to the minimal needle — is the property tester's core service, and it is deterministic once found (the example is saved and replayed).

Two more tools: **`@example`** pins a specific input to *always* be tried (use it to lock in a regression you found, so it can never silently stop being tested); **`assume`** discards a generated input that doesn't meet a precondition (`assume(x != 0)` before dividing), narrowing the strategy without hand-listing inputs.

**Named misconceptions:**

- **"Property tests are random, so they're flaky — a build might fail for no reason."** This is the misconception that stops people from using the best instrument in the module, and it is wrong twice over. Hypothesis is a *directed search*, not a coin flip; and once it finds a falsifying example it **saves it and replays it every run** — so a real failure is *permanently* red until fixed, and a passing property stays green. A property test failing "randomly" means it found a *real* bug in a case your examples never covered; that is the feature, not flakiness.
- **"I can't write a property test without a correct reference implementation to compare against."** The oracle pattern is only one of three. Most functions have an **invariant** (something always true of the output) or a **roundtrip** (an inverse) you can assert with no reference at all — `sorted` is ordered, `dedup` shrinks-or-holds length, `encode`/`decode` round-trips. If you can state *one* thing that must always be true, you have a property.
- **"More generated examples is strictly better, so crank the count up."** Volume is not the point; **coverage of input classes** is. Hypothesis's default budget already probes the boundary values (empties, zeros, extremes) that hand-written examples miss — that is where its power comes from, not from sheer count. A single well-chosen property that quantifies over the right space beats ten thousand draws over the wrong one. And a *roundtrip* over a lenient inverse can run a million examples and still prove nothing, because the property itself is too weak (Lab C).

**Build.** Write the tests **first** (below), run them, watch them go red (Predict #1), *then* implement `load_scores` to turn them green.

```python
# starter: toolkit/scores.py — truly empty of `load_scores` at this point.
# The name is not yet defined anywhere in the file. That absence is what
# makes the first test run raise an ImportError/collection error (Predict #1),
# not an AssertionError — there is no function yet to be wrong about.
#
# The contract load_scores(path) must satisfy, once you write it in Build:
#   - read a whitespace-delimited 'name score' file into {name: int}
#   - skip blank/whitespace-only lines
#   - let a later duplicate name overwrite an earlier one (last wins)
#   - raise FileNotFoundError if `path` does not exist (from the stdlib read)
#   - raise ValueError on a non-blank line that is not exactly 'name score'
#     with an integer score, naming the offending line number
#   - be pure w.r.t. its argument: read the file, return a NEW dict, mutate nothing
```

Solution (write this **after** the tests are red):

```python
from pathlib import Path


def load_scores(path):
    scores = {}
    for lineno, raw in enumerate(Path(path).read_text().splitlines(), start=1):
        line = raw.strip()
        if not line:
            continue                              # skip blank lines
        parts = line.split()                      # split on any whitespace run
        if len(parts) != 2:
            raise ValueError(
                f"line {lineno}: expected 'name score', got {raw!r}"
            )
        name, score_text = parts
        try:
            score = int(score_text)
        except ValueError:
            raise ValueError(
                f"line {lineno}: score {score_text!r} is not an integer"
            ) from None                           # from None: the int-parse is an impl detail
        scores[name] = score                      # last write wins
    return scores
```

**Verify.** Run `python3 -m pytest -q tests/test_scores.py`. Reconcile against your Predict sheet:
- **Before** you wrote `load_scores`, the failure was an `ImportError`/collection error (the name did not exist), **not** an `AssertionError`. That distinction is the lesson: an `AssertionError` means the test reached your code and the claim was false (wired, red for the right reason); an `ImportError` means the test never reached any behavior at all. Test-first, you should see the *second* first, then the *first*, then green.
- `load_scores` on the sample returns `{"alice": 100, "bob": 85}` — `alice`'s second line overwrites the first (last wins), and the blank line is skipped.
- The missing-file call raises `FileNotFoundError` — and **you did not write that raise**; `Path.read_text()` did. Knowing which exceptions the stdlib hands you unbidden is half of exception testing.
- The one parametrized function reports **three** items: `test_load_scores_rejects_malformed[alice]`, `[alice 91 extra]`, `[alice ninety]`. If you predicted "one test," reconcile: parametrize is N tests, not one.

**Test (write these FIRST; `tests/test_scores.py`).**

import pytest

@pytest.fixture
def scores_file(tmp_path):
    """Write a small valid scores file and return its path.

    tmp_path is a built-in fixture: a unique temp directory PER TEST, torn

    """
    p = tmp_path / "scores.txt"
    p.write_text("alice 91\nbob 85\n\nalice 100\n")
    return p


def test_load_scores_reads_and_last_wins(scores_file):

    assert load_scores(scores_file) == {"alice": 100, "bob": 85}


def test_load_scores_skips_blank_lines(tmp_path):
    p = tmp_path / "s.txt"
    p.write_text("\n\nalice 1\n\n")

def test_load_scores_missing_file_raises(tmp_path):
    # We assert on the exception the STDLIB raises, not one we wrote.
    with pytest.raises(FileNotFoundError):
        load_scores(tmp_path / "does_not_exist.txt")


@pytest.mark.parametrize("bad_line", [
    "alice",             # one field
    "alice 91 extra",    # three fields
    "alice ninety",      # non-integer score

### Lab M04-B — Break on purpose: four green tests, and what each one actually proves

**Goal.** Build the discipline that **green is not evidence** — the mirror of M02's "runs-but-lies." You are handed four small tests. For each test your Predict sheet must state: (a) is it green or red? (b) if green, **does a green here prove the function under test is correct** — yes/no; (c) the one-sentence mechanism.

Assume a correct `add(a, b)` returning `a + b` and a `divide(a, b)` returning `a / b`.

**Test 1 — the tautology.**

```python

    x, y = 2, 3
    assert add(x, y) == add(x, y)      # compares the function to ITSELF
```

*Expected prediction:* **green**, proves **nothing**. `add` could `return 999` for everything and this still passes — it asserts only that `add` is deterministic, never that it's *right*. The claim has no correct-answer in it.

**Test 2 — the vacuous pass (no real assertion).**

```python
def test_divide_runs():
    result = divide(10, 2)             # Act
    assert result                       # truthy check: passes for 5.0, 1, -3, "x"...
```

*Expected prediction:* **green**, proves **almost nothing**. `assert result` checks only that the result is truthy; `divide` returning `1.0` or `-99.0` (any nonzero) passes. It would even pass a `divide` that ignores its arguments. The missing piece is `== 5.0`. (A worse cousin — a `test_` function with *no* `assert` at all — is also green, asserting the void.)

**Test 3 — the float that actually fails.**

```python

```

*Expected prediction:* **red** — `0.1 + 0.2` is `0.30000000000000004`, not `0.3`, so `== 0.3` is `False`. This is the one test in the set that goes red, and it goes red for a *correct* `add` — the bug is in the *test*, not the code. Fix: `== pytest.approx(0.3)`.

**Test 4 — the assertion after the raise that never runs.**

```python

The fix is to move any post-raise assertion *outside* the block (and here, delete it — there is no `result` to check).

- Test 3 → `assert add(0.1, 0.2) == pytest.approx(0.3)`.

### Lab M04-C — A property that finds a real bug (and one that doesn't): auditing code you didn't write

**Goal.** You are handed a toolkit function **someone else wrote** — `int_to_roman` — and your job is not to write it but to *audit* it with property tests. (This is the course's codebase-reading pillar: reading and interrogating unfamiliar code is assessed as hard as writing it.) One version has a subtle bug. You will discover that the *obvious* property — a roundtrip — is **green on the buggy code and proves nothing**, and that only a well-chosen **invariant** catches the bug and shrinks it to a counterexample you can read at a glance. Property tests do not automatically find bugs; the *right* property does.

**Predict (on paper, before any code).**
1. The buggy `int_to_roman` builds numerals from only additive symbols (`M D C L X V I`), so `int_to_roman(4)` produces `"IIII"` instead of `"IV"`. Predict the exact output of the buggy function for `4`, `9`, and `40`.
2. The obvious property is a **roundtrip**: `roman_to_int(int_to_roman(n)) == n` for all `n` in `1..3999`, where `roman_to_int` sums symbol values. **Predict: does this roundtrip catch the `IIII` bug — yes or no?** Reason it through: what does `roman_to_int("IIII")` return? (This is the graded insight of the lab.)
3. A stronger property is an **invariant**: a *canonical* roman numeral never repeats a symbol four times in a row (`IIII`, `XXXX`, `CCCC`, `MMMM` never appear). Predict: does *this* property catch the bug? On roughly what input would Hypothesis first falsify it?
4. When Hypothesis falsifies the invariant, it **shrinks**. Predict the *shape* of the counterexample it reports — a giant number in the thousands, or a small one? What single digit will the shrunk `n` end in, and why does that make the bug obvious?

**Build.** You are given the buggy `int_to_roman` (the "starter under test") and the correct `roman_to_int`. Write the two properties, run them, and watch one stay green (worthless) while the other goes red and shrinks. Then repair `int_to_roman` and watch both go green.

```python
# starter: toolkit/roman.py   (int_to_roman is the code UNDER AUDIT — do not trust it)

# Correct additive+subtractive table (this is the FIX for the Build step):
_VALUES = [
    (1000, "M"), (900, "CM"), (500, "D"), (400, "CD"),
    (100, "C"), (90, "XC"), (50, "L"), (40, "XL"),
    (10, "X"), (9, "IX"), (5, "V"), (4, "IV"), (1, "I"),
]

# BUGGY table shipped in the starter: purely additive, no subtractive pairs.
_VALUES_BUGGY = [
    (1000, "M"), (500, "D"), (100, "C"), (50, "L"), (10, "X"), (5, "V"), (1, "I"),
]

_SYM = {"I": 1, "V": 5, "X": 10, "L": 50, "C": 100, "D": 500, "M": 1000}


def int_to_roman(n, _table=_VALUES_BUGGY):     # starter defaults to the BUGGY table
    """Convert 1..3999 to a roman numeral. (AUDIT ME — a version of this is wrong.)"""
    if not 1 <= n <= 3999:
        raise ValueError(f"out of range 1..3999: {n}")
    out = []
    for value, symbol in _table:
        count, n = divmod(n, value)
        out.append(symbol * count)
    return "".join(out)


def roman_to_int(s):
    """Sum a roman numeral to an int (handles subtractive form)."""
    total, prev = 0, 0
    for ch in reversed(s):
        if ch not in _SYM:
            raise ValueError(f"not a roman numeral: {s!r}")
        val = _SYM[ch]
        if val < prev:
            total -= val
        else:
            total += val
            prev = val
    return total
```

## Assessment

The assessment is **gaming-resistant by construction**: the passing bar is the *judgment trail*, not a green test run — and it cannot be reached by "making the tests pass," because in the central task **the tests already pass and the code is still wrong.** A learner who can only turn red bars green has not demonstrated the outcome; the outcome is knowing what a green proves and manufacturing the red that exposes what it doesn't.

Specifically checked: the Lab A `ImportError`-vs-`AssertionError` distinction, the Lab B ranking of green-but-worthless tests, and the Lab C prediction that the roundtrip is too weak.

### Component 2 — Module practical: make the invisible failure visible (55%)

You are handed an **unseen ~40-line Python module together with a green pytest suite**. The suite passes. ## Three-tier reading — the test suite you trust, and the people who wrote the tools that test you

**Tier 1 — Material ground (verifiable facts).** The instruments in this module are real, free, on your machine, and maintained by a countable number of people you can look up by name. `pytest` and `hypothesis` install with one `pip install`, ship no invoice, and are among the most-depended-upon packages in the Python ecosystem — pytest is a test dependency of a very large fraction of PyPI's most-downloaded projects; when it breaks, an enormous slice of the world's CI goes red at once. Every claim in this module is checkable at the keyboard: `assert 2 + 2 == 5` prints `assert 4 == 5` because pytest **rewrites your assertions' bytecode at import** (read `_pytest/assertion/rewrite.py` in the installed package — it is right there); `0.1 + 0.2 == 0.3` is `False` and `== pytest.approx(0.3)` is `True`; a function named `check_add` instead of `test_add` is silently *not collected* (rename one and watch the count drop); a `@given` property over a lenient roundtrip stays green on wrong code while an invariant shrinks the same bug to `IIII`. And one fact of provenance, equally checkable: open the `hypothesis` repository and its history and you find that property-based testing — the single most powerful bug-finding technique you just learned — was brought to Python and is maintained largely by a small group of contributors, much of it unpaid, and that Hypothesis's own bug reports have found and fixed real defects in the standard library and in widely-used packages, filed upstream for free.

**Tier 2 — What the field suppresses.** Two opposite distortions, each hiding the same labor. The **booster** distortion — "we have 95% coverage, we have a green build, we're *tested*" — launders a metric into a virtue and suppresses that **coverage counts lines executed, not claims verified**: every worthless test in Lab B (the tautology, the vacuous truthy, the dead assert after a raise) *executes the code and raises coverage while proving nothing*. A green badge and a coverage number are marketing artifacts as easily as engineering ones; the industry rewards the badge, which is why test *theater* — suites written to pass, to color the bar, to satisfy a gate — is not a fringe failure but a norm, and why "we're well-tested" is a claim you should now distrust on sight until you have read what the tests assert. The **consumer** distortion runs the other way — "testing is table stakes, the tools are just *there*, everyone uses pytest" — and suppresses that the tools which let you certify your own work to the world are themselves **certified to you by strangers on their own time**: the assertion-rewriter that gives you your diagnostics, the shrinker that hands you a one-character counterexample instead of a four-digit one, the decades of edge cases already absorbed into `hypothesis`'s strategies — none of it fell from the sky, and the "everyone uses it" that makes it feel like infrastructure is exactly what makes the handful who maintain it invisible. Both camps avoid the honest middle: the confidence you sell downstream with a green check is **real, and it is borrowed** — from maintainers who gave you the instrument to measure trust and were, for the most part, never paid by the millions who now measure with it.

**Tier 3 — Sit with this (a question you cannot unknow).** You have spent this module learning that a green test is a *claim*, and that a claim can be true, or worthless, or borrowed — and that the difference is judgment, not color. Soon your toolkit will wear a green CI badge, and that badge will say, to anyone who reads your repository, *this is verified; you may trust it.* But every layer of that verification is a claim you did not fully make: pytest asserting your assertions faithfully, Hypothesis asserting it searched hard enough, the maintainers of both asserting — with their unpaid Saturdays — that the instruments are sound. **When you finally publish a green badge over your own work and let a stranger trust it, whose verification are you actually offering them — yours, or the borrowed word of people who built the tools that test you, whom you have never tested, paid, or thanked; and if a test suite is a promise, is a promise you can only keep because someone else charged the battery still wholly yours to make?**
