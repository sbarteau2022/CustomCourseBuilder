## Lessons

### Lesson 1 — What `create_agent` actually replaces

**Teaching text**

Lab M05-A's `run_agent` was eleven-ish lines of loop wrapped around a prompt builder, a regex parser, and a dictionary dispatch — every part of it code the learner read, wrote, and tested. `langchain.agents.create_agent(model, tools)` replaces all of it with one function call that returns a compiled graph: pass it a chat model and a list of tools, call `.invoke({"messages": [...]})`, and the same shape of thing happens — the model is called, its output is parsed into either a tool call or a final answer, tools run, results come back as the next turn's input, repeat. The parsing step is not a regex on this module's side anymore; it is **constrained decoding on the provider's side** — the very distinction M05 Lesson 1's Misconception 1 named in the abstract is what this module now holds in its hand. A LangChain "tool call" is a structured object (`{"name": ..., "args": {...}, "id": ...}`) attached to an `AIMessage`, and it exists because the provider's API was asked, via `bind_tools`, to constrain its own output to match each tool's schema — schema the framework generated automatically from the tool function's type hints and docstring, the same information M05's `Tool(name=..., description=..., run=...)` dataclass required the learner to type out by hand.

That schema generation is also where this lesson's real cost shows up, and it is a smaller win than it looks. M05's `test_lab_a.py` registered a tool in one line — `Tool("search_hr_policy", "Look up an HR policy fact by exact query text.", search_hr_policy)` — because the `Tool` dataclass just wraps an existing function. LangChain's `@tool` decorator needs a **new function** with its own type-hinted signature and its own docstring, even when all it does is call straight through to the exact same `tools.py` function:

```python
@tool
def search_hr_policy(query: str) -> str:
    """Look up an HR policy fact by exact query text."""
    return _tools.search_hr_policy(query)
```

Four lines to register one already-written function, versus M05's one. The framework is not "less code" in any direction you check naively — it removes the loop, the prompt builder, and the parser (a large, real win, verified below) and it adds a wrapper tax on every tool you already had (a small, real cost) — and a learner who only checks the first number and calls it a day has measured half the tradeoff.

**Worked example — the identical two-hop question, verified two ways**

M05 Lesson 1's worked example ran *"How many vacation days do employees get per year, plus a 2-day signing bonus?"* through the hand-built loop and got a three-step trace ending in `"17 vacation days total (15 base + 2 bonus)."`, three model calls. This module's `test_lab_a_langchain.py::test_two_hop_trace_matches_the_hand_built_baseline` runs the **same question, the same two tools, the same final-answer string** through `create_agent`, driven by a scripted fake model instead of a live one, and gets:

```
HumanMessage  "How many vacation days do employees get per year, plus a 2-day signing bonus?"
AIMessage     tool_calls=[{name: search_hr_policy, args: {query: "vacation days per year"}}]
ToolMessage   "C01: Employees accrue 15 days of paid vacation per year, credited at the start of each quarter."
AIMessage     tool_calls=[{name: calculate, args: {expression: "15 + 2"}}]
ToolMessage   "17"
AIMessage     "17 vacation days total (15 base + 2 bonus)."
```

`model.calls[0] == 3` — the identical model-call count as `AgentResult.steps` from Lab M05-A, down to the number. Six messages total (one human, three AI, two tool) where M05's `AgentResult` held three `Step` objects — same information, addressed differently: LangChain represents the *entire* transcript as one flat message list; M05's `Step` list only recorded actions and observations, folding the "final thought" into the returned answer rather than the message stream. Neither shape is more correct; they are different data models for the identical run, and a learner who has not built M05's version first has no baseline to notice the difference exists at all.

The line-count side of the same comparison, produced by actually writing both: M05's `lab_a_agent_loop.py` solution — dataclasses, prompt builder, parser, and loop — is **101 lines**. This module's `lab_a_langchain_loop.py` — the `AgentTrace` wrapper and the `run_langchain_agent` function that calls `create_agent` and reads its result back into that shape — is **50 lines**, of which the function that actually replaces the loop is 24. That is the real win, and it is real: roughly half the code, and the missing half is exactly the part M05 spent an entire lesson teaching by hand (the prompt-builder string formatting, `THOUGHT_RE`/`ACTION_RE`/`FINAL_RE`, the dispatch-or-`ERROR` branch). But the fake model needed to test either version offline runs the other way: M05's `FakeGenerationClient` is **17 lines** because its interface (`complete(prompt: str) -> str`) is a `Protocol` the course designed *specifically to be trivial to fake*. This module's `ScriptedToolCallingChatModel`, satisfying `BaseChatModel` — an interface this module's authors did not design, built for every real chat provider's full surface, tool binding included — is **35 lines**, more than double, for equivalent behavior. "The framework gives you less code to write" is true and it is not the whole ledger; testability of an interface someone else designed is itself a cost, paid once per project, that a self-designed interface doesn't charge you.

**Misconception 1 — "`create_agent` is a different kind of thing from `run_agent`, not the same loop in different clothes."** It is the same loop. `test_two_hop_trace_matches_the_hand_built_baseline`'s three model calls, two tool calls, and exact final-answer string match `AgentResult` from Lab M05-A because the underlying algorithm — call the model, parse its intent, dispatch to a tool or stop, feed the result back, repeat — did not change. What changed is who owns the parsing step (the provider's constrained decoding instead of your regex) and who owns the loop's control flow (a compiled LangGraph graph instead of a Python `for` loop you can set a breakpoint inside).

**Misconception 2 — "Because the framework's loop handles more automatically, it needs a bigger step ceiling, or none at all."** `test_step_ceiling_stops_a_non_terminating_agent_via_graph_recursion_limit` refutes this directly: the same looping scenario Lab M05-A used to prove `run_agent`'s `max_steps` actually stops a non-terminating agent, run through `create_agent` with `config={"recursion_limit": 5}`, halts too — but not the same way. `run_agent` returned cleanly with `stopped_reason="step_ceiling"`, `answer=None`, no exception. The bare graph's `recursion_limit`, hit with no middleware installed, **raises `GraphRecursionError`** instead — this module's own measured mapping, produced by running the same looping script at recursion limits 2 through 7, is `model_calls_completed = ceil(recursion_limit / 2)` (`recursion_limit=5` → 3 model calls, then a raise) — because each full loop iteration costs the graph *two* internal steps, one for the model node and one for the tool node, not one. A learner who assumes "the framework's default is at least as safe as the loop I built by hand" has not yet hit this exception; Lesson 2 is where the framework's *deliberately installed* version of a clean step ceiling lives, and it is not the default.

**Misconception 3 — "Once a framework is available, earlier modules' hand-built versions should be replaced with it."** Nothing in this module deletes or replaces `lab_a_agent_loop.py`, `lab_d_governor.py`, `corpus.py`, or `tools.py` — every one of them is imported into this module's own lab files **unchanged**, and this module's tests assert the framework's behavior *against* them, not instead of them. The point of building framework-last was never "the hand-built version was a stepping stone to be discarded" — it is the permanent, portable ground truth this module (and the shipped-system project after it) checks the framework's behavior against, for exactly as long as the framework is part of the stack.

### Lesson 2 — Bounded autonomy as middleware

**Teaching text**

M05 Lesson 4 built `Governor` — a hard step/cost ceiling that raises *before* an over-budget call is attempted, and a deny-by-default approval gate wrapped around consequential tools — as a layer sitting explicitly *around* the loop, never folded invisibly inside it. LangChain's equivalent is **middleware**: `langchain.agents.middleware` ships more than twenty of them (`ToolCallLimitMiddleware`, `HumanInTheLoopMiddleware`, `SummarizationMiddleware`, `PIIMiddleware`, `ModelFallbackMiddleware`, and others), each one a self-contained hook that intercepts the agent graph at a named point — before or after the model runs, before or after a tool runs — and is passed to `create_agent` as a list: `create_agent(model, tools, middleware=[...])`. This is the "callback/middleware ecosystem" this module's focus statement names directly, and Lesson 2's job is to show it is doing *the same job* `Governor` did, not a different one, by rebuilding the exact PTO scenario from M05 Lesson 4 with two of them installed instead of one hand-written class.

`ToolCallLimitMiddleware(run_limit=N, exit_behavior="end")` is the framework's version of `Governor.before_step` — a hard ceiling on tool calls, and critically, the `exit_behavior="end"` argument is what makes it stop *cleanly*, with a final message, instead of raising the bare `GraphRecursionError` Lesson 1 just demonstrated. `HumanInTheLoopMiddleware(interrupt_on={tool_name: True})` is the framework's version of `Governor.guard_tool` — every call to a named tool pauses the graph and raises a LangGraph `Interrupt` carrying the tool name and arguments, which the caller resolves by resuming the graph with a `Command(resume={"decisions": [...]})` containing an `"approve"` or `"reject"` decision per pending call. Two differences from `Governor` are worth naming precisely, because both are real engineering consequences, not framework trivia: first, `HumanInTheLoopMiddleware` requires a `checkpointer` (this module uses `InMemorySaver`, matching this module's "sandboxed, in-memory only" tools) — the graph has to persist its own paused state somewhere between the interrupt and the resume, a real piece of infrastructure `Governor`'s synchronous `approval_fn` never needed, because `Governor` never actually paused execution; it just decided synchronously and moved on. Second, resuming an interrupt is not "call `approval_fn` again" — it's a second, separate `agent.invoke(Command(resume=...))` call, and a caller has to loop `while result.get("__interrupt__")` to drain every pending approval, which is exactly what this lab's `run_gated_langchain_agent` does.

**Worked example — the identical PTO scenario, gated two ways**

Ungated, no middleware at all, run through `create_agent` with the exact `STEP1`/`STEP2`/`STEP3_UNGATED`/`FINAL_UNGATED` script M05 used: `filed == ["March 10-14", "March 10-14", "March 10-14"]` — `test_ungated_no_middleware_still_files_three_duplicate_requests` reproduces M05's ungated failure number-for-number, because nothing about switching frameworks changes what an uncertain, well-intentioned model does when nothing stops it.

Gated, `ToolCallLimitMiddleware(run_limit=6, exit_behavior="end")` plus `HumanInTheLoopMiddleware(interrupt_on={"file_pto_request": True})`, driven by the same `approve_first_then_deny()` policy M05 used:

```
call 1: file_pto_request[March 10-14] -> interrupt -> approve_first_then_deny() says True  -> filed: ["March 10-14"]
call 2: file_pto_request[March 10-14] -> interrupt -> approve_first_then_deny() says False -> tool never runs
final:  "I've filed your PTO request for March 10-14 (confirmed after one submission;
         a duplicate attempt was blocked)."
```

`test_gated_agent_blocks_the_duplicate_and_files_once` checks `filed == ["March 10-14"]` and `trace.approval_log == [("file_pto_request", {"dates": "March 10-14"}, True), ("file_pto_request", {"dates": "March 10-14"}, False)]` — the same two-entry approval trail `Governor.approval_log` produced in M05, from the same policy function, driving a different underlying mechanism (a paused graph and a resumed `Command`, instead of a synchronous wrapped `run`). And `test_tool_call_limit_middleware_stops_cleanly_at_the_ceiling` — `run_limit=2`, no approval gate at all — shows the contrast with Lesson 1's bare `recursion_limit`: `filed == ["March 10-14", "March 10-14"]`, and the agent's own final message names the limit in plain language, no exception raised. The clean stop `Governor.before_step` gave you for free is *available* in the framework, but it is a middleware you had to choose to install — `ToolCallLimitMiddleware` — not what happens when you do nothing.

**Misconception 1 — "Middleware is a nice-to-have wrapper around the 'real' agent, safe to skip for a first version."** `test_ungated_no_middleware_still_files_three_duplicate_requests` is the refutation, reused directly from M05: an agent with *zero* middleware installed, given a consequential tool, filed three real duplicate requests from ordinary, well-reasoned uncertainty — no jailbreak, no adversarial prompt. Middleware is not a decoration on a working agent; for any tool with a side effect that outlives the call, the ungated version is not a smaller working system, it is an unsafe one that happens to run.

**Misconception 2 — "`HumanInTheLoopMiddleware` pauses the whole program, the way a Python `input()` call would."** It pauses the **graph**, which is a very different thing: `agent.invoke(...)` returns normally, with a `result["__interrupt__"]` payload describing what's pending, and your own code decides what happens next — synchronously in this lab's tests, but in a real deployment that return could be serialized, handed to a different process, sit in a queue for a human reviewer for minutes or days, and be resumed later against the same `thread_id`. `Governor`'s synchronous `approval_fn` could never do this — it decided in the same call stack, in the same instant, with no way to hand the decision to something outside the process. This is a genuine capability the framework adds, not merely a different way of writing the same thing M05 already had.

**Misconception 3 — "Because `ToolCallLimitMiddleware` and `HumanInTheLoopMiddleware` reproduce `Governor`'s two guarantees, the framework's default configuration is exactly as safe as `run_agent_bounded`."** `Governor` a learner builds in M05 is *unconditionally* attached — there is no way to call `run_agent_bounded` without passing a `Governor` instance, and its `approval_fn` defaults to `deny_all`. `create_agent` has no such default: `middleware=[]` is a completely valid, completely silent call, and it produces exactly Lesson 1 and this lesson's ungated failure. The framework makes the *safe configuration reachable* in a few lines; it does not make the *unsafe configuration unreachable*, and a team under deadline pressure reaching for the fastest working `create_agent(model, tools)` call will reach the unsafe one first, because it's shorter.

### Lesson 3 — Tracing and the callback ecosystem

**Teaching text**

`AgentResult.steps` in M05 existed because `run_agent`'s loop body explicitly built a `Step` object and appended it, by hand, on every iteration — the trace was a side effect the learner had to remember to write. LangChain's **callback system** produces an equivalent trace without touching the agent's control flow at all: `BaseCallbackHandler` defines a set of optional hook methods — `on_chat_model_start`, `on_tool_start`, `on_tool_end`, and others — and any subclass that overrides some of them, passed to a call as `config={"callbacks": [handler]}`, gets invoked at the corresponding point in the run. This is the exact mechanism LangSmith and every other LangChain-integrated observability product is built on top of; a callback handler is not a simplified stand-in for "real" tracing, it *is* the primitive real tracing tools use.

The tradeoff is not subtle in this direction, and this lesson names it plainly because Lesson 1 and 2's tradeoffs were genuinely mixed: this is close to a pure win. `TracingHandler` in this module's Lab M07-C is **35 lines**, and it captures the same shape of trace `AgentResult.steps` did, for *any* agent built with `create_agent` — swap in a different question, different tools, different middleware, and the same 35 lines still work, because the hook fires wherever the framework calls it, not wherever your own loop remembered to append to a list. `Step` in M05, by contrast, is coupled to `run_agent`'s specific loop body; a `Step`-shaped trace for `execute_plan` (M05's planner) or a multi-agent system (M06) needed its own separate bookkeeping, hand-written again. This is the honest shape of the "built-in tracing" claim in this module's focus statement: not that the framework's trace contains more information than a careful learner's hand-rolled one, but that it is attached to the *mechanism* rather than to any one loop's body, so it survives every future change to that loop for free.

**Worked example — the same trace, captured two ways**

The vacation-bonus scenario from Lesson 1, run through `create_agent` with a `TracingHandler` attached via `config={"callbacks": [handler]}`, and nothing else changed:

```
model_call | chat_model      | 1 messages in
tool_start | search_hr_policy | {'query': 'vacation days per year'}
tool_end   | ?                | content='C01: Employees accrue 15 days...
model_call | chat_model      | 3 messages in
tool_start | calculate        | {'expression': '15 + 2'}
tool_end   | ?                | content='17' name='calculate' ...
model_call | chat_model      | 5 messages in
```

`test_tracing_handler_reproduces_the_same_shape_as_hand_rolled_steps` checks `model_call_count(handler.events) == 3` and `tool_call_count(handler.events) == 2` — the exact numbers `AgentResult.steps` reported in M05 for the identical question — captured from **7 total events**, with zero changes to `run_langchain_agent`, `create_agent`, or the agent's tools. The message-count column (1, then 3, then 5) is itself a small free diagnostic `Step` never gave you directly: it's counting the transcript growing by two messages (one `AIMessage`, one `ToolMessage`) per completed tool call, visible without inspecting a single `Step` object — an artifact of tracing at the framework's actual data structure instead of a structure this course chose for teaching clarity.

**Misconception 1 — "A callback handler needs custom logic per agent to produce a useful trace."** `TracingHandler` has no reference anywhere to `search_hr_policy`, `calculate`, the specific question, or this module's corpus — it only knows about `BaseMessage`, tool names, and tool inputs/outputs, all of which every LangChain-built agent exposes identically. The same 35 lines instrument `lab_b_langchain_governance.py`'s gated PTO agent, a hypothetical RAG-only agent, or a multi-agent system with no code changes — the generality is the entire value proposition, and it's a property of hooking the framework's own execution points rather than any one loop's variables.

**Misconception 2 — "Built-in tracing replaces the need to design what you want to measure."** `TracingHandler` records that a `model_call` and two `tool_start`/`tool_end` pairs happened; it has no opinion on whether `search_hr_policy` retrieved the *right* chunk, whether the model's tool choice was justified, or whether the final answer is correct — those are exactly M04's retrieval-vs-generation evaluation questions and M05/M06's agent-eval questions, unaffected by which mechanism produced the trace. A framework's callback system gives you the raw events for free; it does not give you the judgment about what those events mean, which is still the eval harness's job, in this course as in any other.

**Misconception 3 — "Because the callback interface is more general, it must also be more complex to use than hand-rolled logging."** `TracingHandler`'s three overridden methods total under 15 lines of actual logic — appending one `TraceEvent` per hook call — versus `Step`'s construction being interleaved directly into `run_agent`'s control flow across four separate call sites. Generality and simplicity are not opposed here: the callback interface is *more* general and simpler to attach precisely because it was factored out from the loop it observes, the same argument M05 Lesson 2 made for pulling planning out of the ReAct loop into its own inspectable step.

### Lesson 4 — The cost side: someone else's stack trace, and the layer under the layer

**Teaching text**

Every "buy" in Lessons 1–3 has a mirror-image cost, and this lesson makes the learner read it directly instead of taking the argument on faith. `ScriptedToolCallingChatModel` — this module's own fake model — silently satisfies `BaseChatModel`'s abstract interface except for one method: `bind_tools`. Miss it, and `create_agent(model, tools).invoke(...)` doesn't fail in `langchain_tools.py`, in `lab_a_langchain_loop.py`, or anywhere in this module's own code at all. It fails ten stack frames deep, inside LangGraph's own execution engine, with a `NotImplementedError` whose message is a single word and whose traceback never mentions the file the learner actually wrote:

```

File ".../langgraph/pregel/_runner.py", line 207, in tick
    run_with_retry(
File ".../langgraph/pregel/_retry.py", line 617, in run_with_retry

File ".../langgraph/_internal/_runnable.py", line 684, in invoke
    input = context.run(step.invoke, input, config, **kwargs)
File ".../langgraph/_internal/_runnable.py", line 426, in invoke
    ret = self.func(*args, **kwargs)

    model_response = _execute_model_sync(request)
```

Ten frames — LangGraph's `Pregel` engine (`main.py`, twice), its retry wrapper, its generic `Runnable` dispatch (twice), LangChain's own agent factory (three frames), before the actual raise site in `langchain_core`. Every hand-built system in M01 through M06 fails *in a function the learner wrote*, at a line the learner can read cold. This is the actual, concrete shape of "debugging through someone else's stack trace": not that the error is wrong, or unfair, or badly documented (the fix — override `bind_tools` — is one line, and this lesson's own `langchain_fakes.py` shows it, with a comment explaining exactly why the base class raises there) but that finding the fix requires reading *past* a dozen frames of infrastructure the learner did not write and — on a first encounter, without this course's own primitives to recognize what a "bind tools" step is even for — has no way to distinguish from a bug in their own code. A learner who built M05's loop by hand knows on sight that the model, the parser, and the dispatcher are three separate things, because they wrote the seam between each one; a learner who only ever called `create_agent` has no seam to reason from, and the ten frames above are opaque instead of legible.

`create_agent` is not the bottom layer either — it is one abstraction over **LangGraph**, a general-purpose graph execution engine `create_agent` uses to build the underlying state machine, visible directly in the traceback above (`langgraph.pregel`, `langgraph._internal`). This matters for exactly the reason M01's foundational lesson mattered for Python's own heap: the abstraction you're taught to reach for is never the bottom of the stack, it's a specific, inspectable layer someone built on top of a more general one, and *that* layer was built, in turn, on the same primitives — a loop, a dispatch table, a message list — this course spent six modules building by hand. Descending into LangGraph itself is out of scope for this module and this course; naming that it exists, and that `create_agent`'s "magic" is a real, readable, general-purpose loop underneath, not a black box with no bottom, is exactly the "framework-last" bet paying off: nothing about a framework, at any depth, needs to be incantation.

**Worked example — see the traceback above**

`test_missing_bind_tools_raises_not_implemented_error_from_inside_the_framework` is this lesson's worked example as a test: a chat model that implements everything `BaseChatModel` requires except `bind_tools`, run through the exact same `create_agent(model=..., tools=[calculate])` call every other lab in this module uses, raises `NotImplementedError` from inside `langchain_core`, never from this module's own files. The fix — which `langchain_fakes.py`'s real `ScriptedToolCallingChatModel` demonstrates by *not* having this bug — is three lines:

```python
def bind_tools(self, tools: Any, **kwargs: Any) -> "ScriptedToolCallingChatModel":
    return self
```

A learner who has not read the traceback past the first two or three frames will not find this on their own; a learner who reads all the way to `chat_models.py`, line 2355, finds the exact site the base class raises `NotImplementedError`, and — because M05 already taught the "the model, the parser, and the dispatcher are three separate concerns" lesson by hand — recognizes `bind_tools` immediately as "the framework's own dispatch-preparation step, unimplemented for this fake," not a mystery.

**Misconception 1 — "A stack trace ten frames deep through unfamiliar code means the bug is probably in that unfamiliar code."** The bug in this lesson's worked example is not in LangGraph, not in `langchain.agents.factory`, and not in `langchain_core` — every one of those frames is doing exactly what it's supposed to do; the actual defect is a missing method in code the learner (or, in this lab, the module) wrote. Depth in a traceback correlates with how many layers of abstraction sit between your code and the failure, not with whose code is at fault — the raise site is almost always the most informative frame, and it is almost always near the *bottom*, not the top, of a framework-generated traceback.

**Misconception 2 — "Once you're inside a framework's internals, there's nothing to learn from reading the trace — just find the fix and move on."** The specific frames in this lesson's traceback are legible, not mysterious, to a reader who's already built the thing the framework is doing: `pregel/main.py`'s `invoke`/`stream` is the graph's own run loop (Lab M05-A's `for step_number in range(...)`, one abstraction up); `_runner.py`'s `tick` is one step of that loop; `agents/factory.py`'s `model_node` and `_execute_model_sync` are "call the model" (`client.complete(prompt)`); `_get_bound_model` is the step M05 never needed, because M05's `LLMClient.complete` took a plain string and never had to prepare a tool schema for the provider's wire format at all. Reading the trace *as* a more elaborate version of a loop you already built, rather than as an opaque wall of file paths, is the direct payoff of having built M05 first.

**Misconception 3 — "A framework built on a general-purpose engine like LangGraph is more capable, in principle, than the loop this course built by hand — LangGraph can do things `run_agent` structurally cannot."** LangGraph is a more general *execution engine* — arbitrary graphs, not just a single loop, with built-in support for the pausing/resuming Lesson 2's `HumanInTheLoopMiddleware` needs — and that generality is real and useful. But "more general" is not "more powerful" in the sense of computing something `run_agent` couldn't: M05's plain Python loop, given enough hand-written state and control flow, can express any of the same control patterns LangGraph expresses as a graph; what LangGraph buys is a reusable, well-tested substrate for expressing them *without* writing that state and control flow by hand every time, plus the pause/resume, checkpointing, and interrupt machinery this lesson's own `HumanInTheLoopMiddleware` example depended on. That is a real engineering win. It is an engineering win, not a computability one — conflating the two is exactly how "frameworks are strictly more powerful" claims get overstated in the field this course is built to outpace.

```python
from __future__ import annotations

import ast
import operator

from corpus import CORPUS, CORPUS_EMBEDDINGS, QUERY_EMBEDDINGS, cosine_similarity

RELEVANCE_THRESHOLD = 0.2


def search_hr_policy(query: str) -> str:
    """Return the single best-matching corpus chunk's id and text for
    `query`, or a named failure observation."""
    normalized = query.strip().lower()
    if normalized not in QUERY_EMBEDDINGS:
        known = ", ".join(sorted(QUERY_EMBEDDINGS))
        return f"UNKNOWN_QUERY: '{query}' is not a query this tool recognizes. Known queries: {known}"
    query_vec = QUERY_EMBEDDINGS[normalized]
    scored = [
        (chunk_id, cosine_similarity(query_vec, CORPUS_EMBEDDINGS[chunk_id]))
        for chunk_id in CORPUS
    ]
    scored.sort(key=lambda pair: (-pair[1], pair[0]))
    best_id, best_sim = scored[0]
    if best_sim < RELEVANCE_THRESHOLD:
        return f"NO_MATCH: no corpus chunk scored above the relevance threshold ({RELEVANCE_THRESHOLD})"
    return f"{best_id}: {CORPUS[best_id]}"


_ALLOWED_BINOPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.Pow: operator.pow,
}
_ALLOWED_UNARYOPS = {ast.UAdd: operator.pos, ast.USub: operator.neg}


def _eval_node(node: ast.AST) -> float:
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _ALLOWED_BINOPS:
        return _ALLOWED_BINOPS[type(node.op)](_eval_node(node.left), _eval_node(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _ALLOWED_UNARYOPS:
        return _ALLOWED_UNARYOPS[type(node.op)](_eval_node(node.operand))
    raise ValueError(f"unsupported expression node: {ast.dump(node)}")


def calculate(expression: str) -> str:
    """Evaluate a pure arithmetic expression (+ - * / ** and parens
    only) through an AST allowlist -- never Python's `eval`."""
    try:
        tree = ast.parse(expression, mode="eval")
        result = _eval_node(tree.body)
    except (SyntaxError, ValueError, ZeroDivisionError, TypeError) as exc:
        return f"ERROR: could not evaluate '{expression}' ({exc})"
    return str(result)
```

```python
"""Ported forward unchanged from AIE-302-M05 Lab M05-A: the hand-built
ReAct tool-call loop. This is M07's ground-truth baseline."""
from __future__ import annotations

import re
from dataclasses import dataclass
from typing import Callable

from llm_client import LLMClient

DEFAULT_MAX_STEPS = 6

THOUGHT_RE = re.compile(r"Thought:\s*(.*?)\n(?:Action:|Final Answer:)", re.DOTALL)
ACTION_RE = re.compile(r"Action:\s*(\w+)\[(.*)\]")
FINAL_RE = re.compile(r"Final Answer:\s*(.*)", re.DOTALL)


@dataclass
class Tool:
    name: str
    description: str
    run: Callable[[str], str]


@dataclass
class ParsedOutput:
    thought: str
    action_name: str | None
    action_input: str | None
    final_answer: str | None


@dataclass
class Step:
    step_number: int
    thought: str
    action_name: str | None
    action_input: str | None
    observation: str | None


@dataclass
class AgentResult:
    answer: str | None
    steps: list[Step]
    stopped_reason: str  # "final_answer" | "step_ceiling"


def build_agent_prompt(question: str, tools: list[Tool], scratchpad: str,
                        step_number: int, agent_id: str) -> str:
    tool_lines = "\n".join(f"- {t.name}: {t.description}" for t in tools)
    marker = f"AGENT_ID: {agent_id} | AGENT_STEP: {step_number}"
    return (
        "You are a ReAct agent. Answer the question using only the tools listed below.\n"
        f"{marker}\n\n"
        f"Tools:\n{tool_lines}\n\n"
        "Respond in exactly one of these two formats:\n"
        "Thought: <reasoning>\nAction: tool_name[input]\n"
        "-- or --\n"
        "Thought: <reasoning>\nFinal Answer: <answer>\n\n"
        f"Question: {question}\n\n"
        f"{scratchpad}"
    )


def parse_model_output(raw: str) -> ParsedOutput:
    thought_match = THOUGHT_RE.search(raw)
    thought = thought_match.group(1).strip() if thought_match else ""
    final_match = FINAL_RE.search(raw)
    if final_match:
        return ParsedOutput(thought=thought, action_name=None, action_input=None,
                             final_answer=final_match.group(1).strip())
    action_match = ACTION_RE.search(raw)
    if action_match:
        return ParsedOutput(thought=thought, action_name=action_match.group(1),
                             action_input=action_match.group(2).strip(), final_answer=None)
    raise ValueError(f"model output had neither a recognizable Action nor Final Answer: {raw!r}")


def run_agent(client: LLMClient, tools: list[Tool], question: str,
              max_steps: int = DEFAULT_MAX_STEPS, agent_id: str = "agent") -> AgentResult:
    tools_by_name = {t.name: t for t in tools}
    scratchpad = ""
    steps: list[Step] = []
    for step_number in range(1, max_steps + 1):
        prompt = build_agent_prompt(question, tools, scratchpad, step_number, agent_id)
        raw = client.complete(prompt)
        parsed = parse_model_output(raw)
        if parsed.final_answer is not None:
            steps.append(Step(step_number, parsed.thought, None, None, None))
            return AgentResult(answer=parsed.final_answer, steps=steps, stopped_reason="final_answer")
        if parsed.action_name not in tools_by_name:
            observation = f"ERROR: unknown tool '{parsed.action_name}'. Available tools: {sorted(tools_by_name)}"
        else:
            observation = tools_by_name[parsed.action_name].run(parsed.action_input)
        steps.append(Step(step_number, parsed.thought, parsed.action_name, parsed.action_input, observation))
        scratchpad += (
            f"Thought: {parsed.thought}\n"
            f"Action: {parsed.action_name}[{parsed.action_input}]\n"
            f"Observation: {observation}\n\n"
        )
    return AgentResult(answer=None, steps=steps, stopped_reason="step_ceiling")
```

```python
"""Ported forward unchanged from AIE-302-M05 Lab M05-D: bounded autonomy
layered ON TOP of the loop primitive. M07's ground-truth baseline for
the bounded-autonomy comparison against framework middleware."""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Callable

from lab_a_agent_loop import AgentResult, Step, Tool, build_agent_prompt, parse_model_output
from llm_client import LLMClient


class StepCeilingExceeded(RuntimeError):
    pass


class CostCeilingExceeded(RuntimeError):
    pass


ApprovalFn = Callable[[str, str], bool]


def deny_all(tool_name: str, tool_input: str) -> bool:
    return False


def approve_first_then_deny(seen: set[tuple[str, str]] | None = None) -> ApprovalFn:
    seen = seen if seen is not None else set()

    def fn(tool_name: str, tool_input: str) -> bool:
        key = (tool_name, tool_input)
        if key in seen:
            return False
        seen.add(key)
        return True

    return fn


@dataclass
class Governor:
    max_steps: int
    max_cost_usd: float
    cost_per_step_usd: float
    consequential_tools: set[str]
    approval_fn: ApprovalFn = deny_all
    steps_taken: int = 0
    cost_spent_usd: float = 0.0
    approval_log: list[tuple[str, str, bool]] = field(default_factory=list)

    def before_step(self) -> None:
        if self.steps_taken >= self.max_steps:
            raise StepCeilingExceeded(
                f"step ceiling ({self.max_steps}) reached after {self.steps_taken} steps"
            )
        self.steps_taken += 1
        self.cost_spent_usd += self.cost_per_step_usd
        if self.cost_spent_usd > self.max_cost_usd:
            raise CostCeilingExceeded(
                f"cost ceiling (${self.max_cost_usd:.2f}) exceeded at "
                f"${self.cost_spent_usd:.2f} after {self.steps_taken} steps"
            )

    def guard_tool(self, tool: Tool) -> Tool:
        if tool.name not in self.consequential_tools:
            return tool

        def gated_run(tool_input: str) -> str:
            approved = self.approval_fn(tool.name, tool_input)
            self.approval_log.append((tool.name, tool_input, approved))
            if not approved:
                return (
                    f"DENIED: a human reviewer did not approve "
                    f"{tool.name}[{tool_input}]. Do not retry this action "
                    "without new information."
                )
            return tool.run(tool_input)

        return Tool(name=tool.name, description=tool.description, run=gated_run)


def run_agent_bounded(client: LLMClient, tools: list[Tool], question: str,
                       governor: Governor, agent_id: str = "agent") -> AgentResult:
    guarded_tools = [governor.guard_tool(t) for t in tools]
    tools_by_name = {t.name: t for t in guarded_tools}
    scratchpad = ""
    steps: list[Step] = []
    step_number = 0
    while True:
        step_number += 1
        governor.before_step()
        prompt = build_agent_prompt(question, guarded_tools, scratchpad, step_number, agent_id)
        raw = client.complete(prompt)
        parsed = parse_model_output(raw)
        if parsed.final_answer is not None:
            steps.append(Step(step_number, parsed.thought, None, None, None))
            return AgentResult(answer=parsed.final_answer, steps=steps, stopped_reason="final_answer")
        if parsed.action_name not in tools_by_name:
            observation = f"ERROR: unknown tool '{parsed.action_name}'."
        else:
            observation = tools_by_name[parsed.action_name].run(parsed.action_input)
        steps.append(Step(step_number, parsed.thought, parsed.action_name, parsed.action_input, observation))
        scratchpad += (
            f"Thought: {parsed.thought}\n"
            f"Action: {parsed.action_name}[{parsed.action_input}]\n"
            f"Observation: {observation}\n\n"
        )


def make_file_pto_tool() -> tuple[Tool, list[str]]:
    filed: list[str] = []

    def run(date_range: str) -> str:
        filed.append(date_range)
        return f"Request filed: {date_range}"

    tool = Tool(
        name="file_pto_request",
        description="File a PTO request for the given date range. CONSEQUENTIAL: creates a real request.",
        run=run,
    )
    return tool, filed
```

```python
from langchain.agents import create_agent


@dataclass
class AgentTrace:
    answer: str | None
    model_calls: int
    messages: list[BaseMessage]
    stopped_reason: str  # "final_answer" | "step_ceiling"


def run_langchain_agent(model: BaseChatModel, tools: list[BaseTool], question: str,
                         max_steps: int = 6) -> AgentTrace:
    agent = create_agent(model=model, tools=tools)
    try:
        result = agent.invoke(
            {"messages": [{"role": "user", "content": question}]},
            config={"recursion_limit": 2 * max_steps + 1},
        )
    except Exception as exc:  # GraphRecursionError
        if type(exc).__name__ != "GraphRecursionError":
            raise
        return AgentTrace(answer=None, model_calls=model.calls[0],
                           messages=[], stopped_reason="step_ceiling")
    final = result["messages"][-1]
    return AgentTrace(answer=final.content, model_calls=model.calls[0],
                       messages=result["messages"], stopped_reason="final_answer")
```

```python
"""Lab M07-B -- reference solution."""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Callable

from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.tools import BaseTool

from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware, ToolCallLimitMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

ApprovalFn = Callable[[str, dict], bool]


def deny_all(tool_name: str, tool_args: dict) -> bool:
    return False


def approve_first_then_deny(seen: set | None = None) -> ApprovalFn:
    seen = seen if seen is not None else set()

    def fn(tool_name: str, tool_args: dict) -> bool:
        key = (tool_name, tuple(sorted(tool_args.items())))
        if key in seen:
            return False
        seen.add(key)
        return True

    return fn


@dataclass
class GatedTrace:
    answer: str | None
    approval_log: list[tuple[str, dict, bool]] = field(default_factory=list)


def run_gated_langchain_agent(model: BaseChatModel, tools: list[BaseTool], question: str, *,
                               run_limit: int, consequential_tools: set[str],
                               approval_fn: ApprovalFn = deny_all, thread_id: str = "t") -> GatedTrace:
    interrupt_on = {name: True for name in consequential_tools}
    agent = create_agent(
        model=model,
        tools=tools,
        middleware=[
            ToolCallLimitMiddleware(run_limit=run_limit, exit_behavior="end"),
            HumanInTheLoopMiddleware(interrupt_on=interrupt_on),
        ],
        checkpointer=InMemorySaver(),
    )
    config = {"configurable": {"thread_id": thread_id}}
    approval_log: list[tuple[str, dict, bool]] = []
    result = agent.invoke({"messages": [{"role": "user", "content": question}]}, config=config)
    while result.get("__interrupt__"):
        requests = result["__interrupt__"][0].value["action_requests"]
        decisions = []
        for req in requests:
            approved = approval_fn(req["name"], req["args"])
            approval_log.append((req["name"], req["args"], approved))
            decisions.append({"type": "approve"} if approved else
                              {"type": "reject", "message": "denied by approval policy"})
        result = agent.invoke(Command(resume={"decisions": decisions}), config=config)
    final = result["messages"][-1]
    return GatedTrace(answer=final.content, approval_log=approval_log)
```

```python
from dataclasses import dataclass, field
from typing import Any

from langchain_core.callbacks import BaseCallbackHandler


@dataclass
class TraceEvent:
    kind: str  # "model_call" | "tool_start" | "tool_end"
    name: str
    detail: str


@dataclass
class TracingHandler(BaseCallbackHandler):
    events: list[TraceEvent] = field(default_factory=list)

    def on_chat_model_start(self, serialized: dict, messages: list, *, run_id: Any, **kwargs: Any) -> None:
        self.events.append(TraceEvent("model_call", "chat_model", f"{len(messages[0])} messages in"))

    def on_tool_start(self, serialized: dict, input_str: str, *, run_id: Any, **kwargs: Any) -> None:
        self.events.append(TraceEvent("tool_start", serialized.get("name", "?"), input_str))

    def on_tool_end(self, output: Any, *, run_id: Any, **kwargs: Any) -> None:
        content = getattr(output, "content", output)
        self.events.append(TraceEvent("tool_end", "?", str(content)))


def model_call_count(events: list[TraceEvent]) -> int:
    return sum(1 for e in events if e.kind == "model_call")


def tool_call_count(events: list[TraceEvent]) -> int:
    return sum(1 for e in events if e.kind == "tool_start")
```

## Assessment — the framework-vs-baseline diagnosis clinic

Gaming-resistant by design, matching this course's reference standard: the artifact graded is the judgment trail — **predict, locate, fix, prove** — never the verdict alone. This module's version adds a step none of AIE-302's earlier assessments required: every diagnosis must be checked against the learner's own hand-built baseline from M05, not against intuition about what a framework "should" do.

**The clinic.** You are handed an unseen `create_agent`-built agent in this module's own shape: a question, a tool set (with at least one tool marked CONSEQUENTIAL), a middleware list, and a fully scripted, deterministic `ScriptedToolCallingChatModel` script that **runs to completion without crashing** and produces a plausible-looking final answer. Exactly one defect is planted, and it is drawn from a wider pool than M05's clinic because this module's defects can live in *either* layer:

- a **usage defect** — the same four M05 governance gaps (no step ceiling, a consequential tool with no approval gate, an unbounded replan, a memory budget that never triggers), now expressed as a missing or misconfigured middleware; or
- a **framework-boundary defect** — a bare `recursion_limit` standing in for a real step ceiling (so the agent raises instead of stopping cleanly), a tool's `@tool`-generated schema silently accepting an argument your own `tools.py` function would have rejected, or a callback handler that only overrides `on_tool_start` and never `on_tool_end`, silently reporting half the trace.

You are not told which kind. You must:

1. **Predict**, from the question, the tool descriptions, and the middleware list alone — before running anything — what could go wrong given what's configured, and whether you expect the defect to be a usage gap (something M05's `Governor` would also have needed) or a framework-boundary gap (something specific to how this framework's defaults or schema inference behave). State the specific evidence that led you there.
2. **Locate**, by running the case twice: once as given, and once through the equivalent hand-built M05 baseline (`run_agent_bounded` with a `Governor` configured to match the *intended* policy) — and report the concrete numbers where they diverge: a `filed` count, an `approval_log`, a message count, an event count from a `TracingHandler`. A defect located by matching the framework's behavior against its own stated intent, with no baseline run for comparison, earns partial credit at most — this module's entire premise is that the baseline is what makes a framework's behavior checkable.
3. **Fix**, using this module's own primitives — add or correct a middleware, override a missing callback hook, replace a bare `recursion_limit` with `ToolCallLimitMiddleware(exit_behavior="end")` — never a change to `tools.py`, `corpus.py`, or the ported-forward baseline files themselves.
4. **Prove**, by re-running the identical scripted script through the fixed system and reporting concrete before/after numbers, **and** stating in one sentence whether the fixed framework version now behaves identically to the M05 baseline it was checked against, or differs in a way you can name (e.g., "identical `filed` count, but the framework's denial message text differs from `Governor`'s, and any code checking DENIED-message text verbatim would need to change").

### Rubric

| Criterion | Full credit | Partial credit | No credit |
|---|---|---|---|
| **Predict** | States a specific expected failure and correctly classifies it as a usage gap or a framework-boundary gap, tied to specific evidence in the question, tools, or middleware list given. | A prediction is made but is generic, or the usage/framework-boundary classification is stated without justification from the given evidence. | No prediction recorded before the Locate step, or the prediction is written/edited after the answer is already known. |
| **Locate** | Runs both the framework case and the equivalent M05 baseline, and reports the exact number(s) where they diverge, correctly isolating which layer (middleware config, tool schema, callback coverage) the divergence traces to. | Runs the framework case and reports some evidence, but never runs the M05 baseline for comparison, or the comparison doesn't clearly isolate the defect. | Asserts the defect from the symptom alone ("the final answer looks fine so nothing's wrong") with no baseline run and no number produced. |
| **Fix** | Implements the correct fix using this module's own middleware/callback primitives, and the fix targets exactly the layer Locate's evidence implicated — never a change to the ported-forward baseline or shared tool files. | A real fix is implemented but targets the wrong layer, is broader than needed, or edits a file this module's discipline says must stay unchanged. | No fix, or a fix that only changes the model's prompt/script rather than the governance or tracing configuration. |
| **Prove** | Re-runs the identical scripted script through the fixed system, reports concrete before/after numbers, and explicitly states whether the fixed framework version now matches the M05 baseline or differs in a named, specific way. | Re-runs the system and it "looks better," but the before/after comparison isn't reported as numbers, or the baseline-match statement is missing or vague. | No re-run, or the claim "it's fixed" with no repeat of the original scripted case and no baseline comparison. |

A submission that classifies the defect correctly by chance, fixes it by chance, and never runs the M05-baseline comparison scores at or near zero on the Locate and Prove rows — the baseline comparison is not optional supporting evidence in this module's assessment, it is the thing being assessed.

## Three-tier reading

Specific to this module's subject — the layer between you and the mechanism, and who decided where to put it.

- **Tier 1 — material ground.** A framework changes *what code you write*, not *what the system does*. This module's own numbers show both halves of that fact at once: the tool-call loop collapses from 101 hand-written lines to roughly half that (Lesson 1), while the exact same ungated PTO scenario files three duplicate real-world side effects whether or not a framework is installed (Lesson 2, `test_ungated_no_middleware_still_files_three_duplicate_requests`) — because the failure was never in the loop's syntax, it was in the absence of a governance decision, and no framework makes that decision for you by default.

- **Tier 2 — what the field suppresses.** "Just use LangChain (or any agent framework), it handles all of this" suppresses that "handles" here means *makes reachable in a few lines*, not *makes automatic* — `middleware=[]` is a valid, silent, unsafe call, and the fastest path through `create_agent`'s own documentation is the ungated one. The opposite overcorrection — "frameworks are an unnecessary abstraction layer real engineers avoid" — is refuted by this same module's own numbers: `HumanInTheLoopMiddleware`'s pause-and-resume-in-a-different-process capability is not something `Governor`'s synchronous `approval_fn` can do at all, at any amount of hand-written effort short of rebuilding a comparable chunk of LangGraph. Neither "frameworks solve this for you" nor "frameworks are training wheels" survives contact with a system where both the win and the gap were actually measured. What a framework buys was never a single yes/no; it is a specific, per-feature ledger — sometimes a real capability gain, sometimes a wrapper tax, sometimes a default that trades your explicit safety net for someone else's implicit one — and "we use a framework" is a sentence that, on its own, tells you nothing about which entries are on which side.

- **Tier 3 — sit with this.** You will, someday, choose a framework for a system with a real consequential action in it, and the choice will feel like a productivity decision — fewer lines, a name recruiters recognize, a community with more Stack Overflow answers than your own hand-built loop will ever have. Trace the accountability chain this course has asked you to trace all module long, one more time, at this specific layer: the model that reasoned its way to a duplicate action; the loop — yours or the framework's — that let it retry; the middleware that was or wasn't installed; the engineer who reached for `create_agent(model, tools)` with no `middleware=` argument because the deadline was real and the empty list typechecks; the traceback that took ten frames to explain what went wrong, if anyone ever read that far; the reviewer who approved a PR that swapped a hand-built `Governor` for a framework default without asking whether the default matched the guarantee. A framework does not remove any link in that chain. It changes how many of those links are legible to the person standing at the end of it, holding the postmortem, deciding who's accountable for what a system nobody fully audited did. Which of those links, in your own next project, will you actually go read?
