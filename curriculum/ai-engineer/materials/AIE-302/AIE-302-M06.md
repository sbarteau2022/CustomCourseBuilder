## Lessons

### Lesson 1 — The task, the baseline, and what "coordination" actually costs

**Teaching text**

Every lesson and lab in this module runs the same six compound HR queries through three different architectures, so the only thing that varies across the comparison is the architecture — not the task, not the corpus, not the model. Each compound query needs **two different things done**: at least one fact retrieved from the HR policy corpus, and one arithmetic step performed on it. *"I've used 9 of my annual vacation days — how many do I have left?"* needs the fact that the annual allowance is 15 days, then `15 - 9`. *"A couple both work here; one takes full primary-caregiver leave, the other full secondary — how many total weeks combined?"* needs **two** facts (12 weeks, 4 weeks), then `12 + 4`. It is tempting to read "this task has two sub-parts" as "this task needs two agents" — one to look things up, one to do arithmetic. That temptation is the entire subject of this module, and it is wrong far more often than the short-course multi-agent tutorials let on.

This lesson builds and measures the alternative first: **one well-scoped agent, with both tools directly available, answering in its own single context.** `single_agent_solve` costs exactly **2 LLM calls per query** — one turn where the agent decides which tool calls to make (a real tool-calling API lets one turn request more than one tool call, so a query needing two facts still costs one decision turn, not two), and one turn producing the final answer once the tools have run. It gets **all six queries right.** And it has a structural property worth naming before any multi-agent pattern is on the table: **there is no seam.** The same agent that retrieved the fact is the one that computed with it — there is no point in the process where the number could be silently replaced by a different agent that never independently verified it. That property doesn't require a supervisor, a validator, or a handoff protocol to hold. It's true by construction, and it disappears the moment a second agent enters the picture (Lessons 2–3).

**Worked example — `CQ1` through the baseline**

Query: *"I've used 9 of my annual vacation days. How many do I have left?"* `facts_needed = ["vacation_annual_days"]`. The agent's own `PolicyResearchTool.lookup` returns `{"value": 15.0, "chunk_id": "C01", ...}`. Ground truth, computed once from the retrieved value and the query's own numbers: `15.0 - 9 = 6.0`.

| Call | Prompt (abridged) | Chars |
|---|---|---|
| 1 (decide) | `BASELINE \| QUERY_ID: CQ1 \| QUESTION: I've used 9... \| KNOWN_FACTS: vacation_annual_days=15.0` | 142 |
| 2 (answer) | *(same, plus)* `\| COMPUTED_RESULT: 6.0` | 165 |

Total: **2 calls, 307 context characters, answer 6.0 — correct.**

**Misconception 1 — "If a task has multiple sub-parts, it needs multiple agents."** A single decision turn can request as many tool calls as a query needs, one fact or several, because a real tool-calling API lets one turn batch more than one request — "how many facts does this need" and "how many agents does this need" are unrelated questions. Lab M06-A's Predict step has you work out exactly what that means for `CQ3`, the one query in this gold set that needs two facts instead of one — derive the number there, don't take it from this paragraph. A task's shape does not determine an architecture's shape; only a measured requirement does.

**Misconception 2 — "Splitting a task into agents makes each agent's job simpler, so the whole system gets simpler."** Each agent *may* get a shorter individual prompt — Lesson 2 will show a supervisor's worker prompts are indeed shorter than the baseline's. But the system did not get simpler: it gained a new component (a plan, a handoff protocol, a validation step) and a new failure surface — a seam between agents — that the baseline structurally cannot have. "Simpler per agent" and "simpler overall" are different claims, and only measurement (Lesson 4) tells you which one, if either, is true for a given pattern.

**Misconception 3 — "A single agent is the naive approach; multi-agent is the sophisticated default for anything nontrivial."** This lesson's own result refutes the premise before multi-agent has even entered the story: 6 of 6 compound queries correct, 12 total LLM calls across the whole gold set, zero handoff seams, using one agent. Sophistication that isn't earning anything measurable is just cost wearing a nicer word.

### Lesson 2 — Supervisor-worker: plan, dispatch, validate, synthesize

**Teaching text**

The supervisor-worker pattern gives one agent (the supervisor) the whole question and no tools of its own. It **plans** (which facts does this need?), **dispatches** each sub-task to a narrowly scoped worker, **validates** each worker's claim before trusting it, and **synthesizes** the final answer only after validation passes. The four verbs matter in that order, but the third — validate — is the one that actually earns supervisor-worker its keep, and it is the one every rushed multi-agent tutorial skips.

A researcher worker's prompt in this module's implementation is `RESEARCHER_WORKER | FACT_KEY: vacation_annual_days` — 50 characters. It never sees the original natural-language question, never sees other facts, never sees the running conversation. A calculator worker's prompt carries only the fact values it needs, not the question either. This is **scoping**, and it is the direct opposite of what Lesson 3's peer-handoff pattern does. Scoping has a real, measurable consequence: even though supervisor-worker costs **more LLM calls** than the baseline for the same query — plan, one call per fact, calculate, synthesize, four verbs metered as four separate turns where the baseline folds the same work into two — its **total context volume across the six-query gold set is lower than the baseline's** — 2,199 characters versus 2,606 — because none of its worker prompts repeat the full question the way the baseline's own two prompts do. (Lab M06-B's Predict step has you total the call count up yourself, verb by verb, for a one-fact query and a two-fact one, before you run anything.) Call count and context volume are two different axes of cost, and they do not move together. A pattern can be more expensive on one and cheaper on the other, and only measuring both tells you which.

The validation step is not an LLM call. It is plain Python: the supervisor has a way to independently derive ground truth (the same `ground_truth()` function used to build this module's own test fixtures), and it compares every worker's claim against that ground truth before accepting it. When a worker's claim doesn't match, the supervisor discards the claim and substitutes the ground-truth value — a repair, not a retry, and it happens in code, for free, because a cheap check that's available should always be preferred to an expensive one.

**Worked example — the planted hallucination, caught**

Plant a fixture where the calculator worker for `CQ6` (the $450 standing-desk / home-office-stipend query) claims the result is `200.0` instead of the correct `150.0` — modeling a worker that, for whatever reason, didn't use the fact value it was actually handed. Trace:

```
plan            -> facts_needed = ["remote_stipend_usd"]
researcher call -> {"fact_key": "remote_stipend_usd", "value": 300.0, "chunk_id": "C12"}
                   supervisor checks: 300.0 == FACTS["remote_stipend_usd"] -> OK, no repair
calculator call -> {"result": 200.0}                      <- the planted lie
                   supervisor checks: ground_truth("CQ6", {"remote_stipend_usd": 300.0}) = 150.0
                   200.0 != 150.0  -> validation_repairs = ["calculation"], use 150.0 instead
synthesize call -> final answer: 150.0
```

Final answer: **150.0 — correct, despite the hallucinating worker.** The `validation_repairs` list is exactly the artifact that proves the gate did something, not just that the answer happened to be right. (Lab M06-B's own Predict step and fixture run this identical mechanism against `CQ1` — a different query, the same failure shape — so predict that one for yourself before reading ahead into the lab.)

**Misconception 1 — "The supervisor is just another LLM call, so it doesn't add real coordination value beyond routing."** The plan and synthesize calls *are* just LLM calls. The thing that actually caught the planted failure above was not an LLM call at all — it was a checkpoint written in ordinary Python that happened to sit inside the supervisor's turn. The value isn't "an LLM is supervising an LLM"; it's "there is a place in the architecture where a claim gets checked against ground truth before it becomes the answer."

**Misconception 2 — "Workers need the full original question and conversation history to do good work."** Every worker prompt in this pattern is under 90 characters and never contains the question text. They still produce correct results on all six queries. Full context is not a prerequisite for a worker doing its narrow job correctly — and carrying it anyway is exactly what inflates peer-handoff's numbers in Lesson 3.

**Misconception 3 — "If the workers are usually correct, the validation step is redundant overhead."** This conflates "usually correct" with "verifiably correct." The fixture above is not a hypothetical edge case dreamed up to pad the lesson — it is the exact shape of failure a real deployed worker can produce (a model that answers confidently from a plausible-sounding number instead of the one it was actually given), and nothing about "usually correct" tells you which specific run you're looking at. The check costs nothing extra here because ground truth was cheap to derive; Lesson 4 returns to what happens when that's not true.

### Lesson 3 — Peer-handoff: no central authority, and where the cost actually lands

**Teaching text**

Peer-handoff removes the supervisor. A researcher peer receives the question directly, does its own retrieval, and when it decides it can't finish the job itself, hands off to a calculator peer — by passing its **entire accumulated prompt, plus its findings, forward as the next agent's own prompt.** Nobody plans centrally. Nobody validates before the answer ships. The calculator peer's claim *is* the final answer, unless it decides on its own to hand back — nothing structural forces it to check its own work against what it was told.

Measure this pattern next to supervisor-worker on the same six queries and the result is genuinely surprising in both directions, which is exactly why measuring both patterns (not just picking one on instinct) matters. On **call count**, peer-handoff comes in cheap in aggregate: 12 total calls across the gold set, tying the single-agent baseline and well under supervisor-worker's 25 — a peer's decision to hand off and a peer's decision to finalize are each exactly one LLM call in this pattern's structure. (Lab M06-C's Predict step has you work out what that structure means for `CQ3`'s own call count specifically, and how it stacks up against supervisor-worker's count for the same query, before you run anything.) On **context volume**, peer-handoff is the worst of all three patterns measured: 3,171 characters total, against the baseline's 2,606 and supervisor-worker's 2,199 — because the calculator peer's prompt is built by *literally embedding* the researcher peer's entire prompt inside it (`build_calculator_peer_prompt` wraps `build_handoff_transcript`, which concatenates the upstream prompt with the findings text). For `CQ1`: researcher peer prompt is 108 characters; calculator peer prompt, which contains that entire 108-character prompt as a literal substring plus the retrieved fact's full source text, is 290 characters. (Whether that inequality is a coincidence of this one query or a guarantee of how `build_handoff_transcript` is put together — true for every query in the gold set or only some — is exactly what Lab M06-C's Predict step asks you to reason out from the construction itself, not from this single example.)

The call-count number looks like an efficiency win. The context number is the bill for how that efficiency was achieved: nothing was ever scoped down. And the third measurement — the one that matters most for anyone downstream trusting this system's output — has nothing to do with either number.

**Worked example — the same planted hallucination, uncaught**

Run the *identical* `CQ6` fixture from Lesson 2 — calculator step claims `200.0` instead of `150.0` — through peer-handoff instead:

```
researcher peer  -> retrieves remote_stipend_usd = 300.0 ("Remote employees may claim a one-time $300 stipend...")
handoff          -> full transcript passed to calculator peer, findings included verbatim
calculator peer  -> {"final": true, "answer": 200.0}     <- the planted lie
                    nothing checks it. it IS the answer.
```

Final answer: **200.0 — wrong, and nothing in the architecture noticed.** The correct fact, `300.0`, was sitting in the calculator peer's own prompt in plain text the entire time — "the researcher peer's finding was right there" is not a defense, because *having the right number in context* and *being checked against it* are not the same property, and peer-handoff only ever had the first one. (Lab M06-C's own Predict step and fixture run this identical mechanism against `CQ1` — the same query Lab M06-B's supervisor-worker fixture caught — so predict, before you run it, whether the outcome differs here and why.)

**Misconception 1 — "Peer-handoff is simpler because there's no supervisor code to write."** The plan/dispatch/validate logic didn't vanish — it moved into `build_handoff_transcript` (deciding what to carry forward) and into each peer's own judgment about when to hand off and what to trust. The total amount of coordination logic in the system is not smaller; it's just distributed across peers instead of concentrated in one inspectable place, and nowhere in that redistribution did a validation step get written by anyone.

**Misconception 2 — "Passing the full running context forward is strictly safer, because the next agent has more information."** The fixture directly refutes this: the calculator peer had the correct fact in its own prompt and still returned a different number. More information in context constrains nothing about what an agent does with that information — that's what a validation step is for, and peer-handoff has none.

**Misconception 3 — "Fewer LLM calls means a cheaper, more efficient architecture."** True on exactly one axis. Peer-handoff ties the baseline's call count and is nowhere near its cheapest on the axis (context volume) it's actually worst at — and the fixture shows the axis that matters most in production (does a bad claim get caught) isn't call count or context volume at all. "Efficient" needs to specify efficient *at what*, every time.

### Lesson 4 — Measuring the whole comparison, and the decision rule

**Teaching text**

Put all three patterns' numbers side by side, across the full six-query gold set, and the shape of the argument becomes visible in a way no single query could show:

| Pattern | Total LLM calls | Total context chars | Correct (clean path) | Caught planted hallucination? |
|---|---|---|---|---|
| Baseline (single agent) | **12** | 2,606 | 6/6 | n/a — no handoff seam exists to exploit |
| Supervisor-worker | 25 | **2,199** | 6/6 | **Yes** — repaired in code, no extra LLM call |
| Peer-handoff | 12 | **3,171** | 6/6 | **No** — fabricated value shipped as the answer |

Every pattern gets a perfect clean-path score. If the eval stopped there — which is exactly what a demo, or a short course's "look, it works" tutorial, stops at — the three architectures would be indistinguishable, and a learner would have no principled way to choose between them beyond taste. That is precisely the trap AIE-204's gaming-resistance discipline exists to catch: **a clean pass rate is not evidence; it's the absence of evidence for the failure mode you haven't tested yet.** Only the planted fixture — one deliberately adversarial case, run through both multi-agent patterns and only meaningful because the baseline has no equivalent seam to test — separates them.

The honest argument this data supports is *not* "supervisor-worker is better, always add a validation gate." It's narrower and more useful than that: supervisor-worker's validation step is free and effective here specifically *because* this task's ground truth was cheaply and independently derivable in code (the same arithmetic the calculator worker was asked to do, the supervisor could always re-derive). A task without that property — genuinely open-ended synthesis, judgment calls with no single correct answer — would not get this validation payoff for free, and a supervisor added to *that* kind of task would be pure overhead: more calls, for a check that has nothing solid to check against. The decision rule this module argues for is not "multi-agent good" or "multi-agent bad." It's: **multi-agent earns its complexity cost when the task requires something a single well-scoped agent structurally cannot provide** — an independently verifiable sub-output worth gating before it ships, genuine parallelism across long-running independent sub-tasks, or specialization that needs different tool permissions or context windows that can't safely coexist in one agent's context. None of those conditions was true of this module's six HR queries, which is exactly why the single baseline agent — cheapest on calls, competitive on context, immune by construction to the one failure mode that actually broke a multi-agent pattern — was the right architecture for this task all along.

**Misconception 1 — "The pattern with the best measured outcome here is the best multi-agent pattern, generally."** Supervisor-worker's win is task-conditional: it depends on ground truth being cheap to check in code. Change the task to something where "correct" isn't independently derivable, and the exact same architecture keeps its overhead (more calls, scoped-but-still-real coordination logic) while losing the one thing that paid for it here. Never generalize an architecture verdict past the property that produced it.

**Misconception 2 — "Since both multi-agent patterns cost more than baseline in some dimension, multi-agent is never justified."** This overcorrects. The rule isn't "avoid multi-agent" — it's "multi-agent has to be buying something a single agent structurally cannot provide, and you have to be able to name what that something is." A task genuinely requiring independent long-running parallel work, or tool access that can't coexist safely in one context, would tip this same argument the other way; this module's task simply never presented that requirement, and the discipline is to check, not to assume a verdict either direction.

**Misconception 3 — "Clean-path correctness is enough evidence to pick an architecture."** All three patterns hit 6/6 here — completely indistinguishable on that number. The measurement that actually mattered required deliberately trying to break each pattern, once, in a way a real deployed system could plausibly break on its own. This is the same lesson AIE-204-M04 taught about a single low-scoring RAG example never proving a system-wide diagnosis, run in the opposite direction: a full set of *high*-scoring examples never proves a system-wide *safety* property either, when the eval never tried the case that would have found the gap.

`tools.py` (provided; shared by all three labs — do not edit):

```python
"""
tools.py -- PolicyResearchTool (a solved retrieval primitive, wrapping
the same HR-policy fact set AIE-302-M03/M04 used) and CalculatorTool (a
narrow, ast-based arithmetic evaluator -- no eval(), no names, no calls).
"""
from __future__ import annotations

import ast
import operator

# fact_key -> (chunk_id, value, source_text)
FACTS: dict[str, tuple[str, float, str]] = {
    "vacation_annual_days": (
        "C01", 15.0,
        "Employees accrue 15 days of paid vacation per year, credited at the start of each quarter.",
    ),
    "vacation_rollover_max_days": (
        "C02", 5.0,
        "Unused vacation days roll over into the next calendar year, up to a maximum of 5 days.",
    ),
    "parental_primary_weeks": (
        "C08", 12.0,
        "The primary caregiver is eligible for 12 weeks of paid parental leave.",
    ),
    "parental_secondary_weeks": (
        "C10", 4.0,
        "The secondary caregiver is eligible for 4 weeks of paid parental leave.",
    ),
    "expense_deadline_days": (
        "C05", 30.0,
        "Expense reports must be submitted within 30 days of the purchase date to be eligible for reimbursement.",
    ),
    "expense_approval_threshold_usd": (
        "C07", 500.0,
        "Any single expense over $500 requires written manager approval before the purchase is made.",
    ),
    "k401_match_pct": (
        "C11", 0.04,
        "The company matches 401(k) contributions up to 4% of salary, and the match vests immediately.",
    ),
    "remote_stipend_usd": (
        "C12", 300.0,
        "Remote employees may claim a one-time $300 stipend toward home office equipment.",
    ),
}


class PolicyResearchTool:
    """A solved retrieval primitive -- this module treats single-call
    retrieval as already evaluated (that was M04's job) and spends its
    own budget on what happens when more than one agent coordinates
    around calling it."""

    def lookup(self, fact_key: str) -> dict:
        if fact_key not in FACTS:
            raise KeyError(f"no such policy fact: {fact_key}")
        chunk_id, value, text = FACTS[fact_key]
        return {"fact_key": fact_key, "chunk_id": chunk_id, "value": value, "text": text}


_ALLOWED_BINOPS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
}
_ALLOWED_UNARYOPS = {ast.USub: operator.neg}


class CalculatorTool:
    """Numbers, + - * /, parentheses. Nothing else. Any business-logic
    decision (is this past the deadline? does this need approval?) has
    to be made by the agent BEFORE it builds the expression -- this tool
    will not make that decision for it. Uses ast, not eval(), so a
    malformed or malicious expression raises ValueError instead of
    executing arbitrary code."""

    def compute(self, expression: str) -> float:
        try:
            node = ast.parse(expression, mode="eval").body
        except SyntaxError as exc:
            raise ValueError(f"could not parse expression: {expression!r}") from exc
        return self._eval(node)

    def _eval(self, node: ast.AST) -> float:
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return float(node.value)
        if isinstance(node, ast.BinOp) and type(node.op) in _ALLOWED_BINOPS:
            return _ALLOWED_BINOPS[type(node.op)](self._eval(node.left), self._eval(node.right))
        if isinstance(node, ast.UnaryOp) and type(node.op) in _ALLOWED_UNARYOPS:
            return _ALLOWED_UNARYOPS[type(node.op)](self._eval(node.operand))
        raise ValueError(f"disallowed expression node: {ast.dump(node)}")
```

`agents_common.py` (provided; shared by all three labs — do not edit):

```python
"""
agents_common.py -- shared helpers every pattern's solve() function uses:
a JSON parser tolerant of a ```json fence (same pattern as AIE-204-M04's
judge parser), a fact fetcher, and ground_truth -- the independently
derivable correct answer every validation step in this module checks
claims against.
"""
from __future__ import annotations

import json
import re

from queries import COMPOUND_QUERIES
from tools import CalculatorTool, PolicyResearchTool

RESEARCH_TOOL = PolicyResearchTool()
CALC_TOOL = CalculatorTool()

_JSON_FENCE = re.compile(r"^```(?:json)?\s*|\s*```$", re.MULTILINE)


def parse_llm_json(raw: str) -> dict:
    cleaned = _JSON_FENCE.sub("", raw.strip()).strip()
    try:
        return json.loads(cleaned)
    except json.JSONDecodeError as exc:
        raise ValueError(f"could not parse LLM response as JSON: {raw!r}") from exc


def fetch_facts(query_id: str) -> dict[str, float]:
    facts_needed = COMPOUND_QUERIES[query_id]["facts_needed"]
    return {fk: RESEARCH_TOOL.lookup(fk)["value"] for fk in facts_needed}


def ground_truth(query_id: str, fact_values: dict[str, float]) -> float:

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Protocol


class LLMClient(Protocol):
    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        ...


@dataclass
class FakeGenerationClient:
    """Deterministic stand-in used by every test and lab. Exact-string
    keys: each canned entry is the FULL prompt a solve() function will
    build, generated by calling the same prompt-builder functions the
    solve() function calls -- so a key can never drift out of sync with
    what gets sent at runtime. Longest-match wins if more than one key
    is a substring of the prompt (kept for consistency with AIE-204-M04's
    client; this module's exact-string keys never actually collide)."""
    canned: dict[str, str] = field(default_factory=dict)

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        matches = [(key, resp) for key, resp in self.canned.items() if key in prompt]
        if not matches:
            raise KeyError(
                "FakeGenerationClient: no canned response matches this prompt. "
                f"prompt was: {prompt!r}"
            )
        _, response = max(matches, key=lambda pair: len(pair[0]))
        return response


class AnthropicClient:
    """The real backend. The only place in this module allowed to
    import a vendor SDK or name a model string."""

    DEFAULT_MODEL = "claude-haiku-4-5"

    def __init__(self, model: str = DEFAULT_MODEL, api_key: str | None = None):
        import anthropic
        self._client = anthropic.Anthropic(api_key=api_key)
        self._model = model

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        response = self._client.messages.create(
            model=self._model,
            max_tokens=max_tokens,
            temperature=temperature,
            messages=[{"role": "user", "content": prompt}],
        )
        return response.content[0].text

"""Lab M06-B -- reference solution."""
from __future__ import annotations

from agents_common import RESEARCH_TOOL, ground_truth, parse_llm_json
from llm_client import LLMClient
from queries import COMPOUND_QUERIES


def build_supervisor_plan_prompt(query_id: str) -> str:
    q = COMPOUND_QUERIES[query_id]["text"]
    return f"SUPERVISOR_PLAN | QUERY_ID: {query_id} | QUESTION: {q}"


def build_researcher_worker_prompt(fact_key: str) -> str:
    return f"RESEARCHER_WORKER | FACT_KEY: {fact_key}"


def build_calculator_worker_prompt(query_id: str, fact_values: dict[str, float]) -> str:
    facts_str = ", ".join(f"{k}={v}" for k, v in sorted(fact_values.items()))
    return f"CALCULATOR_WORKER | QUERY_ID: {query_id} | FACT_VALUES: {facts_str}"


def build_supervisor_synthesize_prompt(query_id: str, result: float) -> str:
    return f"SUPERVISOR_SYNTHESIZE | QUERY_ID: {query_id} | VALIDATED_RESULT: {result}"


def supervisor_solve(client: LLMClient, query_id: str) -> dict:
    steps: list[str] = []
    llm_calls = 0

    plan_prompt = build_supervisor_plan_prompt(query_id)
    plan = parse_llm_json(client.complete(plan_prompt))
    steps.append(plan_prompt)
    llm_calls += 1

    fact_values: dict[str, float] = {}
    validation_repairs: list[str] = []
    for fact_key in plan["facts_needed"]:
        worker_prompt = build_researcher_worker_prompt(fact_key)
        worker_out = parse_llm_json(client.complete(worker_prompt))
        steps.append(worker_prompt)
        llm_calls += 1

        truth = RESEARCH_TOOL.lookup(fact_key)
        if worker_out.get("value") != truth["value"] or worker_out.get("chunk_id") != truth["chunk_id"]:
            validation_repairs.append(f"research:{fact_key}")
            fact_values[fact_key] = truth["value"]
        else:
            fact_values[fact_key] = worker_out["value"]

    calc_prompt = build_calculator_worker_prompt(query_id, fact_values)
    calc_out = parse_llm_json(client.complete(calc_prompt))
    steps.append(calc_prompt)
    llm_calls += 1

    truth_result = ground_truth(query_id, fact_values)
    claimed_result = float(calc_out["result"])
    if abs(claimed_result - truth_result) > 1e-6:
        validation_repairs.append("calculation")
        validated_result = truth_result
    else:
        validated_result = claimed_result

    synth_prompt = build_supervisor_synthesize_prompt(query_id, validated_result)
    synth_out = parse_llm_json(client.complete(synth_prompt))
    steps.append(synth_prompt)
    llm_calls += 1

    return {
        "answer": float(synth_out["answer"]),
        "llm_calls": llm_calls,
        "total_context_chars": sum(len(s) for s in steps),
        "validation_repairs": validation_repairs,
        "steps": steps,
    }
```

## Assessment

Maps to the course's **build labs** (Labs M06-A/B/C above) and **diagnosis clinics** components. The module exam is a diagnosis clinic: the learner receives an **unseen fourth pattern's trace logs** — a short "hierarchical" variant where a top-level supervisor dispatches to two *mid-level* supervisors, each of which dispatches to its own workers — run once cleanly and once against a planted fixture, with call counts and context-character totals provided but unlabeled as to which run is which. The learner does not get the source code.

Gaming-resistance is the design constraint: an unseen architecture and a provided-but-unexplained set of numbers cannot be answered by having memorized this module's own 12/25/12 and 2606/2199/3171 figures, and the rubric grades the *reasoning that produced* a verdict, not whether the verdict matches an answer key.

| Criterion | What's graded | Full credit | Zero credit |
|---|---|---|---|
| **Predict** (before reading the trace's outcome) | On paper: from the trace's *call-count shape alone* (how many calls, and how they cluster), a prediction of which of this module's three patterns the hierarchical trace most resembles, and one sentence naming the structural feature that gave it away | Names a specific structural feature (e.g., "calls cluster in pairs before a jump — looks like nested supervisor dispatch") tied to an actual property of supervisor-worker or peer-handoff from this module | No prediction submitted before the diagnosis section, or a prediction with no stated reason |
| **Diagnose** | Given both runs' call counts and context totals, correctly identifies which failure mode(s) — coordination overhead, context duplication, or an uncaught off-task claim — the numbers actually show, citing the specific comparison (not a general impression) that supports each claim | Correctly separates "more calls than a same-task baseline" from "more context than a same-task baseline" as independent findings, and correctly reads whether the planted fixture was caught from the two runs' differing final answers | Conflates call count and context volume into one "overhead" judgment, or declares a diagnosis without citing the specific numbers that produced it |
| **Argue** | A written judgment on whether the hierarchical pattern's cost (in whichever dimension it actually cost more) was earned by something a flatter pattern from this module could not have provided — not a restatement of "multi-agent is complex" | Names a specific structural capability (real parallelism across the two mid-level branches, independent validation at two levels) the hierarchy provides, and states plainly whether the *provided trace* shows evidence that capability was actually used, or only that it was theoretically available | Argues from vibes ("more agents seems safer" / "more agents seems wasteful") with no reference to what the specific trace shows |
| **Propose** | One concrete, minimal fix for whatever the diagnosis found broken — a validation checkpoint at a named point, a scoping change to a named prompt, or a recommendation to collapse to a flatter pattern — with a one-sentence prediction of which number (calls or chars) the fix would move and in which direction | The fix is addressable to the specific failure diagnosed, not a generic "add more testing," and the predicted metric movement is stated before any re-run | No fix proposed, or a fix unconnected to the diagnosis (e.g., proposing a validation gate for a context-duplication finding) |

A learner who correctly predicts an architecture from call-count shape but cannot connect the hierarchical trace's specific numbers to a diagnosis has demonstrated pattern-matching, not judgment, and scores accordingly — the credit is in showing the reasoning chain from raw numbers to diagnosis to a proposal that would actually move those numbers, exactly as Lab M06-C's `VERDICT` required for a *seen* comparison.

## Three-tier reading

Specific to this module's subject — coordination as an architecture decision with a measurable price — not boilerplate.

- **Tier 1 — material ground.** Adding agents to a system does not add capability by default; it adds coordination structure, and that structure has a cost that shows up on more than one axis at once (call count, context volume, and — the one that matters most — whether anything checks a downstream claim before it ships). This module's own numbers are the evidence, not an opinion about them: 12 baseline calls beat 25 supervisor-worker calls on raw count, while 2199 supervisor-worker context characters beat both baseline's 2606 and peer-handoff's 3171 — three real orderings, none of which agree with each other, which is exactly why "multi-agent costs more" is too simple a sentence to be useful without specifying more of *what*.
- **Tier 2 — what the field suppresses.** Multi-agent orchestration is sold, by frameworks and by the vendors metering API calls behind them, as the sophisticated default for anything beyond a toy demo — and a system that costs twice the calls of a single well-scoped agent looks, to a buyer who never saw a same-task baseline, like more serious engineering rather than what this module's own measurement shows it can be: unearned overhead. The economic incentive to sell coordination (more calls metered, more infrastructure licensed, more "agentic" in the pitch deck) is not the same incentive as being honest about when a single agent would have done the same job for less, and almost nobody selling an orchestration framework publishes the baseline comparison that would let a buyer tell the difference. You just built that comparison yourself, for one task — most teams never do, for any.
- **Tier 3 — sit with this.** A supervisor's validation gate, in this module, silently repairs a hallucinating worker and the system just... keeps working, correctly, with no visible sign anything went wrong. That's the gate succeeding. Now run the tape forward a year: the gate hasn't fired in production in months, because most days nothing tries to slip past it — and someone on a latency budget notices the extra validation call and quietly removes it, because it "hasn't caught anything." The day it would have caught something, it's already gone, and the wrong number reaches someone's paycheck instead. Now run the *other* tape: a peer-handoff system, no gate to begin with, and the same wrong number reaches the same paycheck — but this time, when someone asks "whose decision was this," the honest answer might be that nobody's name was ever on it, because by the time anyone looked, the context that would explain what happened had already been overwritten by the next handoff. Before you reach for "no central authority, it's simpler" on a system whose mistakes reach people: whose hands is that decision actually in, on the day it's wrong — and would you be able to find out?
