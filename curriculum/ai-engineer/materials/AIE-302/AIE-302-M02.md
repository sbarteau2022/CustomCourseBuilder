## Lessons

### Lesson 1 — Why "ask nicely" fails, and what failure actually looks like

A prompt that ends "respond with ONLY a JSON object, no other text" is an *instruction*, not a *constraint*. Nothing about a plain-text completion API enforces that instruction — the model is still, mechanically, predicting the next token, one token at a time, and every one of those tokens is free to be a stray word of politeness, a markdown fence, an apology, or a perfectly reasonable sentence that happens not to be JSON. "Ask nicely" is a real, useful lever — better phrasing measurably raises the fraction of well-formed responses — but it is a lever on a *probability*, not a switch on a *guarantee*, and the gap between those two is where this whole module lives.

**The running task for this module.** A generative system reads a freeform incident report — the kind an on-call engineer or support agent might type in thirty seconds — and extracts a structured ticket record for a downstream triage queue: a `severity`, a `category`, a one-sentence `summary`, a list of `action_items`, and an optional `estimated_resolution_hours`. Nothing downstream can act on this record unless every field is exactly the type and shape the triage queue's code expects — the queue doesn't render markdown, it doesn't catch `IndexError`, and it doesn't know what to do with a `severity` of `"pretty bad"`.

**Worked example — five real completions, one naive prompt.** The naive prompt is: *"Read the incident report and extract severity, category, summary, and action_items. Respond with ONLY a JSON object, no other text."* Below are five representative responses a model can plausibly return to that exact prompt, for five different incident reports:

| # | Raw response (abbreviated) | What's wrong |
|---|---|---|
| 1 | `{"severity": "critical", "category": "outage", "summary": "...", "action_items": [...]}` | Nothing — this is the response every downstream line of code assumed it would always get. |
| 2 | ` ```json\n{"severity": "medium", ...}\n``` ` | Valid JSON, wrapped in a markdown code fence. `json.loads` on the raw string raises `JSONDecodeError` at character 0. |
| 3 | `Sure! Here's the extracted ticket: {"severity": "high", ...} Let me know if you'd like any changes.` | Valid JSON, buried in a sentence. Same failure as #2, different shape. |
| 4 | `{"severity": "urgent", "category": "billing", ...}` | Syntactically perfect JSON. `"urgent"` is not one of the four severities the triage queue's code branches on — this response will parse cleanly and then silently mis-route. |
| 5 | `I don't have enough information in this report to determine a severity level.` | Not JSON at all — a reasonable, well-reasoned answer to a question the prompt didn't quite ask. |

Only #1 is safe to hand to downstream code as written. #2 and #3 are **unparseable** — `json.loads` raises before any of your own logic runs. #4 is worse in a specific way: it is **parseable and silently wrong** — no exception anywhere, just a `severity` value that isn't one of the four the triage dashboard's color-coding logic checks for, which typically means the record renders with no color at all and nobody notices until someone asks why a critical incident showed up grey. #5 is not JSON and is not really a failure of the model *understanding* the task — it's a well-formed answer to an implicit sub-question ("are you sure?") the prompt never asked, because "extract the fields" was never framed as a forced-choice.

**Misconception 1 — "If I ask nicely enough — please, ONLY JSON, no explanation, no markdown — the model will always comply."** Stronger phrasing measurably reduces responses like #3 and #5. It does not reduce them to zero, and it does essentially nothing about #4 — a model that is confident enough to write `"urgent"` instead of one of your four allowed severities was not being sloppy about formatting; it didn't know your enum, because "ask nicely for JSON" never told it. Lesson 4's measured naive failure rate is exactly the size of the gap this misconception hand-waves away.

**Misconception 2 — "Setting `temperature=0` fixes this."** Temperature controls how much the model's *token sampling* varies run to run at a fixed prompt; it does nothing to the *decoding mechanism* — the model is still choosing one token at a time from an unconstrained vocabulary, it's just choosing more deterministically. `temperature=0` will make the *same* prompt fail the *same* way on every retry (which is actually a problem — see Lesson 3's bounded-retry discussion), but it will not stop a different incident report, with different length or ambiguity, from producing response #2, #3, #4, or #5. Determinism and correctness are different properties, and this module tests both separately.

### Lesson 2 — A schema is a contract, and `json.loads` succeeding is not proof it was honored

`json.loads(raw)` answers exactly one question: *is this a syntactically valid JSON document?* It does not answer *does this document have the fields my code needs, are they the right type, and are their values in the set my downstream logic actually branches on?* Response #4 from Lesson 1 makes this concrete: it is valid JSON and it is a broken contract. Treating "it parsed" as "it's safe to use" is the single most common structured-output bug in production code, and it is a bug that raises no exception anywhere — it just produces wrong behavior downstream, sometimes much later and far from the code that caused it.

**A schema, for this module's purposes, is a small, explicit description of shape**, expressed as a nested Python dict — not a library, not an installed dependency, just data the learner writes and a validator the learner writes to check data against it:

```python
TICKET_SCHEMA = {
    "type": "object",
    "required": ["severity", "category", "summary", "action_items"],
    "properties": {
        "severity": {"type": "string", "enum": ["low", "medium", "high", "critical"]},
        "category": {
            "type": "string",
            "enum": ["billing", "auth", "performance", "data-loss", "outage"],
        },
        "summary": {"type": "string", "minLength": 1, "maxLength": 200},
        "action_items": {"type": "array", "items": {"type": "string"}, "minItems": 1},
        "estimated_resolution_hours": {"type": "number"},
    },
}
```

This is a deliberately small subset of what real JSON Schema supports — `type`, `required`, `enum`, `properties`, `items`, `minLength`/`maxLength`, `minItems` — because the point of Lab M02-A is not to reimplement the JSON Schema spec, it's to build *just enough* validator that the learner has personally written the code that turns "the model returned something" into "the model returned something my code can trust," and therefore knows exactly what a library like `jsonschema` or `pydantic` is doing on their behalf when M07 finally introduces one.

**Worked example — a validator error that would have been an invisible bug.** Response #4's `severity` of `"urgent"` fails one check: `"urgent" not in schema["enum"]`. Without that check, here is the downstream code a triage dashboard plausibly runs:

```python
SEVERITY_COLOR = {"low": "gray", "medium": "yellow", "high": "orange", "critical": "red"}
badge_color = SEVERITY_COLOR[ticket["severity"]]   # KeyError: 'urgent'
```

If the dashboard's rendering code doesn't happen to wrap this in a `try/except` (and plenty of real dashboard code doesn't, because "the model already validated this, right?" is exactly the assumption this lesson exists to break), the whole page fails to render for that one incident — or worse, an earlier version of the same code used `.get(ticket["severity"], "gray")`, which doesn't crash, it just paints a genuinely urgent, unrecognized-severity ticket the same dull gray as routine noise. The validator's job is to catch `"urgent"` **before** it reaches either version of that code, with an error message specific enough to fix it — not just "invalid data," but `severity: must be one of ['low', 'medium', 'high', 'critical'], got 'urgent'`, which is what Lesson 3's repair prompt is built to use directly.

**Misconception 1 — "If `json.loads` doesn't raise, the data is safe to use."** `json.loads` guarantees syntax, never shape. A response can be perfectly valid JSON and still violate every business rule your downstream code depends on — wrong enum member, wrong type for a field, a required key silently missing. Treat parsing and validating as two separate, both-mandatory steps, never one.

**Misconception 2 — "The validator should coerce what it can, rather than reject it."** It is tempting to have the validator quietly turn `"3"` into `3`, or `"yes"` into `True`, so that near-miss data doesn't get rejected. Silent coercion trades a loud, catchable failure for a quiet, uncatchable one: a validator that coerces `"pretty bad"` toward the nearest enum member has decided, on your behalf and without telling anyone, what the model "really meant" — which is precisely the kind of unverified inference this whole course's judgment discipline exists to prevent. A validator's job is to report exactly what's wrong, in language specific enough for a repair step to act on (Lesson 3) — not to guess quietly and move on.

### Lesson 3 — Almost-valid JSON: what breaks, what a regex can fix, and what only the model can fix

Most real-world "the model didn't return valid JSON" failures are not the model failing to understand the task — they're small, *mechanical* mismatches between what the model wrote and what a strict parser demands: a markdown fence around otherwise-correct JSON, a trailing comma a human would never notice, `True`/`False`/`None` where JSON needs lowercase `true`/`false`/`null`, or a sentence of preamble before the object starts. None of these require the model to reconsider the *content* of its answer — they're formatting slips a text editor's find-and-replace could catch. Others — a `severity` outside the enum, a required field genuinely missing — are not formatting slips at all; they're the model getting the *content* wrong, and no regex on earth can guess the right enum value.

**The layered-repair principle.** Spend the cheapest fix first. A **deterministic repair** — pure string manipulation, no network call, sub-millisecond — should run before a **model repair retry** — a second real API call, real latency, real cost — is ever attempted. Running an expensive model round-trip to fix a markdown fence a three-line regex would have caught is not just wasteful; at production volume it's the difference between a pipeline that costs what it should and one that doesn't.

**Worked example — what deterministic repair can and cannot touch.**

```
Fence:        ```json\n{"severity": "medium", ...}\n```
Trailing comma: {"severity": "high", ..., "action_items": ["x"],}
Python literal: {"severity": "medium", ..., "false_positive": True}
Prose-wrapped:  Here's the ticket: {"severity": "high", ...} Let me know if you need edits.
```

All four are fixable *without asking the model anything* — strip the fence, find the first `{` and its matching `}` and discard everything outside that span, delete a comma that appears immediately before a closing bracket, swap `True`/`False`/`None` for their JSON spellings. None of these touches what the object actually *says*.

Contrast that with:

```
Bad enum:  {"severity": "urgent", "category": "billing", ...}
Single-quoted: {'severity': 'low', 'summary': "customer's account is locked", ...}
```

The bad-enum case parses as valid JSON — `json.loads` never raises — so no *syntactic* repair even applies; the value itself is wrong, and only re-asking the model (with the validator's specific error fed back in) has any chance of getting the right one. The single-quoted case looks like an obvious regex target — swap `'` for `"` — until the string *value* itself contains a real apostrophe: `"customer's account is locked"`. A blind `'` → `"` swap turns that apostrophe into a structural quote and shreds the string in the middle of a word, producing a *worse*, more confusing parse error than the one it started with. This is why Lab M02-B's `deterministic_repair` deliberately **never touches quote characters inside string content** — the fix that looks obvious is also the one most likely to corrupt real data, and knowing which repairs are safe to automate is as much the lesson as writing the regex.

**Worked example — why the repair prompt has to name the specific error.** Compare two repair instructions sent back to the model after the bad-enum failure above:

> **Vague:** "Your previous response was invalid. Please fix your JSON and try again."
>
> **Specific:** "Your previous response failed validation for this reason: `severity: must be one of ['low', 'medium', 'high', 'critical'], got 'urgent'`. Respond again with ONLY a corrected JSON object."

The vague version gives the model no information about *what* was wrong — a model that was confident `"urgent"` was reasonable the first time has no new evidence to reconsider that choice, and commonly just resends the same or a cosmetically different response, restarting the same failure. The specific version hands the model the exact constraint it violated and the exact list of legal values — the fix Lab M02-A's `judge_summary`-style retry makes is to route the validator's own `errors` list, verbatim, into the next prompt, not to write a second, separate "sorry, please fix" message that has forgotten what was wrong.

**Misconception 1 — "A regex-based repair layer is a hack; it's more robust to just always ask the model to try again."** A pure-retry strategy is *correct* — it will eventually fix a markdown fence — but it is not *cheap*, and "correct but needlessly expensive" is still a design mistake at any real volume. The deterministic layer isn't a hack in place of the real fix; it *is* the fix for an entire class of failures, and reserving model retries for the failures that actually need judgment is the more disciplined design, not the less.

**Misconception 2 — "The retry prompt just needs to say 'fix your JSON.'"** As shown above, a vague repair instruction routinely reproduces the exact failure it was meant to fix, because it gives the model nothing new to act on. Feed back the validator's literal error strings — the same ones a human debugging the pipeline would want to read.

**Misconception 3 — "Retry until it works."** An unbounded retry loop is not robustness, it's a hidden infinite loop with a bill attached, and it hides a pipeline that is fundamentally broken (a report the model genuinely cannot extract a severity from, response #5 in Lesson 1) behind an ever-growing number of API calls instead of surfacing that failure to whoever needs to see it. **Bounded retry — a fixed, small budget, and a real exception when the budget is exhausted** — is the correct API discipline: it fails loud, fails fast, and fails in a way a caller can catch and route (to a human, to a fallback, to a dead-letter queue). This is the same shape of discipline AIE-302-M05 builds up into full agent bounded autonomy — a tool-call retry loop that gives up and asks for help is the same design as this module's `extract_ticket` giving up and raising `ValidationError` after two attempts, at a much smaller scale.

### Lesson 4 — Measuring the gap: naive prompting vs. actual schema constraints

Everything in Lessons 1–3 was built entirely at the *application* layer — parsing, validating, and repairing text the model handed back, after the fact. There is a second, different mechanism, enforced by the *provider's decoding process itself*, not by anything the caller does afterward: giving the API a schema and having the model's token generation constrained, at the moment each token is chosen, to only ever produce something shaped like that schema. On Claude's API, the concrete mechanism is **forced tool use** — define a tool whose `input_schema` *is* your schema, force the model to call that specific tool (`tool_choice`), and the SDK hands back a `tool_use` content block whose `input` was never free-text at all; it came from a decoding path that could not emit `"urgent"` for a field whose schema says `"enum": ["low", "medium", "high", "critical"]`, because "urgent" was never a token sequence the constrained decoder was allowed to consider for that field. That is what "actual schema constraints" means, concretely, and it is a *different mechanism*, not a more politely worded version of Lesson 1's prompt.

**This module's central claim is not "schema constraints are better" as received wisdom — it's a specific, run number.** Lab M02-C runs the exact same 20 incident reports through both paths — naive prompting (Lesson 1's mechanism, classified through Lesson 2's validator) and schema-constrained extraction (this lesson's mechanism, classified through the *same* validator) — and counts, honestly, how many of each fail. On this module's dataset the measured numbers are:

| Path | PASS | JSON_FAIL (unparseable) | SCHEMA_FAIL (parses, wrong shape) | **Failure rate** |
|---|---|---|---|---|
| Naive prompting | 11 / 20 | 5 / 20 | 4 / 20 | **45%** |
| Schema-constrained (forced tool use) | 19 / 20 | 0 / 20 | 1 / 20 | **5%** |

Nine times out of twenty, the naive path handed downstream code something it could not safely use, with no exception ever raised for four of those nine — they parsed fine and were simply wrong. The schema-constrained path failed once in twenty, and even that one failure is instructive, not a rounding error: the model returned `"severity": "Critical"` — structurally exactly right, one string, correct field — with the wrong *case*. Structural constraint enforces shape at generation time; it does not, on its own, guarantee that a downstream string-equality check written for lowercase `"critical"` will match it. **A nine-times reduction in failure rate is not the same claim as "failure rate is now zero," and the difference between those two claims is the whole reason Lab M02-C's validator still runs on the schema-constrained path's output too** — defense in depth, not "we don't need the hand-built validator anymore now that the API has one."

**Re-ascend note.** Once a learner has personally measured this gap, reaching for `tool_choice` (or, later in the course, a framework's structured-output decorator) stops being "the modern way to do it" received wisdom and becomes an informed choice with a known, quantified payoff and a known, still-real remaining failure rate. A learner who reaches for the API's schema-constrained mode *before* measuring the naive failure rate for themselves has the feature without the judgment about what it's actually buying — exactly the trap this course's framework-last philosophy exists to avoid, one API feature early instead of one framework early.

**Misconception 1 — "Schema-constrained output guarantees correctness."** It guarantees *shape* — the right keys, the right types, enum membership. It does not, and cannot, guarantee that a syntactically valid, schema-conformant severity of `"low"` is the *true* severity of the incident. A model can be confidently, fluently, structurally wrong, and a downstream reader who sees valid-looking structured output has no signal at all, from the shape alone, about whether the *content* was verified against anything. This is the same trap AIE-204-M04 named for a fluent-sounding judge: a well-formed answer and a correct answer are different properties, and structural constraint only buys the first one.

**Misconception 2 — "Now that the API can constrain the schema, the hand-built validator from Lab M02-A is obsolete."** The 5% remaining failure rate is the direct rebuttal — even the constrained path produced one item the validator caught that the API's own guarantee did not. A provider's structural guarantee is an external contract you don't control across model versions, pricing tiers, or providers, exactly the way this course's *durability: swappable* framing treats every vendor-specific API surface. The validator built in Lab M02-A is the layer that still runs when that contract quietly changes underneath you, and it is also the *only* layer that checks anything the schema itself can't express — `minLength`, cross-field consistency, anything business-specific enough that it was never going to live in a vendor's schema format anyway.

`llm_client.py` (provided; shared by every lab):

```python
"""
llm_client.py -- the thin interface every extraction pipeline in this module
is built on. Two methods, not one, because this module's whole point is
comparing two DECODING PATHS for the same request:

  complete()            -- naive path. The model receives a plain-text
                            request to "respond with JSON" and returns
                            plain text. Nothing about the API call itself
                            constrains the shape of what comes back.
  complete_structured()  -- schema-constrained path. The caller hands the
                            provider a JSON Schema; the provider's decoding
                            is constrained to emit something matching that
                            shape (Claude's forced tool-use is the real
                            mechanism -- see AnthropicClient below).

Durability discipline, same as AIE-204-M04's llm_client.py: every lesson and
lab in this module imports LLMClient (and, for tests, FakeExtractionClient)
from this file -- never a vendor SDK directly. AnthropicClient is the only
place in the module allowed to import a vendor SDK or name a model string.
"""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Protocol


class LLMClient(Protocol):
    """Anything with these two methods can serve as an extraction backend."""

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        """Naive path: return the raw text completion for `prompt`. No
        structural guarantee about what that text contains."""
        ...

    def complete_structured(self, prompt: str, schema: dict, *, temperature: float = 0.0,
                             max_tokens: int = 512) -> str:
        """Schema-constrained path: return a JSON-encoded string whose
        structure was produced by a decoding path that was constrained by
        `schema` at generation time (not validated after the fact)."""
        ...


@dataclass
class FakeExtractionClient:
    """Deterministic stand-in used by every test in this module, and by the
    labs when run offline. Two independent canned dicts -- one per method --
    because the two paths are different mechanisms, not just different
    prompts for the same mechanism.

    Matching rule (both methods): the LONGEST canned key that is a substring
    of the prompt wins. This is deliberate -- a repair prompt is built by
    APPENDING a marker to the original prompt, so it still contains the
    original prompt's marker as a substring. The longer, more specific
    marker must win, or a repair retry would just replay the original
    response forever.
    """
    canned: dict[str, str] = field(default_factory=dict)
    canned_structured: dict[str, str] = field(default_factory=dict)

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        return self._lookup(prompt, self.canned)

    def complete_structured(self, prompt: str, schema: dict, *, temperature: float = 0.0,
                             max_tokens: int = 512) -> str:
        return self._lookup(prompt, self.canned_structured)

    @staticmethod
    def _lookup(prompt: str, table: dict[str, str]) -> str:
        matches = [(key, response) for key, response in table.items() if key in prompt]
        if not matches:
            raise KeyError(
                "FakeExtractionClient: no canned response matches this prompt. "
                "This almost always means your prompt builder doesn't include "
                "the exact ID marker the test data expects -- check it against "
                "the lab's prompt contract."
            )
        _, response = max(matches, key=lambda pair: len(pair[0]))
        return response


class AnthropicClient:
    """The real backend. This is the ONLY file in this module that imports
    a vendor SDK or names a specific model.

    complete() sends a plain prompt and returns the text response -- the
    naive path, with no structural guarantee.

    complete_structured() defines a single tool whose input_schema IS the
    caller's schema, forces the model to call it (tool_choice), and returns
    the tool call's `input` re-serialized as JSON text. This is what "actual
    schema constraints" means at the API level: the model's decoding is
    constrained to produce an object shaped like the schema BEFORE the SDK
    ever hands you a string -- it is not "ask nicely and hope," it is a
    different generation mechanism.
    """

    DEFAULT_MODEL = "claude-haiku-4-5"

    def __init__(self, model: str = DEFAULT_MODEL, api_key: str | None = None):
        import anthropic  # imported here, not at module scope, so labs that
        # never instantiate AnthropicClient don't require the package installed
        self._client = anthropic.Anthropic(api_key=api_key)
        self._model = model

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        response = self._client.messages.create(
            model=self._model,
            max_tokens=max_tokens,
            temperature=temperature,
            messages=[{"role": "user", "content": prompt}],
        )
        return response.content[0].text

    def complete_structured(self, prompt: str, schema: dict, *, temperature: float = 0.0,
                             max_tokens: int = 512) -> str:
        import json
        tool = {
            "name": "record_extraction",
            "description": "Record the structured extraction result.",
            "input_schema": schema,
        }
        response = self._client.messages.create(
            model=self._model,
            max_tokens=max_tokens,
            temperature=temperature,
            tools=[tool],
            tool_choice={"type": "tool", "name": "record_extraction"},
            messages=[{"role": "user", "content": prompt}],
        )
        for block in response.content:
            if block.type == "tool_use":
                return json.dumps(block.input)
        raise RuntimeError("model did not return a tool_use block despite forced tool_choice")
```

def validate_schema(data, schema: dict, path: str = "$") -> list[str]:
    errors: list[str] = []
    expected_type = schema.get("type")

    if expected_type is not None:
        py_type = _TYPE_MAP[expected_type]
        if expected_type in ("number", "integer") and isinstance(data, bool):
            errors.append(f"{path}: expected {expected_type}, got boolean")
            return errors
        if not isinstance(data, py_type):
            errors.append(f"{path}: expected {expected_type}, got {type(data).__name__}")
            return errors

    if "enum" in schema and data not in schema["enum"]:
        errors.append(f"{path}: must be one of {schema['enum']}, got {data!r}")

    if expected_type == "string":
        if "minLength" in schema and len(data) < schema["minLength"]:
            errors.append(f"{path}: length {len(data)} is below minLength {schema['minLength']}")
        if "maxLength" in schema and len(data) > schema["maxLength"]:
            errors.append(f"{path}: length {len(data)} exceeds maxLength {schema['maxLength']}")

    if expected_type == "object":
        for key in schema.get("required", []):
            if key not in data:
                errors.append(f"{path}: missing required field '{key}'")
        for key, value in data.items():
            sub_schema = schema.get("properties", {}).get(key)
            if sub_schema is not None:
                errors.extend(validate_schema(value, sub_schema, path=f"{path}.{key}"))

    if expected_type == "array":
        if "minItems" in schema and len(data) < schema["minItems"]:
            errors.append(f"{path}: has {len(data)} items, below minItems {schema['minItems']}")
        item_schema = schema.get("items")
        if item_schema is not None:
            for i, item in enumerate(data):
                errors.extend(validate_schema(item, item_schema, path=f"{path}[{i}]"))

    return errors


def parse_and_validate(raw: str, schema: dict) -> dict:
    try:
        data = json.loads(raw)
    except json.JSONDecodeError as exc:
        raise ValidationError([f"not valid JSON: {exc}"], kind="parse") from exc
    errors = validate_schema(data, schema)
    if errors:
        raise ValidationError(errors, kind="schema")
    return data

    required = ", ".join(schema.get("required", []))
    return f"""INCIDENT_ID: {incident_id}
Read the incident report below and extract a structured ticket record.

Required fields: {required}
severity must be one of: low, medium, high, critical

action_items: a JSON array of at least one string
estimated_resolution_hours (optional): a number

INCIDENT REPORT:
{incident_text}

Respond with ONLY a JSON object, no other text."""


def build_repair_prompt(original_prompt: str, previous_raw: str, errors: list[str],
                         incident_id: str) -> str:
    error_lines = "\n".join(f"- {e}" for e in errors)
    return (
        original_prompt
        + f"\n\n[REPAIR REQUEST INCIDENT_ID: {incident_id}] Your previous response was:\n"
        + previous_raw
        + "\n\nThat response failed validation for these specific reasons:\n"
        + error_lines
        + "\n\nRespond again with ONLY a corrected JSON object, no other text."
    )


def extract_ticket(client: LLMClient, incident_id: str, incident_text: str,
                    schema: dict = TICKET_SCHEMA, max_retries: int = 2) -> dict:
    prompt = build_extraction_prompt(incident_id, incident_text, schema)
    raw = client.complete(prompt, temperature=0.0)

    last_error: ValidationError | None = None
    for attempt in range(max_retries + 1):
        try:
            return parse_and_validate(raw, schema)
        except ValidationError as exc:
            last_error = exc
            if attempt == max_retries:
                raise
            raw = client.complete(
                build_repair_prompt(prompt, raw, exc.errors, incident_id),
                temperature=0.0,
            )
    raise last_error  # unreachable, satisfies type-checkers

from __future__ import annotations

import re

from lab_a_extraction import (
    TICKET_SCHEMA, ValidationError, parse_and_validate,
    build_extraction_prompt, build_repair_prompt,
)

INCIDENTS = {
    "INC-B1": "Login is failing for every user after the 2am deploy.",
    "INC-B2": "The invoice PDF generator crashes on invoices with more than 50 line items.",
    "INC-B3": "A customer's account was auto-suspended by the fraud filter in error.",
    "INC-B4": "Search results are missing the last 24 hours of new listings.",
    "INC-B5": "A customer's data-export request has been stuck in 'processing' for two days.",
    "INC-B6": "A customer says their account's billing address won't save.",
}

PREDICTED_REPAIR_PATH = {
    "INC-B1": "deterministic",  # markdown fence around otherwise-valid JSON
    "INC-B2": "deterministic",  # trailing comma
    "INC-B3": "deterministic",  # Python True literal in an extra field
    "INC-B4": "deterministic",  # prose wrapped around valid JSON
    "INC-B5": "model_retry",    # valid JSON, but severity outside the enum
    "INC-B6": "model_retry",    # single-quoted, and the value has a real apostrophe
}


class ExtractionFailed(Exception):
    def __init__(self, errors: list[str], attempts: int):
        super().__init__("; ".join(errors))
        self.errors = errors
        self.attempts = attempts


def _strip_code_fence(text: str) -> str:
    stripped = text.strip()
    if stripped.startswith("```"):
        stripped = re.sub(r"^```(?:json)?\s*", "", stripped)
        stripped = re.sub(r"\s*```$", "", stripped)
    return stripped


def _extract_balanced_object(text: str) -> str | None:
    start = text.find("{")
    if start == -1:
        return None
    depth = 0
    for i in range(start, len(text)):
        if text[i] == "{":
            depth += 1
        elif text[i] == "}":
            depth -= 1
            if depth == 0:
                return text[start:i + 1]
    return None


def deterministic_repair(text: str) -> str:
    fixed = _strip_code_fence(text)
    extracted = _extract_balanced_object(fixed)
    if extracted is not None:
        fixed = extracted
    fixed = re.sub(r",\s*([}\]])", r"\1", fixed)          # trailing commas
    fixed = re.sub(r"\bTrue\b", "true", fixed)
    fixed = re.sub(r"\bFalse\b", "false", fixed)
    fixed = re.sub(r"\bNone\b", "null", fixed)
    return fixed


def extract_ticket_with_repair(client, incident_id: str, incident_text: str,
                                schema: dict = TICKET_SCHEMA, max_retries: int = 1) -> dict:
    prompt = build_extraction_prompt(incident_id, incident_text, schema)
    raw = client.complete(prompt, temperature=0.0)

    try:
        data = parse_and_validate(raw, schema)
        return {"data": data, "repair_path": "none", "attempts": 1}
    except ValidationError as exc:
        first_error = exc

    if first_error.kind == "parse":
        try:
            data = parse_and_validate(deterministic_repair(raw), schema)
            return {"data": data, "repair_path": "deterministic", "attempts": 1}
        except ValidationError:
            pass  # deterministic repair didn't fully resolve it -- fall through

    attempts = 1
    current_raw = raw
    current_error = first_error
    for _ in range(max_retries):
        attempts += 1
        current_raw = client.complete(
            build_repair_prompt(prompt, current_raw, current_error.errors, incident_id),
            temperature=0.0,
        )
        try:
            data = parse_and_validate(current_raw, schema)
            return {"data": data, "repair_path": "model_retry", "attempts": attempts}
        except ValidationError as exc:
            current_error = exc

    raise ExtractionFailed(current_error.errors, attempts=attempts)

@dataclass
class ExperimentResult:
    counts: dict[str, int]
    total: int

    @property
    def failure_rate(self) -> float:
        failures = self.counts.get("JSON_FAIL", 0) + self.counts.get("SCHEMA_FAIL", 0)
        return failures / self.total


def classify_response(raw: str, schema: dict = TICKET_SCHEMA) -> str:
    try:
        parse_and_validate(raw, schema)
        return "PASS"
    except ValidationError as exc:
        return "JSON_FAIL" if exc.kind == "parse" else "SCHEMA_FAIL"


def run_naive_experiment(client, incidents: dict[str, str], schema: dict = TICKET_SCHEMA) -> ExperimentResult:
    counts = {"PASS": 0, "JSON_FAIL": 0, "SCHEMA_FAIL": 0}
    for incident_id, text in incidents.items():
        prompt = build_extraction_prompt(incident_id, text, schema)
        raw = client.complete(prompt, temperature=0.0)
        counts[classify_response(raw, schema)] += 1
    return ExperimentResult(counts=counts, total=len(incidents))


def run_schema_constrained_experiment(client, incidents: dict[str, str],
                                       schema: dict = TICKET_SCHEMA) -> ExperimentResult:
    counts = {"PASS": 0, "JSON_FAIL": 0, "SCHEMA_FAIL": 0}
    for incident_id, text in incidents.items():
        prompt = build_extraction_prompt(incident_id, text, schema)
        raw = client.complete_structured(prompt, schema, temperature=0.0)
        counts[classify_response(raw, schema)] += 1
    return ExperimentResult(counts=counts, total=len(incidents))

## Three-tier reading

Specific to this module's subject — what it means to make a model's output a data structure you trust — not boilerplate.

- **Tier 1 — material ground.** A schema constrains *shape*; it has never, on any provider, at any point in this course's toolchain, constrained *truth*. Structural validity and factual correctness are different properties, verifiable independently, and this module's own Lab M02-C measured exactly one case where they came apart — a structurally perfect record with a wrong value. This is documented in the module's own run output, not asserted.

- **Tier 2 — what the field suppresses.** "Just use structured outputs" — the pitch behind every provider's JSON-mode feature and every wrapper library that ships a decorator promising reliable JSON — suppresses that the reliability being sold is a **shape** guarantee marketed with the confidence of a **correctness** guarantee. The marketing rarely says "your enum will always be one of the values you listed, and that value will still sometimes be wrong" — it says "structured outputs" and lets the reader's own hope fill in the stronger claim. The honest version of the pitch is less exciting and, per this module's own measured numbers, still very much worth having.

- **Tier 3 — sit with this.** Every layer of this module — the validator, the deterministic repair, the bounded retry — exists to make a model's output *safe for code to trust without a human reading it first*. That is the entire design goal: remove the human from the loop for the routine case, because reading every extracted ticket by hand doesn't scale. But the one item in this module's own measured 20 that a structurally perfect response got wrong — the wrong-case severity — is exactly the kind of error that a pipeline built to remove the human from the loop is least likely to have a human still positioned to catch. When you build a system whose entire purpose is "so nobody has to read this by hand," what happens to the one time in twenty it needed a human to read it by hand anyway — and who finds out, and when?
