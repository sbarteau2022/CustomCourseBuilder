## Lessons

### Lesson 1 — The tool-call loop from scratch

**Teaching text**

An "agent" is not a new kind of model. It is a loop wrapped around an ordinary completion call, and the loop has exactly four moving parts: build a prompt that describes the question, the available tools, and everything that's happened so far; call the model; parse whatever text comes back into either an **action** (a tool name and an input) or a **final answer**; if it's an action, run the corresponding Python function and glue its output onto the transcript as an **observation**, then go back to step one. This is the ReAct pattern — **Th**ink, **A**ct, **Observe**, repeat — and every part of it is code you write and can read. The model never "calls" anything. It writes text that looks like `Action: search_hr_policy[vacation days per year]`, and your code — a regular expression, a dictionary lookup, a function call — is the only thing that turns that text into an actual side effect. This is the single fact this lesson exists to make un-forgettable, because every framework and every provider API from here on will work very hard to make it invisible.

The loop needs a **prompt builder** that tells the model, at each step, what tools exist (by name and description only — the model never sees your tool's source, only its description, which means a vague description is a vague contract), what the running transcript looks like so far, and what format to respond in. It needs a **parser** that reads the model's raw text back into a structured `ParsedOutput` — a thought, and either an action name plus an input, or a final answer. And it needs a **dispatcher**: given a parsed action, look the tool up by name and run it, or produce an `ERROR` observation (never a crash) if the model asked for a tool that doesn't exist. Nothing here requires an SDK. It requires string formatting, `re`, and a `dict`.

**Worked example — a real two-hop trace, verified**

Question: *"How many vacation days do employees get per year, plus a 2-day signing bonus?"* Tools: `search_hr_policy` (wraps M04's corpus retrieval) and `calculate` (a safe arithmetic evaluator — see `tools.py` below). Run with `agent_id="vacation_bonus"`, the actual three-step trace this module's `test_lab_a.py` reproduces:

```
AGENT_STEP 1
  Thought: I need the base vacation days first.
  Action: search_hr_policy[vacation days per year]
  Observation: C01: Employees accrue 15 days of paid vacation per year,
               credited at the start of each quarter.

AGENT_STEP 2
  Thought: Now add the 2-day signing bonus.
  Action: calculate[15 + 2]
  Observation: 17

AGENT_STEP 3
  Thought: I have the total.
  Final Answer: 17 vacation days total (15 base + 2 bonus).
```

Three model calls, two tool calls, one final answer — and every line above is data your own `run_agent` function produced and returned as a `Step` object, inspectable after the fact. Nothing about this trace required a framework; it required a prompt builder embedding an `AGENT_STEP` marker so each turn's completion can be scripted and tested deterministically (the same `FakeGenerationClient` pattern M04 used for judges), a parser reading `Action: name[input]` or `Final Answer: ...` back out, and eleven lines of loop.

**Misconception 1 — "Native function-calling / tool-use APIs are a fundamentally different mechanism from 'the model just writes text and you parse it.'"** They are not. When a provider's API returns a structured tool-call object instead of a raw string, the provider has moved the parsing step — usually via constrained decoding that forces the model's output to match a JSON schema — onto their side of the wire. Your code still has to look up the tool by name, still has to run it, still has to serialize its result and hand it back as the next turn's input. The loop's shape — prompt, call, parse, dispatch, observe, repeat, until a stop condition — is identical either way. This module builds the text-parsing version by hand on purpose, so that when a framework hands you a `tool_calls` list in M07, you recognize it immediately as the same four moving parts with the parsing step outsourced, not as a different kind of thing.

**Misconception 2 — "The loop naturally knows when to stop."** It does not. A loop with no `max_steps` and a model that never emits `Final Answer` — because it doesn't trust its own tool result, because a tool's confirmation message is ambiguous, because it's stuck comparing two numbers it already has — runs forever, or until you kill the process. This module's own `test_step_ceiling_stops_a_non_terminating_agent` (Lab M05-A) proves it directly: a two-entry canned script that just keeps calling `calculate[1 + 1]` produces exactly `max_steps` tool calls and a `stopped_reason="step_ceiling"` result with no answer — the loop stopped because the *code* enforced a limit, not because the model decided to. Lesson 4 turns this same fact into a hard safety requirement, not just a loop-hygiene detail.

**Misconception 3 — "More tools make a smarter agent."** Every tool you add is one more label the model has to correctly discriminate, at every single step, from its description alone — it never sees your code, only the one or two sentences you wrote about what the tool does. Two tools with overlapping descriptions (imagine a second `search_benefits_faq` tool that could plausibly also answer a parental-leave question) don't give the agent more capability so much as more ways to guess wrong. This module's `test_unknown_tool_produces_error_observation_and_continues` is the seatbelt for the *loud* version of this failure — a tool name that doesn't exist at all produces a visible `ERROR` observation and the loop survives. There is no equivalent seatbelt, by construction, for the *quiet* version: a tool name that does exist, chosen wrong. That failure produces a plausible-looking observation and a plausible-looking final answer, and nothing about the trace flags it — which is exactly why this module's Assessment (and M06's agent-eval harness) has to go looking for it on purpose, the same way M04 had to go looking for retrieval failures a passing final answer hides.

### Lesson 2 — Planning as a separate, inspectable step

**Teaching text**

ReAct's `Thought` at step *k* is regenerated fresh from the transcript so far, every single time. That is a genuine strength for short, reactive tasks — it can course-correct on new information immediately — and a genuine weakness for anything that needs several tool calls in a *known* order: nothing about the loop ever commits, in writing, to "this task needs four steps, in this order," and nothing about a ReAct transcript is reviewable *before* it runs, only after, as a trace of what already happened. **Plan-and-execute** pulls that commitment out into its own step: one upfront call produces a complete `Plan` — a JSON list of `{tool, input}` steps — before a single tool executes. That plan is an artifact. It can be logged, shown to a human, vetoed, or handed to an eval harness, all before any side effect has happened — which is a property no live ReAct transcript has, because by the time step *k*'s action is visible, step *k*'s action has already run.

Execution then walks the plan step by step, recording each step's observation and status (`pending` → `done` or `failed`). A failed step — a tool that doesn't exist, or (in this module's toy retrieval) a query the embedding table doesn't recognize — triggers exactly **one bounded replan**: the model is shown the completed steps, the failed step, and its observation, and asked to revise only the *remaining* steps. This is not a retry loop. A retry loop repeats the same action hoping for a different result; a replan asks for a *different* action, informed by evidence the first one failed, and it is capped — this module's `execute_plan` accepts `max_replans` and never exceeds it, so a plan that keeps failing gives up cleanly instead of looping forever (Lesson 4 returns to exactly this failure shape, at the level of a whole consequential action instead of one retrieval query).

**Worked example — a real four-step plan, and a real repaired one**

Question: *"How many total weeks of parental leave do both caregivers get combined, and is that more than the standard vacation days?"* — a question no single tool call answers; it needs three facts and one computation. The clean plan, produced by one call and executed without any failure:

```
1. search_hr_policy["primary caregiver parental leave weeks"]  -> C08: ...12 weeks.
2. search_hr_policy["secondary caregiver parental leave weeks"] -> C10: ...4 weeks.
3. search_hr_policy["vacation days per year"]                   -> C01: ...15 days...
4. calculate["12 + 4"]                                          -> 16
```
(12 + 4 = 16 — the actual, verified result `test_clean_plan_executes_and_synthesizes` checks for.) Synthesis, from the four observations alone: *"16 weeks of combined parental leave, which is more than the 15 vacation days."*

Now the same plan with a deliberately imprecise first step — `search_hr_policy["parental leave for primary caregiver"]`, a string this module's toy embedding table doesn't recognize:

```
1. search_hr_policy["parental leave for primary caregiver"]
   -> UNKNOWN_QUERY: 'parental leave for primary caregiver' is not a
      query this tool recognizes. Known queries: ...          [FAILED]

   -- replan triggered, remaining steps (1-4) revised --

1. search_hr_policy["primary caregiver parental leave weeks"]  -> C08: ...12 weeks.  [DONE]
2. search_hr_policy["secondary caregiver parental leave weeks"] -> C10: ...4 weeks.  [DONE]
3. search_hr_policy["vacation days per year"]                   -> C01: ...15 days.  [DONE]
4. calculate["12 + 4"]                                          -> 16               [DONE]
```

One failure, one replan, the same correct synthesis at the end — `test_failed_step_triggers_exactly_one_replan_then_succeeds` reproduces exactly this. And `test_replan_budget_of_one_is_not_exceeded` reproduces the other branch: a repair that is *still* wrong exhausts the one-replan budget and the whole plan reports `answer=None` rather than looping — a clean failure with a legible cause, not a hang.

**Misconception 1 — "ReAct already plans, so an explicit plan step is redundant."** ReAct's `Thought` is local and disposable — it exists for one step and is regenerated from scratch the next. It never commits, before execution, to what step 3 or step 4 will be; there is nothing to review before the loop has already taken those actions. An explicit `Plan` is the opposite: a single artifact, produced once, reviewable by a human or a governor *before* step 1 runs. These are different properties, not different implementations of the same property — a system can have excellent step-by-step reasoning and zero pre-execution auditability at the same time, which is exactly ReAct's situation.

**Misconception 2 — "Planning up front means never replanning."** `execute_plan`'s `max_replans` parameter refutes this directly — planning up front doesn't forbid revision, it *bounds* it. The distinction that matters is between a bounded, logged repair (one replan call, visible in `PlanResult.replanned`, with the failed step and its observation shown to the model) and an unbounded silent retry (the same action, repeated, with no record of why). Lesson 4's ungated PTO scenario is the second pattern at the level of a real side effect; this lesson's replan is the first pattern at the level of a retrieval query — same underlying principle, two different altitudes.

**Misconception 3 — "A bigger, smarter model doesn't need explicit planning — it can just wing it well."** This conflates capability with auditability, which are different axes entirely. Even a model that reasons flawlessly step to step still leaves you, under plain ReAct, with nothing but a post-hoc transcript — there was never a moment before execution where a human or a governor could have looked at "the plan" and vetoed step 3. Explicit planning is an engineering property of the *system*, not a compensation for a weak model: it's the difference between reviewing a flight plan before takeoff and reconstructing one from the black box afterward.

### Lesson 3 — Memory: what persists, what doesn't, and why that's a design choice

**Teaching text**

"Memory" in an agent system is not one thing. This module names three layers, and only builds the middle one, on purpose. **Working memory** is Lab M05-A's `scratchpad` string — it exists for the duration of one `run_agent` call and is gone the instant the function returns; it is not memory across turns at all, it is just the current loop's own transcript. **Session memory** — this lesson's subject — persists across multiple turns of one ongoing conversation, in the same Python process, and is where this module draws a hard line: it is *deliberately* bounded by a token budget, not an unlimited log. **Long-term memory** — persisting across sessions entirely, typically backed by a database or a vector store of past interactions — is real, important, and explicitly out of scope here: this course's "no vector database until it's named" discipline (M01's toolchain note, carried forward) applies to memory exactly as it applies to retrieval, and long-term memory is a heavier commitment (durability, privacy, staleness) this module does not make lightly or in passing.

`ConversationMemory` holds a list of `Turn`s plus a running `summary` string. Every time a turn is added, the class checks its own rendered size against a token budget (M01's `TokenCounter`, ported forward unchanged); if it's over budget, the *oldest* turn is popped and folded into the summary via one more model call — not dropped, not kept forever, **folded**, with an explicit instruction to preserve concrete facts (IDs, numbers, names) and discard pleasantries. One rule holds regardless of budget: the single most recent turn is never evicted, even if it alone exceeds the budget — the agent must always be able to see what was just said to it. This is memory as a budget decision, the same species of tradeoff as M01's context budget, not a capacity to be maximized.

**Worked example — a real, measured trajectory**

Seven turns, budget = 35 tokens (`ApproxTokenCounter`, ~4 chars/token), a scripted, deterministic summarizer. The actual numbers this module's `test_lab_c.py` reproduces:

| Turn added | Content (truncated) | Tokens after add | Turns kept | Summary present? |
|---|---|---|---|---|
| 1 (user) | "My employee ID is E4521..." | 16 | 1 | no |
| 2 (assistant) | "You get 15 vacation days..." | 27 | 2 | no |
| 3 (user) | "What about parental leave..." | 31 | **1** | **yes** — turns 1–2 folded |
| 4 (assistant) | "12 weeks." | 33 | 1 | yes — turn 3 folded |
| 5 (user) | "And secondary caregivers?" | 36 | 1 | yes — turn 4 folded |
| 6 (assistant) | "4 weeks." | 40 | 1 | yes — turn 5 folded |
| 7 (user) | "Can you remind me what my employee ID was?" | 40 | 1 | yes — turn 6 folded |

Two things worth reading closely. First, turns 1 and 2 both get folded into the summary the moment turn 3 is added — one `add_turn` call can trigger more than one eviction, because the `while` loop keeps folding until the render fits or only one turn remains. Second, at turns 5–7 the token count (36, 40, 40) stays *above* the 35-token budget and never comes back down — because the rule "never evict the last turn" wins over the rule "stay under budget" when they conflict, on purpose. After all seven turns: `mem.render()` contains `"E4521"` — the fact survived, because every fold was instructed to preserve concrete facts — but does **not** contain the literal sentence `"How many vacation days do I get?"` — the original wording is gone, paraphrased away three folds ago. A user asking turn 7's question gets a system that still knows their employee ID and has forgotten the exact way they first mentioned it, which is precisely the tradeoff this lesson names as deliberate, not degraded.

**Misconception 1 — "More memory (a bigger budget, keep everything) is always better."** M01 already established that every extra token in context costs real latency and real money on *every subsequent call*, not just the one that added it, and dilutes what the model has to attend to. A memory design that keeps every turn verbatim forever means a conversation's 50th turn pays the full token cost of its first — and by then, the model's attention has to compete against a scratchpad of its own making. The fold-not-keep-everything design in `ConversationMemory` is not a limitation to route around; it is the thing that keeps a long-running agent's prompt from becoming mostly itself.

**Misconception 2 — "Memory means the agent remembers everything forever automatically."** Nothing in `ConversationMemory` survives past the Python process it runs in — it is session memory, not long-term memory, and this module builds no persistence layer at all. Within a session, it's narrower still: the moment the budget is crossed, the exact wording of the oldest turn is *deliberately* replaced by a fact-preserving paraphrase. "The agent forgot exactly how I phrased it, three turns ago" is not a bug report against this design; it's the summarizer doing the one job it has.

**Misconception 3 — "Agent memory and RAG retrieval are the same mechanism."** M03/M04's retrieval selects from a fixed, externally authored corpus — a document nobody in the conversation wrote, sitting there before the conversation started. This lesson's memory selects from and rewrites the agent's *own* conversation history — content the system itself is a party to producing. The two can later share retrieval mechanics (a vector store of past conversations is a legitimate long-term-memory design, out of scope here) without being the same thing: conflating them erases exactly the distinction Lesson 4's ethics reading returns to — *who authored what the system is drawing on*, and who is accountable for it being wrong.

### Lesson 4 — Bounded autonomy: checkpoints, approval gates, hard ceilings

**Teaching text**

Every tool this module has used so far is a **read**: `search_hr_policy` and `calculate` can be called wrong and the worst outcome is a bad observation the loop can recover from or a human can catch in the final answer. A **write** — a tool with a side effect that outlives the call, like this lesson's `file_pto_request` — is a different category entirely: calling it wrong, or calling it *right* three times instead of once, changes something in the world that the loop itself has no way to undo. Bounded autonomy is the engineering answer to that category difference, and it is built here as three separable commitments, layered *around* the loop and the tools (mirroring Lesson 2's argument for planning as its own concern, not folded invisibly into the loop):

1. **A human-approval checkpoint before any consequential action**, deny-by-default. `Governor.guard_tool` wraps a tool named in `consequential_tools` so that every call goes through an `approval_fn` first; with no `approval_fn` wired in, the default (`deny_all`) refuses the action rather than silently allowing it.
2. **A hard step ceiling the agent cannot exceed.** `Governor.before_step` is called once per loop iteration, *before* the model is even asked for that step — it raises `StepCeilingExceeded` the instant the ceiling would be crossed, so the call that would have exceeded it is never attempted, not attempted-and-then-flagged.
3. **A hard cost ceiling**, same enforcement shape, same reason: raise before spending, not warn after.

All three are provable by testing the `Governor` in isolation from any model at all — `guard_tool` and `before_step` are plain functions with no dependency on what a model says, which is exactly what makes them trustworthy as a safety layer instead of one more thing that only works when the prompt goes as expected.

**Worked example — the same model, ungated vs. gated, both scenarios actually run**

Question: *"File a PTO request for March 10-14 and make sure it goes through."* Tool: `file_pto_request` — sandboxed here as an in-memory list append, never a real system, but confirmed with a generic `"Request filed: ..."` message that gives the model no signal about whether an *earlier* call already succeeded. **Ungated** (`run_agent`, no governor, `test_ungated_agent_files_three_duplicate_requests`):

```
STEP 1  Thought: I'll file the PTO request for March 10-14.
        Action: file_pto_request[March 10-14]      -> Request filed: March 10-14
STEP 2  Thought: I'm not fully sure it went through -- I'll file it again to be safe.
        Action: file_pto_request[March 10-14]      -> Request filed: March 10-14
STEP 3  Thought: Still not fully confident -- one more time to be safe.
        Action: file_pto_request[March 10-14]      -> Request filed: March 10-14
STEP 4  Thought: That should be enough attempts.
        Final Answer: I've filed your PTO request for March 10-14.
```

`filed == ["March 10-14", "March 10-14", "March 10-14"]` — three real-world-shaped side effects, from a model that never said anything unreasonable. Every `Thought` above is the kind of caution a human would praise in a person. **Gated** (`run_agent_bounded`, `consequential_tools={"file_pto_request"}`, an `approve_first_then_deny` reviewer, `test_gated_agent_blocks_the_duplicate_and_files_once`):

```
STEP 1  (identical Thought/Action to ungated step 1) -> APPROVED -> Request filed: March 10-14
STEP 2  (identical Thought/Action to ungated step 2) -> DENIED: a human reviewer did not
        approve file_pto_request[March 10-14]. Do not retry this action without new information.
STEP 3  Thought: The second attempt was denied as a duplicate -- I already filed this
        once, so I'll stop retrying and report success.
        Final Answer: I've filed your PTO request for March 10-14 (confirmed after one
        submission; a duplicate attempt was blocked).
```

`filed == ["March 10-14"]`. Read this carefully: the model's step-1 and step-2 *reasoning* is identical in both runs — the gate doesn't change what the model thinks, it changes what actually happens when the model acts on it, and that changed outcome becomes a new observation ("DENIED...") the model's own next `Thought` correctly reasons over. The gate isn't just a wall; it's a fact the loop gets to see and respond to.

**Misconception 1 — "A well-aligned model won't take a harmful or duplicate consequential action on its own."** The ungated trace above refutes this with zero adversarial input and zero jailbreak — every `Thought` is plausible, well-intentioned, and individually reasonable ("let me be extra careful" is good advice in general). Three real side effects came from compounding ordinary uncertainty, not misalignment. "The model will just know not to" describes a hope, not a control; `test_ungated_agent_files_three_duplicate_requests` is what a control looks like — a number you can check.

**Misconception 2 — "A step ceiling is basically a performance or cost optimization, not a safety requirement."** Notice first that a step ceiling *alone* would not have stopped the PTO scenario above — three file calls plus a final answer complete in four steps, comfortably under any reasonable `max_steps`; the ceiling and the approval gate stop *different* failure classes, and neither substitutes for the other. Where the ceiling earns its "safety," not just "budget," label is in `Governor.before_step`'s enforcement shape: `test_step_ceiling_raises_before_a_fourth_call_is_ever_made` proves the call that would exceed the ceiling is never attempted at all — `filed` freezes at exactly the allowed count, not "close to" it. A ceiling that logs a warning and continues is a budget dashboard. A ceiling that raises before the next call happens is a bound.

**Misconception 3 — "Only 'obviously dangerous' tools need an approval gate; read-shaped or mildly-named tools are safe by default."** This module's own default — `deny_all`, applied to anything in `consequential_tools` with no `approval_fn` wired — bets the opposite way on purpose: a tool is judged consequential by what it *does* (creates a side effect that outlives the call), never by how alarming its name sounds. A quietly named `update_status` or `log_request` tool can be exactly as consequential as `delete_everything` if what it writes persists past the conversation; a team that gates by vibes will gate the scary-sounding tool and miss the boring one that does the same kind of damage.

## Labs

Every lab states its **Predict** before its **Build**, on paper, before any code runs. All four labs share `llm_client.py`, `tokenizer.py`, `corpus.py`, and `tools.py` below — write these once.

`llm_client.py` (provided; identical shape to AIE-204-M04's and AIE-302-M01/M04's — reuse directly if you already have it):

```python
"""
llm_client.py -- the thin interface this module's loop, planner, memory
summarizer, and judge are all built on. Identical shape to AIE-204-M04's
judge client and AIE-302-M01/M04's llm_client.py: one method, one
deterministic fake, one vendor adapter.
"""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Protocol


class LLMClient(Protocol):
    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        ...


@dataclass
class FakeGenerationClient:
    """Deterministic stand-in used by every test and lab in this module.
    Maps an exact substring of the prompt to a canned response; when more
    than one canned key matches, the LONGEST (most specific) key wins."""
    canned: dict[str, str] = field(default_factory=dict)

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        matches = [(key, resp) for key, resp in self.canned.items() if key in prompt]
        if not matches:
            raise KeyError(
                "FakeGenerationClient: no canned response matches this "
                "prompt. Check that your prompt-builder embeds the exact "
                "marker this scenario's canned dict expects."
            )
        _, response = max(matches, key=lambda pair: len(pair[0]))
        return response


class AnthropicClient:
    """The real backend. The only place in this module allowed to import
    a vendor SDK or name a model string."""

    DEFAULT_MODEL = "claude-haiku-4-5"

    def __init__(self, model: str = DEFAULT_MODEL, api_key: str | None = None):
        import anthropic
        self._client = anthropic.Anthropic(api_key=api_key)
        self._model = model

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        response = self._client.messages.create(
            model=self._model,
            max_tokens=max_tokens,
            temperature=temperature,

"""
tools.py -- the tools this module's labs give the agent: a retrieval
tool built directly on corpus.py (M04's corpus and cosine retrieval,
ported forward unchanged) and a safe arithmetic tool. Both take a
single string argument and return a single string observation -- the
classic ReAct tool shape.
"""
from __future__ import annotations

import ast
import operator

from corpus import CORPUS, CORPUS_EMBEDDINGS, QUERY_EMBEDDINGS, cosine_similarity

RELEVANCE_THRESHOLD = 0.2


def search_hr_policy(query: str) -> str:
    """Return the single best-matching corpus chunk's id and text for
    `query`, or a named failure observation.

    This module's embeddings are the same toy, hand-assigned table M04
    used (swappable for Lab M01-C's real embedding client outside of
    class) -- which means, unlike a real embedder, this tool can only
    recognize the exact query strings in QUERY_EMBEDDINGS. UNKNOWN_QUERY
    is this toy tool's stand-in for "the tool call failed" in general --
    the same shape a real ticket system, database, or internal API
    returns when it's called with a malformed or unrecognized argument.
    """
    normalized = query.strip().lower()
    if normalized not in QUERY_EMBEDDINGS:
        known = ", ".join(sorted(QUERY_EMBEDDINGS))
        return f"UNKNOWN_QUERY: '{query}' is not a query this tool recognizes. Known queries: {known}"
    query_vec = QUERY_EMBEDDINGS[normalized]
    scored = [
        (chunk_id, cosine_similarity(query_vec, CORPUS_EMBEDDINGS[chunk_id]))
        for chunk_id in CORPUS
    ]
    scored.sort(key=lambda pair: (-pair[1], pair[0]))
    best_id, best_sim = scored[0]
    if best_sim < RELEVANCE_THRESHOLD:
        return f"NO_MATCH: no corpus chunk scored above the relevance threshold ({RELEVANCE_THRESHOLD})"
    return f"{best_id}: {CORPUS[best_id]}"


_ALLOWED_BINOPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.Pow: operator.pow,
}
_ALLOWED_UNARYOPS = {ast.UAdd: operator.pos, ast.USub: operator.neg}


def _eval_node(node: ast.AST) -> float:
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _ALLOWED_BINOPS:
        return _ALLOWED_BINOPS[type(node.op)](_eval_node(node.left), _eval_node(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _ALLOWED_UNARYOPS:
        return _ALLOWED_UNARYOPS[type(node.op)](_eval_node(node.operand))
    raise ValueError(f"unsupported expression node: {ast.dump(node)}")


def calculate(expression: str) -> str:
    """Evaluate a pure arithmetic expression (+ - * / ** and parens
    only) through an AST allowlist -- never Python's `eval`, which
    would run arbitrary code an untrusted model completion could
    smuggle in through a tool argument. This is the smallest possible
    worked example of a lesson this module returns to at full scale in
    Lesson 4: a tool is a capability the model invokes through text it
    wrote, and text used to invoke a capability is exactly what needs
    to be constrained, never trusted outright."""
    try:
        tree = ast.parse(expression, mode="eval")
        result = _eval_node(tree.body)
    except (SyntaxError, ValueError, ZeroDivisionError, TypeError) as exc:
        return f"ERROR: could not evaluate '{expression}' ({exc})"
    return str(result)

"""Lab M05-A -- reference solution: the ReAct tool-call loop from scratch."""
from __future__ import annotations

import re
from dataclasses import dataclass
from typing import Callable

from llm_client import LLMClient

DEFAULT_MAX_STEPS = 6

THOUGHT_RE = re.compile(r"Thought:\s*(.*?)\n(?:Action:|Final Answer:)", re.DOTALL)
ACTION_RE = re.compile(r"Action:\s*(\w+)\[(.*)\]")
FINAL_RE = re.compile(r"Final Answer:\s*(.*)", re.DOTALL)


@dataclass
class Tool:
    name: str
    description: str
    run: Callable[[str], str]


@dataclass
class ParsedOutput:
    thought: str
    action_name: str | None
    action_input: str | None
    final_answer: str | None


@dataclass
class Step:
    step_number: int
    thought: str
    action_name: str | None
    action_input: str | None
    observation: str | None


@dataclass
class AgentResult:
    answer: str | None
    steps: list[Step]
    stopped_reason: str  # "final_answer" | "step_ceiling"


def build_agent_prompt(question: str, tools: list[Tool], scratchpad: str,
                        step_number: int, agent_id: str) -> str:
    tool_lines = "\n".join(f"- {t.name}: {t.description}" for t in tools)
    marker = f"AGENT_ID: {agent_id} | AGENT_STEP: {step_number}"
    return (
        "You are a ReAct agent. Answer the question using only the tools listed below.\n"
        f"{marker}\n\n"
        f"Tools:\n{tool_lines}\n\n"
        "Respond in exactly one of these two formats:\n"
        "Thought: <reasoning>\nAction: tool_name[input]\n"
        "-- or --\n"
        "Thought: <reasoning>\nFinal Answer: <answer>\n\n"
        f"Question: {question}\n\n"
        f"{scratchpad}"
    )


def parse_model_output(raw: str) -> ParsedOutput:
    thought_match = THOUGHT_RE.search(raw)
    thought = thought_match.group(1).strip() if thought_match else ""
    final_match = FINAL_RE.search(raw)
    if final_match:
        return ParsedOutput(thought=thought, action_name=None, action_input=None,
                             final_answer=final_match.group(1).strip())
    action_match = ACTION_RE.search(raw)
    if action_match:
        return ParsedOutput(thought=thought, action_name=action_match.group(1),
                             action_input=action_match.group(2).strip(), final_answer=None)
    raise ValueError(f"model output had neither a recognizable Action nor Final Answer: {raw!r}")


def run_agent(client: LLMClient, tools: list[Tool], question: str,
              max_steps: int = DEFAULT_MAX_STEPS, agent_id: str = "agent") -> AgentResult:
    tools_by_name = {t.name: t for t in tools}
    scratchpad = ""
    steps: list[Step] = []
    for step_number in range(1, max_steps + 1):
        prompt = build_agent_prompt(question, tools, scratchpad, step_number, agent_id)
        raw = client.complete(prompt)
        parsed = parse_model_output(raw)
        if parsed.final_answer is not None:
            steps.append(Step(step_number, parsed.thought, None, None, None))
            return AgentResult(answer=parsed.final_answer, steps=steps, stopped_reason="final_answer")
        if parsed.action_name not in tools_by_name:
            observation = f"ERROR: unknown tool '{parsed.action_name}'. Available tools: {sorted(tools_by_name)}"
        else:
            observation = tools_by_name[parsed.action_name].run(parsed.action_input)
        steps.append(Step(step_number, parsed.thought, parsed.action_name, parsed.action_input, observation))
        scratchpad += (
            f"Thought: {parsed.thought}\n"
            f"Action: {parsed.action_name}[{parsed.action_input}]\n"
            f"Observation: {observation}\n\n"
        )
    return AgentResult(answer=None, steps=steps, stopped_reason="step_ceiling")

    (now revised) step at the same index -- do not just move past a
    failed step. Once every step is "done", call build_synthesis_prompt
    for the final answer; if any step never reaches "done" (replan
    budget exhausted), return answer=None rather than guessing."""
    raise NotImplementedError

```python
"""Lab M05-B -- reference solution: explicit plan-then-execute, built on
Lab A's Tool primitive. A Plan is produced in ONE upfront call --
inspectable and loggable before any tool runs -- then executed step by
step; a failed step triggers exactly one replan before giving up."""
from __future__ import annotations

import json
from dataclasses import dataclass, field

from lab_a_agent_loop import Tool
from llm_client import LLMClient

FAILURE_PREFIXES = ("ERROR:", "UNKNOWN_QUERY:", "NO_MATCH:")


@dataclass
class PlanStep:
    tool: str
    tool_input: str
    status: str = "pending"  # pending | done | failed
    observation: str | None = None


@dataclass
class Plan:
    steps: list[PlanStep]


@dataclass
class PlanResult:
    answer: str | None
    plan: Plan
    replanned: bool


def build_planning_prompt(question: str, tools: list[Tool], agent_id: str) -> str:
    tool_lines = "\n".join(f"- {t.name}: {t.description}" for t in tools)
    marker = f"PLAN_REQUEST: {agent_id}"
    return (
        "You are a planning agent. Before taking any action, produce a "
        "complete plan as a JSON list of steps -- do not call any tool yet.\n"
        f"{marker}\n\n"
        f"Tools:\n{tool_lines}\n\n"
        'Respond with ONLY a JSON list, each item {"tool": "<tool name>", "input": "<tool input>"}.\n\n'
        f"Question: {question}"
    )


def parse_plan(raw: str) -> Plan:
    cleaned = raw.strip()
    if cleaned.startswith("```"):
        cleaned = cleaned.strip("`")
        if cleaned.lower().startswith("json"):
            cleaned = cleaned[4:]
    try:
        items = json.loads(cleaned)
    except json.JSONDecodeError as exc:
        raise ValueError(f"plan was not valid JSON: {raw!r}") from exc
    if not isinstance(items, list) or not items:
        raise ValueError(f"plan must be a non-empty JSON list, got: {raw!r}")
    steps = []
    for item in items:
        if "tool" not in item or "input" not in item:
            raise ValueError(f"plan step missing 'tool' or 'input': {item!r}")
        steps.append(PlanStep(tool=item["tool"], tool_input=item["input"]))
    return Plan(steps=steps)


def make_plan(client: LLMClient, tools: list[Tool], question: str, agent_id: str) -> Plan:
    raw = client.complete(build_planning_prompt(question, tools, agent_id))
    return parse_plan(raw)


def build_replan_prompt(question: str, tools: list[Tool], plan: Plan,
                         failed_index: int, agent_id: str) -> str:
    tool_lines = "\n".join(f"- {t.name}: {t.description}" for t in tools)
    failed_step = plan.steps[failed_index]
    completed = [
        {"tool": s.tool, "input": s.tool_input, "observation": s.observation}
        for s in plan.steps[:failed_index]
    ]
    marker = f"REPLAN_REQUEST: {agent_id}"
    return (
        "A step in your plan failed. Revise the REMAINING steps only "
        "(from the failed step onward), as a JSON list in the same format as before.\n"
        f"{marker}\n\n"
        f"Tools:\n{tool_lines}\n\n"
        f"Question: {question}\n"
        f"Completed steps: {json.dumps(completed)}\n"
        f"Failed step: {json.dumps({'tool': failed_step.tool, 'input': failed_step.tool_input})} "
        f"-> observation: {failed_step.observation}\n"
    )


def build_synthesis_prompt(question: str, plan: Plan, agent_id: str) -> str:
    observations = "\n".join(f"- {s.tool}[{s.tool_input}] -> {s.observation}" for s in plan.steps)
    marker = f"SYNTHESIZE: {agent_id}"
    return (
        "Using ONLY the observations below, answer the question in one sentence.\n"
        f"{marker}\n\n"
        f"Question: {question}\n\nObservations:\n{observations}"
    )


def execute_plan(client: LLMClient, tools: list[Tool], question: str, agent_id: str,
                  max_replans: int = 1) -> PlanResult:
    tools_by_name = {t.name: t for t in tools}
    plan = make_plan(client, tools, question, agent_id)
    replanned = False
    replans_left = max_replans
    i = 0
    while i < len(plan.steps):
        step = plan.steps[i]
        if step.tool not in tools_by_name:
            step.status = "failed"
            step.observation = f"ERROR: unknown tool '{step.tool}'"
        else:
            step.observation = tools_by_name[step.tool].run(step.tool_input)
            step.status = "failed" if step.observation.startswith(FAILURE_PREFIXES) else "done"
        if step.status == "failed" and replans_left > 0:
            raw = client.complete(build_replan_prompt(question, tools, plan, i, agent_id))
            revised = parse_plan(raw)
            plan.steps[i:] = revised.steps
            replanned = True
            replans_left -= 1
            continue  # re-attempt the (now revised) step at index i
        i += 1
    answer = None
    if all(s.status == "done" for s in plan.steps):
        answer = client.complete(build_synthesis_prompt(question, plan, agent_id))
    return PlanResult(answer=answer, plan=plan, replanned=replanned)

`lab_c_memory.py` (solution):

```python
"""Lab M05-C -- reference solution: session memory under a hard token
budget. Old turns are summarized, not silently dropped and not silently
kept forever -- both alternatives are named misconceptions in Lesson 3.
The current turn is never summarized away, even over budget: the agent
must always be able to see what was just said to it."""
from __future__ import annotations

from dataclasses import dataclass, field

from llm_client import LLMClient
from tokenizer import ApproxTokenCounter, TokenCounter


@dataclass
class Turn:
    role: str
    content: str


def build_summary_prompt(existing_summary: str, turn: Turn) -> str:
    marker = "SUMMARIZE_TURN"
    return (
        f"{marker}\nFold the new turn into the running summary. Keep every "
        "concrete fact (IDs, numbers, names) that a later turn might need; "
        "drop pleasantries and restated context.\n\n"
        f"Existing summary: {existing_summary or '(none yet)'}\n"
        f"New turn ({turn.role}): {turn.content}\n\n"
        "Return only the updated summary text, nothing else."
    )


@dataclass
class ConversationMemory:
    client: LLMClient
    budget_tokens: int
    counter: TokenCounter = field(default_factory=ApproxTokenCounter)
    turns: list[Turn] = field(default_factory=list)
    summary: str = ""

    def add_turn(self, role: str, content: str) -> None:
        self.turns.append(Turn(role, content))
        self._enforce_budget()

    def render(self) -> str:
        parts = []
        if self.summary:
            parts.append(f"[SUMMARY OF EARLIER TURNS]\n{self.summary}")
        parts.extend(f"{t.role}: {t.content}" for t in self.turns)
        return "\n".join(parts)

    def token_count(self) -> int:
        return self.counter.count(self.render())

    def _enforce_budget(self) -> None:
        while self.token_count() > self.budget_tokens and len(self.turns) > 1:
            oldest = self.turns.pop(0)
            self.summary = self.client.complete(build_summary_prompt(self.summary, oldest))
```

ApprovalFn = Callable[[str, str], bool]


def deny_all(tool_name: str, tool_input: str) -> bool:
    """The safe default: a consequential tool with no approval_fn wired
    in is denied, never silently allowed."""
    return False


def approve_first_then_deny(seen: set[tuple[str, str]] | None = None) -> ApprovalFn:
    """A scripted stand-in for a human reviewer who approves an action
    once and catches a literal repeat of it."""
    seen = seen if seen is not None else set()

    def fn(tool_name: str, tool_input: str) -> bool:
        key = (tool_name, tool_input)
        if key in seen:
            return False
        seen.add(key)
        return True

    return fn

    max_steps: int
    max_cost_usd: float
    cost_per_step_usd: float
    consequential_tools: set[str]
    approval_fn: ApprovalFn = deny_all
    steps_taken: int = 0
    cost_spent_usd: float = 0.0

        """Called once per loop iteration, BEFORE the model is asked
        for that step. Raise StepCeilingExceeded if steps_taken has
        already reached max_steps -- the call that would exceed it must
        never be attempted. Otherwise increment steps_taken and
        cost_spent_usd (by cost_per_step_usd), then raise
        CostCeilingExceeded if cost_spent_usd now exceeds
        max_cost_usd."""
        raise NotImplementedError

    def guard_tool(self, tool: Tool) -> Tool:
        """If tool.name is not in consequential_tools, return it
        unchanged. Otherwise return a new Tool whose run() calls
        self.approval_fn(tool.name, tool_input) first, records the
        result in self.approval_log, and either runs the real tool (if
        approved) or returns a "DENIED: ..." observation (never raises
        -- the loop must be able to see and reason about a denial)."""
        raise NotImplementedError

    governor.before_step() at the start of every iteration (before
    building the prompt) and pass every tool through
    governor.guard_tool() before the loop can use it."""

```python
"""Lab M05-D -- reference solution: bounded autonomy layered ON TOP of
the loop primitive (Lab A), not folded invisibly inside it. A Governor
enforces a hard step/cost ceiling (raises rather than degrades) and
wraps consequential tools behind a human-approval gate."""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Callable

from lab_a_agent_loop import AgentResult, Step, Tool, build_agent_prompt, parse_model_output
from llm_client import LLMClient


class StepCeilingExceeded(RuntimeError):
    pass


class CostCeilingExceeded(RuntimeError):
    pass


ApprovalFn = Callable[[str, str], bool]


def deny_all(tool_name: str, tool_input: str) -> bool:
    return False


def approve_first_then_deny(seen: set[tuple[str, str]] | None = None) -> ApprovalFn:
    seen = seen if seen is not None else set()

    def fn(tool_name: str, tool_input: str) -> bool:
        key = (tool_name, tool_input)
        if key in seen:
            return False
        seen.add(key)
        return True

    return fn


@dataclass
class Governor:
    max_steps: int
    max_cost_usd: float
    cost_per_step_usd: float
    consequential_tools: set[str]
    approval_fn: ApprovalFn = deny_all
    steps_taken: int = 0
    cost_spent_usd: float = 0.0
    approval_log: list[tuple[str, str, bool]] = field(default_factory=list)

    def before_step(self) -> None:
        if self.steps_taken >= self.max_steps:
            raise StepCeilingExceeded(
                f"step ceiling ({self.max_steps}) reached after {self.steps_taken} steps"
            )
        self.steps_taken += 1
        self.cost_spent_usd += self.cost_per_step_usd
        if self.cost_spent_usd > self.max_cost_usd:
            raise CostCeilingExceeded(
                f"cost ceiling (${self.max_cost_usd:.2f}) exceeded at "
                f"${self.cost_spent_usd:.2f} after {self.steps_taken} steps"
            )

    def guard_tool(self, tool: Tool) -> Tool:
        if tool.name not in self.consequential_tools:
            return tool

        def gated_run(tool_input: str) -> str:
            approved = self.approval_fn(tool.name, tool_input)
            self.approval_log.append((tool.name, tool_input, approved))
            if not approved:
                return (
                    f"DENIED: a human reviewer did not approve "
                    f"{tool.name}[{tool_input}]. Do not retry this action "
                    "without new information."
                )
            return tool.run(tool_input)

        return Tool(name=tool.name, description=tool.description, run=gated_run)


def run_agent_bounded(client: LLMClient, tools: list[Tool], question: str,
                       governor: Governor, agent_id: str = "agent") -> AgentResult:
    guarded_tools = [governor.guard_tool(t) for t in tools]
    tools_by_name = {t.name: t for t in guarded_tools}
    scratchpad = ""
    steps: list[Step] = []
    step_number = 0
    while True:
        step_number += 1
        governor.before_step()
        prompt = build_agent_prompt(question, guarded_tools, scratchpad, step_number, agent_id)
        raw = client.complete(prompt)
        parsed = parse_model_output(raw)
        if parsed.final_answer is not None:
            steps.append(Step(step_number, parsed.thought, None, None, None))
            return AgentResult(answer=parsed.final_answer, steps=steps, stopped_reason="final_answer")
        if parsed.action_name not in tools_by_name:
            observation = f"ERROR: unknown tool '{parsed.action_name}'."
        else:
            observation = tools_by_name[parsed.action_name].run(parsed.action_input)
        steps.append(Step(step_number, parsed.thought, parsed.action_name, parsed.action_input, observation))
        scratchpad += (
            f"Thought: {parsed.thought}\n"
            f"Action: {parsed.action_name}[{parsed.action_input}]\n"
            f"Observation: {observation}\n\n"
        )


def make_file_pto_tool() -> tuple[Tool, list[str]]:
    filed: list[str] = []

    def run(date_range: str) -> str:
        filed.append(date_range)
        return f"Request filed: {date_range}"

    tool = Tool(
        name="file_pto_request",
        description="File a PTO request for the given date range. CONSEQUENTIAL: creates a real request.",
        run=run,
    )
    return tool, filed

## Assessment — the bounded-autonomy audit clinic

Gaming-resistant by design, matching this course's reference standard exactly: the artifact that gets graded is the judgment trail — **predict, locate, fix, prove** — never the verdict alone, and never "it runs." A submission that patches the right thing by luck, with no prediction and no evidence, scores at or near zero.

**The clinic.** You are handed an unseen agent case in this module's own shape: a question, a tool set (with descriptions, at least one marked CONSEQUENTIAL), and a fully scripted, deterministic `FakeGenerationClient` transcript that **runs to completion without crashing** and produces a plausible-looking final answer. Exactly one governance defect is planted in the surrounding harness (never in the model's reasoning, which is always ordinary and well-intentioned) — one of: no step ceiling wired at all; a consequential tool with no `approval_fn` set (or one that approves everything); a plan executor with an unbounded replan (or none at all, so a bad step just gets skipped); or a memory budget so loose it never triggers, silently carrying an unbounded, ever-growing transcript. You are not told which. You must:

1. **Predict**, from the question, the tool descriptions, and the scripted transcript alone — before running anything — what you expect could go wrong given what's *missing* from the harness, and which of the four governance guarantees (step ceiling, cost ceiling, approval gate, bounded replan/memory budget) you predict is weakest or absent. State the specific evidence in the given materials that led you there.
2. **Locate**, by running the case in the sandbox (every consequential tool here is a fake, in-memory-only, exactly like `make_file_pto_tool`) and producing the concrete number that pinpoints the defect: a call count, an `approval_log`, a step count, a `token_count()` trajectory. "It looks unsafe" earns zero credit without a number attached.
3. **Fix**, using this module's own primitives — wire a `Governor`, add the tool to `consequential_tools`, lower a bound, cap a replan, tighten a memory budget — never a new, unrelated mechanism.
4. **Prove**, by re-running the identical scripted transcript through the fixed system and reporting the concrete before/after numbers (three duplicate calls become one; an unbounded transcript now folds at a stated token count) that demonstrate the fix, not merely that the program still runs.

### Rubric

| Criterion | Full credit | Partial credit | No credit |
|---|---|---|---|
| **Predict** | States, before running anything, a specific expected failure and which governance guarantee is weakest, tied to specific evidence in the tools/transcript given. | A prediction is made but is generic ("something might go wrong") or not tied to specific evidence from the case. | No prediction recorded before the Build/Locate step, or the prediction is written/edited after the answer is already known. |
| **Locate** | Runs the sandboxed case and reports the exact number(s) — call count, approval log, step count, or token trajectory — that pinpoint which governance layer is missing or misconfigured. | Runs the case and reports some evidence, but it's incomplete (e.g., a call count with no approval log when the defect is gate-related) or doesn't clearly isolate the defect from the other three guarantees. | Asserts the defect from the symptom alone ("the final answer looks fine so nothing's wrong" or "this seems unsafe") with no number produced by actually running the case. |
| **Fix** | Implements the correct governance control using this module's own `Governor`/`ConversationMemory`/`execute_plan` primitives, and the fix targets exactly the layer Locate's evidence implicated. | A real fix is implemented but targets the wrong layer, is broader than needed (e.g., denies every tool instead of gating the one that's consequential), or isn't built from this module's own primitives. | No fix, or a fix that only changes the model's prompt/wording rather than the governance layer — "ask it to be more careful" is not an engineering control and earns no credit here. |
| **Prove** | Re-runs the identical scripted transcript through the fixed system and reports concrete before/after numbers that demonstrate the specific defect is closed. | Re-runs the system and it "looks better," but the before/after comparison isn't reported as numbers, or a different scenario was substituted instead of the original transcript. | No re-run, or the claim "it's fixed" with no repeat of the original scripted case to demonstrate it. |

A submission that names the right defect by chance, fixes it by chance, and never runs the before/after comparison scores at or near zero on three of the four rows — matching the reference standard's own rule that the label alone is never the deliverable.

Specific to this module's subject — an agent that acts, and the chain of hands behind every action it takes.

- **Tier 1 — material ground.** An agent given a consequential tool and no approval gate will, under entirely ordinary, non-adversarial reasoning, take that action more than once if it has any reason for self-doubt. - **Tier 2 — what the field suppresses.** "Give the agent more autonomy" boosterism suppresses that autonomy was never a single dial turned up for more capability at no cost — it is a specific, per-tool, per-action decision about who is accountable if the model is wrong, and by default that decision is *made by omission*, by whoever didn't wire an `approval_fn`. Autonomy was never binary; it was always a specific, inspectable set of checkpoints someone did or didn't build, and "the agent decided to" is a sentence that erases every one of those choices.

- **Tier 3 — sit with this.** You will build an agent, someday, that is given a tool and no approval gate — because gating every tool felt like too much friction for something that "obviously" wouldn't need it. When that tool does something consequential and wrong, more than once, for reasons the model can articulate afterward that sound completely reasonable — trace the accountability chain out loud, every link: the model that made the call; the loop that let it retry; the tool's confirmation message that gave it no reason to believe it had already succeeded; the engineer who didn't wire a gate; the reviewer who approved the change that shipped without one; the person who typed the original request and never saw any of this happen.
