## Lessons

### Lesson 1 — What context actually is: the token sequence and the budget

Strip away every piece of vocabulary the field uses loosely — "memory," "knowledge," "the
conversation," "the system" — and what a model actually receives on every single call is one
thing: an ordered sequence of tokens, up to some maximum length, that someone's code built by
concatenating strings together. There is no side channel. If a fact, an instruction, a prior
message, or a tool's argument schema is not literally present as tokens in that sequence, the model
has no access to it on that call, full stop. "Context" is not a metaphor for the model's awareness
— it is the literal, countable, finite input, and everything downstream in this course (grounding,
tool use, multi-turn memory) is a story about what gets written into that sequence and what gets
left out.

**The running scenario for this module.** A support-desk assistant, Aria, answers refund-policy
questions for a SaaS company. Every call to the model needs four things concatenated into one
sequence: a **system prompt** (persona and ground rules), **tool schemas** (three JSON functions
Aria can call — `lookup_order_status`, `create_refund`, `escalate_to_human`), **retrieved
documentation chunks** (five policy passages, already ranked by relevance — exactly what an
AIE-110 `NSWIndex.search()` call returns), and **conversation history** (a ten-turn exchange with a
customer asking about two separate refunds). All four are real text, in `scenario.py`, used
unmodified by every lab in this module.

**Worked example — counting what "a paragraph" actually costs.** Here is the system prompt, in
full:

```
You are Aria, a support-desk assistant for a mid-size SaaS company. Answer only
from the retrieved documentation below; if the documentation does not cover the
question, say so plainly instead of guessing. Cite the source chunk id for every
factual claim. Keep answers under six sentences unless the user asks for more
detail. Never invent a policy, price, or deadline that is not present in the
retrieved text.
```

68 words. Counted with `ApproxTokenCounter` (a word/punctuation-boundary regex, `\w+|[^\w\s]`,
close in spirit to a real BPE tokenizer's granularity): **82 tokens** — about 1.2 tokens per word,
which is the ballpark a learner should expect for ordinary prose. Now the three tool schemas,
serialized as JSON, one per line:

```json
{"name": "lookup_order_status", "description": "Look up the current status of a customer order by order id.", "parameters": {"type": "object", "properties": {"order_id": {"type": "string", "description": "The order id, e.g. ORD-10293."}}, "required": ["order_id"]}}
{"name": "create_refund", "description": "Create a refund for a given order id and amount in cents, requires a reason string.", "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}, "amount_cents": {"type": "integer", "description": "Refund amount in cents, must be positive."}, "reason": {"type": "string"}}, "required": ["order_id", "amount_cents", "reason"]}}
{"name": "escalate_to_human", "description": "Escalate the current conversation to a human support agent with a summary.", "parameters": {"type": "object", "properties": {"summary": {"type": "string", "description": "One paragraph summary of the issue so far."}}, "required": ["summary"]}}
```

107 words — fewer words than the system prompt's 68? No: more words, but look at the token count:
**311 tokens**, a ratio of **2.9 tokens per word**. Every `{`, `}`, `"`, `:`, and `,` is its own
token; a structured, punctuation-dense format costs roughly two and a half times more per word than
plain prose says it should. A learner who estimates token budgets by eyeballing word count will
under-budget every JSON-shaped section in their context by the same multiple, every time — tool
schemas, function-call arguments, retrieved data that's itself structured (tables, code, JSON
documents) all pay this same tax, and it's invisible until you actually count.

Add the five retrieved chunks (302 tokens) and the ten-turn conversation history (290 tokens), and
the four sections the assembler must fit into one sequence total **985 tokens**. If the model's
context window is a deliberately small **1,024 tokens** and **200 tokens are reserved for the
model's own output** (it has to generate an answer inside the same budget), the input has **824
tokens** of room — and 985 does not fit in 824. Before a single line of assembly code runs, this
context is **161 tokens overstuffed**, and *something* is going to give.

**Misconception 1 — "The model manages its context window; if something doesn't fit, the model
handles it gracefully."** The model receives whatever token sequence your code hands it and
generates a continuation of exactly that sequence — it has no visibility into what your assembly
code decided to leave out, no way to ask for more room, and no mechanism to flag that anything was
cut. Any "graceful" behavior around an overstuffed context is something *your code* has to
implement; absent that, the failure is a silent, un-signaled truncation performed by whichever
string-concatenation-and-slice logic happens to run, and Lesson 3 is what that silence looks like
in practice.

**Misconception 2 — "A model with a huge context window (100K+ tokens) makes this problem
irrelevant."** A larger window raises the threshold at which overflow happens; it does not remove
the need for a budget, because real systems keep growing the things that compete for it —
longer conversations, more retrieved chunks, more tools — until they hit whatever ceiling exists.
It also does not fix the failure mode Lesson 3 names **lost-in-the-middle**: even well within a
huge window, models attend unevenly across a long context, and stuffing more into an enormous
window does not distribute attention evenly across it. A bigger window changes the constant; it
does not change the discipline this module teaches.

### Lesson 2 — Assembling context by hand: one budget per section, not one global budget

The obvious first implementation of a context assembler is: concatenate every section into one
string, in some order, then if the whole thing is too long, truncate the string down to the
window. This lesson exists to show precisely why that is wrong, and what a correct assembler does
instead — **give every section its own reserved budget, decided by an explicit priority, before
any text is cut.**

**Two kinds of sections.** Some content is **all-or-nothing**: a system prompt with half its rules
missing is not a shorter system prompt, it is a *different, unreviewed* system prompt; a tool's
JSON schema with its closing braces cut off is not a smaller schema, it is invalid JSON that will
make the tool-calling API reject the call outright. These sections need a **hard minimum** — either
they fit in full, or the assembler must fail loudly (`BudgetExceededError`), never silently emit a
corrupted version. Other content is **legitimately truncatable in whole units**: a list of five
retrieved chunks can correctly become a list of three chunks (each one still whole, still valid,
still a complete claim with its citation id attached), and ten conversation turns can correctly
become the four most recent turns (each one still a complete, uncut message). What must never
happen to *either* kind of section is truncation **inside** a unit — inside a JSON object, inside a
single chunk, inside a single turn — because that produces output that looks like data but silently
isn't.

**Worked example — the budget accountant.** `allocate_budget()` takes an ordered list of sections
(each with a token cost and a `hard_min` flag) and the total tokens available for input, and
returns exactly how many tokens each section gets — before anyone decides *how* to cut anything
down to that number:

```
section       requested   allocated   deficit
system              82          82        0      (hard_min — gets it all, always)
tools               311         311        0      (hard_min — gets it all, always)
retrieved           302         302        0      (fits in what's left over)
history             290         129      161      (truncatable — absorbs the deficit)
```

`system` and `tools` are marked `hard_min = True`: 82 + 311 = 393 tokens are reserved for them
unconditionally, before anything else is considered — this is the mechanism that makes "the tool
schema gets corrupted" structurally impossible rather than merely unlikely. Of the remaining
824 − 393 = 431 tokens, `retrieved` (302 tokens, requested in priority order first) fits entirely;
the 431 − 302 = 129 tokens left over go to `history`, which requested 290 and gets 129 — a **161
token deficit**, which is exactly the shortfall Lesson 1 predicted for the whole context. The
accountant's job stops here: it has decided *how much room* `history` gets. Lesson 3's assembler is
what decides *which 129 tokens' worth of history* survives, and that decision — whole units,
oldest-dropped-first, never mid-turn — is the difference between a controlled trim and silent
corruption.

**Priority order is not decorative — it determines who absorbs the deficit.** Swap `history` and
`retrieved`'s priority (assemble history before retrieved) and nothing about the *total* deficit
changes — it is still 161 tokens — but *which section pays it* flips entirely: `history` now fits
in full (290 ≤ 431) and `retrieved` absorbs the whole 161-token deficit instead, losing whole
chunks it would otherwise have kept. The number "161" is a fact about the four texts and the
window; *which section loses those tokens* is a design decision, made by whoever wrote the priority
list, and it is invisible in the code unless you go looking for the line that sets it.

**Misconception 1 — "Truncating the final string is the same as truncating the content."** Cutting
a concatenated string at a token boundary has no idea it just severed a JSON object's closing
brace, or landed mid-word inside a customer's sentence. The *string* got shorter correctly; the
*content* it represents is now broken in a way nothing downstream can detect from the string alone
— a parser either crashes (best case) or, worse, "succeeds" on a truncated JSON fragment that
happens to still be syntactically closeable. Section-aware, unit-aware truncation is not a
refinement of string truncation; it is a different operation that string truncation cannot be
patched into performing.

**Misconception 2 — "Assembling sections in priority order is the same as budgeting them in
priority order."** The order sections are *concatenated* in (which one's text appears first in the
final string) and the order they're *allocated budget* in are two separate decisions that happen to
share a "priority" word but do different jobs — the first affects nothing about correctness; the
second, as the swap above shows, determines who silently loses content. A learner who sets one and
assumes it covers the other has fixed half the problem and doesn't yet know it.

### Lesson 3 — Failure modes, named after being observed: silent drops, mid-unit corruption, and the recency trap

Lessons 1-2 built the vocabulary; this lesson names the failure modes properly, but only after
Lab M01-B makes the learner watch each one happen on the exact scenario from Lesson 1. Naming a
failure abstractly before seeing it is exactly the ordering this course refuses.

**Failure 1 — silent truncation.** The naive assembler (`assemble_naive`: concatenate everything,
call `truncate()` once on the whole string) returns 824 tokens, well-formed as a string, and the
API call it feeds into returns `200 OK` with a fluent answer. Nothing anywhere signals that 161
tokens of real content never made it into the request. This is the single most dangerous property
of context overflow: **a truncated context and a correctly-assembled context are indistinguishable
from the outside** unless the assembly code itself reports what it cut.

**Failure 2 — mid-unit corruption.** On this module's scenario, naive truncation cuts inside
conversation turn 5 (the customer's message about a second, enterprise-plan order), stopping
mid-sentence at *"...it also arrived damaged --"* and silently discarding *"is that one still
eligible?"* along with every turn that follows. Ask what "every turn that follows" contains here,
specifically: turn 10, the customer's actual final message — *"can you confirm the refund for
ORD-88213 will go back to the same card, not store credit? That's actually the most important part
for me right now"* — is gone. The model answering this request has no way to know that question was
ever asked. It will generate a plausible, confident, entirely unaware response to a conversation
that, from its side, ended four exchanges earlier than it actually did.

**Failure 3 — the recency trap.** This is why Failure 2 lands where it does, and it generalizes:
concatenation order and truncation order are the same operation in a naive assembler, and
whichever section is placed **last** in the concatenated string is the one that loses its **most
recent** content when the tail gets cut off. Placing conversation history last (a completely
ordinary, "obvious" choice — it reads naturally as "here's everything, then the current turn") is
precisely what makes the *current turn* the first thing to go when the budget is exceeded. The
failure is not that history is long; it's that *whatever is assembled last pays with its own
ending*, regardless of whether that ending happens to be the single most important sentence in the
whole request.

**Failure 4 — lost-in-the-middle (named, not built by hand here).** Even a context that fits the
window without any truncation at all is not attended to uniformly by the model: content placed
near the start or end of a long context is measurably better-used by the model than content buried
in the middle, a well-documented empirical property of long-context generation, independent of
whether anything was cut. This module does not build a lab to demonstrate it (that requires a real
model and a longer context than this module's toy scenario), but it is named here deliberately,
because a learner who has just fixed Failures 1-3 is at exactly the point of concluding "assembly
is solved" — and lost-in-the-middle is the reminder that a context which fits and isn't corrupted
can *still* be poorly used by the model that reads it. Fitting the budget is necessary; it is not
sufficient.

**The fix, built in Lab M01-B.** `assemble_budgeted()` uses Lesson 2's per-section budgets and two
unit-aware truncation functions: `truncate_chunks_keep_whole` (walks the *already-relevance-ranked*
retrieved chunks from most to least relevant, keeping whole chunks until the next one wouldn't fit,
dropping the rest whole — never cutting inside a chunk) and `truncate_turns_keep_recent` (walks
conversation turns from **newest to oldest**, keeping a contiguous run of whole recent turns until
the next-older one wouldn't fit — deliberately inverting the naive assembler's direction, because
recency is a design decision, not an accident of concatenation order). On this exact scenario, the
budgeted assembler keeps all 5 retrieved chunks whole (they fit in the allocated 302 tokens exactly)
and keeps the 3 most recent conversation turns whole — including the crucial final "same card, not
store credit" question the naive assembler lost — while every tool schema stays intact because
`tools` is `hard_min`. The total, 807 tokens, is comfortably inside the 824-token budget. Nothing
was cut mid-unit. What *was* dropped (the seven oldest turns) was dropped as a stated, inspectable
design decision — recency over completeness — not as an accident of string order.

**Misconception 1 — "If the API call succeeds and returns a coherent-sounding answer, the context
was assembled correctly."** A coherent answer to a truncated context is, if anything, more
dangerous than an error: an error gets investigated, a confident wrong answer ships. Coherence is a
property of the model's generation, not evidence about what the model was given to generate from.

**Misconception 2 — "Lost-in-the-middle means retrieved chunks should never be placed in the
middle of the context."** The lesson from Failure 4 is narrower and easier to misapply: it is
evidence to *weigh* when choosing assembly order for a specific model and task (worth testing:
does moving high-value content toward the edges measurably help your eval scores?), not a universal
rule to apply blind. Treating it as an absolute risks over-engineering assembly order around a
documented tendency instead of measuring whether it matters for the system actually being built —
exactly the eval discipline AIE-204 exists to enforce.

### Lesson 4 — Prompts as versioned specs: tested and diffed, not tuned by vibes

A system prompt is code. It has a specific, testable effect on behavior; editing it without a
version number, a changelog entry, and a suite of cases that must keep passing is functionally
identical to hand-editing a production function with no source control and no tests — the fact
that the "function" is written in English instead of Python does not make it exempt from the
discipline. **Vibes-tuning** is the alternative this lesson names explicitly: edit the prompt, run
one example, see that it looks better, ship it. It fails for the same reason an untested code
change fails — it only checks the one case the editor happened to look at.

**Worked example — a one-line-sounding edit that regresses a case nobody re-checked.** Version
1.0.0 of Aria's system prompt (Lesson 1's text) instructs: *"Cite the source chunk id for every
factual claim... if the documentation does not cover the question, say so plainly instead of
guessing."* A support lead files a complaint: an answer shipped without a citation. The natural fix
— tighten the citation instruction — produces version 1.1.0:

```diff
--- support-desk-system-prompt@1.0.0
+++ support-desk-system-prompt@1.1.0
- ...Answer only from the retrieved documentation below; if the documentation does
- not cover the question, say so plainly instead of guessing. Cite the source
- chunk id for every factual claim. Keep answers...
+ ...Answer only from the retrieved documentation below. Cite the source chunk id
+ in square brackets immediately after every factual claim, and output nothing
+ else beyond the answer and its citations. Keep answers...
```

Run against the case that motivated the edit (*"How long is the refund window for an enterprise
customer?"*), v1.1.0 works exactly as intended: `120-day refund window for enterprise customers
[doc-019#2].` A vibes-tuner stops here — the motivating case passes, ship it. A **regression suite**
of four representative cases — citation on a covered question, citation on a different covered
question, an *uncovered* question, and a duplicate-refund edge case — run against both versions
tells a different story:

| Case | v1.0.0 | v1.1.0 | |
|---|---|---|---|
| Enterprise refund window (covered) | pass | pass | unchanged |
| Shipped-order refund (covered) | pass | pass | unchanged |
| **Crypto refunds (uncovered)** | **pass** | **fail** | **regression** |
| Duplicate refund (edge case) | pass | pass | unchanged |

The new wording — *"output nothing else beyond the answer and its citations"* — was written to
suppress padding, and it does. It also suppresses the one sentence 1.0.0 relied on for the uncovered
case: the plain admission that the documentation doesn't cover cryptocurrency refunds. Under
1.1.0, that admission reads as exactly the kind of "extra" text the new instruction was written to
cut, so the model drops it and answers from an irrelevant chunk instead — a hallucination the
original prompt was specifically written to prevent, reintroduced by an edit aimed at fixing a
*different* problem. Nobody who only reran the motivating case would ever see this. The regression
only exists to be seen because the suite has a case for it.

**Misconception 1 — "A diff that reads as an improvement to a human is an improvement."** A diff
reading better is a hypothesis about behavior, stated in English, about a system that does not
execute English the way a human reading the diff does. It becomes evidence only after the full
suite is re-run — exactly Lesson 4's parallel to AIE-204-M04's "the judge's fluent reasoning is not
evidence it reasoned correctly": fluency (of a diff, of a judge, of a model's output) is never a
substitute for a measured check.

**Misconception 2 — "Spot-checking the case that motivated the edit is basically a regression
test."** It only tells you the edit did what you wanted on the one case you already knew about. A
regression suite's entire value is in the cases the editor had no reason to suspect would be
affected — here, an uncovered-question case that has nothing to do with citations on its face, and
everything to do with them once "output nothing else" enters the prompt.

`tokenizer.py` (provided; shared by every lab):

```python
"""
tokenizer.py -- the thin interface every section budget in this module is
measured against.

Durability discipline: every lesson and lab imports TokenCounter (and, for
tests, ApproxTokenCounter) from this file -- never a vendor tokenizer
directly. When the target model's tokenizer changes, only TiktokenCounter
below needs to change; nothing about allocation or assembly logic knows or
cares which counter answered count().
"""
from __future__ import annotations

import re
from typing import Protocol

_TOKEN_PATTERN = re.compile(r"\w+|[^\w\s]")


class TokenCounter(Protocol):
    """Anything with these two methods can serve as a budget's ruler."""

    def count(self, text: str) -> int: ...
    def truncate(self, text: str, max_tokens: int) -> str: ...


class ApproxTokenCounter:
    """Deterministic, dependency-free counter used by every test in this
    module and by the labs when run offline. Splits on the same
    word/punctuation boundary a real BPE tokenizer roughly follows, at one
    token per match. Not a production token count -- see TiktokenCounter --
    but stable across machines and needs no network call or model download,
    so every prediction in this module is gradable without hitting an API."""

    def encode(self, text: str) -> list[str]:
        return _TOKEN_PATTERN.findall(text)

    def count(self, text: str) -> int:
        return len(self.encode(text))

    def truncate(self, text: str, max_tokens: int) -> str:
        if max_tokens < 0:
            raise ValueError("max_tokens must be >= 0")
        toks = self.encode(text)
        if len(toks) <= max_tokens:
            return text
        return " ".join(toks[:max_tokens])


class TiktokenCounter:
    """The production counter. The ONLY class in this module allowed to
    import tiktoken or name a specific encoding -- that is the point of the
    thin interface above. Swap the encoding here when the target model
    changes and nothing in budget.py or assembler.py changes.

    Requires `pip install tiktoken`, and its first call for a given
    encoding downloads that encoding's BPE ranks over the network unless
    already cached -- this is exactly why every lab and every test in this
    module runs against ApproxTokenCounter instead: predictions and CI
    stay reproducible without a network dependency."""

    def __init__(self, encoding_name: str = "cl100k_base"):
        import tiktoken  # imported here, not at module scope, so labs that
        # never instantiate TiktokenCounter don't require the package installed
        self._enc = tiktoken.get_encoding(encoding_name)

    def count(self, text: str) -> int:
        return len(self._enc.encode(text))

    def truncate(self, text: str, max_tokens: int) -> str:
        if max_tokens < 0:
            raise ValueError("max_tokens must be >= 0")
        ids = self._enc.encode(text)
        if len(ids) <= max_tokens:
            return text
        return self._enc.decode(ids[:max_tokens])
```

"""Lab M01-A -- reference solution."""
from __future__ import annotations

from dataclasses import dataclass

from tokenizer import TokenCounter


class BudgetExceededError(Exception):
    pass


@dataclass
class Section:
    name: str
    text: str
    priority: int
    hard_min: bool = False


@dataclass
class BudgetRow:
    name: str
    requested: int
    allocated: int

    @property
    def deficit(self) -> int:
        return self.requested - self.allocated


# A genuine estimate recorded before any code ran, using "~1.2 tokens/word
# for prose, ~2.5-3x for JSON" from Lesson 1. The true values (82, 311,
# 302, 290) confirm the heuristic without matching it exactly -- exactly
# what an estimate should do.
PREDICTED_TOKENS = {"system": 85, "tools": 260, "retrieved": 290, "history": 270}
PREDICTED_DEFICIT_SECTION = "history"
PREDICTED_DEFICIT_TOKENS = 150


def allocate_budget(sections: list[Section], available: int, counter: TokenCounter) -> dict[str, BudgetRow]:
    ordered = sorted(sections, key=lambda s: s.priority)
    requested = {s.name: counter.count(s.text) for s in ordered}

    hard_total = sum(requested[s.name] for s in ordered if s.hard_min)
    if hard_total > available:
        raise BudgetExceededError(
            f"hard-minimum sections require {hard_total} tokens but only "
            f"{available} are available -- {hard_total - available} tokens "
            "short before a single truncatable section is considered"
        )

    rows: dict[str, BudgetRow] = {}
    remaining = available
    for s in ordered:
        if s.hard_min:
            rows[s.name] = BudgetRow(s.name, requested[s.name], requested[s.name])
            remaining -= requested[s.name]

    for s in ordered:
        if s.hard_min:
            continue
        allocated = max(0, min(requested[s.name], remaining))
        rows[s.name] = BudgetRow(s.name, requested[s.name], allocated)
        remaining -= allocated

    return rows


def budget_report(rows: dict[str, BudgetRow]) -> str:
    lines = [f"{'section':<12}{'requested':>10}{'allocated':>11}{'deficit':>9}"]
    for row in rows.values():
        lines.append(f"{row.name:<12}{row.requested:>10}{row.allocated:>11}{row.deficit:>9}")
    return "\n".join(lines)

"""Lab M01-B -- reference solution."""
from __future__ import annotations

from budget import Section, allocate_budget
from tokenizer import TokenCounter

# Recorded before running assemble_naive: turn index 4 is the fifth
# message ("Full refund please... is that one still eligible?"), reasoned
# from Lab M01-A's 129-token history allocation and the cumulative token
# counts of turns 0-4 (23+24+11+32+45=135 > 129, so the cut lands inside
# turn 4). The final turn (index 9) does not survive.
PREDICTED_CUT_TURN_INDEX = 4
PREDICTED_FINAL_TURN_SURVIVES_NAIVE = False


def assemble_naive(sections: list[Section], available: int, counter: TokenCounter) -> str:
    ordered = sorted(sections, key=lambda s: s.priority)
    full_text = "\n\n".join(s.text for s in ordered)
    return counter.truncate(full_text, available)


def truncate_chunks_keep_whole(chunks, budget, counter):
    kept: list[tuple[str, str]] = []
    used = 0
    for cid, text in chunks:
        unit = f"[{cid}] {text}"
        cost = counter.count(unit)
        if used + cost > budget:
            break
        kept.append((cid, text))
        used += cost
    return kept


def truncate_turns_keep_recent(turns, budget, counter):
    kept: list[tuple[str, str]] = []
    used = 0
    for role, text in reversed(turns):
        unit = f"{role}: {text}"
        cost = counter.count(unit)
        if used + cost > budget:
            if not kept:
                clipped = counter.truncate(unit, budget)
                return [(role, clipped)]
            break
        kept.append((role, text))
        used += cost
    kept.reverse()
    return kept


def assemble_budgeted(sections, available, counter, retrieved_chunks, history_turns):
    section_list = list(sections.values())
    rows = allocate_budget(section_list, available, counter)

    kept_chunks = truncate_chunks_keep_whole(retrieved_chunks, rows["retrieved"].allocated, counter)
    kept_turns = truncate_turns_keep_recent(history_turns, rows["history"].allocated, counter)

    retrieved_text = "\n\n".join(f"[{cid}] {text}" for cid, text in kept_chunks)
    history_text = "\n".join(f"{role}: {text}" for role, text in kept_turns)

    parts = []
    for s in sorted(section_list, key=lambda s: s.priority):
        if s.name == "retrieved":
            parts.append(retrieved_text)
        elif s.name == "history":
            parts.append(history_text)
        else:
            parts.append(s.text)
    return "\n\n".join(parts)

from dataclasses import dataclass, field
from typing import Protocol


class LLMClient(Protocol):
    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str: ...


@dataclass
class FakeClient:
    """Deterministic stand-in used by every test. Maps an exact substring
    of the prompt to a canned response; when more than one key matches,
    the LONGEST (most specific) one wins -- the same rule AIE-204-M04's
    FakeJudgeClient uses, for the same reason."""

    def complete(self, prompt: str, *, temperature: float = 0.0, max_tokens: int = 512) -> str:
        matches = [(key, response) for key, response in self.canned.items() if key in prompt]

                "that render() embeds the exact CASE_ID/PROMPT_VERSION "
                "markers the test data expects."
            )
        _, response = max(matches, key=lambda pair: len(pair[0]))
        return response

from __future__ import annotations

import difflib
from dataclasses import dataclass, field


@dataclass
class PromptSpec:
    name: str
    version: str
    template: str
    changelog: list[str] = field(default_factory=list)


def render(spec: PromptSpec, *, case_id: str, query: str) -> str:
    return (
        f"CASE_ID: {case_id}\n"
        f"PROMPT_VERSION: {spec.version}\n"
        f"{spec.template}\n\n"
        f"USER QUESTION: {query}\n"
        "Answer now."
    )


def diff_specs(a: PromptSpec, b: PromptSpec) -> str:
    a_lines = a.template.splitlines(keepends=True)
    b_lines = b.template.splitlines(keepends=True)
    diff = difflib.unified_diff(
        a_lines, b_lines,
        fromfile=f"{a.name}@{a.version}",
        tofile=f"{b.name}@{b.version}",
    )
    return "".join(diff)

```python
"""Lab M01-C -- reference solution (regression.py)."""
from __future__ import annotations

from dataclasses import dataclass
from typing import Callable

from llm_client import LLMClient
from promptspec import PromptSpec, render


@dataclass
class EvalCase:
    case_id: str
    query: str
    check: Callable[[str], bool]
    check_description: str


@dataclass
class CaseResult:
    case_id: str
    passed: bool
    response: str


@dataclass
class RegressionReport:
    regressions: list[str]
    fixes: list[str]
    unchanged_pass: list[str]
    unchanged_fail: list[str]


def run_case(spec, client, case):
    prompt = render(spec, case_id=case.case_id, query=case.query)
    response = client.complete(prompt)
    return CaseResult(case.case_id, case.check(response), response)


def run_suite(spec, client, cases):
    return {c.case_id: run_case(spec, client, c) for c in cases}


def compare_versions(spec_a, spec_b, client, cases):
    results_a = run_suite(spec_a, client, cases)
    results_b = run_suite(spec_b, client, cases)

    regressions, fixes, unchanged_pass, unchanged_fail = [], [], [], []
    for case in cases:
        a_ok = results_a[case.case_id].passed
        b_ok = results_b[case.case_id].passed
        if a_ok and not b_ok:
            regressions.append(case.case_id)
        elif not a_ok and b_ok:
            fixes.append(case.case_id)
        elif a_ok and b_ok:
            unchanged_pass.append(case.case_id)
        else:
            unchanged_fail.append(case.case_id)
    return RegressionReport(regressions, fixes, unchanged_pass, unchanged_fail)
```

## Assessment

**Component:** build labs (primary weight for this module) and diagnosis clinics.
Gaming-resistance is the design constraint: a learner cannot pass by shipping code that merely
runs.

### Module task — the unseen overstuffed context

Handed to the learner, unseen: a **different** assembly scenario — an internal engineering-wiki
assistant with a longer system prompt, five tool schemas instead of three, eight retrieved runbook
excerpts, and a fourteen-turn incident-response conversation — packaged with a naive
`assemble_naive`-style assembler already wired up and passing its (weak) existing tests. The
learner must, in order:

1. **Predict**, on paper, before writing or running any code: given the stated window and reserved
   output, which single section will end up assembled last in the fixed concatenation order, and
   therefore which section's *tail* will silently absorb the overflow — name the exact turn or
   chunk you expect to be cut or dropped, and state your reasoning from the token arithmetic, not a
   guess.
2. **Locate** the corruption by actually running the provided naive assembler and finding the exact
   byte-or-token-precise point where content breaks — a cut JSON schema, a truncated runbook
   excerpt, or a dropped incident-response turn — and quote it.
3. **Fix** it: implement a per-section budget allocation (Lab M01-A's pattern) and unit-aware
   truncation (Lab M01-B's pattern) so nothing is ever cut mid-unit and hard-minimum sections
   (system prompt, tool schemas) are structurally protected. "Fix" that merely enlarges the context
   window without adding per-section budgeting does not satisfy this row — the point is the
   assembly discipline, not the numerology of a bigger number.
4. **Prove** it: write a regression test that fails (red) against the original naive assembler and
   passes (green) against the fix — the same test must demonstrate the *original* bug, not just
   confirm the fix looks reasonable in isolation.

### Rubric

| Dimension | Full marks require | Why it resists gaming | Points |
|---|---|---|---|
| Predict artifact | The exact section/turn/chunk expected to break, and the token-arithmetic reasoning, written and dated *before* any code runs | A correct fix with no prior prediction scores zero here — grading the forecast, not just the working code, is AI-PRIMM applied to context assembly | 20 |
| Corruption located precisely | The exact cut point identified and quoted from the *provided* naive assembler's real output, not a general description of "truncation happens somewhere" | A vague answer ("something in the middle gets cut") cannot satisfy a rubric that requires the literal quoted fragment — it forces the learner to have actually run and read the broken output | 15 |
| Fix: per-section budgets, unit-aware truncation | Hard-min sections (system, tools) provably always intact; retrieved/history truncation never splits a unit; behavior is deterministic and traceable to an explicit priority | A fix that "seems to work" on the one scenario given but doesn't generalize (e.g., hardcodes which turn to keep instead of computing budgets) fails an unseen second scenario used to re-check this row | 30 |
| Regression test proves the original bug | A test that is RED against the unmodified naive assembler and GREEN against the fix, submitted alongside both | A test that only checks the fix in isolation, without ever having been run red first, cannot demonstrate it actually would have caught the original corruption — this is the same discipline Lesson 4 requires of a prompt regression suite, applied to code | 20 |
| Prompt-spec discipline on any touched template | Any system-prompt or tool-description text touched during the fix carries a version bump and a changelog entry, and the module's own 4-case regression suite (or an equivalent the learner writes) is re-run and shows no case flipped from pass to fail | An edit shipped with no version bump and no re-run suite is exactly the vibes-tuning Lesson 4 names — this row exists so the fix itself cannot introduce the failure mode two lessons earlier described | 15 |

## Three-tier reading

Specific to this module's subject — what gets silently decided when a context is assembled — not
boilerplate.

- **Tier 1 — material ground.** A context window is a hard token budget, and when an assembled
  context exceeds it, *something* is cut with no exception raised and no field in the API response
  that says so — the call still returns `200 OK`. This is a mechanical fact, demonstrated directly
  in Lab M01-B: the naive assembler's output is syntactically fine, token-budget-compliant, and
  missing the customer's actual question, and nothing about the response signals which of those
  three is true.
- **Tier 2 — what the field suppresses.** "Grounded in your data" is marketed as though a RAG
  system faithfully surfaces whatever the corpus says. What that phrase omits is that the assembler
  sitting between "the corpus" and "the model" is making continuous, silent editorial decisions —
  which retrieved chunk survives a budget cut, which historical turn survives, in what priority
  order — and those decisions are ordinary application code, usually written once, by one engineer,
  under no particular scrutiny, and then never revisited as the system's usage patterns change. No
  vendor's marketing page for a "grounded" system discloses its truncation policy, and most teams
  running one could not state their own policy out loud without opening the source.
- **Tier 3 — sit with this.** The fix this module builds works by an explicit priority order: system
  and tools always survive whole; recent conversation outranks old conversation; the top-ranked
  retrieved chunk outranks the fifth-ranked one. That ordering is a value judgment, encoded once, in
  code, applied identically to every customer who ever talks to the system — the customer who
  writes a long, meandering message is not silently favored or penalized on account of length by
  this design, but a different, equally reasonable-sounding priority order could easily have chosen
  otherwise, and would have looked just as correct passing the same tests. You will write a
  priority order like this one for a real system. When two things a real user needed both couldn't
  fit and your code chose which one to drop — silently, the way this module's naive assembler did,
  or openly, the way its fix does — what do you say to the person whose need lost that fight, when
  they ask why the system never mentioned it was even happening?
