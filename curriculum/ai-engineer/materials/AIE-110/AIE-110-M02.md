# AIE-110-M02 — Arrays, hashing, and the structures under NumPy and dicts

**Foundation tier · 14 learner-hours · Prereq: AIE-101 (Python + pytest fluent) · Co-req: AIE-102 (the memory hierarchy — why cache-friendly layout matters) · Builds on: AIE-110-M01 (Big-O, and the provided benchmarking harness)**

> **The descent, stated plainly.** You already use two data structures constantly and neither one is what you think it is. A Python `list` is not "an array of numbers" — it is a contiguous array of *pointers* to boxed integer objects scattered across the heap, which is exactly why `sum(list)` is slow and `np.sum(array)` is not. A Python `dict` is not "a magic key→value thing" — it is an **open-addressed hash table**: a flat array of slots, an index computed by `hash(key) & mask`, and a probing rule for when two keys want the same slot. This module goes *below* both. You will build a hash table from scratch — the real structure, open addressing with linear probing and resize-on-load-factor — test it against `dict` until they are indistinguishable, and then break it on purpose so you can watch the advertised O(1) lookup decay to O(n) in front of you. The wall of this module is not syntax; it is a *belief*: that "hashing is O(1)" is a fact about the structure. It is not. It is a fact about the **hash function spreading the keys**, and it is exactly as true as that assumption holds — no more.

> **The loop under every lab is AI-PRIMM.** Predict (on paper, before code) → Prompt → Read → Verify → Integrate. Here, prediction is not flavor: the whole point of the module is that a hash table that *passes every small test* can still be quadratic on adversarial input, and a benchmark that "looks fast" at N=1000 tells you nothing about N=10⁷. "It ran and the test was green" is never evidence of the *cost*. The artifact you are graded on is your **judgment trail**: what asymptotic curve you predicted, what exponent you measured, and — when they disagreed — the written reconciliation that fixed your model of the machine.

### Harness contract (provided, same across AIE-110)

Every lab ships as a directory with a `bench.py` harness and a `pytest` suite. The toolchain is **Python 3.12+ and NumPy ≥ 2.0**; answer keys are pinned to **CPython 3.12** because two claims in this module (integer `hash(n) == n`, and dict resize at 2/3 load) are CPython implementation details, not language guarantees — where that matters, the text says so.

Commands you will use:

- `pytest` — run the correctness suite. **Green is necessary, never sufficient.** Every lab has a planted failure mode that is *correct on small input and wrong on cost*; the tests certify behavior, the benchmark certifies cost, and only the two together are evidence.
- `python bench.py` — run the growing-N benchmark and print a table of `(N, seconds, ns/element or ns/op)` plus a **measured log–log slope `p`**. For total time `T(N) ≈ c·Nᵖ`: `p ≈ 0` is O(1) per call, `p ≈ 1` is O(N), `p ≈ 2` is O(N²). This is the whole toolchain philosophy in one number — **you predict `p` on paper, the harness measures it, and a Big-O claim with no measured curve behind it does not count.**

The provided `bench.py` (you import from it; you do not rewrite it):

```python
# bench.py — provided harness. Do not modify.
import math
import time
import tracemalloc


def best_time(fn, *args, repeats=5, **kwargs):
    """Minimum wall-clock seconds over `repeats` runs (min rejects noise better than mean)."""
    best = float("inf")
    for _ in range(repeats):
        t0 = time.perf_counter()
        fn(*args, **kwargs)
        best = min(best, time.perf_counter() - t0)
    return best


def peak_bytes(fn, *args, **kwargs):
    """Peak Python-heap bytes allocated while `fn` runs, via tracemalloc."""
    tracemalloc.start()
    try:
        fn(*args, **kwargs)
        _, peak = tracemalloc.get_traced_memory()
    finally:
        tracemalloc.stop()
    return peak


def loglog_slope(ns, times):
    """Least-squares slope p of log(time) vs log(N): the measured Big-O exponent."""
    xs = [math.log(n) for n in ns]
    ys = [math.log(t) for t in times]
    k = len(xs)
    mx, my = sum(xs) / k, sum(ys) / k
    num = sum((x - mx) * (y - my) for x, y in zip(xs, ys))
    den = sum((x - mx) ** 2 for x in xs)
    return num / den


def curve(fn, sizes, make_input):
    """Time fn over a list of N; return (sizes, times, measured slope p)."""
    times = [best_time(fn, make_input(n)) for n in sizes]
    return sizes, times, loglog_slope(sizes, times)
```

> **The evidence standard for this module.** *Your predicted asymptotic exponent matches the harness's measured slope `p`, and where it did not, your written revision explains why.* A passing `pytest` run with no benchmark, or a benchmark at a single N, is explicitly insufficient — the module is built so that both of those pass for code that is secretly quadratic.

## Lessons

### Lesson 1 — The array under the array: why `list` is slow and NumPy is not (callback to AIE-102)

**The teaching.** In AIE-102 you learned the memory hierarchy: a load from L1 cache costs ~1 ns, from main memory ~100 ns, and the hardware bets on **spatial locality** — it fetches a whole 64-byte cache line at once, so if your next read is adjacent, it is nearly free. A data structure is "cache-friendly" when the bytes you touch next are the bytes already in the line you just paid for. This lesson is where that abstract cost becomes a measured 30× on code you already write.

Start with the thing you think you understand. A Python `list` *is* a contiguous, dynamically-grown array — but **contiguous array of what?** Not integers. It is a contiguous array of `PyObject*` — 8-byte *pointers* — each pointing to a separately heap-allocated integer object somewhere else in memory. So `xs[i]` is two loads: one contiguous, cache-friendly load of the pointer, then a **pointer chase** to wherever that integer object lives — which is almost never adjacent to the previous one. Summing a list is a parade of cache misses, and *on top of that*, every `+=` is a full Python-interpreter dispatch: check types, look up `__add__`, box the result as a new object.

A NumPy `ndarray` of `dtype=int64` is the other thing entirely: a contiguous array of the **raw 8-byte integers themselves**, no boxing, no pointers. `a.sum()` walks that array in one C loop — every 64-byte line holds 8 consecutive values, the prefetcher streams them, and the CPU can add several per cycle with SIMD. No per-element interpreter dispatch at all. That is the whole difference, and it is not a constant factor you can shrug off: it is the difference between "touches memory the hardware predicted" and "touches memory the hardware did not."

```
Python list [3, 1, 4]                 NumPy int64 array [3, 1, 4]
+-----------+-----------+-----------+  +-------+-------+-------+
| PyObject* | PyObject* | PyObject* |  |   3   |   1   |   4   |   <- the values, contiguous
+-----------+-----------+-----------+  +-------+-------+-------+
      |           |           |         one cache line holds 8 of these
      v           v           v         streamed; SIMD-summable; no boxing
   [int 3]     [int 1]     [int 4]      <- scattered on the heap; each read a
   (heap)      (heap)      (heap)          possible cache miss + a boxed object
```

**Worked example — the same sum, two structures, one measured gap.**

```python
import time
import numpy as np

def loop_sum(xs):
    total = 0
    for x in xs:          # pointer chase per element + interpreter dispatch per +=
        total += x
    return total

for n in (10**6, 10**7):
    xs = list(range(n))
    a = np.arange(n, dtype=np.int64)     # contiguous raw int64s

    t0 = time.perf_counter(); loop_sum(xs); t1 = time.perf_counter()
    a.sum();                              t2 = time.perf_counter()

    per_list  = (t1 - t0) * 1e9 / n
    per_numpy = (t2 - t1) * 1e9 / n
    print(f"n={n:>9}  list-loop {per_list:5.1f} ns/el   np.sum {per_numpy:4.2f} ns/el   {(t1-t0)/(t2-t1):.0f}x")
```

Representative output (your absolute numbers depend on the machine; the *shape* does not):

```
n=  1000000  list-loop  25.0 ns/el   np.sum 0.88 ns/el   29x
n= 10000000  list-loop  25.2 ns/el   np.sum 0.79 ns/el   32x
```

Read the two invariants. First, both are **flat in ns/element** — total time is linear (O(N)) for each; the *slope* is identical, it is the *constant* that differs by ~30×. Second, that constant is not "NumPy is written in C" hand-waving: it is 25 ns of pointer-chase-plus-dispatch versus <1 ns of streamed contiguous add. AIE-102's numbers *are* this benchmark. NumPy is fast because it put the values where the cache expected them.

**A second fact to bank: `list.append` is amortized O(1), and here is the mechanism.** A list has a `size` and a larger `capacity`; when it fills, CPython allocates a bigger block (growth ≈ `newsize + newsize/8 + 6`, so ~1.125×) and copies. Most appends are a single write into spare capacity; the occasional append pays the copy, and the copies are geometrically rare, so the *average* is constant. This is the same amortized-doubling argument you will use for the hash table's resize in Lesson 3 — bank it now.

**Named misconceptions:**

- **"A Python list stores its numbers contiguously, like a C array."** It stores *pointers* contiguously. The numbers are boxed objects elsewhere on the heap. The contiguity you get buys you O(1) indexing of the *pointer*; it does not buy you cache-friendly traversal of the *values*. That distinction is the entire 30×.
- **"NumPy is faster because C is faster than Python."** Partly, but the load-bearing reason is *layout*: raw contiguous int64s stream through cache and vectorize; a `list` of the same length forces a cache miss and a boxed-object allocation per element. A C program that stored an array of pointers-to-heap-ints would be nearly as slow as the Python loop. Speed is a property of where the bytes are, not only what language moved them.
- **"`sum(xs)` and `np.sum(a)` are the same operation, so timing either is fine."** They are the same *arithmetic* over different *structures*. Benchmarking `sum` over a `list` measures the pointer-chase structure; benchmarking `np.sum` over an `ndarray` measures the contiguous one. Choosing which structure to time *is* the engineering decision — that is what this whole module is about.

### Lesson 2 — What a `dict` really is: hashing, the slot array, and O(1) on a bet

**The teaching.** A dictionary answers "is `key` here, and what's its value?" without scanning. The trick is to turn the key into an integer that *is* an address into a flat array. That integer is the **hash**: `hash(key)` returns a machine-word int, and the table keeps its slots in an array whose length is a power of two, so the slot index is just the low bits: `index = hash(key) & (capacity - 1)`. Store the entry there; to look it up, hash again, go straight to that slot. One arithmetic op, one array load. *That* is where "O(1)" comes from — not from magic, from **computing the address instead of searching for it.**

Two facts make this concrete in CPython. First, `hash` of an int is (almost) the int itself: `hash(0) == 0`, `hash(42) == 42`, and the sole special case `hash(-1) == -2` (because `-1` is CPython's internal error sentinel for `hash`). Second, the table is a real array with a real mask:

```python
>>> hash(42), hash(0), hash(-1)
(42, 0, -2)
>>> # a dict with capacity 8 masks with 7 (= 0b111): only the low 3 bits pick the slot
>>> [k & 7 for k in (0, 8, 16, 5, 13)]
[0, 0, 0, 5, 5]      # 0, 8, 16 all want slot 0;  5 and 13 both want slot 5
```

The moment two keys want the same slot, you have a **collision**, and the table needs a rule for it. CPython uses **open addressing**: everything lives in the one slot array — no linked lists — and on collision you probe *other slots* in a deterministic sequence until you find the key or an empty slot. (The alternative, **separate chaining**, hangs a linked list off each slot; Lesson 3 weighs them. A `dict` is open-addressed, so that is what we build.) The simplest probe sequence is **linear probing**: if slot `i` is taken by a different key, try `i+1`, `i+2`, … wrapping around. CPython uses a fancier perturbed sequence (Lesson 4) for good reason, but linear probing is the honest core and the one you will build.

Lookup, then, is: hash to the home slot; if it holds your key, done; if it holds a *different* key, keep probing; **if it holds EMPTY, the key is absent** — because insertion would have stopped at the first empty slot, so an empty slot on the probe path proves the key was never inserted. That invariant ("stop at empty") is the whole correctness argument, and it is the thing deletion is about to threaten in Lesson 3.

**Worked example — a hash table you can hold in your head.** Insert `0, 8, 16` (all hash to slot 0 in a capacity-8 table) with linear probing:

```
capacity 8, mask 7.  index(k) = k & 7.

insert 0:  slot 0 empty      -> place at 0
insert 8:  slot 0 taken(0)   -> probe 1, empty -> place at 1
insert 16: slot 0 taken(0)   -> probe 1 taken(8) -> probe 2, empty -> place at 2

 idx:   0    1    2    3   4   5   6   7
      [ 0 ][ 8 ][16 ][   ][  ][  ][  ][  ]

lookup 16: index 0 -> holds 0 (not 16) -> 1 holds 8 (not 16) -> 2 holds 16. Found in 3 probes.
lookup 24: index 0 -> 0 -> 8 -> 16 -> slot 3 EMPTY -> ABSENT (never inserted; stop, don't scan on).
```

Three keys, three slots, and already the seed of the whole module: `lookup 16` took **3 probes**, not 1, because the keys collided. On these three keys nobody cares. Multiply the collision by a million (Lesson 4) and the "O(1) lookup" is a linear scan wearing a dictionary's clothes.

**Named misconceptions:**

- **"A dict is a hash table with a bucket list per slot" (the textbook separate-chaining picture).** That is *one* design, and it is not CPython's. A `dict` is open-addressed: one flat array of slots, collisions resolved by probing to *other slots in the same array*, no per-slot linked lists. The textbook chaining diagram will mislead you about cache behavior and about why deletion needs tombstones.
- **"O(1) lookup is a property of hash tables."** O(1) *average* lookup is a property of hash tables *with a hash function that spreads keys roughly uniformly and a bounded load factor*. Strip either assumption and lookup is O(n). The O(1) is a bet on the hash, not a guarantee of the structure — this is the sentence the whole module exists to install.
- **"`hash(key)` is the slot."** `hash(key)` is a full machine-word integer; the slot is `hash(key) & (capacity - 1)` — only the low bits, and the mask changes every time the table resizes. Two keys with wildly different hashes can share a slot because they share low bits; that is precisely a collision.

### Lesson 3 — Load factor, resize, and deletion: why the table grows and why it needs tombstones

**The teaching.** Linear probing is fast *only while the table is not too full*. Define the **load factor** α = (occupied slots) / capacity. When α is small, most home slots are empty and lookups take ~1 probe; as α → 1, keys pile into ever-longer probe runs and the expected probe count for open addressing blows up roughly like `1 / (1 − α)` — at α = 0.9 that's ~10 probes on *average*, at α = 0.99 it's ~100. So a hash table cannot let itself fill up. It **resizes**: when occupancy crosses a threshold, allocate a bigger array (a larger power of two) and **rehash every entry into it**, because the mask changed so every slot index changed. CPython resizes when the table is **2/3 full** and grows so the used entries land around 1/3 full again — keeping α comfortably below the danger zone.

Resize looks O(n) (it copies everything), but like `list.append` in Lesson 1 it is **amortized O(1) per insert**: you only resize after Θ(capacity) cheap inserts, and the resize costs Θ(capacity), so the average extra cost per insert is a constant. You pay a rare large bill funded by many cheap ones. Predicting *when* the bill lands — and that it does not change the asymptotic per-insert cost — is a graded prediction in Lab C.

**Deletion is where open addressing gets subtle, and it is the most common way a hand-built table is silently wrong.** Recall the lookup invariant: an EMPTY slot on the probe path *proves absence*. Now delete a key by just blanking its slot to EMPTY, and watch it break:

```
[ 0 ][ 8 ][16 ]...      delete 8 by writing EMPTY into slot 1:
[ 0 ][EMP][16 ]...      now lookup 16: index 0 -> 0 -> slot 1 EMPTY -> "ABSENT"  <-- WRONG, 16 is right there
```

Blanking to EMPTY severs the probe chain: 16 was reachable only by walking *through* slot 1, and now the walk stops early and lies. The fix is a **tombstone**: a third slot state, DELETED, distinct from EMPTY. A lookup treats DELETED as "keep probing" (the chain continues), while an insert may *reuse* a DELETED slot. Empty still means stop-and-absent; deleted means occupied-for-probing-purposes-but-available-for-insert. Tombstones count toward the resize threshold (they still cost you probes), which is why real tables track *fill* = live + tombstones separately from *used* = live.

**Chaining vs. open addressing — the design fork, stated honestly.** Separate chaining (a linked list per slot) makes deletion trivial (unlink a node) and tolerates α > 1, but every element is a separately-allocated node reached by a pointer chase — the Lesson 1 cache problem, per lookup. Open addressing keeps everything in one contiguous array (cache-friendly, the reason `dict` is fast) at the cost of tombstone bookkeeping and a hard α < 1 ceiling. CPython chose open addressing and paid the tombstone tax to get the cache locality. That trade — pointer-chasing flexibility vs. contiguous speed — is the same trade as Lesson 1, wearing a different hat.

**Worked example — a resize you can predict.** Start capacity 8, CPython-style rule (resize when fill·3 ≥ capacity·2, i.e. at fill = 6):

```
insert 6 distinct non-colliding keys:  fill goes 1..5, no resize yet (5*3=15 < 8*2=16).
On the would-be 6th insert, __setitem__'s pre-insert check fires first: (fill+1)*3 = 6*3=18 >= 16 -> RESIZE,
called BEFORE the 6th key is added — so inside _resize(), self._used is still 5.
new capacity: smallest power of two > used*3 = 5*3 = 15  ->  16.
the 5 already-inserted entries are rehashed with mask 15 (new low-4-bit slots), fill reset to 5;
then the 6th key is inserted normally. fill = used = 6, load 6/16 = 0.375.
```

So the table doubled from 8 to 16, not quadrupled, because `_resize()` sizes off `self._used` **as it stood before the triggering key was counted**, not an anticipated `(used+1)`. That one-key offset between the *trigger* (which looks ahead with `fill+1`) and the *target size* (which does not look ahead) is the detail worth tracing by hand rather than trusting prose — and it is why a benchmark that stops at N=1000 can completely miss a resize that dominates at N=10⁶.

**Named misconceptions:**

- **"Delete a key by clearing its slot."** In open addressing that severs probe chains and makes *other* keys unfindable. You must write a **tombstone** (DELETED), distinct from EMPTY, that lookups probe through and inserts may reuse. This is the single most common correctness bug in a from-scratch hash table, and a small test with no collisions will not catch it — you need colliding keys plus a delete-in-the-middle to expose it (that exact test is in Lab B).
- **"Resize is O(n), so inserts aren't really O(1)."** Resize is O(n) but happens only every Θ(capacity) inserts, so it *amortizes* to O(1) per insert — same argument as `list.append`. The correct claim is "O(1) amortized," and the benchmark's flat ns/op curve (with periodic blips at resize points) is the proof.
- **"Load factor is just a memory-vs-speed tuning knob."** It is that, but it is also a *correctness-adjacent* knob: let α approach 1 in open addressing and expected probes explode like 1/(1−α), turning "O(1)" into a linear scan without any bug at all. The 2/3 threshold is a chosen point on that curve, not an arbitrary constant.

### Lesson 4 — When hashing degrades: adversarial keys, perturbation, and the O(n) that hides in production

**The teaching.** Everything so far assumed the hash *spreads* the keys. Remove that assumption and the structure does not break — it *silently degrades*, which is worse, because it still returns correct answers, just slowly, and only under inputs you did not test. Three ways the spread fails, in increasing subtlety:

**(1) A degenerate hash function.** If `hash(key)` returns a constant — say a custom class with `def __hash__(self): return 0` — every key lands in the same home slot, every insert probes past all prior keys, and a table of n such keys costs 1+2+…+n = Θ(n²) to build and Θ(n) per lookup. This is not exotic: a naïve `__hash__` on a custom object, or hashing only one field of a compound key, produces exactly this. It passes every correctness test — the answers are right — and turns a request handler into a quadratic time bomb.

**(2) Keys that collide in the low bits.** Even with `hash(n) == n`, keys chosen so their *low bits* agree all target the same home slot: in a table with mask `2^b − 1`, keys `0, 2^b, 2·2^b, …` all have index 0. With plain linear probing that is Θ(n²) clustering again — and it is why CPython does **not** use plain linear probing. Its probe sequence *perturbs* with the high bits:

```
i = hash & mask
perturb = hash
repeat:
    perturb >>= 5
    i = (i*5 + perturb + 1) & mask     # mixes in 5 more high bits each step
```

Because `perturb` feeds in five higher bits per step, keys that agree only in the low bits *diverge* after a couple of probes. This is a real defense you can measure: 100 000 integer keys of the form `i << 20` (identical in the low 20 bits) stay findable in a real `dict` — measurably slower (~5× here, because the first couple of probes still collide before the high bits kick in) but **not** the catastrophic O(n) that plain linear probing would suffer. The perturbation is why your hand-built linear-probing table is *more* fragile than `dict` on structured integer keys — a humbling, correct thing to discover in Lab C.

**(3) An adversary who controls keys — "hash flooding."** If the hash is *predictable*, an attacker who chooses the keys (JSON payloads, HTTP headers, form fields — anything that becomes dict keys) can hand you a set that all collide, forcing Θ(n²) and taking your service down with a small request. This was a real, cross-language vulnerability disclosed in 2011 (CVE-2012-1150 and the oCERT-2011-003 advisory) that hit Python, and CPython's answer since 3.3 is **SipHash with a per-process random seed** (`PYTHONHASHSEED`): string hashes are randomized per run, so an attacker cannot precompute a colliding set. Confirm it yourself — the same string hashes differently across runs:

```
$ python3 -c "print(hash('victim'))"
 8724009212345...      # a value
$ python3 -c "print(hash('victim'))"
-3391005559876...      # a different value, next process
```

But note the sharp asymmetry the module keeps returning to: **integer hashes are *not* randomized** (`hash(n) == n` every run), and a **constant `__hash__` is not defended against at all**. SipHash protects you from an adversary guessing *string* hashes; it does nothing about a bad hash *you wrote*. The clean, reliable way to force O(n) in a real `dict` is not clever colliding strings — it is the constant `__hash__` from failure mode (1).

**Worked example — the constant-hash time bomb, measured.**

```python
import time

class BadKey:
    __slots__ = ("v",)
    def __init__(self, v): self.v = v
    def __hash__(self): return 0                     # every key -> same home slot
    def __eq__(self, o): return isinstance(o, BadKey) and self.v == o.v

for n in (1000, 2000, 4000):
    objs = [BadKey(i) for i in range(n)]
    t0 = time.perf_counter()
    d = {}
    for o in objs:      # each insert probes past all prior keys -> Theta(n^2) total
        d[o] = 1
    t1 = time.perf_counter()

    good = {}
    t2 = time.perf_counter()
    for k in range(n):  # hash(int)==int, keys spread -> Theta(n) total
        good[k] = 1
    t3 = time.perf_counter()
    print(f"n={n:>5}  bad_hash {t1-t0:7.4f}s   good {t3-t2:.6f}s   ratio {(t1-t0)/(t3-t2):.0f}x")
```

Representative output:

```
n= 1000  bad_hash  0.0342s   good 0.000094s   ratio  363x
n= 2000  bad_hash  0.1390s   good 0.000169s   ratio  821x
n= 4000  bad_hash  0.5538s   good 0.000428s   ratio 1293x
```

Read the *shape*: double n and `bad_hash` roughly **quadruples** (0.034 → 0.139 → 0.554) — the signature of Θ(n²) — while `good` merely doubles (Θ(n)). The ratio therefore doubles each step. Both dicts are *correct*: every key is present, every value is right, `pytest` would be green. The only thing wrong is the cost, and the cost is invisible until n is large and the keys are adversarial. That gap — correct-but-quadratic, green-but-doomed — is the thing this module exists to make you able to *see before you ship it*.

**Named misconceptions:**

- **"Python randomizes hashes, so hash flooding is solved."** It randomizes *string* (and bytes) hashes via SipHash. Integer hashes are unrandomized (`hash(n) == n`), and any object with a weak or constant `__hash__` you wrote is wide open. The mitigation is specific and partial, not a blanket guarantee.
- **"If my tests pass, my dict usage is O(1)."** Correctness tests certify *answers*, never *cost*. A constant `__hash__` gives correct answers with quadratic cost and green tests. Only a growing-N benchmark with a measured slope distinguishes O(1)-amortized from O(n) — which is why the harness measures `p`.
- **"Linear probing and CPython's probing are basically the same."** CPython's perturbed sequence deliberately mixes high bits so that keys colliding in the low bits still spread. Plain linear probing does not, so it clusters catastrophically on structured integer keys where `dict` shrugs. When your from-scratch table is slower than `dict` on `i << 20` keys, that is not a bug in your code — it is the perturbation you didn't implement.
- **"A collision is a bug."** Collisions are *normal and expected* — the birthday paradox guarantees them well before the table is full. The structure is *designed* to handle a bounded rate of them cheaply. The pathology is not "a collision"; it is "*all* keys colliding," caused by a hash that doesn't spread or an adversary who exploits that it doesn't.

```python
class HashTable:
    _EMPTY = object()
    _DELETED = object()

    def __init__(self, capacity=8, auto_resize=True):
        assert capacity >= 8 and (capacity & (capacity - 1)) == 0, "capacity must be power of two >= 8"
        self._capacity = capacity
        self._used = 0
        self._fill = 0
        self._auto_resize = auto_resize
        self._keys = [self._EMPTY] * capacity
        self._values = [None] * capacity

    def __len__(self):
        return self._used

    def load_factor(self):
        return self._fill / self._capacity

    def __setitem__(self, key, value):
        if self._auto_resize and (self._fill + 1) * 3 >= self._capacity * 2:
            self._resize()
        mask = self._capacity - 1
        i = hash(key) & mask
        first_deleted = -1
        while True:
            slot = self._keys[i]
            if slot is self._EMPTY:
                if first_deleted != -1:     # reuse an earlier tombstone: no new fill
                    i = first_deleted
                else:
                    self._fill += 1
                self._keys[i] = key
                self._values[i] = value
                self._used += 1
                return
            if slot is self._DELETED:
                if first_deleted == -1:
                    first_deleted = i        # remember, but keep probing for a live match
            elif slot == key:
                self._values[i] = value      # overwrite in place
                return
            i = (i + 1) & mask

    def __getitem__(self, key):
        mask = self._capacity - 1
        i = hash(key) & mask
        while True:
            slot = self._keys[i]
            if slot is self._EMPTY:
                raise KeyError(key)          # empty proves absence
            if slot is not self._DELETED and slot == key:
                return self._values[i]
            i = (i + 1) & mask               # probe through tombstones and non-matches

    def __delitem__(self, key):
        mask = self._capacity - 1
        i = hash(key) & mask
        while True:
            slot = self._keys[i]
            if slot is self._EMPTY:
                raise KeyError(key)
            if slot is not self._DELETED and slot == key:
                self._keys[i] = self._DELETED   # tombstone, NOT empty
                self._values[i] = None
                self._used -= 1                 # fill unchanged: tombstone still occupies
                return
            i = (i + 1) & mask

    def __contains__(self, key):
        try:
            self[key]; return True
        except KeyError:
            return False

    def probe_count(self, key):
        mask = self._capacity - 1
        i = hash(key) & mask
        count = 1
        while True:
            slot = self._keys[i]
            if slot is self._EMPTY:
                return count
            if slot is not self._DELETED and slot == key:
                return count
            i = (i + 1) & mask
            count += 1

    def _resize(self):
        old_keys, old_values = self._keys, self._values
        target = self._used * 3
        new_capacity = 8
        while new_capacity <= target:
            new_capacity *= 2
        self._capacity = new_capacity
        self._keys = [self._EMPTY] * new_capacity
        self._values = [None] * new_capacity
        self._used = 0
        self._fill = 0
        for k, v in zip(old_keys, old_values):     # live entries only; tombstones vanish
            if k is not self._EMPTY and k is not self._DELETED:
                self[k] = v
```

## Three-tier reading — hashing, the average case, and whose lookup is the slow one

**Tier 1 — Material ground (verifiable facts).** A hash table computes a slot from a key instead of searching for it: `index = hash(key) & (capacity − 1)`, one arithmetic op and one array load, and *that* is the source of "O(1)." Every claim in this module is checkable at the keyboard. `hash(42) == 42` and `hash(-1) == -2` in CPython; a `list` of a million ints and an `int64` NumPy array of the same values sum with identical O(N) slope but a ~30× constant gap you can measure; a from-scratch open-addressed table that deletes with EMPTY *will* fail to find a colliding key after a middle delete, and a tombstone *will* fix it, both demonstrable in five lines; a `dict` built from objects whose `__hash__` returns a constant builds in Θ(n²) — double n, quadruple the time — while remaining perfectly *correct*, every key present with the right value. And CPython's string-hash randomization is real: `python3 -c "print(hash('x'))"` prints a different number each process. None of this is opinion; all of it is a measured slope or a printed value.

**Tier 2 — What the field suppresses.** Two opposite distortions hide the same truth. The booster distortion — "hash tables are O(1), use a dict and move on" — suppresses that the O(1) is an **average over a uniformity assumption**, and averages have distributions. "O(1) average" is compatible with *some specific keys* costing O(n): the keys that collide, the keys an adversary chose, the keys whose `__hash__` you wrote carelessly. The cost did not disappear; it got **redistributed onto whichever keys the hash fails to spread**, and the aggregate stayed cheap precisely because the expensive cases are rare — rare, not absent, and not randomly assigned. The traditionalist distortion — hashing as a solved, boring primitive, collisions as a textbook footnote — suppresses that collision behavior is a live *security and fairness* surface: hash flooding was a real cross-language CVE, string randomization is a mitigation with a known hole (integers and custom hashes are undefended), and the "average" that makes the structure fast is an average *someone's* keys sit at the bad tail of. Both camps avoid the honest middle: **a hash table is fast on average by being slow on a minority, and which minority is not decided by the structure — it is decided by the hash function and by who supplies the keys.**

**Tier 3 — Sit with this (a question you cannot unknow).** You will build systems that hash people. Deduplication that hashes names and birthdates to decide who is "the same person"; caches keyed by user ID; feature stores, join keys, blocked-record matching — all of it leaning on the same bet, that the hash spreads the keys so the average stays O(1). But the average is bought by a tail, and the tail is not random: it is the keys that collide, the values that repeat, the names that are common, the records that don't fit the shape the hash was tuned for. The person whose lookup is the slow one, the record that lands in the over-full bucket, the identity that collides with someone else's and gets silently merged — **when you report your system's latency as a single average number and it passes every correctness test, whose O(n) did you fold into everyone else's O(1), and would you be able to name them — or has the structure, by design, made the person paying the cost the one you are least able to see?**
