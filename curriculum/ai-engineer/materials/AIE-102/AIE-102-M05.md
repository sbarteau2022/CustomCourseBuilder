## Lessons

### Lesson 1 — `PyObject`: the C struct under every single Python value

In M03 you built a growable vector as a C struct: a length, a capacity, a pointer to heap. You managed its lifetime by hand. Now look at what CPython does for *every value you have ever typed*.

Here is the actual definition, from CPython's `Include/object.h` (simplified to the shape that has been stable since Python 2.x; the 3.12 change is noted below):

```c
typedef struct _object {
    Py_ssize_t    ob_refcnt;   // how many references point at me
    PyTypeObject *ob_type;     // pointer to my type (int, str, list, ...)
} PyObject;
```

That is it. **Two machine words.** On a 64-bit build: 8 bytes of reference count, 8 bytes of type pointer — 16 bytes of header that sits at the front of *every* Python object in existence. `None` has it. `True` has it. The number `7` has it. Your 4-gigabyte model weights tensor has exactly one of these headers at its front.

Objects that carry a variable number of elements (ints of arbitrary size, tuples, strings) start with a slightly longer header, `PyVarObject`, which adds one field:

```c
typedef struct {
    PyObject      ob_base;     // the two-word header above
    Py_ssize_t    ob_size;     // number of elements (digits, chars, items)
} PyVarObject;
```

**A Python `int` is a struct.** From `Include/cpython/longobject.h` (pre-3.12 form):

```c
struct _longobject {
    PyObject_VAR_HEAD          // ob_refcnt, ob_type, ob_size  (24 bytes)
    digit ob_digit[1];         // the actual value, base-2^30 digits (4 bytes each)
};
```

This is why the empty-cost of a Python integer is not 4 or 8 bytes:

```python
>>> import sys
>>> sys.getsizeof(0)      # ob_size == 0 → no digits stored
24
>>> sys.getsizeof(10)     # ob_size == 1 → one 4-byte digit
28
>>> sys.getsizeof(2**30)  # ob_size == 2 → two digits
32
```

24 = `ob_refcnt` (8) + `ob_type` (8) + `ob_size` (8). Every additional 30 bits of magnitude costs another 4-byte digit. The number `10` in Python is a 28-byte heap allocation with a reference count and a pointer to the `int` type object — where in C it was one register.

#### Worked example — the same list, one layer down

In M03 you wrote `int *a = malloc(3 * sizeof(int));` and got 12 bytes of contiguous `int`s. Here is what `x = [1, 2, 3]` actually is:

- `x` is a **name** → a pointer to a `PyListObject` on the heap.
- The `PyListObject` header is `ob_refcnt`, `ob_type` (points to `PyList_Type`), `ob_size` (== 3), then `ob_item` — a pointer to a *separate* heap block of `PyObject *`.
- That block is **three pointers**, not three ints. Each pointer aims at a *separate 28-byte `PyLongObject`* elsewhere on the heap.

So the M03 C array `{1, 2, 3}` is 12 contiguous bytes. The Python list `[1, 2, 3]` is: one list header (~64 bytes) + one pointer array (24 bytes) + three boxed ints (28 bytes each) = **~172 bytes, in five separate heap allocations, connected by pointers you chase.** This single picture — boxes on the heap connected by arrows — is the reason a NumPy array of a million ints (8 contiguous MB) crushes a Python list of a million ints (chasing a million pointers to a million cold 28-byte boxes). You measured that cache penalty in M04. Now you know what is scattered.

> **3.12 note (say it, don't hide it):** In Python 3.12 the header changed. `ob_refcnt` became a union (to support *immortal* objects, PEP 683), and `PyLongObject` replaced `ob_size` + `ob_digit` with a tagged `_PyLongValue` (`lv_tag`). The *shape of the idea* — a refcount word, a type pointer, an inline payload — is unchanged and is what you must be able to draw. We teach the durable shape and flag the version-specific field names so a learner reading real source in 2027 is not blindsided.

#### Misconception 1 — "a variable holds a value; an int is 4 bytes"

In C, `int x = 10;` puts the *bytes* `10` in a stack slot. In Python, `x = 10` binds the name `x` to a *pointer* to a heap `PyLongObject`. The name is the pointer; the value is the boxed struct. **Nothing in Python is unboxed** (there is no `int` living directly in a variable slot — CPython has no unboxed scalars at all). This is not pedantry: it is the entire reason a Python `for` loop is slow (Lesson 4) and the entire reason `is` and `==` differ (Lab A). Name-is-a-pointer, value-is-a-heap-struct. Draw it as two boxes and an arrow, exactly like M03.

### Lesson 2 — Refcounting: `malloc`/`free`, automated, and watchable

In M03 you called `free()` yourself, and forgetting it was a leak and doing it twice was a double-free crash. CPython does the `free()` for you — but the mechanism is not magic, it is a counter, and you can watch it.

Every `PyObject` carries `ob_refcnt`. Two operations mutate it. From `Include/object.h`, conceptually:

```c
static inline void Py_INCREF(PyObject *op) {
    op->ob_refcnt++;                 // one more reference now points here
}

static inline void Py_DECREF(PyObject *op) {
    if (--op->ob_refcnt == 0) {      // the last reference just went away
        _Py_Dealloc(op);             // → calls ob_type->tp_dealloc → free()
    }
}
```

That is the whole garbage collector for the common case. When you write `y = x`, CPython does `Py_INCREF` on the object. When `x` goes out of scope or is rebound, `Py_DECREF`. When the count reaches zero, the object's type's `tp_dealloc` runs (which, for simple objects, is essentially `free()`). **`free()` from M03 is still happening — it is triggered by a subtraction reaching zero.**

You can read the counter directly:

```python
>>> import sys
>>> a = object()
>>> sys.getrefcount(a)
2
```

#### Misconception 2 — "`getrefcount` is broken, it says 2 for one reference"

It is not broken; you are watching the machine. `sys.getrefcount(a)` **passes `a` as an argument**, and passing an argument does `Py_INCREF`. So while the function runs, there are two references: your name `a`, and the function's parameter. The answer is always one higher than the count "outside." This off-by-one *is* the lesson: argument passing is a refcount event. Once you see that, you predict it instead of tripping on it.

#### Worked example — watching lifetime happen

```python
import sys

class Loud:
    def __del__(self):
        print("  tp_dealloc ran — I am being freed")

x = Loud()                       # refcnt effectively 1
print(sys.getrefcount(x))        # 2  (the +1 is getrefcount's own arg)
y = x                            # Py_INCREF
print(sys.getrefcount(x))        # 3
del y                            # Py_DECREF
print(sys.getrefcount(x))        # 2
print("about to del x")
del x                            # Py_DECREF → count hits 0 → free()
print("done")                    # __del__ printed BEFORE this line
```

The `__del__` message prints *between* `del x` and `done` — deallocation is synchronous and immediate, the instant the count hits zero. This is not a lazy sweep at some later time. It is a `free()` the moment a subtraction reaches 0.

#### Misconception 3 — "refcounting handles everything; Python has no leaks"

Refcounting cannot free a **reference cycle**. Two objects pointing at each other keep each other's count at ≥ 1 forever, even when nothing outside can reach them:

```python
import gc, sys
a = {}
b = {}
a["b"] = b          # a references b
b["a"] = a          # b references a  → cycle
del a, b            # outside references gone; counts still 1 each → NOT freed
# refcounting alone leaks this forever.
gc.collect()        # the *cyclic* garbage collector exists precisely for this
```

This is the real division of labor, and the field routinely blurs it: **refcounting is the primary, immediate mechanism; the `gc` module is a secondary, periodic tracer that exists only to catch cycles refcounting cannot.** Most objects never touch the cyclic collector at all — they die the instant their count hits zero. Knowing which mechanism owns which death is the difference between "Python has a garbage collector" (vague) and "Python frees on refcount-zero and traces for cycles" (true).

> **3.12 immortality subtlety (used in the assessment):** In 3.12+, `None`, `True`, `False`, and the small ints `-5..256` are *immortal* (PEP 683) — their `ob_refcnt` is pinned near `SIZE_MAX` and `Py_INCREF`/`Py_DECREF` are no-ops on them. So `sys.getrefcount(None)` returns an enormous constant, not a small number. A learner who predicts "small" and reasons "None is shared everywhere so its count is huge" is *right in mechanism even if wrong about the exact absurd number*. That is exactly how we grade (Lesson-4 principle applied early).

### Lesson 3 — The GIL: why one non-atomic counter forces one global lock

Now the payoff of Lesson 2's detail. Look again at `Py_INCREF`:

```c
op->ob_refcnt++;
```

In M02 you learned that `x++` on a machine is **three operations**: load `x` from memory into a register, add 1, store back. It is *not* atomic. Now put two OS threads on two cores both doing `op->ob_refcnt++` on the *same* object at the *same* time:

```
Thread A: load ob_refcnt (=5)                 Thread B: load ob_refcnt (=5)
Thread A: add 1 → 6                            Thread B: add 1 → 6
Thread A: store 6                              Thread B: store 6
```

Two increments happened; the count went from 5 to **6, not 7**. One reference is now uncounted. Later, one `Py_DECREF` too many will drive the count to zero while a live reference still exists → the object is `free()`'d → the other thread dereferences freed memory → **use-after-free**, the exact M03-B bug, now in the interpreter's own bookkeeping. Or the symmetric race leaks. Either way: silent corruption.

CPython's answer, since 1992: the **Global Interpreter Lock**. A single mutex that a thread must hold to touch *any* Python object. Only one thread runs Python bytecode at a time. With the GIL held, `ob_refcnt++` can never race, so it never needs to be atomic — and atomics are expensive, so single-threaded Python stays fast. The GIL is not an accident or a bug to be embarrassed about; it is a *deliberate trade*: give up thread parallelism, buy a dead-simple, fast, stable object model and a C-extension ABI that assumes single-threaded access.

#### The measurable consequence

```python
import time, threading

def burn(n):
    x = 0
    for _ in range(n): x += 1

N = 40_000_000

t = time.perf_counter()          # one thread
burn(N)
print("1 thread :", round(time.perf_counter() - t, 2), "s")

t = time.perf_counter()          # four threads, N/4 each
ts = [threading.Thread(target=burn, args=(N // 4,)) for _ in range(4)]
for th in ts: th.start()
for th in ts: th.join()
print("4 threads:", round(time.perf_counter() - t, 2), "s")
```

On a 4-core machine you will see the four-thread version take **the same wall-clock time or slightly worse** — not 4x faster. The four threads take turns holding the GIL; the CPU work is serialized, plus lock-handoff overhead. Swap `threading.Thread` for `multiprocessing.Process` and it *does* speed up ~4x — separate processes have separate interpreters, separate GILs, separate memory.

#### Misconception 4 — "the GIL makes Python single-threaded / threads are useless"

False, and the correction is precise: **the GIL is released around blocking I/O and inside C extensions that opt to release it.** A thread waiting on a socket, a disk read, or `time.sleep` has released the GIL — so I/O-bound threading *does* give real concurrency. And NumPy, `hashlib`, compression libraries, and PyTorch release the GIL around their heavy C loops, so a Python thread that spends its time inside `np.dot` *is* running C on another core while other Python threads proceed. "Threads are useless in Python" is wrong; "threads don't parallelize *pure-Python CPU* work" is right. The distinction is the whole lesson.

> **Free-threaded note (PEP 703, opt-in from 3.13):** CPython now ships an experimental *no-GIL* build. It does not wave away Lesson 3 — it makes `ob_refcnt` operations atomic (or biased/deferred) and pushes locking responsibility down into every object and every C extension. The cost the GIL centralized gets *distributed*, and every C extension must be re-audited for the thread-safety it never previously needed. We flag it as real and coming; we do not pretend it is free. It is Tier 2 of this module's reading, made concrete.

### Lesson 4 — Why a Python loop is slow, read from the C

We can now finish the sentence "Python is slow" in machine terms — no hand-waving.

Take `s = 0; for i in range(N): s += i`. In C that inner loop is: register `+=` register, one instruction, no memory traffic, the branch predictor nails the loop. Here is what CPython does **per iteration**, and you can now name every cost.

First, the bytecode (real output of `dis`):

```python
>>> import dis
>>> dis.dis("s += i")
  0 LOAD_NAME     0 (s)
  2 LOAD_NAME     1 (i)
  4 BINARY_OP    13 (+=)
  6 STORE_NAME    0 (s)
```

Every one of those opcodes is dispatched through the **evaluation loop** in `Python/ceval.c` — conceptually a giant switch inside a `for(;;)`:

```c
for (;;) {
    opcode = NEXTOP();               // fetch next bytecode
    switch (opcode) {                // dispatch (a computed-goto in real CPython)
        case BINARY_OP: {
            PyObject *rhs = POP();    // pop pointer off the value stack
            PyObject *lhs = TOP();
            // dispatch through the TYPE: lhs->ob_type->tp_as_number->nb_add
            PyObject *res = PyNumber_Add(lhs, rhs);
            SET_TOP(res);
            Py_DECREF(lhs);          // refcount churn (Lesson 2)
            Py_DECREF(rhs);          // every iteration
            DISPATCH();
        }
        ...
    }
}
```

Now count the per-iteration cost in the machine terms you learned:

1. **Bytecode fetch + dispatch** — a branch through a big switch/computed-goto, per opcode. Four opcodes per `s += i`.
2. **Two pointer chases to boxed operands** — `s` and `i` are pointers to heap `PyLongObject`s (cold, per M04's cache lesson), not registers.
3. **A type dispatch** — `PyNumber_Add` follows `lhs->ob_type->tp_as_number->nb_add`: pointer → type object → number-methods table → function pointer → **indirect call**. That is 3 dependent pointer chases plus an indirect branch the predictor can miss, *before any addition happens*.
4. **The add itself allocates a new object.** Ints are immutable, so `long_add` (in `Objects/longobject.c`) `malloc`s a fresh `PyLongObject` for the result:

```c
static PyObject *
long_add(PyLongObject *a, PyLongObject *b)
{
    // fast path for single-digit ints, but STILL returns a new object:
    if (IS_MEDIUM_VALUE(a) && IS_MEDIUM_VALUE(b))
        return PyLong_FromLong(MEDIUM_VALUE(a) + MEDIUM_VALUE(b));
    // ... general case: allocate, add digit-by-digit with carry ...
}
```

5. **Refcount churn** — `Py_DECREF` on both operands, `Py_INCREF`/store on the result, every iteration (Lesson 2). Each is a memory write.

So the "one instruction" C loop becomes, per iteration in Python: ~4 dispatched opcodes, 3+ pointer chases, an indirect call through a type table, a heap allocation for the result, and several refcount writes. That is the **50–100x** you will measure — and now you can *attribute* it, not just quote it.

> **The adaptive interpreter (PEP 659, 3.11+) — say it, it's real:** After a few iterations CPython notices both operands are ints and *specializes* `BINARY_OP` into `BINARY_OP_ADD_INT`, which **skips the type dispatch** (step 3) and adds inline. It is a genuine speedup and it is exactly why measuring on 3.11+ shows a smaller factor than the textbook "100x." It removes step 3; it cannot remove steps 1, 2, 4, 5. A learner who measures 40x on 3.12 and attributes the remaining cost to boxing + allocation + refcount churn is *reasoning correctly* even though the number is not 100. That is the grading principle of this whole course.

#### Worked example — put a number on it

```python
import timeit
N = 10_000_000
py = timeit.timeit(lambda: sum(range(N)), number=1)        # builtin, C-level loop
loop = timeit.timeit("s=0\nfor i in range(N): s+=i",
                     globals={"N": N}, number=1)            # pure-Python loop
print(f"pure-Python loop: {loop:.3f}s   builtin sum: {py:.3f}s   ratio: {loop/py:.1f}x")
```

`sum()` is a C loop over the same objects; the pure-Python loop pays every cost above. The ratio you print (typically 5–15x against `sum`, and ~50x+ against a true C `for`) is the descent made visible. **This is the module's thesis: the slowness is not mysterious, it is `PyObject` boxing + `ceval` dispatch + allocation + refcount churn, every single item.**

**Goal:** predict, before running, exactly which workloads the GIL serializes and which it does not — and tie the answer to the non-atomic `ob_refcnt++` of Lesson 3.

#### Build

**Starter / Solution** (`gil_bench.py`):

```python
import time, threading, multiprocessing as mp

def cpu(n):
    x = 0
    for _ in range(n): x += 1

def io(_):
    time.sleep(1.0)

def np_dot(_):
    import numpy as np
    a = np.random.rand(1200, 1200)
    for _ in range(20): a = a @ a * 0.0 + a   # keep it in C, GIL released

def bench(fn, arg, workers, kind):
    t = time.perf_counter()
    if workers == 1:
        fn(arg)
    elif kind == "thread":
        ts = [threading.Thread(target=fn, args=(arg,)) for _ in range(workers)]
        [t_.start() for t_ in ts]; [t_.join() for t_ in ts]
    else:
        ps = [mp.Process(target=fn, args=(arg,)) for _ in range(workers)]
        [p.start() for p in ps]; [p.join() for p in ps]
    return time.perf_counter() - t

# --- the race demo: shared, unlocked, non-atomic ---
counter = 0
def racer(n):
    global counter
    for _ in range(n): counter += 1     # LOAD_FAST/ADD/STORE — interleavable

if __name__ == "__main__":
    base = bench(cpu, 40_000_000, 1, "thread")
    print("CPU  1x:", round(base, 2))
    print("CPU  4 threads  ratio:", round(base / bench(cpu, 10_000_000, 4, "thread") * 1, 2))
    print("CPU  4 procs    ratio:", round(base / bench(cpu, 10_000_000, 4, "proc"), 2))

    counter = 0
    ts = [threading.Thread(target=racer, args=(1_000_000,)) for _ in range(4)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print("race counter (want 4_000_000):", counter)   # often LESS
```

### Lab M05-C — Read the source, attribute the cost

**Goal:** the M03-C-shaped capstone. Predict *where* the time in a Python loop goes, then instrument to attribute it to specific `PyObject`/`ceval` operations. Graded like M03-C: **full marks for correct mechanism even if the factor is off; zero for a right factor with the wrong mechanism.**

#### Predict (on paper)

For `s = 0; for i in range(1_000_000): s += i`:

1. How many **new `PyLongObject`s** are allocated over the whole loop, roughly, and why (immutability → new object per add; note the small-int cache spares `-5..256`)?
2. Rank these four costs from largest to smallest for this loop and justify: (a) bytecode dispatch in `ceval`, (b) boxing/allocation of result ints, (c) refcount `INCREF`/`DECREF`, (d) the actual integer addition.
3. Predict the ratio of the pure-Python loop to `sum(range(1_000_000))`. State whether the adaptive interpreter (`BINARY_OP_ADD_INT`) is active on your Python version and what step it removes.

#### Build

```python
# (1) see the bytecode you are paying for, per iteration

# (2) time it against the C-level builtin

def f():
    s = 0
    for i in range(N): s += i
    return s
f()  # warm up the adaptive interpreter
dis.dis(f, adaptive=True)   # look for BINARY_OP_ADD_INT (3.11+)
```

- Your allocation prediction: essentially one new int per iteration once values exceed 256 (≈ 1,000,000 − 257 allocations), because ints are immutable and each `+` returns a fresh object; small results reuse the cache. Confirm the mechanism from `long_add` returning `PyLong_FromLong(...)`.
- Your cost ranking is graded on *reasoning*: for this loop, allocation + dispatch dominate; the addition itself is nearly free. ### Module exam — unseen program, predict before running

The learner is handed **one unseen ~35-line Python program** drawn at random from a bank, each containing exactly one internals-level defect, and must produce a four-part artifact:

**(a) Predict** the behavior *before running* — in `PyObject`/refcount/GIL/`ceval` terms.
**(b) Locate** the mechanism by reading (and, where relevant, by reading the header out of memory with `ctypes` as in M05-A).
**(c) Fix or optimize** it.
**(d) Prove** the fix with a measurement or a refcount/`gc` observation.

Example bank items (the learner sees one, unseen):

## Three-tier reading

- **Tier 1 — material ground (verifiable facts).** Refcounting and the GIL are documented CPython design, not opinion. Every value is a heap `PyObject` whose first machine word is a reference counter; when it hits zero, `tp_dealloc` frees the object immediately. Because `Py_INCREF`/`Py_DECREF` mutate that word with a non-atomic `++`/`--`, two threads on two cores would corrupt it — freeing an object early (the M03 use-after-free, now inside the interpreter) or leaking it. The GIL is the single mutex that makes those unprotected writes safe, and its measurable consequence — pure-Python CPU threads do not parallelize — is undisputed and reproducible (Lab M05-B). This was a deliberate 1992 trade: give up thread parallelism, buy a simple, fast, stable object model and C-extension ABI.

- **Tier 2 — what the field suppresses.** "Python is fast enough, just use NumPy" and "Python is slow, just remove the GIL" suppress the *same* fact: the single-lock model is **why** the C-extension ecosystem exists and stays stable. Every line of NumPy, PyTorch, and CPython's own C API was written assuming one thread mutates objects at a time; that assumption is load-bearing across millions of lines you never read. The speed you "get from NumPy" is the speed of C that releases the GIL and manages memory by hand — the same dangerous manual memory from M03 — offloaded to maintainers you never see. Free-threaded CPython (PEP 703) does not delete this cost; it *distributes* it, making every C extension responsible for its own locking and re-exposing the refcount races the GIL was hiding. Safety and speed were never free — they were borrowed against strangers' correctness.

- **Tier 3 — sit with this (a question you cannot unknow).** The performance you will ship comes from dropping into C someone else wrote and trusting that it increments and decrements every refcount correctly, and holds — or correctly releases — the one lock. When your model serves a million requests and a C extension leaks one `PyObject` per call, or drops a refcount one too many and frees an object another thread is still reading: whose object was it, whose lock was it, and at what moment did you agree to trust that it was being managed?
