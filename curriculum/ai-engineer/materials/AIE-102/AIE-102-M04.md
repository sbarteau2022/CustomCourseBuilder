### The provided timing + reporting harness (`hz.h`)

All labs `#include "hz.h"`. It gives you a monotonic nanosecond clock, a "touch this so the optimizer can't delete my loop" sink, and a tiny table printer. You do not implement this; you use it.

```c
/* hz.h — provided. Monotonic timer + anti-DCE sink + reporting. */
#ifndef HZ_H
#define HZ_H
#include <stdio.h>
#include <stdint.h>
#include <time.h>

static inline double hz_now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e9 + (double)ts.tv_nsec;
}

/* Force the compiler to believe `v` is used and may escape, so it cannot
   delete the loop that produced it. Works on gcc/clang. */
static inline void hz_sink_u64(uint64_t v) {
    __asm__ volatile("" : : "r"(v) : "memory");
}
static inline void hz_sink_f64(double v) {
    __asm__ volatile("" : : "x"(v) : "memory");
}

/* Median of an array of doubles (destructive: sorts in place). */
static inline double hz_median(double *a, int n) {
    for (int i = 1; i < n; i++) {          /* insertion sort, n is tiny */
        double k = a[i]; int j = i - 1;
        while (j >= 0 && a[j] > k) { a[j+1] = a[j]; j--; }
        a[j+1] = k;
    }
    return (n & 1) ? a[n/2] : 0.5 * (a[n/2 - 1] + a[n/2]);
}
#endif
```

Build every C program with **`-O2`** (this is real code as the machine runs it, not debug code) and, where a lab says so, also under **`valgrind --tool=cachegrind`** (which simulates the cache and reports miss counts, isolating memory behavior from everything else). Compile line for every lab:

```
gcc -O2 -o prog prog.c        # -lrt only on ancient glibc
```

> **Measurement hygiene (read once, apply everywhere).** A single timing is noise. Every number in this module is a **median of ≥5 runs**, each run doing enough work to last **≥50 ms**, after **one untimed warm-up pass** to fault in pages and prime the caches. Close your browser. Pin the frequency if you can (`cpupower frequency-set -g performance`). If a plateau in your data wobbles by 15%, that is not a bug — that is a shared machine. The *shape* of the curve is the signal; the third significant figure is not.

## Lessons

### Lesson 1 — The latency ladder is a number, and you have never seen it

**Descend.** In Python, `x[i]` is uniform. `a[0]` and `a[100_000_000]` "cost the same" — the language gives you no way to tell them apart, so you have quietly assumed array indexing is O(1) with a small constant. In M03 you learned that a C array is `base + i*stride` bytes — one add, one load. So it *is* one machine instruction. The abstraction was not lying about the instruction count.

It was lying about the **time that one load takes**, which is not a constant. It is a *function of where the byte currently lives*, and the byte can live in six places, spanning nearly three orders of magnitude:

**Representative latencies, modern x86 desktop (~2020s). You will measure your own — these are the ballpark to predict against.**

| Where the byte lives | Typical latency | In CPU cycles (~3 GHz) | Relatable scale (if L1 = 1 second) |
|---|---|---|---|
| Register | ~0 (it's already there) | 0 | — |
| L1 data cache (~32–48 KB) | ~1 ns | ~4 | 1 second |
| L2 cache (~256 KB–1 MB) | ~3–4 ns | ~12 | 4 seconds |
| L3 cache (shared, ~8–32 MB) | ~12–20 ns | ~40–60 | ~15 seconds |
| Main memory (DRAM) | ~80–100 ns | ~250–350 | ~1.5 minutes |
| NVMe SSD (a page fault to disk) | ~50,000–100,000 ns | ~200,000+ | ~1 day |
| Spinning disk seek | ~5,000,000 ns | ~15,000,000 | ~2 months |

Read the right-hand column again. If an L1 hit were one second, going to DRAM is a coffee break, and touching disk is a **day off**. The reason your slow Python loop is slow is very often that it is taking coffee breaks it did not have to.

**The key move: how do you measure the latency of a *single dependent load* when a load is under a nanosecond and your clock has ~20 ns resolution?** You cannot time one. You time a hundred million of them **chained so each load's address depends on the previous load's result** — a *pointer chase* around a random cycle. Because load `k+1` cannot begin until load `k` returns, the CPU cannot overlap them; you measure true latency, not throughput. Vary the size of the region you chase through, and the average latency *steps up* every time the working set outgrows a cache level. You will see the ladder.

```c
/* WORKED EXAMPLE (also the core of Lab M04-A).
   Chase a random single-cycle permutation and report ns per dependent load. */
#include <stdlib.h>
#include "hz.h"

/* Wire `next[]` into ONE random Hamiltonian cycle over n slots. */
static void make_ring(size_t *next, size_t n) {
    size_t *perm = malloc(n * sizeof(size_t));
    for (size_t i = 0; i < n; i++) perm[i] = i;
    for (size_t i = n - 1; i > 0; i--) {      /* Fisher–Yates */
        size_t j = (size_t)rand() % (i + 1);
        size_t t = perm[i]; perm[i] = perm[j]; perm[j] = t;
    }
    for (size_t i = 0; i < n; i++)            /* single cycle: perm[i]->perm[i+1] */
        next[perm[i]] = perm[(i + 1) % n];
    free(perm);
}

static double chase_ns_per_load(size_t working_bytes) {
    size_t n = working_bytes / sizeof(size_t);
    size_t *next = malloc(n * sizeof(size_t));
    make_ring(next, n);

    size_t idx = 0, steps = 100u * 1000u * 1000u;   /* 100M dependent loads */
    for (size_t s = 0; s < n; s++) idx = next[idx];  /* warm-up (untimed) */

    double t0 = hz_now_ns();
    for (size_t s = 0; s < steps; s++) idx = next[idx];
    double t1 = hz_now_ns();

    hz_sink_u64((uint64_t)idx);                      /* keep the loop alive */
    free(next);
    return (t1 - t0) / (double)steps;
}
```

> **Laptop caution — peak footprint is ~2× the working set.** `make_ring` holds `next[]` *and* the temporary `perm[]` at the same time, so at the 256 MB working set the peak allocation is **~512 MB** (both freed before the timed chase, but live during setup). On a memory-tight laptop that setup can trigger swapping, and a swap-inflated setup or a swap-contended chase reads as a falsely huge "DRAM plateau." If your top size is near your free RAM, cap the sweep (e.g. stop at 128 MB) or free `perm[]` conceptually by generating the cycle without a full permutation buffer — do not mistake swap for the memory wall.

Run it for `working_bytes` sweeping from 8 KB (fits L1) to 256 MB (deep in DRAM) and you get numbers like: **~1.0 ns** while you fit in L1, a step to **~4 ns** past L2's size, **~15 ns** past L3's size, and a plateau near **~90 ns** once you are firmly in DRAM. The step *locations* are your cache sizes. The step *heights* are the ladder above. You just measured the pyramid.

> **Named misconception 1 — "Array indexing is constant time."** It is constant *instruction count* and wildly variable *time*. `a[i]` costs 1 ns or 90 ns depending only on whether `a[i]`'s cache line is resident. Big-O hides the constant, and here the constant spans 90×. In this module Big-O is not the tool; **the latency ladder is.**

### Lesson 2 — The cache line is 64 bytes, and it is why your loop order matters more than your loop body

**Descend.** The hardware never moves one byte. When you touch `a[i]`, the CPU pulls the entire **64-byte cache line** containing it — on typical x86, that is 8 doubles or 16 `int`s — into L1. This is a *bet* the hardware makes on your behalf: *you asked for one, you'll probably want its neighbors.* This bet is called **spatial locality**, and your access pattern either collects on it or pays for it.

Consider two functions that do **byte-for-byte identical arithmetic** — same number of adds, same data, same result — differing only in the **order** they walk an `n×n` matrix stored row-major (C's layout, the M03 layout: element `[i][j]` at `i*n + j`):

```c
/* WORKED EXAMPLE (the heart of Lab M04-B). Identical FLOPs, opposite locality. */
double sum_rowmajor(const double *a, size_t n) {   /* walks memory in order */
    double s = 0.0;
    for (size_t i = 0; i < n; i++)
        for (size_t j = 0; j < n; j++)
            s += a[i*n + j];        /* stride 8 bytes: 8 hits per line fetched */
    return s;
}
double sum_colmajor(const double *a, size_t n) {   /* jumps by a whole row */
    double s = 0.0;
    for (size_t j = 0; j < n; j++)
        for (size_t i = 0; i < n; i++)
            s += a[i*n + j];        /* stride n*8 bytes: 1 use per line fetched */
    return s;
}
```

`sum_rowmajor` marches through memory address-order: it fetches a 64-byte line and *uses all 8 doubles in it* before moving on — 1 memory fetch amortized over 8 adds. `sum_colmajor` jumps `n*8` bytes each step; for a large `n` **every single access lands on a fresh line**, uses one of its 8 doubles, and (once the matrix exceeds cache) evicts it before the column comes back around. Same adds. **8× more lines fetched**, and once you blow past L3, those fetches are ~90 ns DRAM trips.

Measured on a 4096×4096 matrix of doubles (128 MB, far bigger than any cache), representative result:

| Function | Wall time | cachegrind LL miss rate (`DLmr`) | Adds performed |
|---|---|---|---|
| `sum_rowmajor` | ~45 ms | ~0.8% | 16,777,216 |
| `sum_colmajor` | ~380 ms | ~11% | 16,777,216 |

Roughly **8× slower for the identical computation.** Not because it did more work — because it *asked the memory system to haul 8× the bytes.* The `cachegrind` column is the proof that it is a memory story and not a compiler-vectorization story: the slow one *misses* far more.

**Re-ascend the connection to M03.** This is the same fact that made struct-of-arrays beat array-of-structs in Lab M03-C. SoA put the field you sum contiguously so one line fetch served many elements; AoS interleaved it with fields you did not touch, so each line fetch was mostly waste. **Padding, alignment, SoA/AoS, and row/column order are all one phenomenon: are the bytes you fetch the bytes you use?** And it is the reason NumPy has `order='C'` vs `order='F'` and exposes `.strides` — an array's *shape* is a promise about arithmetic; its *strides* are a promise about locality, and Lesson 4's re-ascent will show you paying for the wrong one in Python.

> **Named misconception 2 — "Fewer operations means faster; count the FLOPs."** Two functions with *identical* FLOP counts here differ 8×. On the memory-bound side of the world, the operation count is nearly irrelevant and the **access pattern is the cost model.** A learner who predicts these two run "about the same, they do the same math" is holding the exact wrong model, and Lab M04-B is built to detonate it.

### Lesson 3 — Stride, prefetching, and the cliff you can locate to the byte

**Descend.** Lesson 2 compared two access patterns. Lesson 3 turns access pattern into a **continuous knob** — the *stride* — and finds the exact place the machine falls off a cliff. Take a large `int` array and sum every `stride`-th element, holding the *number of accesses* fixed so only locality changes:

```c
/* WORKED EXAMPLE (core of Lab M04-C, part 1). Fixed access count, swept stride. */
static double time_stride(int *a, size_t n_elems, size_t stride) {
    size_t touches = 4u * 1000u * 1000u;   /* fixed work regardless of stride */
    long acc = 0; size_t i = 0;
    for (size_t k = 0; k < n_elems/stride; k++) acc += a[(k*stride) % n_elems]; /* warm */
    double t0 = hz_now_ns();
    for (size_t k = 0; k < touches; k++) {
        acc += a[i];
        i += stride; if (i >= n_elems) i -= n_elems;   /* wrap */
    }
    double t1 = hz_now_ns();
    hz_sink_u64((uint64_t)acc);
    return (t1 - t0) / (double)touches;                /* ns per access */
}
```

Sweep `stride` over 1, 2, 4, 8, 16, 32, 64, 128 (in `int`s) on an array far larger than L3. The per-access time is **flat and cheap** while stride ≤ 16 ints, then **rises and plateaus** once stride ≥ 16. Why exactly 16? A cache line is 64 bytes; an `int` is 4 bytes; **64/4 = 16**. At stride < 16, several of your accesses share a line, so the line's cost is amortized. At stride ≥ 16, **each access lands on its own line** — no sharing left to exploit — and you pay a full miss per access. The cliff is at stride = (cache line)/(element size), and you can predict it *to the byte* from two numbers you can look up. That is the module's whole thesis in one benchmark: the hardware's behavior is not mysterious, it is arithmetic.

There is a second actor: the **hardware prefetcher**. The CPU watches your access stream, and if it detects a simple pattern — *sequential*, or a small *constant stride* — it fetches lines *ahead of your demand*, hiding latency. This is why sequential (`sum_rowmajor`) is even faster than "1 miss per 8 accesses" would predict, and why the pointer chase in Lesson 1 deliberately uses a **random** cycle: randomness is how you *defeat* the prefetcher to measure true latency. Predictable patterns get help; unpredictable ones (linked lists, hash probes, sparse-gather, embedding lookups) get none.

> **Named misconception 3 — "A bigger cache fixes it."** Cache helps only to the extent your working set *fits* and your access pattern *reuses*. A pure streaming pass over data larger than any cache gets **zero** benefit from a 2× bigger L3 — you touch each line exactly once and evict it; there is nothing to reuse. A random pointer chase over 256 MB is bounded by DRAM latency no matter how big the cache. "Add cache" is not a universal fix; **reshape the access pattern** is. This is precisely why GPUs did *not* win by having bigger caches — they win with enormous *bandwidth* (Lesson 4), and it is why the industry's "more compute" reflex misses the constraint.

### Lesson 4 — Bandwidth vs latency, arithmetic intensity, and why "training is memory-bound"

**Descend, then re-ascend.** Lessons 1–3 were about **latency** — how long *one* fetch takes when you cannot overlap it. But a well-behaved streaming loop *does* overlap: the prefetcher and multiple memory channels keep many fetches in flight, so what limits you is **bandwidth** — bytes per second the memory system can sustain, typically tens of GB/s on a desktop, ~1–3+ TB/s on a GPU's HBM. Latency is "how far to the store"; bandwidth is "how big the truck." Streaming code is truck-bound.

Measure bandwidth with a **STREAM-style triad**, `a[i] = b[i] + q*c[i]`:

```c
/* WORKED EXAMPLE (Lab M04-C, part 2). Sustained memory bandwidth. */
static void triad(double *a, const double *b, const double *c, double q, size_t n) {
    for (size_t i = 0; i < n; i++) a[i] = b[i] + q * c[i];
}
/* Bytes moved per iter (STREAM convention): read b, read c, write a = 3*8 = 24.
   GB/s = (24 * n) / (seconds * 1e9). Caveat: write-allocate makes real traffic
   ~32 bytes/iter because writing `a` first reads its line; report both. */
```

Now the concept that ties the whole course together: **arithmetic intensity (AI) = FLOPs performed ÷ bytes moved.** It tells you, before you run anything, whether a kernel is memory-bound or compute-bound.

- **Triad:** 2 FLOPs (one add, one multiply) per 24 bytes → **AI ≈ 0.083 FLOP/byte.** Deeply memory-bound. On a machine that can do, say, 100 GFLOP/s but only stream 20 GB/s, the memory ceiling is `20e9 * 0.083 ≈ 1.7 GFLOP/s` — you will hit **under 2%** of peak FLOPS no matter how fast the ALU is. The truck is the limit; the workers are idle.
- **Dense matmul (N×N):** ~`2N³` FLOPs over ~`3N²·8` bytes → AI grows like `N/12`. For large `N` this is **high** intensity → compute-bound, the one kernel that actually approaches peak FLOPS. This is why matmul is the workload accelerators are *designed to feast on*.

**This is the check M04 writes for the rest of the course.** A great deal of real ML is *not* big dense matmul: elementwise ops, activations, LayerNorm/RMSNorm, softmax, residual adds, embedding gathers, and attention over long sequences are all **low arithmetic intensity → memory-bound.** And even matmul, at inference with small batch, is bound by *streaming the weights* from memory once per token. So the headline "our accelerator does X petaFLOPS" describes the one corner (big compute-bound matmul) where you might approach the number, while your actual kernel — memory-bound — runs at a small fraction of it. **You can now prove which corner any kernel lives in with two numbers you compute on paper (its FLOPs and its bytes) before you ever run it.** That is the skill M06 (vectorize) and M07 (GPUs) assume.

**Re-ascent to Python (the payoff, previewed).** Everything above is visible from NumPy without writing C:

```python
import numpy as np, time
n = 4096
A = np.random.rand(n, n)          # C-contiguous (row-major), like Lesson 2
def timed(f, reps=5):
    f(); t = []                    # warm-up, then median of reps
    for _ in range(reps):
        s = time.perf_counter(); f(); t.append(time.perf_counter()-s)
    return sorted(t)[len(t)//2]
row = timed(lambda: A.sum(axis=1))   # sum along contiguous axis  -> cache-friendly
col = timed(lambda: A.sum(axis=0))   # sum across the stride       -> cache-hostile
print(row, col, col/row)             # col/row is materially > 1 on most machines
```

Same array, same total additions, different axis — and the ratio you measured in C reappears in Python. When M06 says "know why one line of NumPy is slow," *this* is the knowing. The metal stopped being a metaphor.

> **Named misconception 4 — "More FLOPS/GHz makes any workload faster; performance = compute."** For a memory-bound kernel, a faster ALU changes nothing — you were waiting on bytes, not on math. Doubling FLOPS on a triad-shaped kernel yields ~0% speedup; doubling *bandwidth* nearly doubles it. The learner who reaches for "get a faster/bigger chip" before asking "what is this kernel's arithmetic intensity?" is optimizing the wrong axis, and the assessment is built to catch exactly that reflex.

## Assessment

Maps to the course's **measurement labs (30%)** and **C implementation labs (35%)** weights. Gaming-resistance is the design constraint: the deliverable is a **judgment trail**, and the numbers alone cannot earn the marks.

### Component 1 — The three labs (predict artifacts + mechanism evidence)

Each lab is graded primarily on its **Predict sheet** and its **mechanism evidence** (cachegrind miss rates, plateau locations, AI classification), *not* on wall-clock beauty. A correct program with no prediction trail scores **below** a program with an imperfect measurement but an accurate, well-reasoned prediction of its own curve. You cannot pass by cloning fast code, because fast code with no committed-in-advance prediction earns almost nothing.

### Component 2 — The sealed module exam: *classify, predict, measure, intervene, re-measure*

You are handed an **unseen ~40-line C kernel** you have not benchmarked (e.g., a naive matrix transpose, a histogram with a scattered index array, or a linked-list sum). With **no runs yet**, you must:

1. **Classify** it memory-bound or compute-bound by computing its arithmetic intensity on paper (FLOPs and bytes, shown).
2. **Predict**, before running: its dominant bottleneck, the *direction* of its cache miss rate (high/low) and roughly where its bytes come from (which level of the ladder), and an order-of-magnitude wall time.
3. **Measure** with the harness + cachegrind and record actual numbers.
4. **Intervene:** propose exactly **one** change to its access pattern (not "use `-O3`", not "buy a bigger cache" — a *layout or traversal* change), and **predict its effect before applying it.**
5. **Re-measure** and reconcile: did your intervention move the metric you predicted? If not, why not?

**Why it cannot be gamed.** The kernel is unseen, so there is no code to copy. The marks live in steps 1, 2, and 4 — all committed **before** the corresponding measurement — so producing a fast final program without the predictions earns a failing grade. A learner who "just makes it fast" by trial and error, with no correct AI classification and no pre-registered prediction, **fails**, exactly as intended: the artifact being graded is the reasoning, and the reasoning is timestamped before its own confirmation.

### Rubric (gaming-resistant)

| Dimension | 0 — absent/wrong | 2 — partial | 4 — proficient | 6 — masterful |
|---|---|---|---|---|
| **Arithmetic-intensity classification** (exam step 1) | No AI computed, or memory/compute call is wrong | AI computed but bytes or FLOPs miscounted; call defensible | Correct AI and correct classification with the byte/FLOP arithmetic shown | Correct, and names *why* (which term dominates) and at what problem size the class would flip |
| **Pre-registered prediction quality** (labs + exam step 2) | Prediction missing, vague, or written after seeing results | Direction right (which is slower) but no mechanism (no line/stride/miss reasoning) | Mechanism-grounded prediction: cites cache line, cache sizes, prefetcher, or bandwidth by name | Predicts the *metric* (miss-rate direction, plateau location, GB/s) and nails location/direction, off only on magnitude |
| **Mechanism evidence, not just a stopwatch** | Only wall time; no cachegrind / no plateau / no bandwidth | Collected the mechanism metric but did not tie it to the prediction | Miss rate / plateau / bandwidth collected *and* explains the wall time | Uses two independent metrics (e.g., miss rate + bandwidth) that corroborate one story |
| **Intervention reasoning** (exam steps 4–5) | Change is "compile flag / bigger hardware" or unjustified | Plausible layout change but effect not predicted in advance | Layout/traversal change with a *pre-registered* predicted effect | Predicted effect confirmed by re-measurement, or a correct account of *why the prediction failed* |
| **Calibration & honesty** | Claims a match that the data does not show; hides the miss | Reports numbers but does not reconcile with prediction | Reconciles predicted vs measured, owns the misses | Treats a productive surprise (a wrong prediction that taught something) as a finding, states the corrected model |

**Passing** requires ≥ 4/6 on *both* "Arithmetic-intensity classification" and "Pre-registered prediction quality" — you cannot pass on measurements alone. A buggy or slow program with an accurate, mechanism-grounded, pre-registered prediction outscores a fast program with no judgment trail. **Right number, wrong (or absent) reasoning = zero on that dimension**, per the M03-C precedent.

## Elle pacing notes (signals for the adaptation runtime)

- **Wall — measurement noise reads as failure.** A learner on a shared/thermal-throttling machine sees plateaus that wobble or a factor of 5× instead of 8×, concludes "my benchmark is broken / I did it wrong," and stalls. This fires `struggle-blocked` fast and *looks* like a bug hunt. **Reroute:** do not debug the code; enforce the hygiene ritual — warm-up pass, median of ≥5, ≥50 ms per run, close other apps — and re-run. Teach that the *shape* (steps exist, hostile ≫ friendly) is the signal and the third sig-fig is not. Return to the lab once they trust the shape.
- **Wall — cache sizes / the ladder mapping.** Reading `lscpu` and translating "L2 = 512 KB" into "the plateau should start near a 512 KB working set" is a surprisingly common stall; it reads as struggle-blocked on Lab M04-A's Predict step. **Reroute:** one session of *drawing only* — no code — sketch the ladder, label each step with the learner's own cache sizes in bytes, before touching the benchmark. Same move as M03's boxes-and-arrows reroute for pointers.
- **Wall — cachegrind output overwhelms.** The `D1`/`LL`/`Dr`/`Dw` table is dense and the learner cannot find the miss rate that matters. **Reroute:** hand them one pre-annotated cachegrind dump with the `LLmiss%` line circled and the rest greyed, *before* asking them to read their own — mirrors M03's single-annotated-valgrind-example reroute.
- **Signal — "same math, so same speed" surprise is the lesson landing.** A learner who predicts `sum_rowmajor` and `sum_colmajor` run "about the same" (Misconception 2) and is shocked by 8× is **exactly on track** — that shock is Lesson 2 detonating the FLOP-counting model. Log `struggle-productive`, **never** `blocked`. Do not rescue the prediction before they commit it; the wrong prediction is the pedagogical payload.
- **Signal — predicting "compute-bound" for the triad.** Reaching for "more FLOPS makes it faster" on a memory-bound kernel (Misconception 4) is the productive error M04-C and the exam are built to surface. Let them predict it, measure the <2%-of-peak reality, and correct the model. This is the single most important belief-change in the module; treat the surprise as success.
- **Accelerate.** A learner who (a) runs a clean 3-plateau ladder on M04-A first try, (b) predicts M04-B's factor *and* miss-rate direction correctly, and (c) correctly classifies all three M04-C kernels by arithmetic intensity **may skip the M04-C build** and submit the AI classifications + the NumPy coda only — they have demonstrated the outcome and the hands-on triad adds little. They proceed to the sealed exam early.
- **Do not accelerate past the exam.** The classify→predict→intervene loop is the transferable skill M05–M07 assume; even a fast learner sits the exam.

## Three-tier reading — the memory hierarchy

- **Tier 1 — material ground (verifiable, measured this module).** The memory wall is a number, not a metaphor: an L1 hit is ~1 ns and a DRAM miss ~100 ns — a 50–100× gap you reproduced with a pointer chase. A cache line is 64 bytes, and the identical computation runs ~8× apart depending only on whether you walk memory in order (Lab M04-B, confirmed by cachegrind miss rates). Arithmetic intensity — FLOPs ÷ bytes — predicts *before you run* whether a kernel is memory-bound, and most real ML kernels (elementwise, normalization, softmax, embedding gather, attention over long context, small-batch inference streaming weights) are memory-bound, running at a small fraction of peak FLOPS. Moving a byte from DRAM costs on the order of 100× the *energy* of the arithmetic done on it. None of this is opinion; it is on your machine's stopwatch.
- **Tier 2 — what the field suppresses.** Accelerators are sold in FLOPS because FLOPS are advertisable and grow fast, and that headline suppresses that the binding constraint for most kernels is **memory bandwidth and the energy of data movement**, not arithmetic. "Just add more compute" and "just buy a bigger cache" are the reflexes; the roofline says both often buy ~nothing, because you were waiting on the truck, not the workers. The peak-FLOPS number describes the one corner — big dense matmul — where you might approach it, while your actual kernel lives in the memory-bound corner the spec sheet never mentions. The gap between advertised and achievable is structural, and no one selling silicon is paid to print the achievable number on the box.
- **Tier 3 — sit with this.** Moving a byte costs far more time and energy than computing on it — so most of what a data center bills, in watts and cooling water, is spent not thinking but *hauling*: the same weights shuttled past idle arithmetic units, again and again, data movement you never chose and cannot see from Python. Who decided a byte should be that expensive to move, who profits from the gap between advertised and achievable FLOPS — and on the day you finally optimize a kernel from memory-bound to compute-bound, whose watershed did you just stop spending?
