## Lessons

### Lesson 1 — What Python was hiding about a *value*: fixed-width types and the box of bytes

**The teaching.** In Python, `x = 10**40` just works. `int` is arbitrary-precision: the interpreter grows the object as needed and you never see a ceiling. That convenience hid a fact about the machine: **the CPU does not have arbitrary-precision integers. It has fixed-width registers.** When you write C, you choose the box:

| Type | Bytes (typical) | Range |
|---|---|---|
| `int8_t` / `uint8_t` | 1 | −128..127 / 0..255 |
| `int32_t` / `uint32_t` | 4 | ≈ ±2.1e9 / 0..4.29e9 |
| `int64_t` / `uint64_t` | 8 | ≈ ±9.2e18 / 0..1.8e19 |
| `int` | 4 (LP64) | implementation-defined "natural" int |
| `size_t` | 8 (64-bit) | unsigned, sizes/indices |

A C type is a **promise about bytes**: how many, and how to interpret them. `sizeof(T)` tells you the count; the signedness tells you the interpretation. The value does not grow to fit — when it runs off the end of the box, it **wraps** (for unsigned, this is defined modular arithmetic) or is **undefined behavior** (for signed overflow — the compiler is legally allowed to assume it never happens, which is its own trap).

**Worked example — the counter that forgets.**

```c
#include <stdio.h>
#include <stdint.h>

int main(void) {
    uint8_t count = 250;
    for (int i = 0; i < 10; i++) {
        printf("count = %u\n", count);
        count = count + 1;   // defined wrap for UNSIGNED: 255 -> 0
    }
    return 0;
}
```

Output:

```
count = 250
count = 251
count = 252
count = 253
count = 254
count = 255
count = 0      <-- the box overflowed; 256 does not fit in 8 bits
count = 1
count = 2
count = 3
```

`255 + 1` in an 8-bit unsigned box is `0`, not `256`. The high bit fell off the top of the world. In Python you would have gotten `256` and never noticed the machine underneath. This is the same arithmetic that, at 32 bits, turned the Boeing 787's generator-control counter into a shutdown after 248 days of uptime, and at 32-bit signed overflowed Unix time into 2038.

**Signed is worse than wrong — it is undefined.** Repeat the example with `int8_t count = 125;` incrementing past `127`. On most machines you will *see* it wrap to `-128` (two's complement), but the C standard says signed overflow is **undefined behavior**: the optimizer may assume `x + 1 > x` always holds and delete your overflow check entirely. Rule you carry forward: **if you need defined wrapping, use unsigned; never rely on signed overflow.**

**Named misconceptions:**

- **"An `int` is just a number, like in Python."** No — it is a fixed number of bytes. It has a ceiling and a floor, and stepping past them does not raise; it wraps or invokes undefined behavior. Numbers in math are unbounded; `int` is a box.
- **"Signed overflow wraps to negative, so I can rely on that."** In practice you often observe two's-complement wrap, but the *standard* makes signed overflow undefined, which means the compiler may optimize as if it cannot occur. Observed behavior ≠ guaranteed behavior. This is the first place "it ran fine" is not evidence.
- **"`sizeof` returns bits."** It returns *bytes*. `sizeof(int32_t) == 4`. And `sizeof` is evaluated at compile time — it is a property of the type, not a runtime measurement.

### Lesson 2 — Functions and the stack frame: pass-by-value, and the swap that does nothing

**The teaching.** When a C function is called, the machine pushes a **stack frame**: a contiguous slab of memory holding that call's parameters and local variables, plus bookkeeping (return address, saved frame pointer). Parameters are **copies** — C is strictly pass-by-value. The callee gets its own private duplicate of each argument's *value*. When the function returns, its frame is **destroyed** (the stack pointer moves back), the return value is copied out, and every local address inside that frame becomes meaningless.

Draw the stack growing downward. `main` has a frame; calling `f` stacks a new frame beneath it; `f` returning pops it.

```
higher addresses
  +------------------+
  | main's frame     |   x = 3   y = 7
  +------------------+
  | swap's frame     |   a = 3   b = 7   (COPIES of x, y)
  +------------------+  <- top of stack while swap runs; gone after it returns
lower addresses
```

**Worked example — the swap that swaps nothing.**

```c
#include <stdio.h>

void swap(int a, int b) {   // a and b are COPIES
    int t = a;
    a = b;
    b = t;                  // we swapped the copies, then threw them away
}

int main(void) {
    int x = 3, y = 7;
    swap(x, y);
    printf("%d %d\n", x, y);   // prints: 3 7   (NOT 7 3)
}
```

This is the single most clarifying failure in early C. Coming from Python — where `list.append` mutating through a shared reference *felt* like functions changing their arguments — the natural prediction is `7 3`. The machine prints `3 7`. The reason is not a bug; it is the definition: `swap` operated on its private copies `a`, `b` in its own frame, then that frame vanished. `x` and `y` in `main` were never touched. **To change a caller's variable, the callee needs the caller's *address*, not a copy of its value.** That is the doorway to Lesson 3.

**A second failure to plant now, harvest in Lesson 4 — returning a local's address:**

```c
int *make_answer(void) {
    int local = 42;
    return &local;      // returns the ADDRESS of a variable that is about to cease to exist
}
```

This compiles (with a warning we have promoted to an error via `-Werror`, which is the point). The address is real for exactly as long as the frame lives — which ends the instant `make_answer` returns. We name it here and dissect it in Lesson 4.

**Named misconceptions:**

- **"Functions can modify their arguments" (the Python hangover).** In Python, mutable objects passed in *can* be mutated because the name is a reference to a shared object. In C, a plain scalar parameter is a copy; mutating it is local and invisible to the caller. The illusion in Python was that names-are-references (pointers) all along.
- **"The local variable still exists after the function returns; I just can't name it."** No — its *storage* is reclaimed. The frame is popped. The address may still hold `42` for a moment out of sheer inertia (nothing overwrote it yet), which is exactly what makes this bug lie to you.
- **"Passing a big struct by value is the same as passing a reference."** By value means the whole thing is *copied* into the new frame — expensive for large structs, and mutations don't propagate. (Structs land in M03; flagged here so the value/reference distinction is clean.)

### Lesson 3 — Pointers: the central new idea (`&` gets the address, `*` goes to it)

**The teaching. This is the wall.** A **pointer** is a value whose content is an **address** — a location in memory — carried with a type that says how to read the bytes there. Two operators are the entire vocabulary:

- `&x` — **address-of**: "give me the address where `x` lives." Read `&` as *"address of."*
- `*p` — **dereference**: "go to the address in `p` and use the value there." Read `*p` as *"the thing at."*

They are near-inverses: `*(&x)` is `x`. But do not memorize them as an algebra of symbols — **draw them.** A pointer is a box that holds an arrow. `&x` fills the box with an arrow to `x`. `*p` follows the arrow.

```
   int x = 3;              int *p = &x;

   x: [ 3 ] @0x7ffd...a4        p: [ 0x7ffd...a4 ] ----> x:[ 3 ]
                                   (a box holding an arrow to x)

   *p        reads 3   (follow the arrow, read the box it points at)
   *p = 9    writes 9 INTO x   (follow the arrow, write there)  -> now x == 9
```

The type matters: `int *p` means "`p` points at an `int`," so `*p` reads 4 bytes and treats them as a signed integer. `char *c` reads 1 byte. The star in the *declaration* `int *p` is spelling out the type ("pointer to int"); the star in the *expression* `*p` is the dereference operation. Same character, two jobs — a real source of the wall. Say them differently in your head: declaration-star is "pointer-to," expression-star is "the-thing-at."

**Worked example — the swap that works.**

```c
#include <stdio.h>

void swap(int *a, int *b) {   // a, b are addresses of the caller's ints
    int t = *a;               // t = the thing at a  (the caller's x)
    *a = *b;                  // the thing at a  = the thing at b
    *b = t;                   // the thing at b  = old x
}

int main(void) {
    int x = 3, y = 7;
    swap(&x, &y);             // hand over the ADDRESSES of x and y
    printf("%d %d\n", x, y);  // prints: 7 3   -- it actually swapped
}
```

Trace it with the drawing. `swap` still gets copies — but copies *of the addresses*, not of the values. Following either arrow lands you back in `main`'s frame, at the real `x` and `y`. The frame boundary is no longer a wall to the data, because the pointer reaches across it. This is precisely what pass-by-value could not do, and it is *the* reason pointers exist.

**Worked example — reading `&` and `*` by printing addresses.**

```c
#include <stdio.h>

int main(void) {
    int x = 3;
    int *p = &x;
    printf("value of x      : %d\n", x);       // 3
    printf("address of x    : %p\n", (void*)&x);
    printf("value stored in p: %p\n", (void*)p);   // == &x
    printf("thing at p (*p) : %d\n", *p);      // 3
    *p = 99;
    printf("x after *p = 99 : %d\n", x);       // 99  -- we wrote through the pointer
}
```

`p` literally contains the same number that `&x` prints. That equality — *the pointer's value IS the address* — is the whole idea, made visible.

**Named misconceptions:**

- **"A pointer *is* the value it points to."** No. A pointer is the *address*. `p` and `*p` are different things: `p` is a location, `*p` is what lives there. Confusing them is the single most common early error, and drawing the box-with-an-arrow prevents it.
- **"`*` and `&` cancel, so I can sprinkle them until it compiles."** They are not interchangeable decorations. `&` produces an address (moves you *up* a level of indirection); `*` consumes an address (moves you *down*). Sprinkling to satisfy the compiler is the anti-pattern this module is built to kill — predict the level of indirection *before* you type.
- **"`int *p` and `int* p` and `int * p` mean different things."** Whitespace is irrelevant; all three declare `p` as pointer-to-int. But beware `int* a, b;` — this declares `a` as pointer-to-int and `b` as a plain `int`. The `*` binds to the *declarator*, not the type. Write `int *a, *b;` and you will never be surprised.
- **"A dereferenced pointer is safe if the code compiles."** Dereferencing NULL, an uninitialized pointer, or a pointer to a dead frame all compile fine and are all undefined behavior. Compilation proves syntax, never validity.

### Lesson 4 — Pointers, arrays, and the stack you can read: pointer arithmetic, out-parameters, and the dangling pointer you can predict

**The teaching.** An array in C is a contiguous run of elements. Its name, used in an expression, **decays** to a pointer to its first element — `arr` becomes `&arr[0]`. This is why you can pass an array to a function that takes a pointer. But an array is **not** a pointer: `sizeof(arr)` is the whole array's byte size where it is declared, while `sizeof(p)` is 8 (one pointer). The decay is a convenience, not an identity.

**Pointer arithmetic is typed.** `p + 1` does not add 1 byte — it adds `sizeof(*p)` bytes, advancing to the next element. For `int *p`, `p + 1` is 4 bytes further along. `p[i]` is defined as `*(p + i)`. So walking an array by incrementing a pointer and walking it by indexing are the same traversal spelled two ways:

```c
#include <stddef.h>

int sum_index(const int *a, size_t n) {   // const: promise not to write through a
    int s = 0;
    for (size_t i = 0; i < n; i++) s += a[i];     // a[i] == *(a + i)
    return s;
}

int sum_walk(const int *a, size_t n) {
    int s = 0;
    for (const int *q = a; q < a + n; q++) s += *q;  // move the pointer, read the thing at it
    return s;
}
```

Both return the same sum; `q` marches in 4-byte steps from `a` to `a + n` (one-past-the-end, which is legal to *form* but not to dereference).

**Out-parameters: giving a function somewhere to put an answer.** C functions return one value. To return several — or to fill in a result the caller owns — you pass the *address* of the caller's variable and write through it. This is the everyday use of pointers, far more common than swap:

```c
// Returns min, max, and sum of a[0..n) via out-parameters. Returns 0 on success, -1 if n==0.
int stats(const int *a, size_t n, int *min_out, int *max_out, long *sum_out) {
    if (n == 0) return -1;               // nothing to compute; don't touch the outputs
    int mn = a[0], mx = a[0];
    long total = 0;
    for (size_t i = 0; i < n; i++) {
        if (a[i] < mn) mn = a[i];
        if (a[i] > mx) mx = a[i];
        total += a[i];
    }
    *min_out = mn;                        // write the answer into the caller's box
    *max_out = mx;
    *sum_out = total;
    return 0;
}
```

The caller:

```c
int data[] = {4, -1, 9, 2, 9, -6};
int mn, mx; long total;
if (stats(data, 6, &mn, &mx, &total) == 0)
    printf("min=%d max=%d sum=%ld\n", mn, mx, total);  // min=-6 max=9 sum=17
```

Note `long total` — the sum of many `int`s can overflow an `int` box (Lesson 1 returns), so the accumulator is wider than the elements.

**The dangling pointer, now dissected — and predictable.** Harvest the seed from Lesson 2:

```c
#include <stdio.h>

int *make_answer(void) {
    int local = 42;
    return &local;        // address of a variable in THIS frame
}                          // <- frame popped here; local's storage reclaimed

int main(void) {
    int *p = make_answer();   // p now holds an address into a DEAD frame
    printf("%d\n", *p);       // undefined behavior: often prints 42, sometimes garbage
    printf("%d\n", foo());    // calling anything reuses that stack space...
    printf("%d\n", *p);       // ...now *p is much more likely to be garbage
}
```

You can **read this bug to its line before running it.** The rule: *a pointer must never outlive the storage it points to.* `local` lives in `make_answer`'s frame; that frame dies on return; therefore `p` is dangling the instant `make_answer` returns. The treachery — and the reason prediction is graded, not crashes — is that the first `*p` frequently prints `42`, because nothing has overwritten that stack slot *yet*. It is stale-but-plausible. It will not reliably crash. (Contrast with dereferencing NULL, which faults on essentially every run.) This is the exact shape of the M03 use-after-free, met one level up, with no heap required.

**Named misconceptions:**

- **"An array is a pointer."** An array *decays* to a pointer in most expressions, but it is not one: `sizeof(arr)` ≠ `sizeof(int*)`, and `&arr` has a different type than `&arr[0]` (pointer-to-array vs pointer-to-int) even though they print the same address.
- **"`p + 1` moves one byte."** It moves one *element* — `sizeof(*p)` bytes. Pointer arithmetic is scaled by the pointed-to type. Forgetting this produces reads at the wrong stride.
- **"A returned pointer to a local is fine because it printed the right value."** The right value is the bug's disguise. The storage is dead; the correct print is luck that ends the moment another call reuses the slot. "It printed 42" is the opposite of evidence here.
- **"`const int *a` means the pointer can't change."** It means you can't write *through* it (`*a = x` is illegal), but you can repoint `a` itself. The other spelling, `int *const a`, is the reverse. Read declarations right-to-left: `const int *a` = "`a` is a pointer to a const int."

### Lab M02-B — Break pointers on purpose (predict behavior, grade the prediction)

**Goal.** Build the discipline that "it ran" is not evidence. You are handed four small stack-only programs, each with a planted pointer defect. You **predict the behavior of each before running**, then run, then reconcile. **The grade is on the prediction and its reasoning, not on whether the program crashes.**

For each program, your Predict sheet must state: (a) does it compile? (b) if it runs, what does it print? (c) does it crash — and crucially, does it crash **reliably** (every run) or **unreliably** (sometimes)? (d) one-sentence mechanism.

**Program 1 — dangling pointer to a dead frame.**

```c

static int noise(void) { int junk[8]; for (int i=0;i<8;i++) junk[i]=i*7; return junk[3]; }

int main(void) {
    int *p = make_answer();
    printf("first  read: %d\n", *p);      // ?
    noise();                              // reuse the stack slot
    printf("second read: %d\n", *p);      // ?
    return 0;
}
```

*Expected prediction:* compiles (with a warning we've made fatal — so actually `-Werror` **rejects** it; note this as the compiler catching you). If forced to run, the first read *often* prints 42 (stale-but-plausible), the second is *likely garbage* after `noise` reused the frame. **Does not crash reliably.** Mechanism: `p` outlives `local`'s storage.

**Program 2 — dereference NULL.**

```c
#include <stdio.h>
int main(void) { int *p = NULL; printf("%d\n", *p); return 0; }
```

*Expected prediction:* compiles cleanly. **Crashes reliably** (segfault) on every mainstream OS — address 0 is unmapped. This is the *reliable* end of the spectrum; contrast with Program 1.

**Program 3 — wrong level of indirection (the compiler saves you).**

```c
#include <stdio.h>
void set(int *out) { *out = 99; }
int main(void) { int x = 0; set(x); printf("%d\n", x); return 0; }
```

*Expected prediction:* **does not compile** — `set` wants `int*`, got `int`. `-Werror` (and the type system) rejects it. Fix is `set(&x)`. Mechanism: passing a value where an address is required is a type error, not a runtime one.

**Program 4 — uninitialized pointer.**

```c
#include <stdio.h>
int main(void) { int *p; *p = 5; printf("done\n"); return 0; }
```

*Expected prediction:* compiles with a warning (`p` used uninitialized) → fatal under `-Werror`. If forced to run, `p` holds whatever garbage was on the stack; `*p = 5` writes to a random address — **crashes unreliably** (segfault if the garbage address is unmapped, silent corruption if it happens to be a mapped-but-wrong location). Mechanism: an uninitialized pointer is not NULL; it is *arbitrary*.

    long total = 0;
    for (size_t i = 0; i < n; i++) {
        if (a[i] < mn) mn = a[i];
        if (a[i] > mx) mx = a[i];
        total += a[i];
    }
    *min_out = mn; *max_out = mx; *sum_out = total;
    return 0;
}
```

**Verify.** `make run` prints the walking pointer's addresses (the demo `main` `printf`s each `q`). Confirm the step is exactly `sizeof(int) == 4` bytes and the addresses are your predicted `A, A+4, A+8, ...`. Confirm `min=-6 max=9 sum=17`. If your address prediction used a step of 1, write the correction: *pointer arithmetic scales by the element type.*

**Test sketch (`make test`).**

    int d[] = {4, -1, 9, 2, 9, -6};

}
```

**Integrate.** Two sentences: why the accumulator is `long` not `int` (tie to Lesson 1 overflow), and why the `n == 0` guard writes *nothing* to the outputs (a caller may pass sentinels it expects untouched — the pointer gives you write access, and restraint is part of the contract).

## Assessment

The assessment is **gaming-resistant by construction**: the passing bar is the *judgment trail*, not a green test run. A learner cannot pass by producing a program that compiles and prints plausible output, because several graded items *do exactly that while being wrong*.

### Component 1 — Lab Predict sheets (30%)

Submitted **before** each lab's Build. Graded on: were predictions committed in writing before code; where the machine contradicted the prediction, is there a written revision with a correct mechanism. **A correct prediction with wrong reasoning scores below an incorrect prediction with sound reasoning that was then correctly revised** — because the outcome we are certifying is *modeling the machine*, not guessing.

### Component 2 — Module exam: read a stack bug before running it (55%)

You are handed an **unseen ~35-line C program** that compiles and runs and prints a plausible number, but contains **one planted pointer/stack defect** (drawn from: returned pointer to a local, wrong indirection level that still type-checks via a `void*` or cast, off-by-one one-past-the-end dereference, or an out-parameter written under a failure path). Time-boxed, in this order, and **the order is graded**:

1. **Predict (before running):** state what the program will print and whether it is correct; identify the defect **by reading**, cite the line, and state whether it will crash *reliably* or *lie*.
2. **Locate:** point to the exact line and explain the lifetime/indirection violation in one or two sentences.
3. **Fix:** minimal correct change.
4. **Prove:** run the provided test; for a non-crashing bug, explain what observable *other than a crash* distinguishes the buggy from the fixed version (e.g., the value changes after an intervening call).

Submitting a fix without the prediction caps this component at 40% — because a fix found by trial-and-error is exactly the skill this course exists to *replace*.

### Component 3 — Boxes-and-arrows viva (15%)

A 5-minute oral/whiteboard: draw the stack for a given two-function program, place every pointer as a box-holding-an-arrow, and answer "what does `*p` read *here*, and is it valid?" This certifies the mental model directly, independent of syntax fluency — you cannot bluff a drawing.

## Three-tier reading — pointers, the stack, and the address you were never shown

**Tier 1 — Material ground (verifiable facts).** A pointer is a value: the numeric address of a byte in memory, held in one machine word (8 bytes on a 64-bit CPU) and typed so the machine knows how many bytes to read and how to read them. You can check every claim in this module at the keyboard: `sizeof(int*)` prints 8; `&x` prints x's address and `p == &x` after `int *p = &x`; a plain `swap(int,int)` provably cannot change its caller's variables while `swap(int*,int*)` provably can; the call stack is real and finite, and unbounded recursion aborts the process with a stack overflow. Two failures anchor the module because they sit at opposite ends of a spectrum: dereferencing NULL **faults reliably** on every mainstream OS, while dereferencing a pointer to a returned-from local is **undefined behavior that usually returns a stale-but-plausible value** and only later decays to garbage. Both compile. Neither is opinion.

**Tier 2 — What the field suppresses.** Two opposite distortions, each hiding the same truth. The booster distortion — "pointers are legacy pain, modern languages freed you" — suppresses that **every Python name, every Java object handle, every JavaScript reference *is* a pointer** with the address hidden: `a = b; a.append(x)` mutating `b` is pointer aliasing you have been doing since AIE-101 without being shown the address. The abstraction did not delete the pointer; it deleted your *view* of it. The traditionalist distortion — pointer arithmetic as a rite of passage, the `*`/`&` syntax as an intelligence filter — suppresses that the idea is a box and an arrow a child can draw, and that the *syntax*, not the concept, is the entire wall. Both camps avoid the honest middle: the reference semantics you rely on every day are pointers that **someone else's C dereferences for you, correctly, millions of times** — CPython, the JVM, V8 — and the safety is real but **borrowed**. The NULL checks you never wrote are running; they are just written in a language the boosters told you that you'd never need to read.

**Tier 3 — Sit with this (a question you cannot unknow).** You have written `a = b` a thousand times and then watched a mutation "leak" from `a` into `b` — that was a pointer, an address the language refused to print for you. Now that you can finally see it with `&` and read through it with `*`: when you eventually ship a model whose serving loop dereferences a config that some upstream call left NULL, the machine will not raise a friendly typed exception — it will hand you a segfault, or worse, a plausible wrong number that passes your tests. **Who decided the address should stay invisible to you right up until the moment it kills your process — and does hiding it actually make the system safer, or does it only remove your ability to see the failure coming while someone else's C quietly absorbs the risk on your behalf?**
