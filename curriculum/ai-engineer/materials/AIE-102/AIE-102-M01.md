### Lesson 1 — What Python was hiding: memory

#### Teaching text

In AIE-101 you wrote `x = 3` a thousand times and never once asked what it cost. The mental picture almost everyone carries is: *there is a little box called `x`, and the number 3 is sitting in it.* That picture is wrong in a way that will matter for the rest of your career.

In CPython, `x = 3` does this: somewhere on the **heap** there is an object — a `PyLongObject` — that contains a **reference count**, a **pointer to its type** (`int`), a **size field**, and finally the actual digits of the number. The name `x` does not hold `3`. It holds a **pointer** to that object. The number 3 is not in a box called `x`; `x` is a signpost pointing at a 28-byte structure that lives somewhere else entirely.

We can weigh it:

```python
import sys
sys.getsizeof(0)        # 28  — the number ZERO costs 28 bytes
sys.getsizeof(1)        # 28
sys.getsizeof(2**30)    # 32  — bigger number, one more 4-byte digit
sys.getsizeof(2**60)    # 36
sys.getsizeof(2**120)   # 44  — Python ints are arbitrary-precision; they grow
```

A C `int` is 4 bytes and holds a fixed range. A Python int for the value 0 is **28 bytes** and can grow without bound — because it is carrying a reference count, a type pointer, and length metadata everywhere it goes. That overhead is the price of "you never have to think about integer overflow." You just paid it; you simply weren't shown the receipt.

Now the list. `[1, 2, 3]` in Python is **not** three integers laid end to end in memory. It is a `PyListObject` — a header plus a heap-allocated array of **pointers** — and each pointer aims at a *separate* int object living elsewhere.

```python
sys.getsizeof([])          # 56  — empty list, all header/bookkeeping
sys.getsizeof([1, 2, 3])   # 88  — header + room for pointers (over-allocated)
sys.getsizeof(list(range(1000)))  # 8056 — ~8 bytes per element, just for the POINTERS
```

That 8056 bytes is only the pointer array. The thousand int objects it points at are *additional* memory somewhere else. In C, `int a[1000]` is 4000 contiguous bytes and nothing else. Python's list of 1000 ints is 8056 bytes of pointers **plus** up to a thousand 28-byte objects — well over 30 KB to hold what C holds in 4 KB, scattered across the heap instead of sitting in one cache-friendly block. (Why "scattered" will cost you dearly is M04's whole story; plant the flag now.)

One more thing the abstraction hides: some objects are **shared**. CPython keeps a cache of the small integers −5 through 256 as permanent singletons. So two "different" 100s are the *same object*, but two 257s are not:

```python
a = int("100"); b = int("100"); a is b   # True  — both point at the cached 100
a = int("257"); b = int("257"); a is b   # False — two separate 257 objects
```

(We use `int("100")` rather than the literal `100` so the compiler's constant-folding doesn't hide the effect. `is` asks "same object?"; `==` asks "same value?" — the descent begins the moment you notice those are different questions.)

#### Worked example — draw the picture, then check it

Take `nums = [10, 20, 10]`. Before running anything, draw it: one box for the list object, arrows out to int objects. How many *distinct* int objects exist?

Naively you'd say three. But 10 and 20 are both in the small-int cache, and the two 10s are the *same* cached object. So there are **two** distinct int objects, and the list holds three pointers — two of which are identical:

```python
nums = [10, 20, 10]
id(nums[0]) == id(nums[2])   # True  — same cached 10
id(nums[0]) == id(nums[1])   # False
[hex(id(n)) for n in nums]   # two of the three addresses match
```

The list is an array of *pointers*, and pointers can alias. You now know something about `[10, 20, 10]` that a Python-only programmer can go years without knowing.

#### Misconceptions to surface (name them out loud)

- **"A variable holds its value."** No — a name holds a *pointer* to a heap object. This is the single most load-bearing correction in the module. Surface it by asking the learner to predict `a = [1]; b = a; b.append(2); print(a)` and watch `a` change too.
- **"A list stores its numbers."** No — it stores pointers to number objects that live elsewhere. Surface it with the 8056-byte measurement: the list is *bigger* than the raw numbers would be in C, yet doesn't even contain them.
- **"Equal numbers are the same object."** True only inside the −5..256 cache. Surface it with the `int("257")` vs `int("100")` pair — the learner who predicted "always True" just learned the cache exists.

### Lesson 2 — What Python was hiding: types

#### Teaching text

Here is the innocent line `c = a + b`. In C, if `a` and `b` are declared `int`, the compiler already knows their types, so this compiles to a **single machine instruction**: `ADD`. There is nothing to decide at runtime.

In Python, at the moment `a + b` runs, the interpreter knows *nothing* about the types yet. It must, every single time:

1. Look up what object `a` currently points to and find its type.
2. Ask that type: "do you define addition?" (find the `__add__` slot).
3. Call that C function, which checks `b`'s type too.
4. Compute the result — and because ints are **immutable**, *allocate a brand-new int object* to hold it (that's a fresh 28-byte heap allocation).
5. Adjust reference counts on everything involved.

That is the price of dynamic typing: the types live on the *objects*, not on the *variables*, so they can only be discovered at runtime, on every operation, forever. C decides types once, at compile time, and then forgets about them. Python re-derives them on every `+`.

This is why type *annotations* don't make Python faster:

```python
def add(a: int, b: int) -> int:
    return a + b
```

The `: int` here is **ignored at runtime** — it is documentation for humans and type-checkers, not an instruction to the interpreter. `a + b` does the exact same runtime type-hunt whether or not you annotated. We will prove this with `dis` in Lab M01-C: the bytecode is byte-for-byte identical.

#### Worked example — the receipt for one `+=`

```python
import dis
dis.dis(compile("s += x", "<demo>", "exec"))
```

```
LOAD_NAME    0 (s)     # go find what name 's' points to
LOAD_NAME    1 (x)     # go find what name 'x' points to
BINARY_OP   13 (+=)    # dispatch on s's type, find __iadd__/__add__, call it,
                       #   ALLOCATE a new int for the result
STORE_NAME   0 (s)     # rebind 's' to the new object
```

Four bytecode operations, each of which is a call into C, plus one heap allocation, to do what C does in a single `ADD`. And this runs *once per loop iteration*. Multiply by a million and you can feel where the time went — which is exactly Lesson 3.

#### Misconceptions to surface

- **"Adding `: int` annotations speeds up my code."** No — annotations are ignored at runtime. Surface it with the identical `dis` output (Lab M01-C). This misconception is *extremely* sticky; let the disassembly settle it, not your assertion.
- **"Python has no types / is untyped."** No — Python is dynamically *and strongly* typed. The types are real; they just live on objects and are checked at runtime, not declared on variables at compile time. Surface it with `TypeError: 'int' + 'str'` — the type check is very much happening, just late.
- **"`+` is `+`."** No — `+` is a runtime dispatch to whatever `__add__` the left operand's type provides. `[1]+[2]`, `"a"+"b"`, and `1+2` are three different C functions selected at runtime.

### Lesson 3 — What Python was hiding: execution

#### Teaching text

C is compiled to **machine code**: the CPU runs your program's instructions directly. Python is not. CPython compiles your source to **bytecode** — a compact instruction set for a *virtual* machine — and then a big loop written in C (the "eval loop," `ceval.c`) reads those bytecodes one at a time and does what each one says. Between your `s += x` and the CPU's `ADD` there is an entire software interpreter, spending machine instructions just to *decide which machine instructions to run*. That decision cost, paid per bytecode, is the interpreter overhead.

You can see the bytecode for any code object with `dis`, and you can see the loop's shape:

```python
import dis
dis.dis(compile("for x in data: s += x", "<loop>", "exec"))
```

The loop body dispatches roughly: `FOR_ITER`, `STORE_NAME`, `LOAD_NAME`, `LOAD_NAME`, `BINARY_OP`, `JUMP` — about six bytecodes **per iteration**, each one a trip through the C interpreter loop (fetch the bytecode, jump to its handler, do the work, come back), plus the int allocation from Lesson 2, plus reference-count bookkeeping. Tens to hundreds of machine instructions to accomplish one integer addition.

Now measure it. Summing one million integers:

```python
import timeit
setup = "data = list(range(1_000_000))"
timeit.timeit("s=0\nfor x in data: s+=x", setup=setup, number=5) / 5
# ~0.034 s  → 34 ms  → ~34 nanoseconds per addition
```

34 nanoseconds per add. On a ~3 GHz machine that's roughly **100 CPU cycles to add two numbers** — work the hardware can do in *one* cycle. The other ~99 cycles are the interpreter loop, the type dispatch, the allocation, and the refcounting. That factor of ~100 is not a bug and not a slow computer. It is the standing cost of the abstraction, and it is *always there*, on every pure-Python numeric loop you will ever write.

One preview for M05: this eval loop runs **one bytecode at a time, in one thread at a time**, guarded by the Global Interpreter Lock (the GIL). That is why adding threads to a CPU-bound Python loop doesn't speed it up. We're not ready to explain it — just notice that the same "one interpreter, stepping through bytecode" picture is about to explain that too.

#### Worked example — the ladder, first rung

Same million-integer sum, three ways, measured on the authoring machine:

| How | Time | Per-add | Why |
|---|---|---|---|
| Pure `for` loop with `+=` | ~34 ms | ~34 ns | full interpreter tax per element |
| Built-in `sum(data)` | ~7 ms | ~7 ns | the loop runs in C inside `sum`; still boxes each int |
| NumPy `arr.sum()` *(preview)* | ~1 ms | ~1 ns | no per-element Python objects at all; a tight C loop over raw bytes |

Same arithmetic. Same answer. A **30x+ spread**, entirely explained by *how much interpreter, how many objects, how much dispatch* sits between the code and the CPU. `sum()` is faster because its loop is C, not Python — but it still walks a list of pointers to boxed int objects. NumPy is faster still because there are no Python int objects at all: just a contiguous block of raw 8-byte integers and a C loop that adds them. Every rung down the ladder removes a layer of what Python was hiding.

#### Misconceptions to surface

- **"Python is compiled to machine code, like C."** No — it's compiled to *bytecode* for a virtual machine, then interpreted. Surface it by showing `dis` output (bytecode) and contrasting with the idea of an assembly listing.
- **"The `.pyc` file is machine code / a real speedup."** No — `.pyc` is cached *bytecode*; it skips re-parsing, not interpreting. The interpreter loop runs identically.
- **"`sum()` is fast because it's a clever algorithm."** No — it's the same O(n) addition; it's faster because the *loop itself* runs in C instead of in the bytecode interpreter. The speed is about the substrate, not the algorithm.

### Lesson 4 — Why descend: the bill, and the map

#### Teaching text

Put the three lessons together on one line of code you've written a hundred times:

```python
total = 0
for x in data:
    total += x
```

You now know what that costs, and *why*: each iteration pays the **interpreter** tax (Lesson 3), pays the **type dispatch** tax on `+=` (Lesson 2), and **allocates a fresh int object** while walking a list of **pointers to scattered objects** (Lesson 1). Three hidden costs, one innocent loop, a measured 30x you could recover by descending — and you could not even *name* those costs a week ago.

So why go to C, a language you may never ship to production? Not for nostalgia, and not because "real programmers use C." The reason is this: **the fast substrate you already depend on is C.** CPython is C. NumPy's inner loops are C. PyTorch's kernels are C and CUDA. The kernel your model runs on is C. When you write `arr.sum()` and it's 30x faster, you did not escape the machine — you *borrowed someone else's descent*. They went down to C so you wouldn't have to look. The entire re-ascent of this course (M06: fast Python because you know the metal) is impossible until the machine stops being a metaphor, and the only way to stop it being a metaphor is to build the thing by hand, once, in the substrate. That is M02 and M03.

**The course map, so the descent has a shape:**

- **M01 (here)** — see what Python hides. *Trailhead.*
- **M02** — C: values, types, pointers, the stack. *The pointer becomes real.*
- **M03** — C: the heap, `malloc`/`free`, structs, the segfault. *The bottom. You own the memory now.*
- **M04** — the memory hierarchy, measured. *Why "scattered" costs 30x.*
- **M05** — back up: what a Python object *really* is (refcounts, the GIL). *Everything in M01, now explained from the C side.*
- **M06** — the re-ascent: fast Python because you know the metal. *You command NumPy instead of cargo-culting it.*
- **M07** — GPUs: why they exist, what they cost, when they pay.

Every rung you saw on the ladder in Lesson 3 is a module. You are not learning C. You are learning to see the cost of every line you write — and C is the only place the cost is visible.

#### Worked example — measure your own ladder

Before you believe any of the numbers above, reproduce the spread on *your* machine (Lab M01-B). The lesson is not "it's 30x"; the lesson is "there is a large, systematic, explainable spread, and I can now say where every factor of it comes from." A learner who can look at a slow loop and say *"that's the interpreter tax plus per-element allocation; vectorizing removes both"* has already re-ascended one rung — and we haven't written a line of C yet.

#### Misconceptions to surface

- **"I'll never write C, so this is wasted."** The goal is not employment as a C programmer; it's the ability to reason about the C substrate you *do* run on every day. Surface it by naming the C in their stack: the interpreter, NumPy, Torch, the OS.
- **"Fast Python just means: use NumPy."** Cargo-culting NumPy without knowing *why* it's fast fails the instant the workload doesn't vectorize (branchy logic, ragged data, custom kernels). Surface it by asking *when* NumPy would **not** help — a question they can't answer yet, and will be able to after the descent.
- **"The abstraction is free because it's convenient."** Convenience and cost are different axes. The abstraction is convenient *and* someone always pays the cost — the Tier-3 reading is exactly this.

### Lab M01-B — The cost of dynamism *(the flagship measurement)*

**Goal:** reproduce the 30x ladder on your own machine and — this is the graded part — say *where every factor comes from* before you measure.

- (c) `sum(x for x in data)` — a generator
- (d) NumPy `arr.sum()` *(preview; provided)*

Write it as an ordering with reasons, e.g. *"d < b < a because …; c is near a because the generator still runs Python bytecode per element."* Seal it: `sealed_predict('M01-B')`.

#### Build

Starter (`ladder.py`):

```python
import timeit
from m01harness import report

N = 1_000_000

def bench():
    setup = f"data = list(range({N}))"
    t_loop = timeit.timeit("s=0\nfor x in data: s+=x", setup=setup, number=5) / 5
    t_sum  = timeit.timeit("sum(data)", setup=setup, number=20) / 20
    t_gen  = timeit.timeit("sum(x for x in data)", setup=setup, number=20) / 20
    try:
        import numpy  # noqa: F401
        setup_np = f"import numpy as np; data = np.arange({N})"
        t_np = timeit.timeit("data.sum()", setup=setup_np, number=100) / 100
    except ImportError:
        t_np = float("nan")
    return [
        ("pure for-loop (ms)",  round(t_loop * 1e3, 2)),
        ("builtin sum (ms)",    round(t_sum  * 1e3, 2)),
        ("generator sum (ms)",  round(t_gen  * 1e3, 2)),
        ("numpy sum (ms)",      round(t_np   * 1e3, 3)),
    ]

if __name__ == "__main__":
    report(bench())
```

### Lab M01-C — Read the receipt *(execution / bytecode)* — accelerate-optional

**Goal:** confirm from the disassembly itself that annotations are free and that every iteration allocates.

#### Predict (before running)

1. `dis.dis` of `s += x` shows how many bytecode ops? List them.
2. Does adding `x: int` to a function change its bytecode? Yes/No — commit before you look.
3. In `for x in data: total += x`, is a **new** int object allocated each iteration, or is one reused? Why? (Recall: ints are immutable.)

Seal it: `sealed_predict('M01-C')`.

#### Build

```python
import dis, tracemalloc

def with_hint(a: int, b: int) -> int:
    return a + b

def no_hint(a, b):
    return a + b

def show_bytecode():
    print("--- with annotation ---");  dis.dis(with_hint)
    print("--- without annotation ---"); dis.dis(no_hint)

def count_allocations():
    data = list(range(200_000))
    tracemalloc.start()
    before = tracemalloc.get_traced_memory()[0]
    total = 0
    for x in data:
        total += x          # each += builds a new int result object
    after = tracemalloc.get_traced_memory()[0]
    tracemalloc.stop()
    return after - before   # net bytes retained (allocation churn is larger)

if __name__ == "__main__":
    show_bytecode()
    print("net bytes during loop:", count_allocations())
```

Verify: the two disassemblies are **identical** (annotation is free — misconception killed by the machine, not by the instructor). Note that `total` grows large so it climbs *out* of the small-int cache after 256 — real allocation, not reuse. (`tracemalloc` shows retained bytes; the true allocation *churn* — objects made and immediately freed — is larger, which motivates M03's lifetime story.)

#### Integrate

One sentence: *"The interpreter re-derives types and allocates results at runtime; annotations describe intent to humans, not instructions to the machine."*

## Three-tier reading

Specific to this module's subject — *the cost of the abstraction you can't see* — not boilerplate.

- **Tier 1 — material ground (verifiable, reproducible today).** The abstraction has a measurable price and you can put a number on it on your own laptop. The integer 0 costs 28 bytes in CPython, not 8, because it is a heap object carrying a reference count and a type pointer. A list of three ints is an 88-byte array of *pointers* to three separate objects, not twelve contiguous bytes of values. Summing a million integers is ~34 ms in a pure Python loop, ~7 ms with built-in `sum`, ~1 ms in NumPy — same arithmetic, a 30x+ spread. All of this is reproducible with `sys.getsizeof`, `dis`, and `timeit`, which ship with the interpreter. It is documented, not opinion.

- **Tier 2 — what the field suppresses.** "Python is fast enough, optimize for readability" and "just use NumPy" both hide the same thing: the speed you depend on is *borrowed, not owned*. It lives in C — CPython's eval loop, NumPy's ufuncs, PyTorch's kernels — written and maintained by people you'll never meet, in exactly the dangerous language the safety advice tells you to avoid. The booster can't admit the abstraction leaks and someone downstream eats the cost; the C-nostalgic critic can't admit that hand-writing that substrate for every program would be ruinous. Both are half true. "Just use a library" is not the *alternative* to descending — the library **is** the descent, made once by someone else, and the ability to reason about it is the very skill being sold to you as unnecessary.

- **Tier 3 — sit with this (a question you can't unknow).** When your model's inference bill, or a data center's power draw, is the summed cost of abstractions no one on your team can see through — and everyone above you has been told "it just works" — at what point does *not being able to see the cost* stop being ignorance and become a choice you made? And whose watershed pays for the 30x you never looked at?
