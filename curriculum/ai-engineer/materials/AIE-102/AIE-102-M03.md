# AIE-102-M03 — The heap, manual memory, structs, and the segfault

**Course:** AIE-102 — Down to the Metal: C, and the Machine Under Python · **Tier:** foundation · **Durability:** durable
**Hours:** 20 · **Sits in the descent:** the bottom. Python is fully behind us; the learner is alone with `malloc`, a pointer, and the consequences.
**Prereq:** AIE-102-M02 (values, types, pointers, the stack). This is the module where the stack gives way to the heap.

## Lessons

1. **What Python was hiding.** Reveal that `x = [1,2,3]` in Python was always a heap allocation, a refcount, and a pointer the interpreter managed. We now manage it ourselves. Worked example: the same list, in C, as a `malloc`'d array — and everything that can now go wrong.
2. **The heap and `malloc`/`free`.** Lifetime as a thing you own. Worked example: a growable array (`realloc`), the doubling strategy the learner met abstractly in AIE-110 now built in bytes. Misconception to surface: "freeing memory zeroes it" — it does not; it just returns it. Demonstrate use-after-free returning stale-but-plausible data (the scariest bug, because it often works).
3. **Structs and memory layout.** A struct is a contract about bytes. Worked example: padding and alignment — print `sizeof` and watch it exceed the sum of the fields; explain why. Connect forward: this is why NumPy dtypes and tensor strides exist.
4. **The segfault, read from the code.** Not a mystery message — a specific dereference of memory you don't own. Worked example: three programs that segfault for three different reasons; read each fault back to its line before running under a debugger.

## Labs

Each states Predict before Build — AI-PRIMM.

### Lab M03-A — Build a growable int vector in C

*Predict:* on paper, the sequence of capacities as 10 pushes land, and the total number of `realloc` copies. *Build:* implement `vec_push`, `vec_get`, `vec_free`; pass the provided tests; run clean under `valgrind` (zero leaks, zero invalid reads). *Verify:* your predicted copy count against an instrumented counter.

### Lab M03-B — Break it on purpose

*Predict:* for each of four planted mutations (off-by-one bound, double free, use-after-free, missing null check), state what will happen and whether it will crash *reliably*. *Build:* run each under valgrind and record actual behavior. *Integrate:* write the one-sentence rule each bug teaches. This lab grades the prediction, not the crash — the point is that use-after-free often does *not* crash, and the learner must have predicted that.

### Lab M03-C — A struct-of-arrays vs array-of-structs benchmark

*Predict:* which layout is faster for a summing workload and by roughly how much, and why, from the memory hierarchy in M04's preview. *Build:* implement both, measure. *Verify:* calibration of your prediction — full marks for correct reasoning even if the factor is off, zero for a right number with wrong reasoning.

## Assessment

Maps to the course's "C implementation labs" and "measurement labs" components. Gaming-resistance is the design constraint. A learner cannot pass by copying working code, because:

1. The three labs are graded primarily on the **Predict** artifacts and the valgrind cleanliness, not on "it compiles." A correct program with no prediction trail scores below a buggy program with an accurate prediction of its own bug.
2. The module exam hands the learner an **unseen 40-line C program with one planted memory error** and asks them to (a) predict the failure before running, (b) locate it by reading, (c) fix it, (d) prove the fix under valgrind. The artifact is the judgment trail, exactly as AIE-100 established.

## Elle pacing notes

Signals for the adaptation runtime.

- **Wall — pointer syntax (`*` vs `&`).** The classic stall; reads as `struggle-blocked` fast. **Reroute:** drop to a boxes-and-arrows drawing exercise (no code) for one session, then return.
- **Wall — valgrind output overwhelms.** **Reroute:** a single annotated example reading before asking them to interpret their own.
- **Signal — a learner who predicts use-after-free as "will crash" and is surprised.** This is exactly on track — that surprise is the lesson landing, not a failure. Log `struggle-productive`, never `blocked`.
- **Accelerate — clean M03-A first try and correct M03-B prediction.** Such a learner can skip M03-C's build and submit only its prediction and reasoning.

## Three-tier reading

Specific to this module's subject — the danger and the debt of manual memory — not boilerplate.

- **Tier 1 — material ground.** Manual memory management is why C is fast and why C is dangerous; the majority of historically severe security vulnerabilities trace to exactly the errors in Lab M03-B. This is documented, not opinion.
- **Tier 2 — what the field suppresses.** "Just use a memory-safe language" suppresses that the entire fast substrate — CPython, NumPy, PyTorch, the kernel — is written in C, and someone maintains that danger so you don't have to see it. The safety is real and it is also borrowed.
- **Tier 3 — sit with this.** You will spend your career on top of C you will never audit, trusting strangers' `free()` calls. When a model you deploy leaks memory in production at 3am, whose hands does it turn out it was always in?
