**Course:** AIE-102 "Down to the Metal" · **Module:** M06 · **Hours:** 12 · **Durability:** durable (the NumPy *contract* outlasts the API surface)

This is the payoff module: the machine is no longer a metaphor, so vectorization is no longer a magic word.

## Lessons

### Lesson 1 — What the metal bought us: the ndarray IS a struct

**Descend.** In M03 you built a growable vector: a struct holding a `data` pointer to a `malloc`'d block, plus `length` and `capacity`. You already built NumPy's core. A NumPy array is that same idea with three more fields bolted on: a **dtype** (what one element is), a **shape** (how many along each axis), and **strides** (how many bytes to step to move one index along each axis). Here is the actual CPython/NumPy C struct your `np.array([...])` allocates (trimmed from `numpy/_core/include/numpy/ndarraytypes.h`):

```c
typedef struct tagPyArrayObject_fields {
    PyObject_HEAD          /* refcount + type ptr — M04. It's a Python object too. */
    char        *data;     /* pointer to ONE malloc'd raw buffer — M03 */
    int          nd;       /* number of dimensions */
    npy_intp    *dimensions; /* shape:   length nd */
    npy_intp    *strides;    /* strides: length nd, IN BYTES */
    PyObject    *base;     /* if this is a VIEW, who owns the buffer */
    PyArray_Descr *descr;  /* the dtype: itemsize, kind ('i','f'), byteorder */
    int          flags;    /* C_CONTIGUOUS | F_CONTIGUOUS | OWNDATA | WRITEABLE ... */
    PyObject    *weakreflist;
} PyArrayObject_fields;
```

Read it as an M03 struct: `data` is the pointer to the block; `descr->elsize` is `itemsize` (8 for `int64`/`float64`); `dimensions` and `strides` are two little heap arrays of length `nd`. And exactly like M03 Lesson 3, `sizeof(PyArrayObject)` exceeds the sum of its fields because of **padding/alignment** — the metadata header is ~100+ bytes on a 64-bit build, which is why a scalar in a NumPy array is a terrible idea and a million of them is a great one.

**The contrast that is the whole point.** A Python `list` of a million ints and a NumPy `int64` array of a million ints are not two speeds of the same thing. They are two different shapes of memory:

- **`list`:** a contiguous C array of a million `PyObject*` — eight-byte *pointers*. Each pointer aims at a separate `PyLongObject` (M04: ~28 bytes, its own refcount, scattered wherever the allocator happened to put it). To read element `k` you follow a pointer to somewhere else in the heap. A million tiny objects, a million potential cache misses (M05).
- **`ndarray`:** *one* `malloc`'d block of a million raw `int64`s — 8 MB, back to back, no pointers, no per-element objects, no per-element refcounts. Element `k` lives at `data + k*8`. Pointer arithmetic. One stream the prefetcher loves (M05).

**Re-ascend.** When someone says "NumPy is faster," what they are actually saying is: *the data stopped being a million boxed objects and became one C array with a type tag.* Everything else in this module is a consequence of that one sentence.

**Worked example — see the two memory shapes and the boxing tax.**

```python
import sys, numpy as np

py = list(range(1000))                 # 1000 PyObject* -> 1000 PyLongObjects
np_ = np.arange(1000, dtype=np.int64)  # one 8000-byte block

print(sys.getsizeof(py))     # ~8056: the list's pointer array + header ONLY
print(sys.getsizeof(np_))    # ~8112: 8000 bytes data + ~112 header

# getsizeof(py) is a LIE by omission — it does not count the 1000 int objects
# the pointers point at. The real footprint of `py` is ~8056 + 1000*28 ≈ 36 KB.
# The array's real footprint IS ~8112. That gap is the boxing tax, in bytes.

print(np_.itemsize, np_.nbytes)                 # 8   8000  — no hidden objects
print(np_.__array_interface__['data'][0])       # the raw pointer value (an int)
```

**Named misconception 1a — "a NumPy array is just a faster list."**
It is a *different kind of object in memory*, not a tuned version of the same one. The speed is a side effect of the memory shape. Surface it by having the learner compute the *true* byte footprint of the list (recurse into the elements) versus the array — the array is smaller *and* faster, and they'll want to know why one number (`getsizeof`) hid it.

**Named misconception 1b — "`np.array(mylist)` is basically free."**
It is a full traversal: unbox a million `PyObject`s, type-check each, and copy the raw value into the block (M04 in reverse). The conversion pays the boxing tax one last time to escape it forever. Surface it by timing `np.array(big_list)` against an operation *on* the resulting array — the conversion is often the expensive part.

### Lesson 2 — Strides: the dtype/stride contract, and views vs copies

**Descend.** The magic word "vectorization" hides a quieter, more important idea: **strides**. A stride is the number of *bytes* you step in the buffer to advance one index along one axis. For a C-contiguous `(3, 4)` `int64` array the strides are `(32, 8)`: step 8 bytes to move one column (the next element), step 32 bytes (`4 * 8`) to move one row. The address of element `[i, j]` is, literally:

```
addr(i, j) = data + i*strides[0] + j*strides[1]
```

That is the M03 pointer-arithmetic formula, generalized to N axes: `addr = data + Σ_k index[k] * strides[k]`. NumPy indexing *is* this multiply-add on the raw pointer. Nothing more.

**Why this is the load-bearing idea.** Because shape and strides are *just metadata over the same buffer*, a huge class of operations are **views** — new header, same `data` pointer, zero bytes copied:

- **`reshape`** on a contiguous array: same buffer, new `(shape, strides)`. A view.
- **`transpose` / `.T`:** does not move a single byte. It *swaps the strides.* `(32, 8)` becomes `(8, 32)`. Now "step one row" and "step one column" mean the opposite byte-steps — you're reading the same block in a different order. A view.
- **Basic slicing** `a[1:3, ::2]`: bump the `data` pointer to the first element and scale the strides. A view.

And a smaller class are **copies** — a fresh `malloc` and a traversal:

- **Fancy indexing** `a[[0, 2, 5]]` or boolean masks `a[a > 0]`: the result can't be described by a single (offset, stride) pair, so NumPy must copy.
- **`reshape` that can't be expressed as a stride trick** (e.g. after a transpose that made the array non-contiguous) copies.

**Re-ascend.** The view/copy distinction is where fast NumPy is won or lost, and it's the aliasing footgun from M03 all over again: a view *shares the buffer*, so mutating the view mutates the base, and mutating the base mutates the view. Two names, one block of memory — exactly the pointer-aliasing hazard, now wearing a friendly Python face.

**Worked example — transpose moves no bytes; a view aliases the base.**

```python
import numpy as np

a = np.arange(12, dtype=np.int64).reshape(3, 4)
print(a.strides)          # (32, 8)  C-contiguous
print(a.T.strides)        # (8, 32)  transpose = swapped strides, ZERO copy
print(a.T.flags['C_CONTIGUOUS'], a.T.flags['F_CONTIGUOUS'])  # False True

# addr of a[2,3] is data + 2*32 + 3*8 = data + 88 bytes; value is 2*4+3 = 11
print(a[2, 3])            # 11

v = a[1:3, :]             # basic slice -> VIEW
print(np.shares_memory(a, v))   # True — same buffer
v[0, 0] = -999            # mutate the view...
print(a[1, 0])            # -999  — ...the base changed. Aliasing.

f = a[[0, 2]]             # fancy index -> COPY
print(np.shares_memory(a, f))   # False
f[0, 0] = 12345
print(a[0, 0])            # 0 — the base is untouched
```

**Named misconception 2a — "transpose (or reshape) copies the data."**
Both are usually O(1) metadata edits. Surface it with `np.shares_memory(a, a.T)` returning `True` and `a.T.strides` being the swap of `a.strides`. The learner who believed transpose is expensive has been paying imaginary costs and missing the real one (the eventual copy that a `.copy()` or a non-contiguous reshape forces).

**Named misconception 2b — "slicing a NumPy array gives me an independent copy, like a Python list slice does."**
`list[1:3]` copies; `ndarray[1:3]` is a view. This reverses a habit from AIE-101. Surface it by mutating a slice and watching the base change — then contrast with the identical-looking Python-list code where it doesn't. This is the single most common silent-bug generator in NumPy code.

### Lesson 3 — Why vectorization is fast, in machine terms (not "because C")

**Descend.** Take the slowest honest thing: add two million-element sequences elementwise in a pure-Python loop. Account for what *one iteration* costs, using M04 and M05 vocabulary, not hand-waving:

```python
c = [0]*n
for i in range(n):
    c[i] = a[i] + b[i]
```

Per iteration, CPython actually does:
1. **Bytecode dispatch** — the interpreter's eval loop fetches and switches on several bytecodes (`BINARY_SUBSCR`, `BINARY_OP`, `STORE_SUBSCR`, loop machinery). A `switch` and pointer chases per op.
2. **Unbox ×3** — follow `a[i]` and `b[i]` pointers to their `PyLongObject`s (M04), each a possible cache miss (M05), read the actual integer out of the struct.
3. **Type dispatch** — `a[i] + b[i]` calls `PyNumber_Add`, which looks up `__add__` through the type's `nb_add` slot. Indirect calls, branches.
4. **Box ×1** — the result is a fresh `PyLongObject`: a heap allocation (M03), refcount set to 1 (M04).
5. **Refcount churn** — incref/decref on operands and temporaries; the decref that hits zero triggers a free.
6. **Store** — write the new pointer into `c[i]`, decref whatever was there.

Six kinds of overhead, and the *actual arithmetic* — one `add` instruction the CPU does in under a nanosecond — is a rounding error inside all of it. That is the tax. It is not "Python is interpreted" as a vibe; it is these six named, countable costs, most of which are **memory** costs (pointer chases, allocations, scattered objects) not compute costs.

Now the vectorized version:

```python
c = a + b     # a, b are np.ndarray
```

This dispatches *once* into a C **ufunc** loop that, for contiguous `int64`, is essentially:

```c
for (npy_intp i = 0; i < n; i++)
    out[i] = a[i] + b[i];   /* raw int64, in one malloc'd block each */
```

What vanished:
- **No per-element boxing/unboxing** — the values are already raw `int64` in the block. (This is the big one.)
- **No per-element refcounts** — there are no per-element objects to count. (The other big one.)
- **No per-element type dispatch** — the dtype was resolved *once*, before the loop; the C compiler emitted a single `add` per element.
- **No interpreter** — the loop is compiled machine code.
- **Cache-friendly (M05)** — three contiguous streams; the prefetcher sees the linear access pattern and has the next cache line waiting. Near-zero misses after warmup.
- **SIMD, as a bonus** — the compiler/NumPy can add 4–8 `int64`s per instruction (AVX2/AVX-512). Real, but *smaller* than removing the boxing; do not let learners credit SIMD for the 100x.

**Re-ascend.** "Vectorized is fast" now decomposes into: *you deleted five layers of per-element Python object machinery and handed a contiguous buffer to a compiled loop the CPU can stream.* The speedup (typically 50–200x for elementwise work) is mostly *boxing + refcount + interpreter removed*, and secondarily *cache + SIMD*. A learner who says "because C is compiled" has named the least important reason.

**Worked example — measure it and attribute it.**

```python
import numpy as np, time

n = 1_000_000
al, bl = list(range(n)), list(range(n))
aa, ba = np.arange(n), np.arange(n)

t = time.perf_counter()
cl = [al[i] + bl[i] for i in range(n)]
py = time.perf_counter() - t

t = time.perf_counter()
ca = aa + ba
npt = time.perf_counter() - t

print(f"python: {py*1e3:6.1f} ms   numpy: {npt*1e3:6.1f} ms   speedup: {py/npt:5.1f}x")
# typical: python ~90 ms, numpy ~1.5 ms, ~60x — and near NONE of the gap is
# "arithmetic speed". It is boxing, refcounts, dispatch, and cache.
```

**Named misconception 3a — "vectorized is fast because C is compiled and Python is interpreted."**
Partly, but if compilation were the reason, a compiled *Python-object* loop (boxing each element) would be fast too — it isn't. The dominant win is that the data stopped being objects. Surface it: point out that `np.add` on a `dtype=object` array (an array of `PyObject*`!) is barely faster than the Python loop, because it *reintroduces* boxing and refcounts even though the ufunc loop is still compiled C.

```python
o = np.arange(n, dtype=object)   # array of PyObject* — boxed again
# o + o is ~as slow as the pure-Python loop. Compiled C, but the tax is back.
```

**Named misconception 3b — "NumPy is fast because it uses my GPU / multiple cores."**
Base NumPy elementwise ops are single-threaded and CPU-only. The speed is per-core, from the object-removal above. (BLAS matmul may use multiple threads — Lesson 4/Lab C — but `a + b` does not.) Surface it by watching one core pin during a large elementwise op.

**Named misconception 3c — "so I should vectorize everything, always."**
For tiny arrays the *fixed* per-call cost (dtype resolution, output allocation, ufunc setup) dominates and a plain Python loop can win. Vectorization amortizes overhead across many elements; with few elements there's nothing to amortize. Surface it by timing `a + b` for `n = 4` vs a Python `+` — the scalar wins. (Set up for Lesson 4.)

### Lesson 4 — The vectorization discipline: temporaries, broadcasting, dtype, and where it bites

**Descend.** Vectorization removed the per-element tax but introduced a *new* cost the loop never had: **temporaries**. Every intermediate array in an expression is a fresh `malloc`'d block (M03) that gets written, read once, and freed. Read this the way you read a struct's memory:

```python
z = (X - X.mean(0)) / X.std(0)
```

For `X` of shape `(m, k)`, this allocates: `X.mean(0)` `(k,)`, `X.std(0)` `(k,)`, the broadcast subtraction `(m, k)`, the division result `(m, k)`. Two full `(m, k)` temporaries. If `X` is 400 MB, this expression touches ~1.2 GB of memory traffic and can blow past cache (M05) and even RAM. The Python loop, for all its per-element tax, held *one* element in a register at a time. So vectorization trades **per-element object overhead** for **whole-array memory bandwidth and allocations** — usually a great trade, but now *the temporary is the thing you optimize.*

**Killing temporaries.** Use `out=` and in-place operators to reuse buffers:

```python
z = X - X.mean(0)     # one temporary (m,k)
z /= X.std(0)         # in-place: no second (m,k) temporary
```

**Broadcasting** is the stride contract doing a favor: a `(k,)` array added to an `(m, k)` array is treated as if its `(k,)` row were repeated `m` times — but no repetition is materialized; NumPy sets the missing axis's **stride to 0** so the same row is re-read. Free repetition via a zero stride (M03 pointer arithmetic: `index * 0` never advances the pointer). The rule: align shapes on the right; each axis must be equal or one of them `1`.

**Re-ascend.** Reading a vectorized expression is now a *memory-accounting* skill: count the full-size temporaries, know which are views (free) and which are copies (a `malloc` + a pass over memory), and know that dtype decides the itemsize of every one of them. Which brings the traps:

- **dtype promotion / overflow.** `int8` arithmetic wraps silently; `a.sum()` on `int32` can overflow; mixing `float32` and `float64` upcasts the whole temporary to `float64` (double the bytes, double the bandwidth). The dtype is a contract you must read.
- **Catastrophic cancellation** (Lab C): algebraically-equal formulas are not numerically equal in float; `a² + b² − 2ab` can go slightly negative where `(a−b)²` cannot.
- **When vectorization loses:** genuinely data-dependent control flow (each step depends on the last — e.g. some recurrences), or arrays too small to amortize call overhead (Lesson 3c). Those are the cases where the *next* descent (Numba/Cython/back to C) earns its place — but only after you've proven pure NumPy can't, and named *why*.

**Worked example — temporaries and a dtype trap you can measure.**

```python
import numpy as np

X = np.random.rand(4000, 4000).astype(np.float32)   # 64 MB
# Naive: allocates two extra (4000,4000) float32 temporaries (128 MB of churn)
z1 = (X - X.mean(0)) / X.std(0)
# Lean: one temporary, then in-place
z2 = X - X.mean(0)
z2 /= X.std(0)
assert np.allclose(z1, z2, atol=1e-5)

# dtype trap: mean() of float32 accumulates in float32 -> precision loss on big n
big = np.full(10_000_000, 0.1, dtype=np.float32)
print(big.mean())                      # 0.10000001 — visibly off from 0.1
print(big.mean(dtype=np.float64))      # 0.10000000149... — accurate; accumulator dtype matters
```

**Named misconception 4a — "vectorized code has no allocations, it's all in place."**
Every operator makes a new array unless you *made* it in-place with `out=`/`+=`. A chain of five operations is five allocations. Surface it by watching resident memory climb during a long expression on a large array, then flatten when rewritten in-place.

**Named misconception 4b — "broadcasting copies the smaller array to match."**
It sets a stride to 0 and re-reads. No copy. Surface it with `np.broadcast_to(v, (m, k)).strides` showing a `0` and `np.shares_memory` being `True` with `v`.

**Named misconception 4c — "the two algebraically-equal formulas give the same answer."**
In float, order and cancellation matter. Surface it in Lab C when the gram-matrix distance produces `-3.6e-15` on the diagonal and a `sqrt` yields `nan`.

### Lab M06-B — The re-ascent: make the slow loop fast, with evidence

**Goal.** Take a correct-but-slow pure-Python numeric routine, account for its cost in M04/M05 terms, vectorize it, and *prove* the result is numerically the same and faster — and know how many temporaries you spent to get there.

**Provided (`slow.py`) — column z-score standardization on a list-of-lists:**
```python
def standardize_slow(X: list[list[float]]) -> list[list[float]]:
    m, k = len(X), len(X[0])
    means = [0.0] * k
    for i in range(m):
        for j in range(k):
            means[j] += X[i][j]
    for j in range(k):
        means[j] /= m
    stds = [0.0] * k
    for i in range(m):
        for j in range(k):
            d = X[i][j] - means[j]
            stds[j] += d * d
    for j in range(k):
        stds[j] = (stds[j] / m) ** 0.5
    out = [[0.0] * k for _ in range(m)]
    for i in range(m):
        for j in range(k):
            out[i][j] = (X[i][j] - means[j]) / stds[j]
    return out
```

#### Predict (on paper)
1. **Cost breakdown.** For the inner statement `out[i][j] = (X[i][j] - means[j]) / stds[j]`, name every per-element cost from Lesson 3 (bytecode dispatch, unbox count, refcount events, `__sub__`/`__truediv__` lookups, box count, and the cache behavior of indexing a `list[list[float]]` vs a contiguous array). Assign each a rough share of the time.
2. **Speedup.** Predict the speedup of a clean vectorized `standardize(X)` over `standardize_slow` for `X` shape `(10000, 50)`. Tie the number to the costs in (1).
3. **Temporaries.** For the naive vectorized form `(X - X.mean(0)) / X.std(0)` versus a lean in-place form, predict how many full `(m, k)` temporaries each allocates. Which touches more memory (M05)?
4. **A trap.** If `X` arrives as `float32`, predict what `X.mean(0)` does to precision for large `m`, and one line you'd add to prevent a wrong answer.

#### Build (`lab_b.py`)
```python
import numpy as np

def standardize_naive(X: np.ndarray) -> np.ndarray:
    return (X - X.mean(axis=0)) / X.std(axis=0)

def standardize_lean(X: np.ndarray) -> np.ndarray:
    Z = X - X.mean(axis=0)        # one (m,k) temporary
    Z /= X.std(axis=0)            # in-place: no second (m,k) temporary
    return Z
```

#### Verify
- **Equivalence (the gate):** `np.allclose(standardize_naive(Xa), np.array(standardize_slow(Xa.tolist())), atol=1e-6)` must hold. A fast wrong answer scores zero.
- **Timing:** report `standardize_slow` vs both vectorized forms; expect ~50–150x. Grade the *attribution* against prediction 1–2.
- **Temporary count:** confirm prediction 3 by reasoning (and optionally by measuring peak memory with `tracemalloc`). Lean should show ~one fewer `(m, k)` block of traffic.
- **Trap:** confirm prediction 4 — `X.mean(0)` in `float32` drifts; `X.mean(0, dtype=np.float64)` fixes it.

### Lab M06-C (capstone) — Pairwise squared distances: three ways, and the cache

**Goal.** The re-ascent under load. Compute the `(N, N)` matrix of squared Euclidean distances between rows of an `(N, D)` matrix `X`, three ways, and *predict from the memory hierarchy* which wins and why — including the temporary that will surprise you and the numerical trap that will bite you.

The three implementations:
- **(1) triple loop** — pure Python, `D[i,j] = Σ_d (X[i,d]-X[j,d])²`.
- **(2) naive broadcast** — `((X[:,None,:] - X[None,:,:])**2).sum(-1)`.
- **(3) gram-matrix identity** — `‖x‖² + ‖y‖² − 2·XXᵀ`, one matmul plus two norm vectors.

#### Predict (on paper, before building)
1. **Peak memory.** For `N = 2000`, `D = 50`, `float64`, predict the peak *extra* allocation of each method. (Hint for (2): what is the shape of `X[:,None,:] - X[None,:,:]` *before* the `.sum(-1)`?) Give bytes.
2. **Speed ranking and WHY.** Rank the three fastest→slowest and justify each in machine terms: which streams contiguous memory, which materializes an `N×N×D` temporary that overflows cache (M05), which dispatches to BLAS (a hand-tuned, cache-blocked, multi-threaded matmul), and which pays the full per-element Python tax (M04).
3. **The trap.** The gram-matrix form is algebraically exact but not numerically exact. Predict what appears on the diagonal of method (3) and what `np.sqrt` would then produce. Predict the one-line fix.
4. **FLOPs vs. wall-clock.** Methods (2) and (3) both do ~`O(N²D)` arithmetic. Predict why (3) is nonetheless much faster despite equal FLOPs — name the cause (temporary/bandwidth/BLAS), not just "it's optimized."

#### Build (`lab_c.py`)
```python
import numpy as np

def dist2_loop(X):
    N, D = len(X), len(X[0])
    out = [[0.0]*N for _ in range(N)]
    for i in range(N):
        for j in range(N):
            s = 0.0
            for d in range(D):
                diff = X[i][d] - X[j][d]
                s += diff*diff
            out[i][j] = s
    return out

def dist2_broadcast(X):                       # X: (N, D) ndarray
    diff = X[:, None, :] - X[None, :, :]      # (N, N, D) TEMPORARY
    return (diff * diff).sum(axis=-1)

def dist2_gram(X):                            # X: (N, D) ndarray
    sq = np.einsum("ij,ij->i", X, X)          # ||x||^2 per row, shape (N,)
    G = X @ X.T                               # BLAS matmul, (N, N)
    D2 = sq[:, None] + sq[None, :] - 2.0 * G
    np.maximum(D2, 0.0, out=D2)               # clip cancellation to >= 0
    return D2
```

#### Verify
- **Equivalence:** all three `allclose` (after the clip) at `atol=1e-8` on a small `N` where the loop is affordable.
- **Peak memory:** measure with `tracemalloc`; method (2)'s `(N,N,D)` temporary is `2000*2000*50*8 = 1.6 GB` — confirm it dwarfs (3)'s `~32 MB`. This is prediction 1, made real.
- **Timing:** `(3) ≪ (2) ≪ (1)` on wall-clock; grade the *reasoning* in prediction 2 and 4. **Full marks for correct memory/cache/BLAS attribution even if your measured factor is off; zero for the right ranking with wrong reasoning** (e.g. crediting SIMD or "C is compiled" for the gram win when the real causes are the missing 1.6 GB temporary and BLAS cache-blocking).
- **Trap:** confirm the diagonal of the *un-clipped* gram result has tiny negatives (~`-3.6e-15`), and that `sqrt` without the clip yields `nan`. Prediction 3, made real.

**Test sketch (`test_lab_c.py`):**
```python
import numpy as np, lab_c as C
def test_three_agree():
    X = np.random.default_rng(0).standard_normal((60, 8))
    a = np.array(C.dist2_loop(X.tolist()))
    b = C.dist2_broadcast(X)
    c = C.dist2_gram(X)
    assert np.allclose(a, b, atol=1e-8) and np.allclose(a, c, atol=1e-8)
def test_gram_nonneg():
    X = np.random.default_rng(1).standard_normal((100, 5))
    assert C.dist2_gram(X).min() >= 0.0        # clip worked
```

## Assessment

**Format.** Timed practical (2.5 h). The learner receives an **unseen** ~35-line pure-Python numeric routine (they do not see it before the exam). Example class: a per-row min-max normalization followed by a length-`w` moving-average smoothing over each row of a matrix — correct, slow, and containing **one planted numerical trap** (an `int` input path that makes `(x - min)/(max - min)` do integer division / overflow, or a `float32` accumulation that loses precision, or an algebraic rewrite that cancels). The learner must, **in this order, with each step submitted as a timestamped artifact before the next is unlocked:**

1. **Predict (before writing any NumPy).** A written cost accounting of the given loop in M04/M05 terms (boxing, refcounts, dispatch, cache), a predicted speedup with reasoning, an enumeration of every full-size temporary a naive vectorization would allocate, and an explicit call on the planted trap: *what will go wrong, on what input, and how you'll detect it.*
2. **Vectorize.** Produce a correct vectorized implementation.
3. **Prove equivalence.** A test showing `np.allclose` to the reference within a stated, justified tolerance — including on the input class that triggers the trap.
4. **Measure.** A timing and a peak-memory measurement (naive vs. temporary-lean), reported with the method.
5. **Explain the residual.** One paragraph: after vectorizing, what still costs — and whether the *next* descent (out of NumPy) is warranted, with a reason.

**Why it is gaming-resistant.** You cannot pass by wrapping the loop in `np.` and getting a faster number:
- The **Predict artifact is submitted and locked before code**, so a fast-but-unexplained solution cannot back-fill reasoning. The prediction is graded on the cost decomposition, not on being numerically right about the factor.
- The **planted trap** means the naive vectorization that "just works" is *wrong* on the trap input; only a learner who predicted and tested it passes the equivalence gate. A green "it ran and was faster" that fails the trap input scores zero on correctness.
- **Equivalence is a hard gate**: a faster wrong answer fails outright. Speed points are unreachable without the `allclose` proof.
- **Temporary enumeration** is checked against the actual memory measurement; you cannot claim understanding of temporaries you didn't allocate-account.
- The **residual explanation** cannot be satisfied by "it's fast now" — it must name a specific remaining cost, which requires having done the accounting.

## Three-tier reading — NumPy internals and vectorization

**Tier 1 — material ground (verifiable).**
NumPy is a C library. The `ndarray` is one contiguous, `malloc`'d buffer plus a small metadata header: a dtype (itemsize + kind), a shape, and strides in bytes. Indexing is pointer arithmetic on that buffer (`addr = data + Σ index·stride`); transpose, reshape-on-contiguous, and basic slices are metadata-only *views* that copy nothing and *alias* the base. Vectorization is fast for a mechanically specific reason: it deletes the per-element `PyObject` boxing, the per-element refcount traffic, and the interpreter dispatch, and hands a contiguous buffer to a compiled loop the CPU prefetches and (sometimes) SIMDs — you can prove the boxing is the dominant cost by watching a compiled ufunc stay slow on a `dtype=object` array. The heavy linear algebra (`@`, `dot`, `einsum` contractions) is dispatched to **BLAS** — OpenBLAS or Intel MKL — cache-blocked, multi-threaded assembly kernels hand-tuned per CPU microarchitecture by a very small number of people.

**Tier 2 — what the field suppresses.**
The booster line is "just vectorize" / "just use NumPy and it's fast for free." That phrasing hides three things. First, the speed is *borrowed*: it comes from a C/Fortran/BLAS substrate that a tiny cadre of maintainers keep alive, and from assembly kernels retuned for each new chip — you are standing on unpaid or barely-paid infrastructure labor and calling the result "your" optimization. Second, the danger from M03 did not go away; it went under the floor. A stride you set wrong (`np.lib.stride_tricks.as_strided`) reads arbitrary process memory with no bounds check — the same out-of-bounds read that segfaulted your C vector, now one keyword-arg away, and NumPy has shipped real CVEs for buffer overflows and integer-overflow-to-heap-corruption. "Memory-safe Python" is safe only until you touch the array internals that make it fast. Third, the critics' idealization — "if you need speed, just write it in a fast language" — suppresses that the entire scientific-Python and modern-ML stack (NumPy, SciPy, PyTorch, JAX) *is* exactly that borrowing, packaged so you don't have to; the choice was never "safe Python vs. fast C," it was always "fast C someone else maintains, presented to you as Python." And the quieter suppression: "vectorized" is sold as free, but it trades your explicit one-value-in-a-register loop for hidden whole-array temporaries that can silently exhaust memory or upcast your dtype and double your bandwidth bill.

**Tier 3 — sit with this (a question you cannot un-ask).**
You will spend your career making numeric code fast by handing it to matmul kernels you did not write, cannot audit, and could not rebuild — tuned by strangers for silicon you will never open, maintained by a handful of people whose names aren't on your slide. When your model's throughput number becomes a headline and the training bill is real money: how much of that speed did you *author*, and how much did you inherit, wrap in one line, and take credit for — and if the borrowed floor cracks at 3am, whose kernel was it always running on?
