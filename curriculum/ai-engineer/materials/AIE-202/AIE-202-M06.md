### Lesson 1 — `nn.Module` and autograd: PyTorch's tape is your tape, compiled

Every `Value` object in the M01 engine did two things when an operation touched it: it computed a forward result, and it recorded a closure — `_backward` — that knew how to push a gradient one step back through that specific operation. `.backward()` walked the resulting graph in reverse topological order and called every closure. That is, in full, what "autograd" means. PyTorch's autograd is the identical idea, at the identical granularity, with three substitutions: `Value` becomes `torch.Tensor` (with `requires_grad=True`), the closure PyTorch records per operation is called a `grad_fn` instead of `_backward`, and the interpreter loop that builds and walks the graph is written in C++ instead of Python. Nothing about *what* is computed changes. What changes is *how fast* the bookkeeping around each operation happens — Lesson 2 measures exactly that gap. This lesson establishes that the graph itself, and the numbers it produces, are unchanged.

**The correspondence, explicit:**

| M01 `Value` engine | PyTorch |
|---|---|
| `Value(data, _children=(), _op="")` | `torch.Tensor` with `requires_grad=True` |
| a learned number: `Value(w)` | `nn.Parameter(torch.tensor(w))` |
| `out._backward = <closure>` attached per op | `out.grad_fn` attached per op (e.g. `MulBackward0`) |
| `v.grad` (accumulates via `+=`) | `t.grad` (accumulates via `+=`, identical semantics) |
| `build_topo(root)` then walk in reverse | `torch.autograd.Graph` traversal inside `.backward()` |
| `loss.backward()` (your code, M01 L3) | `loss.backward()` (identical call, different engine underneath) |
| `MLP`/`Layer`/`Neuron` classes (M02) | `nn.Module`/`nn.Linear` (parameters registered, not manually listed) |

`nn.Module` is not a new idea either — it is `MLP.__init__`'s `self.layers = [...]` pattern, formalized: it walks its attributes, finds every `nn.Parameter` (including ones nested inside child modules), and hands you `model.parameters()` the way M02's `MLP.parameters()` method did by hand.

**Worked example — the same 2→3→1 network, three ways, one set of numbers.** Fix explicit weights (no random init — the point of this example is that three different computational routes land on the *same* numbers, and hardcoded weights make the comparison exact rather than seed-dependent):

```
W1 = [[ 0.526558,  0.888246],
      [-1.276646, -0.068983],
      [ 0.506860,  0.676071]]      b1 = [0, 0, 0]
W2 = [[ 0.326894,  0.748559,  0.144979]]      b2 = [0]
x  = [0.6, -0.8]        target = 1.0
```

Forward pass: `z1 = W1@x + b1 = [-0.394662, -0.710802, -0.236741]`, `h1 = tanh(z1) = [-0.375372, -0.611179, -0.232415]`, `yhat = W2@h1 + b2 = -0.613906`, `loss = (yhat - target)² = 2.604692`.

Backward pass, computed by hand (this *is* what `.backward()` does, one operation's local derivative at a time, same as M01 Lesson 2's `d(x*y)/dx = y` rule):

```
dL/dyhat = 2*(yhat - target)         = -3.227812
dL/dW2   = dL/dyhat * h1             = [1.211631, 1.972771, 0.750192]
dL/db2   = dL/dyhat                  = -3.227812
dL/dh1   = W2 * dL/dyhat             (broadcast)
dL/dz1   = dL/dh1 * (1 - h1**2)      = [-0.906477, -1.513657, -0.442686]
dL/dW1   = outer(dL/dz1, x)          = [[-0.543886,  0.725182],
                                         [-0.908194,  1.210926],
                                         [-0.265612,  0.354149]]
dL/db1   = dL/dz1                    = [-0.906477, -1.513657, -0.442686]
```

Now the PyTorch route — same weights, loaded explicitly so there is no RNG to keep in sync:

```python
import torch
import torch.nn as nn

class TinyMLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(2, 3)
        self.fc2 = nn.Linear(3, 1)

    def forward(self, x):
        h1 = torch.tanh(self.fc1(x))
        return self.fc2(h1)

torch.set_default_dtype(torch.float64)   # match the hand computation's precision
model = TinyMLP()
with torch.no_grad():
    model.fc1.weight.copy_(torch.tensor([[ 0.526558,  0.888246],
                                          [-1.276646, -0.068983],
                                          [ 0.506860,  0.676071]]))
    model.fc1.bias.copy_(torch.zeros(3))
    model.fc2.weight.copy_(torch.tensor([[0.326894, 0.748559, 0.144979]]))
    model.fc2.bias.copy_(torch.zeros(1))

x = torch.tensor([0.6, -0.8], requires_grad=True)
target = torch.tensor([1.0])
yhat = model(x)
loss = (yhat - target).pow(2).sum()
loss.backward()

print(loss.item())              # 2.604692...
print(model.fc1.weight.grad)    # matches dL/dW1 above, to ~1e-9
print(x.grad)                   # matches dL/dx computed the same way: [1.230712, -1.000046]
```

Run this and diff `model.fc1.weight.grad` against the hand-computed `dL/dW1` above: the maximum absolute difference is on the order of `1e-9` or smaller — floating-point roundoff, not a different answer. A central finite-difference check on `W1[0,0]` (perturb by `±1e-6`, recompute the loss, divide by `2e-6`) gives `-0.5438864323`, against the analytic/autograd value `-0.5438864318` — agreement to nine significant figures, the residual entirely explained by finite-difference truncation error, exactly the tolerance you learned to expect from M01 Lesson 4's `gradcheck`. Three routes — hand-derived calculus, PyTorch's `.backward()`, and numerical finite differences — land on the same fifteen digits. That agreement, not a claim about what PyTorch "must" be doing internally, is the evidence this lesson is built to produce.

**Named misconception 1 — "PyTorch's autograd is a fundamentally different, more sophisticated algorithm than the `Value` engine I built."** The gradient-parity numbers above refute this directly: `dL/dW1` computed by the hand-derived chain rule and `model.fc1.weight.grad` computed by `loss.backward()` agree to float64 precision. PyTorch's autograd is reverse-mode automatic differentiation over a dynamically-built graph — the *exact* algorithm from M01 Lesson 3, applied at every operation instead of once. The only thing "more sophisticated" is the engineering underneath it (Lesson 2's subject), not the mathematics on top of it.

**Named misconception 2 — "`nn.Module` hides the graph, so `.backward()` must be computing something aggregated or approximate rather than the exact chain rule at every node."** `nn.Module` hides *bookkeeping* (parameter registration, submodule traversal) — it does not hide or approximate the graph. Every tensor operation inside `forward()` still gets its own node with its own `grad_fn`; you can inspect this directly: `yhat.grad_fn` is `<AddmmBackward0 ...>`, and `yhat.grad_fn.next_functions` points at the operations that fed it, walkable exactly like `Value._prev`. `nn.Module` is a container for parameters, not a different execution model.

**Named misconception 3 — "each call to `.backward()` resets gradients to a fresh, correct-for-this-call value automatically."** False, and this is the single most consequential PyTorch habit this module installs. `t.grad` accumulates via `+=` on every `.backward()` call, exactly like `Value.grad` in M01 — reread M01 Lesson 3's diamond example (`b = a*a`) if this feels unfamiliar. Call `loss.backward()` twice on two different batches without an intervening `optimizer.zero_grad()` (or `model.zero_grad()`, or manually setting `.grad = None`), and the second gradient **adds onto** the first rather than replacing it. This is not a PyTorch quirk to memorize and forget — it is the same accumulate-by-default semantics your own engine has always had, and forgetting it is the exact bug this module's Assessment is built around.

### Lesson 2 — Tensors, vectorization, and where the speed actually comes from

M01's `Value` engine represents a scalar computation as one Python object per number, with one Python function call per operation. A network with 1,000 weights doing one forward pass touches on the order of several thousand individual Python-level `Value.__mul__`/`__add__`/`__tanh__` calls — and the Python interpreter pays dispatch overhead (looking up the method, building a stack frame, running bytecode) on *every single one* of them, regardless of how simple the underlying arithmetic is. M03's shift to NumPy `Tensor`s was the first fix: instead of "N Python-level multiply calls," a matrix multiply became "one call into a compiled routine that does N multiplies internally, in C, with no per-element Python overhead." PyTorch's `torch.Tensor` is the same fix, generalized and hardware-accelerated: batched operations dispatch once into a compiled kernel (BLAS/MKL on CPU, cuBLAS/cuDNN on GPU), and — critically for training — the *backward* pass is compiled and batched the same way the forward pass is, instead of walking one Python closure per scalar the way M01's `.backward()` does.

**This is a dispatch-overhead story, not a different-mathematics story.** The operation being computed — a matrix multiply, a convolution as a matrix multiply after `im2col`, a `tanh` — is the identical operation regardless of which engine runs it. What differs is how many times the Python interpreter has to wake up to make it happen: once per scalar (M01's `Value` engine), or once per batched call (NumPy, PyTorch, either device).

**Worked example — measured on this packet's reference machine, both implementations computing the identical convolution.** A single-channel 8×8 image convolved with four 3×3 kernels, once as literal nested Python loops (the M03 "first, naive" version — four indices deep: output channel, output row, output column, then the kernel window itself) and once as `im2col` (unfold every 3×3 window into a row of a matrix, then a single matrix multiply against the reshaped kernels — the M03 "vectorized" version):

```python
def naive_conv(img, kernels):
    C_out, kh, kw = kernels.shape
    out_h, out_w = img.shape[0]-kh+1, img.shape[1]-kw+1
    out = np.zeros((C_out, out_h, out_w))
    for c in range(C_out):
        for i in range(out_h):
            for j in range(out_w):
                acc = 0.0
                for a in range(kh):
                    for b in range(kw):
                        acc += img[i+a, j+b] * kernels[c, a, b]
                out[c, i, j] = acc
    return out

def im2col_conv(img, kernels):
    C_out, kh, kw = kernels.shape
    out_h, out_w = img.shape[0]-kh+1, img.shape[1]-kw+1
    cols = np.stack([img[i:i+kh, j:j+kw].ravel()
                      for i in range(out_h) for j in range(out_w)])
    W = kernels.reshape(C_out, -1)
    return (cols @ W.T).T.reshape(C_out, out_h, out_w)
```

Timed over 200 calls each (identical `img`, identical `kernels`, `numpy` 2.4.6, no GPU):

| scale | naive Python loop | `im2col` + BLAS matmul | speedup | max abs output diff |
|---|---|---|---|---|
| 8×8 image, 4 output channels | 0.5355 ms/call | 0.0481 ms/call | **11.1×** | `1.1e-16` |
| 32×32 image, 8 output channels | 24.150 ms/call | 1.1711 ms/call | **20.6×** | `1.1e-16` |

Two things in this table matter more than the raw speedup. First, **the outputs are identical to floating-point roundoff** (`1.1e-16` is one machine epsilon at float64, i.e. "not a different computation, the same computation") — vectorizing did not trade accuracy for speed, it eliminated Python overhead while computing the same sums in the same order-independent way (addition is associative up to roundoff). Second, **the speedup grows with problem size** (11× at 8×8, nearly 21× at 32×32) because Python dispatch overhead is roughly constant per element while BLAS's advantage compounds with better cache use and larger matrix-multiply tiles at scale — which is exactly why the gap between hand-rolled and framework code widens, not narrows, as you move from this module's toy examples toward real model sizes. `nn.Conv2d` takes this same `im2col`-style reformulation (or a related direct-convolution algorithm) one step further by routing it through cuDNN — vendor-tuned, hardware-specific kernels — and by making the *backward* pass just as vectorized as the forward pass, which is the piece a hand-rolled NumPy CNN (M03 built forward and backward both, but wrote both by hand) gets for free from `loss.backward()`. Lab M06-B has you measure your own machine's numbers rather than trust the table above — the qualitative pattern (vectorized wins, and wins by more as size grows) is the durable claim; the exact multiplier is hardware-specific.

**Named misconception 1 — "PyTorch is fast because it uses a fundamentally different, cleverer algorithm than the one I wrote by hand."** The `1.1e-16` diff column refutes this directly: `im2col_conv` and `naive_conv` compute the *same* convolution, to floating-point precision — the speedup comes entirely from where the arithmetic executes (one compiled BLAS call vs. thousands of Python-level operations), not from a different formula. `nn.Conv2d` is a further turn of the identical crank: same convolution, dispatched to a kernel written by people who know the target chip intimately, but computing the mathematics you already derived from scratch in M03.

**Named misconception 2 — "vectorization is an approximation — the 'real' answer is whatever the careful, element-by-element loop computes."** Backwards, if anything: floating-point addition is not perfectly associative, so a vectorized sum and a loop-accumulated sum over the *same* terms can differ in the last bit or two depending on summation order — and the measured diff above (`1.1e-16`, one unit in the last place) shows that difference is genuinely negligible, not evidence that one version is "more correct." Neither the loop nor the vectorized call is the ground truth; both are finite-precision approximations of the same exact real-number computation, and they agree to the limits of that precision.

**Named misconception 3 — "one timed run tells you the real speedup."** A single call's wall-clock time is noisy — OS scheduling jitter, CPU frequency scaling, cache state left over from whatever ran immediately before. The measurement above averages 200 calls per implementation for exactly the reason M01/M02 averaged multiple seeds before trusting a gradient-magnitude claim: a single sample is an anecdote, a distribution is evidence. Lab M06-B enforces this structurally, not just by convention: its shared `timeit` helper raises `ValueError` if asked to run fewer than 20 repetitions, so a benchmark script cannot silently time one call of each version, and a dedicated `pytest` check confirms that floor cannot be bypassed.

### Lesson 3 — `Dataset`, `DataLoader`, and optimizers as thin wrappers over what M02 already built

**Batching is index bookkeeping, not new math.** M02's training loop sliced minibatches by hand: `for i in range(0, N, batch_size): batch_x, batch_y = X[i:i+batch_size], Y[i:i+batch_size]`. PyTorch's `Dataset`/`DataLoader` pair formalizes exactly this and nothing more. A `Dataset` is an object with `__len__` (how many examples) and `__getitem__(i)` (return example `i`); a `DataLoader` wraps it, optionally shuffles a permutation of `range(len(dataset))` once per epoch, and yields index-sliced batches from that permutation. **Shuffling changes which examples land in which batch — it does not change the loss function, the gradient computed for a given batch, or any hyperparameter.** A gradient computed from `{x_4, x_6, x_2}` is the same number whether that triple was assembled by `DataLoader(shuffle=True)` or by hand-slicing a pre-permuted array; summation (the core operation inside a batch loss) doesn't care what order its terms arrive in — the identical fact Lesson 2's `im2col` diff check leaned on, and the identical fact M04 Lesson 3's attention "weighted sum" argument leaned on.

**Worked example — the permutation, made visible.** `torch.utils.data.DataLoader(dataset, batch_size=3, shuffle=True)` over 10 examples, `torch.manual_seed(0)`-equivalent permutation behavior reproduced here with NumPy's `default_rng(0)` (the mechanism — draw one permutation of the index range per epoch, then slice it into contiguous batches — is identical regardless of which library's RNG drew it):

```
epoch 1 permutation: [4, 6, 2, 7, 3, 5, 9, 0, 8, 1]
  batches (drop_last=False): [4,6,2] [7,3,5] [9,0,8] [1]
  batches (drop_last=True):  [4,6,2] [7,3,5] [9,0,8]        <- last, short batch dropped
epoch 2 permutation: [2, 9, 3, 6, 0, 4, 8, 7, 5, 1]         <- reshuffled, new epoch
```

Nothing here is inaccessible: `drop_last=True` exists because a batch of size `1` (the leftover from `10 % 3`) produces a noisier gradient estimate and, for certain layers (batchnorm with `batch_size=1`), an outright error — a real engineering tradeoff, not a hidden default to take on faith.

**Optimizers read `.grad` and mutate `.data` — nothing else.** `optimizer.step()` has no access to the loss value, the model's forward activations, or the data. Its entire input is whatever is sitting in each parameter's `.grad` (populated by the `.backward()` call you made *before* calling `.step()`) plus whatever internal state the optimizer itself keeps (for `SGD` with momentum: a running velocity per parameter; for `Adam`: two running moment estimates per parameter). This is precisely the signature of M02's hand-rolled `update(params, grads, ...)` function — a pure transformation of parameters given gradients and optimizer state, unaware of anything else in the training loop.

**Worked example — one parameter tensor, two `Adam` steps, computed by hand against PyTorch's exact update rule.** `Adam` (`lr=0.01, betas=(0.9, 0.999), eps=1e-8`, matching PyTorch's own defaults) on `theta = [0.5, -0.3, 1.2]`, first gradient `grad = [0.10, -0.25, 0.05]`:

```
m = 0.9*0 + 0.1*grad             = [ 0.010, -0.025,  0.005]
v = 0.999*0 + 0.001*grad**2      = [1.0e-5, 6.25e-5, 2.5e-6]
mhat = m / (1 - 0.9**1)          = [ 0.100, -0.250,  0.050]   <- exactly grad; see below
vhat = v / (1 - 0.999**1)        = [ 0.010,  0.0625, 0.0025]  <- exactly grad**2
theta_new = theta - 0.01 * mhat/(sqrt(vhat)+eps)
          = [0.49, -0.29, 1.19]
```

A fact worth naming, not just observing: at `t=1`, `mhat` always equals the raw gradient exactly (`m = (1-β1)*grad`, divide by `1 - β1^1 = 1-β1`, the `(1-β1)` cancels), and likewise `vhat = grad²` exactly — so `mhat/sqrt(vhat) = sign(grad)` exactly. **Adam's very first update, always, on every parameter, is exactly `theta -= lr * sign(grad)`** — a fixed-size step in the gradient's direction, regardless of gradient magnitude. That's not a coincidence you have to discover by staring at PyTorch's source; it falls straight out of the bias-correction algebra, and you just derived it. A second step, with a new gradient `grad2 = [0.08, -0.20, 0.02]` and the `m`, `v` carried over, lands at `theta_new2 = [0.480119, -0.280119, 1.181014]` — no longer exactly `sign`-scaled, because by `t=2` the bias correction and the moving average have started to diverge from the single-sample case.

```python
import torch

theta = torch.nn.Parameter(torch.tensor([0.5, -0.3, 1.2], dtype=torch.float64))
opt = torch.optim.Adam([theta], lr=0.01)

theta.grad = torch.tensor([0.10, -0.25, 0.05], dtype=torch.float64)
opt.step()
print(theta.data)          # tensor([ 0.4900, -0.2900,  1.1900]) -- matches hand computation exactly

opt.zero_grad()
theta.grad = torch.tensor([0.08, -0.20, 0.02], dtype=torch.float64)
opt.step()
print(theta.data)          # tensor([ 0.4801, -0.2801,  1.1810]) -- matches theta_new2 to 6 places
```

**Named misconception 1 — "shuffling the data changes the math of the gradient update, so `shuffle=True` vs `shuffle=False` trains a meaningfully different model on step 1."** Refuted by the permutation table: shuffling changes *which* examples are grouped into a batch, and therefore changes the *value* of the gradient a given batch produces (a batch of different examples has a different mean loss) — but it does not change the formula computing that gradient, and it does not make the optimizer do anything structurally different with it. The reason shuffling matters for training quality is statistical (avoiding correlated batches, e.g. all-class-A examples in a row if the dataset is sorted by label), not because it alters the update rule itself.

**Named misconception 2 — "Adam is a black-box heuristic — nobody can really say what it will do to a given gradient."** Refuted by reproducing two full steps by hand to six decimal places, using nothing but the bias-corrected moving-average formulas — the same kind of formula-first discipline M02 used for `SGD`+momentum. `Adam`'s `torch.optim.Adam` source is public and is, at its core, exactly the four-line update above wrapped in bookkeeping for per-parameter state and numerical edge cases (`eps` for divide-by-zero, `amsgrad` as an optional variant). "Adaptive" describes *what the formula does* (scale each parameter's step by that parameter's own gradient history) — it does not mean "uninspectable."

**Named misconception 3 — "`optimizer.step()` looks at the current loss to decide how big a step to take."** It cannot — by the time `.step()` runs, the loss tensor that produced the gradients has typically already gone out of scope, and `.step()`'s signature takes no loss argument at all. Its only inputs are `.grad` (already computed and stored on each parameter) and the optimizer's own internal `state` dict (`m`, `v`, `step count` for `Adam`; `momentum buffer` for `SGD`). This is precisely why `loss.backward()` must run *before* `optimizer.step()`, and precisely why forgetting `optimizer.zero_grad()` between iterations is a silent bug rather than a loud crash — `.step()` will happily consume a `.grad` that has quietly summed across every previous call, because reading `.grad` is genuinely all it does. Lesson 1's misconception 3 and this module's Assessment are the same bug, viewed from the optimizer's side of the boundary instead of the tensor's.

### Lesson 4 — Rebuilding the descent, idiomatically, and making "just fast infrastructure" a number

Every architecture this course has built — M02's MLP, M03's CNN, M04's RNN and single-head attention, M05's full transformer block — has an idiomatic PyTorch equivalent that is a near-literal translation, not a redesign:

| built from scratch | idiomatic PyTorch | what actually changed |
|---|---|---|
| M02 `MLP`/`Layer`/`Neuron` | `nn.Sequential(nn.Linear, nn.Tanh, ...)` | parameter bookkeeping only |
| M03 `im2col`-based conv (NumPy) | `nn.Conv2d` | dispatch target: BLAS call → cuDNN kernel |
| M04 `RNNCell` (M01 `Value` loop) | `nn.RNNCell` / `nn.RNN` | scalar closures → batched, fused CUDA/CPU kernel |
| M04 hand-rolled scaled dot-product attention | `torch.nn.functional.scaled_dot_product_attention` or a manual `Q@K.T` in `torch` | identical formula, vectorized across heads and batch |
| M05 transformer block | `nn.TransformerEncoderLayer` (or a hand-assembled `nn.MultiheadAttention` + `nn.LayerNorm` + MLP) | same block, PyTorch owns the plumbing |

The audit technique that makes "these are the same" a checkable claim rather than an assertion is always the same three-step move, and it is the single most important habit this module installs: **(1) build both versions, (2) copy the exact same weight values from the hand-rolled version into the PyTorch version, (3) feed both the exact same input and diff the outputs.** If the diff is at floating-point roundoff, the two are computing the same function. If it is not, either a shape/transpose mismatch, a missing scaling factor, or a genuinely different operation is hiding somewhere — and the diff tells you which layer to inspect, exactly the way M01's `gradcheck` told you which operation's `_backward` to re-derive.

**Worked example — single-head scaled dot-product attention, hand-rolled NumPy vs. the weight-copy parity check.** Four tokens, input dimension 4, key/query/value dimension 3, deterministic weights and input (`np.random.default_rng(7)`):

This is the check Lab M06-C runs formally, and it is the check to run on *any* PyTorch layer you are not yet sure you trust: load identical weights, feed identical input, diff. `nn.MultiheadAttention` passes this same check (once you account for its packed `in_proj_weight` layout, which stacks `Wq`/`Wk`/`Wv` into one tensor rather than three — a storage detail, not a mathematical one).

**Named misconception 1 — "`nn.MultiheadAttention` (or any library attention implementation) computes something more sophisticated than the attention derived by hand in M04."** Refuted directly by the weight-copy parity check: once the same `Wq`/`Wk`/`Wv` values are loaded into both versions and the same tokens are fed in, the outputs match to floating-point precision. "Multi-head" adds exactly one structural idea beyond M04's single head — run several independent `(Wq, Wk, Wv)` triples in parallel and concatenate their contexts — and that idea is also just repeating the single-head formula, batched, not a new mechanism.

**Named misconception 2 — "using a library layer means you no longer understand what happens inside it."** Every PyTorch layer's parameters are inspectable (`layer.state_dict()`), every intermediate tensor is inspectable via forward hooks (`module.register_forward_hook(...)`), and — as this lesson just demonstrated — every layer's *function* is checkable by the weight-copy-and-diff technique. Opacity is a choice (not reading the source, not running the parity check), not a property `nn.Module` forces on you.

**Named misconception 3 — the ethics-thread one: "if I can rebuild an architecture from scratch and prove it's numerically identical to the library version, I understand how the resulting model will behave."** This is false, and it is false in a way the parity check itself cannot catch, because the parity check only ever compares *architectures* — the same weights through the same graph produce the same output, on both sides, by definition. It says nothing about what a **trained** version of that architecture — weights learned from data, not copied in by hand — will actually do on inputs you didn't test. Two attention heads can be architecturally identical, numerically verified down to the sixteenth decimal digit, and still learn to attend to wildly different things depending on what they were trained on. "I built it, therefore I understand its behavior" is the exact substitution this module's Tier 2 reading names as something the field's own benchmarking practice quietly relies on and rarely says out loud. Lab M06-C's ablation step is built to make you feel that gap, not just read about it.

def hand_backward(x, target, W1, b1, W2, b2):
    x = np.asarray(x, dtype=np.float64)
    z1 = W1 @ x + b1
    h1 = np.tanh(z1)
    yhat = W2 @ h1 + b2
    dL_dyhat = 2 * (yhat - target)
    dL_dh1 = W2.T @ dL_dyhat if W2.ndim == 2 else W2 * dL_dyhat
    dL_dz1 = np.ravel(dL_dh1) * (1 - h1 ** 2)
    dL_dW1 = np.outer(dL_dz1, x)

# solution.py
import time
import numpy as np
import torch
import torch.nn as nn

torch.set_default_dtype(torch.float64)


def naive_conv(img, kernels):
    C_out, kh, kw = kernels.shape
    out_h, out_w = img.shape[0] - kh + 1, img.shape[1] - kw + 1
    out = np.zeros((C_out, out_h, out_w))
    for c in range(C_out):
        for i in range(out_h):
            for j in range(out_w):
                acc = 0.0
                for a in range(kh):
                    for b in range(kw):
                        acc += img[i + a, j + b] * kernels[c, a, b]
                out[c, i, j] = acc
    return out


def im2col_conv(img, kernels):
    C_out, kh, kw = kernels.shape
    out_h, out_w = img.shape[0] - kh + 1, img.shape[1] - kw + 1
    cols = np.stack([img[i:i + kh, j:j + kw].ravel()
                      for i in range(out_h) for j in range(out_w)])
    W = kernels.reshape(C_out, -1)
    return (cols @ W.T).T.reshape(C_out, out_h, out_w)


def torch_conv(img_t, kernels_t):
    C_out, kh, kw = kernels_t.shape
    layer = nn.Conv2d(1, C_out, kernel_size=(kh, kw), bias=False)
    with torch.no_grad():

    x = img_t.unsqueeze(0).unsqueeze(0)               # (1, 1, H, W)
    return layer, x

def test_torch_matches_numpy_reference(toy):
    """The weight-copy-and-diff parity check, formalized."""
    d_in, d_k, Wq, Wk, Wv, X = toy
    ctx_np, w_np = numpy_attention(X, Wq, Wk, Wv, d_k)
    model = load_weights(TorchAttention(d_in, d_k), Wq, Wk, Wv)
    ctx_t, w_t = model(torch.from_numpy(X))
    assert np.abs(w_np - w_t.detach().numpy()).max() < 1e-8
    assert np.abs(ctx_np - ctx_t.detach().numpy()).max() < 1e-8


def test_zeroing_query_projection_produces_uniform_attention(toy):
    """If every query is the zero vector, every score is 0/sqrt(d_k) = 0,
    and softmax of an all-zero vector is uniform -- 1/seq per position,
    regardless of what the keys are. This is the ablation's mathematical
    prediction, made into an assertion."""
    d_in, d_k, Wq, Wk, Wv, X = toy
    model = load_weights(TorchAttention(d_in, d_k), Wq, Wk, Wv)
    with torch.no_grad():
        model.Wq.weight.zero_()
    _, weights = model(torch.from_numpy(X))
    seq = X.shape[0]
    expected = np.full((seq, seq), 1.0 / seq)
    assert np.allclose(weights.detach().numpy(), expected, atol=1e-10)

## Assessment — "the gradients stopped updating right"

**Scenario.** You are handed `train.py`: a from-scratch-to-PyTorch port of the M02 linear-regression training loop (the simplest case that still exercises every mechanism this module covers — a `Parameter`, a `.backward()` call, an optimizer `.step()`). It fits `y = 2x + 1` on four points. It runs without error, top to bottom, no traceback, no NaN, no shape mismatch. Its loss log looks like this:

```
step 0: loss=41.000000
step 1: loss=18.192600
step 2: loss=0.504914      <- looks great, converging fast
step 3: loss=9.594853      <- jumped back up
step 4: loss=34.331356     <- now worse than step 1
step 5: loss=44.424214     <- worse than step 0
step 6: loss=27.513987
step 7: loss=4.305966
```

The learner is *not* handed the diff against a known-good version. The learner is handed this log, the full `train.py` source, and the assessment's grading is on the judgment trail — predict, locate, fix, prove — not on whether a corrected script happens to run.

**Predict.** Before opening `train.py` past a first read, write down: (1) which category of bug this is — a data bug, a model/architecture bug, or a gradient-management bug — and the specific piece of evidence in the loss log that rules out the other two categories; (2) a specific mechanism, named, for how a training loop with a completely correct forward pass, a completely correct loss function, and a completely correct optimizer can still produce this exact shape of curve (fast initial improvement, then overshoot, then partial recovery); (3) which single line you expect to be missing or misplaced, stated as a prediction to be checked, not a guess to be revised after peeking.

**Locate.** Find the exact line (or absence of a line) responsible. "Somewhere in the training loop" does not satisfy this step — cite the line number and the specific call that is missing or misordered.

**Fix.** Correct it with the minimal change — this assessment is not asking for a rewrite of `train.py`, it is asking for the one-line (or few-line) fix that removes the specific defect you located.

**Prove — three independent kinds of evidence, all required:**

1. **Rerun evidence.** The corrected script's loss log, run to the same 8 steps, must monotonically decrease (or come extremely close — a single non-monotonic step from optimizer noise is acceptable, six-out-of-eight-steps getting *worse* is not).
2. **Mechanistic evidence — a targeted test.** Write (or adapt Lab M06-A's) a test that isolates the *specific* defect: e.g., a test asserting that `param.grad` immediately after a given step's `.backward()` equals that step's *own* gradient, not an accumulation of every step's gradient since the start of training.
3. **Written evidence — one paragraph, tied to a specific lesson.** Explain, referencing the exact mechanism from this module (not "PyTorch is finicky"), why this bug produces *this specific* loss curve shape rather than, say, an immediate crash or a silently-wrong-but-stable answer. A correct answer will invoke Lesson 1 misconception 3 or Lesson 3's "optimizer reads only `.grad`" fact by name, in the learner's own words, connected to the actual numbers in the log (e.g., why the effective step size at step 4 is roughly `4×` the step size at step 1, if the defect is the one this assessment plants).

**Gaming-resistant rubric.**

| Criterion | Fails to demonstrate | Meets bar | Exceeds bar |
|---|---|---|---|
| **Predict** | No prediction filed before locating, or prediction is unfalsifiable ("something's wrong with gradients") | Predicts bug category and cites the specific loss-log evidence ruling out the other categories, before opening the fix | Prediction also states the *mechanism* (grad accumulation → growing effective step size) before locating the line, and that mechanism matches the actual defect |
| **Locate** | Cites "the training loop" or a wrong line; or found the right line only after being shown the log's numeric pattern by trial-and-error edits | Cites the exact line/omission, independent of trial-and-error (the loss-log evidence alone was sufficient) | Also explains why the bug is *silent* — no exception, no shape error — tying it to the specific PyTorch semantics that make it silent |
| **Fix** | Fix removes the symptom (e.g., lowers the learning rate until the curve looks smoother) without removing the defect | Minimal, correct fix that removes the actual defect (restores the missing/misordered call) | Fix is accompanied by a one-line comment explaining *why* this call must occur in this position relative to `.backward()` and `.step()` |
| **Prove — rerun** | No rerun, or rerun loss log still non-monotonic in a way inconsistent with a real fix | Rerun log is included and monotonically improves | Rerun is compared numerically against the *original correct* trajectory from Lesson 3 / this module's reference and matches to a stated tolerance |
| **Prove — test** | No test, or a test that only checks "loss went down" (passes even under a different, unrelated fix) | A test that isolates the specific defect (e.g., asserts `.grad` does not accumulate across an un-zeroed step) and would fail against the original buggy script | Test also fails against at least one *plausible wrong fix* (e.g., "just lower the learning rate") the learner explicitly considered and rejected, cited in the written evidence |
| **Prove — written** | Restates that the script "works now" with no mechanism named | Names the correct mechanism (grad accumulation, or whichever defect was planted) by lesson and explains the loss-curve shape it produces | Connects the mechanism explicitly back to M01 Lesson 3's `Value.grad` `+=` semantics — i.e., correctly identifies that this "PyTorch bug" is not PyTorch-specific at all |

A learner who patches the symptom (drops the learning rate until the loss curve happens to look smoother, without ever locating or naming the actual defect) fails **Locate**, **Fix**, and the mechanistic **Prove** criteria even if the rerun curve technically decreases — the rubric is built so "it runs, and the numbers went down" is reachable by three or four different actions, only one of which is the real fix, and only the judgment trail (predict → locate → fix → prove) distinguishes them.

## Three-tier reading — PyTorch fluency and the modern stack

**Tier 1 — material ground, checkable.** Framework-driven speedups are not folklore; they are a direct, measurable consequence of moving batched numerical operations from a Python-level interpreter loop into compiled, vendor-tuned kernels (BLAS/MKL on CPU, cuBLAS/cuDNN on GPU), exactly as this module's own benchmark labs measured on real hardware, not asserted from a marketing table. This is also why "the framework got faster" and "the model got better" are independent claims that the field keeps conflating in public discourse: a 10× throughput improvement from a new kernel library changes nothing about what any given trained model has learned to do — it only changes how quickly you can run the identical computation. Every parity check this module runs (Lab A's gradient diff, Lab B's output diff, Lab C's weight-copy diff) is evidence of exactly one thing: architectural equivalence between a hand-rolled implementation and a library one, verified numerically rather than assumed.

**Tier 2 — what the field doesn't say out loud.** The industry's benchmarking and "framework fluency" culture routinely substitutes *architecture parity* for *understanding*, in both directions, and both substitutions are load-bearing lies of convenience. In one direction: a huge number of practicing engineers can call `nn.MultiheadAttention`, `nn.Conv2d`, and `torch.optim.Adam` fluently, ship production models with them, and have never once derived the backward pass those calls perform — "I use it correctly" is treated, tacitly, as equivalent to "I understand it," and the gap rarely surfaces until something breaks in a way no StackOverflow answer covers, at which point the gap is suddenly very expensive. In the other direction — the one this module's own pedagogy has to guard against in itself — a learner who *has* rebuilt every layer from scratch and verified numerical parity against the library version can walk away with an equally false confidence: "I built the architecture, therefore I understand what a trained instance of it will do." Lesson 4's Named Misconception 3 and Lab M06-C's ablation exist because that confidence is exactly as unearned as the first kind. Architecture parity is a claim about a *fixed set of weights* producing the *same output* through the *same graph* — it says nothing about what a different set of weights, learned from data nobody hand-picked, will do with that same graph. The field's benchmarking practice — comparing model architectures on leaderboards, publishing ablation tables, citing parameter-matched baselines — runs on exactly this substitution, silently, at scale, and mostly gets away with it because "the architecture is well-understood" reads, to a reader skimming a paper's methods section, as "the model's behavior is well-understood." It is not the same claim.

**Tier 3 — sit with this, don't resolve it.** You can now, in this module, take any PyTorch layer apart, load your own weights into it, and prove — not assert, prove, with a diff on screen — that it computes exactly the function you already understood before you ever imported `torch`. That is real, earned fluency, and it is also, deliberately, the *last* thing this course lets you fully verify. Starting in M07, you will debug pathological *trained* models — models whose architecture you can audit completely and whose behavior you cannot predict from that audit alone. Here is the question this module leaves open, on purpose, for you to keep carrying rather than answer today: when a system's architecture is fully known, fully rebuildable, fully verified down to the sixteenth decimal digit — and its trained behavior still surprises the people who built it — where does that surprise actually live? Is it a temporary gap, one better tooling or a more careful audit will eventually close? Or is "the weights learned something the architecture doesn't predict and the builder didn't intend" simply what training *is*, permanently, no matter how well you understand every operation in the graph? You will not need to answer this to pass M07's debugging labs. You will need to have asked it honestly, here, before the debugging starts to feel like it should have a tidy resolution.
