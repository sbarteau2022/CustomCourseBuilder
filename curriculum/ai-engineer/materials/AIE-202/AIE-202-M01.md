## Lessons

### Lesson 1 — What autograd actually is: a graph you build, then walk backward

In AIE-103-M03 you computed `∂g/∂a` for expressions like `g = (a·b + c)·2` entirely on paper, by hand, applying the chain rule term by term. That process had two phases whether or not you noticed them: first you evaluated the expression forward, arriving at a number; second you walked back through every intermediate step, multiplying local derivatives together, until you reached `a`. Autograd is that same two-phase process, mechanized. The forward pass does not just compute a number — it **builds a graph** as a side effect, a record of every operation and its inputs. The backward pass then **walks that graph in reverse**, applying the chain rule at each node using only information local to that node: the operation's own derivative rule and the gradient handed to it from the node downstream. Nothing about backward differentiation requires global knowledge of the whole expression at any single point — that is precisely what makes it mechanizable into a general-purpose engine instead of a fresh hand-derivation for every new expression.

The record of the forward pass — the graph of who-came-from-what — is usually called **the tape**. "Tape" is a historical name (from the reel-to-reel tape recorders early automatic-differentiation systems used as a metaphor for an append-only log of operations) and it survives in the field's vocabulary: PyTorch's `autograd` module is famously described as recording a tape as your code runs. You are about to build exactly that.

**Worked example.** Take `g = (a·b + c)·2` with `a=2, b=-3, c=10`. Forward pass: `e = a·b = -6`, `f = e + c = 4`, `g = f·2 = 8`. That forward pass, if it also records each node's inputs, has built this graph:

```
a ──┐
    ├─(*)─→ e ──┐
b ──┘            ├─(+)─→ f ──(*2)─→ g
c ───────────────┘
```

Backward pass, seeded with `∂g/∂g = 1`: `∂g/∂f = 2` (local rule for `·2`). `∂g/∂e = ∂g/∂f · ∂f/∂e = 2·1 = 2` and `∂g/∂c = ∂g/∂f · ∂f/∂c = 2·1 = 2` (local rule for `+` is "pass the gradient through unchanged to both inputs"). `∂g/∂a = ∂g/∂e · ∂e/∂a = 2·b = 2·(-3) = -6` and `∂g/∂b = ∂g/∂e · ∂e/∂b = 2·a = 2·2 = 4` (local rule for `*` is "multiply by the *other* input"). Final: `a.grad = -6, b.grad = 4, c.grad = 2`. Every one of those steps used only the node's own local rule and the single number handed down from above — never the full expression at once. That locality is the whole design.

**Named misconception: "the engine differentiates the expression."** It does not. There is no symbolic expression anywhere in memory once the forward pass finishes — there is only a graph of concrete numbers and closures. Autograd is not symbolic differentiation (what a computer algebra system does to `y = x²` to produce the string `"2x"`) and it is not numeric differentiation (finite differences, which you'll build as the *verifier* for this engine in Lesson 4, not as the engine itself). It is a third thing: **reverse-mode automatic differentiation**, exact to floating-point precision, computed by executing local derivative rules along a concrete recorded path. This distinction is not academic pedantry — it is the reason autograd can differentiate through Python control flow (`if` statements, loops with data-dependent bounds) that would defeat a symbolic system, and the reason it needs the graph rebuilt fresh on every forward pass, which is a design choice you'll feel directly in Lab M01-C when the graph is thrown away and rebuilt every training step.

### Lesson 2 — The `Value`: local derivatives, closed over

The tape needs a concrete home. Build a class, `Value`, that wraps a single number and, every time it is combined with another `Value` through an operation, records what made it and *how to route a gradient backward through that operation* — as a closure, captured at the moment the operation happens.

```python
class Value:
    def __init__(self, data, _children=(), _op=""):
        self.data = data
        self.grad = 0.0
        self._backward = lambda: None   # default: leaf node, nothing to propagate
        self._prev = dict.fromkeys(_children)  # the nodes that fed into this one (order-preserving, deduplicated)
        self._op = _op                  # for debugging/printing only

    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other), "+")
        def _backward():
            self.grad  += 1.0 * out.grad
            other.grad += 1.0 * out.grad
        out._backward = _backward
        return out

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other), "*")
        def _backward():
            self.grad  += other.data * out.grad
            other.grad += self.data  * out.grad
        out._backward = _backward
        return out
```

Read `_backward` for `__mul__` against Lesson 1's local rule: "multiply by the other input" is `other.data * out.grad` and `self.data * out.grad` — exactly the chain rule term for each parent, expressed as code. Every operation you add to this class (subtraction, division, powers, `tanh`, `exp`, `relu`) is the same move: compute the forward value, and in the same breath write the one-line local derivative rule as a closure that will run later, during the backward pass, once `out.grad` is known.

**Why a closure and not a lookup table.** `_backward` closes over `self`, `other`, and `out` — three specific objects that exist at the moment the operation was called, not three names re-resolved later. This is what lets each node's backward rule be self-contained: when the engine later calls `out._backward()` in some arbitrary later moment, it does not need to know *which* operation produced `out` or look up a rule by op-name; it just calls the function that op-specific code already attached. This is also precisely why the graph must be rebuilt every forward pass — the closures reference concrete objects from *this* pass, not a reusable template.

**Named misconception: "`_backward` runs the chain rule."** `_backward` is *one link* of the chain rule — it converts one node's `out.grad` (the accumulated gradient *up to* that node, handed down from everything above it) into contributions to its own inputs' `.grad`. The chain rule as a whole is not implemented in any single method; it emerges from calling every node's `_backward` exactly once, in the right order, after `out.grad` has already received every contribution it is ever going to receive. Get that order wrong — call a node's `_backward` before all of its downstream consumers have contributed to `out.grad` — and the "chain rule" silently computes garbage using an incomplete `out.grad`. That order is Lesson 3.

### Lesson 3 — Topological order and why gradients accumulate

`out.grad` must be *complete* before `out._backward()` runs — every node that used `out` as an input must have already added its contribution. That is a **topological order** constraint: process every node only after all of its consumers (the nodes that used it as an input) have been processed. Reverse of that requirement — build a list where each node appears only after all of *its own inputs* have been listed (a standard post-order depth-first traversal), then walk that list in reverse.

```python
def backward(self):
    topo, visited = [], set()
    def build(v):
        if v not in visited:
            visited.add(v)
            for child in v._prev:
                build(child)
            topo.append(v)          # append AFTER recursing into children
    build(self)
    self.grad = 1.0                 # seed: d(self)/d(self) = 1
    for v in reversed(topo):
        v._backward()
```

Two details earn their keep here. First, `self.grad = 1.0` — the seed. `.backward()` is always called on the final scalar (a loss), and the derivative of anything with respect to itself is 1; every other gradient in the graph is scaled relative to that seed. Miss it and every single downstream gradient computes as some multiple of zero, silently. Second, `self.grad += ...` in every backward closure, not `=`. This is the detail that separates a toy that happens to work on simple chains from an engine that survives contact with a real network, where a weight is reused across many timesteps or many neurons feed from the same input — a **diamond** in the graph.

**Worked example — the diamond.** `b = a * a`, with `a = 3`. Here `a` is *the same object* used as both operands of `*`. By the ordinary product rule, `d(a²)/da = 2a = 6`. Trace it through the engine: `b`'s `_backward` runs `self.grad += other.data * out.grad` then `other.grad += self.data * out.grad` — but `self` and `other` are the same `Value` object, so both lines add into the *same* `.grad` attribute: `3.0 * 1.0` then `3.0 * 1.0` again, landing on `6.0`. That correctness is entirely due to `+=`. Swap it for `=` and the second write **overwrites** the first instead of adding to it: `a.grad` ends at `3.0`, not `6.0` — silently half the correct answer, and every graph without a diamond in it would have looked completely correct while you tested it that way, because a plain chain (`a` used exactly once) never exercises the difference between `=` and `+=` at all.

**Named misconception: "if my simple test cases pass, accumulation is not a real bug."** This is the misconception Lab M01-B is built to break. An overwrite bug is invisible on any expression where every value is consumed exactly once, and every neural network you will build starting in M02 reuses weights across many inputs — the diamond is not an edge case in this engine, it is the normal shape of every real graph you will ever build on it.

### Lesson 4 — Trusting nothing: gradcheck against finite differences

You now have an engine that *computes* gradients. You have no evidence yet that it computes *correct* ones beyond hand-tracing three-node examples. The independent check is **numerical differentiation** — finite differences — which needs none of the machinery above and is therefore trustworthy as a referee: perturb one input by a small `ε`, measure how much the output moved, divide. The **central difference** form is standard because its error shrinks as `O(ε²)` rather than `O(ε)` for the one-sided version:

```
f'(x) ≈ (f(x + ε) − f(x − ε)) / (2ε)
```

```python
def gradcheck(f, inputs, eps=1e-6):
    out = f(inputs)
    for v in inputs:
        v.grad = 0.0
    out.backward()
    analytic = [v.grad for v in inputs]

    numeric = []
    for v in inputs:
        orig = v.data
        v.data = orig + eps; f_plus  = f(inputs).data
        v.data = orig - eps; f_minus = f(inputs).data
        v.data = orig
        numeric.append((f_plus - f_minus) / (2 * eps))

    max_rel_err = max(
        abs(a - n) / max(abs(a), abs(n), 1e-8)
        for a, n in zip(analytic, numeric)
    )
    return analytic, numeric, max_rel_err
```

**Worked example.** `f(a,b,c) = tanh(a·b + c)` at `a=0.9, b=-0.7, c=0.3`. The engine's `.backward()` reports `analytic = [-0.628981160277, 0.808690063213, 0.898544514681]`. `gradcheck` reports `numeric = [-0.628981160294, 0.808690063248, 0.898544514655]`. Max relative error: `4.3e-11` — agreement to ten significant figures, the expected size of floating-point-plus-truncation error at `ε = 1e-6`, and the signature of a correct backward pass. Contrast with the broken accumulation engine from Lesson 3 on `f = a·a + a` at `a=3`: analytic reports `3.0`; `gradcheck`'s numeric side (using the *correct* engine as referee, since finite differences need no backward pass at all) reports `7.000000002`. Relative error `≈ 0.57` — not floating-point noise, a wrong answer by more than half, and gradcheck is what turns "the loss curve looks a little off" into "parameter 3 of 41 fails gradcheck at 57% relative error" before you have wasted a single GPU-hour training on it.

**Named misconception: "if the loss goes down, the gradients must be right."** They do not have to be. Broken gradients can still point in a direction correlated enough with the true descent direction to shrink the loss for a while — noisy, sub-optimal, and often silently capped at a much worse final result than the correct gradient would have reached, with no error message anywhere to tell you why. A training curve that goes down is evidence of *a* direction, not evidence that it is *the right* direction. Gradcheck is the only test in this module that checks the mechanism directly rather than inferring it from a downstream symptom, and it is why Lab M01-A never lets you touch training before every operation in the engine passes it.

```python
# lab_a_solution.py
import math

class Value:
    def __init__(self, data, _children=(), _op=""):
        self.data = data
        self.grad = 0.0
        self._backward = lambda: None
        self._prev = dict.fromkeys(_children)  # order-preserving, deduplicated (deterministic backward order)
        self._op = _op

    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other), "+")
        def _backward():
            self.grad  += 1.0 * out.grad
            other.grad += 1.0 * out.grad
        out._backward = _backward
        return out

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other), "*")
        def _backward():
            self.grad  += other.data * out.grad
            other.grad += self.data  * out.grad
        out._backward = _backward
        return out

    def __pow__(self, p):
        assert isinstance(p, (int, float)), "only supports int/float powers"
        out = Value(self.data ** p, (self,), f"**{p}")
        def _backward():
            self.grad += (p * self.data ** (p - 1)) * out.grad
        out._backward = _backward
        return out

    def tanh(self):
        t = math.tanh(self.data)
        out = Value(t, (self,), "tanh")
        def _backward():
            self.grad += (1 - t ** 2) * out.grad
        out._backward = _backward
        return out

    def relu(self):
        out = Value(0.0 if self.data < 0 else self.data, (self,), "ReLU")
        def _backward():
            self.grad += (out.data > 0) * out.grad
        out._backward = _backward
        return out

    def __neg__(self): return self * -1
    def __radd__(self, other): return self + other
    def __sub__(self, other): return self + (-other)
    def __rsub__(self, other): return other + (-self)
    def __rmul__(self, other): return self * other
    def __truediv__(self, other): return self * other**-1
    def __rtruediv__(self, other): return other * self**-1

    def backward(self):
        topo, visited = [], set()
        def build(v):
            if v not in visited:
                visited.add(v)
                for child in v._prev:
                    build(child)
                topo.append(v)
        build(self)
        self.grad = 1.0
        for v in reversed(topo):
            v._backward()

    def __repr__(self):
        return f"Value(data={self.data:.6g}, grad={self.grad:.6g})"


def gradcheck(f, inputs, eps=1e-6):
    out = f(inputs)
    for v in inputs:
        v.grad = 0.0
    out.backward()
    analytic = [v.grad for v in inputs]

    numeric = []
    for v in inputs:
        orig = v.data
        v.data = orig + eps; f_plus  = f(inputs).data
        v.data = orig - eps; f_minus = f(inputs).data
        v.data = orig
        numeric.append((f_plus - f_minus) / (2 * eps))

    max_rel_err = max(
        abs(a - n) / max(abs(a), abs(n), 1e-8)
        for a, n in zip(analytic, numeric)
    )
    return analytic, numeric, max_rel_err
```

### Lab M01-B — Break it on purpose

*Predict (on paper, before running anything).* You are given four **complete, standalone** mutated copies of the Lab M01-A engine, each with exactly one planted bug, described below by diff rather than by name. Each copy is its own full file — this matters, and Build will show you why. For each bug, predict its result on *three* differently-shaped test expressions before running anything: (1) a **chain**, `(a*b+c)*2` with no value reused; (2) a **diamond**, `a*a+a`, where `a` is reused but `**` is never called; (3) a **pow probe**, `a**2` on a single leaf, two nodes deep, no reuse and no `+`. For each of the twelve (bug × shape) cells, predict pass or fail, and if fail, whether you expect a wrong-but-nonzero number or a value stuck at zero.

- **Bug 1 — accumulation.** Every `_backward` closure uses `=` instead of `+=`.
- **Bug 2 — power rule.** `__pow__`'s local derivative is written as `p * self.data ** p` (missing the `-1` in the exponent).
- **Bug 3 — traversal order.** In `build`, the line `topo.append(v)` is moved to *before* the loop that recurses into `v._prev`, instead of after.
- **Bug 4 — missing seed.** `backward()` never sets `self.grad = 1.0` before the loop.

*Build.* A tempting way to write these four files is to subclass the correct engine and override only the one broken method. **Do not do this — it does not work, and discovering why is part of the lab.** `Value.__add__` and `Value.__mul__` construct their output node by calling the literal name `Value(...)`, not `type(self)(...)`. If a `Bug3` subclass only overrides `backward()`, then the very first `a * b` inside a chain silently constructs a plain, correct `Value` node instead of a `Bug3` node — the bug falls out of the graph after one hop, and you would ship a "broken" engine that quietly always uses the correct code path. Each bug below is instead a full standalone class, every arithmetic method rewritten, so the one planted mutation is the only thing different from Lab M01-A's solution anywhere in the file — the same shape of file the module assessment will later hand you unseen.

```python
# lab_c_solution.py
import random
from lab_a_solution import Value

class Neuron:
    def __init__(self, nin):
        self.w = [Value(random.uniform(-1, 1)) for _ in range(nin)]
        self.b = Value(0.0)

    def __call__(self, x):
        act = sum((wi * xi for wi, xi in zip(self.w, x)), self.b)
        return act.tanh()

    def parameters(self):
        return self.w + [self.b]

class Layer:
    def __init__(self, nin, nout):
        self.neurons = [Neuron(nin) for _ in range(nout)]

    def __call__(self, x):
        outs = [n(x) for n in self.neurons]
        return outs[0] if len(outs) == 1 else outs

    def parameters(self):
        return [p for n in self.neurons for p in n.parameters()]

class MLP:
    def __init__(self, nin, nouts):
        sz = [nin] + nouts
        self.layers = [Layer(sz[i], sz[i + 1]) for i in range(len(nouts))]

    def __call__(self, x):
        for layer in self.layers:
            x = layer(x)
        return x

    def parameters(self):
        return [p for layer in self.layers for p in layer.parameters()]


def train(model, xs, ys, lr=0.05, epochs=30):
    losses = []
    for epoch in range(epochs):
        ypred = [model(x) for x in xs]
        loss = sum((yout - ygt) ** 2 for ygt, yout in zip(ys, ypred))
        for p in model.parameters():
            p.grad = 0.0
        loss.backward()
        for p in model.parameters():
            p.data -= lr * p.grad
        losses.append(loss.data)
    return losses
```

## Three-tier reading

Specific to this module's subject — what it means to build, and then trust, the machine that computes every gradient for the rest of the course.

- **Tier 1 — material ground.** Reverse-mode automatic differentiation is not a heuristic or an approximation — it computes exact derivatives (to floating-point precision) at a cost of roughly one extra pass over the graph, independent of the number of parameters being differentiated with respect to. This is precisely why training a network with a hundred million parameters against one scalar loss is tractable at all: forward-mode differentiation would cost one full pass *per parameter*. This asymmetry is documented in the field's own literature on automatic differentiation (surveyed comprehensively in Baydin, Pearlmutter, Radul & Siskind, "Automatic Differentiation in Machine Learning: a Survey," 2018), not a claim original to this course.
- **Tier 2 — what the field suppresses.** "We built the engine, we understand it" quietly elides a gap. Passing gradcheck proves the *mechanism* is correct — that the machine implements calculus faithfully on the graph you handed it. It proves nothing about whether that graph — the architecture, the loss function you wired it to — encodes the objective you actually intend. A perfectly correct autograd engine will backpropagate flawlessly into a subtly wrong loss function and hand you exact, confident, entirely correct gradients pointed at the wrong target, with no error anywhere in the chain to warn you. The field's language around "interpretable," "well-understood" architecture routinely collapses these two very different kinds of correctness into one reassuring sentence.
- **Tier 3 — sit with this.** From this module forward, you will trust `.backward()` — first the one you wrote, then PyTorch's, for the rest of this course and probably your career — the same way you trust `+`. You verified this one, once, by hand, against finite differences that you also had to decide to trust. Every architecture built on top of this module inherits that single act of verification and does not repeat it. At what point in that stack does "I verified this" stop being a true sentence you could actually still defend if asked — and once you've passed that point, what exactly are you trusting instead?

A plain Python `set` of objects without `__hash__`/`__eq__` overrides iterates in an order driven by `id()`-based hashing, which is not guaranteed stable across runs or processes (it can vary with `PYTHONHASHSEED`, memory layout, and object allocation order). `backward()` walks `v._prev` while building the topological order, so a non-deterministic `_prev` iteration order made the topological order — and therefore the exact sequence of floating-point `+=` accumulations in `_backward()` — non-deterministic too. For the short, well-conditioned graphs used in this module's own Lessons and Lab M01-A, floating-point addition is commutative enough in practice that the final numbers don't visibly move. But the same engine is reused unmodified in downstream modules (this module's own header: "M02 wraps this scalar `Value` engine... identical `_backward`-closure and topological-sort design"), where longer, badly-initialized, un-normalized chains can compound run-to-run float-order differences into large final-answer spread — confirmed independently by an adversarial reviewer re-running downstream printed code multiple times and observing >80% relative spread in a downstream table (AIE-202-M02 Lab B). Fix applied everywhere the canonical `Value` class states child storage in this file — Lesson 2's code block, Lab M01-A's starter, and Lab M01-A's solution — changing `self._prev = set(_children)` to `self._prev = dict.fromkeys(_children)`: a plain `dict` preserves first-seen insertion order and still deduplicates repeated children (a node used twice as an operand, e.g. `a*a`, is still visited once in `build()`), so `backward()`'s topological order — and every downstream floating-point accumulation order — is now identical on every run, on every machine, regardless of `PYTHONHASHSEED`.
