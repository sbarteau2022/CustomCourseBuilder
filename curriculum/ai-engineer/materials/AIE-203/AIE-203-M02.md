Every ETL tutorial on the internet shows you the happy path: a script reads a file,
transforms it, writes a table, the demo works, everyone claps. This module refuses that

## Lessons

### Lesson 1 — Raw ETL, by hand

Extract, transform, load is not a framework feature — it is three plain functions and a
place to put the output. Before naming any tool, build the pipeline as three functions
you can read start to finish in thirty seconds: `extract()` reads rows, `transform()`
reshapes and types them, `load()` writes them somewhere durable. This is the "descend"
step: every ETL framework you'll meet later (dbt, Airflow's `PythonOperator`, Dagster's
`@asset`) is this same shape wearing configuration.

The point of building it raw first is that it makes every failure mode visible and
hand-traceable. When `load()` is three lines of `cursor.execute` in a loop, you can see
exactly which row it was on when it died. When it's buried inside a framework's task
abstraction, that same failure produces a stack trace through code you didn't write.

**Worked example.** A daily orders extract, three functions, one SQLite sink:

```python
import csv
import sqlite3


def extract(csv_path: str) -> list[dict]:
    with open(csv_path, newline="") as f:
        return list(csv.DictReader(f))


def transform(rows: list[dict]) -> list[dict]:
    out = []
    for r in rows:
        out.append({
            "order_id": r["order_id"],
            "customer_id": r["customer_id"],
            "amount_cents": round(float(r["amount"]) * 100),
            "updated_at": r["updated_at"],
        })
    return out


def load(conn: sqlite3.Connection, rows: list[dict]) -> None:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS orders (
            order_id TEXT,
            customer_id TEXT,
            amount_cents INTEGER,
            updated_at TEXT
        )
    """)
    for r in rows:
        conn.execute(
            "INSERT INTO orders (order_id, customer_id, amount_cents, updated_at) "
            "VALUES (?, ?, ?, ?)",
            (r["order_id"], r["customer_id"], r["amount_cents"], r["updated_at"]),
        )
    conn.commit()
```

Run it against a three-row `orders.csv` and `orders` has three rows. Clean, readable,
correct — for exactly one invocation. This is the pipeline Lab M02-A hands you to break.

**Named misconceptions**

- *"If `extract` and `transform` are pure functions, the pipeline is safe."* Purity of
  the read/reshape steps buys you nothing about the pipeline's behavior over time — all
  of the danger in this module lives in `load()`, the one stateful step, and in what
  happens between load calls that don't know about each other.
- *"ETL is a framework feature."* Orchestrators schedule and retry ETL; they do not make
  it correct. A framework running a broken `load()` on a schedule just breaks the table
  reliably, on time, forever. Lesson 4 makes this precise.

### Lesson 2 — Idempotency is not free

An operation is idempotent if applying it more than once produces the same result as
applying it once — `f(f(x)) == f(x)`. For a batch load, this is a property about the
**end state of the table**, not about what the second run does internally. A load that
runs its full logic a second time, rewrites every row with byte-identical values, and
changes nothing observable is idempotent. A load that runs faster the second time
because it "did nothing" is a separate, optional optimization — not the requirement.

Lesson 1's loader has no identity: nothing tells the database that two rows both
describing `order_id=O1` are the *same fact reported twice* rather than two different
orders. The fix is a natural key plus an explicit merge rule, expressed as an upsert:

```sql
INSERT INTO orders (order_id, customer_id, amount_cents, updated_at, content_hash)
VALUES (:order_id, :customer_id, :amount_cents, :updated_at, :content_hash)
ON CONFLICT(order_id) DO UPDATE SET
    customer_id   = excluded.customer_id,
    amount_cents  = excluded.amount_cents,
    updated_at    = excluded.updated_at,
    content_hash  = excluded.content_hash
WHERE excluded.updated_at > orders.updated_at;
```

Two things are doing work here. `ON CONFLICT(order_id) DO UPDATE` is the identity: it
makes the primary key the definition of "the same order," so replays land on the same
row instead of appending a new one. The `WHERE excluded.updated_at > orders.updated_at`
clause is a second, separate guarantee: without it, an upsert is idempotent *only* under
in-order replay. Feed it the same batch twice, in the same order, and you're fine. Feed
it a late-arriving batch whose data is *older* than what's already loaded — a retried
message, a straggler partition, a backfill running behind live traffic — and a bare
upsert will happily let stale data stomp fresh data, because "last write wins" silently
means "last **arrival** wins," not "last **truth** wins." The `WHERE` guard makes the
loader order-aware: a row only wins the conflict if it is actually newer, regardless of
when it happened to show up.

**Worked example.** Content hashing turns "did this row change?" into a single
comparable value instead of a five-column diff, and lets the loader report what
actually happened on a replay — not just "success," but *written* vs *skipped, already
current* vs *skipped, arrived stale*:

```python
import hashlib

def transform_row(r: dict) -> dict:
    amount_cents = round(float(r["amount"]) * 100)
    content_hash = hashlib.sha256(
        f"{r['order_id']}|{r['customer_id']}|{amount_cents}".encode()
    ).hexdigest()
    return {**r, "amount_cents": amount_cents, "content_hash": content_hash}
```

Replaying the exact same batch twice against this loader leaves the row count and every
value unchanged — `cur.rowcount` is `0` on the second run because `updated_at` is not
*strictly greater*, and the row is already byte-identical. That zero is the proof of
idempotency, not a bug in the loader.

**Named misconceptions**

- *"Idempotent means the second run does nothing."* Wrong, and this exact wrong belief
  causes learners to "fix" an idempotent loader that's still doing writes on replay
  (equal-but-different-object rows, or an `UPDATE` that reassigns the same values).
  Idempotent means the **end state converges**; work performed to reconfirm that state
  is allowed and often unavoidable.
- *"An upsert on a natural key is enough to make a loader idempotent."* It is enough to
  make it idempotent under *in-order* replay. Without an ordering guard, a bare upsert
  is not idempotent under out-of-order arrival — it is silently wrong in a way that
  produces no error, no exception, and a table that looks perfectly normal. This is the
  single most dangerous property in this lesson: the failure is invisible until someone
  asks "why did this record revert?"

### Lesson 3 — Partial failure and transactional boundaries

A batch of 10,000 rows dies at row 6,342 — a bad row, a lost connection, an out-of-memory
kill. What is true of the table right now, and what does "run it again" mean? The answer
depends entirely on where you drew the transaction boundary, and there are exactly three
strategies, none of them free:

1. **One giant transaction.** `BEGIN`, insert all 10,000 rows, `COMMIT` at the end. If
   row 6,342 is malformed, the whole transaction rolls back — all 6,341 good rows ahead
   of it are discarded too. Recovery means redoing the entire batch from scratch, and if
   the batch is slow, you're now racing the failure that killed it the first time.
2. **Autocommit per row.** Each `INSERT` is its own transaction. A crash at row 6,342
   leaves exactly 6,341 rows committed — no wasted work — but if a single logical record
   spans more than one statement (an order row plus an order-line row), a crash between
   those two statements leaves a logical record half-written, with no transaction
   boundary that ever wrapped both halves together.
3. **Chunked transactions plus a checkpoint.** Commit every N rows (e.g., 500), and
   record the last successfully committed offset in a checkpoint table, in the *same*
   transaction as the chunk it belongs to. A crash loses at most N rows of committed
   progress, a resume reads the checkpoint and continues from there, and because the
   loader from Lesson 2 is idempotent, re-touching a row or two at the seam between
   "already committed" and "resumed from checkpoint" is harmless — the upsert makes
   double-processing the boundary chunk a no-op, not a duplicate.

**Worked example.** A checkpointed batch load: commit every 500 rows, and write the
checkpoint atomically with the data it protects, in the same transaction:

```python
def load_checkpointed(conn, rows: list[dict], batch_id: str, chunk_size: int = 500):
    conn.execute("""
        CREATE TABLE IF NOT EXISTS load_checkpoints (
            batch_id TEXT PRIMARY KEY,
            rows_committed INTEGER NOT NULL
        )
    """)
    start = conn.execute(
        "SELECT rows_committed FROM load_checkpoints WHERE batch_id = ?", (batch_id,)
    ).fetchone()
    offset = start[0] if start else 0

    for chunk_start in range(offset, len(rows), chunk_size):
        chunk = rows[chunk_start:chunk_start + chunk_size]
        conn.execute("BEGIN")
        try:
            for r in chunk:
                upsert_row(conn, r)  # the Lesson 2 upsert
            new_offset = chunk_start + len(chunk)
            conn.execute(
                "INSERT INTO load_checkpoints (batch_id, rows_committed) VALUES (?, ?) "
                "ON CONFLICT(batch_id) DO UPDATE SET rows_committed = excluded.rows_committed",
                (batch_id, new_offset),
            )
            conn.commit()
        except Exception:
            conn.rollback()
            raise
```

Kill the process at chunk 8 of 20 and re-run with the same `batch_id`: chunks 1–7 are
untouched (already committed, checkpoint says so), chunk 8 is redone in full (its
transaction never committed, so none of it landed — and because `upsert_row` is
idempotent, redoing it is safe even for rows within the chunk that *did* momentarily
exist before the rollback undid them), and chunks 9–20 proceed as normal.

**Named misconceptions**

- *"A bigger transaction is always safer."* It is safer against *inconsistency* (nothing
  half-written survives) and dramatically worse against *availability* — one bad row
  anywhere in a 10,000-row batch destroys all the good work already done, and the
  correct chunk size is not "as big as possible" but "small enough that redoing one
  chunk is cheap."
- *"Autocommit per row is the safe default because it loses the least work."* It loses
  the least *row-level* work while offering zero atomicity across statements — a design
  that is fine for single-statement loads and actively dangerous for multi-table writes.
- *"Idempotency and checkpointing are two ways to solve the same problem — you only need
  one."* They solve different problems and this lesson exists because the field
  conflates them. Checkpointing limits how much work a crash makes you redo.
  Idempotency makes redoing that work safe. A checkpoint without idempotent writes still
  duplicates the boundary chunk; idempotent writes without a checkpoint still force a
  full-batch redo on every failure. You want both.

### Lesson 4 — Build the orchestrator: a ~200-line DAG runner

A batch pipeline is rarely one step. `extract → transform → load → report` is a graph of
tasks with dependencies, and the moment you have more than two steps you need three
things no single script gives you for free: an execution order derived from the
dependencies (not hand-written and easy to get wrong), a retry policy for the step that
talks to something flaky, and — the property this whole module has been building toward
— a way to **re-invoke the whole pipeline safely** after a partial failure, resuming
instead of redoing.

Build the orchestrator at the substrate before naming Airflow or Dagster, so what those
tools add is a concrete, comparable delta instead of unexamined magic. The core of a DAG
runner is smaller than it looks: a topological sort (Kahn's algorithm, met in AIE-110)
to get execution order, a per-task try/retry loop, and a **run ledger** — a table keyed
by `(run_id, task_name)` recording which tasks have already succeeded for this run,
consulted before each task executes and updated after.

**Worked example.** The ledger is what makes `run(run_id)` idempotent at the
orchestration layer — re-invoking it with the same `run_id` after a crash skips every
task already marked `success` and resumes exactly at the one that failed:

```python
def run(self, run_id: str, context: dict | None = None) -> dict:
    context = context if context is not None else {}
    order = self._topo_order()
    results = {}
    for name in order:
        task = self.tasks[name]
        if self._status(run_id, name) == "success":
            results[name] = "skipped-already-succeeded"
            continue
        attempts = 0
        last_err = None
        while attempts <= task.max_retries:
            attempts += 1
            try:
                results[name] = task.func(context)
                self._mark(run_id, name, "success", attempts)
                last_err = None
                break
            except Exception as exc:
                last_err = exc
                self._mark(run_id, name, "failed", attempts)
        if last_err is not None:
            raise DAGError(f"task {name!r} failed after {attempts} attempt(s)") from last_err
    return results
```

Run a four-task DAG (`extract → transform → load → report`) where `load` raises on its
first attempt and succeeds on retry: `extract` and `transform` each run exactly once,
`load` runs twice (attempt 1 fails, attempt 2 succeeds) and is marked `success` once,
`report` runs once. Now simulate a **harder** failure: `load` fails past its retry
budget. `run()` raises. `extract` and `transform` are marked `success` in the ledger;
`load` is marked `failed`; `report` never ran. Fix whatever made `load` fail and call
`run()` again with the **same** `run_id`: `extract` and `transform` are skipped (already
succeeded), `load` is attempted again, `report` runs after it succeeds. Call `run()`
with a **new** `run_id` instead, and everything runs from scratch — a fresh ledger row
for every task. That distinction, same-`run_id`-resumes vs new-`run_id`-restarts, is the
entire idempotency contract of the orchestration layer, stated in one sentence a learner
should be able to recite before touching Airflow's `run_id`/`execution_date` semantics,
which are this exact mechanism with a scheduler daemon and a UI wrapped around it.

**What Airflow/Dagster add on top.** Not the DAG-plus-ledger-plus-retry core — you just
built that. They add: a **scheduler daemon** that fires runs on a cron/sensor without a
human invoking `run()`; a **distributed executor** that runs tasks across workers instead
of one process, so the ledger has to be a shared database, not a local SQLite file;
**sensors** that block a task until an external condition is true (a file lands, an
upstream DAG finishes) instead of you hand-coding a poll loop; a **backfill CLI** that
re-runs a DAG across a historical range of `run_id`s in one command; a **UI** over the
exact ledger table you just built by hand, so "which tasks failed last Tuesday" is a
click instead of a `SELECT`; and, in Dagster specifically, **asset lineage** — the DAG
is defined over the *data* (an "asset") rather than the *task*, so the tool can tell you
which downstream tables are stale when an upstream one changes. Every one of these is a
real, valuable addition. None of them is the idea. The idea is the run ledger.

**Named misconceptions**

- *"The DAG runner makes the pipeline idempotent."* It makes **re-invocation** of the
  pipeline safe — it does not make any individual task idempotent. If `load`'s own logic
  is Lesson 1's naive appender wrapped in a task, resuming after a partial failure will
  happily duplicate whatever `load` half-wrote before it died. The orchestrator's
  idempotency and the task's idempotency are two separate properties, built in two
  separate lessons, and both are required.
- *"Airflow is just a nicer version of what we built."* It is what we built, run by a
  scheduler, distributed across workers, with a UI — genuine, substantial engineering —
  but a learner who cannot say what the run ledger is doing underneath Airflow's
  `TaskInstance` table has not actually understood the tool, only memorized its screens.

# idempotent_etl.py — solution
import csv
import hashlib
import sqlite3


def extract(csv_path: str) -> list[dict]:
    with open(csv_path, newline="") as f:
        return list(csv.DictReader(f))


def transform(rows: list[dict]) -> list[dict]:
    out = []
    for r in rows:
        amount_cents = round(float(r["amount"]) * 100)
        content_hash = hashlib.sha256(
            f"{r['order_id']}|{r['customer_id']}|{amount_cents}".encode()
        ).hexdigest()
        out.append({
            "order_id": r["order_id"],
            "customer_id": r["customer_id"],
            "amount_cents": amount_cents,
            "updated_at": r["updated_at"],
            "content_hash": content_hash,
        })
    return out


def ensure_schema(conn: sqlite3.Connection) -> None:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS orders (
            order_id TEXT PRIMARY KEY,
            customer_id TEXT NOT NULL,
            amount_cents INTEGER NOT NULL,
            updated_at TEXT NOT NULL,
            content_hash TEXT NOT NULL
        )
    """)
    conn.commit()


def load(conn: sqlite3.Connection, rows: list[dict]) -> dict:
    ensure_schema(conn)
    stats = {"written": 0, "skipped_stale": 0, "skipped_unchanged": 0}
    for r in rows:
        cur = conn.execute(
            """
            INSERT INTO orders (order_id, customer_id, amount_cents, updated_at, content_hash)
            VALUES (:order_id, :customer_id, :amount_cents, :updated_at, :content_hash)
            ON CONFLICT(order_id) DO UPDATE SET
                customer_id = excluded.customer_id,
                amount_cents = excluded.amount_cents,
                updated_at = excluded.updated_at,
                content_hash = excluded.content_hash
            WHERE excluded.updated_at > orders.updated_at
            """,
            r,
        )
        if cur.rowcount == 0:
            existing = conn.execute(
                "SELECT content_hash FROM orders WHERE order_id = ?", (r["order_id"],)
            ).fetchone()
            if existing and existing[0] == r["content_hash"]:
                stats["skipped_unchanged"] += 1
            else:
                stats["skipped_stale"] += 1
        else:
            stats["written"] += 1
    conn.commit()
    return stats


def run(csv_path: str, db_path: str) -> dict:
    conn = sqlite3.connect(db_path)
    rows = transform(extract(csv_path))
    stats = load(conn, rows)
    conn.close()
    return stats


if __name__ == "__main__":
    import sys
    print(run(sys.argv[1], sys.argv[2]))

```python
# dag_runner.py — solution
from __future__ import annotations

import sqlite3
import time
from dataclasses import dataclass, field
from typing import Any, Callable


class DAGError(Exception):
    """A DAG-level failure: bad structure or a task that never succeeded."""


class CycleError(DAGError):
    """The task graph is not a DAG."""


@dataclass
class Task:
    name: str
    func: Callable[[dict], Any]
    deps: list[str] = field(default_factory=list)
    max_retries: int = 0
    retry_backoff_seconds: float = 0.0


class DAG:
    """A ~200-line orchestrator: topological execution, retries, and an
    idempotent run ledger so re-invoking run() with the same run_id resumes
    instead of redoing completed work."""

    def __init__(self, ledger_conn: sqlite3.Connection):
        self.tasks: dict[str, Task] = {}
        self.conn = ledger_conn
        self._init_ledger()

    def _init_ledger(self) -> None:
        self.conn.execute(
            """
            CREATE TABLE IF NOT EXISTS task_runs (
                run_id TEXT NOT NULL,
                task_name TEXT NOT NULL,
                status TEXT NOT NULL,
                attempts INTEGER NOT NULL DEFAULT 0,
                completed_at REAL,
                PRIMARY KEY (run_id, task_name)
            )
            """
        )
        self.conn.commit()

    def add_task(
        self,
        name: str,
        func: Callable[[dict], Any],
        deps: list[str] | None = None,
        max_retries: int = 0,
        retry_backoff_seconds: float = 0.0,
    ) -> None:
        if name in self.tasks:
            raise DAGError(f"task {name!r} already registered")
        self.tasks[name] = Task(name, func, deps or [], max_retries, retry_backoff_seconds)

    def _topo_order(self) -> list[str]:
        indeg = {n: 0 for n in self.tasks}
        adj: dict[str, list[str]] = {n: [] for n in self.tasks}
        for name, task in self.tasks.items():
            for dep in task.deps:
                if dep not in self.tasks:
                    raise DAGError(f"task {name!r} depends on unknown task {dep!r}")
                adj[dep].append(name)
                indeg[name] += 1
        ready = sorted(n for n, deg in indeg.items() if deg == 0)
        order: list[str] = []
        while ready:
            ready.sort()
            n = ready.pop(0)
            order.append(n)
            for m in adj[n]:
                indeg[m] -= 1
                if indeg[m] == 0:
                    ready.append(m)
        if len(order) != len(self.tasks):
            raise CycleError("cycle detected among tasks")
        return order

    def _status(self, run_id: str, task_name: str) -> str | None:
        row = self.conn.execute(
            "SELECT status FROM task_runs WHERE run_id = ? AND task_name = ?",
            (run_id, task_name),
        ).fetchone()
        return row[0] if row else None

    def _mark(self, run_id: str, task_name: str, status: str, attempts: int) -> None:
        self.conn.execute(
            """
            INSERT INTO task_runs (run_id, task_name, status, attempts, completed_at)
            VALUES (?, ?, ?, ?, ?)
            ON CONFLICT(run_id, task_name) DO UPDATE SET
                status = excluded.status,
                attempts = excluded.attempts,
                completed_at = excluded.completed_at
            """,
            (run_id, task_name, status, attempts, time.time()),
        )
        self.conn.commit()

    def run(self, run_id: str, context: dict | None = None) -> dict[str, Any]:
        context = context if context is not None else {}
        order = self._topo_order()
        results: dict[str, Any] = {}
        for name in order:
            task = self.tasks[name]
            if self._status(run_id, name) == "success":
                results[name] = "skipped-already-succeeded"
                continue
            attempts = 0
            last_err: Exception | None = None
            while attempts <= task.max_retries:
                attempts += 1
                try:
                    results[name] = task.func(context)
                    self._mark(run_id, name, "success", attempts)
                    last_err = None
                    break
                except Exception as exc:  # noqa: BLE001 - intentional retry boundary
                    last_err = exc
                    self._mark(run_id, name, "failed", attempts)
                    if attempts <= task.max_retries and task.retry_backoff_seconds:
                        time.sleep(task.retry_backoff_seconds)
            if last_err is not None:
                raise DAGError(
                    f"task {name!r} failed after {attempts} attempt(s): {last_err}"
                ) from last_err
        return results
```

## Three-tier reading

Specific to this module's subject — the conflict-resolution rule buried inside every
upsert — not the course-level scraping/consent reading, which belongs to AIE-203-M05.

- **Tier 1 — material ground.** A duplicate-row bug from a replayed batch is not an
  abstraction — it is a duplicate charge on a real invoice, a second copy of a shipping
  notification, a customer support ticket that says "why was I billed twice." An
  out-of-order overwrite that loses a legitimate update is a customer's corrected
  address silently reverting to the wrong one, with no error logged anywhere, because
  nothing about that overwrite looked like a failure to the system that performed it.
  These are documented, recurring categories of production incident, not hypotheticals
  invented for this module.

- **Tier 2 — what the field suppresses.** "The pipeline is idempotent" gets used as a
  talisman — once a team says it, the conversation about *what specifically happens on
  conflict* usually stops, as if idempotency were a single yes/no property rather than a
  specific, chosen rule. But `WHERE excluded.updated_at > orders.updated_at` is a policy
  decision — *whose write wins a tie, and by what evidence* — made once, in one line of
  SQL, by one engineer, and then applied without re-examination to every future conflict
  the table will ever see. Calling that "just idempotency" hides that a governance
  choice was made and never revisited.

- **Tier 3 — sit with this.** You now have the exact mechanism that decides which of two
  conflicting writes survives. Put a person on one side of it: a user submits a
  data-deletion request. At nearly the same moment, a delayed upstream batch — queued
  behind a slow retry, carrying a system clock's `updated_at` you don't control — replays
  their last known profile update, timestamped *before* the deletion request. Your
  ordering guard is about to pick a winner between "delete this person's data" and
  "restore their last known state." Which one wins under the rule you wrote in Lesson 2,
  and did you choose that on purpose — or did you just call it idempotent and move on?
