---

Every "cloud storage is basically free now" explainer on the internet compares the price
of a gigabyte of disk today to a gigabyte of disk in 2005, and declares storage a solved
problem. That comparison is not wrong on its own terms — it is answering a question this
module refuses to accept as the only one worth asking. Storing a corpus is not the
expensive part of owning a corpus. *Querying* it is, and it stays expensive for a
structural reason that has nothing to do with how cheap disks get: every read-heavy cloud
system that bills by usage charges for **bytes scanned**, not bytes stored, and bytes
scanned is a property of how the data is *laid out on disk* and *how often you ask it a
question*, not a property that shrinks on its own just because storage prices fell. A
100,000,000-row corpus stored as CSV and queried once a month costs almost nothing. The
same corpus, same format, queried by fifty downstream jobs a day, can cost more in a
single month than a year of the "basically free" storage bill. This module builds the
mechanism that determines which of those two worlds you're in — by hand, with real
formulas, before naming a single vendor.

## Lessons

### Lesson 1 — Row-major vs. column-major: what a query actually has to touch

Every table this course has queried — `documents`, `orders`, the streaming log's
`Record`s — has, physically, two ways it can sit on disk. **Row-major** layout writes
each record's fields together, one full row after another: this is how CSV works, and
it's how SQLite and Postgres store an ordinary table's heap pages by default. **Column-major**
layout writes each *field* together across every record, as its own contiguous run: all
the `source_id` values in one place, all the `word_count` values in another, entirely
separate from where the `content_hash` values live. Nothing about which values exist
changes between the two layouts — every row is still fully reconstructable from either
one. What changes is **which bytes a given query has to touch to answer itself**, and
that's the entire lesson.

Take the query this course keeps coming back to, the shape of most analytic questions
asked against a corpus: `AVG(word_count) WHERE source_id = X` — an aggregate over one
column, filtered by another, ignoring the rest of the row entirely. Row-major storage
gives that query no way to skip the columns it doesn't need: `word_count` and
`content_hash` and `license` are physically interleaved, one row's worth at a time, so
reading row 500,000's `source_id` means the disk head (or the OS page cache, or the
network read against object storage) has already been handed row 500,000's 64-byte
`content_hash` too, whether the query wanted it or not. Column-major storage puts
`source_id` and `word_count` in their own files entirely — the query opens exactly those
two, and the other four columns, wherever they live, are never touched. This is **column
pruning**, and it is the single biggest lever in this module, more consequential than any
compression codec, because it changes what gets read *before* compression ever enters the
picture.

**Worked example.** A `documents` record with six fields — `doc_id` (8 bytes),
`source_id` (4 bytes), `license` (20-byte fixed text), `published_year` (2 bytes),
`word_count` (4 bytes), `content_hash` (64-byte hex string) — is 102 bytes per row,
uncompressed, fixed-width. The query above needs exactly two of those fields:
`source_id` (4 bytes) and `word_count` (4 bytes), 8 bytes of the 102. At 100,000 rows:

| Store | File(s) the query opens | Bytes touched | Formula |
|---|---|---|---|
| Row-major | 1 file, every full row | 10,200,000 | 102 × 100,000 |
| Column-major | 2 files (`source_id.col`, `word_count.col`) | 800,000 | (4 + 4) × 100,000 |

**12.75× fewer bytes touched** — 102 ÷ 8 — for the identical query, over the identical
data, with **zero compression applied anywhere in this table.** That ratio is the whole
of Lesson 1: pure layout, no encoding tricks yet. Lab M06-A builds both stores by hand,
in plain Python and plain files, and measures this number directly rather than taking it
on faith.

**Named misconceptions**

- *"Parquet is basically compressed CSV."* Compression is Lesson 2's contribution, layered
  on top of a structural change this lesson makes on its own. An **uncompressed** column
  store already beats an uncompressed row store on this query, by exactly the ratio above
  — because the advantage is about which bytes get *read*, not how small the bytes are.
  Conflating the two hides which mechanism is doing which part of the work.
- *"Columnar storage means less data on disk."* Not by itself. Sum every column file's
  size in the table above and it is roughly the same total bytes as the row store (plus a
  little per-file overhead) — a column store, absent compression, does not shrink total
  storage at all. What shrinks is the bytes a *specific query* has to touch. Total-bytes
  shrinkage is Lesson 2's job, and it only helps because column-major layout puts
  same-typed, often repetitive values next to each other where a compressor can exploit
  the pattern — a row-major file interleaves six different data distributions and gives a
  compressor almost nothing to work with by comparison.
- *"The advantage only matters at huge scale."* The ratio 102:8 is scale-invariant — it is
  exactly 12.75× at 1,000 rows and exactly 12.75× at 100,000,000 rows, because both
  numerators and denominators scale by the same row count. What changes with scale is not
  *whether* the advantage exists, but how many dollars and seconds it is worth — which is
  precisely Lesson 4's subject.

### Lesson 2 — Compression and encoding: shrinking the bytes that do get touched

Lesson 1's win was entirely about *which* bytes a query reads. Lesson 2 is about shrinking
the *size* of those bytes, and column-major layout is what makes this cheap: because a
column file holds one, homogeneous distribution of values instead of six interleaved
ones, simple encodings can exploit structure a row-major file hides. The workhorse for a
**low-cardinality** column — one with few distinct values relative to its row count, like
`license` (four or five real-world values: `cc-by`, `cc0`, `public-domain`,
`all-rights-reserved`) — is **dictionary encoding**: build a small table mapping each
distinct string to a short integer code, then store the *codes* (one byte apiece, if
there are 256 or fewer distinct values) instead of repeating the full string on every row.

**Worked example.** 100,000 rows of `license`, drawn from those four strings, stored
fixed-width at 20 bytes/row versus dictionary-encoded:

| Representation | Bytes | Formula |
|---|---|---|
| Raw fixed-width | 2,000,000 | 20 × 100,000 |
| Dictionary-encoded (1 code byte/row + table) | 100,044 | (1 × 100,000) + 44 |

The 44-byte dictionary table is four entries, each a 1-byte length prefix plus its UTF-8
payload: `(1+5) + (1+3) + (1+13) + (1+19) = 44`. **≈19.98× smaller** — call it "about
20×" — and this is *before* the general-purpose byte-level compressor (Snappy, Zstd) that
a real system layers on top gets anywhere near it.

That ratio depends entirely on cardinality staying low relative to row count, and the
dependency cuts both ways. Run the identical mechanism against `content_hash` — every
value distinct by construction, since it's a content hash — at just 100 rows: the
dictionary table now has to store one full 64-byte entry *per row*, plus a 1-byte length
prefix, plus the 1-byte code that points at it: `100 × (1 + 64) = 6,500` bytes of table
plus `100 × 1 = 100` bytes of codes, **6,600 bytes total** — more than the `6,400` bytes
(`64 × 100`) the raw fixed-width column would have cost with no encoding at all. Dictionary
encoding didn't fail to help here; it actively lost, because every "entry" in the
dictionary was used exactly once, so the codes are pure overhead on top of the same string
data stored twice. Lab M06-B proves both directions of this with the same three functions
and no special-casing.

**Named misconceptions**

- *"gzip a CSV and you get what Parquet gives you."* A general-purpose compressor
  shrinks the byte *stream*, but the query engine still has to decompress the whole file
  to reach any of it — CSV plus gzip has no column files to open selectively and no
  per-column statistics for a query planner to use. It gets Lesson 2's win without Lesson
  1's, and Lesson 1's is the larger of the two at any nontrivial query frequency.
- *"Dictionary encoding always shrinks the data."* False whenever cardinality approaches
  row count — `content_hash` above is the concrete counterexample, not a contrived edge
  case; any column whose values are close to unique per row (hashes, UUIDs, precise
  timestamps) behaves the same way. A real columnar format chooses its encoding
  per-column, by measured cardinality, for exactly this reason — "always dictionary-encode
  everything" is not a real system's actual policy.
- *"Compression is a pure win with no cost."* Decoding takes CPU time the raw bytes
  didn't need. For a workload that reads a handful of *specific* rows very frequently by
  primary key — the OLTP shape a row-major engine like Postgres or SQLite is built for —
  that decode overhead, paid on every single-row read, isn't worth it, which is a real
  part of why transactional databases stay row-major even though this module keeps
  finding reasons columnar wins for *analytic* queries. The two layouts are optimized for
  different query shapes, not ranked "better" and "worse" in general.

### Lesson 3 — Lake vs. warehouse: who pays the schema cost, and when

Lessons 1 and 2 were about file layout. Lesson 3 is about a decision one level above the
file: where does a corpus live, and when does its structure get enforced? A **data
warehouse** is schema-on-write — a table's columns and types are declared before any data
lands, and every load validates against that declaration, once, at ingest time. A **data
lake** is schema-on-read — raw or semi-structured files land in cheap object storage
(what M05's ingestion stage already produces) with no schema enforced at write time at
all; structure is imposed later, by whoever writes the query, against whatever the file
actually turns out to contain.

| | Warehouse (schema-on-write) | Lake (schema-on-read) |
|---|---|---|
| When schema is enforced | Once, at load | Every time, at each query |
| Ingest cost | Higher — validate, transform, load into structured tables | Lower — near-raw copy into object storage |
| Per-query cost | Lower — engine already knows the schema, can use indexes/partitions | Higher — parse and infer structure on every read |
| Flexibility for an unknown future format | Lower — a new field needs a migration | Higher — store first, decide the schema later |
| Failure mode when unmanaged | Rigid: a schema change blocks ingestion until fixed | "Swamp": ungoverned files nobody can safely query without re-deriving what's inside |

The trade is not "one is better" — it's "who pays, and how many times." A warehouse pays
the validation cost exactly once, at load, no matter how many times the table is later
queried. A lake pays nothing at load, and instead every single downstream reader —
M05's corpus is read by contamination checks, by AIE-301's retrieval pipeline, by a
dashboard, by an ad hoc audit — repeats the schema-inference and validation work the
warehouse would have done once. If a corpus has one consumer, the lake's deferred cost is
strictly cheaper. If it has fifty, as M05's is explicitly built to (AIE-301 alone is one
of many), the fifty repeated parsing costs can exceed the warehouse's one-time validation
bill by a wide margin — the exact same *shape* of trade-off Lesson 4 puts real numbers on:
pay once, or pay per read.

**Named misconceptions**

- *"A lake is just a warehouse without a schema."* It differs in *when* structure is
  imposed and *who* pays for imposing it, not in whether structure exists at all — a
  query against a lake still needs a schema to run, it's just declared by the query
  instead of the table.
- *"Always use a lake, because storage is cheap."* Cheap ingest is not free ingest — it's
  *deferred* ingest cost, repaid by every reader. A corpus queried rarely by one consumer
  is a lake's best case. A corpus queried often by many consumers pays that deferred cost
  over and over, and a warehouse's one-time validation can become the cheaper total.
  "Storage is cheap" answers a real but narrow question; it says nothing about the
  *query-side* cost this misconception quietly assumes away.

### Lesson 4 — The cost model: bytes scanned, storage tier, query frequency

Every lever from Lessons 1–3 collapses into one formula, computed by hand, for a specific
workload — not a general opinion about which format or vendor is "good."

```
monthly_cost = storage_cost + query_cost

storage_cost = gb_stored × price_per_gb_month(tier)
query_cost   = queries_per_month × gb_scanned_per_query × (price_per_gb_scanned + retrieval_fee_per_gb)
```

`retrieval_fee_per_gb` is a real, separate charge most cold/archive storage tiers add on
top of the ordinary scan price for actually reading data back out — the fee that makes
"cold storage is always cheaper" false once query frequency rises. `gb_scanned_per_query`
is Lesson 1's column-pruning ratio and Lesson 2's compression ratio, combined, applied to
this specific query against this specific format.

**Worked example — format choice, fixed storage tier.** A 100,000,000-row corpus: as CSV,
10 GB total, no column pruning possible (a query engine reading CSV out of object storage
generally can't skip columns mid-row, so every query scans the full object); as
compressed Parquet, 2 GB total, with this module's recurring query scanning ~10% of it via
column pruning + dictionary encoding (0.2 GB/query). Illustrative hot-tier prices:
$0.02/GB-month storage, $0.005/GB scanned:

| Format | `monthly_cost(q)` | at q=10/month | at q=100/month |
|---|---|---|---|
| CSV, hot | 0.2 + 0.05q | $0.70 | $5.20 |
| Parquet, hot | 0.04 + 0.001q | $0.05 | $0.14 |
| **Ratio (CSV ÷ Parquet)** | — | **14×** | **37×** |

The gap *widens* with query frequency, because format changes the **marginal** cost per
query, and marginal cost is exactly what scales with how often the corpus gets asked
anything. Storage-tier choice barely moved either number — at this scale, storage cost is
close to noise next to query cost, the moment query frequency is more than occasional.

**Worked example — storage tier, fixed format, the crossover.** Same 2 GB Parquet corpus,
same 0.2 GB/query, compared hot ($0.02/GB-month, no retrieval fee) against cold
($0.004/GB-month, plus a $0.01/GB retrieval fee on every byte actually read back):

```
cost_hot(q)  = 2×0.02  + q×0.2×0.005          = 0.04  + 0.001q
cost_cold(q) = 2×0.004 + q×0.2×(0.005+0.01)   = 0.008 + 0.003q
```

Set them equal and solve for the crossover query frequency `q*`:

```
0.04 + 0.001q = 0.008 + 0.003q
0.032 = 0.002q
q* = 16
```

Below 16 queries/month, cold tier is cheaper (its lower storage price dominates, and
retrieval fees are paid rarely). Above 16 queries/month, hot tier is cheaper (its lack of
a retrieval fee starts to outweigh its higher storage price, once that fee is paid often
enough). At exactly 16, they're equal — `cost_hot(16) = cost_cold(16) = $0.056`. This is
not a rule of thumb to memorize; it is a number this specific workload's parameters
produce, and Lab M06-C makes the learner find it two ways: algebraically, on paper, before
touching code, and computationally, by search, after.

> **Current landscape (mixed durability — this box will date faster than the rest of the
> module; check current pricing before recommending anything for real).**
> - **Object storage tiers**: Amazon S3 (Standard / Infrequent Access / Glacier), Google
>   Cloud Storage (Standard / Nearline / Coldline / Archive), Azure Blob (Hot / Cool /
>   Archive) — the hot/cold split and retrieval-fee shape in this lesson's cost model
>   mirrors all three directly.
> - **Columnar file formats**: Apache Parquet (row-group + column-chunk layout, dictionary
>   and run-length encoding, per-chunk min/max statistics enabling predicate pushdown) and
>   ORC — the production version of Lab M06-A's toy column store, with real compression
>   codecs (Snappy, Zstd) layered on top of Lesson 2's dictionary encoding.
> - **Bytes-scanned query engines**: Google BigQuery, AWS Athena, Snowflake — priced
>   roughly per-TB-scanned (BigQuery on-demand has hovered around $5–6.25/TB scanned) or
>   per compute-second (Snowflake's warehouse-seconds model) — either way, this lesson's
>   `price_per_gb_scanned` term.
> - **Lakehouse table formats**: Apache Iceberg, Delta Lake, Apache Hudi — add ACID
>   transactions, schema evolution, and time travel on top of Parquet-on-object-storage,
>   narrowing much of the gap Lesson 3 draws between "lake" and "warehouse."
>
> Treat every dollar figure and vendor name above as a snapshot, not a fact to memorize.
> The formulas — `storage_cost`, `query_cost`, the tier crossover — are the durable part;
> they will still be the right questions to ask long after these numbers move.

**Named misconceptions**

- *"Minimize GB stored — that's the cost driver."* At any nontrivial query frequency, the
  worked example above shows query cost dwarfing storage cost by one to two orders of
  magnitude. Obsessing over storage footprint while ignoring `gb_scanned_per_query` is
  optimizing the smaller term.
- *"Cold/archive tier is always cheaper — it's the same data, lower price per GB."* True
  only below the crossover frequency. Above it, the retrieval fee — paid every time,
  proportional to bytes actually read — makes cold tier strictly more expensive. There is
  no tier that is cheaper in general; there is only a tier that is cheaper *for a given
  query frequency*, which is exactly what `q*` computes.
- *"The right format/tier is a property of the data."* It's a property of the
  **workload** — the same corpus, queried ten times a month by a compliance audit versus
  ten thousand times a month by a live retrieval system, has two different correct
  answers to "where should this live and in what format," and this lesson's formula is
  how you compute which one applies, instead of guessing.

```python
# toy_storage.py -- solution
from __future__ import annotations

import os
import struct
from dataclasses import dataclass

DOC_ID_FMT = "Q"
SOURCE_ID_FMT = "I"
YEAR_FMT = "H"
WORD_COUNT_FMT = "I"
LICENSE_WIDTH = 20
HASH_WIDTH = 64

ROW_STRUCT = struct.Struct(f"<{DOC_ID_FMT}{SOURCE_ID_FMT}{YEAR_FMT}{WORD_COUNT_FMT}")
ROW_WIDTH = ROW_STRUCT.size + LICENSE_WIDTH + HASH_WIDTH  # 18 + 20 + 64 = 102

COLUMN_FORMATS = {
    "doc_id": (DOC_ID_FMT, 8),
    "source_id": (SOURCE_ID_FMT, 4),
    "published_year": (YEAR_FMT, 2),
    "word_count": (WORD_COUNT_FMT, 4),
}


@dataclass(frozen=True)
class DocRecord:
    doc_id: int
    source_id: int
    license: str
    published_year: int
    word_count: int
    content_hash: str


def _pack_text(value: str, width: int) -> bytes:
    raw = value.encode("utf-8")[:width]
    return raw.ljust(width, b"\x00")


def write_row_store(records: list[DocRecord], path: str) -> None:
    with open(path, "wb") as f:
        for r in records:
            f.write(ROW_STRUCT.pack(r.doc_id, r.source_id, r.published_year, r.word_count))
            f.write(_pack_text(r.license, LICENSE_WIDTH))
            f.write(_pack_text(r.content_hash, HASH_WIDTH))


def query_avg_word_count_row_store(path: str, source_id: int) -> tuple[float, int]:
    total, count, bytes_read = 0, 0, 0
    with open(path, "rb") as f:
        while True:
            row = f.read(ROW_WIDTH)
            if not row:
                break
            bytes_read += len(row)
            doc_id, source, year, word_count = ROW_STRUCT.unpack(row[: ROW_STRUCT.size])
            if source == source_id:
                total += word_count
                count += 1
    return (total / count if count else 0.0), bytes_read


def write_column_store(records: list[DocRecord], dir_path: str) -> None:
    os.makedirs(dir_path, exist_ok=True)
    for name, (fmt, width) in COLUMN_FORMATS.items():
        with open(os.path.join(dir_path, f"{name}.col"), "wb") as f:
            for r in records:
                f.write(struct.pack(f"<{fmt}", getattr(r, name)))
    with open(os.path.join(dir_path, "license.col"), "wb") as f:
        for r in records:
            f.write(_pack_text(r.license, LICENSE_WIDTH))
    with open(os.path.join(dir_path, "content_hash.col"), "wb") as f:
        for r in records:
            f.write(_pack_text(r.content_hash, HASH_WIDTH))


def query_avg_word_count_column_store(dir_path: str, source_id: int, n_rows: int) -> tuple[float, int]:
    src_fmt, src_width = COLUMN_FORMATS["source_id"]
    wc_fmt, wc_width = COLUMN_FORMATS["word_count"]
    bytes_read = 0
    with open(os.path.join(dir_path, "source_id.col"), "rb") as f:
        src_bytes = f.read()
        bytes_read += len(src_bytes)
    with open(os.path.join(dir_path, "word_count.col"), "rb") as f:
        wc_bytes = f.read()
        bytes_read += len(wc_bytes)
    total, count = 0, 0
    for i in range(n_rows):
        source = struct.unpack_from(f"<{src_fmt}", src_bytes, i * src_width)[0]
        if source == source_id:
            word_count = struct.unpack_from(f"<{wc_fmt}", wc_bytes, i * wc_width)[0]
            total += word_count
            count += 1
    return (total / count if count else 0.0), bytes_read
```

```python
# dict_encode.py -- solution
from __future__ import annotations


def build_dictionary(values: list[str]) -> dict[str, int]:
    distinct = sorted(set(values))
    if len(distinct) > 256:
        raise ValueError(f"{len(distinct)} distinct values exceeds 1-byte code space (256)")
    return {value: code for code, value in enumerate(distinct)}


def encode_column(values: list[str], dictionary: dict[str, int]) -> bytes:
    if len(dictionary) > 256:
        raise ValueError("dictionary too large for 1-byte codes")
    return bytes(dictionary[v] for v in values)


def decode_column(encoded: bytes, dictionary: dict[str, int]) -> list[str]:
    reverse = {code: value for value, code in dictionary.items()}
    return [reverse[b] for b in encoded]


def dictionary_size_bytes(dictionary: dict[str, int]) -> int:
    return sum(1 + len(value.encode("utf-8")) for value in dictionary)


def raw_fixed_width_size_bytes(values: list[str], width: int) -> int:
    return width * len(values)


def encoded_size_bytes(values: list[str], dictionary: dict[str, int]) -> int:
    return len(values) + dictionary_size_bytes(dictionary)
```

```python
# cost_model.py -- solution
from __future__ import annotations

from dataclasses import dataclass


@dataclass(frozen=True)
class StorageConfig:
    name: str
    gb_stored: float
    price_per_gb_month: float
    price_per_gb_scanned: float
    retrieval_fee_per_gb: float = 0.0


def storage_cost(config: StorageConfig) -> float:
    return config.gb_stored * config.price_per_gb_month


def query_cost(config: StorageConfig, queries_per_month: int, gb_scanned_per_query: float) -> float:
    return queries_per_month * gb_scanned_per_query * (
        config.price_per_gb_scanned + config.retrieval_fee_per_gb
    )


def monthly_cost(config: StorageConfig, queries_per_month: int, gb_scanned_per_query: float) -> float:
    return storage_cost(config) + query_cost(config, queries_per_month, gb_scanned_per_query)


def cheaper_config(
    config_a: StorageConfig,
    config_b: StorageConfig,
    queries_per_month: int,
    gb_scanned_per_query: float,
) -> StorageConfig:
    cost_a = monthly_cost(config_a, queries_per_month, gb_scanned_per_query)
    cost_b = monthly_cost(config_b, queries_per_month, gb_scanned_per_query)
    return config_a if cost_a <= cost_b else config_b


def find_crossover_frequency(
    config_a: StorageConfig,
    config_b: StorageConfig,
    gb_scanned_per_query: float,
    max_queries: int = 10_000,
) -> int | None:
    for q in range(max_queries + 1):
        cost_a = monthly_cost(config_a, q, gb_scanned_per_query)
        cost_b = monthly_cost(config_b, q, gb_scanned_per_query)
        if cost_b <= cost_a:
            return q
    return None
```

## Three-tier reading

Specific to this module's subject — the economics of where a corpus lives and how long it
stays there — not the course-level scraping/consent reading, which belongs to
AIE-203-M05.

- **Tier 1 — material ground.** Bytes-scanned billing is a documented, recurring source of
  real financial surprise: an unbounded query — a `SELECT *` or an unfiltered join against
  a large table, run against a pay-per-scan engine — has produced real, five- and
  six-figure single-query bills at real organizations, discovered only when the invoice
  arrived. This is not a hypothetical this module invented to motivate Lesson 4; it is the
  reason every real bytes-scanned query engine now ships a "preview the bytes this query
  will scan before you run it" feature as a first-class safety control, not an
  afterthought.

- **Tier 2 — what the field suppresses.** "Storage is basically free" is true, narrowly,
  about the price of a gigabyte sitting idle — and that narrow truth gets generalized, in
  planning conversations, into "so keep everything." What that generalization hides is a
  second, harder fact this module's own architecture surfaces without meaning to:
  column-major, compressed, often append-only formats — the exact formats Lessons 1 and 2
  spent this whole module recommending, for good, real, load-bearing reasons — make
  deleting *one specific row* structurally expensive in a way a row-major OLTP table never
  was. An OLTP database deletes one customer's row with a point `DELETE` in milliseconds.
  A Parquet file, or a lakehouse table built on one, generally cannot cheaply remove one
  row in place — the row lives inside a compressed column-chunk shared with thousands of
  others, and "delete this one" usually means rewriting the file, or the row-group, or
  waiting for the table format's own compaction to catch up. The same physical layout that
  makes storage and querying cheap makes *targeted deletion* comparatively expensive
  engineering work — and that asymmetry is rarely said out loud in the same breath as
  "storage is basically free," because it complicates the pitch.

- **Tier 3 — sit with this.** You now know, from this module, that keeping a corpus in
  cold storage costs a few tenths of a cent per gigabyte per month, and that actually
  deleting one person's record out of a compressed, column-oriented file costs real
  engineering hours you'd otherwise spend on something else. Someone will eventually ask
  you — a person exercising a deletion request, a policy your team wrote and now has to
  honor, your own future self doing a compliance pass — to remove one person's data from a
  corpus built on the formats this module just taught you to prefer. The honest technical
  answer, most of the time, will be: it is cheaper, in dollars and in your own time, to
  just leave it there, quietly, in the tier that costs almost nothing to keep paying for,
  than to do the actual work of taking it out. You built the cost model. You know the exact
  number that makes "keep it" the path of least resistance. When that number is real and
  the request is real, does the fact that deletion costs *you* more than retention costs
  *the invoice* change what you do — and if you keep the record because removing it is
  inconvenient rather than because removing it is wrong, is that a decision you could
  defend out loud to the person who asked?
