**Course:** AIE-203 — Data Engineering for AI · **Tier:** core · **Durability:** mixed
**Hours:** 14 · **Sits in the descent:** the pipes now carry data that must be *trusted*,
not just delivered. AIE-203-M02 made loads idempotent and resumable; this module asks a

**Prereq:** AIE-203-M02 (batch pipelines: idempotency, orchestration). Lesson 4 of this
module extends that module's DAG runner directly — the quality gate is a task, using the
exact ledger machinery M02 already built, not a new mechanism. Feeds AIE-203-M05 (corpus
construction), whose provenance and contamination-check work is this module's
expectations and lineage tooling pointed at scraped/licensed text instead of orders rows.

---

Every data-quality tutorial on the internet shows a single check, run once, against
clean-ish data, that returns `True`. This module refuses that shape for two reasons. The
first is that a check which never states *how much* is broken is not a check — it is a
boolean opinion, and Lesson 1 spends real effort making every check report a count, not a
verdict. The second, larger reason is that a passing check proves nothing about what it
didn't look at. A null-rate check tuned to a 5% threshold does not fire on a single null
value at 4% — that value is not wrong, it's *invisible* to that check, on that batch,
today. This module's spine is learning to predict, for a specific planted bug, exactly
which of your checks will catch it and which will walk right past it — because a data
engineer who cannot answer that question in advance is not testing their pipeline, they
are hoping at it.

## Lessons

### Lesson 1 — Data expectations as executable checks

An expectation is a claim about data that would previously have lived in a comment, a
wiki page, or someone's memory — "customer_id should never be null," "amount is always
non-negative," "every order's customer_id exists in the customers table" — rewritten as a
function that runs every time the batch loads and reports, numerically, whether the claim
held. This is the same move AIE-101 made for code: an assertion in a docstring is a wish;
an assertion in a test is enforced. Four check *classes* cover most of what a table can
violate without the pipeline itself raising an exception:

1. **Schema** — do the expected columns exist, with no unexpected ones, and does each
   column's values match an expected type?
2. **Range** — does a numeric column stay within a plausible bound (an amount that's
   never negative, a percentage that's never over 100)?
3. **Null-rate** — what fraction of a column's values are missing, and is that fraction
   under a tolerance you chose on purpose?
4. **Referential** — does every value in a foreign-key-shaped column actually exist in
   the table it's supposed to reference?

A check in this module always returns a `CheckResult` that reports `checked`,
`violations`, and a few `samples` — never a bare `True`/`False`. The reason is
diagnostic, not stylistic: "the check failed" tells an on-call engineer nothing; "4 of
25,000 rows violate `amount_cents >= 0`, first offender is row 812" tells them where to
look in under a second.

**Worked example.** A range check and a schema/type check, and the design decision that
keeps one from crashing on the other's mess:

```python
def check_range(rows, column, min_val=None, max_val=None):
    violations = []
    for i, r in enumerate(rows):
        v = r.get(column)
        if v is None:
            continue  # a missing value is check_null_rate's job, not this check's
        if not isinstance(v, (int, float)):
            continue  # a wrong-typed value is check_schema's job — don't crash on it
        if (min_val is not None and v < min_val) or (max_val is not None and v > max_val):
            violations.append((i, v))
    return CheckResult(f"range:{column}", len(violations) == 0, len(rows), len(violations), violations[:5])
```

Without that second `isinstance` guard, a single row where `amount_cents` was accidentally
loaded as the string `"1000"` (a real, common transform bug — a CSV column that used to
be numeric silently started carrying a currency symbol upstream) would make `v < min_val`
raise `TypeError: '<' not supported between instances of 'str' and 'int'` and crash the
*entire quality check step*, not just flag one row. A defensively-skipped value is safe
but it is not a pass in any meaningful sense — it means "I could not evaluate this," and
Lesson 4's bug-matrix exercise makes you name, explicitly, which check is responsible for
catching what the range check just declined to look at.

**Named misconceptions**

- *"A passing check is proof the data is correct."* `check_range` reporting `passed=True`
  on a batch where one value silently drifted from `int` to `str` does not mean that value
  is fine — it means the range check could not evaluate it and quietly moved on. A green
  check answers "did I find a violation of *this specific claim*," never "is this data
  correct." Confusing the two is this lesson's most consequential misconception, because
  it is the one that produces false confidence in production.
- *"If it loads without an exception, the data is fine."* Type coercion in most loaders
  succeeds silently in more cases than it fails — an `INSERT` into a loosely-typed SQLite
  column, or a pandas `read_csv` inferring a column as `object` instead of raising, will
  swallow a malformed value rather than surface it. The absence of an error is not
  evidence of correctness; it's evidence that nothing was checked.
- *"A null-rate check catches missing data."* It catches missing data *above a threshold,
  on this batch*. A single null under threshold is real, present in the table, and
  invisible to this check by design — Lesson 3 exists because of exactly this gap.

### Lesson 2 — A minimal lineage tracker

After a pipeline has run for a year and gone through three transform stages, "which raw
source produced this row" stops being a rhetorical question and becomes the first thing
asked in every incident: a bad number reached a report, and someone needs to know which
upstream file, sent by which partner, on which day, is actually at fault. A `source_file`
column bolted onto the final table answers this for data that passed straight through
unchanged — it collapses the moment a row is the product of a **join** (two parents) or
an **aggregate** (many parents), because there is no longer one source column to point to.

The fix does not require storing every version of the data, only a graph of *pointers*.
At extract time, tag each raw row with an id tied to its origin. At every transform stage
after that, record which parent id(s) produced each output id — a join records two
parents per output row; an aggregate records however many rows fed the group. Tracing a
row backward is then a graph walk: follow parent pointers until you hit ids with no
further parents — the raw sources — and stop.

**Worked example.** A two-hop pipeline: `orders.csv` and `customers.csv` are extracted,
joined into `enriched_orders`, then aggregated into `region_totals`.

```python
class LineageTracker:
    def __init__(self):
        self.sources: dict[str, tuple[str, int]] = {}   # record_id -> (source_file, source_row)
        self.derived_from: dict[str, list[str]] = {}    # record_id -> [parent_record_id, ...]

    def record_source(self, record_id, source_file, source_row):
        self.sources[record_id] = (source_file, source_row)

    def record_derivation(self, record_id, parent_ids):
        self.derived_from[record_id] = list(parent_ids)

    def trace(self, record_id):
        seen, leaves, stack = set(), set(), [record_id]
        while stack:
            rid = stack.pop()
            if rid in seen:
                continue
            seen.add(rid)
            if rid in self.sources:
                leaves.add(self.sources[rid])
            elif rid in self.derived_from:
                stack.extend(self.derived_from[rid])
            else:
                raise KeyError(f"unknown record id {rid!r}")
        return leaves
```

Three orders (`O1`/`C1`, `O2`/`C1`, `O3`/`C2`) join against two customers (`C1`→west,
`C2`→east) to produce `eo:0`, `eo:1`, `eo:2`; those aggregate by region into `rt:west`
(from `eo:0` + `eo:1`) and `rt:east` (from `eo:2`). Calling `trace("rt:west")` walks
`rt:west → eo:0, eo:1 → orders.csv:0, orders.csv:1, customers.csv:0` (twice, from both
`eo:0` and `eo:1`) and returns the **set** `{("orders.csv", 0), ("orders.csv", 1),
("customers.csv", 0)}` — three distinct raw records, not four, because `customers.csv:0`
is deduplicated even though two different enriched rows both point to it. That dedup is
not a nicety; it's the entire reason `trace` returns a `set` and not a list — a fan-in
record must appear exactly once in the answer to "which raw sources touched this row,"
regardless of how many downstream paths reached it.

**Named misconceptions**

- *"A `source_file` column is lineage enough."* It answers the question for pass-through
  data and silently stops answering it the moment a row is the product of more than one
  parent — which is most rows, past the first pipeline stage.
- *"Lineage is a debugging nicety."* It is the mechanism a contamination check needs
  (AIE-203-M05: which raw document produced this training example, so you can pull it if
  it turns out to be in your eval set) and the mechanism an incident response needs (which
  upstream partner's feed produced this corrupted row). It is infrastructure a quality
  program depends on, not an optional extra.
- *"Row-level lineage means storing every historical copy of every row."* It means storing
  *pointers* — ids and their parent ids — which is orders of magnitude cheaper than
  storing full row snapshots at every stage, and is exactly what the graph above does.

### Lesson 3 — Monitoring: catching drift, not just violations

An expectation is a claim about *this batch*, evaluated with no memory of any other batch.
That is precisely why it cannot catch the two failure modes this lesson targets: a source
that starts sending a new fraction of nulls it never used to (a **null-rate spike**), and
a source that stops sending a column it used to always send (**schema drift**). Neither
one is a violation of a fixed rule — they are violations of *history*, and catching them
requires comparing today's batch to a rolling baseline built from prior runs, with a
threshold for how much deviation is normal noise versus signal.

**Worked example.** A null-rate drift check using a z-score against the mean and standard
deviation of prior runs, with an explicit cold-start guard:

```python
import math

def check_null_rate_drift(column, history, latest, min_history=3, z_threshold=3.0):
    if len(history) < min_history:
        return None  # not enough baseline yet — don't guess
    mean = sum(history) / len(history)
    variance = sum((h - mean) ** 2 for h in history) / (len(history) - 1)
    stdev = math.sqrt(variance)
    if stdev == 0:
        if latest != mean:
            return Alert(column, "null_rate", f"changed from a constant {mean:.4f} to {latest:.4f}")
        return None
    z = (latest - mean) / stdev
    if abs(z) > z_threshold:
        return Alert(column, "null_rate", f"z={z:.2f} (latest={latest:.4f}, baseline mean={mean:.4f})")
    return None
```

Run this against five days of a perfectly steady `customer_id` null-rate of `0.02`, then a
sixth day at `0.30`: the first three days return `None` (fewer than `min_history=3` prior
runs — there is no baseline yet to compare against, and guessing anyway is how monitors
earn a reputation for crying wolf and getting muted). Days four and five compare against a
baseline of `[0.02, 0.02, 0.02]` (then four such values): `stdev` is exactly `0`, and since
`0.02 == 0.02`, no alert. Day six compares `0.30` against a still-constant baseline — the
`stdev == 0` branch fires because the baseline never varied *and this value does*, which
is the single most common real shape a monitor needs to catch (most healthy columns are
boringly stable; the interesting event is the first time they aren't).

The same discipline applies to columns disappearing: `check_schema_drift(expected, actual)`
diffs today's column set against the set the pipeline has always seen and reports
`missing`/`unexpected` — a source that quietly stopped sending a `region` field is caught
here, not by any per-row check, because no single row in a schema-drifted batch is
individually malformed; the batch as a whole is missing something it used to have.

**Named misconceptions**

- *"Monitoring after load is good enough."* Catching a regression in a dashboard a human
  happens to glance at next week is not monitoring — it is hoping someone looks. Lesson 4
  wires this check into the pipeline itself, before a downstream consumer ever reads the
  batch, which is the only place "catches it before it reaches a downstream consumer"
  (this module's stated bar) can actually be satisfied.
- *"A single-run threshold is monitoring."* It's Lesson 1's expectation again, wearing a
  different name. Monitoring requires *history* — which is precisely why day one through
  three above cannot alert: there is nothing yet to have drifted from.
- *"If it's always been broken, monitoring will catch it eventually."* It will not. A
  column with a constant 40% null rate since the pipeline's first run looks perfectly
  *stable* to a drift check — nothing about it changes, ever, so `z` stays near zero
  forever. Monitoring only sees deltas; a permanent, original defect has no delta to see.
  That specific gap is exactly what Lesson 1's static expectations exist to close, and it
  is why this module builds both layers rather than treating one as a replacement for the
  other.

### Lesson 4 — Wiring it together: the quality gate, and the bug matrix

None of the three preceding lessons is sufficient alone, and Lesson 4's job is to make
that fact executable rather than asserted. First, integration: a quality gate is not a
new orchestration mechanism — it is a **task**, inserted into the M02 DAG runner between
`load` and whatever consumes the loaded table, that runs Lesson 1's expectations and
Lesson 3's drift checks and raises if any of them fail:

```python
def quality_gate_task(ctx: dict) -> dict:
    rows, history = ctx["loaded_rows"], ctx["null_rate_history"]
    results = [
        check_schema(rows, EXPECTED_COLUMNS, EXPECTED_TYPES),
        check_range(rows, "amount_cents", min_val=0),
        check_null_rate(rows, "customer_id", max_rate=0.05),
        check_referential(rows, "customer_id", ctx["valid_customer_ids"]),
    ]
    alerts = [
        check_null_rate_drift("customer_id", history, compute_null_rate(rows, "customer_id")),
        check_schema_drift(EXPECTED_COLUMNS, set(rows[0].keys()) if rows else EXPECTED_COLUMNS),
    ]
    failures = [r for r in results if not r.passed] + [a for a in alerts if a is not None]
    if failures:
        raise QualityGateError(failures)  # downstream task never runs on this batch
    return {"gate": "passed"}
```

Because this is *just another task* in the DAG runner built in AIE-203-M02, it inherits
that module's retry and ledger machinery for free — a transient failure in the gate itself
retries like any other task, and re-invoking `run()` with the same `run_id` after a fix
resumes exactly where it left off, without re-running `extract`/`transform`/`load`. This
is the payoff of having built the orchestrator by hand instead of importing one on faith:
the quality gate cost one function and zero new infrastructure.

Second — and this is the module's actual center of gravity — no single check or monitor
covers every failure. The following matrix, built from this module's own labs, is what
every Predict step in this module is training you to reconstruct from first principles,
not memorize:

| Bug | Schema check | Range check | Null-rate check | Referential check | Schema-drift monitor | Null-rate drift monitor |
|---|---|---|---|---|---|---|
| Negative `amount_cents` | miss | **catch** | miss | miss | miss | miss |
| Orphan `customer_id` (not in `customers`) | miss | miss | miss | **catch** | miss | miss |
| Type drift (`amount_cents` becomes a string) | **catch** | miss (defensively skips, doesn't crash) | n/a | n/a | miss | miss |
| One null `customer_id`, under the batch's threshold | miss | n/a | miss | miss | miss | miss (one batch, no trend yet) |
| Null `customer_id` rate creeping up over many batches | miss (each batch individually under threshold) | n/a | miss (per batch) | miss | miss | **catch** |
| A source column silently stops arriving | catch, *if* schema check enforces the exact column set | n/a | n/a | n/a | **catch** | n/a |
| A column has been 100% null since the pipeline's first run | miss | n/a | catches only if `max_rate` was set below the constant rate | n/a | miss (it never changes) | miss (no delta to detect) |

Read the last row twice. It is the row every learner gets wrong on first Predict, and it
is the row this module exists to teach: a defect present since day one is invisible to
*any* check whose threshold wasn't set specifically to catch it, and invisible to *every*
drift monitor, because drift monitors only see change. The only thing that catches a
day-one defect is a human deciding, on purpose, what the acceptable rate actually is — not
an inferred baseline. No amount of monitoring substitutes for that judgment call.

**Named misconceptions**

- *"More checks are strictly better."* Every check and monitor has a false-positive cost —
  a `z_threshold` set too low pages someone at 3am for ordinary noise, and a team that gets
  paged for noise starts muting the monitor, which is worse than not having built it.
  Coverage and precision trade off; naming which specific failure a check is *for* (as the
  matrix above does) is what keeps that trade-off deliberate instead of accidental.
- *"A quality gate that blocks the pipeline is itself a production failure."* It is a
  visible, logged, recoverable failure. The alternative — the gate not existing, and a bad
  batch reaching a report, a model, or a customer — is the actual failure; it is just a
  silent one, which is why it feels less alarming and is far more damaging.

```python
# checks.py — solution
from __future__ import annotations
from dataclasses import dataclass, field


@dataclass
class CheckResult:
    name: str
    passed: bool
    checked: int
    violations: int
    samples: list = field(default_factory=list)

    def __repr__(self) -> str:
        status = "PASS" if self.passed else "FAIL"
        return f"<{self.name}: {status} ({self.violations}/{self.checked} violations)>"


def check_schema(rows, expected_columns, expected_types=None) -> CheckResult:
    if not rows:
        return CheckResult("schema", True, 0, 0)
    actual_columns = set(rows[0].keys())
    missing = expected_columns - actual_columns
    extra = actual_columns - expected_columns
    samples: list[str] = []
    violations = 0
    if missing:
        samples.append(f"missing columns: {sorted(missing)}")
        violations += 1
    if extra:
        samples.append(f"unexpected columns: {sorted(extra)}")
        violations += 1
    if expected_types:
        for i, r in enumerate(rows):
            for col, typ in expected_types.items():
                v = r.get(col)
                if v is None:
                    continue
                if not isinstance(v, typ):
                    violations += 1
                    if len(samples) < 5:
                        samples.append(f"row {i}: {col}={v!r} is {type(v).__name__}, expected {typ.__name__}")
    return CheckResult("schema", violations == 0, len(rows), violations, samples[:5])


def check_range(rows, column, min_val=None, max_val=None) -> CheckResult:
    violations = []
    for i, r in enumerate(rows):
        v = r.get(column)
        if v is None:
            continue
        if not isinstance(v, (int, float)):
            continue
        if (min_val is not None and v < min_val) or (max_val is not None and v > max_val):
            violations.append((i, v))
    return CheckResult(f"range:{column}", len(violations) == 0, len(rows), len(violations), violations[:5])


def check_null_rate(rows, column, max_rate) -> CheckResult:
    n = len(rows)
    nulls = sum(1 for r in rows if r.get(column) is None or r.get(column) == "")
    rate = nulls / n if n else 0.0
    return CheckResult(f"null_rate:{column}", rate <= max_rate, n, nulls, [f"rate={rate:.4f}"])


def check_referential(rows, column, valid_values) -> CheckResult:
    violations = []
    for i, r in enumerate(rows):
        v = r.get(column)
        if v is None or v == "":
            continue
        if v not in valid_values:
            violations.append((i, v))
    return CheckResult(f"referential:{column}", len(violations) == 0, len(rows), len(violations), violations[:5])
```

from __future__ import annotations


class LineageTracker:
    def __init__(self):
        self.sources: dict[str, tuple[str, int]] = {}
        self.derived_from: dict[str, list[str]] = {}

    def record_source(self, record_id: str, source_file: str, source_row: int) -> None:
        self.sources[record_id] = (source_file, source_row)

    def record_derivation(self, record_id: str, parent_ids: list[str]) -> None:
        self.derived_from[record_id] = list(parent_ids)

    def trace(self, record_id: str) -> set[tuple[str, int]]:
        seen: set[str] = set()
        leaves: set[tuple[str, int]] = set()
        stack = [record_id]
        while stack:
            rid = stack.pop()
            if rid in seen:
                continue
            seen.add(rid)
            if rid in self.sources:
                leaves.add(self.sources[rid])
            elif rid in self.derived_from:
                stack.extend(self.derived_from[rid])
            else:
                raise KeyError(f"unknown record id {rid!r}: not a recorded source or derivation")
        return leaves
```

# monitoring.py — solution
from __future__ import annotations
import math
from dataclasses import dataclass


@dataclass
class Alert:
    column: str
    metric: str
    message: str

    def __repr__(self) -> str:
        return f"<ALERT {self.column}.{self.metric}: {self.message}>"


def compute_null_rate(rows: list[dict], column: str) -> float:
    n = len(rows)
    if n == 0:
        return 0.0
    nulls = sum(1 for r in rows if r.get(column) is None or r.get(column) == "")
    return nulls / n


def check_null_rate_drift(column, history, latest, min_history=3, z_threshold=3.0):
    if len(history) < min_history:
        return None
    mean = sum(history) / len(history)
    variance = sum((h - mean) ** 2 for h in history) / (len(history) - 1)
    stdev = math.sqrt(variance)
    if stdev == 0:
        if latest != mean:
            return Alert(column, "null_rate", f"changed from a constant {mean:.4f} to {latest:.4f}")
        return None
    z = (latest - mean) / stdev
    if abs(z) > z_threshold:
        return Alert(
            column, "null_rate",
            f"z={z:.2f} (latest={latest:.4f}, baseline mean={mean:.4f}, baseline stdev={stdev:.4f})",
        )
    return None


def check_schema_drift(expected_columns: set[str], actual_columns: set[str]):
    missing = expected_columns - actual_columns
    added = actual_columns - expected_columns
    if not missing and not added:
        return None
    parts = []
    if missing:
        parts.append(f"missing: {sorted(missing)}")
    if added:
        parts.append(f"unexpected: {sorted(added)}")
    return Alert("*", "schema", "; ".join(parts))
```

## Assessment

Maps to the course's **pipeline labs (40%)** component. Per `dispatch.qualityGates`,
gaming-resistance is the design constraint: a learner must not be able to pass by
submitting checks that merely run without demonstrating they catch (or correctly fail to
catch) the right things.

**Module exam.** The learner receives an unseen ~40-row `events` table, a `sources` table
it should reference, six days of prior batch profiles, and exactly one planted defect from
this module's taxonomy (a range violation, an orphaned reference, a schema/type drift, or
a null-rate creep that no single batch's threshold catches). The learner must, in order:
(a) **predict**, in writing, which of a provided set of checks and monitors will and will
not catch the defect, and — separately — what the table will look like after all six days
of batches are applied in sequence, before running anything; (b) **run** the checks and
monitors and **diagnose** which defect category actually produced the observed result,
citing the specific check or monitor (or absence of one) responsible; (c) **fix** it using
this module's patterns — a tightened threshold, an added check, a drift baseline — not a
rewrite of the pipeline; (d) **trace**, using a provided `LineageTracker` populated across
the batch's transform stages, exactly which raw source file and row produced one specific
flagged output row, for remediation; (e) **prove** the fix with a test that re-applies all
six days of batches and passes. Passing requires all five; a correct fix with no
prediction, or a passing test with no lineage trace, both fail.

|---|---|---|---|---|

## Three-tier reading

Specific to this module's subject — the quiet policy decisions embedded in thresholds and
the double use of a lineage tracker — not the course-level scraping/consent reading, which
belongs to AIE-203-M05.

- **Tier 1 — material ground.** A null-rate spike or a silently dropped column that
  reaches a downstream consumer unflagged is not an abstraction: it is a fraud model
  retrained on quietly corrupted labels, a metrics dashboard a team is evaluated against
  silently under- or over-reporting, a partner's feed change that nobody noticed for
  three weeks. These are documented, recurring categories of production incident, not
  hypotheticals invented for this module — and every one of them was, at the moment it
  happened, sitting behind a system somebody described as having "data quality checks."

- **Tier 2 — what the field suppresses.** "We have monitoring" functions as a talisman the
  same way "the pipeline is idempotent" did in AIE-203-M02 — once said, the conversation
  about *what threshold, chosen by whom, tolerating how much* usually stops. But
  `max_rate=0.05` and `z_threshold=3.0` are not neutral defaults; they are policy
  decisions about how much silent wrongness is acceptable before a human is told, made
  once, by one engineer, on one day, and then applied without re-examination to every
  future batch the pipeline will ever see. And this module's own Lesson 4 proves the
  suppression runs deeper than tuning: a defect present since the pipeline's first day is
  invisible to *every* drift-based monitor by construction, no matter how well-tuned — a
  dashboard that has been "all green" since launch can mean "stable" and not "correct,"
  and the field's language rarely distinguishes the two out loud.

- **Tier 3 — sit with this.** The lineage tracker you built in Lab M04-B answers "which
  raw source produced this row" — a debugging question. The exact same graph, walked in
  the same direction, answers a different question with different stakes: "which
  downstream artifacts did this one person's record produce." Someone will eventually ask
  you to build lineage tracking "for data quality," and someone else — a compliance team,
  a person exercising a deletion request, a subpoena — will ask to query that same tracker
  for a different reason. Is that the same request wearing two names, or two different
  requests that happen to run on the same code? You will be the one who knows, because you
  will be the one who built the graph — and the answer you give will already be running
  in production before most of the people affected by it ever learn the graph exists.
