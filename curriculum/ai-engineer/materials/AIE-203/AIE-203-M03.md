Every streaming tutorial on the internet says some version of "Kafka gives you
exactly-once delivery." It is worth saying plainly, on the first page of this module,
that this claim is false in the sense most people hear it, and true only in a narrow,
specific sense this module will make precise. You cannot build a system that reliably
delivers a message across an unreliable network exactly one time — not with Kafka, not
with SQS, not with anything, because the acknowledgment that tells the sender "it
arrived" can itself be lost, and there is no way for the sender to distinguish "the
message was lost" from "the message arrived and only the ack was lost." That is not an
engineering gap someone forgot to close. It is a genuine, load-bearing fact about
communicating over a network that cannot guarantee delivery. What every real system that
*advertises* exactly-once actually does is deliver **at least once** — retry until
acked, accepting duplicates — and then make the duplicates harmless through idempotent
processing downstream. "Exactly-once" is the name for what an at-least-once system looks
like from the outside, once you can no longer see the duplicates it quietly absorbed.
This module builds the mechanism that does that absorbing, by hand, and then makes you
watch it fail when the mechanism is placed one line off from where it needs to be.

## Lessons

### Lesson 1 — Logs as the substrate

A batch pipeline's input is a file: it has a first row and a last row, and "done" is a
real, observable state. A stream's input is a **log** — an append-only, ordered sequence
of records that never has a last row, because a producer can always append one more.
Everything this module builds sits on top of one data structure: an append-only list
where each record gets a **offset** — its position in *ingest order*, assigned the
instant it's appended — that is completely separate from its **event_time** — the
moment the thing the record describes actually happened, assigned by whoever produced
it, long before or after it reached the log.

Those two orders are not the same axis, and the entire module lives in the gap between
them. A consumer resumes from an **offset** — "give me everything after position 41" —
because offset order is what "resume where I left off" means for an append-only log. But
a consumer that needs to reason about *when things happened* — was this the customer's
5th click or their 6th, is this window of activity closed — has to reason in
**event_time**, and event_time is not guaranteed to arrive in order. A phone that loses
signal for ten minutes and then flushes a buffer of ten minutes of taps does not
reorder them to look punctual; they land at whatever offset the log happens to be at
when the connection comes back, carrying event_times from ten minutes ago.

**Worked example.** A minimal log, showing the split explicitly:

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Record:
    offset: int
    key: str
    value: dict
    event_time: float


class Log:
    def __init__(self):
        self._records: list[Record] = []

    def append(self, key: str, value: dict, event_time: float) -> int:
        offset = len(self._records)          # ingest order — assigned here, now
        self._records.append(Record(offset, key, value, event_time))
        return offset

    def read_from(self, start_offset: int):
        return iter(self._records[start_offset:])
```

```python
log = Log()
log.append("tap", {"screen": "checkout"}, event_time=100.0)   # offset 0
log.append("tap", {"screen": "confirm"},  event_time=101.0)   # offset 1
# phone was offline 09:38–09:39 in event-time terms; reconnects, flushes buffer:
log.append("tap", {"screen": "cart"},     event_time=38.0)    # offset 2, event_time < offset 0's!
```

Offset order is `0, 1, 2` — that will never change, and a consumer resuming from offset 2
gets exactly what it expects. Event_time order is `38.0, 100.0, 101.0` — the record at
offset 2 belongs *before* the other two, chronologically, despite arriving last. Nothing
about the log is broken. This is what "real-time" actually has to contend with.

**Named misconceptions**

- *"'Real-time' means no delay."* It means bounded, small delay for the *processing*
  step — offset 2 above was appended to the log immediately on arrival, in real time. It
  says nothing about whether the event_time it carries is recent. Every streaming system
  has to define, explicitly, how it handles event_times that arrive after the fact —
  Lesson 4 is that definition.
- *"Offset order is the true order events happened in."* Offset order is *ingest* order —
  useful, durable, and exactly what a consumer resumes from — but it is a different axis
  from event_time, and treating them as interchangeable is the single most common root
  cause of "why is my windowed count wrong" bugs. Lab M03-C exists to make this
  concrete and unforgettable.

### Lesson 2 — Delivery semantics: a genuinely hard distributed-systems problem

There are exactly three delivery semantics a consumer can have with respect to a
producer, and only two of them are achievable in isolation:

1. **At-most-once.** Send it once, don't retry. If the ack is lost, or the receiver
   never got it, the message is gone. Simple, and silently lossy.
2. **At-least-once.** Retry until acked. If the ack is lost but the receiver *did* get
   it, you retry anyway — the receiver gets it again. Simple, and silently duplicating.
3. **Exactly-once.** Achievable *only* by combining #2 with a mechanism that makes
   duplicates harmless. It is not a third delivery mode a network can give you; it is a
   *processing property* built on top of #2.

The reason #3 cannot exist as a pure delivery mode is a real impossibility, not a
missing feature: the sender cannot distinguish "the message never arrived" from "the
message arrived and the ack was lost on the way back," because both look identical from
where the sender is standing — silence. Retrying resolves that ambiguity in favor of
availability (never lose a message) at the cost of correctness (you might deliver it
twice). Not retrying resolves it the other way. There is no third option at the delivery
layer. You must pick a side, and this module assumes you always pick at-least-once,
because losing data silently is almost always worse than a duplicate you can detect and
absorb — which is exactly what Lessons 3–4 build the machinery for.

**Worked example.** A consumer loop that reads a record, processes it, and *then* moves
its position forward is at-least-once by construction — if it dies between "processed"
and "moved forward," the record is read again on restart:

```python
def run_at_least_once(log, offsets, group, process):
    start = offsets.get(group)
    for record in log.read_from(start):
        process(record)                       # side effect happens first
        offsets.commit(group, record.offset + 1)   # THEN the position moves
```

Flip the two lines — commit the offset *before* calling `process` — and the same loop
becomes at-most-once: a crash between the commit and the processing means that record's
position is marked done, but its side effect never ran, and no retry will ever revisit
it. Neither ordering is a bug. They are two different, named contracts, and a real
production incident often traces back to nothing more than which line came first.

**Named misconceptions**

- *"Kafka/Kinesis/SQS give exactly-once, so I don't have to think about this."* Kafka's
  "exactly-once semantics" (EOS) is real, but scoped: a transactional producer plus a
  transactional consumer offset commit lets Kafka guarantee atomicity *for writes that
  stay inside Kafka* (read from one topic, write to another, commit the offset — all one
  transaction). The instant your processing does something outside Kafka's transaction
  coordinator — an HTTP call, a write to Postgres, a charge to a card — that guarantee
  does not reach it. You are back to plain at-least-once at that boundary, and you need
  your own idempotency mechanism there. That mechanism is Lesson 3.
- *"At-least-once is strictly safer than at-most-once, so always retry."* Retrying
  converts a *lost-forever* failure into a *duplicated* failure. Whether that trade is an
  improvement depends entirely on whether what's downstream is idempotent. Retrying an
  unguarded "charge this card $50" webhook is not safer than occasionally missing one —
  it is a different, and often worse, kind of incident.

### Lesson 3 — The exactly-once illusion: what mechanism is actually doing the work

Given at-least-once delivery (Lesson 2's forced choice) and an unbounded stream (Lesson
1), "exactly-once" reduces to one question: **can you make a duplicate delivery produce
no observable duplicate effect?** The answer is always the same shape, called an
**idempotency key**: every record gets a stable identity — here, its offset within a
consumer group is enough, since offsets are unique and monotonic per group — and before
performing an effect that can't be undone, the consumer atomically checks "have I
already applied this identity?" and records "yes" in the same breath as applying it.

The word *atomically* is not decoration. If the check-and-apply is two separate steps
(read a table, see it says "no," apply the effect, then write "yes") a crash between
them reproduces exactly the at-least-once duplicate Lesson 2 described — you've just
moved the race condition, not closed it. The fix is to make the dedup marker, the effect
itself, and the offset commit **one transaction**: either all three land, or none do.

```python
def run_effectively_once(log, conn, group, apply_fn):
    for record in log.read_from(get_offset(conn, group)):
        conn.execute("BEGIN")
        try:
            cur = conn.execute(
                "INSERT OR IGNORE INTO processed (consumer_group, offset) VALUES (?, ?)",
                (group, record.offset),
            )
            if cur.rowcount == 1:            # first time we've seen this offset
                apply_fn(conn, record)        # the effect — same transaction
            conn.execute(
                "INSERT INTO consumer_offsets (consumer_group, next_offset) VALUES (?, ?) "
                "ON CONFLICT(consumer_group) DO UPDATE SET next_offset = excluded.next_offset",
                (group, record.offset + 1),
            )
            conn.commit()
        except Exception:
            conn.rollback()
            raise
```

This closes the local case completely: a crash mid-`apply_fn` rolls back the dedup
marker along with it, so a retry sees a clean slate and applies exactly once. But look
carefully at what the transaction actually protects: only the SQL statements between
`BEGIN` and `commit()`. If `apply_fn` also does something *outside* SQL — increments a
Python counter, fires an HTTP request, writes to a different system — that action is not
covered, cannot be rolled back, and will duplicate on a crash-and-retry exactly like
Lesson 2's naive loop did. The transaction did not make the whole function
exactly-once. It made the part inside it exactly-once. When the real effect is external
(a payment API, a downstream webhook), the fix is the same idea one layer out: send the
same idempotency key *to that external system*, so it can do its own dedup check — this
is precisely what Stripe's `Idempotency-Key` header and similar mechanisms are for. The
pattern doesn't change; only which system is enforcing it does.

**Worked example.** Redelivery with no crash at all — the broker forgets your ack and
resends the entire log from the start — is blocked *before* `apply_fn` ever runs a
second time, because the dedup check happens first:

```python
run_effectively_once(log, conn, "g1", apply_fn)   # applies all 5 records once each
# ... broker "forgets", redelivers from offset 0 ...
run_effectively_once(log, conn, "g1", apply_fn)   # every record: INSERT OR IGNORE
                                                    # finds it already present, rowcount
                                                    # is 0, apply_fn is never called
```

Contrast this with a crash *during* `apply_fn` on a single record: the non-transactional
half of that one record's effect has already fired before the crash interrupts it, so it
duplicates even though the SQL half rolls back cleanly. Same mechanism, two different
outcomes, depending entirely on whether the dedup check ran to completion *before* the
irrevocable action or was interrupted partway through it. Lab M03-B makes both of these
real and measurable in the same test file.

**Named misconceptions**

- *"Wrapping the offset commit in a transaction makes the whole operation exactly-once."*
  It makes exactly the statements inside that transaction exactly-once. Any effect that
  happens outside the transaction — in application memory, or on a system the
  transaction doesn't span — is unprotected and can still duplicate. Precision about
  *which* mechanism covers *which* effect is the entire point of this lesson.
- *"Idempotency keys are a Kafka feature / a Stripe feature."* They are a general
  pattern — stable identity, checked and recorded atomically with the irrevocable action
  — that different systems implement in different places. Naming the pattern once here
  means recognizing it under a dozen different vendor names later, instead of learning
  each as a new, unrelated trick.

### Lesson 4 — Out-of-order events and the watermark

Lesson 1 showed that event_time can arrive out of offset order. Lesson 4 is about what a
consumer does when it needs to compute something *over* event_time — a count of events
per minute, a rolling total — on a stream that never ends and where "a little more data
for the window I already reported on" can always still show up. You cannot sort an
unbounded stream: sorting requires knowing you've seen everything that belongs before a
given point, and on a live stream you can never be sure of that. The only lever available
is a **watermark**: a moving, heuristic estimate of "I am now confident no more data
older than this will arrive," computed as `max(event_time seen so far) − allowed
lateness`. A time window is **finalized** — its count is emitted and frozen — the moment
the watermark passes the window's end. Any record that arrives afterward, whose event_time
falls in an already-finalized window, is **late**, and by policy is dropped rather than
silently revising a count you already reported as final.

`allowed_lateness` is the one knob, and it is a real trade, not a free parameter to
maximize: raise it and you catch more genuinely on-time-but-slow-arriving data, at the
cost of finalizing every window later (more latency, more state held in memory, since
nothing can be forgotten until its window closes). Lower it and windows finalize fast and
cheap, at the cost of treating more legitimately-late data as unrecoverable.

**Worked example.** Seven events, `window_size=60`, `allowed_lateness=30` — hand-trace
the watermark after each one (`max_event_time` so far, minus 30):

| # | event_time | window | max_event_time after | watermark after | window finalized this step? |
|---|---|---|---|---|---|
| 1 | 5 | 0 | 5 | −25 | — |
| 2 | 50 | 0 | 50 | 20 | — |
| 3 | 65 | 1 | 65 | 35 | — |
| 4 | 95 | 1 | 95 | 65 | **window 0** (end 60 ≤ 65) → emit `(0, 2)` |
| 5 | 40 | 0 | 95 | 65 | window 0 already finalized → **dropped as late** |
| 6 | 130 | 2 | 130 | 100 | — (window 1 end 120 > 100, still open) |
| 7 | 155 | 2 | 155 | 125 | **window 1** (end 120 ≤ 125) → emit `(1, 2)` |

Window 0 finalizes at event 4 with count 2 (events 1, 2) — event 5's event_time of 40
belongs to window 0, but window 0 is already closed by the time event 5 *arrives* (it
was delayed in transit), so it is counted as late and dropped rather than silently
bumping an already-reported total to 3. Window 2 is never finalized in this trace — it
stays open, waiting for the watermark to catch up.

**Named misconceptions**

- *"Sort the stream by event_time before processing and this problem goes away."* You
  cannot sort a sequence that never ends — there is no "later" to look ahead to and
  confirm nothing earlier is still coming. A watermark is not a workaround for the lack
  of a sort; it is the only tool available once you accept the stream is genuinely
  unbounded.
- *"A watermark guarantees no late data is ever lost."* It guarantees the *opposite*,
  by design: it is a bet, tuned by `allowed_lateness`, that trades completeness for
  bounded latency and bounded memory. Event 5 above is not a bug in the watermark — it is
  the watermark doing exactly its job, at the lateness threshold the policy chose.

```python
from __future__ import annotations

import sqlite3
from dataclasses import dataclass
from typing import Callable, Iterator


@dataclass(frozen=True)
class Record:
    offset: int
    key: str
    value: dict
    event_time: float


class Log:
    def __init__(self):
        self._records: list[Record] = []

    def append(self, key: str, value: dict, event_time: float) -> int:
        offset = len(self._records)
        self._records.append(Record(offset, key, value, event_time))
        return offset

    def read_from(self, start_offset: int) -> Iterator[Record]:
        return iter(self._records[start_offset:])

    def __len__(self) -> int:
        return len(self._records)


class OffsetStore:
    def __init__(self, conn: sqlite3.Connection):
        self.conn = conn
        self.conn.execute(
            """
            CREATE TABLE IF NOT EXISTS consumer_offsets (
                consumer_group TEXT PRIMARY KEY,
                next_offset INTEGER NOT NULL
            )
            """
        )
        self.conn.commit()

    def get(self, group: str) -> int:
        row = self.conn.execute(
            "SELECT next_offset FROM consumer_offsets WHERE consumer_group = ?",
            (group,),
        ).fetchone()
        return row[0] if row else 0

    def commit(self, group: str, next_offset: int) -> None:
        self.conn.execute(
            """
            INSERT INTO consumer_offsets (consumer_group, next_offset)
            VALUES (?, ?)
            ON CONFLICT(consumer_group) DO UPDATE SET next_offset = excluded.next_offset
            """,
            (group, next_offset),
        )
        self.conn.commit()


class ConsumerCrash(Exception):
    """Raised by test code to simulate a process dying mid-loop."""


def run_at_least_once(
    log: Log,
    offsets: OffsetStore,
    group: str,
    process: Callable[[Record], None],
) -> int:
    start = offsets.get(group)
    n_processed = 0
    for record in log.read_from(start):
        process(record)                               # side effect first
        offsets.commit(group, record.offset + 1)       # then advance
        n_processed += 1
    return n_processed
```

```python
# test_streaming_log.py
import sqlite3

import pytest

from streaming_log import ConsumerCrash, Log, OffsetStore, run_at_least_once


def build_log(n=5):
    log = Log()
    for i in range(n):
        log.append(key=f"o{i}", value={"amount": i}, event_time=float(i))
    return log


def test_clean_run_processes_every_record_exactly_once():
    log = build_log(5)
    conn = sqlite3.connect(":memory:")
    offsets = OffsetStore(conn)
    sink = []
    run_at_least_once(log, offsets, "g1", lambda r: sink.append(r.offset))
    assert sink == [0, 1, 2, 3, 4]
    assert offsets.get("g1") == 5


def test_crash_after_processing_before_commit_duplicates_on_restart():
    """This is the bug the lab exists to demonstrate: process-then-commit is
    at-least-once, and a crash in the gap between the two reprocesses the
    record on restart."""
    log = build_log(5)
    conn = sqlite3.connect(":memory:")
    offsets = OffsetStore(conn)
    sink = []
    crashed = {"already": False}

    def process(record):
        sink.append(record.offset)
        if record.offset == 2 and not crashed["already"]:
            crashed["already"] = True
            raise ConsumerCrash("simulated crash: after side effect, before commit")

    with pytest.raises(ConsumerCrash):
        run_at_least_once(log, offsets, "g1", process)

    # Side effect for offset 2 already landed; the position never advanced past it.
    assert sink == [0, 1, 2]
    assert offsets.get("g1") == 2

    # "Restart": invoke the same loop again with the same group.
    run_at_least_once(log, offsets, "g1", process)

    assert sink == [0, 1, 2, 2, 3, 4]
    assert offsets.get("g1") == 5
```

```python
# effectively_once.py — solution
from __future__ import annotations

import sqlite3

from streaming_log import Log, Record


def ensure_schema(conn: sqlite3.Connection) -> None:
    conn.executescript(
        """
        CREATE TABLE IF NOT EXISTS processed (
            consumer_group TEXT NOT NULL,
            offset INTEGER NOT NULL,
            PRIMARY KEY (consumer_group, offset)
        );
        CREATE TABLE IF NOT EXISTS state (
            key TEXT PRIMARY KEY,
            value TEXT NOT NULL,
            applied_offset INTEGER NOT NULL
        );
        CREATE TABLE IF NOT EXISTS consumer_offsets (
            consumer_group TEXT PRIMARY KEY,
            next_offset INTEGER NOT NULL
        );
        """
    )
    conn.commit()


def get_offset(conn: sqlite3.Connection, group: str) -> int:
    row = conn.execute(
        "SELECT next_offset FROM consumer_offsets WHERE consumer_group = ?", (group,)
    ).fetchone()
    return row[0] if row else 0


def run_effectively_once(log: Log, conn: sqlite3.Connection, group: str, apply_fn) -> tuple[int, int]:
    ensure_schema(conn)
    n_applied, n_skipped = 0, 0
    for record in log.read_from(get_offset(conn, group)):
        conn.execute("BEGIN")
        try:
            cur = conn.execute(
                "INSERT OR IGNORE INTO processed (consumer_group, offset) VALUES (?, ?)",
                (group, record.offset),
            )
            if cur.rowcount == 1:
                apply_fn(conn, record)      # effect + dedup marker: same transaction
                n_applied += 1
            else:
                n_skipped += 1
            conn.execute(
                """
                INSERT INTO consumer_offsets (consumer_group, next_offset)
                VALUES (?, ?)
                ON CONFLICT(consumer_group) DO UPDATE SET next_offset = excluded.next_offset
                """,
                (group, record.offset + 1),
            )
            conn.commit()
        except Exception:
            conn.rollback()
            raise
    return n_applied, n_skipped
```

*Verify.* Two tests: one proves the transaction's boundary (what it protects, what it
doesn't), one proves the dedup key blocks a redelivery before `apply_fn` ever runs again.

```python
# test_effectively_once.py
import sqlite3

import pytest

from streaming_log import Log
from effectively_once import get_offset, run_effectively_once


def build_log(n=5):
    log = Log()
    for i in range(n):
        log.append(key=f"k{i}", value={"amount": i * 10}, event_time=float(i))
    return log


def make_apply_fn(calls: dict, crash_at_offset=None, crashed=None):
    def apply_fn(conn, record):
        # NOT protected by the SQL transaction -- fires the instant this line runs.
        calls[record.key] = calls.get(record.key, 0) + 1
        # Protected: this write is inside the same transaction as the dedup marker.
        conn.execute(
            "INSERT INTO state (key, value, applied_offset) VALUES (?, ?, ?) "
            "ON CONFLICT(key) DO UPDATE SET value = excluded.value, "
            "applied_offset = excluded.applied_offset",
            (record.key, str(record.value), record.offset),
        )
        if (
            crash_at_offset is not None
            and record.offset == crash_at_offset
            and not crashed["already"]
        ):
            crashed["already"] = True
            raise RuntimeError("simulated crash mid-apply, inside the transaction")

    return apply_fn


def test_crash_inside_transaction_rolls_back_dedup_and_state_but_not_the_counter():
    log = build_log(5)
    conn = sqlite3.connect(":memory:")
    calls: dict = {}
    crashed = {"already": False}
    apply_fn = make_apply_fn(calls, crash_at_offset=2, crashed=crashed)

    with pytest.raises(RuntimeError):
        run_effectively_once(log, conn, "g1", apply_fn)

    # Offset 2's dedup marker, state row, and offset commit are ALL rolled back
    # together -- that's the point of one transaction.
    row = conn.execute(
        "SELECT COUNT(*) FROM processed WHERE consumer_group='g1' AND offset=2"
    ).fetchone()
    assert row[0] == 0
    assert get_offset(conn, "g1") == 2
    # But calls["k2"] already fired in plain Python before the raise -- the
    # rollback cannot reach it.
    assert calls["k2"] == 1

    # Restart: same group, offset 2 is reprocessed from scratch.
    run_effectively_once(log, conn, "g1", apply_fn)

    assert get_offset(conn, "g1") == 5
    assert calls["k2"] == 2          # the irrevocable, non-transactional effect DID duplicate
    state_row = conn.execute("SELECT applied_offset FROM state WHERE key='k2'").fetchone()
    assert state_row[0] == 2         # the transactional effect landed exactly once


def test_full_redelivery_is_blocked_before_apply_fn_ever_runs_again():
    log = build_log(5)
    conn = sqlite3.connect(":memory:")
    calls: dict = {}
    apply_fn = make_apply_fn(calls)

    n_applied, n_skipped = run_effectively_once(log, conn, "g1", apply_fn)
    assert n_applied == 5
    assert n_skipped == 0
    assert all(v == 1 for v in calls.values())

    # Simulate the broker forgetting our ack and redelivering the whole log from
    # the start -- OUR dedup store (the `processed` table) still remembers.
    conn.execute("UPDATE consumer_offsets SET next_offset = 0 WHERE consumer_group = 'g1'")
    conn.commit()

    n_applied2, n_skipped2 = run_effectively_once(log, conn, "g1", apply_fn)
    assert n_applied2 == 0
    assert n_skipped2 == 5
    # apply_fn never ran a second time for any key: the dedup check happens
    # BEFORE apply_fn, so a clean redelivery never reaches the counter at all.
    assert all(v == 1 for v in calls.values())
```

```python
# watermark_agg.py — solution
from __future__ import annotations

from streaming_log import Record


class WatermarkAggregator:
    def __init__(self, window_size: float, allowed_lateness: float):
        self.window_size = window_size
        self.allowed_lateness = allowed_lateness
        self.max_event_time = float("-inf")
        self.counts: dict[int, int] = {}
        self.finalized: set[int] = set()
        self.emitted: list[tuple[int, int]] = []
        self.late_dropped: list[Record] = []

    def _window_id(self, event_time: float) -> int:
        return int(event_time // self.window_size)

    def _watermark(self) -> float:
        return self.max_event_time - self.allowed_lateness

    def process(self, record: Record) -> None:
        self.max_event_time = max(self.max_event_time, record.event_time)
        window_id = self._window_id(record.event_time)

        if window_id in self.finalized:
            self.late_dropped.append(record)
        else:
            self.counts[window_id] = self.counts.get(window_id, 0) + 1

        watermark = self._watermark()
        newly_closeable = sorted(
            w
            for w in self.counts
            if w not in self.finalized and (w + 1) * self.window_size <= watermark
        )
        for w in newly_closeable:
            self.emitted.append((w, self.counts[w]))
            self.finalized.add(w)
```

## Three-tier reading

Specific to this module's subject — the policy hiding inside every "exactly-once" claim
and every watermark's lateness bound — not the course-level scraping/consent reading,
which belongs to AIE-203-M05.

- **Tier 1 — material ground.** Duplicate and lost events from streaming systems are not
  academic. A duplicated at-least-once delivery with no dedup key is a second copy of a
  fraud alert, a doubled inventory decrement, a customer billed twice for one purchase. A
  watermark set too aggressively is a fraud-detection window that closes before the
  slower, and often more suspicious, transaction pattern finishes arriving — closing
  early because closing early is cheap, not because the data was actually done arriving.
  These are documented, recurring categories of production incident, not hypotheticals
  invented for this module.

- **Tier 2 — what the field suppresses.** "Our platform guarantees exactly-once" is
  marketing shorthand for a real, narrow, internal guarantee (Lesson 2's Kafka-to-Kafka
  scoping) that gets quietly generalized, in conversation and in architecture diagrams,
  to cover effects it was never designed to reach. The suppression is not that the claim
  is a lie — it's technically true, inside its scope — it's that saying "exactly-once"
  out loud tends to end the conversation about where that scope stops, exactly at the
  point where the actual engineering (an idempotency key, sent one hop further, by a
  human who has to decide to do it) still has to happen.

- **Tier 3 — sit with this.** `allowed_lateness` is a number you pick, and it decides
  whose events count. A person on a slow or intermittent connection — a rural signal, an
  older device, a shared computer at a shelter with a queue for the terminal — is
  structurally more likely to have their events arrive after the watermark has already
  moved on. Their action still happened. Your system will not report an error, will not
  flag an anomaly, will not tell anyone it happened and was dropped — because, by the
  definition your `allowed_lateness` wrote, it wasn't late in a way the system considers
  wrong. It was late in a way the system considers *finished*. You already have the exact
  mechanism that decides this. When you set that number, on purpose, for a real system —
  whose lateness are you willing to let the watermark erase, and would you still set it
  the same way if you had to say that sentence to the person it erased?
