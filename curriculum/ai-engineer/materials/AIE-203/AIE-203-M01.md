# AIE-203-M01 — SQL and data modeling to fluency

**Course:** AIE-203 — Data Engineering for AI · **Tier:** core · **Durability:** mixed
**Hours:** 18 · **Sits in the descent:** the entry module. Before you can build a pipeline that survives replays, or a corpus you can stand behind, you need a place to put the data that doesn't quietly rot — a schema that models what actually happened, and a query engine you understand well enough to interrogate. This module descends from "query the database" (a skill most learners already half-have) to **relational modeling as a discipline**: normalization as a defense against specific, nameable anomalies; denormalization as a documented trade you choose, not a shortcut you fall into; and the **index** as a concrete structure you build by hand and measure — not folklore ("just add an index"), a B-tree you can reason about, on an engine that will show you its query plan if you ask.
**Prereq:** AIE-101 (Python fluency, testing discipline), AIE-110 (data structures at scale — this module cashes in AIE-110/M03's tree lesson directly: a SQL index *is* the balanced-tree-vs-heap decision rule made concrete on disk). **Co-req:** none within AIE-203; M02 (batch pipelines) assumes the schemas this module builds are already fluent territory.

> **Design note.** This module runs on **SQLite** — a real embedded engine, not an in-memory toy, with a real query planner, a real B-tree index implementation, and a real `EXPLAIN QUERY PLAN`. Every number below (row counts, timings, plan text) was **measured**, not invented, on the authoring machine (Python 3.11, single SSD-backed file, no other load). Learners re-measure on their own hardware — the exact milliseconds will move; the *shapes* (scan vs. search, the order-of-magnitude speedup, the plan text changing) will not. Everything here also runs unmodified against PostgreSQL with `EXPLAIN ANALYZE` in place of `EXPLAIN QUERY PLAN`; the module calls out the two or three places the wording differs. The domain running through every lesson and lab is deliberately the one this course will need again in M05: a table of ingested **documents**, their **sources**, their **authors**, and their **licenses** — the exact relational plumbing a training corpus needs before it can claim any provenance at all.

## Lessons

Four lessons. The first shows that normalization is not a style preference but a defense against three specific, nameable failure modes. The second shows the same discipline broken *on purpose*, as a documented trade rather than a shortcut. The third builds a B-tree index by hand — reading its effect in the query planner's own words, before and after — on a million-row table, so "add an index" stops being folklore. The fourth is where the schema gets asked questions nobody designed it for, and SQL fluency becomes the ability to answer them without rebuilding the schema.

1. **From one flat table to a schema — normalization as anomaly elimination.** 1NF/2NF/3NF as a checklist for update, insertion, and deletion anomalies you can point at, not an abstract purity test.
2. **Breaking normal form on purpose — denormalization as a documented trade.** When read cost dominates and redundancy is a choice you write down, not a mistake you didn't notice.
3. **The index is a concrete trade — B-tree, `EXPLAIN QUERY PLAN`, and the seek you bought.** Predict the plan before you run it; build the index; read the plan changing in the engine's own words; price what the index cost you.
4. **SQL fluency against a schema nobody designed for.** Joins, CTEs, window functions, and a recursive CTE — the tools that let a fixed schema answer questions its designer never anticipated.

### Lesson 1 — From one flat table to a schema: normalization as anomaly elimination

#### Teaching text

Every schema starts, if you let it, as one flat table — one row per fact, every column that seems relevant crammed in, because a flat table is the fastest thing to `SELECT *` from and the easiest to reason about when there are four rows in it. Here is that table, `documents_raw`, tracking documents ingested from external sources, before this course applies any discipline to it:

```sql
CREATE TABLE documents_raw (
    doc_id          INTEGER PRIMARY KEY,
    source_name     TEXT NOT NULL,
    source_url      TEXT NOT NULL,
    author_name     TEXT NOT NULL,
    author_email    TEXT NOT NULL,
    license_code    TEXT NOT NULL,
    license_text    TEXT NOT NULL,
    published_date  TEXT NOT NULL,
    token_count     INTEGER NOT NULL
);
```

Four rows in it, three from the same source:

| doc_id | source_name | source_url | author_name | license_code | published_date |
|---|---|---|---|---|---|
| 1 | Harborline Weekly | `harborline.example/rss` | J. Alvarez | cc-by | 2023-01-04 |
| 2 | Harborline Weekly | `harborline.example/rss` | J. Alvarez | cc-by | 2023-01-11 |
| 3 | Harborline Weekly | `harborline.example/rss` | M. Tran | cc-by | 2023-01-18 |
| 4 | OpenNotes Blog | `opennotes.example` | R. Okafor | cc0 | 2023-02-02 |

This table is not merely inelegant. It has three specific, demonstrable failure modes, and normalization exists to eliminate exactly these three — nothing more mystical than that:

**The update anomaly.** Harborline Weekly changes its feed URL. That fact is true once, but it is *stored* three times (rows 1, 2, 3), because the table repeats the source's attributes on every row that mentions it. `UPDATE documents_raw SET source_url = '...' WHERE source_name = 'Harborline Weekly'` will correctly touch all three rows *if you remember to write the `WHERE` that way* — but nothing in the schema enforces that the three copies stay identical. A partial update (a crashed job, a hand-run patch that only fixed row 1) silently produces a table where `documents_raw` disagrees with itself about Harborline's own URL. The anomaly isn't that updates are slow; it's that the schema has no way to guarantee the three copies ever *agree*.

**The insertion anomaly.** You learn about a new source — Third Voice Zine — before it has published anything. You cannot record that fact in `documents_raw`, because every column is `NOT NULL` and every row requires a `doc_id`, a `published_date`, a `token_count` — attributes of a document that doesn't exist yet. The table can only talk about a source *through* a document, so a source with zero documents is structurally unrepresentable. You'd have to invent a fake document to hang the source's facts on, which is worse than not recording it.

**The deletion anomaly.** `DELETE FROM documents_raw WHERE doc_id = 4` removes OpenNotes Blog's only document. Its URL, its license, its existence in your system, vanish in the same statement — not because you meant to forget OpenNotes Blog, but because its facts had nowhere else to live. Deleting a fact about a document silently deletes a fact about a source. Two different real-world things were sharing one row, and removing one destroyed the other.

**Normal forms are the fix, and each one targets a specific kind of repetition:**

- **1NF (first normal form):** every column holds a single, atomic value — no comma-packed lists, no repeating groups. `documents_raw` is already in 1NF; this is the floor, not the destination.
- **2NF:** every non-key column depends on the *whole* primary key, not part of it. This only bites composite keys (e.g., a table keyed on `(doc_id, tag)` where `source_name` depends only on `doc_id`, not on the tag) — `documents_raw` has a single-column key, so 2NF is automatically satisfied here, but it's the rule that would catch a *worse* version of this table.
- **3NF:** every non-key column depends on the key **and nothing but the key** — no column depends on another non-key column. This is the one `documents_raw` violates everywhere: `source_url` depends on `source_name`, not on `doc_id`; `license_text` depends on `license_code`, not on `doc_id`; `author_email` depends on `author_name`, not on `doc_id`. Each of those is a **transitive dependency** — `doc_id → source_name → source_url` — and every transitive dependency is a live update anomaly waiting to happen.

The fix is mechanical once you can name the transitive dependencies: **pull each one out into its own table**, keyed on the thing it actually depends on, and reference it by a foreign key.

```sql
CREATE TABLE sources (
    source_id   INTEGER PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,
    url         TEXT NOT NULL
);

CREATE TABLE licenses (
    license_code TEXT PRIMARY KEY,
    license_text TEXT NOT NULL
);

CREATE TABLE authors (
    author_id   INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,
    email       TEXT NOT NULL UNIQUE
);

CREATE TABLE documents (
    doc_id          INTEGER PRIMARY KEY,
    source_id       INTEGER NOT NULL REFERENCES sources(source_id),
    author_id       INTEGER NOT NULL REFERENCES authors(author_id),
    license_code    TEXT NOT NULL REFERENCES licenses(license_code),
    published_date  TEXT NOT NULL,
    token_count     INTEGER NOT NULL
);
```

Now `source_url` is stored **exactly once per source**, no matter how many documents that source has published. Updating it is one row:

```sql
UPDATE sources SET url = 'https://harborline.example/feed/v2' WHERE source_id = 1;
```

— and every document that references `source_id = 1` sees the new URL the instant you join, because there is only ever one copy to be stale. A source can exist with zero documents (insertion anomaly gone — `INSERT INTO sources (name, url) VALUES (...)` needs nothing from `documents`). Deleting every document for a source no longer deletes the source (deletion anomaly gone — `sources` and `documents` are independent tables connected by a foreign key, not one row wearing two hats). Reconstructing the original flat view, when you need it, is one join:

```sql
SELECT d.doc_id, s.name AS source_name, a.name AS author_name,
       l.license_text, d.published_date, d.token_count
FROM documents d
JOIN sources  s ON s.source_id    = d.source_id
JOIN authors  a ON a.author_id    = d.author_id
JOIN licenses l ON l.license_code = d.license_code
ORDER BY d.doc_id;
```

Normalization did not make the data harder to read — it made the *facts* have exactly one home each, and moved the cost from "keep N copies in sync forever" to "run a join when you want the flat view back." That trade — write-time integrity for read-time join cost — is the entire subject of Lesson 2.

#### Worked example — counting the anomaly, not just naming it

Take `documents_raw` above and ask three concrete, gradeable questions instead of "is this normalized":

1. **How many rows does one true fact about Harborline Weekly's URL currently occupy?** Count them: rows 1, 2, 3 — **three**. That number is the size of the update anomaly. Grow the table to 50,000 documents from Harborline Weekly and the number becomes 50,000 — the anomaly doesn't get worse in kind, only in blast radius.
2. **Run the migration and re-ask the question.** In the normalized schema, `SELECT COUNT(*) FROM sources WHERE name = 'Harborline Weekly'` returns **one**. One row, one fact, one place to be wrong.
3. **Prove the fix, not just assert it.** After `UPDATE sources SET url = '...' WHERE source_id = 1`, rejoin and confirm all three (or 50,000) documents report the new URL — a single `UPDATE`, zero risk of partial application, because there was never a second copy to miss.

This is the pattern Lab M01-A grades: not "did you write four `CREATE TABLE` statements" but "did you predict the anomaly count *before* migrating, and can you prove, with a single-row `UPDATE` and a rejoin, that the anomaly is gone."

#### Misconceptions to surface

- **"Normalization means lots of small tables, and more tables is always more 'correct.'"** No — normalization targets *specific* transitive dependencies. A table with no transitive dependencies (e.g., a pure key-value config table) is already in 3NF at one table; splitting it further buys nothing and costs a join. Surface it by asking the learner to name the transitive dependency each new table removes — if they can't name one, the split isn't normalization, it's just fragmentation.
- **"1NF/2NF/3NF is a strict ladder you climb once and never revisit."** In practice engineers reason almost entirely in terms of 3NF (or its stricter cousin, BCNF) directly, by asking "does this column depend on anything other than the whole key?" — the intermediate forms exist to name *why* a design fails, not as a checklist to run in numeric order. Surface it by going straight to "name the transitive dependency" on a new table and seeing whether the learner can skip 2NF's ceremony when there's no composite key to trigger it.
- **"A foreign key is just documentation; the real work is remembering to keep IDs in sync in application code."** No — `REFERENCES sources(source_id)` is enforceable by the engine (`PRAGMA foreign_keys = ON` in SQLite; on by default in Postgres) and will reject an `INSERT` that references a `source_id` that doesn't exist. Surface it by attempting `INSERT INTO documents (source_id, ...) VALUES (9999, ...)` with a nonexistent source and watching the engine — not application discipline — refuse it.

### Lesson 2 — Breaking normal form on purpose: denormalization as a documented trade

#### Teaching text

Lesson 1 built four tables and paid for it with a four-way join every time you want the flat view. That join is not free: on a large `documents` table, computing `RANK() OVER (...)` or a per-source daily count by joining out to `sources` and `authors` for every row, every time a dashboard refreshes, is real repeated work. **Denormalization** is the decision to pre-compute or duplicate some of that work — deliberately reintroducing redundancy — because the read pattern is now known, frequent, and worth the write-time cost of keeping the redundant copy current. It is normalization's mirror image, and it is not a mistake when it's *chosen*; it becomes a mistake only when it's an accident nobody wrote down.

The concrete trade, in both directions:

| | Normalized (3NF) | Denormalized |
|---|---|---|
| **Write cost** | Cheap — one row changes, one place | More expensive — every redundant copy must be kept in sync |
| **Read cost** | A join per query | Often zero joins — the answer is already sitting in one row |
| **Risk of disagreement** | Structurally impossible (one copy) | Real — the copies *can* drift if the sync path has a bug |
| **When it wins** | Write-heavy, ad hoc reads, correctness-critical | Read-heavy, known query shape, staleness tolerable |

A concrete example that belongs in this exact schema: a dashboard needs "documents ingested per source per day" refreshed on every page load, hit by many viewers, against a `documents` table that may hold tens of millions of rows by the time M05 needs it. Recomputing that with a live `GROUP BY` on every page view is real, repeated cost. Instead, maintain a **summary table**, updated once per ingestion batch rather than once per read:

```sql
CREATE TABLE daily_ingest_summary (
    source_id    INTEGER NOT NULL,
    ingest_date  TEXT NOT NULL,
    doc_count    INTEGER NOT NULL,
    token_total  INTEGER NOT NULL,
    PRIMARY KEY (source_id, ingest_date)
);

-- refreshed once per batch, not once per read:
INSERT INTO daily_ingest_summary (source_id, ingest_date, doc_count, token_total)
SELECT source_id, published_date, COUNT(*), SUM(token_count)
FROM documents
WHERE published_date = :batch_date
GROUP BY source_id, published_date
ON CONFLICT (source_id, ingest_date)
DO UPDATE SET doc_count   = excluded.doc_count,
              token_total = excluded.token_total;
```

`daily_ingest_summary` is redundant by construction — every number in it is derivable from `documents` — and that redundancy is exactly the point: the dashboard now reads one indexed row instead of scanning and aggregating millions. The cost moved from "every read pays the aggregation" to "every ingestion batch pays one small upsert," which is the correct place to pay it if reads outnumber writes by orders of magnitude, as dashboard reads against ingestion batches typically do.

The discipline this lesson insists on is not "avoid denormalization" — it's **write down the redundancy and its sync path**. A denormalized table with no documented answer to "what keeps this in sync, and what happens if that job fails" is not a deliberate trade; it's the exact same silent-drift risk as `documents_raw`'s update anomaly, just moved one level up and dressed as an optimization. The three questions every denormalization decision must answer in writing: **(1) which table is the source of truth**, (2) **what process keeps the derived copy current, and how often**, (3) **what does a consumer see during the gap between a write to the source and the derived copy catching up** (this is the eventual-consistency question M03's streaming module returns to under a different name).

#### Worked example — pricing the trade at scale

At 10,000,000 rows in `documents`, `SELECT source_id, COUNT(*), SUM(token_count) FROM documents WHERE published_date = ? GROUP BY source_id` scans and aggregates a meaningful fraction of the table on every call, even with an index on `published_date` — the aggregation work itself (not just the row lookup) is proportional to the number of matching rows, easily tens of thousands for a busy ingestion day. Read that query 500 times a day (a live dashboard, several viewers, auto-refresh) and you've paid that aggregation cost 500 times for data that changed, at most, once (the last ingestion batch that day).

`daily_ingest_summary` pays the aggregation **once per batch** (say, once per hour during active ingestion — 24 times a day, not 500) and every dashboard read after that is `SELECT * FROM daily_ingest_summary WHERE source_id = ? AND ingest_date = ?` against a two-column primary key — an O(log N) index lookup on a tiny table, not an O(N) scan-and-aggregate on a huge one. The trade is real: 24 expensive writes instead of 500 expensive reads, at the cost of a dashboard that can be up to one batch-interval stale, and the up-front discipline of writing down that staleness bound so nobody downstream is surprised by it.

#### Misconceptions to surface

- **"Denormalization means giving up and going back to one flat table."** No — `daily_ingest_summary` doesn't replace `documents`, `sources`, `authors`; it sits *alongside* them as a derived, disposable cache of an aggregate. The normalized tables remain the source of truth; you can always `DROP TABLE daily_ingest_summary` and rebuild it from a `GROUP BY` on `documents` — that rebuildability is the test for "this is a deliberate derived table," not an undocumented flat-table regression.
- **"If it's faster, it's better — always denormalize hot paths."** Only when the write-side sync cost and drift risk are genuinely smaller than the read-side savings, and only when someone has written down the sync path. Surface it by asking: for a table that's written once and read once (no repeated-read pattern), what does denormalizing buy you? (Nothing — you've added sync risk with no read savings to pay for it.)
- **"A materialized/summary table and a cache are the same thing, so consistency doesn't matter."** A cache is expected to be evictable and can be wrong-but-refreshed on any read; a denormalized table like `daily_ingest_summary` is queried directly as if authoritative. Surface it by asking what a dashboard shows a viewer in the window between an ingestion batch committing to `documents` and the summary upsert running — if the answer is "stale numbers presented as current, with no way to tell," that's the documented staleness bound question (3) from the teaching text, and skipping it is how a deliberate trade becomes an accidental lie.

### Lesson 3 — The index is a concrete trade: B-tree, `EXPLAIN QUERY PLAN`, and the seek you bought

#### Teaching text

AIE-110/M03 built a balanced binary search tree by hand and derived a decision rule: a balanced tree buys O(log N) search and ordered range queries, at the cost of more structure (and more memory) than a heap needs for the narrower job of "give me the extreme." A **SQL index** is that exact trade, materialized on disk, for the exact job of "find rows matching a condition without reading every row." Without an index, a `WHERE` clause forces the engine to read **every row** and test the condition on each one — a **table scan**, O(N) in the row count, no matter how selective the condition actually is. With a B-tree index on the filtered column, the engine can **descend** the tree — O(log N) — straight to the matching rows, exactly the way AIE-110 derived for a balanced BST.

Here is the mechanism, not folklore: a SQL index is (almost always) a **B-tree** — a balanced, multi-way tree, disk-page-aware so each node holds many keys instead of two — built once over the values in the indexed column(s), each leaf entry pointing back to the full row. `CREATE INDEX` builds this tree; every subsequent `INSERT`/`UPDATE`/`DELETE` on the indexed column(s) must also update the tree, which is the index's write-time cost — the same trade Lesson 2 named for denormalization, now paid on every write instead of every batch. Read the trade honestly: an index accelerates the reads that use it and taxes every write that touches the indexed column, plus the storage the tree itself occupies. That is why you do not index every column "just in case" — you index the columns your actual query patterns filter, join, or sort on, and nothing else.

**Predict before you run `EXPLAIN`.** This is the module's core discipline, lifted straight from AI-PRIMM: before executing a query against a table you haven't indexed, state on paper whether you expect a **scan** or a **search**, and why, based on what indexes exist. Then run `EXPLAIN QUERY PLAN` and read the engine's own answer. A one-million-row `documents` table, no index beyond the primary key, and this query:

```sql
SELECT doc_id, token_count
FROM documents
WHERE source_id = 137 AND published_date >= '2023-01-01'
ORDER BY published_date;
```

*Predict:* no index exists on `source_id` or `published_date`, so the engine has no way to jump to matching rows — it must read all 1,000,000 rows and test each against both conditions. Expect `SCAN documents`.

*Measured plan, before any index:*

```
QUERY PLAN
|--SCAN documents
`--USE TEMP B-TREE FOR ORDER BY
```

Both lines matter. `SCAN documents` confirms the table scan — every one of 1,000,000 rows read and tested. `USE TEMP B-TREE FOR ORDER BY` is a *second* cost: with no index to deliver rows already in `published_date` order, the engine builds a throwaway sorting structure over the 691 matching rows just to satisfy `ORDER BY`. Measured wall-clock, best-of-five runs after cache warmup: **43 ms**.

Now build the index the query actually needs — on the *columns the `WHERE` filters*, in an order that matches how they're used (equality column first, range column second — more on why below):

```sql
CREATE INDEX idx_documents_source_pubdate
ON documents(source_id, published_date);
```

*Predict, before rerunning:* the engine can now descend the tree on `source_id = 137` directly to that source's rows, and within them, the `published_date` portion of the same tree is already sorted, so the range condition *and* the `ORDER BY` should both be satisfied by walking the index — no scan, no temp sort. Expect `SEARCH documents USING INDEX ...` and the `TEMP B-TREE` line to disappear.

*Measured plan, after the index:*

```
QUERY PLAN
`--SEARCH documents USING INDEX idx_documents_source_pubdate (source_id=? AND published_date>?)
```

Exactly the predicted shape: one line, `SEARCH` (not `SCAN`), naming the index and both conditions it satisfies in a single descent — and the `ORDER BY` sort vanished, because the composite index's leaf order *is* ascending `published_date` within each `source_id`, so no temp structure was needed. Measured wall-clock, best-of-five: **1.18 ms** — a **~36×** speedup, for identical results (row sets compared equal). That factor is not a constant you should expect to reproduce exactly — it depends on selectivity (how many of the 1,000,000 rows actually match `source_id = 137`: here, ~2,000, or 0.2% — a *highly* selective filter, exactly the case an index is built for) — but the **shape** (`SCAN` → `SEARCH`, milliseconds to fraction-of-a-millisecond) reproduces on any engine, any hardware, any table past a few thousand rows.

**Column order in a composite index is not cosmetic.** `(source_id, published_date)` and `(published_date, source_id)` are two *different* trees. A composite index is only useful as a seek for a **prefix** of its columns — `source_id` alone, or `source_id` + `published_date` together, both use the index; `published_date` alone, without `source_id`, cannot descend the tree efficiently on this index, because the tree is sorted by `source_id` first. Measured: filtering by `published_date` alone against the *same* `(source_id, published_date)` index still produces a plan mentioning the index (`SCAN documents USING COVERING INDEX idx_documents_source_pubdate`) — but note the verb: **`SCAN`, not `SEARCH`**. The engine chose to scan the narrower index instead of the wider table (a real, smaller win — the index doesn't carry every column, so there's less to read), but it is still reading every entry, not seeking. This is the misconception worth planting deliberately: **an index being named in the plan does not mean a seek happened.** Read the verb.

An index also has a genuine cost, and Lesson 2's ledger discipline applies here too: building `idx_documents_source_pubdate` over 1,000,000 rows took 0.75 seconds and added roughly 25% to the on-disk size of the table (measured: base table ~70 MB, +~25 MB for this one two-column index). Every future `INSERT` into `documents` now also inserts into this B-tree. An index is exactly the write-cost-for-read-speed trade Lesson 2 named for denormalization — the mechanism differs, the ledger is identical.

#### Worked example — reading a plan for a query with *no* good index

Ask a different question of the same table: "which content hashes appear under more than one `source_id`?" — a direct preview of the contamination check M05 formalizes.

```sql
SELECT content_hash, COUNT(DISTINCT source_id) AS n_sources, COUNT(*) AS n_docs
FROM documents
GROUP BY content_hash
HAVING COUNT(DISTINCT source_id) > 1;
```

*Predict:* `idx_documents_source_pubdate` is built on `(source_id, published_date)` — `content_hash` isn't in it anywhere, so this query gets no benefit from the index that exists. Expect a full table scan regardless.

*Measured plan:*

```
QUERY PLAN
|--SCAN documents
|--USE TEMP B-TREE FOR GROUP BY
`--USE TEMP B-TREE FOR count(DISTINCT)
```

Confirmed: `SCAN documents` — the existing index is irrelevant to this access pattern — plus *two* temp B-trees, one to group by `content_hash`, one to deduplicate for `COUNT(DISTINCT source_id)`. Measured: **0.81 seconds** on 1,000,000 rows — 20× slower than even the *unindexed* single-source query, because this query must touch every row and do real aggregation work on each, not just filter. This is the honest cost of a naive contamination check at scale, and the reason M05 will introduce a hash-based structure purpose-built for exactly this membership test rather than a `GROUP BY HAVING` on a billion-row table. The index built for one access pattern (find one source's recent documents) did nothing for a different access pattern (find hashes shared across sources) — **an index is scoped to the query shapes it was built for, not a general accelerant.**

#### Misconceptions to surface

- **"Once you add an index, every query against that table gets faster."** No — an index accelerates only queries whose filter/join/sort matches a *prefix* of its columns. The contamination-check query above ran against a table with an index and was still a full scan plus two temp B-trees, because the index didn't cover `content_hash`. Surface it by having the learner predict, then check, whether a *specific* new query benefits from an *existing* index before assuming any index helps.
- **"If `EXPLAIN QUERY PLAN` mentions my index by name, it did a seek."** No — read the verb. `SCAN documents USING COVERING INDEX ...` is still O(N); the engine chose the narrower index over the wider table (a real but smaller win) without ever descending to a subset. Only `SEARCH ... USING INDEX ... (column=?)` is the O(log N) seek. Surface it by comparing the two measured plans above side by side and asking which one actually skipped rows.
- **"Composite index column order doesn't matter, it indexes both columns either way."** It indexes both, but only in *one* order, and the index can only be used as a seek for a query matching a *left prefix* of that order. `(source_id, published_date)` seeks on `source_id` alone or `source_id + published_date` together; it cannot seek on `published_date` alone. Surface it by having the learner predict the plan for a `published_date`-only filter against this exact index before running it (expected miss: most predict `SEARCH`; measured reality is `SCAN ... USING COVERING INDEX`).

### Lesson 4 — SQL fluency against a schema nobody designed for

#### Teaching text

A schema is designed against the questions its author anticipated. It will be asked questions its author did not. That gap — not the `CREATE TABLE` statements — is where SQL fluency actually lives, and it's exercised through four tools that let a fixed schema answer questions it wasn't built for, without adding a column or a table: **joins** (already fluent by this point), **CTEs** (`WITH`, for structuring a multi-step query into named, readable stages), **window functions** (`OVER (...)`, for computing a value *per row* while still seeing the whole partition — ranks, running totals, comparisons to a group without collapsing it), and **recursive CTEs** (`WITH RECURSIVE`, for generating or walking a structure the table doesn't itself enumerate — a calendar of dates, a hierarchy).

**Window functions answer "rank within a group without losing the rows."** A plain `GROUP BY` collapses rows into one per group — useful for "how many documents per source," useless for "which source ranks where, while still seeing every source's row." A window function computes its result *per row*, using a group ("window") of related rows, without collapsing anything:

```sql
SELECT source_id, doc_count,
       RANK() OVER (ORDER BY doc_count DESC) AS rank_by_volume
FROM (
  SELECT source_id, COUNT(*) AS doc_count
  FROM documents
  GROUP BY source_id
)
ORDER BY rank_by_volume
LIMIT 5;
```

Measured against the 1,000,000-row table (500 sources, roughly 2,000 documents each):

```
(115, 2136, 1)
(64,  2124, 2)
(4,   2110, 3)
(48,  2110, 3)
(230, 2102, 5)
```

Read the tie: sources 4 and 48 both published 2,110 documents and both received rank **3** — `RANK()` leaves a gap (the next rank is 5, not 4) precisely because two rows tied for 3rd; `DENSE_RANK()` would instead assign 4 with no gap, and `ROW_NUMBER()` would arbitrarily break the tie and assign 3 and 4. Which of the three you want is a real modeling decision, not a stylistic one — "top 5 by rank" behaves differently under each when ties exist, and picking the wrong one silently drops or duplicates a source at the boundary.

**A CTE turns a nested subquery into a named, readable pipeline stage** — no new capability over a subquery, but a real fluency difference once queries have more than one step. A running monthly token total for one source:

```sql
WITH monthly AS (
  SELECT substr(published_date, 1, 7) AS ym, SUM(token_count) AS tokens
  FROM documents
  WHERE source_id = 137
  GROUP BY ym
)
SELECT ym, tokens,
       SUM(tokens) OVER (ORDER BY ym) AS running_total
FROM monthly
ORDER BY ym
LIMIT 6;
```

Measured (first six months for source 137):

```
('2019-01', 220984, 220984)
('2019-02', 162205, 383189)
('2019-03', 169389, 552578)
('2019-04', 195525, 748103)
('2019-05', 161002, 909105)
('2019-06', 176196, 1085301)
```

The `monthly` CTE computes the aggregate once, by name; the outer `SELECT` adds a running total over it with `SUM(...) OVER (ORDER BY ym)` — a window function whose window is "every row up to and including this one," the running-total idiom. Nest that same logic as a bare subquery and it's identical in cost, and meaningfully harder to read once there are three stages instead of one; the CTE is a fluency and maintainability tool, not a performance one.

**A recursive CTE generates rows the table doesn't contain**, most commonly a calendar, to find *gaps* — a question no `SELECT` over existing rows can ever answer on its own, because a missing row has no row to select. "Which months did source 77 fail to ingest anything?":

```sql
WITH RECURSIVE months(m) AS (
  SELECT '2023-01'
  UNION ALL
  SELECT strftime('%Y-%m', date(m || '-01', '+1 month'))
  FROM months
  WHERE m < '2023-06'
)
SELECT months.m AS month,
       COALESCE(ingest_log.doc_count, 0) AS docs,
       CASE WHEN ingest_log.doc_count IS NULL
            THEN 'GAP - no ingestion recorded' ELSE 'ok' END AS status
FROM months
LEFT JOIN ingest_log
       ON ingest_log.ym = months.m AND ingest_log.source_id = 77
ORDER BY months.m;
```

Measured, against an `ingest_log` with real rows for January–March and May–June but nothing for April:

```
('2023-01', 340, 'ok')
('2023-02', 298, 'ok')
('2023-03', 311, 'ok')
('2023-04', 0,   'GAP - no ingestion recorded')
('2023-05', 402, 'ok')
('2023-06', 388, 'ok')
```

The `months` CTE recurses — `UNION ALL` of a base case (`'2023-01'`) and a recursive step that advances one month at a time until the stop condition (`WHERE m < '2023-06'`) is no longer true — to *manufacture* the six calendar rows the table was never going to contain on its own. `LEFT JOIN` against that manufactured calendar is what turns "missing data" into a queryable, provable fact (`'2023-04'` with `NULL` on the right side) instead of a silent absence nobody notices until someone asks why April's numbers look low in a downstream report. This is the general shape of "answering a question the schema wasn't designed for": the schema records *presence*; the question is about *absence*; a recursive CTE builds the universe of things that could have been present, so the join can expose what wasn't.

**Fluency, for this module's purposes, is the ability to look at a new ad hoc question and correctly predict which of these tools it needs — and whether the existing indexes will help it — before writing a line of SQL.** That prediction, sealed before the query runs, is what Lab M01-C grades.

#### Worked example — the same question, three ways, three different plans

"Show me source 137's documents from 2023 onward, in order" can be written as a plain filtered `SELECT`, and it uses the seek from Lesson 3 (`SEARCH ... USING INDEX idx_documents_source_pubdate`). "Rank every source by document count" needs a window function over a `GROUP BY`, and — because no index covers `content_hash`-free aggregation over *all* sources — it still scans, just the narrower covering index rather than the full table. "Which content hashes cross sources" needs neither a window function nor an index that exists yet; it's an unindexed `GROUP BY HAVING` and pays the 0.81-second full-scan cost measured in Lesson 3. Three questions against the *same* schema, three different tools, three different costs — and predicting which is which, before running any of them, is the actual skill this lesson installs. A learner who can write correct SQL but can't predict "this one will scan, that one will seek" hasn't finished the lesson; they've finished a syntax tutorial.

#### Misconceptions to surface

- **"A window function is just a fancier `GROUP BY`."** A `GROUP BY` reduces N rows to (number of groups) rows; a window function keeps all N rows and attaches a per-row computed value derived from its window. `RANK() OVER (...)` on 500 sources returns 500 rows, one rank per source, not one row for "the ranking." Surface it by asking the learner to predict the row count of the window-function query above before running it (expected: 500, or `LIMIT 5` of those 500 — not 1).
- **"CTEs make queries faster."** A `WITH` clause is (in SQLite and most engines, by default) inlined the same as an equivalent subquery — same plan, same cost. It buys readability and the ability to reference the same intermediate result twice without repeating the subquery, not speed. Surface it by comparing `EXPLAIN QUERY PLAN` for the CTE version of a query against the equivalent nested-subquery version and confirming the plans match.
- **"You need application code (a loop, a script) to find gaps in dates — SQL can't generate rows that aren't there."** A recursive CTE manufactures exactly those rows inside the engine, and a `LEFT JOIN` against them exposes the absence as a normal `NULL` you can filter, count, or report on — no round trip to application code required. Surface it by asking the learner to solve the April-gap example in Python first (a loop generating months, a set difference against observed months) and then show them the six-line SQL equivalent doing the same work inside the engine, at the same place the data already lives.

```python
# m01harness.py — provided, shared by all three labs
import json, time, timeit, sqlite3

def sealed_predict(name, answers: dict, path="predictions.jsonl"):
    """Append-only prediction log. Call once per lab, before running any query
    against the real database. `answers` is a plain dict of your predictions."""
    record = {"lab": name, "ts": time.time(), "answers": answers}
    with open(path, "a") as f:
        f.write(json.dumps(record) + "\n")
    return record

def explain(cur: sqlite3.Cursor, sql: str, params=()):
    """Run EXPLAIN QUERY PLAN and return the plan lines as a list of strings."""
    cur.execute("EXPLAIN QUERY PLAN " + sql, params)
    return [row[-1] for row in cur.fetchall()]

def bench(fn, repeats=5):
    """Best-of-`repeats` wall-clock seconds for one call to fn()."""
    return min(timeit.timeit(fn, number=1) for _ in range(repeats))
```

def create_normalized_schema(con: sqlite3.Connection):
    con.execute("PRAGMA foreign_keys = ON;")
    con.executescript("""
    CREATE TABLE sources (
        source_id   INTEGER PRIMARY KEY,
        name        TEXT NOT NULL UNIQUE,
        url         TEXT NOT NULL
    );
    CREATE TABLE licenses (
        license_code TEXT PRIMARY KEY,
        license_text TEXT NOT NULL
    );
    CREATE TABLE authors (
        author_id   INTEGER PRIMARY KEY,
        name        TEXT NOT NULL,
        email       TEXT NOT NULL UNIQUE
    );
    CREATE TABLE documents (
        doc_id          INTEGER PRIMARY KEY,
        source_id       INTEGER NOT NULL REFERENCES sources(source_id),
        author_id       INTEGER NOT NULL REFERENCES authors(author_id),
        license_code    TEXT NOT NULL REFERENCES licenses(license_code),
        published_date  TEXT NOT NULL,
        token_count     INTEGER NOT NULL
    );
    """)
    con.commit()

def migrate(con: sqlite3.Connection):
    con.execute("""
        INSERT INTO sources (name, url)
        SELECT DISTINCT source_name, source_url FROM documents_raw;
    """)
    con.execute("""
        INSERT INTO licenses (license_code, license_text)
        SELECT DISTINCT license_code, license_text FROM documents_raw;
    """)
    con.execute("""
        INSERT INTO authors (name, email)
        SELECT DISTINCT author_name, author_email FROM documents_raw;
    """)
    con.execute("""
        INSERT INTO documents (doc_id, source_id, author_id, license_code,
                                published_date, token_count)
        SELECT r.doc_id, s.source_id, a.author_id, r.license_code,
               r.published_date, r.token_count
        FROM documents_raw r
        JOIN sources s ON s.name  = r.source_name
        JOIN authors a ON a.email = r.author_email;
    """)
    con.commit()

Three questions, asked cold by a hypothetical stakeholder who has never seen the schema design:

Reference solution:

```python
def top5_sources_with_ties(con: sqlite3.Connection):
    cur = con.cursor()
    cur.execute("""
        SELECT source_id, doc_count,
               RANK() OVER (ORDER BY doc_count DESC) AS rank_by_volume
        FROM (
            SELECT source_id, COUNT(*) AS doc_count
            FROM documents GROUP BY source_id
        )
        ORDER BY rank_by_volume
        LIMIT 5;
    """)
    return cur.fetchall()

def running_monthly_tokens(con: sqlite3.Connection, source_id: int):
    cur = con.cursor()
    cur.execute("""
        WITH monthly AS (
            SELECT substr(published_date, 1, 7) AS ym, SUM(token_count) AS tokens
            FROM documents
            WHERE source_id = ?
            GROUP BY ym
        )
        SELECT ym, tokens, SUM(tokens) OVER (ORDER BY ym) AS running_total
        FROM monthly
        ORDER BY ym;
    """, (source_id,))
    return cur.fetchall()

def cross_source_duplicate_hashes(con: sqlite3.Connection):
    cur = con.cursor()
    cur.execute("""
        SELECT content_hash, COUNT(DISTINCT source_id) AS n_sources, COUNT(*) AS n_docs
        FROM documents
        GROUP BY content_hash
        HAVING COUNT(DISTINCT source_id) > 1;
    """)
    return cur.fetchall()

def ingestion_gaps(con: sqlite3.Connection, source_id: int, start_ym: str, end_ym: str):
    cur = con.cursor()
    cur.execute("""
        WITH RECURSIVE months(m) AS (
            SELECT :start
            UNION ALL
            SELECT strftime('%Y-%m', date(m || '-01', '+1 month'))
            FROM months WHERE m < :end
        ),
        actual AS (
            SELECT DISTINCT substr(published_date, 1, 7) AS ym
            FROM documents WHERE source_id = :sid
        )
        SELECT months.m AS month,
               CASE WHEN actual.ym IS NULL THEN 'GAP' ELSE 'present' END AS status
        FROM months
        LEFT JOIN actual ON actual.ym = months.m
        ORDER BY months.m;
    """, {"start": start_ym, "end": end_ym, "sid": source_id})
    return cur.fetchall()
```

## Assessment

Maps to AIE-203's **pipeline labs** (this module's contribution is the schema and index literacy every later pipeline lab assumes) and **SQL fluency exams** (20% of course grade) components. Gaming-resistance is the design constraint, not an afterthought:

1. **The three labs are graded primarily on the sealed Predict artifacts, reconciled against measurement — not on "the query returned the right rows."** A learner who runs `CREATE INDEX` on every column of a table until a query happens to get fast, with no prediction trail, scores below a learner who predicted `SCAN` correctly, built one targeted index, and reconciled a wrong speedup-magnitude guess with the correct mechanism.
2. **The module exam hands the learner an unseen schema (3–5 tables, at least one genuine 3NF violation, no indexes beyond primary keys) and a slow ad hoc query against it**, and grades the full judgment trail:

| Step | What's graded | Gaming-resistance |
|---|---|---|
| **Predict** | Before running anything: state whether the query will scan or seek, and why, given the schema and indexes as provided | Cannot be produced by trial-and-error against the live database — it's timestamped before DB access is granted |
| **Locate** | Identify the specific missing index (or the specific transitive dependency causing a 3NF violation) that explains the slow plan | A learner who only knows "add an index somewhere" without naming *which* columns, in *which* order, cannot score full marks here |
| **Fix** | Write the `CREATE INDEX` (or schema migration) that resolves it | Copy-pasted DDL from elsewhere fails silently if it doesn't match the specific schema given — this is not a fill-in-the-blank |
| **Prove** | Show `EXPLAIN QUERY PLAN` before and after, and the measured wall-clock difference, matching the predicted verb and rough magnitude | The proof artifact is the engine's own output on the learner's own run — it cannot be faked without actually building and measuring the fix |

**Rubric (per exam item, 0–4 scale):**

| Score | Predict | Locate | Fix | Prove |
|---|---|---|---|---|
| **4** | Correct verb + correct mechanism named, before access to results | Names the exact column(s)/order or exact dependency | Minimal, correct DDL/migration; no unnecessary indexes/tables added | Before/after plan and timing both shown, matches predicted shape, reconciled if it didn't |
| **3** | Correct verb, mechanism vague or partially wrong | Right table, imprecise on column order or which dependency | Correct but with one unnecessary addition | Proof present, one gap in before/after comparison |
| **2** | Wrong verb, but reasoning shows understanding of scan vs. seek | Right general area, wrong specific column | Fix addresses the symptom, not the root query pattern | Only "after" state shown, no before comparison |
| **1** | No prediction, or predicted after peeking at results | Cannot name a specific fix location | Fix doesn't resolve the measured slowness | No plan/timing evidence, verbal claim only |
| **0** | — | — | Fix breaks other data (e.g., FK violation, lost rows) | — |

A learner cannot pass this exam by having memorized `CREATE INDEX` syntax; the schema and the slow query are unseen, generated per learner, and the score is dominated by the Predict and Locate columns — the parts that require actually reasoning about the specific schema in front of them, not reciting a pattern.

## Three-tier reading

Specific to this module's subject — what a schema chooses to make representable, and what it silently forecloses — not the course-level boilerplate restated.

- **Tier 1 — material ground.** Every column you define is a decision about what can later be asked, and every column you omit is a decision about what cannot. `documents_raw`'s `license_code` enum (`cc-by`, `cc-by-sa`, `cc0`, `unlicensed-scrape`, `publisher-licensed`) is not a neutral technical fact discovered from the data — it is a finite list someone chose, and every document that doesn't cleanly fit one of those five values will be *forced* into one of them the moment it's ingested, by whoever writes that day's ingestion code, usually without a second thought. This is documented, verifiable, and true of every schema in this course, not a special property of this one.
- **Tier 2 — what the field suppresses.** "The schema just models the data" suppresses that the schema was written *before* most of the data existed, by someone guessing at the shape of facts they hadn't seen yet — and that every later engineer who queries this schema inherits those early guesses as if they were neutral infrastructure rather than a series of judgment calls. A `license_code` column with five values quietly teaches every downstream consumer that licensing has five possible states, because the column makes the other states — contested, unknown, revoked-since-ingestion, dual-licensed-in-a-way-none-of-these-five-capture — literally impossible to record, not merely inconvenient. The suppression isn't in the schema itself; it's in treating schema design as a solved technical step you do once at the start, rather than a recurring act of narrowing that every later query, index, and pipeline in this course will inherit without re-examining.
- **Tier 3 — sit with this.** A document arrives whose licensing status doesn't fit cleanly into any of your five `license_code` values — ambiguous provenance, a source that's since disputed its own rights to redistribute, a license that changed after ingestion but before you noticed. You have two options and both are cheap to execute and expensive to live with: force it into the closest existing value (`unlicensed-scrape`, probably) and let the narrowness silently become the policy, indistinguishable in every future query from documents that were genuinely, simply unlicensed from the start — or widen the schema, slow down every index and every query built against the old five-value assumption, and make every future engineer who touches this table confront the ambiguity you didn't resolve. Neither option is obviously correct. Pick one, and write down — in the schema's own migration history, not in a comment nobody will read — which one you picked and why, because the record of that decision is the only thing that will let someone three modules from now know it was a decision at all, rather than a fact about the world.
