## Lessons

### Lesson 1 — Concurrency is not parallelism

These two words are used interchangeably in job postings and blog posts, and the conflation is the source of an enormous amount of confused code. They are different axes.

- **Concurrency is a property of *structure*:** a program is concurrent if it is *composed of* multiple independently-progressing tasks whose lifetimes overlap. Concurrency is about **dealing with** many things at once — how you decompose the work so that a task that is waiting (on a socket, a disk, a lock) does not stop the others.
- **Parallelism is a property of *execution*:** a program runs in parallel if multiple tasks are *physically executing at the same instant*, which requires multiple execution units — multiple CPU cores. Parallelism is about **doing** many things at once.

The classic framing (Rob Pike's): *concurrency is dealing with lots of things at once; parallelism is doing lots of things at once.* Concurrency is a way to **structure** a solution; parallelism is one possible **execution** of that structure. You can have either without the other:

| | Not parallel (1 core) | Parallel (≥2 cores) |
|---|---|---|
| **Not concurrent** | one task, run start to finish | (meaningless — one task can't use two cores) |
| **Concurrent** | many tasks, *interleaved* on one core (time-slicing) — this is what a single-core OS does with 200 processes | many tasks, some *simultaneously* on separate cores |

The single-core "concurrent but not parallel" cell is the one people forget exists, and it is the key to the whole GIL story in Lesson 4. On one core the OS runs task A for a few milliseconds, saves its registers, loads task B's, runs B, and so on — a **context switch**. The tasks *make progress in overlapping windows of wall-clock time*; they never execute in the *same instant*. To a human watching, both "run at once." To the silicon, they take strict turns.

Two ways to get concurrency, and the distinction is the spine of Lesson 2:

- **Threads** — multiple flows of control **inside one process, sharing one address space.** Every thread sees the same heap, the same globals, the same open file descriptors. Cheap to create, cheap to switch between (no address-space change). And — the whole reason this module exists — they can step on each other's memory, because it is *the same memory*.
- **Processes** — multiple flows of control, **each with its own private address space** (the M01 fact). A global in one process is invisible to another. Heavier to create, heavier to communicate across (you must explicitly send bytes — a pipe, a socket, shared memory you opt into). And — the whole *safety* story — they *cannot* accidentally corrupt each other's memory, because they do not share any.

That is the trade this entire module turns on: **threads share memory (fast, dangerous); processes isolate memory (safe, costly to coordinate).** Hold it.

#### Worked example — the same four tasks, three ways

Four HTTP requests, each 100 ms of network wait (so mostly *waiting*, not computing), plus a tiny bit of parsing:

```
Sequential (M02's loop):   [req0 100ms][req1 100ms][req2 100ms][req3 100ms]  → ~400 ms
                            one task at a time; total = sum of the waits.

Concurrent, 1 core:        req0 ▓░░░░░░░░░  (issue, then WAIT for the socket)
                           req1 ░▓░░░░░░░░
                           req2 ░░▓░░░░░░░  all four sockets in flight at once;
                           req3 ░░░▓░░░░░░  the core is idle during the waits →
                                            → ~100 ms (bounded by the slowest wait)
                           NOT parallel — the core did almost no work; it overlapped the *waiting*.

Parallel, 4 cores:         each request's *computation* on its own core simultaneously.
                           Buys nothing here (the work is waiting, not computing) —
                           it pays only when the tasks are CPU-bound.
```

The middle case is the revelation: four requests finished in ~100 ms on **one** core, no parallelism involved. The win came from **overlapping the waiting**, which is a *concurrency* win, not a parallelism win. This is precisely why an I/O-bound server (M02's server, waiting on sockets) needs concurrency but barely benefits from parallelism — and why Python's GIL, which blocks parallelism but not concurrency, is fine for exactly that workload (Lesson 4).

#### Misconception 1 — "concurrency and parallelism are the same thing; both mean 'fast'"

They are orthogonal, and neither is automatically fast. Concurrency is a *structuring* decision that lets independent tasks overlap; on a single core it makes a *waiting-bound* workload faster (overlap the waits) and a *compute-bound* workload **slightly slower** (you added context-switch overhead and got no extra compute). Parallelism needs multiple cores and only helps *compute-bound* work. Conflating them produces both classic mistakes: throwing threads at a CPU-bound Python job and getting *no speedup* (Lab M03-B — you needed parallelism, and the GIL denied it), and throwing processes at an I/O-bound job and paying heavy startup cost for a win that a handful of threads or one event loop would have gotten far cheaper.

#### Misconception 2 — "more threads = more speed"

Threads are not a throttle you turn up for performance. On a machine with `C` cores, at most `C` threads run truly in parallel; beyond that, threads *time-slice*, and each context switch costs (save/restore registers, cache disruption, scheduler overhead). For CPU-bound work, the sweet spot is roughly one thread per core — more threads means *more overhead for the same total compute*. Threads pay off past core-count only when they spend most of their time **blocked** (waiting on I/O), because a blocked thread costs nothing to have around. "Add threads until it's fast" is how you get a program that is slower *and* now has races.

### Lesson 2 — The shared-mutable-state hazard: `counter++` with a second actor

This is the beating heart of the module, and AIE-102 already loaded the gun. Recall from AIE-102 that `counter++` is not an instruction — it is a **read-modify-write** sequence. On x86-64 with the value in memory it is (conceptually):

```
    load   counter -> register   ; read  the current value into the CPU
    add    register, 1           ; modify the register
    store  register -> counter   ; write it back to memory
```

With **one** flow of control this is invisible — the three steps run back to back, nobody looks in between. The instant a **second thread shares that memory**, the three steps become a place where the other thread can be scheduled *in the middle*. Interleave two threads, A and B, both doing `counter++` when `counter == 41`:

```
    A: load counter -> regA        (regA = 41)
    B: load counter -> regB        (regB = 41)   ← B read BEFORE A stored
    A: add regA, 1                 (regA = 42)
    A: store regA -> counter       (counter = 42)
    B: add regB, 1                 (regB = 42)
    B: store regB -> counter       (counter = 42)   ← B clobbers A's 42 with 42
```

Two increments happened. The counter went up by **one**. A's update was *lost* — overwritten by B, who had read the stale value before A's store landed. This is a **lost update**, the canonical symptom of a **data race**: two threads access the same memory, at least one writes, and there is no ordering forcing one to happen-before the other. The result is not merely "wrong sometimes" — it is **undefined**: the C and C++ standards say a program with a data race has *no defined behavior at all*, and the compiler is licensed to assume races never happen (which is why it may cache the value in a register and skip your store entirely — see the misconception).

The corruption is **non-deterministic**: it depends on the exact interleaving the scheduler picked this run, which depends on timing you do not control. Run the program once, it might be right. Run it a million times, the deficit shows. This is what makes races the worst class of bug: **the test passes, the code ships, production loses money at 3 a.m.** and you cannot reproduce it on your laptop. The discipline of this module — **predict the race from the structure before you run it** — exists because you *cannot* rely on observing it.

#### Worked example — the race, made to confess

The compiler is allowed to hoist a plain `counter++` loop into a register and store once at the end, which *hides* the race (no per-iteration store to interleave). To keep the read-modify-write in memory every iteration — so the race is visible — mark the counter `volatile` (which forces the load and store each time) and **note carefully**: `volatile` does *not* make it safe. It forces the memory traffic that *exposes* the race; it provides no atomicity and no ordering. `volatile` is a promise about *when memory is touched*, never about *indivisibility*. (This confusion has its own misconception below.)

```c
volatile long counter = 0;                 // volatile: reload/store each time (exposes the race)
void *worker(void *_) {
    for (long i = 0; i < 2000000; i++)
        counter++;                          // load, add, store — three steps, no lock
    return NULL;
}
// two threads run worker(); expected 4,000,000
```

Measured, three runs on a 4-core machine:

```
expected=4000000 got=2066141 deficit=1933859
expected=4000000 got=2096881 deficit=1903119
expected=4000000 got=2158331 deficit=1841669
```

Nearly **half** the increments vanished, and a *different* number vanished each run. That non-repeating deficit is the signature of a data race — and you will predict its existence, then produce it, in Lab M03-A.

#### Misconception 3 — "`volatile` makes a variable thread-safe"

The single most common false fix in C. `volatile` tells the compiler "do not cache this in a register; touch memory every time" — it exists for memory-mapped hardware registers and signal handlers. It does **not** make `counter++` atomic (the load-add-store is still three separable steps), and it does **not** impose ordering between threads. A `volatile` counter incremented by two threads still loses updates — the worked example above *is* `volatile*. Thread safety for a plain integer comes from a **lock** (Lesson 3) or an **atomic type** (`_Atomic`/`atomic_fetch_add`), never from `volatile`. Reaching for `volatile` to fix a race is a reliable sign the read-modify-write decomposition has not landed.

#### Misconception 4 — "if the race is that rare, it's not a real bug"

The rarity is the danger, not the excuse. A race that manifests one time in ten million is a race that your unit tests will never catch, your staging environment will never show, and production will hit thousands of times a day at scale — precisely when the system is busiest and the stakes are highest, because more load means more concurrent access means more interleavings sampled. "It works on my machine" is the *expected* observation for a data race, not evidence against one. A defect whose probability rises with load and whose reproduction is non-deterministic is more dangerous than a deterministic crash, not less — the deterministic crash you fix on Tuesday; the race you debug for three weeks.

### Lesson 3 — Locks: making a sequence of steps indivisible

The race exists because *load-add-store* can be interrupted between its steps. The fix is to make the whole sequence **indivisible** — to declare a **critical section** that at most one thread may execute at a time. That is what a **mutex** (mutual-exclusion lock) does.

```c
pthread_mutex_lock(&m);     // acquire: if another thread holds it, BLOCK until it releases
counter++;                  // critical section: load-add-store, now uninterruptible by another locker
pthread_mutex_unlock(&m);   // release: let the next waiter in
```

`lock` is the guarantee: while thread A holds `m`, any other thread that calls `lock(&m)` **sleeps** until A calls `unlock`. So the three steps of `counter++` run start-to-finish with no other *locking* thread able to touch `counter` in between. The lost-update interleaving from Lesson 2 becomes impossible: B cannot read `counter` until A has stored and released.

What *is* a lock, underneath, so it isn't turtles all the way down? A mutex is itself built on a hardware **atomic** instruction — a single, indivisible read-modify-write the CPU guarantees (`lock cmpxchg` / test-and-set on x86, `LL/SC` on ARM). "Acquire the lock" is atomically "test whether the lock word is 0, and if so set it to 1, in one uninterruptible step." The hardware provides *one* indivisible operation; the mutex bootstraps *arbitrary-length* critical sections on top of it. This is the descent-and-re-ascent in miniature: the lock is not magic, it is a hardware atomic wearing a convenient API.

Three hard truths about locks, each a way to trade one problem for a worse one:

1. **A lock has a cost.** Acquiring and releasing is far cheaper than a system call but not free (tens of nanoseconds uncontended; far more under contention when threads actually block and the scheduler gets involved). Wrap *only* the critical section — the shared access — not the whole loop. Lock the `counter++`, not the million-iteration `for`. Over-locking serializes work that could have run concurrently and throws away the concurrency you paid threads to get.
2. **Locks can deadlock.** If thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1, both sleep forever. The standard prevention is a **lock ordering discipline**: every thread that needs multiple locks acquires them in the same global order. Deadlock is the price of mutual exclusion; ordering is the premium that avoids it.
3. **A lock only works if *every* accessor uses it.** The lock is a *convention*, not a fence around the memory. One thread that touches `counter` without acquiring `m` reintroduces the entire race — the lock protects the variable only insofar as all code agrees to take the lock first. There is nothing in the hardware tying `m` to `counter`; the association lives only in your discipline.

For the narrow case of a single integer, there is a lighter tool than a lock: a **hardware atomic type**. `_Atomic long` with `atomic_fetch_add(&c, 1)` performs the entire read-modify-write as *one* indivisible instruction — no separate lock word, no blocking, no deadlock risk. Atomics are faster and simpler *when your critical section is exactly one such operation*; the moment the critical section spans multiple variables or multiple steps (check-then-act — Lesson 4, Lab C), you are back to a lock, because only a lock can make a *sequence* indivisible.

#### Worked example — the two fixes, both correct

```c
long counter = 0;  pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;   // lock version
_Atomic long acounter = 0;                                          // atomic version

void *worker(void *_) {
    for (long i = 0; i < 2000000; i++) {
        pthread_mutex_lock(&m); counter++; pthread_mutex_unlock(&m);   // critical section
        atomic_fetch_add(&acounter, 1);                                // indivisible add
    }
    return NULL;
}
```

Measured with two threads:

```
mutex=4000000 atomic=4000000 expected=4000000
```

Both hit the exact expected total, every run, deterministically. The deficit is gone because no interleaving can now split the increment. In Lab M03-A you will predict *why each works in terms of the load-add-store*, then confirm the deficit collapses to zero.

#### Misconception 5 — "the lock protects the *variable*"

The lock protects a *critical section of code*, not a location in memory. Nothing in the machine associates `m` with `counter`; the mutex is a gate that at most one thread passes at a time, and it guards `counter` **only** because you, by convention, took the gate before every access. A single unlocked write anywhere reopens the race in full. The correct mental model is "this lock guards *this set of operations on this data, everywhere in the program*," which is why the guarded data and its lock are documented and reviewed together — the compiler will not check it for you.

#### Misconception 6 — "just lock everything to be safe"

Correctness by one giant lock ("the big lock") is correct and *slow*: it serializes the whole program, converting your multi-threaded design back into a single-threaded one that also pays lock overhead — the worst of both worlds. Real systems use **fine-grained** locking (a lock per independent piece of data) so unrelated work proceeds concurrently, which reintroduces the multi-lock deadlock risk and the ordering discipline that avoids it. The engineering is the *balance*: lock little enough to keep concurrency, order carefully enough to avoid deadlock, cover every accessor to keep correctness. "Lock everything" fails the first goal; "lock nothing" fails the third.

### Lesson 4 — The GIL: why Python parallelism is process-level

Now the callback pays off. From AIE-102: **CPython holds a Global Interpreter Lock — a single mutex around the interpreter — so that only one thread executes Python bytecode at any instant.** With Lesson 1's vocabulary you can now state precisely what that does and does not buy.

**What the GIL costs:** it makes CPython threads **concurrent but not parallel for Python-level compute.** Spin up four threads to run a CPU-bound Python loop on a 4-core machine and they do **not** run four-at-once — they take turns holding the GIL, one bytecode-executor at a time, time-sliced onto one effective core. You get *no speedup*, and slightly *worse* than single-threaded (context-switch and GIL hand-off overhead for zero extra compute). This is Misconception 1 and 2 made concrete in a specific runtime: threads are the wrong tool for CPU-bound Python, and no number of them helps.

**What the GIL does *not* cost:** it does not block **concurrency for I/O-bound work.** A thread that calls a blocking I/O function (a socket `read`, a `time.sleep`, a DB query) **releases the GIL while it waits** and reacquires it when the data is ready. So while thread A waits on a socket, thread B holds the GIL and runs. For M02's I/O-bound server — mostly waiting on sockets — Python threads overlap the waiting beautifully (Lesson 1's middle case) and give a real, large speedup. The GIL is a poor fit for CPU-bound work and a *fine* fit for the waiting-bound work most services actually do.

**The consequence — parallelism in Python is process-level.** To use multiple cores for CPU-bound Python you run multiple **processes** (the `multiprocessing` module, or multiple OS processes). Each process has its **own interpreter and its own GIL** (Lesson 1: processes have private address spaces), so N processes genuinely run N Python bytecode streams on N cores. The cost is exactly Lesson 2's trade inverted: processes do not share memory, so you cannot corrupt shared state by accident — *and* you cannot share it for free; passing data between processes means **serializing it** (pickling) and copying it through a pipe, which for large data can cost more than the parallelism saves.

```
Python, CPU-bound (measured, 4 workers, 4 cores):
    serial   = 0.54 s        threads = 0.59 s   (NO speedup — GIL serializes; overhead makes it worse)
    processes= 0.32 s        (real parallelism — separate interpreters, separate GILs, separate cores)

Python, I/O-bound (measured, 4 tasks × 200 ms wait):
    serial   = 0.80 s        threads = 0.20 s   (~4× — GIL released during the waits; concurrency wins)
```

The decision rule falls straight out: **CPU-bound Python → processes** (or drop to C/NumPy that releases the GIL); **I/O-bound Python → threads or async** (concurrency is all you need, and threads are cheap). You will produce this exact table yourself in Lab M03-B and predict each cell before running it.

One more thing the GIL does **not** do, and it is the trap in Lab M03-C: **the GIL does not make your *program logic* race-free.** The GIL guarantees each *bytecode* is atomic, but `counter += 1` is *several* bytecodes (`LOAD`, `ADD`, `STORE`), and the interpreter can switch threads between them — so the Lesson 2 lost-update happens in pure Python too. Worse, any **check-then-act** (`if balance >= 10: balance -= 10`) spans many bytecodes with a decision in the middle, and two threads can both pass the check before either acts. The GIL protects the *interpreter's* internal state, not *your* invariants. Application-level races need application-level locks (`threading.Lock`), GIL or no GIL.

#### Worked example — the check-then-act race the GIL doesn't stop

```python
balance = 100
def withdraw():                     # 20 threads run this
    global balance
    for _ in range(50):
        if balance >= 10:           # CHECK  (LOAD, COMPARE — several bytecodes)
            time.sleep(0)           # force a thread switch between check and act
            balance -= 10           # ACT    (LOAD, SUB, STORE — the check is now stale)
```

Measured, three runs:

```
no-lock final balance: -30
no-lock final balance: -40
no-lock final balance: -30
```

The balance went **negative** — every thread checked `balance >= 10` while it was still positive, then all of them decremented. The GIL was held the entire time; it made each bytecode atomic and did nothing for the invariant "balance never goes below zero," because that invariant spans a *check* and an *act* the scheduler split apart. The fix is a `threading.Lock` around *both* the check and the act, so the decision and the action are one indivisible critical section.

#### Misconception 7 — "the GIL makes Python thread-safe, so I don't need locks"

The most dangerous half-truth in Python concurrency. The GIL makes each *bytecode instruction* atomic — it does **not** make *your operations* atomic. `x += 1` is at least three bytecodes; `if x: use(x)` is a check and an act; `d[k] = d[k] + 1` is a read and a write. Any of these can be split by a thread switch, and the classic lost-update and check-then-act races follow (Lab M03-C reproduces them in pure Python). "The GIL protects me" confuses *the interpreter cannot corrupt its own reference counts* with *my bank balance cannot go negative* — only the first is true. You need `threading.Lock` for any multi-step invariant, exactly as you need a mutex in C.

#### Misconception 8 — "the GIL is why Python is slow / removing it makes threads faster for everything"

The GIL affects *parallelism*, not single-threaded speed, and only for *CPU-bound* code. Single-threaded Python is exactly as fast with the GIL as it would be without; I/O-bound threaded Python already scales fine *because* blocking calls release the GIL. Removing the GIL (the ongoing "free-threaded"/no-GIL CPython work) helps *only* CPU-bound multi-threaded workloads — and historically cost single-threaded performance and required every C extension to add its own locking (the safety the GIL provided for free). The GIL is a *design trade*: it buys simple, fast single-threaded execution and safe reference counting at the price of multi-core CPU parallelism for pure-Python threads. "Just remove it" is not free; it moves the locking burden onto everyone.

**Solution** (`race.c`):

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <stdatomic.h>

#define ITER 2000000

volatile long counter = 0;
long safe = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
_Atomic long atomic_counter = 0;

void *worker(void *_) {
    for (long i = 0; i < ITER; i++) {
        counter++;                                  // racy: three steps, unguarded

        pthread_mutex_lock(&m);                     // critical section: indivisible vs other lockers
        safe++;
        pthread_mutex_unlock(&m);

        atomic_fetch_add(&atomic_counter, 1);       // one indivisible read-modify-write
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    long expected = 2L * ITER;
    printf("racy   : expected=%ld got=%ld deficit=%ld\n", expected, counter, expected - counter);
    printf("mutex  : expected=%ld got=%ld\n", expected, safe);
    printf("atomic : expected=%ld got=%ld\n", expected, (long)atomic_counter);
    return 0;
}
```

```bash

```

### Lab M03-C — The race the GIL does not save you from

**Goal:** reproduce a **check-then-act** race in *pure Python* — proving Misconception 7 false at your own keyboard — then fix it with a `threading.Lock` and predict why the lock, not the GIL, is what restores the invariant.

#### Predict (on paper, before running)

A shared `balance = 100`. Twenty threads each try to withdraw 10, fifty times, guarding with `if balance >= 10: balance -= 10`. Write down, with a mechanism for each:

**Solution** (`bank.py`) — the safe path wraps the whole check-then-act:

```python
import threading
import time

THREADS      = 20
WITHDRAWALS  = 50
AMOUNT       = 10
START        = 100

balance_unsafe = START

def withdraw_unsafe():
    global balance_unsafe
    for _ in range(WITHDRAWALS):
        if balance_unsafe >= AMOUNT:
            time.sleep(0)
            balance_unsafe -= AMOUNT

balance_safe = START
lock = threading.Lock()

def withdraw_safe():
    global balance_safe
    for _ in range(WITHDRAWALS):
        with lock:                       # critical section: check AND act are indivisible
            if balance_safe >= AMOUNT:
                time.sleep(0)            # even yielding here is safe now — we hold the lock
                balance_safe -= AMOUNT

def run(target):
    ts = [threading.Thread(target=target) for _ in range(THREADS)]
    for t in ts: t.start()
    for t in ts: t.join()

if __name__ == "__main__":
    run(withdraw_unsafe)
    run(withdraw_safe)
    print(f"unsafe final balance: {balance_unsafe}   (invariant: should never be < 0)")
    print(f"safe   final balance: {balance_safe}")
```

## Assessment

**Design constraint: gaming-resistance.** A learner cannot pass by pasting a working locked program, because the score lives in the **Predict artifacts** and the **mechanistic reasoning**, not in "it produced the right number." A correct program has *no diagnostic value* here — a program with a lock always prints the right total whether or not the author understands *why*, and a racy program often prints the right total *by luck*. So the artifact graded is the judgment trail: predict the race from the load-add-store, locate the exact interleaving, name the tool that closes it and *why*, and prove the fix removed the specific mechanism. A right total with no predicted mechanism caps low; a predicted mechanism with an off number scores full.

### Module exam — unseen scenario, predict before running

The learner is handed **one unseen scenario** drawn at random from a bank, each containing exactly one concurrency defect or misdiagnosis, and must produce a four-part artifact:

**(a) Predict** the behavior *before running* — in load-add-store / interleaving / lock / GIL terms.
**(b) Reproduce** the defect — produce the non-deterministic wrong result (force the interleaving with a `sleep(0)`/`usleep`, raise the iteration count or thread count, or lower the switch interval) and *locate the exact steps that interleaved*.
**(c) Fix** the defect or **correct the misdiagnosis** — with the *minimal correct tool* (atomic for one op, lock for a multi-step invariant, process for CPU parallelism) and say why a cheaper/other tool would not suffice.

## Elle pacing notes (signals for the runtime)

- **Wall — the learner cannot see the race because `-O2` optimized it away.** They write the racy counter, run it, get exactly 4,000,000, and conclude "there's no race / threads are fine." The compiler hoisted the `volatile`-less loop into a single register add. **Reroute:** this is a *teaching* moment, not a bug — have them compile once with `-O2` (no race visible) and once with `-O0` plus `volatile` (deficit appears), and *predict which will show it and why*. The disappearing race under optimization is itself the lesson that a race is a property of the *program's memory semantics*, not of any one run. Do not let "it printed the right number" stand as evidence of safety — that is Misconception 4, live.
- **Wall — `volatile` is grabbed as the fix and *feels* right.** The learner reads "volatile means the value can change under you" and concludes it handles concurrency. It is the single most common false fix. **Reroute:** point at the worked example — the racy counter *is* `volatile` and still loses half its updates. Force the decomposition: "`volatile` guarantees the load and the store *happen in memory*; does it make the load-add-store *one step*? No. So where can the other thread still land?" The word "atomic" is the missing concept; `volatile` is about *visibility/timing*, atomicity is a different axis. This is `struggle-productive` — let them try `volatile`, measure it fail, then reach for the lock.
- **Signal — a learner who predicts the deficit will be *different every run* before running has understood non-determinism; a learner who expects a *fixed* wrong number has not.** The expectation of a stable deficit means they are modeling the race as a deterministic off-by-something rather than a scheduler-dependent interleaving. Probe: "if you run it twice, same wrong number or different?" The "different" answer *is* the understanding; it also motivates why the test asserts structure, not a value.
- **Wall — CPU-bound threading "should" be faster and the flat timing reads as a broken benchmark.** The learner sees `threading` no faster (or slower) than serial and assumes their timing code is wrong. **Reroute:** it is *correct and it is the whole point*. Have them predict the number *before* running (Lab B Predict), so the flat result confirms a prediction instead of contradicting an expectation. Then immediately run `multiprocessing` and watch it speed up — the contrast (same work, threads flat, processes fast) is what makes "the GIL blocks CPU-thread parallelism" land as a measured fact, not a claim. ## Three-tier reading

- **Tier 1 — material ground (verifiable facts).** `counter++` is a read-modify-write — load, add, store — and two threads sharing that memory can interleave those steps so an update is lost; the deficit is real, large, and *non-deterministic*, reproducible on demand (Lab M03-A). `volatile` forces the memory traffic that exposes the race but provides no atomicity and no thread-safety (Misconception 3, demonstrated). A mutex makes a *sequence* of steps indivisible by convention among all accessors; a hardware atomic makes *one* read-modify-write indivisible by the CPU; a lock is itself built on a hardware atomic (Lesson 3). CPython's GIL lets only one thread execute bytecode at a time, so Python threads give *no* CPU-parallel speedup (measured flat in Lab M03-B) but *do* overlap I/O because blocking calls release the GIL (measured ~N× in Lab M03-B) — which is why CPU-bound Python scales with *processes*, each carrying its own GIL. The GIL guarantees each bytecode is atomic and nothing more: a pure-Python check-then-act still races and can drive a bank balance negative with the GIL held the entire time (Lab M03-C, reproducible). None of this is opinion; it is measured behavior you produced.

- **Tier 2 — what the field suppresses.** The industry sells concurrency as a *performance knob* — "make it multi-threaded," "add workers," "we scaled it" — and suppresses that concurrency is first a *correctness* problem and only sometimes a speed one: the same shared state that lets threads cooperate is the state they corrupt, and the corruption is *invisible in exactly the conditions you test under* (low load, one run) and *manifest in exactly the conditions you ship into* (high load, millions of runs). "It passed the tests" is, for a data race, no evidence at all — a fact rarely said because it undermines the test suite as proof. The other suppressed truth is directional: the reason a race is dangerous is that it *scales with success*. A service nobody uses never hits the interleaving; a service under real load samples millions of interleavings a day, so **the bug's probability rises precisely with the number of users you are serving** — the corruption is a function of scale, and scale is what the whole course celebrates. And the GIL, defended and attacked as a *performance* villain, is more honestly a *safety* trade: it exists so that CPython's reference-counting memory model is thread-safe without the interpreter's C code locking on every object — remove it and that safety burden lands on every extension author. "Just remove the GIL for speed" suppresses who pays for the safety it currently provides for free.

- **Tier 3 — sit with this (a question you cannot unknow).** You have now made a program lose half its work and never crash, and violate its own most basic rule — never go below zero — with every safety mechanism the language advertises still switched on. The lost update had a face: in the bank lab it was money that vanished, and in a real system it is a seat sold twice, a vote counted once, a medication dose double-logged, a balance that goes negative on a stranger's account you will never see. The race is not rare because it is unlikely; it is rare because *your* load is low — and it becomes common at exactly the moment your service succeeds, i.e. at exactly the moment the most strangers are trusting it with the most consequential data. The scale you are being trained to build for is the scale at which these interleavings stop being one-in-a-million and start being hourly. So: when the corruption is invisible under every condition you can afford to test, manifests only under the load that means you succeeded, and falls on people who are — by the very design that let you scale — reduced to a row and an integer you never look at individually, **what standard of proof do you owe them that "it passed the tests" can never meet, and who is accountable for the interleaving nobody chose and everybody shipped?**
