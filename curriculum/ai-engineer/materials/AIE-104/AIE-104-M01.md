### Lesson 1 — The shell is a program that runs programs

#### Teaching text

When you type `ls -l` and press Enter, it is tempting to think "the computer ran `ls`." One layer down, something more specific happened: **the shell** — itself just a program, `/bin/bash`, a process like any other — read your line, split it into words, decided `ls` was an *external* program, found the file `/usr/bin/ls`, **forked a copy of itself**, had that copy **replace its own program image with `ls`** (`exec`), and then **waited** for it to finish. The shell is a read-eval-print loop whose "eval" is *launch a process and wait for it*.

Two kinds of command exist, and the difference is load-bearing:

- **External commands** are files on disk. `ls`, `grep`, `python3`, `gcc` — each is an executable the shell finds by searching the directories in `$PATH`, left to right, and launches as a new process.
- **Builtins** are *inside* the shell; no new process is created. `cd`, `export`, `exit` **must** be builtins — `cd` has to change the shell's *own* directory, and a forked child changing *its* directory then exiting would leave the parent shell exactly where it was.

You can ask which is which:

```bash
type cd        # cd is a shell builtin
type ls        # ls is /usr/bin/ls   (hashed after first use)
type type      # type is a shell builtin
which python3  # /usr/bin/python3    (searches PATH, externals only)
```

`PATH` is why `python3` works but `./myscript` needs the `./`: the shell searches `PATH` for bare names, and `.` (the current directory) is deliberately **not** on it, so that a malicious `ls` dropped in a directory you `cd` into does not shadow the real one. That absence is a security decision you inherited.

Every command returns an **exit code** — an 8-bit integer, `0` for success, non-zero for failure — and the shell stashes it in `$?`. This is not decoration; it is the return value of the whole process, and it is what makes shell *composition* possible (`&&`, `||`, `if`, pipelines all read it).

```bash
ls /etc >/dev/null; echo $?     # 0   — succeeded
ls /nonesuch 2>/dev/null; echo $?   # 2   — ls's "does not exist" code
grep zzz /etc/hostname; echo $?     # 1   — grep: "ran fine, matched nothing"
```

Note that last one: `grep` returning `1` is **not an error** — it is grep telling you *no match*, which is different from grep *failing* (code `2`, e.g. unreadable file). A shell programmer who treats every non-zero as "broken" will write scripts that misfire on the most normal outcome there is.

#### Worked example — decode a command line before running it

Take `sort names.txt | uniq -c | sort -rn | head -3`. Before running, narrate what the shell builds: it forks **four** processes, wires the stdout of each into the stdin of the next (Lesson 3), and the pipeline's exit code is that of the *last* command (`head`) unless you ask otherwise. Read right to left for *intent* ("top 3, by descending count, of unique lines") but left to right for *dataflow*. The judgment being trained: you can state a pipeline's output and its exit behavior on paper, before the terminal confirms it.

```bash
printf 'a\nb\na\nc\na\nb\n' > names.txt
sort names.txt | uniq -c | sort -rn | head -3
#       3 a
#       2 b
#       1 c
echo $?     # 0  — head's exit code, not sort's
```

#### Misconceptions to surface (name them out loud)

- **"The shell runs the command."** More precisely: the shell *forks and execs* the command as a separate process, then waits. Surface it by having the learner run `sleep 30 &` and then `ps --ppid $$` — the sleep is a *child process* with the shell as its parent, visible and separate.
- **"`cd` is a program like `ls`."** No — `cd` must be a builtin, because a child process cannot change its parent's directory. Surface it with `type cd` vs `type ls`, then ask why `cd` *cannot* work as an external.
- **"Non-zero exit means the command is broken."** No — `grep` returns `1` for "no match found," a normal, expected result. Surface it with `echo hi | grep zzz; echo $?` → `1`, and contrast with a real error (`grep zzz /root/shadow 2>/dev/null; echo $?` → `2`).
- **"`$PATH` includes the current directory."** On Linux it deliberately does not, which is why you type `./script`. Surface it with `echo $PATH` — no `.` — and name the attack it prevents.

### Lesson 2 — The process tree: fork, exec, wait

#### Teaching text

Every process on a Unix system except the very first has exactly one parent, and the whole set forms a **tree** rooted at PID 1 (`init`/`systemd`). A process is created by exactly one mechanism: **`fork()`**, which makes a near-identical copy of the calling process — same code, same memory (copy-on-write), same open file descriptors — differing in exactly one observable: `fork()` returns the child's PID to the parent and `0` to the child. That single divergent return value is how one call becomes two processes that then run different code.

`fork()` alone would only ever give you copies of the shell. The other half is **`exec()`**, which does *not* create a process — it *replaces the current process's program image* with a different executable, keeping the same PID and open file descriptors. The shell's core trick is the pair: **fork, then in the child, exec.** The child briefly is a clone of the shell, then becomes `ls`. The parent shell stays itself and calls **`wait()`** to collect the child's exit status.

```
shell (pid 100)
   │  fork()
   ├────────────► child (pid 101)  ← a copy of the shell
   │                   │ execvp("ls", ...)
   │                   │ now running /usr/bin/ls, still pid 101
   │  waitpid(101)     │ exit(0)
   └──────◄───────────┘   status collected; pid 101 released
```

Two things go wrong when the timing is off, and both have names:

- **Orphan.** The parent exits *before* the child. The child is not killed — it is **re-parented to PID 1**, which will `wait()` for it. Orphans are normal and harmless (this is exactly how daemons "detach").
- **Zombie (`<defunct>`).** The child exits *before* the parent `wait()`s for it. The child's memory is gone, but a scrap of it — its **exit status** — must be kept until someone reads it, so the kernel keeps a husk in the process table. A zombie holds no memory and no CPU; it holds a PID and a status nobody has collected. A parent that forks in a loop and never `wait()`s leaks PIDs until the table fills. The fix is always the same: **`wait()` for your children.**

The kernel *tells* the parent a child has died by sending it the signal **`SIGCHLD`** (Lesson 4 makes signals concrete) — which is how a parent knows there is a status waiting to be reaped without polling.

You can see the tree and the states directly:

```bash
ps -o pid,ppid,stat,comm       # STAT column: R run, S sleep, Z zombie, T stopped
pstree -p                      # the whole tree, PIDs shown
cat /proc/$$/status            # the shell's own kernel-visible state; $$ is this shell's PID
ls /proc/$$/fd                 # the shell's open file descriptors, as symlinks
```

`/proc` is the kernel's process tree exposed as files — every process is a directory `/proc/<pid>/`. This is the descent's payoff: the process is not an abstraction you trust, it is a directory you can read.

#### Worked example — one fork, decoded

```c
pid_t pid = fork();
if (pid == 0) {
    /* child: fork returned 0 here */
    printf("child, my pid=%d, my parent=%d\n", getpid(), getppid());
} else {
    /* parent: fork returned the child's pid here */
    printf("parent, my pid=%d, my child=%d\n", getpid(), pid);
    waitpid(pid, NULL, 0);      /* reap, so the child never becomes a zombie */
}
```

The same code after `fork()` runs in *two* processes. The `if` does not choose a branch "randomly" — the parent and child each take a *different* branch because `fork()` handed each a different return value. This is the single most important thing to see about `fork`: one line of source, two processes, distinguished only by a return value. Predict the two lines of output and their PID relationship *before* compiling — that prediction is Lab M01-B.

#### Misconceptions to surface

- **"`fork()` starts a new program."** No — `fork()` *copies the running one*; `exec()` starts a new program *in place*. Surface it with a `fork()` that has *no* `exec` — you get two copies of the same C program, proven by both printing from the same `printf`.
- **"A zombie is using memory / is dangerous / must be killed."** A zombie holds no memory and no CPU — only a PID and an unread exit status; you cannot `kill` it (it is already dead). Surface it by watching `ps` show `Z`/`<defunct>` while the parent sleeps, then vanish the instant the parent `wait()`s or exits (init reaps it).
- **"An orphaned process dies with its parent."** No — it is re-parented to PID 1 and keeps running. Surface it by backgrounding a `sleep 100`, killing its parent shell, and finding the sleep alive with `PPID 1`.
- **"The child shares memory with the parent, so writes are seen by both."** No — `fork` gives copy-on-write *copies*; a variable the child changes does not change in the parent. (This is precisely why AIE-102's threads-share-memory / processes-don't distinction matters here — the child is a *process*, not a thread.)

### Lesson 3 — File descriptors and the pipe

#### Teaching text

A process does not read from "the keyboard" or write to "the screen." It reads and writes **file descriptors** — small non-negative integers the kernel hands out, each an index into that process's table of open things. Three are open by convention when a process starts:

- **0 — standard input (`stdin`)**
- **1 — standard output (`stdout`)**
- **2 — standard error (`stderr`)**

A file descriptor is deliberately *not* typed to a device. The same integer `1` might point at your terminal, a file, or the write-end of a pipe — the program writing to it neither knows nor cares. This uniformity is the whole reason redirection and pipes work: the *shell* rewires the descriptors *before* `exec`, and the program, unchanged, writes to fd 1 as always.

```bash
echo hi > out.txt        # shell points fd 1 at out.txt before exec'ing echo
echo hi 2> err.txt       # points fd 2 (stderr) at err.txt; stdout still the terminal
python3 app.py > log 2>&1  # fd 1 -> log, then fd 2 -> "wherever 1 points" = log too
sort < names.txt         # shell points fd 0 at names.txt; sort reads "stdin" as usual
```

Order matters in `> log 2>&1`: `2>&1` means "make fd 2 a copy of fd 1 *as it is now*." Reverse them to `2>&1 > log` and stderr is duplicated onto the terminal *first*, then stdout alone is redirected to the file — a classic bug you can now predict instead of discover.

A **pipe** (`a | b`) is a kernel buffer with two ends. The shell creates it, points `a`'s fd 1 at the write-end and `b`'s fd 0 at the read-end, then `exec`s both — they run **concurrently**, `b` consuming what `a` produces. Data flows without ever touching disk. This is composition at the OS level: small tools, each reading fd 0 and writing fd 1, chained into a program the shell assembles on the fly.

Two consequences most people meet only as bugs:

- **`SIGPIPE`.** If the reader closes early — `yes | head -1` — the writer (`yes`) tries to write into a pipe with no reader, and the kernel kills it with **`SIGPIPE`** (signal 13). This is a *feature*: it is how `head` stops an infinite producer. The producer dies by signal, but the pipeline reports `head`'s success.
- **Pipeline exit code and `pipefail`.** By default a pipeline's exit code is **only the last command's**. So `grep pattern huge.log | head` reports `head`'s success even if `grep` couldn't open the file. `set -o pipefail` changes this: the pipeline fails if *any* stage fails. This is the difference between a script that quietly processes nothing and one that tells you the input was missing.

```bash
false | true; echo $?                 # 0   — only 'true' (last) is seen
set -o pipefail; false | true; echo $?  # 1   — now the failing 'false' is reported
```

#### Worked example — predict, then confirm, a redirection order bug

```bash
# Intended: send both stdout and stderr to log.txt
prog 2>&1 > log.txt      # BUG: stderr goes to the *terminal*, stdout to the file
prog > log.txt 2>&1      # CORRECT: stdout to file, then stderr follows to the same file
```

Predict for each line *where stderr lands* before testing with a program that writes to both streams (`sh -c 'echo out; echo err >&2'`). The rule you extract: `2>&1` copies fd 1's *current* target, so it must come *after* the redirection of fd 1. This is Lab M01-A territory — a behavior you assert on paper and the shell adjudicates.

#### Misconceptions to surface

- **"`>` and `>>` and `|` are the same kind of thing."** `>`/`>>` connect a descriptor to a *file*; `|` connects two *processes* through a kernel buffer with no file at all. Surface it by showing `a | b` runs `a` and `b` *simultaneously* (put `sleep` in each and watch), whereas `a > f; b < f` runs them in sequence.
- **"`2>&1` redirects stderr to stdout's file."** It copies fd 1's *current destination* into fd 2 — order-sensitive. Surface it with the `2>&1 > log` vs `> log 2>&1` pair above.
- **"A pipeline succeeds if it produced output."** No — its exit code is the last stage's by default; earlier failures are invisible without `pipefail`. Surface it with `false | cat; echo $?` → `0`.
- **"`yes | head` errors because `yes` was killed."** The `SIGPIPE` death of `yes` is *how the pipeline is meant to stop*; the pipeline reports `head`'s success. Surface it with `yes | head -1; echo $?` → `0`.

### Lesson 4 — Permissions and signals

#### Teaching text

**Permissions.** Every file carries an owner, a group, and nine permission bits — read/write/execute for **user**, **group**, **other** — which the kernel checks on every open. `ls -l` shows them as `-rw-r-----`; the same bits are the octal `640` (`rw-`=6, `r--`=4, `---`=0). "Execute" on a *file* means "may run as a program"; on a *directory* it means "may traverse into it" — a directory you can read but not execute lets you list names but not `cd` in or `stat` the entries.

```bash
touch data; chmod 640 data; stat -c '%a %A %U:%G' data   # 640 -rw-r----- you:you
chmod u+x,g-r data; ls -l data                            # -rwx------
umask                                                     # 0022 — bits masked OFF at create time
```

`umask 0022` is why new files are born `644` not `666`: the mask *removes* write-for-group-and-other by default. Permissions are the OS's answer to "who may touch this" — and, as the course ethics thread will press, a service holding strangers' data enforces exactly these nine bits and nothing about whether it *should*.

**Signals.** A signal is the kernel's (or another process's) way of interrupting a process with a one-integer message: "your child died" (`SIGCHLD`), "the user pressed Ctrl-C" (`SIGINT`), "please terminate" (`SIGTERM`), "you wrote to a dead pipe" (`SIGPIPE`), "die now, no argument" (`SIGKILL`). A running process can, for most signals, **install a handler** — a function the kernel calls when the signal arrives — or **ignore** it, or let the **default** action run (usually: terminate).

The two that matter most in operations:

- **`SIGTERM` (15)** — "please shut down." *Catchable.* This is what `kill <pid>` sends, what `docker stop` sends, what an orchestrator sends first. A well-behaved service catches it and drains: finish the in-flight request, flush buffers, close sockets, *then* exit. This is **graceful shutdown**.
- **`SIGKILL` (9)** — "terminate immediately." **Uncatchable, unignorable, unblockable.** The kernel does not deliver it to your code; it just removes the process. `SIGSTOP` (pause) is the same — you cannot handle it. This asymmetry is deliberate: there must exist a way to end a process that the process *cannot* refuse. Trying to handle it is an error:

```python
import signal
signal.signal(signal.SIGKILL, signal.SIG_IGN)
# OSError: [Errno 22] Invalid argument   — the kernel refuses
```

When a process is killed *by* a signal, its exit status is **128 + signal number** — so a process terminated by `SIGTERM` (15) exits `143`, by `SIGKILL` (9) exits `137`, by `SIGINT` (2) exits `130`. Seeing `137` in a container's logs and reading it as "OOM-killer sent SIGKILL" is a fluency this lesson buys you.

```bash
sleep 100 & kill -TERM $!; wait $!; echo $?   # 143  = 128 + 15
```

The operational pattern behind `docker stop`, `kubectl delete`, and every init system: send **`SIGTERM`**, wait a grace period, then send **`SIGKILL`** if the process hasn't exited. Your job as the service author is to make the first signal enough — to exit cleanly before the kill. A double-signal pattern (first `SIGTERM` drains, a second forces exit) gives an impatient operator an out without waiting for the `SIGKILL`.

#### Worked example — a service that shuts down gracefully

```python
import signal, sys, time, os

running = True
def on_term(signum, frame):
    global running
    print(f"[{os.getpid()}] {signal.Signals(signum).name}: draining", flush=True)
    running = False                       # tell the main loop to stop; do NOT exit here mid-work

signal.signal(signal.SIGTERM, on_term)
signal.signal(signal.SIGINT, on_term)     # Ctrl-C handled the same way
while running:
    time.sleep(0.05)                      # stand-in for "serve one request"
print(f"[{os.getpid()}] drained cleanly; bye", flush=True)
sys.exit(0)
```

The handler does the *minimum*: flip a flag. The main loop notices and unwinds on its own terms. Handlers that do heavy work are a bug — a signal can arrive at *any* instruction, including inside `malloc`, so the safe move is to record "a signal happened" and act in the normal flow. Predict: what exit code does this print on `kill -TERM`? (`0` — it caught the signal and exited cleanly, *not* `143`; catching the signal is exactly what changes the exit code.)

#### Misconceptions to surface

- **"`kill` means kill."** `kill` *sends a signal* — by default `SIGTERM`, a polite request the process may catch and act on. Surface it with the graceful service: `kill <pid>` makes it drain and exit `0`, not die.
- **"`kill -9` is the normal way to stop things."** `SIGKILL` gives the process no chance to flush or close — corrupting half-written files and leaking locks. It is the *last* resort, after `SIGTERM` was ignored. Surface it by killing the graceful service with `-9` and showing "drained cleanly" never prints.
- **"A signal handler can safely do anything."** No — it can be invoked between any two machine instructions; do minimal, reentrant work (set a flag) and act in the main loop. Surface it by naming the hazard: a handler that calls `print`/`malloc` can deadlock if the signal arrived inside `malloc`.
- **"Exit code 137 is a mysterious crash."** It is `128 + 9` — the process was `SIGKILL`ed (often the OOM killer). Surface it with `sleep 100 & kill -9 $!; wait $!; echo $?` → `137`.

### Lab M01-B — Build the shell's core: fork, exec, wait, and a zombie *(C)*

**Goal:** write, in C, the exact fork/exec/wait triad the shell uses — then deliberately create a zombie and watch it in `ps`, so the process tree stops being a diagram and becomes something you caused.

#### Predict (on paper, before compiling)

1. In the `fork()` below, after the call there are two processes. What does `fork()` return **in the parent**? **In the child**? Which `if` branch does each take?

#include <unistd.h>
#include <sys/wait.h>
#include <sys/types.h>

int main(int argc, char *argv[]) {
    if (argc < 2) { fprintf(stderr, "usage: %s CMD [ARGS...]\n", argv[0]); return 2; }

    printf("[parent] pid=%d about to fork\n", getpid());
    fflush(stdout);

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }

        printf("[child]  pid=%d ppid=%d exec %s\n", getpid(), getppid(), argv[1]);

Reference solution (`service.py`):

```python
#!/usr/bin/env python3
"""A toy service that drains on the first SIGTERM/SIGINT and hard-exits on the second.
SIGKILL is not (and cannot be) handled — that is the point of Lab step 2."""
import signal, sys, time, os

class Service:
    def __init__(self):
        self.running = True
        self.draining = False
        self.ticks = 0

    def request_stop(self, signum, frame):
        name = signal.Signals(signum).name
        if not self.draining:
            print(f"[{os.getpid()}] {name}: draining, finishing current work", flush=True)
            self.draining = True
            self.running = False        # ask the main loop to unwind; do NOT exit here
        else:
            print(f"[{os.getpid()}] {name} again: hard exit", flush=True)
            sys.exit(1)

    def run(self):
        while self.running:
            self.ticks += 1
            time.sleep(0.05)
        print(f"[{os.getpid()}] drained after {self.ticks} ticks; bye", flush=True)
        sys.exit(0)

if __name__ == "__main__":
    svc = Service()
    signal.signal(signal.SIGTERM, svc.request_stop)
    signal.signal(signal.SIGINT, svc.request_stop)   # Ctrl-C, same path
    print(f"[{os.getpid()}] up (try: kill -TERM {os.getpid()})", flush=True)
    svc.run()
```

## Three-tier reading

Specific to this module's subject — *the OS as the authority over your running program: who may touch a file, and who may end a process* — not boilerplate. This is Tier 1 of the course ethics thread (the systems that scale operate without knowing their users individually) meeting its most concrete substrate.

- **Tier 1 — material ground (verifiable, reproducible today).** Control over a running program is not metaphor; it is mechanism you can exercise on your own machine. A file's nine permission bits (`chmod 640`, verifiable with `stat -c '%a'`) are the *entire* enforcement the kernel performs on "who may read this" — the check happens on every `open`, and it knows nothing about *who you are*, only your numeric UID and group. A process can catch `SIGTERM` and choose to drain (exit `0`), but `SIGKILL` (9) is delivered by the kernel to no handler at all — the process exits `137` (`128 + 9`) whether or not it consented, provably: `signal.signal(SIGKILL, ...)` raises `OSError: [Errno 22]`. The asymmetry is by design: there must exist a command to end a process that the process cannot refuse.

- **Tier 2 — what the field suppresses.** "The OS just manages resources fairly" and "permissions keep data safe" both hide the same thing: permission bits encode *authority*, not *ethics*, and the two are routinely confused. A file readable by `group=analytics` is readable by *every* member of that group and by `root` unconditionally — the bits say who *may*, never who *should*, and `root` is exempt from all of them. The booster selling "least privilege" and "defense in depth" cannot dwell on the fact that the model grants a superuser total access by construction and that "the service holds the data securely" means "securely from everyone except the dozen people with `sudo` and the cloud provider under them." The privacy critic who says "just encrypt everything" cannot admit that the process *decrypting* it to serve a request runs under exactly these bits, killable and inspectable by whoever administers the box. The permission model is real security *and* it is a map of who already has power over the data — those are the same nine bits, read two ways.

- **Tier 3 — sit with this (a question you can't unknow).** You will build a service in this course that holds strangers' data. The kernel will let you `SIGKILL` it mid-write, and let anyone with `root` read every byte it has decrypted to serve a request — and *none* of that is a bug; it is the operating system working exactly as designed, because the system that scales is precisely the one that operates without knowing its users individually. So when the only thing standing between a stranger's data and everyone with a shell on the box is a permission bit *you* set and a shutdown *you* chose to make graceful — and the OS enforces neither your care nor your carelessness, only your bits — at what point does "the platform handles security" stop being true, and become the name for a decision you quietly made on a stranger's behalf?
