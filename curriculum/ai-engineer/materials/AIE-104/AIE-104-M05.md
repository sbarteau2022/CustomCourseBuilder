## Lessons

### Lesson 1 — Predicting the SLO: capacity is a number you can compute before you load-test

#### Teaching text

An SLO ("service-level objective" — e.g. "p95 latency ≤ 100 ms at 200 requests/second") is not a wish. It is a claim about a system whose capacity you can calculate **before running it**, from two numbers you already know how to produce: how many independent workers can serve a request at once, and how long one worker takes to serve one request.

If a service runs **W** synchronous workers — each a separate OS **process**, each handling exactly one request at a time — and a single request takes **S** seconds of that process's time end to end, then the service's maximum sustained throughput is:

```
capacity (requests/sec)  ≈  W / S
```

This is Little's Law wearing work clothes. Little's Law states `L = λ·T` — the average number of requests *in the system* (being served or waiting) equals the arrival rate times the average time each spends in the system. Point a **closed-loop load generator** at the service — `C` client threads, each holding at most one request in flight, immediately sending the next the moment a response returns — and `L = C` by construction: there are always exactly `C` requests in the system. Rearranged, `T = C / λ`. Two regimes fall straight out:

- **`C ≤ W`** — every request finds a free worker immediately. No queueing. `T ≈ S` (just the service time), and throughput `λ ≈ C / S`, rising linearly with concurrency.
- **`C > W`** — more requests are in flight than there are workers to serve them. The excess sits in a queue (mechanically: the OS's `listen()` backlog from M02, or the WSGI server's internal accept queue — the same queueing structure M02 Lesson 1 introduced, now with real requests sitting in it under load). Throughput **plateaus** at `W/S` — you cannot serve faster than `W` workers at `S` seconds each, no matter how many clients are waiting — while `T` grows to `C / (W/S)`, i.e. **latency rises linearly with excess concurrency** even though nothing is broken.

This is the single most important shape in the module: **throughput is a step function that plateaus at capacity; latency is what keeps rising after it plateaus.** A load test that never pushes `C` past `W` will report perfect latency and can validate throughput far below what the service actually needs to sustain — and ship an SLO that was never really tested (this is the module's version of M03's "it passed the test" trap, transplanted from a race condition to a load test).

**Why `W` must mean *processes*, not threads, for CPU-bound work.** This is where M03 pays its whole debt. If your endpoint does real CPU work (parsing, hashing, model inference, anything that isn't mostly waiting on I/O), `W` — the number of workers that can *actually* execute Python bytecode simultaneously — is bounded by the number of **OS processes**, because the GIL lets only one thread per process execute Python bytecode at any instant (M03 Lesson 4). A synchronous WSGI server (Gunicorn's `sync` worker class) that pre-forks `N` **processes** gives you real `N`-way CPU parallelism, each with its own interpreter and its own GIL. A single process running `N` **threads** (Gunicorn's `gthread` worker class) gives you `N`-way *concurrency* for I/O-bound work and **zero** extra CPU-bound throughput — the threads take turns holding the one GIL in that one process, exactly Lesson 4's flat-threading result, now costing you a production capacity miscalculation instead of a benchmark surprise.

#### Worked example — measuring `S`, predicting capacity, and the trap that looks identical

The service you will build in Lab M05-A exposes `/hash?n=<rounds>`, doing `n` rounds of chained SHA-256 — real, CPU-bound, deterministic work standing in for "the compute your endpoint actually does." Measured on the authoring machine (Linux x86-64, Python 3.11, one uncontended worker, `n` tuned so the per-request cost is easy to reason about): **S ≈ 40 ms.**

```
predicted capacity, W=1:  1 / 0.040  = 25   req/s
predicted capacity, W=4:  4 / 0.040  = 100  req/s
```

Measured, three configurations, same endpoint, same machine:

```
sync,  workers=1               concurrency=1   -> throughput= 24.6 req/s   p50= 40.1ms  p95= 43.8ms
sync,  workers=4               concurrency=4   -> throughput= 96.8 req/s   p50= 41.3ms  p95= 49.7ms
sync,  workers=4               concurrency=40  -> throughput= 98.2 req/s   p50=392.4ms  p95=649.8ms
gthread, workers=1 threads=4   concurrency=4   -> throughput= 25.3 req/s   p50=155.7ms  p95=168.2ms
```

Read all four lines together. Line 1 confirms `S`. Line 2 confirms `W/S` at `C=W` with latency still ≈`S` (no queueing — `C ≤ W`). Line 3 is `C=40 ≫ W=4`: throughput is pinned at the same ~100 req/s ceiling — Little's Law predicts `T = C/λ = 40/100 = 0.40 s = 400 ms`, and the measured p50 of 392 ms lands almost exactly there. **Line 4 is the trap:** four *threads* in **one** process, same total "worker count" on paper, but throughput sits at the **W=1** ceiling (25, not 100) and latency roughly quadruples (155 ms ≈ 4 × 40 ms) — because the GIL serializes the four threads' CPU-bound work onto one effective server. Four threads bought queueing, not parallelism, for this endpoint. This is Lesson 1's whole argument, produced as four numbers instead of asserted as a rule.

#### Misconception 1 — "adding threads to a worker adds capacity"

True only for I/O-bound work (M03 Lesson 4's other branch — a thread blocked on a socket read releases the GIL, and another thread runs). For CPU-bound work it is false and doubly expensive: it buys **no** additional throughput (the GIL still serializes the actual computation, worked example line 4) while simultaneously increasing the number of requests that can be *concurrently in memory* inside one process (Lab M05-C's entire failure mode). "Just add `--threads`" for a compute-bound endpoint is a change that makes your memory footprint worse and your throughput identical — the worst kind of fix, one that looks like it did something because concurrency (connections accepted) went up while capacity (requests actually completed per second) did not.

#### Misconception 2 — "if it handled the load test fine, it will scale"

A load test run at `C ≤ W` cannot distinguish a service with headroom to spare from one running at exactly its ceiling with zero slack, because both report `T ≈ S` and zero errors — the queueing symptom (Lesson 1's whole point) only appears once `C` crosses `W`. "We load-tested it and latency was fine" is evidence about the concurrency level you tested, and only that level. A load test that never reaches the target throughput has validated nothing about the target throughput; it has validated a smaller number and hoped linearity holds past a cliff it never approached.

### Lesson 2 — Reading the resource envelope while the service is running

#### Teaching text

Lesson 1 predicts the envelope; this lesson reads it back, live, from the same places M04 taught you to look. Three sources, three different truths:

- **The client's view — latency percentiles from the load generator.** `p50`, `p95`, `p99` measure what the *requester* experienced: service time plus any queueing delay. This is the number the SLO is written against, and it is the only one of the three that is fully visible to the humans on the other end of the connection.
- **`docker stats`** — a convenient, human-legible, **sampled snapshot**: CPU %, memory usage vs. limit, refreshed roughly once a second. Good for a dashboard; not a proof, because it samples — a spike that peaks and triggers an OOM kill *between* two samples is invisible to it (Misconception 3 below).
- **The cgroup files themselves (M04 Lesson 2), read live** — the ground truth, because Docker's dashboard is reading the same files you can read directly:

```bash
CID=$(docker inspect -f '{{.Id}}' svc)
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/memory.current   # bytes, RIGHT NOW
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/memory.max       # the hard cap
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/cpu.stat
# usage_usec 48219873
# user_usec 41003221
# system_usec 7216652
# nr_periods 481
# nr_throttled 398        <- of 481 scheduling periods, this cgroup was throttled in 398
# throttled_usec 36512004 <- total microseconds spent waiting out a throttle
```

`nr_throttled` and `throttled_usec` are the fingerprint Lesson 1's "capacity plateau" needs a second opinion on: a service can plateau at a lower-than-predicted throughput for **two structurally different reasons** — it has run out of **workers** (Lesson 1, `W/S`, `nr_throttled≈0`) or it has run out of **CPU quota** (M04 Lesson 2's `cpu.max`, `nr_throttled` climbing) — and from throughput alone the two are indistinguishable. Reading `cpu.stat` is how you tell them apart, and Lab M05-B is built to make you need to.

#### Worked example — three ceilings, one number, three different causes

All three configurations below plateau at **the same throughput, ~25 req/s** — and are three different bugs:

| Configuration | Throughput ceiling | `nr_throttled` | Root cause |
|---|---|---|---|
| `--workers 1` (sync), no cgroup cap | ~25 req/s | ~0 | **process-count-bound** — one worker, `W/S = 1/0.040` (Lesson 1) |
| `--workers 1 --threads 4` (gthread), no cgroup cap | ~25 req/s | ~0 | **GIL-bound** — four threads, one process, one effective server (M03) |
| `--workers 4` (sync), `--cpus=1` | ~25 req/s | high, climbing | **cgroup-quota-bound** — four processes, but only one core's worth of CPU-seconds per period to share among them (M04) |

Same visible symptom (a ~25 req/s ceiling), three unrelated mechanisms, three different fixes (add processes; stop adding threads and add processes instead; raise `--cpus` or cut the per-request compute cost). The only way to tell them apart is to check **worker configuration** (`docker inspect`'s command, or your own launch flags) and **`cpu.stat`** together — throughput alone is not diagnostic. This table *is* Lesson 3's method in miniature, and Lab M05-B builds exactly the middle-vs-right contrast.

#### Misconception 3 — "if `docker stats` never showed memory near the limit, it never got close"

`docker stats` samples on an interval (roughly once a second); the kernel's OOM decision is made continuously, against `memory.current`, the instant an allocation would cross `memory.max`. A burst that spikes past the cap and gets killed **between two samples** never appears in the dashboard's history — the last thing you see is a comfortably low number, and then the container is gone. The dashboard is a *sample* of the truth, not the truth; treating "my monitoring never showed danger" as "there was no danger" is the same reasoning error as M03's "the test passed once" — absence of an observation is not evidence of absence, it is evidence of an under-sampled window.

#### Misconception 4 — "sustained 100% CPU means something is wrong"

For a CPU-bound service under load, pinning its allotted cores at 100% is **the correct, desired outcome** — it means the work you paid for is being done. The question worth asking is never "is CPU high," it is "is the SLO still met, and is the cgroup throttling me below what I actually need." A container idling at 40% CPU while missing its latency SLO is a worse state than one at 100% CPU comfortably inside it. Reflexively treating high CPU% as an alarm, without checking `nr_throttled` or the actual latency numbers, produces exactly the wrong reaction — "scale it down, it's greedy" — to a service that is working as intended.

### Lesson 3 — Where it actually breaks: a diagnosis, not a guess

#### Teaching text

Put Lessons 1 and 2 together and a service under increasing load produces exactly **four** distinguishable failure signatures, each traceable to one module you have already completed. Learning to read the signature *before* reaching for a fix is the entire point of this module's Predict step, and it is what makes the module exam gaming-resistant: a learner who jumps straight to "add more resources" without reading the signature is guessing, and guessing is scoreable.

| Signature (what you observe) | Mechanism | Module | Correct fix |
|---|---|---|---|
| Throughput plateaus at `W/S`; `p95` rises with excess concurrency; **no errors**; memory flat; `nr_throttled≈0` | **Queueing at worker capacity** — more requests in flight than workers to serve them; the excess waits in the accept queue | M02 (the queue) + Lesson 1 (`W/S`) | Add worker **processes** (not threads, unless the endpoint is I/O-bound — M03) |
| Throughput plateaus **below** the `W/S` prediction; process count looks adequate; memory flat; `nr_throttled` high and climbing; container stays alive | **cgroup CPU throttling** — the quota, not the worker count, is the binding constraint | M04 Lesson 2 (`cpu.max`) | Raise `--cpus`, or cut the per-request compute cost `S` |
| Throughput at or near a plateau; **latency looks fine right up until the container disappears**; `docker inspect` exit code **137**; `dmesg` shows `Memory cgroup out of memory` | **cgroup memory kill** — usage crossed `memory.max` | M04 Lesson 2 (the OOM killer) | Right-size `--memory` from a computed ceiling, or cut per-request/per-thread memory footprint — never guess a bigger number |
| Errors and rising latency with CPU and memory both flat and unremarkable; connections timing out or refused before reaching the app at all | **Backlog / accept-queue exhaustion**, or a downstream dependency stalling | M02 Lesson 1 | Raise the listen backlog only if the backlog itself is the bottleneck (rare); otherwise fix the actual bottleneck upstream — a bigger backlog just delays the same collapse |

The load-bearing move is: **read the signature, name the mechanism, then pick the fix that matches the mechanism** — not the fix that is fastest to type. "Add more workers" fixes row 1 and makes row 3 worse (more processes means a higher memory baseline against the same cap, Lab M05-C). "Raise `--memory`" fixes row 3 and does nothing for row 1 or row 2. There is no universal fix; there is a diagnosis, and then a fix that follows from it.

#### Worked example — the restart loop that "fixed itself"

A service is capped at `--memory=80m`, gets OOM-killed under a traffic spike, and Docker's restart policy (`--restart unless-stopped`) brings it back up seconds later. The dashboard shows "1 restart, service healthy" and the incident is closed as "transient blip, self-healed." Read against the table: exit code 137, `dmesg` shows the cgroup kill — this is **row 3**, a memory ceiling that is simply too low for the load it received, and the restart did not fix anything; it discarded every in-flight request the killed process was holding and started a fresh process that will hit the identical ceiling the next time load spikes. "It came back up" is not evidence the problem is solved — it is evidence the *symptom* is self-hiding, which is worse: the fix (compute the real ceiling, Lab M05-C) never gets applied because nothing forced anyone to look at `dmesg`.

#### Misconception 5 — "the container restarted and came back healthy, so the problem is fixed"

A restart policy converts a crash into a *periodic* crash — it does not change the ceiling that was crossed. Every request in flight at the moment of an OOM kill is lost with no response to its caller (Tier 3 will ask what that costs someone). "Self-healing" infrastructure that silently restarts a crash-looping container is hiding the diagnosis, not performing it; the fix requires reading the exit code and `dmesg`, computing the real ceiling (Lesson 1's arithmetic, applied to memory instead of throughput), and setting the cap to match it — not trusting that recovery implies correction.

#### Misconception 6 — "the fix for a bottleneck is always more resources"

Sometimes the correct minimal fix is **cheaper per request**, not **bigger container**: reducing `S` (the compute cost) helps every row in the table simultaneously — it raises the queueing-bound ceiling (row 1), it reduces how much CPU quota each request consumes (row 2), and if the cost driving memory is per-request buffer size rather than baseline, it lowers the memory ceiling too (row 3). Reflexively raising `--memory`, `--cpus`, or `--workers` without first asking whether the per-request cost itself is inflated is the infrastructure version of M03's "lock everything to be safe" — it works, it is expensive, and it treats a design cost as an infrastructure problem forever, on every future unit of scale.

**Solution** (`service.py`) — `cpu_work` filled in (this file is reused, unmodified, in Labs M05-B and M05-C):

```python
from flask import Flask, jsonify, request
import hashlib

app = Flask(__name__)

DEFAULT_ROUNDS = 250000

def cpu_work(n):
    h = hashlib.sha256(b"seed")
    for _ in range(n):
        h = hashlib.sha256(h.digest())
    return h.hexdigest()

@app.route("/hash")
def hash_endpoint():
    n = int(request.args.get("n", DEFAULT_ROUNDS))
    digest = cpu_work(n)
    return jsonify(rounds=n, digest=digest)

@app.route("/render")
def render_endpoint():
    # Used by Lab M05-C: builds and holds an in-memory "report" for the life of the request --
    # a real per-request MEMORY cost, as opposed to /hash's per-request CPU cost.
    rows = int(request.args.get("rows", 20000))
    data = [{"id": i, "value": i * i, "label": f"row-{i}"} for i in range(rows)]
    checksum = sum(r["value"] for r in data)
    return jsonify(rows=rows, checksum=checksum)

@app.route("/health")
def health():
    return jsonify(status="ok")

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)
```

**`load.py`** — the harness you will reuse, unmodified, for the rest of the module. It is deliberately **threaded**, not sequential: each request is a blocking, I/O-bound `urlopen()` call from the *client's* point of view, so the client threads release the GIL while waiting on the socket and truly overlap (M03 Lesson 4's "I/O-bound Python → threads" case, now doing useful work instead of being a demo):

```python
#!/usr/bin/env python3
"""load.py -- a small closed-loop HTTP load generator.

Closed-loop: `concurrency` threads, each holding at most one in-flight request
at a time, immediately re-issuing the next request the instant a response
returns. By construction, the number of requests "in the system" is always
`concurrency` -- this is Little's Law's L, set directly by a command-line flag.
"""
import argparse
import time
import urllib.request
import urllib.error
from concurrent.futures import ThreadPoolExecutor, as_completed


def one_request(url, timeout=10.0):
    t0 = time.perf_counter()
    ok = False
    try:
        with urllib.request.urlopen(url, timeout=timeout) as resp:
            resp.read()
            ok = 200 <= resp.status < 300
    except (urllib.error.URLError, OSError, TimeoutError):
        ok = False
    return time.perf_counter() - t0, ok


def percentile(sorted_values, p):
    if not sorted_values:
        return float("nan")
    idx = min(len(sorted_values) - 1, int(len(sorted_values) * p))
    return sorted_values[idx]


def run(url, total, concurrency, timeout=10.0):
    latencies = []
    errors = 0
    t_start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=concurrency) as pool:
        futures = [pool.submit(one_request, url, timeout) for _ in range(total)]
        for f in as_completed(futures):
            dt, ok = f.result()
            latencies.append(dt)
            if not ok:
                errors += 1
    wall = time.perf_counter() - t_start
    latencies.sort()
    return {
        "total": total,
        "concurrency": concurrency,
        "wall_s": wall,
        "throughput_rps": total / wall if wall > 0 else float("inf"),
        "errors": errors,
        "p50_ms": percentile(latencies, 0.50) * 1000,
        "p95_ms": percentile(latencies, 0.95) * 1000,
        "p99_ms": percentile(latencies, 0.99) * 1000,
        "max_ms": (latencies[-1] * 1000) if latencies else float("nan"),
    }


def main():
    ap = argparse.ArgumentParser(description="closed-loop HTTP load generator")
    ap.add_argument("url")
    ap.add_argument("--total", type=int, default=400)
    ap.add_argument("--concurrency", type=int, default=4)
    ap.add_argument("--timeout", type=float, default=10.0)
    args = ap.parse_args()
    m = run(args.url, args.total, args.concurrency, args.timeout)
    print(f"requests={m['total']} concurrency={m['concurrency']} wall={m['wall_s']:.2f}s "
          f"throughput={m['throughput_rps']:.1f}req/s errors={m['errors']}")
    print(f"p50={m['p50_ms']:.1f}ms p95={m['p95_ms']:.1f}ms "
          f"p99={m['p99_ms']:.1f}ms max={m['max_ms']:.1f}ms")


if __name__ == "__main__":
    main()
```

```python
    """Structural claims only -- absolute req/s is hardware-dependent, exactly as in
    every prior module's tests. We assert RATIOS and DIRECTIONS, which encode the
    mechanism (process parallelism vs GIL-serialized threads), not a machine-specific number."""
    base_url = "http://localhost:8080"

    one_worker = load.run(f"{base_url}/hash", total=80, concurrency=1)
    four_sync  = load.run(f"{base_url}/hash", total=320, concurrency=4)
    four_thread = load.run(f"{base_url}/hash", total=320, concurrency=4)  # against a gthread server

    # Four SYNC workers must approach 4x the single-worker ceiling (real process parallelism).
    ratio_sync = four_sync["throughput_rps"] / one_worker["throughput_rps"]
    assert ratio_sync > 3.0, (
        f"4 sync workers only reached {ratio_sync:.2f}x a single worker's throughput -- "
        f"expected close to 4x. Are all 4 workers really separate processes?")

    # 4 THREADS in one process must NOT show that speedup -- the GIL serializes CPU work.
    ratio_thread = four_thread["throughput_rps"] / one_worker["throughput_rps"]
    assert ratio_thread < 1.5, (
        f"4 threads in one process reached {ratio_thread:.2f}x a single worker -- that would "
        f"mean the GIL let 4 threads execute CPU-bound bytecode in parallel, which it cannot.")

    print(f"PASS: sync ratio={ratio_sync:.2f}x (near 4x, real parallelism), "
          f"thread ratio={ratio_thread:.2f}x (near 1x, GIL-serialized)")

if __name__ == "__main__":
    test_worker_count_beats_thread_count_for_cpu_bound_endpoint()
```

The test compares the **sync** server to the **gthread** server started against the same port in sequence (start `svc4`, run `four_sync`, stop it, start `svcT` on the same port, run `four_thread`) — a runner script wiring that up is provided alongside the test. As in every prior module, the assertions are ratios and directions, never an absolute req/s figure, so the test encodes the mechanism (process parallelism vs. GIL-serialized threads) and cannot be satisfied by a program that merely runs fast on one particular machine.

## Three-tier reading

- **Tier 1 — material ground (verifiable facts).** A service's throughput ceiling is computable before you run a single request: `capacity ≈ W/S`, where `W` is the count of independently-scheduled **processes** (not threads, for CPU-bound work — M03's GIL verdict, reproduced in Lab M05-A as a measured 4x-vs-1x contrast) and `S` is the measured per-request service time. Past that ceiling, throughput plateaus and latency grows with the excess concurrency, exactly as Little's Law predicts (`T = C/λ`), and the excess requests are queued in a real, nameable place (M02's backlog). A cgroup CPU cap (`--cpus`) **throttles** — descheduling, not killing, `nr_throttled` climbing while the container stays alive — while a cgroup memory cap (`--memory`) **kills** — exit code 137, `dmesg`'s "Memory cgroup out of memory," the process simply gone (M04 Lesson 2, now read live from a service the learner sized themselves). Three configurations can present an *identical* throughput ceiling for three *unrelated* mechanisms (Lesson 2's table), and only reading the right file — `cpu.stat`, `docker inspect`'s exit code, the worker/thread configuration — tells them apart. None of this is estimation; it is measured, in Lab M05-A/B/C, on a service the learner built and load-tested themselves.

- **Tier 2 — what the field suppresses.** "We'll add more resources if it doesn't scale" is offered as an engineering answer and is actually a **deferral** — it substitutes spend for arithmetic, and it works often enough (cloud budgets are elastic; formula-derivation is not free) that teams stop deriving the ceiling at all and start guessing round numbers upward until the dashboard turns green. The industry's reliability vocabulary — "self-healing," "auto-recovery," "N nines of uptime" — is built to describe a *restart loop* and a *genuine fix* in the same reassuring language, and the two are not the same thing: a container that OOM-kills and restarts every four minutes under peak load can post a green "healthy" status the entire time, because uptime metrics count whether *something* is listening on the port, not whether the specific request a specific stranger just sent got an answer. The suppressed fact is that **a throughput SLO is, by definition, a promise you will not keep to everyone** — once offered load exceeds capacity, someone's request queues, times out, or gets dropped by an OOM kill, and "the SLO was met" (p95 across all requests) is compatible with a real subset of requests failing outright. The dashboard reports the aggregate; it was never built to report who was in that subset.

- **Tier 3 — sit with this (a question you cannot unknow).** You just built a service, capped its memory correctly on paper, and then watched it lose an in-flight request anyway — the OOM kill in Lab M05-C did not return an error to the client that sent it; it simply stopped, mid-`/render`, with no response at all. Somewhere on the other side of that dropped connection was a caller who sent a request, is still waiting, and will never learn whether it was processed, half-processed, or lost. Nothing in the container enforces an answer to that caller. The cgroup enforces a byte ceiling. The load balancer enforces a retry policy, maybe. Neither one enforces the thing the caller actually needed, which was to know what happened to their request. The service you just built holds strangers' data — not hypothetically; every request into `/render` or `/hash` was, in a real system, someone's report, someone's balance, someone's record — and the entire module has trained you to reason about the machine's failure in terms of bytes, cores, and exit codes, because those are the terms the machine understands. The caller does not experience an exit code. They experience silence, or a spinner that never resolves, or a number that doesn't match what they expected, and they have no way to know whether that was a bug, a capacity decision someone made on purpose, or a cost someone decided was acceptable to pass to them without asking. So: when your own sizing math says "at this load, some fraction of requests will be dropped, and that fraction is the price of the SLO we chose" — a sentence this module has taught you to write with real numbers in it — **who decided that price was acceptable to pay, who paid it, and did anyone tell them?**
