## Lessons

### Lesson 1 — The socket: a file descriptor with a machine on the other end

In M01 you opened a file: `int fd = open("log.txt", ...)`, then `read(fd, ...)`/`write(fd, ...)`. The kernel handed you a small integer; the bytes came from a disk. A **socket** is the same idea with the disk swapped for a network peer:

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
```

`fd` is a file descriptor — the same kind of integer `open` returns, indexing the same per-process table from M01. `AF_INET` = IPv4 addresses; `SOCK_STREAM` = TCP, a **reliable, ordered byte stream**; `0` = default protocol for that pair (TCP). After the connection is established you `read(fd, ...)` and `write(fd, ...)` on it exactly like a file. **The network is a file you happen to share with a stranger's machine.** That is not a metaphor; it is the Unix design — "everything is a file descriptor" — and it is why the same `read`/`write` you learned on disk files work here unchanged.

A connection is named by a **5-tuple**: `(protocol, local IP, local port, remote IP, remote port)`. `(TCP, 10.0.0.2, 51000, 93.184.216.34, 443)` is *one specific connection* and no other. This is why your laptop can hold 200 simultaneous connections to the same server on port 443 — each has a different **local** port, so each 5-tuple is unique. The port is a 16-bit number (0–65535); "the server listens on port 8080" means "the kernel routes TCP segments whose destination port is 8080 to the process that called `bind` on 8080."

The two roles differ in the calls they make:

| Server (passive open) | Client (active open) |
|---|---|
| `socket()` | `socket()` |
| `bind()` — claim a port | |
| `listen()` — mark it accepting | |
| `accept()` — **block** until a client arrives, return a *new* fd for that client | `connect()` — reach out, complete the handshake |
| `read`/`write` on the per-client fd | `read`/`write` on the connected fd |

The subtlety that trips everyone: `accept()` returns a **brand-new file descriptor** for the one client that just connected. Your `listen_fd` keeps listening; the returned `conn_fd` is the actual pipe to that one peer. One listening socket, many connection sockets.

Underneath `connect()`/`accept()` is TCP's **three-way handshake**, three segments before a single byte of your data moves:

```
client                                 server
  |------------- SYN (seq=x) ----------->|    "let's talk; my sequence starts at x"
  |<-------- SYN-ACK (seq=y, ack=x+1) ---|    "ok; mine starts at y; I got your x"
  |------------- ACK (ack=y+1) ---------->|    "got your y; we're connected"
  |------------- your data ------------->|    (can piggyback on the third packet)
```

That exchange costs **one round trip** (SYN out, SYN-ACK back — you can send data with the third ACK). Hold that number; Lesson 4 adds it to DNS and TLS to explain why a "fast" API call still takes 300 ms.

#### Worked example — the smallest honest server, annotated

```c
int listen_fd = socket(AF_INET, SOCK_STREAM, 0);   // an fd, like open() gave you

struct sockaddr_in addr = {0};                     // a fixed byte layout (AIE-102 struct)
addr.sin_family = AF_INET;
addr.sin_addr.s_addr = htonl(INADDR_ANY);          // 0.0.0.0 = "any of my interfaces"
addr.sin_port = htons(8080);                        // htons: host->network byte order

bind(listen_fd, (struct sockaddr *)&addr, sizeof(addr));   // claim port 8080
listen(listen_fd, 16);                                      // backlog of 16 pending

int conn_fd = accept(listen_fd, NULL, NULL);   // BLOCKS here until a client connects
// conn_fd is a NEW fd for that one client; listen_fd is still listening
char buf[4096];
ssize_t n = read(conn_fd, buf, sizeof(buf));   // read bytes from the peer, like a file
write(conn_fd, buf, n);                          // echo them straight back
close(conn_fd);
```

`htons` ("host to network short") is where AIE-102's endianness lesson pays rent: the network byte order is big-endian, your x86 laptop is little-endian, so the port number `8080` must be byte-swapped before it goes on the wire. Forget `htons` and you bind to port 36895 (8080 with its bytes flipped) and spend an hour wondering why nobody can reach you. **The wire has one byte order; your CPU may not share it.**

#### Misconception 1 — "`send()`/`write()` sends *a message*; one `write` on the client is one `read` on the server"

This is the single most expensive networking misconception, and TCP guarantees it is false. `SOCK_STREAM` is a **byte stream**, not a message stream. TCP promises exactly two things: every byte you write arrives (reliability) and arrives in order (ordering). It promises **nothing** about *boundaries*. If the client does `write("HELLO")` then `write("WORLD")`, the server's `read` may return `"HELLOWORLD"`, or `"HEL"` then `"LOWORLD"`, or `"HELLOWOR"` then `"LD"` — the kernel coalesces and splits at will based on buffer sizes, the network's MTU, and Nagle's algorithm. If you want messages, **you** must frame them (a length prefix, or a delimiter like the `\r\n\r\n` HTTP uses in Lesson 2). This is not an edge case you might hit; it is the normal case on any connection that carries more than a few bytes or crosses a real network. Every "it worked on localhost and broke in production" networking bug is some version of this.

#### Misconception 2 — "a socket is a special kind of object; networking is its own API"

It is a file descriptor. `read`, `write`, `close`, `select`, `poll`, even `dup` — the M01 file syscalls — all operate on it. The *only* socket-specific calls are the ones that set up the connection (`socket`, `bind`, `listen`, `accept`, `connect`) and a few that tune it (`setsockopt`). Once connected, it is a bidirectional pipe of bytes you `read` and `write` exactly as you did a file in M01. Internalizing "it's just an fd" is what lets you reason about it instead of memorizing an API.

### Lesson 2 — HTTP is text on a wire

You have called HTTP APIs for years through `requests.get(...)` or `fetch(...)`. Strip the library away and HTTP/1.1 is **plain ASCII text you could type by hand** — and in this lesson's lab, you will. A request is a request line, then header lines, then a blank line, then an optional body. Every line ends with `\r\n` (carriage-return + line-feed, bytes `0x0D 0x0A` — this is the framing from Misconception 1 made concrete).

Here is a complete, valid HTTP/1.1 request, byte for byte (`␍␊` marks each `\r\n`):

```
GET /index.html HTTP/1.1␍␊
Host: example.com␍␊
User-Agent: curl/8.4.0␍␊
Accept: */*␍␊
␍␊
```

- **Request line:** `METHOD SP target SP version` — `GET /index.html HTTP/1.1`.
- **Headers:** `Name: value`, one per line, case-insensitive names.
- **Blank line** (`\r\n` on its own): the delimiter that says "headers are done." This is the message framing — the server reads bytes until it sees `\r\n\r\n`.
- **Body:** for `GET` there is none; for `POST` it follows the blank line, and its length is given by the `Content-Length` header.

The response has the identical shape, with a **status line** instead of a request line:

```
HTTP/1.1 200 OK␍␊
Content-Type: text/html␍␊
Content-Length: 13␍␊
Connection: close␍␊
␍␊
Hello, wire!
```

`Content-Length: 13` is the promise that exactly 13 bytes of body follow the blank line (`Hello, wire!\n` is 13 bytes). This is how the client knows when the response is complete without the connection closing — it reads the headers, finds `Content-Length`, then reads exactly that many body bytes. **The length header is the message-framing solution to Lesson 1's boundary problem, done in the protocol.**

#### Worked example — read a real request/response by hand

You do not need a browser or a client library. `nc` (netcat) opens a raw TCP connection; you type the HTTP yourself. The `Host` header is mandatory in HTTP/1.1 (one IP can serve many sites — "virtual hosting" — so the server needs to be told which one you want):

```bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' \
  | nc example.com 80
```

You will see the raw response headers and HTML scroll past — no library between you and the bytes. `Connection: close` tells the server to hang up after one response (simplest to reason about; the default in HTTP/1.1 is `keep-alive`, reusing the connection). The `printf` writes the exact CRLFs; if you use `echo` or forget the final blank line, the server waits forever because it never sees the `\r\n\r\n` that ends your headers — **you will have reproduced Lesson 1's framing rule by starving it.**

#### Misconception 3 — "HTTP is a binary protocol / the browser does something magic"

HTTP/1.1 is human-readable ASCII with a rigid line grammar; that is the whole reason `curl`, `nc`, and telnet can speak it and you can read a capture with your eyes. The browser does nothing you cannot do by hand — it resolves DNS (Lesson 3), opens a TCP socket (Lesson 1), writes those exact text lines, and reads the response. (HTTP/2 and HTTP/3 *are* binary and compressed for efficiency, but they carry the identical semantic model — methods, paths, headers, status codes — and every HTTP/2 server still understands the concepts you are typing here. We teach the text protocol because it is the one you can read, and the model is unchanged underneath the binary framing.)

#### Misconception 4 — "`Content-Length` is optional / the server just sends until it's done"

If you send a body without either `Content-Length` or `Transfer-Encoding: chunked`, an HTTP/1.1 client cannot tell where your response ends versus where the next one begins on a reused (keep-alive) connection — and a mismatch between the `Content-Length` you *declare* and the bytes you *send* is a genuine security bug (HTTP request smuggling exploits exactly this disagreement between two servers counting bytes differently). The length is not bookkeeping; it is the frame. In this module's lab you compute it as `len(body)` and never hard-code it — a hard-coded length that disagrees with the body is the defect the assessment plants.

### Lesson 3 — DNS and TLS: the two things that happen before your `GET`

When you type `curl https://example.com`, the `GET` from Lesson 2 does not go out first. Two full exchanges happen before it — and each costs round trips you will account for in Lesson 4.

**DNS — turning a name into an address.** TCP connects to an *IP address*, not a name. `example.com` must first be resolved. Your machine asks a **resolver** (usually your ISP's or `8.8.8.8`), which, on a cache miss, walks the hierarchy: root servers → `.com` servers → `example.com`'s authoritative server, then returns the `A` record (IPv4) or `AAAA` (IPv6). If nothing is cached this is several round trips; if your resolver has it cached, it is one. The answer carries a **TTL** — seconds you may cache it — which is why DNS changes "take time to propagate" and why a resolved address is not free the first time and nearly free after.

```bash
dig +noall +answer example.com
# example.com.  3600  IN  A  93.184.216.34     <- name, TTL=3600s, type A, the address
```

**TLS — turning a plaintext socket into an encrypted one.** `https` is *not* "http with an s." After the TCP handshake (Lesson 1) completes, a **TLS handshake** runs *inside* that TCP connection: the client and server agree on a cipher, the server proves its identity with a certificate signed by a CA your system trusts, and they derive session keys. Only then does your `GET` go out — encrypted. The cost in round trips depends on the version:

- **TLS 1.2 full handshake:** 2 round trips.
- **TLS 1.3:** 1 round trip (and 0-RTT for resumption, with caveats).

You can watch the whole thing, including the certificate chain:

```bash
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
# subject=CN=example.com     <- who the cert is for
# issuer=CN=...CA...          <- who vouched for it (must chain to a root you trust)
# notBefore/notAfter=...      <- validity window
```

`-servername` sends **SNI** (Server Name Indication) — the plaintext hostname inside the TLS hello, so a server hosting many HTTPS sites on one IP knows which certificate to present. It is the TLS-era analogue of the `Host` header, and note the consequence: the hostname you are visiting is *not* encrypted even under HTTPS (Tier 2 of the reading picks this up).

#### Worked example — the four things between you and a byte, in order

A cold `curl https://example.com` (nothing cached) does, in strict sequence:

1. **DNS:** resolve `example.com` → `93.184.216.34` (≈1 RTT to a warm resolver).
2. **TCP:** three-way handshake to `93.184.216.34:443` (1 RTT).
3. **TLS:** handshake inside that TCP connection (1 RTT on TLS 1.3).
4. **HTTP:** send the `GET`, receive the response (1 RTT to first byte).

Four sequential round trips **before the response body streams** — and not one of them is made faster by buying more bandwidth (Lesson 4). On a warm connection (DNS cached, TCP + TLS reused via keep-alive), steps 1–3 vanish and you pay only step 4. This is the entire reason connection reuse and HTTP/2 exist.

#### Misconception 5 — "`https` just encrypts the same request; it's `http` plus encryption"

HTTPS adds an entire handshake, an identity proof (the certificate chain, validated against your system's trust store), and per-connection key derivation *before* any HTTP flows — and it changes what an observer can see (they see the IP, the SNI hostname, and traffic sizes/timings, but not the path or body). The `s` is a separate protocol layer (TLS) sitting between TCP and HTTP, with its own round-trip cost and its own failure modes (expired cert, untrusted CA, hostname mismatch, protocol-version mismatch) that have nothing to do with your application. When `curl` says `SSL certificate problem`, no HTTP ever happened — you failed at step 3.

#### Misconception 6 — "DNS is instant / DNS is part of the HTTP request"

DNS is a **separate protocol** (usually UDP on port 53), resolved before the TCP socket is even opened, and on a cache miss it can be the *slowest* part of a cold request — several round trips up the hierarchy. It is invisible in your application code, which is exactly why a "the API is slow" report so often turns out to be "our resolver was slow" once you break down the timing (Lab C). Caching (the TTL) is what makes it feel instant on the second call; the first call pays.

### Lesson 4 — Latency vs bandwidth: the two numbers that are not the same, and don't trade off

This is the lesson that reorganizes how you think about "fast." Two independent numbers describe a link:

- **Latency (RTT):** how long one round trip takes — you send, you get an answer back. Measured in *milliseconds*. Set mostly by **distance and the speed of light** plus per-hop switching. Same city ≈ 1–5 ms; across a continent ≈ 30–80 ms; across the world ≈ 150–300 ms. You cannot buy your way under the speed of light: light in fiber covers ~200 km/ms, so a 6,000 km path is ~30 ms *one way*, ~60 ms round trip, and no amount of money changes that.
- **Bandwidth (throughput):** how many bytes per second the link can carry once data is flowing. Measured in *Mbps/Gbps*. Set by the **narrowest link** on the path. This is what your ISP sells you and calls "speed."

They are **orthogonal**. A satellite link can be 1 Gbps of bandwidth with 600 ms of latency (a fat, long pipe). A cross-town copper line can be 10 Mbps with 2 ms latency (a thin, short pipe). Upgrading one does nothing for the other. The industry markets bandwidth as "speed" because it is the number they can sell more of; latency is set by physics and geography and they mostly can't.

**Which one dominates depends on the size of what you move.** The transfer time of a response is, roughly:

```
total ≈ (setup round trips × RTT)  +  (payload bytes ÷ bandwidth)
         \_______ latency-bound _______/    \___ bandwidth-bound ___/
```

Run the numbers on a link with **RTT = 100 ms** and **bandwidth = 10 Mbps** (= 1.25 MB/s):

| Payload | Latency part (4 RTT cold: DNS+TCP+TLS+HTTP) | Bandwidth part | Total | Bound by |
|---|---|---|---|---|
| 1 KB JSON API reply | 400 ms | 0.0008 s ≈ 0.8 ms | **≈ 401 ms** | **latency** (99.8%) |
| 10 MB image | 400 ms | 8.0 s | **≈ 8.4 s** | **bandwidth** (95%) |

The API call is **99.8% latency** — doubling your bandwidth to 20 Mbps changes its total from 401 ms to 400.4 ms, a rounding error. The image is **95% bandwidth** — there, doubling bandwidth nearly halves the time. **Small and frequent = latency-bound; large and bulk = bandwidth-bound.** Almost every API you will build is the first row, which is why the wins come from *removing round trips* (caching DNS, reusing TCP+TLS connections, HTTP/2 multiplexing, putting servers physically closer to users via a CDN) — not from a faster pipe. An engineer who reaches for "add bandwidth" to fix a slow API is optimizing the 0.2%.

The companion number is the **bandwidth-delay product** — `bandwidth × RTT` — the amount of data "in flight" filling the pipe at any instant (10 Mbps × 100 ms = 125 KB). If TCP's window is smaller than this, you leave the pipe half-empty and never reach full bandwidth no matter how fat the link. It is the quantitative reason a single TCP connection over a long-fat link underperforms until the window grows — the metal reason behind "why is my transcontinental transfer slow even on a gigabit line."

#### Worked example — put a real breakdown on it

`curl` reports the phase timeline. The `%{time_*}` fields are **cumulative timestamps from the start of the request**, not per-phase durations — so a phase's cost is the *difference* between consecutive timestamps (this is the prediction trap in Lab C):

```bash
curl -s -o /dev/null -w \
'dns=%{time_namelookup}  tcp=%{time_connect}  tls=%{time_appconnect}  ttfb=%{time_starttransfer}  total=%{time_total}\n' \
  https://example.com
# dns=0.031  tcp=0.061  tls=0.120  ttfb=0.151  total=0.152
```

Read it as *cumulative*, then difference to get phases:

- DNS: `0.031 − 0` = **31 ms** (name lookup).
- TCP handshake: `0.061 − 0.031` = **30 ms** (≈ 1 RTT — this *is* your RTT to the server).
- TLS handshake: `0.120 − 0.061` = **59 ms** (≈ 2 RTT on 1.2, or 1 RTT + compute).
- Server think + first byte: `0.151 − 0.120` = **31 ms** (≈ 1 RTT to first byte).
- Body transfer: `0.152 − 0.151` = **1 ms** (tiny payload — negligible, this response is latency-bound).

A learner who reads `tls=0.120` and reports "TLS took 120 ms" has made the cumulative-vs-phase error and inflated TLS by 4x. The whole cold request is 152 ms and **151 of it is setup round trips** — the body was 1 ms. That is Lesson 4's thesis on one real line: for a small response, *the request is round trips, not bytes.*

#### Misconception 7 — "faster internet (more Mbps) makes everything faster"

More Mbps shortens only the bandwidth term. It does nothing to RTT, and RTT is what dominates small, frequent requests — the entire category most APIs live in. This is why a 1 Gbps connection to a server 8,000 km away still shows ~200 ms per uncached request, and why moving the server closer (a CDN edge, a nearer region) — cutting the *distance*, hence the latency — beats buying bandwidth for that workload. "Upgrade the pipe" is the right instinct for bulk transfer and the wrong instinct for chatty APIs.

#### Misconception 8 — "latency and bandwidth trade off against each other"

They are independent axes, not two ends of one dial. You can have any combination: low/low (thin short link), low/high (ideal LAN), high/low (bad satellite), high/high (fat transcontinental fiber). Optimizing one leaves the other untouched. The engineering skill is diagnosing **which one your workload is bound by** (the table above) and spending effort only there. Guess wrong and you can double your infrastructure cost and move the p99 by nothing.

**Solution** (`echo_server.c`):

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <sys/socket.h>
#include <netinet/in.h>

int main(int argc, char **argv) {
    int port = (argc > 1) ? atoi(argv[1]) : 8080;

    int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (listen_fd < 0) { perror("socket"); return 1; }

    int yes = 1;
    setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes));

    struct sockaddr_in addr = {0};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);   // 0.0.0.0
    addr.sin_port = htons(port);                 // host -> network byte order

    if (bind(listen_fd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        perror("bind"); return 1;
    }
    if (listen(listen_fd, 16) < 0) { perror("listen"); return 1; }
    printf("listening on :%d\n", port);

    for (;;) {
        int conn_fd = accept(listen_fd, NULL, NULL);   // a NEW fd for this one client
        if (conn_fd < 0) { perror("accept"); continue; }

        char buf[4096];
        ssize_t n;
        while ((n = read(conn_fd, buf, sizeof(buf))) > 0) {   // 0 = peer closed, <0 = error
            ssize_t off = 0;
            while (off < n) {                                  // write may be partial
                ssize_t w = write(conn_fd, buf + off, n - off);
                if (w < 0) { perror("write"); break; }
                off += w;
            }
        }
        close(conn_fd);                                        // one client, then next
    }
}
```

**Client** (`echo_client.c`):

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <sys/socket.h>

// writes all `len` bytes from buf to fd, looping over partial writes
static int write_all(int fd, const char *buf, size_t len) {
    size_t off = 0;
    while (off < len) {
        ssize_t w = write(fd, buf + off, len - off);
        if (w < 0) return -1;
        off += (size_t)w;
    }
    return 0;
}

int main(int argc, char **argv) {
    const char *host = (argc > 1) ? argv[1] : "127.0.0.1";
    int port         = (argc > 2) ? atoi(argv[2]) : 8080;

    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) { perror("socket"); return 1; }

    struct sockaddr_in addr = {0};
    addr.sin_family = AF_INET;
    addr.sin_port   = htons(port);
    if (inet_pton(AF_INET, host, &addr.sin_addr) != 1) {
        fprintf(stderr, "bad address: %s\n", host); return 1;
    }
    if (connect(fd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        perror("connect"); return 1;   // fails here if the 3-way handshake can't complete
    }

    // Two separate writes on purpose: prove TCP does NOT preserve these boundaries.
    if (write_all(fd, "PING", 4) < 0) { perror("write"); return 1; }
    if (write_all(fd, "PONG", 4) < 0) { perror("write"); return 1; }

    // Read the 8 echoed bytes back; they may arrive in 1, 2, or more chunks.
    char buf[64];
    size_t got = 0;
    while (got < 8) {
        ssize_t n = read(fd, buf + got, sizeof(buf) - got);
        if (n <= 0) break;                 // 0 = server closed, <0 = error
        printf("read() returned %zd byte(s): %.*s\n", n, (int)n, buf + got);
        got += (size_t)n;
    }
    printf("total received: %.*s\n", (int)got, buf);
    close(fd);
    return 0;
}
```

#### Build

**Starter / Solution** (`http_server.py`):

```python
"""A minimal, correct HTTP/1.1 handler on raw sockets.

Deliberately single-threaded and Connection: close — one request per connection,
one client at a time. Concurrency (many clients at once) is M03's problem; this
lab is about the protocol as bytes, not about scale.
"""
import socket


def build_response(body: bytes, status: str = "200 OK",
                   content_type: str = "text/plain; charset=utf-8") -> bytes:
    # Content-Length is computed from the body, never hard-coded: the frame
    # (Lesson 2) must equal the bytes that follow it, or the client miscounts.
    head = (
        f"HTTP/1.1 {status}\r\n"
        f"Content-Type: {content_type}\r\n"
        f"Content-Length: {len(body)}\r\n"
        f"Connection: close\r\n"
        f"\r\n"
    ).encode("ascii")
    return head + body


def parse_request(raw: bytes):
    """Split head from body at the first blank line; parse the request line
    and headers. Returns (method, target, version, headers, body)."""
    head, _sep, body = raw.partition(b"\r\n\r\n")
    lines = head.split(b"\r\n")
    method, target, version = lines[0].decode("ascii", "replace").split(" ", 2)
    headers = {}
    for line in lines[1:]:
        if not line:
            continue
        name, _c, value = line.partition(b":")
        headers[name.decode().strip().lower()] = value.decode().strip()
    return method, target, version, headers, body


def read_request(conn: socket.socket) -> bytes:
    """Read from the socket until the end-of-headers delimiter (\\r\\n\\r\\n).
    This is the message framing: without it we would not know when the client's
    headers are done (Lab A's boundary problem, solved by the protocol)."""
    buf = b""
    while b"\r\n\r\n" not in buf:
        chunk = conn.recv(4096)
        if not chunk:            # peer closed before finishing headers
            break
        buf += chunk
    return buf


def handle(conn: socket.socket) -> None:
    raw = read_request(conn)
    if not raw:
        return
    method, target, version, headers, _body = parse_request(raw)
    if target == "/hello":
        payload = b"Hello, wire!\n"
        conn.sendall(build_response(payload))
    else:
        payload = f"you asked for {target} via {method}\n".encode("utf-8")
        conn.sendall(build_response(payload, status="404 Not Found"
                                    if target != "/" else "200 OK"))


def serve(host: str = "127.0.0.1", port: int = 8080) -> None:
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind((host, port))
    s.listen(16)
    print(f"serving http://{host}:{port}  (Ctrl-C to stop)")
    try:
        while True:
            conn, _addr = s.accept()      # blocks; one client at a time (M03 sets up scale)
            try:
                handle(conn)
            finally:
                conn.close()
    except KeyboardInterrupt:
        pass
    finally:
        s.close()


if __name__ == "__main__":
    serve()
```

```python
# rtt_probe.py — time just the TCP three-way handshake to host:port, N times.
import socket, time, sys, statistics

def tcp_rtt(host: str, port: int) -> float:
    addrinfo = socket.getaddrinfo(host, port, socket.AF_INET, socket.SOCK_STREAM)
    family, socktype, proto, _canon, sockaddr = addrinfo[0]
    s = socket.socket(family, socktype, proto)
    t0 = time.perf_counter()
    s.connect(sockaddr)          # returns when the 3-way handshake completes: ~1 RTT
    dt = time.perf_counter() - t0
    s.close()
    return dt * 1000.0           # ms

if __name__ == "__main__":
    host = sys.argv[1] if len(sys.argv) > 1 else "example.com"
    port = int(sys.argv[2]) if len(sys.argv) > 2 else 443
    samples = [tcp_rtt(host, port) for _ in range(5)]
    print(f"{host}:{port}  TCP handshake RTT (ms): "
          f"min={min(samples):.1f}  median={statistics.median(samples):.1f}")
```

```python
# Verifies the ATTRIBUTION LOGIC the learner must reason about: cumulative
# curl timestamps must be differenced into non-negative phase durations, and

def phases_from_cumulative(t):
    """t: dict of cumulative curl timings (seconds). Return per-phase durations."""
    return {
        "dns":      t["namelookup"] - 0.0,
        "tcp":      t["connect"]    - t["namelookup"],
```

## Assessment

**Design constraint: gaming-resistance.** A learner cannot pass by pasting a working server, because the score lives in the **Predict artifacts** and the **mechanistic reasoning**, not in "it served a page." A program that runs with no prediction trail caps low; a prediction with the right mechanism and off numbers scores full.

### Component weights

| Component | % | What it measures | Why it can't be gamed |
|---|---|---|---|
| M02-A predict-and-diff | 20 | stream-vs-message, `accept` semantics, byte order, from a working socket pair | score is the *reasoned diff*; a working echo with no prediction of read-count behavior caps at 40% of this component; the test forbids asserting a read count, so "it echoed" proves nothing about the boundary lesson |
| M02-B protocol by hand | 25 | HTTP as exact bytes; `Content-Length` correct by construction; CRLF framing | full marks require naming *why* a wrong length is a real bug (stream desync / smuggling); a server that happens to work with a hard-coded length fails the mechanism gate |
| M02-C round-trip attribution | 25 | differencing cumulative timings into phases; latency- vs bandwidth-bound | **zero for reading cumulative timestamps as phase durations**, and **zero for "more bandwidth fixes this" on a small payload**, even if never run — the reasoning is the gate |
| Module exam (below) | 30 | unseen scenario: predict → read the wire → locate → fix → prove | the artifact is the judgment trail; a fix with no prediction fails |

### Module exam — unseen scenario, predict before running

The learner is handed **one unseen scenario** drawn at random from a bank, each containing exactly one wire-level defect or misdiagnosis, and must produce a four-part artifact:

**(a) Predict** the behavior *before running* — in socket / stream / HTTP-framing / round-trip terms.
**(b) Read the wire** — capture the actual bytes or timings (`nc`, `curl -v`, `curl -w`, `ss`, `openssl s_client`, or the `rtt_probe.py`) and locate the mechanism.
**(c) Fix** the defect or **correct the misdiagnosis**.
**(d) Prove** the fix with a capture or a timing measurement that *demonstrates the named mechanism was the cause*.

Example bank items (the learner sees one, unseen):

- **The framing bug:** a server that reads one `recv()` and assumes it got the whole request, shipped as "working" because it works on localhost. Predict *why* it corrupts under a client that sends headers in two packets (stream, not messages — M02-A), reproduce by splitting the send, fix by reading until `\r\n\r\n` (M02-B), prove with a capture showing the two-packet request now handled.
- **The `Content-Length` lie:** a handler that hard-codes `Content-Length: 100` but sends a 40-byte body. Predict what the client believes about the 60 missing bytes and why a keep-alive connection then desyncs (Misconception 4). Prove with `curl -v` hanging/erroring, fix to `len(body)`.

| Dimension | 0 — absent/gamed | 1 — partial | 2 — full |

## Three-tier reading

- **Tier 1 — material ground (verifiable facts).** A network connection is a file descriptor over which bytes stream; TCP guarantees delivery and order but **not** message boundaries, so the count of your writes is not the count of the peer's reads (Lab M02-A, reproducible). HTTP/1.1 is ASCII text with a rigid line grammar delimited by `\r\n`, framed by a blank line and a `Content-Length`; you can type a valid request by hand into `nc` and read the raw response (Lab M02-B). Before any HTTP flows, a name is resolved by DNS and — under HTTPS — a TLS handshake runs inside the TCP connection and proves identity with a CA-signed certificate; each is a separate protocol with its own round-trip cost (Lesson 3). Latency (RTT, set by distance and the speed of light) and bandwidth (bytes/second, set by the narrowest link) are independent numbers, and which one bounds a transfer is decided by payload size — small frequent requests are latency-bound, bulk transfers bandwidth-bound (Lesson 4, arithmetic in the table, measurable in Lab M02-C). None of this is opinion; it is documented protocol behavior you measured.

- **Tier 2 — what the field suppresses.** The abstraction the whole industry sells — "just call the API," "the CDN handles it," "we're on gigabit" — suppresses that **scale is bought by refusing to know individual users, and by moving computation physically closer to them.** "More bandwidth = faster" is marketed relentlessly because bandwidth is the number an ISP can sell you more of; latency is set by geography and the speed of light and mostly can't be sold, so it is quietly dropped from the sales pitch — even though it dominates the exact chatty-API workload most services actually run. The other suppressed fact is what the encrypted padlock does *not* hide: even under HTTPS, the SNI hostname is sent in plaintext and the pattern of packet sizes and timings leaks which page you loaded — the confidentiality is real but partial, and "it's encrypted, you're safe" papers over the metadata that is not. And the reliability you lean on — TCP's guaranteed, ordered delivery — is itself a layer someone maintains over an unreliable network of strangers' routers that drop, reorder, and duplicate packets constantly; "the connection is stable" is a fiction TCP renders convincingly on top of one that is not.

- **Tier 3 — sit with this (a question you cannot unknow).** The service you are about to build in this course will `accept()` a connection from a machine you will never see, read bytes a stranger's client wrote, and write bytes back — and the entire relationship is a 5-tuple and a byte stream. Scale, you now know, is the decision to serve that stranger *without knowing them individually* — that is precisely what lets one process answer a million of them. But the bytes they send you are their login, their location, their query, their data, arriving over a connection whose only guarantee is order, not privacy, and whose encryption hides the page but not the pattern. When your server holds ten thousand of those connections open at once, each one a person reduced to a file descriptor so that you *can* hold ten thousand: what do you owe the stranger on the other end of a socket you designed specifically so you would never have to know they are there — and at which layer, if any, does anything force you to pay it?
