# AIE-104-M04 — Containers and reproducible environments, opened up

**Hours:** 14 · **Sits in the descent:** the fourth descent of the course, and the one where every prior layer gets folded into a single object you have used a thousand times without opening. M01 gave you the process, the file descriptor, and the `/proc` window into a running program. M02 gave you the socket and the port. M03 gave you concurrency — many processes, one kernel, the byte two threads fight over. This module takes the sentence *"just run it in a container,"* *"it works on my machine so ship the image,"* *"the container is like a lightweight VM"* — and walks it down to what a container actually **is**: an ordinary Linux process, on the host's one kernel, wearing three disguises — a **namespace** (what it can see), a **cgroup** (what it can use), and a **union filesystem** (what it thinks its disk is). There is no second machine. `docker run` forks a process, lies to it about the world with namespaces, fences its resources with cgroups, and mounts a stack of read-only layers under it. We will open every one of those from the host — find the container's real PID, read its namespace inodes, watch a cgroup OOM-kill it, and take an image apart layer by layer — then re-ascend to a Dockerfile you can reason about: predicting its image size and its cache behavior **before** you build it. **"It's basically a VM" is a sentence we are about to disprove with `docker inspect -f '{{.State.Pid}}'` and one `ps` on the host.**

> **Prereq check (from M01–M03 and AIE-102):** you can say that a process has a PID and its own address space (M01); that `/proc/<pid>/` is the kernel's live window into a running process (M01); that a file descriptor is a small integer into a per-process table (M01); that many processes share **one kernel** and are scheduled onto real cores (M03); that the GIL means Python parallelism is process-level, not thread-level (AIE-102); and that a mount is the kernel attaching a filesystem at a path (M01). Every one is load-bearing here: a container **is** a process (so it has a host PID and a `/proc` entry), namespace isolation is enforced by that **one shared kernel** (there is no second kernel — that is the whole VM distinction), and "the container's filesystem" is a stack of mounts. If any is shaky, that is an M01/M03 reroute, not an M04 failure.

## Lessons

### Lesson 1 — A container is a process wearing a namespace, not a machine

Start from what you can already see. On the host, run a container and then look for it with the M01 tools:

```bash
docker run -d --name box alpine sleep 1000     # start a container running `sleep`
docker inspect -f '{{.State.Pid}}' box          # -> e.g. 24817  (its PID *on the host*)
ps -o pid,comm -p 24817                          #   24817 sleep   <- it's just a process
```

There it is in the host's process table: PID 24817, command `sleep`. **The container is not running "inside" anything. It is a process the host kernel scheduled onto a real core, exactly like every other process from M03.** What makes it *feel* like a separate machine is a kernel feature called a **namespace**: a way of giving a process a private, filtered view of one kind of global resource. The process still runs on the one kernel; the kernel just answers its questions differently.

There are several namespace types, each virtualizing one global thing:

| Namespace | Virtualizes | The lie it tells the process |
|---|---|---|
| **PID** | process IDs | "you are PID 1; you can only see your own descendants" |
| **mount (mnt)** | the filesystem tree | "your root `/` is this image, not the host's disk" |
| **network (net)** | interfaces, ports, routes | "you have your own `eth0` and your own port space" |
| **UTS** | hostname | "your hostname is `a1b2c3`, not the host's" |
| **IPC** | shared memory, semaphores | "you can't see the host's IPC objects" |
| **user** | UID/GID mapping | "you are root (uid 0) — but only in here" |

The killer demonstration is the PID namespace. Inside the container, that same `sleep` process believes it is **PID 1**:

```bash
docker exec box ps -o pid,comm     #   PID COMMAND
                                    #     1 sleep          <- PID 1 *in here*
```

One process, **two PIDs**: 24817 on the host, 1 inside its PID namespace. The kernel maintains both numbers for the same task. This is the entire trick of containers in one fact — **there is no isolation object called "the container"; there is a process with a set of namespace memberships, and `docker` is a program that sets them up.** You can read those memberships directly. Every namespace a process belongs to appears as a symlink under `/proc/<pid>/ns/`, and the symlink target is an inode number naming the namespace:

```bash
sudo ls -l /proc/24817/ns/            # the container process's namespaces
# lrwxrwxrwx ... pid -> 'pid:[4026532...]'   <- a DIFFERENT pid namespace than the host's
sudo ls -l /proc/1/ns/                # the host's init (systemd) namespaces
# lrwxrwxrwx ... pid -> 'pid:[4026531836]'   <- the host's pid namespace
```

If two processes show the **same** inode for a namespace type, they share that namespace; different inodes, isolated. The container's `pid` inode differs from the host's — that is the isolation, made of nothing but a different number the kernel checks. This is why `nsenter` works: it is a program that joins your shell to another process's namespaces, so you can walk *into* the container using only its host PID:

```bash
sudo nsenter -t 24817 -p -m -n sh     # enter the target's PID, mount, and net namespaces
# now `ps`, `ls /`, `ip addr` show the CONTAINER's view — from a plain host shell, no docker
```

**A container is a process; `docker` is the setup crew; namespaces are the disguise; the one kernel is never fooled — it is the one holding both PID numbers.**

#### Worked example — one kernel, proven with `uname`

The single sharpest way to feel "one kernel, not two machines": the container cannot have a different kernel version than the host, because it is not running a kernel at all.

```bash
uname -r                              # host kernel, e.g. 6.8.0-40-generic
docker run --rm alpine uname -r       # 6.8.0-40-generic   <- IDENTICAL. same kernel.
```

Alpine's userland is nothing like Ubuntu's, yet `uname -r` is byte-identical, because `uname` asks the kernel its version and **there is only one kernel to ask.** A real VM boots its own kernel and would report a different version. This one command separates "container" (shares the host kernel) from "VM" (boots its own). It is also why you cannot run a Windows container on a Linux kernel, and why a container built for kernel features your host lacks will fail: there is no second kernel to provide them.

#### Misconception 1 — "a container is a lightweight virtual machine"

A VM boots a **second kernel** on **virtual hardware** provided by a hypervisor; it has its own memory management, its own device drivers, its own `uname`. A container has **none of that** — it is a host process whose view of PIDs, mounts, network, and hostname is filtered by namespaces and whose resources are capped by cgroups, all enforced by the **one host kernel it shares with every other process on the box**. The consequences are concrete, not academic: (1) a container has near-zero boot time because there is no kernel to boot — `docker run` is `fork`+`exec` with namespaces set, microseconds not seconds; (2) a kernel exploit inside a container attacks the *host's* kernel, because it *is* the host's kernel — container isolation is weaker than VM isolation for exactly this reason; (3) you cannot change kernel parameters or load kernel modules per-container in the way you can per-VM, because there is one kernel. "Lightweight VM" gets the weight right and the mechanism catastrophically wrong, and the mechanism is what determines the security boundary.

#### Misconception 2 — "the container has its own operating system (`FROM ubuntu` installs Ubuntu)"

`FROM ubuntu` gives you Ubuntu's **userland** — its `/bin`, `/lib`, its `apt`, its libc — as a filesystem the process sees as root. It does **not** give you Ubuntu's kernel; there is no kernel in the image. An "OS" is a kernel plus a userland; a container image is userland only. This is why an image is measured in tens or hundreds of megabytes, not gigabytes — it is missing the entire kernel and the entire hardware-driver stack a real OS carries. When you run `FROM ubuntu` on a Fedora host, you are running Ubuntu's `apt` and glibc against the *Fedora host's kernel*. It works because the Linux kernel's syscall interface is stable across distributions — the userland and the kernel are decoupled, and the container ships only the top half.

### Lesson 2 — cgroups: the fence around what a process can *use*

Namespaces control what a process can **see**. They do nothing about what it can **consume** — a process in its own PID and mount namespace can still eat all the host's RAM and peg every core, starving everything else on the one shared kernel. The second half of a container is the **control group (cgroup)**: the kernel mechanism that meters and caps a process's CPU, memory, I/O, and process count. **Namespaces = the disguise (what you see); cgroups = the leash (what you get).** A container is a process with both.

On a modern Linux host with **cgroups v2**, every cgroup is a directory under `/sys/fs/cgroup/`, and its limits and usage are plain files you read and write. When you run a memory-limited container:

```bash
docker run -d --name capped --memory=50m alpine sleep 1000
PID=$(docker inspect -f '{{.State.Pid}}' capped)
cat /proc/$PID/cgroup                             # -> 0::/system.slice/docker-<id>.scope
cat /sys/fs/cgroup/system.slice/docker-*.scope/memory.max   # -> 52428800   (== 50 * 2^20)
```

`memory.max` is the hard cap in bytes. `50m` became `52428800` — the kernel now refuses to let this process tree's resident memory exceed that. What happens when it tries? The kernel's **OOM (out-of-memory) killer** fires *inside that cgroup only* and kills the offending process — the host and every other container are untouched, because the limit is per-cgroup. The container exits with code **137** (= 128 + 9, meaning "killed by signal 9, SIGKILL"). That exit code is the fingerprint of a cgroup memory kill, and you will learn to read it on sight.

CPU is metered differently — not a kill but a **throttle**. `--cpus=0.5` tells the CPU controller to allow this cgroup 50,000 microseconds of CPU per 100,000-microsecond period (`cpu.max` = `50000 100000`). A busy-looping process does not get killed; it gets **descheduled** once it spends its slice, so it runs at half a core no matter how hard it spins. This is the M03 scheduler from the prior module, now steered by a cgroup quota.

```bash
docker run --rm --cpus=0.5 alpine sh -c 'yes > /dev/null'   # pins to 50% of one core, not 100%
# watch it from the host with `top` or `docker stats`: CPU% hovers at ~50, not 100
```

**A container's resource limits are not Docker features; they are kernel cgroup files Docker writes on your behalf.** You can read them, and in the lab you will watch one enforce a memory cap by killing the process — from the host, through the cgroup filesystem, with no Docker command in the loop.

#### Worked example — provoke the OOM kill and read the fingerprint

```bash
# A container capped at 20 MB, told to allocate ~100 MB. Predict the exit code first.
docker run --name hog --memory=20m alpine \
  sh -c 'a=""; while true; do a="$a$(head -c 1000000 /dev/zero | tr "\0" "x")"; done'
# ...the shell grows `a` past 20 MB, the cgroup OOM killer fires, the process dies.
echo "exit code: $(docker inspect -f '{{.State.ExitCode}}' hog)"   # -> 137
dmesg | tail                                                        # kernel logs the OOM kill
# "Memory cgroup out of memory: Killed process ... (sh) ... anon-rss:..."
```

Exit **137** and a `Memory cgroup out of memory` line in `dmesg` are the two-part proof: the cap was enforced *by the kernel's cgroup*, not by Docker, and it killed *only* this cgroup's process. A learner who predicts "the container will use more than 20 MB, Docker doesn't really stop it" is wrong about where the enforcement lives — it is in the kernel, and it is absolute.

#### Misconception 3 — "`--memory=50m` means the container reserves/pre-allocates 50 MB"

It is a **ceiling, not a reservation**. The container uses as little as it needs and is killed the instant its cgroup's usage would exceed the cap. Nothing is set aside; a `--memory=50m` container using 3 MB is consuming 3 MB of host RAM, not 50. The number is the point at which the OOM killer fires, not an allocation. This matters for capacity planning: you can pack many low-usage containers with generous caps onto one host precisely because caps are limits, not reservations — until they all spike at once, which is the failure mode this misconception hides.

#### Misconception 4 — "a container that hits its CPU limit crashes / errors"

CPU limits **throttle**, they do not kill. A process over its CPU quota is simply descheduled until the next period — it runs slower, it does not die or error. (Memory is the opposite: over the memory cap you get killed, because you cannot "run a program more slowly" out of a RAM shortfall — the bytes must exist or they don't.) Confusing the two leads to the classic misdiagnosis: a service is *slow* under load and someone reaches for "raise the memory limit," when the symptom (slow, not dead, exit code 0 or still running) points at **CPU throttling**, not memory. The exit code and the symptom tell you which fence you hit: 137 + dead = memory; alive + slow = CPU.

### Lesson 3 — Images and layers: a stack of read-only diffs, content-addressed and cached

The third disguise is the filesystem. A container's `/` is not a copy of a disk — it is a **stack of read-only layers** union-mounted together, with one thin writable layer on top. Each layer is a **diff**: the set of files that instruction added, changed, or deleted relative to the layer below. An **image** is that stack of read-only layers plus metadata; a **container** is the image plus one writable top layer where its runtime changes go (and which is discarded when the container is removed).

Where do layers come from? **Almost every instruction in a Dockerfile that changes the filesystem creates one layer.** Consider:

```dockerfile
FROM python:3.11-slim        # layer 0..n: the base image's own layers (~130 MB)
WORKDIR /app                 # metadata-ish, tiny layer
COPY requirements.txt .      # a layer: adds one file
RUN pip install -r requirements.txt   # a layer: adds the installed packages (could be 50+ MB)
COPY . .                     # a layer: adds your source
CMD ["python", "app.py"]     # metadata only, no filesystem layer
```

Two properties make layers the whole game:

**1. Layers are content-addressed and cached.** Each layer has a hash derived from its contents and the instruction that built it. When you rebuild, Docker walks the Dockerfile top-down and, for each instruction, asks "do I already have a cached layer for this exact instruction applied to this exact parent?" If yes, it **reuses** the cached layer and moves on — instantly. The cache holds **until the first instruction whose inputs changed**; from that instruction down, *every* layer is rebuilt, because each layer's identity depends on its parent. This is why **instruction order is a performance decision.** If you `COPY . .` (all your source) *before* `RUN pip install`, then editing one line of source invalidates the `COPY` layer, which invalidates the `pip install` below it, and you reinstall every dependency on every code change — minutes wasted. If you copy `requirements.txt` and install *first*, then `COPY . .` last, a source edit invalidates only the final cheap copy; the expensive install stays cached. **The ordering that caches well and the ordering that reads naturally are different orderings, and knowing which is which is a real skill this module drills.**

**2. Layers are additive — a later layer cannot shrink an earlier one.** Because each layer is stacked read-only on the ones below, deleting a file does not remove its bytes from the image; it writes a **whiteout** entry in the upper layer that *hides* the file from the union view. The bytes are still down there, still shipped, still counted in the image size. This is the single most expensive image-size misconception, and it has a precise fix (Lesson 4's `RUN` combining and multi-stage builds).

You can read the whole stack with `docker history`, which shows every layer, the instruction that made it, and its size:

```bash
docker history myimage:latest
# IMAGE     CREATED BY                                      SIZE
# <hash>    CMD ["python" "app.py"]                         0B        <- metadata, no bytes
# <hash>    COPY . . # buildkit                             12kB      <- your source
# <hash>    RUN pip install -r requirements.txt # buildkit  48.3MB    <- the expensive layer
# <hash>    COPY requirements.txt . # buildkit              214B
# <hash>    WORKDIR /app                                    0B
# <missing> ... base python:3.11-slim layers ...            130MB
```

**The image is the sum of its layers' sizes; the build speed is decided by which layers the cache can keep; both are predictable from the Dockerfile before you ever run `docker build`.** That prediction is Lab M04-B.

#### Worked example — the delete that doesn't shrink

```dockerfile
FROM alpine
RUN dd if=/dev/zero of=/bigfile bs=1M count=100    # layer A: +100 MB
RUN rm /bigfile                                     # layer B: writes a whiteout, ~0 bytes freed
```

Predict the image size, then check:

```bash
docker build -t fat .
docker history fat
# <hash> RUN rm /bigfile     # ...   0B     <- the delete added ~nothing
# <hash> RUN dd ...100 MB    # ...   100MB  <- STILL HERE, still shipped
# <hash> FROM alpine         # ...   7.8MB
docker image inspect fat -f '{{.Size}}'    # ~113 MB, NOT ~8 MB
```

The image is **113 MB** even though the final container sees no `/bigfile` — the 100 MB lives in layer A, and layer B only hid it. The fix is to never let the bytes land in a committed layer in the first place — create and delete **within one `RUN`**, so the layer's *net* diff is empty:

```dockerfile
FROM alpine
RUN dd if=/dev/zero of=/bigfile bs=1M count=100 && rm /bigfile   # one layer, net ~0 bytes
```

Now `docker image inspect` reports ~8 MB. Same commands, same final filesystem, **13x smaller image**, because a layer commits its *net* diff and this one nets to nothing. Every "why is my image 1.2 GB when the app is 10 MB" bug is some version of this — build tools, apt caches, and downloaded tarballs deleted in a *later* layer than the one that created them.

#### Misconception 5 — "the image is the size of its final filesystem / deleting files shrinks the image"

The image is the **sum of every layer's diff**, and a layer's diff is frozen the moment the instruction commits. Files deleted in a later layer are hidden, not removed; their bytes ship in the earlier layer forever. `docker history` shows you exactly where the weight lives, and it is often in a layer whose files no longer appear in the running container at all. The final `ls /` size can be a fraction of the image size. The fix is never "add a cleanup layer"; it is "don't create the bytes in a separate, earlier layer" — combine into one `RUN`, or use a multi-stage build (Lesson 4) that copies only the finished artifact out.

#### Misconception 6 — "the layer cache keys on time, or I have to `--no-cache` to be safe"

The cache keys on **content and instruction**, not on wall-clock time. `RUN pip install -r requirements.txt` reuses its cached layer as long as (a) the instruction text is byte-identical and (b) the parent layer is unchanged and (c) for `COPY`/`ADD`, the copied files' contents are unchanged. It does **not** re-run just because a day passed — which is exactly why `RUN apt-get update` can serve you a *stale* package index from a cached layer weeks later (Lesson 4's reproducibility trap), and why people reach for `--no-cache` and then blame the cache for slowness. The cache is doing precisely what it promises: reuse when inputs match. Understanding the key (content, not time) is what lets you order a Dockerfile to hit the cache on purpose instead of fighting it.

### Lesson 4 — Reproducible "enough": where the container's promise leaks

The reason the industry adopted containers is the promise "**it works on my machine → it works everywhere**," delivered by shipping the whole userland in the image. The promise is real and it is enormous. It is also **leakier than the marketing admits**, and an engineer who trusts it blindly ships the non-reproducibility inside the image and calls it reproducible. This lesson is the descent under the word "reproducible" to find the three places it lies.

**Leak 1 — tags are mutable pointers, digests are immutable.** `FROM python:3.11-slim` looks like it pins a version. It does not. `3.11-slim` is a **tag** — a human-friendly name that the registry can (and does) repoint to a new image whenever a patch release ships. Build today and in three months from the *same Dockerfile* and `FROM python:3.11-slim` may resolve to different bytes. The genuinely immutable reference is the **digest** — the content hash of the exact image:

```bash
docker pull python:3.11-slim
docker inspect --format='{{index .RepoDigests 0}}' python:3.11-slim
# python@sha256:9c1f...   <- THIS is immutable; the tag is not
```

`FROM python@sha256:9c1f...` builds the same base forever; `FROM python:3.11-slim` builds *a* python:3.11-slim, whichever one the tag points at the day you build. `FROM python:latest` is the extreme: `latest` is just a conventional tag name with **no** guarantee of being newest or stable — it is the mutable pointer with the most-often-moved target, and pinning to it is pinning to nothing.

**Leak 2 — the build reaches out to the moving internet.** Even with a digest-pinned base, these lines pull *whatever is current at build time*:

```dockerfile
RUN apt-get update && apt-get install -y curl     # installs WHATEVER curl version is current
RUN pip install flask                             # installs WHATEVER flask is latest today
RUN curl -o tool https://example.com/tool         # WHATEVER that URL serves today
```

`apt-get install curl` with no version, `pip install flask` with no `==`, a `curl` of a URL with no checksum — each is a hole through which the outside internet's current state leaks into your "reproducible" image. The build succeeds identically today and produces a *different* image next month, silently. The fixes are version pins and lockfiles: `pip install flask==3.0.3` or, better, `pip install -r requirements.txt` where `requirements.txt` is a fully-pinned lockfile (`flask==3.0.3\nwerkzeug==3.0.3\n...`); `apt-get install curl=7.88.1-10` for apt; and a checksum verify for raw downloads. **A Dockerfile is a script that runs against the live internet; "reproducible" is only as true as the number of things in it that are pinned.**

**Leak 3 — the cache hides the leak from you.** Here is the cruelest part. Because the layer cache (Lesson 3) keys on the *instruction text*, `RUN apt-get update && apt-get install -y curl` keeps serving you the **same cached layer** for weeks — so *your* rebuilds look perfectly reproducible. The non-reproducibility only surfaces on a machine with a **cold cache** (a CI runner, a teammate, a fresh checkout), which re-runs the instruction against today's internet and gets different bytes. "It's reproducible, I rebuilt it ten times" is a statement about your warm cache, not about the Dockerfile. The gaming-resistant test in this module runs on a cold cache for exactly this reason.

**What "reproducible enough" actually means.** True bit-for-bit reproducibility (identical image digest from identical source, anywhere, anytime) is achievable but demanding. The pragmatic target is: **pin everything a human named** — base image by digest, OS packages by version, language packages by lockfile, raw downloads by checksum — so that a cold-cache rebuild on CI produces a *functionally identical* image. The skill is auditing a Dockerfile for the unpinned lines: each one is a place the outside world can change your image without changing your source. Lab M04-C is that audit, done as a linter you can run.

#### Worked example — the multi-stage build (small *and* more reproducible)

Multi-stage builds solve size (Lesson 3) and tighten reproducibility at once: build in a fat stage, copy only the finished artifact into a slim final stage, so the compilers, caches, and downloaded tarballs never reach the shipped image.

```dockerfile
# ---- build stage: has the toolchain, none of it ships ----
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                 # cached unless go.mod/go.sum change (Lesson 3 ordering)
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

# ---- final stage: just the binary on a minimal base ----
FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app         # copy ONLY the artifact; leave the 800 MB toolchain behind
ENTRYPOINT ["/app"]
```

The `golang:1.22` build stage is ~800 MB; the final image is the static binary plus a ~2 MB distroless base — perhaps **10 MB total**. The Go compiler, the module cache, and the source never ship. And because the final base is `distroless` (no shell, no package manager, no `apt`), there is *nothing in it that reaches the internet at build time* — the only variable inputs are `go.sum` (a lockfile, pinned) and the base digest. Size and reproducibility improve from the same structural move: **ship the artifact, not the factory.**

#### Misconception 7 — "the container makes my build reproducible"

The container makes the *runtime environment* reproducible — the same userland runs the same way on any host with a compatible kernel. It does **nothing** to make the *build* reproducible: `docker build` of an unpinned Dockerfile against the live internet produces different images on different days, and the container faithfully, reproducibly runs *whichever* non-reproducible thing you built. Reproducible **runtime** and reproducible **build** are different properties; containers give the first for free and the second only if you pin. Conflating them is how a team ships a `latest`-based, `apt-get install`-laden Dockerfile and believes the green "it runs" is evidence of reproducibility. It is evidence the runtime is reproducible; the build is a coin flip they haven't watched land.

#### Misconception 8 — "`latest` means the newest version"

`latest` is a **tag string with no special meaning to the registry** — it is newest only if the publisher happens to keep repointing it, which many do not, and some point it at a deliberately old "stable" release. It is a convention, not a guarantee, and it is *mutable*, so even when it does track newest, it changes under you between builds. Depending on `latest` couples your build to a pointer someone else moves on a schedule you don't control. The professional default is: pin the base by digest, name exact versions, and treat `latest` as "unspecified," because that is what it is.

### Lab M04-A — Open up a container from the host: prove it is a process

**Goal:** take a running container apart from the host and prove, with `/proc` and cgroup files, that it is one ordinary process wearing a PID namespace and a memory cgroup — not a machine. Predict every number *before* you read it.

#### Predict (on paper, before touching the keyboard)

Write down, with a one-line mechanistic reason for each:

1. You run `docker run -d --name box alpine sleep 1000`. Inside the container, what PID will `sleep` report (`docker exec box ps`)? On the **host**, will that same process appear in `ps`, and will its PID be the same number? Why can one process have two PIDs?
2. `uname -r` on the host prints `6.8.0-40-generic`. What will `docker run --rm alpine uname -r` print, and what does your answer prove about how many kernels are running?
3. You compare `/proc/<host-pid>/ns/pid` (the container process) against `/proc/1/ns/pid` (the host's init). Will the inode numbers match or differ? What does a *matching* inode vs a *differing* inode mean?
4. You run a second container with `--memory=20m` and a shell that appends a megabyte to a string in an infinite loop. Predict the **exit code**, and name *which component* kills it (Docker? the shell? the kernel?). Where does the enforcement physically live?
5. Predict what `cat /sys/fs/cgroup/.../memory.max` reads for the `--memory=20m` container — the exact byte number — and why it is that number and not `20000000`.

#### Build

```bash
# 1) Start a long-lived container and find its identity from BOTH sides.
docker run -d --name box alpine sleep 1000
HOSTPID=$(docker inspect -f '{{.State.Pid}}' box)
echo "host sees PID: $HOSTPID"
ps -o pid,comm -p "$HOSTPID"            # the container process, in the HOST process table
docker exec box ps -o pid,comm          # the SAME process, as PID 1, from inside

# 2) One kernel, proven.
uname -r
docker run --rm alpine uname -r         # identical string => same kernel

# 3) Read the namespace inodes and compare.
sudo ls -l /proc/"$HOSTPID"/ns/pid      # container's pid namespace inode
sudo ls -l /proc/1/ns/pid               # host init's pid namespace inode
#   different inode numbers == isolated pid namespaces

# 4) Walk INTO the container with nsenter, using only its host PID (no docker exec):
sudo nsenter -t "$HOSTPID" -p -m -u sh -c 'echo "hostname in here: $(hostname); pid1 is: $(ps -o comm= -p 1)"'

# 5) Provoke and read a cgroup memory kill.
docker run --name hog --memory=20m alpine \
  sh -c 'a=""; while true; do a="$a$(head -c 1000000 /dev/zero | tr "\0" x)"; done'
echo "exit code: $(docker inspect -f '{{.State.ExitCode}}' hog)"    # expect 137
CGDIR=$(dirname "$(grep -l . /sys/fs/cgroup/system.slice/docker-*.scope/memory.max 2>/dev/null | head -1)" 2>/dev/null)
# (or find it live for the running 'box' container:)
BOXPID=$(docker inspect -f '{{.State.Pid}}' box)
cat /proc/"$BOXPID"/cgroup              # 0::/system.slice/docker-<id>.scope
sudo dmesg | grep -i 'out of memory' | tail -3   # the kernel's OOM log line for 'hog'

# cleanup
docker rm -f box hog >/dev/null 2>&1 || true
```

#### Verify

- **PID duality (predict #1).** The container's `ps` shows `sleep` as **PID 1**; the host's `ps` shows the *same* process at `$HOSTPID` (some large number). One process, two PIDs, because the kernel tracks it in two PID namespaces at once. **Naming "one task, two namespace-local PIDs" earns the mark; "docker renumbers it" does not — the kernel holds both numbers simultaneously.**
- **One kernel (predict #2).** `docker run --rm alpine uname -r` prints the **host's** kernel version, byte-identical, because the container runs no kernel — it asks the one host kernel. If a learner predicted a different version, they were still modeling a container as a VM; the identical string is the disproof.
- **Namespace inodes (predict #3).** The container's `pid` inode **differs** from host init's — that *difference* is the isolation, and it is made of a number the kernel checks on every PID lookup. A *matching* inode would mean shared namespace (e.g. `--pid=host`). Full marks require "different inode = isolated namespace = the kernel filters this process's PID view," not "they're separate because Docker separates them."
- **The OOM kill (predict #4, #5).** Exit code is **137** (128 + SIGKILL's 9), the process is killed **by the kernel's cgroup OOM killer**, not by Docker and not by the shell — Docker only *wrote* `memory.max`; the kernel enforced it. `memory.max` reads **20971520** (= 20 × 2²⁰), not 20,000,000, because `20m` is 20 mebibytes (powers of two), the unit cgroups use. **The credit is naming the kernel cgroup as the enforcer and reading 137 as "SIGKILL from the cgroup OOM killer"; "the container crashed" without the mechanism scores zero.**
- A learner who predicted "Docker stops it / the container just uses more than 20 MB" has the enforcement in the wrong place. It is in the kernel, it is absolute, and `dmesg`'s `Memory cgroup out of memory` line is the proof.

### Lab M04-B — Predict image size and layer caching, then take the image apart

**Goal:** predict, *from the Dockerfile text alone*, (a) roughly how big the image will be and where the bytes live, and (b) which layers rebuild after a one-line source change — then build twice, read `docker history`, and diff reality against your prediction. This is the "reproducible environments, opened up" core: an image is a stack of diffs whose size and cache behavior you can compute before you build.

#### Predict (on paper)

You are given two Dockerfiles for the same Python app (`app.py`, `requirements.txt` with `flask==3.0.3`), differing only in **instruction order**:

**Dockerfile.slow**
```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
```

**Dockerfile.fast**
```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

Predict, with a mechanism for each:

1. On the **first** build, will the two produce images of (roughly) the **same size** or different sizes? Why? (Think: same layers, or same total bytes in a different order?)
2. You now edit one line in `app.py` and rebuild **both**. For each Dockerfile, list which instructions **rerun** and which are served from cache. Which build reruns `pip install`, and *why* does the ordering decide that?
3. In `docker history`, which single instruction will show the largest `SIZE` — `FROM`, `COPY . .`, or `RUN pip install`? Roughly what fraction of the image is the base vs the installed packages?
4. Consider this third Dockerfile:
   ```dockerfile
   FROM alpine
   RUN dd if=/dev/zero of=/big bs=1M count=100
   RUN rm /big
   ```
   Predict `docker image inspect -f '{{.Size}}'`: closer to **8 MB** or **108 MB**? Why does the `rm` not reclaim the space, and what one-line change would?
5. Predict what changes in prediction #2's answer if you edit `requirements.txt` (add a package) instead of `app.py`. Which Dockerfile now reruns `pip install`? (Both, or one?)

#### Build

**`app.py`**
```python
from flask import Flask
app = Flask(__name__)

@app.get("/")
def index():
    return "hello from a layer\n"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)
```

**`requirements.txt`**
```
flask==3.0.3
```

Build both, twice, and read the history:

```bash
# First build of each (cold): time them and record sizes.
docker build -f Dockerfile.slow -t app:slow . && docker image inspect -f '{{.Size}}' app:slow
docker build -f Dockerfile.fast -t app:fast . && docker image inspect -f '{{.Size}}' app:fast

# Edit one line of app.py, then rebuild both and WATCH the cache lines:
sed -i 's/hello from a layer/hello from a CHANGED layer/' app.py
docker build -f Dockerfile.slow -t app:slow .    # note "Using cache" vs re-run on pip install
docker build -f Dockerfile.fast -t app:fast .    # note which steps say "CACHED"

# Take the image apart: where do the bytes live?
docker history app:fast

# The delete-that-doesn't-shrink:
cat > Dockerfile.fat <<'EOF'
FROM alpine
RUN dd if=/dev/zero of=/big bs=1M count=100
RUN rm /big
EOF
docker build -f Dockerfile.fat -t app:fat .
docker image inspect -f '{{.Size}}' app:fat      # ~113 MB, not ~8 MB
docker history app:fat                            # the 100 MB layer is still there

# The one-line fix (net-zero layer):
cat > Dockerfile.thin <<'EOF'
FROM alpine
RUN dd if=/dev/zero of=/big bs=1M count=100 && rm /big
EOF
docker build -f Dockerfile.thin -t app:thin .
docker image inspect -f '{{.Size}}' app:thin      # ~8 MB
```

#### Verify

- **Same size, different cache (predict #1, #2).** On the *first* build both images are ~the same total size (same base, same packages, same source — layer *order* doesn't change total bytes). But after editing `app.py`: **`Dockerfile.slow` reruns `pip install`** (because `COPY . .` sits *above* it and the source change invalidates it, cascading down), while **`Dockerfile.fast` serves `pip install` from cache** (the source change only invalidates the final `COPY . .`). The build-time difference is dramatic — seconds vs a fresh dependency install. **Full marks name the cascade: "a changed layer invalidates every layer below it, so an early `COPY . .` drags `pip install` into the rebuild." "The fast one is just faster" without the cascade mechanism scores zero.**
- **Where the bytes live (predict #3).** `docker history` shows the largest layers are the **base image** (`python:3.11-slim`, ~130 MB) and the **`RUN pip install`** layer (Flask + deps, tens of MB); `COPY . .` is kilobytes. The base dominates. A learner who guessed "`COPY . .` is the big one" was modeling image size as source size, not base + dependencies.
- **The delete that doesn't shrink (predict #4).** `app:fat` is **~113 MB**, not 8 — the `rm` wrote a whiteout in a *later* layer and freed nothing in the earlier 100 MB layer, which still ships. `docker history` shows the 100 MB layer intact. The fix is combining create-and-delete into **one `RUN`** (`app:thin`, ~8 MB) so the layer's net diff is empty. **The mechanism — "a layer commits its net diff; a later layer can only hide, not remove, earlier bytes" — is the mark. "Docker didn't clean up" is not.**
- **Which change busts which cache (predict #5).** Editing `requirements.txt` invalidates the `COPY requirements.txt` layer in **`Dockerfile.fast`**, so *now fast also reruns `pip install`* — correctly, because the dependencies genuinely changed. `Dockerfile.slow` reruns it too. The lesson lands: `fast` caches `pip install` across *source* edits but *not* across *dependency* edits, which is exactly right — a dependency change *should* reinstall. Naming that the cache key for `pip install` is "the `requirements.txt` contents plus the instruction" is full credit.
- **Grade = prediction + mechanism.** Correct cache cascade with a slightly-off size estimate is full marks; exact sizes with "I don't know why order matters" is a partial.

#### Test sketch (`test_m04b.sh`)

```bash
#!/usr/bin/env bash
# Verifies the two mechanisms the learner predicted:
#  (1) ordering decides whether a source edit reruns pip install (cache cascade);
#  (2) a delete in a later layer does NOT shrink the image (layers are additive).
# Reasoning is graded from the predict sheet; this checks ground truth only.
set -euo pipefail

# BuildKit's non-TTY progress output (what `$(docker build ... 2>&1)` captures)
# prints each step's description and its CACHED/DONE status as SEPARATE lines,
# both prefixed with the same "#N" step id, e.g.:
#   #5 [3/5] RUN pip install -r requirements.txt
#   #5 CACHED
# Join lines sharing a "#N" prefix into one line per step so a single-line
# "<command>.*CACHED" grep still works regardless of progress format.
join_buildkit_steps() {
  awk '
    match($0, /^#[0-9]+/) {
      id = substr($0, RSTART, RLENGTH)
      rest = substr($0, RLENGTH + 1)
      if (!(id in seen)) { order[++n] = id; seen[id] = 1 }
      group[id] = group[id] rest " "
      next
    }
    { print }
    END { for (i = 1; i <= n; i++) print group[order[i]] }
  '
}

work=$(mktemp -d); cd "$work"
cat > app.py <<'EOF'
print("v1")
EOF
echo "flask==3.0.3" > requirements.txt

cat > Dockerfile.slow <<'EOF'
FROM python:3.11-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python","app.py"]
EOF
cat > Dockerfile.fast <<'EOF'
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python","app.py"]
EOF

docker build -q -f Dockerfile.slow -t t:slow . >/dev/null
docker build -q -f Dockerfile.fast -t t:fast . >/dev/null

# Edit source, rebuild, and detect whether pip install was cached.
echo 'print("v2")' > app.py

# FAST: pip install must be CACHED after a source-only change.
out_fast=$(docker build -f Dockerfile.fast -t t:fast . 2>&1)
joined_fast=$(printf '%s\n' "$out_fast" | join_buildkit_steps)
echo "$joined_fast" | grep -Eiq 'pip install.*CACHED|CACHED.*pip install' \
  || { echo "FAIL: fast Dockerfile re-ran pip install on a source-only change"; exit 1; }

# SLOW: pip install must RE-RUN (not cached) after the same change.
out_slow=$(docker build -f Dockerfile.slow -t t:slow . 2>&1)
joined_slow=$(printf '%s\n' "$out_slow" | join_buildkit_steps)
if echo "$joined_slow" | grep -Eiq 'pip install.*CACHED'; then
  echo "FAIL: slow Dockerfile cached pip install; ordering should have busted it"; exit 1
fi

# Additive layers: delete-in-later-layer does not shrink the image.
cat > Dockerfile.fat <<'EOF'
FROM alpine
RUN dd if=/dev/zero of=/big bs=1M count=100
RUN rm /big
EOF
cat > Dockerfile.thin <<'EOF'
FROM alpine
RUN dd if=/dev/zero of=/big bs=1M count=100 && rm /big
EOF
docker build -q -f Dockerfile.fat  -t t:fat  . >/dev/null
docker build -q -f Dockerfile.thin -t t:thin . >/dev/null
fat=$(docker image inspect -f '{{.Size}}' t:fat)
thin=$(docker image inspect -f '{{.Size}}' t:thin)
# fat must be > 90 MB larger than thin (the 100 MB layer still ships in fat).
[ "$((fat - thin))" -gt 90000000 ] \
  || { echo "FAIL: fat image was not >90MB larger than thin (delete unexpectedly reclaimed space)"; exit 1; }

echo "PASS: ordering controls the pip-install cache cascade; deleted bytes still ship unless removed in the same layer"
docker rmi -f t:slow t:fast t:fat t:thin >/dev/null 2>&1 || true
```

### Lab M04-C — Audit a Dockerfile for reproducibility leaks, then close them

**Goal:** the capstone. Given a Dockerfile that *builds and runs perfectly on your warm cache*, predict — before running anything — every place the outside internet can change the resulting image without changing the source, then build a linter that flags those leaks, and prove that a cold-cache rebuild is where the non-reproducibility surfaces. Graded like the reference C-labs: **full marks for correct mechanism even if you miss a leak or two; zero for "it builds, so it's reproducible."**

#### Predict (on paper)

Here is a Dockerfile that a teammate calls "reproducible — I've rebuilt it a dozen times, identical every time":

```dockerfile
FROM python:latest
RUN apt-get update && apt-get install -y curl
RUN pip install flask requests
RUN curl -o /usr/local/bin/tool https://example.com/tool && chmod +x /usr/local/bin/tool
COPY . /app
CMD ["python", "/app/main.py"]
```

Predict, with a mechanism for each:

1. **List every line that can produce different bytes on a different day or a different machine**, and say *what* varies in each. (There are at least four.)
2. The teammate rebuilt it a dozen times, identical every time. **Why is that not evidence of reproducibility?** What is their "dozen rebuilds" actually a statement about? (Name the mechanism from Lesson 3.)
3. On which machine will the non-reproducibility **first surface**, and why? (Warm cache vs cold cache — a CI runner, a new teammate.)
4. For each leak in #1, name the **one fix** that pins it: `FROM python:latest`, `apt-get install -y curl`, `pip install flask requests`, the raw `curl` download. What does each pin to?
5. `FROM python:3.11-slim` looks pinned. Is it? What is the difference between a **tag** and a **digest**, and which line would you write to pin the base immutably?

#### Build

**`repro_lint.py`** — a real, runnable reproducibility linter you will complete:

```python
#!/usr/bin/env python3
"""Flag reproducibility leaks in a Dockerfile: unpinned FROM tags, `latest`,
unversioned apt/pip installs, and checksum-free downloads. Each finding is a
place the live internet can change your image without changing your source.

Usage:  python3 repro_lint.py path/to/Dockerfile
Exit:   0 if clean, 1 if any leak found (so CI can gate on it).
"""
import re
import sys


def _join_continuations(lines):
    """Merge backslash-continued physical lines into logical lines so a
    multi-line RUN is inspected as the single instruction it actually is.
    Each logical line keeps the line number of its first physical line."""
    logical = []
    buf = []
    start = None
    for i, raw in enumerate(lines, start=1):
        text = raw.rstrip("\n")
        if start is None:
            start = i
        if text.rstrip().endswith("\\"):
            buf.append(text.rstrip()[:-1])
            continue
        buf.append(text)
        logical.append((start, " ".join(buf)))
        buf, start = [], None
    if buf:  # dangling continuation at EOF
        logical.append((start, " ".join(buf)))
    return logical


# A finding is (line_number, rule_id, human message).
def audit(lines):
    findings = []
    for i, raw in _join_continuations(lines):
        line = raw.strip()
        if not line or line.startswith("#"):
            continue

        # LEAK 1: FROM using a mutable tag (or :latest, or no digest).
        m = re.match(r"^FROM\s+(\S+)", line, re.IGNORECASE)
        if m:
            ref = m.group(1)
            if "@sha256:" not in ref:                      # not pinned by digest
                if ref.endswith(":latest") or ":" not in ref:
                    findings.append((i, "FROM-latest",
                        f"`FROM {ref}` pins to `latest`/no tag — a mutable pointer. "
                        f"Pin by digest: FROM name@sha256:..."))
                else:
                    findings.append((i, "FROM-tag",
                        f"`FROM {ref}` uses a tag (mutable). The registry can repoint it. "
                        f"Pin by digest for immutability: {ref.split(':')[0]}@sha256:..."))

        # LEAK 2: apt-get install without a pinned version (name=version).
        if re.search(r"apt-get\s+install", line):
            # crude: flag packages that have no '=' version pin
            pkgs = re.findall(r"install\s+(?:-y\s+)?(.*)", line)
            if pkgs and any(tok and "=" not in tok and not tok.startswith("-")
                            for tok in pkgs[0].split()):
                findings.append((i, "apt-unpinned",
                    "apt-get install without `pkg=version` — installs whatever is current. "
                    "Pin: apt-get install -y curl=7.88.1-10+deb12u5"))

        # LEAK 3: pip install without == version pins (and not from a lockfile).
        if re.search(r"pip\s+install", line) and "-r" not in line:
            args = line.split("pip", 1)[1]
            if "==" not in args:
                findings.append((i, "pip-unpinned",
                    "pip install without `==` and not from a -r lockfile — floats to latest. "
                    "Pin: pip install flask==3.0.3, or -r requirements.txt (fully pinned)"))

        # LEAK 4: curl/wget a URL with no checksum verification anywhere in
        # this logical instruction (continuation lines are already joined,
        # so `curl ... \` followed by `&& ... sha256sum -c \` is seen as one).
        if re.search(r"\b(curl|wget)\b", line) and re.search(r"https?://", line):
            verified = re.search(
                r"\b(?:sha256sum|sha512sum|sha1sum|shasum|md5sum)\s+(?:-c\b|--check\b)",
                line)
            if not verified:
                findings.append((i, "download-unverified",
                    "downloads a URL with no checksum — the server can serve different bytes. "
                    "Verify: echo '<sha256>  file' | sha256sum -c"))
    return findings


def main():
    if len(sys.argv) != 2:
        print("usage: repro_lint.py <Dockerfile>", file=sys.stderr)
        return 2
    with open(sys.argv[1], encoding="utf-8") as f:
        lines = f.read().splitlines()
    findings = audit(lines)
    for ln, rule, msg in findings:
        print(f"{sys.argv[1]}:{ln}: [{rule}] {msg}")
    if findings:
        print(f"\n{len(findings)} reproducibility leak(s). "
              f"Each is a place the internet can change your image without changing your source.")
        return 1
    print("clean: no reproducibility leaks found.")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

#### Verify

- **Enumerate the leaks (predict #1).** The four are: `FROM python:latest` (mutable tag, and the worst one), `apt-get install -y curl` (unversioned OS package), `pip install flask requests` (unpinned language packages), and `curl -o ... https://...` (unverified download). Your linter must flag all four. **Missing one leak but correctly explaining the *category* ("anything that reaches the live internet unversioned is a leak") is a partial-to-full; flagging all four with no mechanism ("the linter said so") is not the credential.**
- **Why "a dozen rebuilds" proves nothing (predict #2, #3).** The teammate's identical rebuilds are a statement about their **warm layer cache** (Lesson 3: the cache keys on instruction text, so `apt-get install curl` serves the same cached layer for weeks), **not** about the Dockerfile. The non-reproducibility surfaces first on a **cold cache** — CI, a new teammate, `--no-cache` — where each unpinned instruction re-runs against *today's* internet. **Naming "warm cache masks it; cold cache reveals it" is the central mark of this lab.** A learner who accepts "it built identically a dozen times" as proof has fallen for exactly the trap Lesson 4 names.
- **The fixes (predict #4, #5).** `FROM` → pin by **digest** (`python@sha256:...`), not tag; `apt-get` → `curl=<version>`; `pip` → `==` or a pinned `-r requirements.txt` lockfile; download → verify with `sha256sum -c`. And the tag-vs-digest distinction (#5): `python:3.11-slim` is a **tag** — a mutable pointer the registry can repoint; the **digest** is the content hash and is immutable. **Full marks require "a tag is a name that can move; a digest is content-addressed and cannot" — the same content-addressing idea as image layers (Lesson 3), now applied to the base.**
- **Grade = prediction + mechanism.** Correctly explaining *why* the warm cache lies, even while missing one of the four leaks, beats a linter that flags all four with the learner unable to say what a digest is. The mechanism — pinning closes the hole through which the live internet leaks into a "reproducible" image — is the gate.

## Assessment

**Design constraint: gaming-resistance.** A learner cannot pass by pasting a Dockerfile that builds, because the score lives in the **Predict artifacts** and the **mechanistic reasoning**, not in "the image ran." A build that works with no prediction trail caps low; a prediction with the right mechanism and an off number scores full. The container labs bite hardest here because *everything builds green on a warm cache* — "it works on my machine" is precisely the illusion this module exists to puncture, so "it works on my machine" earns nothing.

### Module exam — unseen scenario, predict before running

The learner is handed **one unseen scenario** drawn at random from a bank, each containing exactly one container-level defect or misdiagnosis, and must produce a four-part artifact:

**(a) Predict** the behavior *before running* — in namespace / cgroup / layer / reproducibility terms.
**(b) Open it up** — read the actual state (`docker inspect`, `/proc/<pid>/ns`, `docker history`, `docker image inspect`, a cold-cache rebuild, the linter) and locate the mechanism.
**(c) Fix** the defect or **correct the misdiagnosis**.
**(d) Prove** the fix with a measurement that *demonstrates the named mechanism was the cause* (a smaller `docker image inspect` size, a `CACHED` line, an exit code, a digest).

Example bank items (the learner sees one, unseen):

- **The 1.4 GB image:** a Dockerfile that `apt-get install`s a build toolchain, compiles, and `rm`s the toolchain in a later `RUN`, shipping a 1.4 GB image for a 12 MB binary. Predict *why* the `rm` freed nothing (layers are additive; a later layer hides, it doesn't remove — M04-B), locate the fat layer with `docker history`, fix with a **multi-stage build** that copies only the artifact, prove with `docker image inspect` showing ~15 MB.
- **The "my CI build is different from local" mystery:** an image that works locally and behaves differently on CI. Predict that the Dockerfile has unpinned reaches (`pip install` without `==`, `FROM :latest`) that the *local warm cache masks* and the *CI cold cache reveals* (M04-C). Locate with the linter and a `--no-cache` local rebuild reproducing CI's result, fix by pinning, prove the cold rebuild is now stable.
- **The rebuild that reinstalls everything:** a Dockerfile where every one-line code change triggers a full `pip install`/`npm install`, making the dev loop minutes long. Predict the cache cascade: `COPY . .` sits above the install, so any source edit invalidates the install layer (M04-B). Fix by reordering (copy the lockfile and install *before* copying source), prove with a rebuild showing the install step now `CACHED`.
- **The "container is a security sandbox" misdiagnosis:** someone runs untrusted code in a container believing it is as isolated as a VM. Predict and prove that the container shares the **host kernel** (`docker run --rm <img> uname -r` == host), so a kernel exploit is a *host* compromise (Misconception 1) — the isolation is namespaces + cgroups on one kernel, not a hardware boundary. Re-ascend to the real mitigation (gVisor/Kata/VM boundary, seccomp, non-root user, dropped capabilities) and explain *what* each adds that a plain namespace does not.
- **The OOM misread as a crash:** a container that exits 137 under load, blamed on "a bug in the app." Predict that 137 = 128 + SIGKILL and points at the **cgroup memory cap** OOM-killing it (M04-A), locate with `dmesg | grep 'Memory cgroup out of memory'` and the container's `memory.max`, fix by raising the limit *or* fixing the leak, and prove by reading the cgroup file and the kernel log — explaining why "it's an app crash" was never consistent with exit 137.
- **The CPU throttle misread as a memory problem:** a service that is *slow but alive* under load, with a proposal to raise its memory limit. Predict that alive-and-slow with exit 0 is **CPU throttling** (`cpu.max` quota, M04-A/Lesson 2), *not* memory (which kills). Prove with `docker stats` showing CPU pinned at the quota and memory well under cap, re-ascend to raising `--cpus` or optimizing the hot path, and explain why more memory would have moved nothing.

### Rubric (applied to the exam and echoed in each lab)

| Dimension | 0 — absent/gamed | 1 — partial | 2 — full |
|---|---|---|---|
| **Prediction present & prior** | no written prediction, or written after building | prediction present but vague ("it'll be big / it'll break") | specific, falsifiable prediction made before opening it up (a host PID, a size, a `CACHED`/re-run call, an exit code) |
| **Mechanism named in kernel/layer terms** | "containers are weird / Docker did something" | correct layer named, mechanism fuzzy | names the exact structure (namespace inode, cgroup `memory.max`/`cpu.max`, additive layer net-diff, cache cascade, tag-vs-digest, warm-cache masking) |
| **Prediction calibrated** | right outcome, wrong reason **(scores 0 — the gaming-resistant gate)** | reasoning right, numbers/size/cache-set off | reasoning right and quantitatively close (size within a category, correct set of rerun layers, exact exit code) |
| **Fix + proof** | fix with no evidence, or "it builds now" | fix + weak evidence | fix + a measurement that *demonstrates the named mechanism* (smaller `image inspect` size, a `CACHED` line, exit 137 + `dmesg`, a pinned digest, a green cold-cache rebuild) |

The load-bearing rule, identical to the reference module: **a right number with the wrong mechanism scores zero; a wrong number with the right mechanism scores full.** For a containers module this bites hardest on M04-C — "it built a dozen times identically" is a plausible-sounding reproducibility claim and still a zero, because the mechanism (a warm cache masking unpinned internet reaches) makes it evidence of nothing. You are grading the judgment trail, not the green build. The whole module's thesis in one grading rule: **"it works on my machine" is the disease, not the cure — so it earns no marks by itself.**

## Elle pacing notes (signals for the runtime)

- **Wall — "a container is a lightweight VM" is deeply held and every tutorial reinforces it.** The learner has read "containers vs VMs" diagrams for years and models a container as a tiny computer. **Reroute:** do not argue it abstractly — run `docker run --rm alpine uname -r` next to the host `uname -r` and let the *identical string* land the blow. One kernel, one version, asked by both. Then `docker inspect -f '{{.State.Pid}}'` + host `ps` shows the process in the host's own table. The disproof is two commands, and it must be *run*, not described. This is the module's foundational reroute; until "it's a process on my kernel" is felt, nothing else in the module is stable.
- **Wall — the PID duality reads as a contradiction ("how can it be PID 1 *and* 24817?").** The learner thinks a process has *one* PID. **Reroute:** frame it as the namespace's whole job — "PID is not a global fact about a process; it is a fact *relative to a PID namespace*, and this process is a member of two, so it has two." Tie back to M01: the PID was always a kernel bookkeeping number, and now there are two books. The inode comparison (`/proc/<pid>/ns/pid` differing from the host's) makes the "two books" concrete — the namespaces are literally different objects with different inode numbers.
- **Wall — the layer cache *confirms* non-reproducibility as reproducibility (M04-C's trap).** The learner rebuilds an unpinned Dockerfile, gets identical images every time on their machine, and concludes it is reproducible — the warm cache *reinforces* the misconception, exactly as localhost coalescing reinforced "one write = one read" in M02. **Reroute:** this is the module's most important reroute. Have them rebuild with `--no-cache` (or on a fresh machine / CI) and watch the unpinned lines re-run against today's internet. Same Dockerfile, cold cache, potentially different bytes. The variability *is* the proof, and the warm-cache rebuild was never evidence. Do not pre-warn them; let the dozen-identical-rebuilds feel like proof, then break it with the cold cache. The surprise is the instruction.
- **Wall — "I deleted the file, why is the image still huge?" eats an afternoon.** The learner adds a `RUN rm` cleanup layer and watches the image size not budge. **Reroute:** frame it as success — "you just proved layers are additive; the `rm` did exactly what it can do, which is hide, not remove." Show `docker history` with the fat layer still sitting there below the whiteout. Name it: a layer commits its *net* diff, and a *later* layer's net diff can't be negative against an *earlier* one. Then the one-line fix (combine into one `RUN`) and the multi-stage build land as obvious.
- **Signal — reading `--memory=50m` as a reservation is common and `struggle-productive`.** Many learners predict the container "takes" 50 MB. Letting them predict that, then reading `memory.max` as a *ceiling* and watching a 3 MB container use 3 MB, is a genuine click about limits-vs-reservations. Do not pre-correct; let the prediction be wrong and diff it against `docker stats`.
- **Signal — exit code 137 as "a crash" is near-universal on first sight and productive to correct.** The learner sees 137 and reads "crashed." The correction — 137 = 128 + 9 = killed by SIGKILL, and *which* SIGKILL (the cgroup OOM killer, per `dmesg`) — is a real forensic skill. Let them mis-read it once, then decode it; the decode sticks because the wrong first read set it up.
- **Accelerate — a clean M04-A (correct PID duality + one-kernel prediction + 137 decoded to the cgroup) plus a correct M04-B cache-cascade prediction lets the learner skip M04-C's linter *build* and submit only the audit of the leaky Dockerfile + the warm-vs-cold-cache reasoning.** If they can already name every unpinned reach and explain why a warm cache masks it, writing the linter adds little; take the reasoning and move on.
- **Signal — a learner who, unprompted, connects "the container shares the host kernel" to "so it's a weaker security boundary than a VM" is reading the module's Tier-2 thesis on their own and is ready to accelerate.** Same for a learner who ties "layers are content-addressed diffs" (M04-B) to "digests are content-addressed and immutable" (M04-C) without prompting — the two halves of content-addressing closing into one idea is the module's spine, and noticing it unprompted is the accelerate signal.
- **Bridge-back / bridge-forward:** M04 folds the whole course into one object. The container *is* M01's process (host PID, `/proc` entry), fenced by M03's shared-kernel reality (cgroups arbitrate the cores M03 taught you to schedule onto), serving M02's sockets (a `--publish` port is a net-namespace mapping). If a learner asks "so `docker run -p 8080:80` — where does the port live?", that is the net namespace + the M02 socket meeting, and it is the right question to let them chase. The course's re-ascent is here: they can now reason about a running containerized service's failure modes — is it OOM-killed (cgroup), CPU-throttled (cgroup), un-reproducible (unpinned build), or bloated (additive layers) — instead of trusting `docker run` as a black box.

## Three-tier reading

- **Tier 1 — material ground (verifiable facts).** A container is an ordinary Linux process on the host's **one** kernel, given a filtered view of PIDs/mounts/network/hostname by **namespaces** and a resource cap by **cgroups** — both enforced by that shared kernel, both readable from the host as files (`/proc/<pid>/ns/*` inodes, `/sys/fs/cgroup/.../memory.max`). The proof is reproducible: the container's process appears in the host's `ps` at a real PID while reporting PID 1 inside, and `docker run --rm alpine uname -r` returns the host's kernel version byte-for-byte, because there is no second kernel to ask (Lab M04-A). An image is a **stack of read-only, content-addressed layers**, each the *net diff* of one instruction; the image size is the sum of those diffs, so a file deleted in a later layer still ships in the earlier one (Lab M04-B, `docker history`), and the layer cache keys on instruction content, so instruction *order* decides whether a source edit reinstalls every dependency. "Reproducible" leaks wherever a build reaches the live internet unpinned — mutable tags, unversioned `apt`/`pip`, checksum-free downloads — and a **warm layer cache masks the leak** until a cold-cache rebuild on CI reveals it (Lab M04-C). None of this is opinion; it is documented kernel and build behavior you measured.

- **Tier 2 — what the field suppresses.** The abstraction the whole industry sells — *"just containerize it,"* *"it works on my machine so ship the image,"* *"the container isolates it"* — suppresses three things. First, **the isolation is namespaces and cgroups on one shared kernel, not a hardware boundary**, so a container is a *weaker* security boundary than a VM (a kernel exploit inside is a host compromise), yet "container" and "sandbox" are marketed as synonyms — the weaker guarantee is quietly dropped from the pitch because "lightweight" sells and "shares your kernel with untrusted code" does not. Second, **"reproducible" is sold as a property of containers when it is a property of *pinning*** — an unpinned Dockerfile is reproducible only in the sense that it reproducibly runs *whatever non-reproducible thing you built today*; the container gives reproducible *runtime* for free and reproducible *builds* only if you do the unglamorous pinning work, and the warm cache actively hides that you haven't. Third, and underneath both: **scale is bought by making the environment a disposable, interchangeable thing** — the container is designed so the machine it runs on, and the user it serves, are anonymous and replaceable, which is exactly what lets you run ten thousand identical copies and also exactly what makes "where did my data go, on whose kernel, under what cap" a question the abstraction is built to stop you from asking.

- **Tier 3 — sit with this (a question you cannot unknow).** You have now opened the container all the way up: it is a process you can find by PID on a kernel you share, holding a stranger's bytes in a memory region a cgroup will let the kernel kill without warning, on a filesystem assembled from layers you can prove still carry the things you thought you deleted. The whole design — namespaces so the process cannot see its neighbors, cgroups so it cannot starve them, images so it is identical and disposable everywhere — is a design for **not having to know**: not the host it lands on, not the neighbors it shares a kernel with, not the person whose login and location and query are sitting in that capped, killable memory. That not-knowing is what makes the thing scale, and it is genuinely load-bearing engineering, not negligence. But the deleted file still ships in the layer below; the "reproducible" build still reached out to an internet you didn't watch; the isolation you called a sandbox is a number the shared kernel checks and a kernel bug walks through. When you run ten thousand containers so that you never have to know any single one of them individually — what, exactly, are you responsible for having verified about the layers you shipped and the strangers whose data rides inside them, given that *nothing in the container, and nothing in Docker, forces you to verify any of it* — and if the answer is "nothing forces me," is "it worked on my machine" a thing you are still allowed to say?
